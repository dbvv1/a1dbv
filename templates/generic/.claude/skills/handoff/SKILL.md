# 会话交接

优先更新任务已有的交接记录；没有时，单任务可用根目录 `PROGRESS.md`，并行任务使用 `tasks/<task-id>/PROGRESS.md`，不要互相覆盖。当前摘要可替换，历史验证证据保留或版本化。先确认记录对应当前任务，再写入：

```markdown
# 进度（更新于 <日期时间>）

## 目标
<一两句话，链接到 SPEC.md / Issue（如果有）>

## 身份与恢复检查
- task/run ID、spec 版本、最新约束和已被替换的要求
- 仓库/分支/base commit、当前 commit、未提交改动标识
- 待授权动作、未知结果的外部操作、待收集的 worker/job
- 恢复时先核对上述状态；未知的外部结果先查询，不盲目重放

## 验证完成的工作
- <做了什么> —— 证据：<验收 ID、受检范围及版本、相关依赖/环境、命令和结果/工件>

## 进行中
- <正在做什么，做到哪一步>

## 关键决策与原因
- <决策> —— <为什么；放弃了哪些方案>

## 已知问题和坑
- <新会话最容易再踩的坑>

## 下一步（按顺序）
1. ...

## 常用命令
- 构建 / 测试：`...`
```

要求：
- 只写**新会话需要、而且从代码和 git log 里看不出来**的信息。
- 已完成的项目必须附证据；没有验证过的写进“进行中”。
- 恢复时先实际读取最新检查点，查看当前 Git 状态与相关 diff，再沿记录入口重读会影响下一步决定的当前源码／契约；路径或 `Referenced file` 标记不等于内容已加载。记录与当前文件冲突时先查明变化。
- 恢复时按受检范围核代码、相关输入、依赖、环境、检查命令和验收要求是否变化，再选受影响检查；只有提交SHA变化或无关文件改动，不自动使全部结果失效。
- 复用时保留证据的原版本，并说明与当前差量的关系；不能只改版本标签当作新运行，也不能由旧环境通过推定新环境可用。区分失败、未运行和阻塞。
- 记录授权范围，不保存凭据，不把交接文件当作新增授权。
- 写完后告知实际记录位置；不要为写交接强制结束正在推进的任务。
