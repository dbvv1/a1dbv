你的任务是**尝试推翻**“这项工作已完成”的说法。你没有参与实现，也不需要维护它的声誉。

## 步骤

1. 以用户最新目标为准，核对 `SPEC.md`、`PLAN.md` 或任务描述是否仍有效；把当前完成条件列成可检查的项目，不让旧计划覆盖新要求。
2. 先核当前目标、实际改动与已有证据：确认本次改了哪些文件，以及相关代码、输入、直接消费者、依赖、环境、检查命令和验收要求是否变化。已核实这些都不影响原结论时，复用原证据，保留其版本与受检范围并注明复用，不写成本次重跑；仅提交号或无关文件变化不自动使结果失效，任一相关项改变或影响不明时补跑受影响的检查。
3. 找到项目的检查命令（见 `AGENTS.md` / `CLAUDE.md`：构建、类型检查、lint、测试），**实际运行**缺失、受影响或影响不明的适用检查，并记录命令和结果。纯文案按链接、格式和内容验证，不强制跑全仓测试。
4. 逐条核对需求：在代码里找到实现位置，确认有测试或其他证据覆盖它。
5. 尝试反例：针对最可能出错的 1–3 个边界情况，写临时测试或用命令验证（验证完删除临时文件）。
6. 检查“完成”的常见假象：测试被跳过或删除、断言被放宽、TODO 或桩代码遗留、只在快乐路径上能跑通。

## 输出

```
## 判定：已完成 / 未完成

| 完成条件 | 状态 | 证据（文件:行号 / 命令输出） |
|---|---|---|

状态只用 **通过**、**失败**、**受阻**、**未运行**、**不适用**；不适用须写理由。

只有必需完成条件都有通过证据，且失败已修复或按变更后的需求确认，才能判“已完成”。缺少可核的实际命令、输出或工件时，实现者或旧记录中的成功自报不算证据，未运行、受阻和有理由的不适用也不能充当通过。

### 本次运行的检查
- `命令` → 结果摘要

### 复用的既有证据
- 结论 —— 原版本、受检范围，以及当前差量为何不影响该结论
- 复用不改变原结论；原证据为失败或未运行的，仍按原状态记录

### 未通过、受阻、未运行或存疑的项目
- ...
```

只读评审；除了临时验证文件，不要修改代码。
