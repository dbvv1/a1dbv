## 评级与证据体系

### 评级（借鉴 ThoughtWorks 技术雷达）

| 标记 | 含义 |
|---|---|
| ✅ **采用** | 证据充分、风险可控，推荐默认使用 |
| 🧪 **试用** | 值得在真实项目中小范围试，可能有明显收益 |
| 👀 **评估** | 有潜力但不成熟、证据不足或争议大，先观察 |
| ⛔ **暂缓** | 有明显问题（维护停滞、风险、性价比低），不建议新采用 |

### 证据等级

| 标记 | 含义 |
|---|---|
| **[一手]** | 直接阅读了官方文档、源码、changelog、规范原文或官方博客 |
| **[社区]** | 使用者、维护者的公开经验与讨论；注明单例或多份独立来源，标签本身不表示共识 |
| **[研究]** | 论文、系统性调查或本仓库有明确方法的分析；注明外部研究/本仓库分析，以及实际阅读或验证范围 |
| **[二手]** | 只有搜索摘要或单一第三方文章，未能读到原文，需谨慎 |
| **[经验]** | 业内常见做法或作者经验判断，没有单一出处 |

这些标签标识来源或论证类型，**不是从高到低的可信度分数**。官方文档可确认产品契约，不能自动证明生产力；源码可确认实现路径，不能替代运行结果；本仓库分析不能借用论文标签的权威。使用 `[研究：本仓库分析]` 时写出推理依据；采用建议通常标 `[经验：采用判断]`。历史标签逐条维护，不因本次定义澄清而视为全仓已复核。

## 本轮审查与验证状态（2026-10-10）

本轮新增 20–23，复核部分高影响技术说法；来源与未覆盖范围见 [审查记录](research/2026-10-10-audit.md)。社区项目与 GitHub 原帖另见 [23](23-community-workflows.md)。历史日期不代表本轮重复验证。

**来源类型与验证状态分开记录**：一手来源可能只证明“厂商这样写”，社区原帖可能只是作者自述；二者都不等于本仓库已经实测。新内容标明“原文已读 / 仅摘要 / 文档确认未实测 / 实测有产物 / 待复核”，并写适用范围。

- 易变事实（价格、版本、权限、API、排行榜）附检查日期、直接来源与适用版本；GitHub 尽量用固定提交。
- 实验附输入、配置、运行脚本、逐次结果、失败记录和验收产物；公开摘要不能替代原始记录。[19](19-experiments.md) 的历史产物待补齐。
- 工程建议明确标注推论或经验，不借来源的权威替自己的建议背书。
- 访问失败记为未验证，不能据此宣布原结论错误；未读原帖不能宣称社区共识。
- 社区调查同时看 README、实际 Skill/源码、失败 Issue、维护者反馈与交付案例；区分作者推广、使用者报告和独立复现。

长期研究目标、判断原则与下一步线索见 [研究路线](research/README.md)。这些记录服务于具体判断，不要求每篇文档都套用额外模板。

## 维护流程

1. **跟踪一手源和社区**（见 [12-resources](12-resources.md#5-如何持续跟进)）：每周看一次 Claude Code、Codex、Gemini CLI 的 changelog 和 HN 热帖；每月更新一次 [13 前沿雷达](13-frontier-radar.md)。
2. **新东西先进 Backlog**：写进 `12-resources.md` 的“待验证”列表，验证后再进正文。
3. **每条结论配证据**：没有来源的不写；只有二手来源的标出来。
4. **定期删除**：被取代的工具、过时的数字直接删掉，不保留“历史版本”（git 历史里有）。
