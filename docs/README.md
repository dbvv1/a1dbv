## 评级与证据体系

**判断一个结论能不能直接用，看两件事：页面成熟度（能否照做）和证据等级（结论怎么来的）。** 证据标签之间没有高低之分，成熟度才有级别；成熟度见下一节，本节定义采用评级和证据标签。

### 评级（借鉴 ThoughtWorks 技术雷达）

| 标记 | 含义 |
|---|---|
| ✅ **采用** | AI coding 主干的核心推荐已有真实采用，且新读者按页实际做成；只覆盖注明的任务与条件，不表示整页所有功能或模型收益已验证 |
| 🟡 **待补实做／采用** | 已有答案，但新读者实际做成或核心推荐的真实采用仍待补 |
| 🧪 **试用** | 值得在真实项目中小范围试，可能有明显收益 |
| 👀 **评估** | 有潜力但不成熟、证据不足或争议大，先观察 |
| ⛔ **暂缓** | 有明显问题（维护停滞、风险、性价比低），不建议新采用 |

AI coding 主干的 ✅／🟡 与[首页读者入口](../README.md#按目标开始阅读)一致；工具候选保留 🧪／👀 等评级。下文 L1–L4 与原核实日期记录历史内容成熟度，不据此推定历史页面已完成运行验证；游戏分支沿用既有细则。

### 证据等级

| 标记 | 含义 |
|---|---|
| **[一手]** | 直接阅读了官方文档、源码、changelog、规范原文或官方博客 |
| **[社区]** | 使用者、维护者的公开经验与讨论；注明单例或多份独立来源，标签本身不表示共识 |
| **[研究]** | 论文、系统性调查或本仓库有明确方法的分析；注明外部研究/本仓库分析，以及实际阅读或验证范围 |
| **[二手]** | 只有搜索摘要或单一第三方文章，未能读到原文，需谨慎 |
| **[经验]** | 业内常见做法或作者经验判断，没有单一出处 |

这些标签标识来源或论证类型，**不是从高到低的可信度分数**。官方文档可确认产品契约，不能自动证明生产力；源码可确认实现路径，不能替代运行结果；本仓库分析不能借用论文标签的权威。使用 `[研究：本仓库分析]` 时写出推理依据；采用建议通常标 `[经验：采用判断]`。新页和已改写的页面把标签写在节末“依据”行；旧页逐句标注的标签含义相同。

## 维护流程

**新结论先进 Backlog，验证后再进正文；易变事实写清核实日期、来源、适用版本与复核触发条件，过时内容直接删。** 五步流程：

1. **跟踪一手源和社区**（见 [12-resources](12-resources.md#5-什么变化值得继续跟进)）：每周核对 Codex、Claude Code 的 changelog 与官方文档，按建议变化同步专题与 [13 前沿雷达](13-frontier-radar.md)，注明版本和日期；Gemini CLI、社区原帖按具体研究问题补查，没有改变建议的新闻不进正文。
2. **新东西先进 Backlog**：写进 `12-resources.md` 的“待验证”列表，验证后再进正文。
3. **每节结论配依据行**：没有来源的不写；只有二手来源的标出来。
4. **把复核落到影响推荐的动态事实**：价格、版本、许可、地区与平台规则，除上述核实日和来源外，在已有研究记录中补“下次复核日期或触发条件、对建议的影响”；不用为每条稳定事实建表。换型号／套餐／用途或准备采用、发布时提前查，访问失败保留“待复核”，不能把尝试日期当成原文已核实。参照[游戏阶段 F 动态事实表](research/2026-10-14-game-wp2-2d-assets.md#9-阶段-f-b图像动态事实表)，正文只同步会改变选择的结论，避免复制多套价格和许可清单。复核日期是维护计划，不代表已建立自动监控。
5. **定期删除**：被取代的工具、过时的数字直接删掉，不保留“历史版本”（git 历史里有）。
