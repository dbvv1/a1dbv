# 运行细则

> 只放操作步骤：Git 发布与恢复（§1）、分支与交付检查（§2、§2.1）、本地中转（§2.2）。执行规则以[运行手册](LONG-TERM-PLAN.md)为准；2026-10-22 删除了旧的统计口径、角色、成熟度、工作线、节奏等第 3–11 节（已并入运行手册或作废，见 Git 历史）。

## 1. 发布与恢复

- **首选 `git push`**：授权和写认证可用时，本地提交后整批推送；shell 缺写认证则用既有授权连接器，不反复试推、不自行新增凭据；
  提交身份元数据与远端写认证分开处理：需要本地 commit 时，用本次命令的 `-c user.name=… -c user.email=…` 如实标识实际执行者，不改全局配置、不冒用用户或厂商身份。缺作者本身不是用户授权缺口，也不需要新建凭据。[一手，2026-10-17（UTC+8）核实：[身份配置](https://git-scm.com/docs/git-config#Documentation/git-config.txt-username)、[命令级配置](https://git-scm.com/docs/git#Documentation/git.txt--cltnamegtltvaluegt)] [经验，2026-10-17（UTC+8），Git 2.47.3] 隔离临时仓库、`user.useConfigOnly=true` 禁用身份猜测时，未配置身份的 commit 退出128，本次命令提供执行者身份后退出0且未持久化身份；仅证明本地提交行为，未验证 push 授权或认证。
- **增量发布**：固定最新远端 `main` SHA，只上传变化文件；已确认成功的对象可复用，在工具上限内批量写入，最后以该 SHA 为预期旧值更新分支（CAS）。发布前发现基线已前进，或更新被拒后确认远端旧值已变，先停发、整合并按手册§7重验受影响路径；其他拒绝按失败恢复核因，不强推；
  TASKS 交接超过约10行时，后续移出的原文按归档当日（UTC+8）追加至既有 `archive/` 的当日日档；旧 `completed-through-2026-10-16.txt` 保持原样，不按文件名重切历史。新日档创建时同步 TASKS 与既有归档索引的链接，增量发布只提交变化文件，避免反复上传封存历史。
- **失败恢复**：记录失败阶段和成功回执；对象创建成功不等于分支发布成功。超时、断连或 `user cancelled` 只表明结果待核，不足以判定人工取消或审批超时。先读远端分支、目标提交及文件内容；确认已生效就不重发，未生效才从断点恢复。明确拒绝权限时停止该动作，不换路绕过；
- **工作目录不可见**：先在已知可用目录核 shell 与指定任务路径；不能据此猜测用户删除、权限变化或整台机器离线。核远端固定提交后可在新目录恢复已发布副本，不覆盖旧路径；未取回的原始记录／未发布断点仍标不可复查，不把恢复文稿当重新实测。10-24 01:05（UTC+8）曾遇旧路径不可见，已由远端 `0a3e275` 恢复；原因未核，不归为审批等待。
- **续接本地操作**：开始操作前保存预期分支和本地 HEAD；恢复时及暂存／提交前逐一核对，不符或缺失就保留改动、先对账，不把当前值直接重记为旧操作的预期值。连接器发布可能生成不同 commit SHA，结合发布回执、tree 与内容确认原成果；已发布且没有实质增量时，不重复追加状态或提交。这些检查不是并发锁，仍须串行整合；发布前逐个核对新生成提交的直接父与构造时指定值、最终 tree 与受检树一致。分支快进检查预期旧 SHA 是否为目标提交的祖先，允许中间有多次提交：`git merge-base --is-ancestor <旧SHA> <目标SHA>` 返回 0 表示是祖先，1 表示不是，其他非零值表示检查出错；远端旧值核对（CAS）是独立条件，仍须保留。见 [20 的恢复边界](../20-codex-long-horizon.md#9-超时后动作究竟发生了吗)；
  [一手，2026-10-18（UTC+8）核实：[快进定义](https://git-scm.com/docs/git-push#_note_about_fast_forwards)、[祖先检查](https://git-scm.com/docs/git-merge-base)、[旧值核对](https://git-scm.com/docs/git-update-ref)] [经验，Git 2.52.0] 隔离无远端仓库中，两跳祖先检查返回 0、分叉检查返回 1，匹配旧值更新成功、陈旧旧值更新失败且 ref 不变；仅验证本地 Git 行为，未验证连接器、发布权限或远端更新。
- **无人值守时**：开跑前确认发布授权、认证和审批路径；确需人工确认时保存断点，转做不依赖该确认的工作。汇报分别写远端 SHA、内容核对和 hosted CI 状态；
- **研究与发布分开**：研究并行，合入和发布串行、小批量进行。[经验，单仓单例] `c9e71c7` 发布前整合了前进到 `244bc9f` 的远端；`7a475db` 的发布回执核实了分支更新和五文件内容一致，hosted CI 未运行。这些记录支持恢复步骤，不证明失败率下降。

## 2. 分支与交付树检查

- **分支**：每个执行者用自己的分支，例如 `<执行者>/<主题>`；小步提交，合入前读取远端 `main`；检查 fetch refspec，若未跟踪 `main`，用 `git fetch origin main` 后立即固定 `FETCH_HEAD` 的 SHA，不把旧 `origin/main` 当最新。整合并按手册§7重验受影响路径后再发布。不强推，不改写已发布的历史，不覆盖他人的提交；
- **检查实际交付树**：核对新增与未跟踪文件，仅暂存本次内容并跑 `git diff --cached --check`；检查必须对应将要发布的内容。任务独占且文件一致的工作树直接验证，不强制导出／重建。只有并行脏树混入无关内容或依赖Git对象的测试需要隔离时，才使用真实Git工作树或适合该检查的隔离副本；不要对依赖Git对象的检查使用无Git归档。整合后按手册§7复用未变结果、补受影响检查，不重复制作同树证明。


### 2.1 跨执行者的发现与交接

**2026-10-21用户临时分工**：B权限恢复前，B推到分支的成果由A固定SHA复核、保历史整合并发布；已被其他发布先行合入则只核结果，不重复合入，不据发布成功推定权限恢复。

以下是本仓库对 Git 分支和 GitHub PR 的使用约定，适用于人及任何 Agent，不依赖特定模型或聊天转发：

- **用 git 自己合入，不走 PR（2026-10-20 用户决定）**：
  1. 在自己的分支完成一个项目，按手册§7完成一次全新上下文独审或复用有效独审；TASKS自己的认领与结果行纳入同次受检交付，不单独提交；
  2. 按§2核fetch refspec并固定最新远端SHA，将其合并进自己的分支（不 rebase 已推送的提交），解决冲突时保留他人的 TASKS 行；
  3. 按手册§7完成适用检查、公开文件与提交扫描，读一遍 `git diff origin/main`；
  4. `git push origin HEAD:main`。只允许快进；拒绝后先核原因，确认是 `main` 前进才回到第 2 步。认证缺失、明确权限拒绝及结果不明按§1处理，不把所有拒绝都当并发，不强推；
  5. 推送回执明确快进成功即可记录；结果不明或连接器重建提交时，再核远端目标与内容。CI状态按需读取，无运行记录不称通过，不因发布成功再重跑测试，不另交状态提交。

  已开的草稿 PR：把对应分支按上述步骤合入后不再处理，能关闭就关闭，关闭需要审批也不阻塞。跨执行者复核改由阶段审计抽查。

- **主动发现**：每次开工、恢复、选择下一单元和合入前，读取最新远端 `main`、未合入分支及开放 PR；不能只看 `main` 的 TASKS。更新项目板水位时重新核开放PR并记录真实采样截止，不沿用开工时的旧列表；先核对 `git config --get-all remote.origin.fetch`；可用 `git fetch origin '+refs/heads/*:refs/remotes/origin/*'` 更新远端跟踪分支（不改本地工作分支），用 `git branch -r --no-merged origin/main` 找候选，再用 `git show <远端分支>:docs/collaboration/TASKS.md` 看认领及交接。远端已删除分支以 `git ls-remote --heads origin` 核对，PR 状态从托管平台读取；读不到时记录发现范围，不假定没有别人工作。
- **分工与认领**：同页单作者、独立文件并行，各执行者只合入自己的成果；跨执行者质量由阶段审计抽查，不设专门整合者。开工核实际活动及旧断点，认领不证明正在执行。TASKS只在合入提交里改自己的行，合并记录问题、起点SHA、分支、文件和结果；不单独提交认领，不覆盖他人行。每位执行者待合入成果最多2份，先收口积压再开新项目。
- **固定证据复用**：受检内容、依赖与行为未变时复用已有来源、独立评审和检查记录；有新改动、反证或未覆盖风险才追加调查。与最新main整合后按手册§7补验受影响路径，完整入口仅用于该节规定的范围；提交SHA变化本身不使结果失效。新SHA重建保留本地到远端映射，以tree、父链及变化文件确认交付，不把原本地SHA冒称远端SHA。
- **真实搭建／运行限时（2026-10-21用户决定）**：单次最多2小时；受阻记录原因与下一输入，转可执行项目，不继续扩展探针。临时分区满时先核容量；可在已有授权工作区为本次运行指定临时目录（如进程级TMPDIR），保留原证据，不把存储故障记成待授权，也不广泛清理其他任务目录。短服务遇跨执行调用的非权限连接失败，可先在同次调用内启停、请求与回收核实；不据一次ECONNREFUSED猜为权限或产品故障，不改网络权限。若同次请求可达而云端浏览器不可达，先核目录是否可见及是否同一运行宿主；确认属于dot云端的原生终端可正常启动同一公开预览，再以浏览器实操确认，不能仅凭服务启动就记客户端通过。结果JSON保读者摘要，原始输出留工作区；中转离线先做P41资料，恢复先冒烟，再P38／P44。
- **受阻只停依赖动作**：先保存成功对象、未发布成果和下一具体动作，再接续有授权、无文件冲突的内容或只读研究。授权／输入未变化，不重复被拒动作；没有新状态，不提交“仍在等待”或要求用户转述。等待、实际作业和验证范围分报；并行或一次发布成功不证明提效。
- **通知边界**：Git 保存可复查的状态，旧PR仅作历史提案与评审线索；它们不保证唤醒另一会话。上述检查由仍在运行或按既有安排恢复的执行者完成；恢复时读取项目、断点及下一步并继续已授权工作，不把既有调度的正常续接再列为用户审批项。对已结束的执行任务补交接文字不等于重新启动；须核新的开始回执，未确认只记待接续，不报正在执行。没有活动任务时如实记等待／结束及恢复条件；未配置并验证事件接收端时，不声称 webhook 已送达、持续在线或全天自动执行，也不因本约定新增凭据、调度或权限。[一手，2026-10-17：[GitHub PR](https://docs.github.com/en/pull-requests/reference/pull-requests)、[webhook](https://docs.github.com/en/webhooks/about-webhooks)]

### 2.2 本地模型协作：普通生产与专项验证

**2026-10-25 用户扩大授权，替换“只作被测对象、不能研究写作、DSH暂不用”的旧限制。** A和B均可把任务内的公开资料探索、源码调查、方案候选、明确规格实现、资源处理脚本、测试、文档初稿和整理工作交给本机已配置的DSH＋DeepSeek、Claude Code＋DeepSeek或ZCode。优先委派目标明确、可独立实施和检查的工作；复杂任务也可拆出清楚范围，不要求每项都先证明模型适用或重新测试联通。

**默认投入与Workflow（10-25用户补充）**：本项目使用现有DSH＋DeepSeek、Claude Code＋DeepSeek、ZCode＋GLM 5.3／GLM 5.3 Flash通道时，不设人为模型调用次数或token节省预算，按质量、完整性与有效结果投入。这是本项目使用约定，不是供应商永久免费的价格承诺，也不授权新收费服务。普通委派默认使用该平台原生Workflow组织实施和独立验证，失败时针对性修复；明确禁工具的正式实验保留专用入口，不机械套Workflow。沿实际限流和资源占用调度，不为少调用跳过必要工作，也不重复无新信息的调用；已验证入口不反复探针。

**分工**：dot保方向、关键取舍、任务拆分、最终整合和发布质量；本地Codex可组织模型工作、检查产物、修正常规调用和集成问题，不再限定为原样转发脚本。实际模型负责被委派的工作。调用方式复用本机已维护的协作入口与正常Workflow；P79禁工具CLI仅用于其专项测试，不能套给普通开发。按本机现行配置选上述通道，不凭客户端名猜模型，不公开连接信息；常规任务无需固定模型先后顺序，换通道按质量与可用性选择并记录，正式比较仍保指定模型。

派发只需目标、必要来源、独占文件／分支范围和期望产物；复用现有任务记录，不强制新脚本、批次表或hash证明。多个独立任务可并行，避免同一文件、运行实例和输出目录多方写入。拿到结果就按§7做适用检查，失败才针对性修复；不要重复派发已经完成的工作，或将每次普通协作升级成benchmark。

**公开与权限边界**：仅提供任务所需且允许交给对应服务的材料，不把公司代码、私人历史、凭据或无关文件交给模型；公开仓库内容在回传／提交前检查事实、代码、来源和敏感信息。扫描覆盖实际产物，新增未跟踪文件也应纳入；审查不能只看模型自报。沿既有配置使用的模型无需逐项申请，既有用户成本约定继续适用，不因“预算字段未填”停工；新收费服务、凭据、额外账号访问或破坏性操作仍按实际授权处理。放开工作种类不等于放开这些动作。

**跨账号接续**：网页dot与本机客户端属于不同账号时，不假定能按thread ID读写对方会话。复用双方已可访问的Git仓库：委托方在既有TASKS／任务分支描述公开可交付的目标，由独立的本地协作会话取回并派给模型，结果回同任务分支，由原负责人接收。本机登录账号与研究职责分开；B的任务由本地协作会话承接，A的AI coding主任务不负责B的排队、盯执行或内容验收，也不要求A为每份B产物重审。接收者缺失时记待接续，不默认落给A主任务。仓库不得保存密钥、私人会话或本机路径。2026-10-25用户已授权独立本地接收端自动取任务：入口为[local-jobs](local-jobs/README.md)，由该会话的原生定时唤醒读取main并接续，实际启用状态以本机计划为准。Git推送不等于已接收；认领、产物与待验结果回原任务。保留宿主账号和跨聊天权限，不暴露本机端口。
