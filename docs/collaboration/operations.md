# 运行细则

> 2026-10-17 从[运行手册](LONG-TERM-PLAN.md)移出，开工、恢复和选择下一单元时读第 2.1 节；发布、交付检查或统计运行信号时再读对应章节。

## 1. 发布与恢复

- **首选 `git push`**：授权和写认证可用时，本地提交后整批推送；shell 缺写认证则用既有授权连接器，不反复试推、不自行新增凭据；
  提交身份元数据与远端写认证分开处理：需要本地 commit 时，用本次命令的 `-c user.name=… -c user.email=…` 如实标识实际执行者，不改全局配置、不冒用用户或厂商身份。缺作者本身不是用户授权缺口，也不需要新建凭据。[一手，2026-10-17（UTC+8）核实：[身份配置](https://git-scm.com/docs/git-config#Documentation/git-config.txt-username)、[命令级配置](https://git-scm.com/docs/git#Documentation/git.txt--cltnamegtltvaluegt)] [经验，2026-10-17（UTC+8），Git 2.47.3] 隔离临时仓库、`user.useConfigOnly=true` 禁用身份猜测时，未配置身份的 commit 退出128，本次命令提供执行者身份后退出0且未持久化身份；仅证明本地提交行为，未验证 push 授权或认证。
- **增量发布**：固定最新远端 `main` SHA，只上传变化文件；已确认成功的对象可复用，在工具上限内批量写入，最后以该 SHA 为预期旧值更新分支（CAS）。发布前发现基线已前进，或更新被拒后确认远端旧值已变，先停发、整合并重验；其他拒绝按失败恢复核因，不强推；
  TASKS 交接超过约10行时，后续移出的原文按归档当日（UTC+8）追加至既有 `archive/` 的当日日档；旧 `completed-through-2026-10-16.txt` 保持原样，不按文件名重切历史。新日档创建时同步 TASKS 与既有归档索引的链接，增量发布只提交变化文件，避免反复上传封存历史。
- **失败恢复**：记录失败阶段和成功回执；对象创建成功不等于分支发布成功。超时、断连或 `user cancelled` 只表明结果待核，不足以判定人工取消或审批超时。先读远端分支、目标提交及文件内容；确认已生效就不重发，未生效才从断点恢复。明确拒绝权限时停止该动作，不换路绕过；
- **续接本地操作**：开始操作前保存预期分支和本地 HEAD；恢复时及暂存／提交前逐一核对，不符或缺失就保留改动、先对账，不把当前值直接重记为旧操作的预期值。连接器发布可能生成不同 commit SHA，结合发布回执、tree 与内容确认原成果；已发布且没有实质增量时，不重复追加状态或提交。这些检查不是并发锁，仍须串行整合；发布前逐个核对新生成提交的直接父与构造时指定值、最终 tree 与受检树一致。分支快进检查预期旧 SHA 是否为目标提交的祖先，允许中间有多次提交：`git merge-base --is-ancestor <旧SHA> <目标SHA>` 返回 0 表示是祖先，1 表示不是，其他非零值表示检查出错；远端旧值核对（CAS）是独立条件，仍须保留。见 [20 的恢复边界](../20-codex-long-horizon.md#9-超时后动作究竟发生了吗)；
  [一手，2026-10-18（UTC+8）核实：[快进定义](https://git-scm.com/docs/git-push#_note_about_fast_forwards)、[祖先检查](https://git-scm.com/docs/git-merge-base)、[旧值核对](https://git-scm.com/docs/git-update-ref)] [经验，Git 2.52.0] 隔离无远端仓库中，两跳祖先检查返回 0、分叉检查返回 1，匹配旧值更新成功、陈旧旧值更新失败且 ref 不变；仅验证本地 Git 行为，未验证连接器、发布权限或远端更新。
- **无人值守时**：开跑前确认发布授权、认证和审批路径；确需人工确认时保存断点，转做不依赖该确认的工作。汇报分别写远端 SHA、内容核对和 hosted CI 状态；
- **研究与发布分开**：研究并行，合入和发布串行、小批量进行。[经验，单仓单例] `c9e71c7` 发布前整合了前进到 `244bc9f` 的远端；`7a475db` 的发布回执核实了分支更新和五文件内容一致，hosted CI 未运行。这些记录支持恢复步骤，不证明失败率下降。

## 2. 分支与交付树检查

- **分支**：每个执行者用自己的分支，例如 `<执行者>/<主题>`；小步提交，合入前读取远端 `main`；检查 fetch refspec，若未跟踪 `main`，用 `git fetch origin main` 后立即固定 `FETCH_HEAD` 的 SHA，不把旧 `origin/main` 当最新。整合并重验后再发布。不强推，不改写已发布的历史，不覆盖他人的提交；
- **检查实际交付树**：先用 `git status --short` 核对新增文件；`git diff --check` 不覆盖未跟踪文件，暂存本单元后还要跑 `git diff --cached --check`。并行脏工作树不能代表待交付内容：固定索引树并导出到隔离目录运行离线入口，记录树 SHA；提交树须一致，整合或改动后重验。不要暂存其他执行者的文件。[经验，单仓单例] E4 日志的公开复演记录保留了去尾空格说明；2026-10-16 离线 Git 行为检查也复现了未跟踪文件漏检、暂存后检出尾空格；

### 2.1 跨执行者的发现与交接

**2026-10-21用户临时分工**：B权限恢复前，B推到分支的成果由A固定SHA复核、保历史整合并发布；已被其他发布先行合入则只核结果，不重复合入，不据发布成功推定权限恢复。

以下是本仓库对 Git 分支和 GitHub PR 的使用约定，适用于人及任何 Agent，不依赖特定模型或聊天转发：

- **用 git 自己合入，不走 PR（2026-10-20 用户决定）**：
  1. 在自己的分支完成一个项目，按手册§1通过全新上下文独审；TASKS自己的认领与结果行纳入同次受检交付，不单独提交；
  2. 按§2核fetch refspec并固定最新远端SHA，将其合并进自己的分支（不 rebase 已推送的提交），解决冲突时保留他人的 TASKS 行；
  3. 跑完整离线入口和 `python3 scripts/check_public.py --commits origin/main..HEAD`，读一遍 `git diff origin/main`；
  4. `git push origin HEAD:main`。只允许快进；拒绝后先核原因，确认是 `main` 前进才回到第 2 步。认证缺失、明确权限拒绝及结果不明按§1处理，不把所有拒绝都当并发，不强推；
  5. 推送后核对远端main、tree、父链、变化文件及精确提交CI；无运行记录不称CI通过，不另交状态提交。

  已开的草稿 PR：把对应分支按上述步骤合入后不再处理，能关闭就关闭，关闭需要审批也不阻塞。跨执行者复核改由阶段审计抽查。

- **主动发现**：每次开工、恢复、选择下一单元和合入前，读取最新远端 `main`、未合入分支及开放 PR；不能只看 `main` 的 TASKS。更新项目板水位时重新核开放PR并记录真实采样截止，不沿用开工时的旧列表；先核对 `git config --get-all remote.origin.fetch`；可用 `git fetch origin '+refs/heads/*:refs/remotes/origin/*'` 更新远端跟踪分支（不改本地工作分支），用 `git branch -r --no-merged origin/main` 找候选，再用 `git show <远端分支>:docs/collaboration/TASKS.md` 看认领及交接。远端已删除分支以 `git ls-remote --heads origin` 核对，PR 状态从托管平台读取；读不到时记录发现范围，不假定没有别人工作。
- **分工与认领**：同页单作者、独立文件并行，各执行者只合入自己的成果；跨执行者质量由阶段审计抽查，不设专门整合者。开工核实际活动及旧断点，认领不证明正在执行。TASKS只在合入提交里改自己的行，合并记录问题、起点SHA、分支、文件和结果；不单独提交认领，不覆盖他人行。每位执行者待合入成果最多2份，先收口积压再开新项目。
- **固定证据复用**：未变化的SHA复用已有来源、独立评审和检查记录；有新改动、反证或未覆盖风险才追加调查。与最新main整合后，实际最终树仍须完整验证。新SHA重建保留本地到远端映射，以tree、父链及变化文件确认交付，不把原本地SHA冒称远端SHA。
- **真实搭建／运行限时（2026-10-21用户决定）**：单次最多2小时；受阻记录原因与下一输入，转可执行项目，不继续扩展探针。结果JSON保读者摘要，原始输出留工作区；中转离线先做P41资料，恢复先冒烟，再P38／P44。
- **受阻只停依赖动作**：先保存成功对象、未发布成果和下一具体动作，再接续有授权、无文件冲突的内容或只读研究。授权／输入未变化，不重复被拒动作；没有新状态，不提交“仍在等待”或要求用户转述。等待、实际作业和验证范围分报；并行或一次发布成功不证明提效。
- **通知边界**：Git 保存可复查的状态，旧PR仅作历史提案与评审线索；它们不保证唤醒另一会话。上述检查由仍在运行或按既有安排恢复的执行者完成；恢复时读取项目、断点及下一步并继续已授权工作，不把既有调度的正常续接再列为用户审批项。没有活动任务时如实记等待／结束及恢复条件；未配置并验证事件接收端时，不声称 webhook 已送达、持续在线或全天自动执行，也不因本约定新增凭据、调度或权限。[一手，2026-10-17：[GitHub PR](https://docs.github.com/en/pull-requests/reference/pull-requests)、[webhook](https://docs.github.com/en/webhooks/about-webhooks)]

### 2.2 本地薄中转：验证优化的真实效果（已获启用授权）

> 2026-10-21 用户直接启用：立即按已备清单做真实入口冒烟，再做窄提示；允许工作区内安装公开依赖、运行公开项目和测试数据库。本地Codex仍只做薄中转，机制暂停扩建；不扩大到付费、引擎、大模型下载、凭据或全局配置变更。

**先验核心内容能否照做生效，再判断优化有没有大差异。** 本地验证分三档：

1. **照着做能否跑通**：核心页的命令、配置、AGENTS.md／CLAUDE.md加载、templates/的Hook与Skill，在指定真实Agent中按文档是否生效。执行项逐条判通过／失败，未运行另列；发现错误就修正文档或模板。
2. **大差异的小样本对照**：给完成条件和检查命令／不给（谎报完成率）、原生起步／整套工作流Skill、第二次修改有／无交接信息，以及已预注册的窄提示。固定任务、实际模型、工具和预算，只改变指定条件。
3. **不在本地测**：模型排名和价格、Claude／GPT专属默认、长程可靠性、游戏手感和资产质量。

执行顺序为**第①档 → 窄提示 → 第②档其他低成本对照 → listmonk**。优先复用已有校验、Hook回归及[workflow-ablation](../../experiments/workflow-ablation/README.md)的评估部件；具体范围和缺口见[预注册](../../templates/long-task/README.md#relay-pilot-plan)。复跑旧夹具只是接入／回归，不当新发现。

负责人定假设、冻结输入和验收；本地Codex只调用指定入口、检查及回传，由实际模型完成任务。报告写明模型／版本、客户端和配置，并说明**在DeepSeek上的结果不代表Sonnet／GPT**。入口失败如实报，不擅换模型；人工或中转补做不计模型成果。

第②档只有主要差异大且一致、没有新增关键失败，才改所测范围内的评级。未测出差异写“**本地试点未测得差异**”；未运行、无法评分和样本不足分别说明。保留全部尝试、独立检查与人工介入，未知时间不补零。

沿用§2.1交接，复用用户指定的既有本地会话并核精确ID，先承接已跑通的派发、任务目录与结果回收方法；切换入口也不让新会话从头试错。新任务启动失败不代表原会话不可用，Git更新也不保证会话已读取。校验器只核记录和快照，不执行任务或实施权限隔离。

**隔离运行环境暂不考虑。** 不把历史目录外读取列为启用前提，事实留TASKS；不自行配置专用账户、虚拟机、沙箱或凭据。任务目录只放公开仓库副本，回传及提交前运行`check_public.py`并人工检查，不把本机路径、私人文件内容或凭据带入回执／仓库。扫描须实际覆盖待回传文件；仓库模式只查已跟踪文件，未跟踪产物须导出到非Git的待回传目录，用`--root`检查。只传安全结果，不自动push，不扩大安装、认证或付费权限。

## 3. M4 运行信号的统计口径

- **周报与进度**：窗口为UTC+8周一00:00至下周一00:00，未满周标截止；沿用既有周报，不以单元数衡量进度。TASKS报三项：①A／B实际在线／内容执行比例及未知覆盖，另列Git空档代理，二者不混用；运行状态仅在变化时记录时间、项目、原因、断点及下一步，未覆盖时段不插值，未设定并核实可运行窗口前不报真实百分比。②满足整体验收且有远端交付证据的项目完成数，K1–K7映射P1–P7，部分交付另列，新项目不改旧分母。③固定首尾main回执SHA，按同一分类计算协作净字节／内容净字节，同时附新增／删除行（不识别重命名）及正文／研究小计；协作为docs/collaboration含归档及AGENTS／CLAUDE，内容为README＋docs／domains扣除协作，research目录单列研究，其余路径排除并报量。内容净增≤0时报比值不适用，不把压缩当负效率；跨类移动单列。每段超过1小时的Git空档分别写A／B已知原因、证据等级和未知范围，不据共同作者名推断执行者或停机。
- **诊断与改进**：发布尝试／失败、实质返工、交接等待和无人值守中断仍作辅助诊断，不作为完成项数。分母或运行段缺失写未知，结果不明单列；自报与平台回执分开，局部阻塞不归因整段。诊断后在既有细则或执行安排中改正，只有同口径后续证据才报提效，不另增过程文档或为填信号提交空状态。

## 4. 角色与独审

执行者认领、调查、写作、整合；阶段审计按§6审增量并写reviews；抽审抽查已合入main的单元并在BACKLOG补候选。通常dot执行、用户发起Claude审计、Codex间歇抽审，其他Agent也可阶段审计，但不得审自己执行的工作；角色不绑定工具，缺席不阻其他工作、不扩授权。

单元完成前全新上下文独审，只给diff、验收和§6，不给作者推理；逐项处理附位置／依据的实质问题，不改须写理由，TASKS留结论。无独审则留待审并做独立只读研究，不称通过。自审不替代阶段审计；阶段审计和抽审发现的问题均优先。


## 5. 内容成熟度

L1有方案与来源；L2有默认、分档、撤回及30秒结论；L3关键事实交叉核对、反证／日期／入口一致，正文可独立决策；L4有本仓可复查实验（§7后续阶段）。目标核心页L3；docs/README表记级别、差距和下一步，优先读者多且差距大的页。

**第二条轴：前沿比较状态**（2026-10-21 加，采纳[独立质量审计](reviews/2026-10-21-quality-audit.md)）。L1–L4 只衡量事实可靠和可用，不衡量离最高水平多远。成熟度表每页另记一项：**已比较**（与当前最高水平或领先候选做过同问题比较）、**仅候选**（知道领先做法，没比较）、**未知**（没找过）。审计的差距分（0–3）记在这一项旁边。


## 6. 工作线与阶段验收

单元归M1–M6／GA–GF，项目板定选题；四主线由M3承接，R01–R16与已交理论的WP0–WP13只作索引。挂不到旧线的新方向写BACKLOG待用户决定。各线可并行，阶段标志不是终点；已完成与缺口在BACKLOG区分，不重跑旧先导，不以案例重开条件冻结整线。

## 8. 运行节奏

- 单元：核状态／认领→执行→独审→整合验证→交接续做。问答后回当前单元，独立调查可并行，不把排队称运行。
- 每天UTC+8首单元由dot-A按最新分工更新项目板状态／阻塞／水位；每周：M2、成熟度、M4。每周或约100提交由阶段审计核默认／前沿、规则效果、方向和项目，事实约抽10单元。每两周一次**质量审计**，由未参与写作的 Agent 独立找出各核心页的当前最高水平，再与正文的“当前最高水平”一节比对，按差距打分；分歧本身就是待补的缺口。
- 每约10单元编辑轮：措辞、入口、篇幅、摘要／旧推理、TASKS归档与简短复盘；每月复核游戏动态、研究总量、开工篇幅和优先级。
- 等待前核真实工作、外部结果及独立项，缺权限／证据只停相关项并按§2兜底；恢复按§0／4.5。同行优先：用户／审计→运行阻塞→M2→项目板→规划，不阻其他线。
