# 运行细则

> 只放操作步骤：Git 发布与恢复（§1）、分支与交付检查（§2、§2.1）、本地模型协作（§2.2）、Dot 运行保障（§3）。执行规则以[运行手册](LONG-TERM-PLAN.md)为准。

## 1. 发布与恢复

- **首选 `git push`**：授权和写认证可用时，本地提交后整批推送；shell 缺写认证则用既有授权连接器，不反复试推、不自行新增凭据；
  提交身份元数据与远端写认证分开处理：需要本地 commit 时，用本次命令的 `-c user.name=… -c user.email=…` 如实标识实际执行者，不改全局配置、不冒用用户或厂商身份。缺作者本身不是用户授权缺口，也不需要新建凭据。
- **增量发布**：固定最新远端 `main` SHA，只上传变化文件；已确认成功的对象可复用，在工具上限内批量写入，最后以该 SHA 为预期旧值更新分支（CAS）。发布前发现基线已前进，或更新被拒后确认远端旧值已变，先停发、整合并按手册§7重验受影响路径；其他拒绝按失败恢复核因，不强推；
  TASKS 交接超过约10行时，后续移出的原文按归档当日（UTC+8）追加至既有 `archive/` 的当日日档；旧 `completed-through-2026-10-16.txt` 保持原样，不按文件名重切历史。新日档创建时同步 TASKS 与既有归档索引的链接，增量发布只提交变化文件，避免反复上传封存历史。
- **失败恢复**：记录失败阶段和成功回执；对象创建成功不等于分支发布成功。超时、断连或 `user cancelled` 只表明结果待核，不足以判定人工取消或审批超时。先读远端分支、目标提交及文件内容；确认已生效就不重发，未生效才从断点恢复。明确拒绝权限时停止该动作，不换路绕过；
- **工作目录不可见**：先在已知可用目录核 shell 与指定任务路径；不能据此猜测用户删除、权限变化或整台机器离线。核远端固定提交后可在新目录恢复已发布副本，不覆盖旧路径；未取回的原始记录／未发布断点仍标不可复查，不把恢复文稿当重新实测。
- **续接本地操作**：开始操作前保存预期分支和本地 HEAD；恢复时及暂存／提交前逐一核对，不符或缺失就保留改动、先对账，不把当前值直接重记为旧操作的预期值。连接器发布可能生成不同 commit SHA，结合发布回执、tree 与内容确认原成果；已发布且没有实质增量时，不重复追加状态或提交。这些检查不是并发锁，仍须串行整合；发布前逐个核对新生成提交的直接父与构造时指定值、最终 tree 与受检树一致。分支快进检查预期旧 SHA 是否为目标提交的祖先，允许中间有多次提交：`git merge-base --is-ancestor <旧SHA> <目标SHA>` 返回 0 表示是祖先，1 表示不是，其他非零值表示检查出错；远端旧值核对（CAS）是独立条件，仍须保留。见 [20 的恢复边界](../20-codex-long-horizon.md#9-超时后动作究竟发生了吗)；
- **无人值守时**：开跑前确认发布授权、认证和审批路径；确需人工确认时保存断点，转做不依赖该确认的工作。汇报分别写远端 SHA、内容核对和 hosted CI 状态；
- **研究与发布分开**：研究并行，合入和发布串行、小批量进行。

## 2. 分支与交付树检查

- **分支**：每个执行者用自己的分支，例如 `<执行者>/<主题>`；小步提交，合入前读取远端 `main`；检查 fetch refspec，若未跟踪 `main`，用 `git fetch origin main` 后立即固定 `FETCH_HEAD` 的 SHA，不把旧 `origin/main` 当最新。整合并按手册§7重验受影响路径后再发布。不强推，不改写已发布的历史，不覆盖他人的提交；
- **检查实际交付树**：核对新增与未跟踪文件，仅暂存本次内容并跑 `git diff --cached --check`；检查必须对应将要发布的内容。任务独占且文件一致的工作树直接验证，不强制导出／重建。只有并行脏树混入无关内容或依赖Git对象的测试需要隔离时，才使用真实Git工作树或适合该检查的隔离副本；不要对依赖Git对象的检查使用无Git归档。整合后按手册§7复用未变结果、补受影响检查，不重复制作同树证明。


### 2.1 跨执行者的发现与交接

**2026-10-21用户临时分工**：B权限恢复前，B推到分支的成果由A固定SHA复核、保历史整合并发布；已被其他发布先行合入则只核结果，不重复合入，不据发布成功推定权限恢复。

以下是本仓库对 Git 分支和 GitHub PR 的使用约定，适用于人及任何 Agent，不依赖特定模型或聊天转发：

- **用 git 自己合入，不走 PR（2026-10-20 用户决定）**：
  1. 在自己的分支完成一个项目，按手册§7完成一次全新上下文独审或复用有效独审；TASKS自己的认领与结果行纳入同次受检交付，不单独提交；
  2. 按§2核fetch refspec并固定最新远端SHA，将其合并进自己的分支（不 rebase 已推送的提交），解决冲突时保留他人的 TASKS 行；
  3. 按手册§7完成适用检查、公开文件与提交扫描，读一遍 `git diff origin/main`；
  4. `git push origin HEAD:main`。只允许快进；拒绝后先核原因，确认是 `main` 前进才回到第 2 步。认证缺失、明确权限拒绝及结果不明按§1处理，不把所有拒绝都当并发，不强推；
  5. 推送回执明确快进成功即可记录；结果不明或连接器重建提交时，再核远端目标与内容。CI状态按需读取，无运行记录不称通过，不因发布成功再重跑测试，不另交状态提交。

  已开的草稿 PR：把对应分支按上述步骤合入后不再处理，能关闭就关闭，关闭需要审批也不阻塞。跨执行者复核改由阶段审计抽查。

- **主动发现**：每次开工、恢复、选择下一单元和合入前，读取最新远端 `main`、未合入分支及开放 PR；不能只看 `main` 的 TASKS。更新项目板水位时重新核开放PR并记录真实采样截止，不沿用开工时的旧列表；先核对 `git config --get-all remote.origin.fetch`；可用 `git fetch origin '+refs/heads/*:refs/remotes/origin/*'` 更新远端跟踪分支（不改本地工作分支），用 `git branch -r --no-merged origin/main` 找候选，再用 `git show <远端分支>:docs/collaboration/TASKS.md` 看认领及交接。远端已删除分支以 `git ls-remote --heads origin` 核对，PR 状态从托管平台读取；读不到时记录发现范围，不假定没有别人工作。
- **分工与认领**：同页单作者、独立文件并行，各执行者只合入自己的成果；跨执行者质量由阶段审计抽查，不设专门整合者。开工核实际活动及旧断点，认领不证明正在执行。TASKS只在合入提交里改自己的行，合并记录问题、起点SHA、分支、文件和结果；不单独提交认领，不覆盖他人行。每位执行者待合入成果最多2份，先收口积压再开新项目。
- **固定证据复用**：受检内容、依赖与行为未变时复用已有来源、独立评审和检查记录；有新改动、反证或未覆盖风险才追加调查。与最新main整合后按手册§7补验受影响路径，完整入口仅用于该节规定的范围；提交SHA变化本身不使结果失效。新SHA重建保留本地到远端映射，以tree、父链及变化文件确认交付，不把原本地SHA冒称远端SHA。
- **真实搭建／运行限时（2026-10-21用户决定）**：单次最多2小时；受阻记录原因与下一输入，转可执行项目，不继续扩展探针。临时分区满时先核容量；可在已有授权工作区为本次运行指定临时目录（如进程级TMPDIR），保留原证据，不把存储故障记成待授权，也不广泛清理其他任务目录。短服务遇跨执行调用的非权限连接失败，可先在同次调用内启停、请求与回收核实；不据一次ECONNREFUSED猜为权限或产品故障，不改网络权限。若同次请求可达而云端浏览器不可达，先核目录是否可见及是否同一运行宿主；确认属于dot云端的原生终端可正常启动同一公开预览，再以浏览器实操确认，不能仅凭服务启动就记客户端通过。结果JSON保读者摘要，原始输出留工作区；
- **受阻只停依赖动作**：先保存成功对象、未发布成果和下一具体动作，再接续有授权、无文件冲突的内容或只读研究。授权／输入未变化，不重复被拒动作；没有新状态，不提交“仍在等待”或要求用户转述。等待、实际作业和验证范围分报；并行或一次发布成功不证明提效。
- **通知边界**：Git 保存可复查的状态，旧PR仅作历史提案与评审线索；它们不保证唤醒另一会话。上述检查由仍在运行或按既有安排恢复的执行者完成；恢复时读取项目、断点及下一步并继续已授权工作，不把既有调度的正常续接再列为用户审批项。对已结束的执行任务补交接文字不等于重新启动；须核新的开始回执，未确认只记待接续，不报正在执行。没有活动任务时如实记等待／结束及恢复条件；未配置并验证事件接收端时，不声称 webhook 已送达、持续在线或全天自动执行，也不因本约定新增凭据或权限；dot 的心跳定时任务见§3。[一手，2026-10-17：[GitHub PR](https://docs.github.com/en/pull-requests/reference/pull-requests)、[webhook](https://docs.github.com/en/webhooks/about-webhooks)]

### 2.2 本地模型协作

**范围（2026-10-25 用户授权）**：A、B 都可把任务内的探索、源码调查、方案候选、实现、资源制作与处理、测试、文档初稿交给本机已配置的 DSH＋DeepSeek、Claude Code＋DeepSeek、ZCode＋GLM 5.3／GLM 5.3 Flash。不设人为调用次数或 token 节省预算，普通任务默认原生 Workflow（实施＋独立验证，失败才修），只看质量与完整结果；遵守实际限流和资源占用，停止无新信息的重复调用。这是项目使用约定，不授权新收费服务。

**分工**：dot 负责方向、拆分、关键取舍、接收和发布质量；独立的“dot 本地协作”会话接收任务、组织模型执行和常规修正；模型负责被委派的工作。派发只需目标、必要来源、独占文件／分支和期望产物，入口与状态约定见 [local-jobs](local-jobs/README.md)。多个独立任务可并行，同一文件、运行实例或输出目录不多方写入；已完成的工作不重复派发。

**跨账号**：网页 dot 与本机属于不同账号，交接只走共享 Git，不按 thread ID 互访；接收端定时唤醒发现 main 及 `dot-a/*`／`dot-b/*` 分支的任务与反馈，实际启用状态以本机计划为准。A 研究主任务不代管 B 的执行或验收；接收端缺失时记待接续。

**公开与权限**：只把允许交给对应服务的材料交给模型，不含公司代码、私人历史、凭据或无关文件；回传与提交前检查实际产物（含新增文件）并跑公开扫描。新收费服务、凭据、额外账号访问或破坏性操作仍按实际授权处理；P7／P27 等特定未决动作不因一般委派解除。

**正式方法对照**：仅在用户明确要求时开展，届时沿用[试验入口](../../experiments/absorption/README.md)的冻结、隔离与独立判分条件。P79 已于 2026-10-25 收口为描述性记录，不再续批。普通生产以实际产物和接收为准，不升级成 benchmark。

## 3. Dot 运行保障

> 2026-10-25 用户授权。两个 dot 是主要产能，它们停下就是主线停下。

**心跳定时任务**：每个 dot 保留一个定时任务，约每 2 小时运行一次（时区 Asia/Shanghai，无结束日期，用户可随时停用）。每次运行：

1. 正在推进就安静结束，不打断当前工作。
2. 空闲、做完一轮或在等待时：同步 a1dbv 最新 main，读 TASKS“当前重点”、本人 local-jobs 的结果和待合分支，接下一项。
3. 在等批准、确认或被拒的动作逐条记在 TASKS 对应行，只停这些动作，其余继续。
4. 只在需要用户决定、碰到额度上限、或连续两次心跳都无法推进时通知用户。

建好后让 Dot 列出它保存的定时任务（指令、频率、时区、通知规则），确认无误。每个 dot 只保留这一个心跳，不叠加其他调度；本地接收端 `dot-git` 每小时发现一次新任务和反馈，空队列安静结束；已启动的 Workflow 沿原调用持续执行，完成结果在接收端下次运行时汇回。无新变化不调用模型或重跑检查。沿已有心跳运行，不另建轮询服务。

**减少等待**：常规的 GitHub 提交与推送由用户在各账号的 Custom rules（Settings → Personalization → Custom rules，插件权限另设）里设为无需询问。提交身份沿用§1 的单次 GitHub noreply，不需要再确认。

**额度**：和 Dot 对话不占额度；它启动的 Work／Codex 任务占对应额度，社区还报告有每日重置的 preview limit。执行类工作优先派给本地模型（§2.2），Dot 负责方向、拆分与接收。碰到额度上限时在 TASKS 记下恢复时间，恢复前只做不耗额度的工作。

**静默检查**：Codex 审计会话在增量审计时看两个 dot 的最近提交时间。某个 dot 超过 3 小时没有提交，且心跳没有把它叫醒，就在 TASKS 当前重点标出，并提醒用户去看该 Dot 的 Activity。
