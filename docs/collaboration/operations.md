# 运行细则

> 操作步骤：发布（§1）、分支与发现（§2、§2.1）、本地模型协作（§2.2）、Dot 运行保障（§3）。规则以[运行手册](LONG-TERM-PLAN.md)为准。

## 1. 发布与恢复

**谁发布**：每个执行者把自己接收的成果直接快进推送到 `main`（锚点 2026-10-21 授权）。A 和 B 各自发布，不互相代合，也不走 PR（2026-10-20 用户决定）。范围是 a1dbv 的 `main` 和负责人自己的案例仓库默认分支（Star-Rush-Reborn 的 `master`，MOBA-Like、FPS-Like 的 `main`）。用 GitHub 连接器写 Git 数据或更新 ref 与命令行推送等价，同样只做快进。发布不包括部署，也不改账户权限。

1. 在自己的分支（`<执行者>/<主题>`）完成一个可接收结果，按手册§7完成审查和适用检查。
2. `git fetch origin main:refs/remotes/origin/main`（确保 `origin/main` 是最新），把它合并进自己的分支，不 rebase 已推送的提交；冲突时保留他人的 TASKS 行，本人的 TASKS 行随同一次交付修改。
3. 暂存本次内容，跑 `git diff --cached --check` 和 `python3 scripts/check_public.py`；提交后跑 `python3 scripts/check_public.py --commits origin/main..HEAD`，有任何发现就停下，不推送；合并提交也要用 noreply 身份（在本仓库设 `git config user.email` 为 noreply，不改全局配置）。再读一遍 `git diff origin/main`。
4. `git push origin HEAD:main`，只允许快进；不强推，不改写已发布的历史。

**提交身份**：在本次命令里用 `-c user.name=… -c user.email=…` 标明实际执行者，邮箱用 GitHub noreply 或 Agent 平台的固定机器身份（如 `noreply@anthropic.com`）。不改全局配置，也不必再向用户确认。

**推送失败时**：

- `main` 前进了：回到第 2 步。
- shell 没有写认证：改用已授权的 GitHub 连接器发布同一批文件，以最新 `main` SHA 作为预期旧值；不新建凭据。
- 明确的权限拒绝：只停被拒的那部分。某个文件或某类上传被拒时，其余改动照常发布（先移除或替换对被拒文件的引用，保证版本可玩），被拒部分留在自己的分支；在 TASKS“需要用户决定”记一行，接着做其他工作。不转交别的执行者代发。
- 超时、断连或结果不明：先读远端 `main` 和目标文件；已生效就不重发，未生效再从断点继续。

研究可以并行，发布串行、小批量。TASKS 移出的旧行追加到 `archive/` 的当日（UTC+8）日档。

## 2. 分支与交付

- 每个执行者用自己的分支，小步提交。同一文件同一时间只有一个写者，独立文件并行。
- 检查对应将要发布的内容：只暂存本次文件；并行的脏工作树混入无关内容时，才用隔离的工作树检查。
- 受检内容、依赖和行为没变时，复用已有审查和检查结果；提交 SHA 变化本身不使结果失效，整合后只补受影响的检查。
- 同一文件同一时间只有一份待合入成果；在途数量不设上限，每条有活的线至少一个在途。

### 2.1 跨执行者的发现与交接

- **开工、恢复和选下一项前**：运行 `git fetch origin '+refs/heads/*:refs/remotes/origin/*'`，用 `git branch -r --no-merged origin/main` 看他人的在制分支，再读 `main` 上的 TASKS。认领只在合入提交里改自己的 TASKS 行。
- **跨执行者质量**由 Codex 审计会话的增量审计抽查，不设专门整合者。旧的草稿 PR 按§1 合入后关闭；关闭需要审批时不必等待。
- **真实搭建和运行**单次最多 2 小时（2026-10-21 用户决定）；受阻时记下原因和下一步需要的输入，转做其他项目。
- **受阻只停依赖动作**：保存已完成的成果和下一步，继续其他有授权的工作。授权和输入没变，就不重复被拒的动作，也不提交“仍在等待”。
- **唤醒**：Git 和 PR 不会唤醒其他会话，dot 靠§3 的心跳续接。没有在运行的任务时，如实记录等待和恢复条件。

### 2.2 本地模型协作

**范围（2026-10-25 用户授权）**：做法已定、规格写得清的任务都下发给本机模型，和 dot 自己的代理并行，例如：按 Skill 做的探索与候选收集、按提纲起草正文、非作者照页面做一遍的实测、事实与链接复核、规格明确且有测试兜底的编码单元，以及需要本机 GPU 或本机工具的生成、素材代取和验证（浏览器只用 headless，不开窗口、不动键鼠）。dot 保留方向、规格、关键取舍、质量判断和最终发布。接收端现用 Claude Code＋DeepSeek v4.1 flash，最多 4 个任务并行；同时只派一个需要 GPU 的任务。Workflow 见§3；不设人为调用或 token 预算，遵守实际限流，停止无新信息的重复调用，不开新收费服务。接收端在 Windows 原生环境跑 `check_repo`＋`check_public`，完整离线门禁只在 POSIX 环境要求。

**分工**：本机接收端（§3）领取任务、调用模型并发布结果。任务写目标、按哪个 Skill 或规格做、独占文件／分支和怎样算做成，入口与状态约定见 [local-jobs](local-jobs/README.md)。多个独立任务可并行，同一文件、运行实例或输出目录不多方写入；已完成的工作不重复派发。

**跨账号**：网页 dot 与本机属于不同账号，交接只走共享 Git，不按 thread ID 互访。本机接收端是本机计划任务运行的固定脚本，不占 dot 的心跳名额；它从 main 及 `dot-a/*`／`dot-b/*` 分支发现任务与反馈，产物推到 `relay/*` 结果分支。接收端缺失时记待接续。

**公开与权限**：只把允许交给对应服务的材料交给模型，不含公司代码、私人历史、凭据或无关文件；回传与提交前检查实际产物（含新增文件）并跑公开扫描。凭据、付费、账户设置和破坏性操作属于锚点红线，其余按默认授权执行。

**正式方法对照**：仅在用户明确要求时开展，沿用[试验入口](../../experiments/absorption/README.md)的冻结、隔离与独立判分；日常在真实任务上比较新旧做法不需要这些。

## 3. Dot 运行保障

> 2026-10-25 用户授权，10-26 按官方能力重写。两个 dot 是主要产能，目标是没有空档：一项结果回来，下一项已经在跑。

**运行方式**：dot 负责方向、拆分、取舍和抽查，同时推进多条工作线，不串行等待。

- **并行与接续**：按长期提示词的工作线，把无文件冲突、输入齐备的交付单元并行推进；同时留出非作者审查、返工和发布的容量，不以代理数量或开满状态作为产出。四线各有一个可接续单元，或写明当前阻塞动作和恢复条件。结果交回就在同一轮验收／返工／保全，不等下一次心跳。认领、排队、`running` 标签和静态文件都不算实际执行；读到本次工具结果、进程观察或产物增量才记相应观察。超过 30 分钟无新证据只触发核查，先核原调用、远端和已产物，不自动终止、清锁或重开。活跃单元不打断、不重复派发。浏览器及本机操作仍按当前授权执行。
- **dot 的代理、云电脑和本机模型同时用，Codex 额度最后用**：

| 顺序 | 产能 | 适合 | 额度 |
|---|---|---|---|
| 1 | dot 的后台代理（dot 内并行） | 调查、读源码、写初稿、写代码、独立审查 | 不计额度 |
| 1 | dot 的云电脑 | 克隆仓库、构建、测试、无头浏览器 smoke、资源处理，用户电脑关机也能跑 | 同上 |
| 1 | 本机模型（§2.2） | 做法明确的单元，和 dot 的代理并行下发 | 免费，要本机开机并已登录；接收端是固定脚本，不耗 Codex 额度 |
| 3 | Codex 云任务、本机 Codex 任务 | dot 自己做不了时才用，例如需要 Codex 环境的大批并行编码，或 dot 正在休息 | 计入 Codex 额度 |

**哪个 dot 直连本机会变化**，以 dot 资料页 Computers 显示的 “Your computer · Connected” 为准，不写死。直连的 dot 可以直接在本机开 Codex 任务，不等接收端；另一个 dot 走 local-jobs。两种方式都在 local-jobs 写任务文件：直连 dot 自己开的任务写 `status: running` 并注明“dot 直接执行”，接收端不再认领。

- **醒来的方式**：dot 自己决定暂停和唤醒，手上还有可做的事就不结束；在途任务回来就接续。dot 的 GitHub 事件只覆盖 PR（新建、转待审、关闭／合入、提交更新、审查、评论），不含分支推送、issue 和 CI。本仓库直接推送、不走 PR，所以靠 dot 自己唤醒加每小时心跳兜底（定时任务的最短间隔）；dot-A 向上游开的 PR 订阅审查和评论事件，维护者一回复就醒。
- **心跳每次运行**：
  1. 在跑的任务不打断，但检查各条线有没有空档，把可独立的工作派满；仍按第 4、5 步判断是否通知。
  2. 否则重读本人长期提示词和 TASKS 当前重点，同步最新 main，处理已回来的结果，把可做的独立工作派出去。
  3. 等批准、确认或被拒的动作记在 TASKS 对应行，只停这些动作。
  4. **dot-A 的两小时回执（2026-10-26 用户授权）**：按 Run 计划时间换算为 `Asia/Shanghai`，双数小时（00、02、04、06、08、10、12、14、16、18、20、22）向本 ChatGPT 对话发一次两小时短回执，正常运行即每两次心跳一次；奇数小时只接续。按计划时段而非实际到达小时判断，同窗重试先核已发送记录去重，实际延迟如实注明。
     - 最多三条：完成与真实变化；实际执行与等待分列；新增阻塞（没有则写“无新增”）。
     - 沿用同一个小时心跳及既有 PR 事件订阅，不新增调度。
  5. 需要用户决定、遇到平台休息提示、或连续两次心跳确无推进时，仍即时通知，不等双数小时。

**笔记与定时任务**：dot 的笔记独立于本仓库，旧决定会一直沿用。指导有方向层修订时，让 dot 列出与 a1dbv 相关的笔记，删除或改正与当前规则冲突的条目；同时列出定时任务，只保留这一个心跳。笔记与本仓库冲突时，以本仓库为准。

**本机接收端**是本机计划任务每 20 分钟运行一次的固定脚本，脚本和配置只在本机。每次运行：

1. 从 main 和 `dot-a/*`、`dot-b/*` 发现新任务与反馈，领取 `ready`／`revision_requested`，先在 main 写 `running`。
2. 每个任务在目标仓库的独立 worktree 里交给 Claude Code＋DeepSeek，按 `kind` 跑固定原生 Workflow：`build`（默认）实施后三个审查者并行看读者可用、事实与链接、实际运行，修到全部通过，最多三轮；`reader-test` 读者只照页面做，非读者按验收核对并分清页面卡点；`explore` 三路收集候选、核实链接后整理再审。逐项清单的任务按单元推进，每单元约 60–90 分钟。
3. 模型只改文件；提交、公开扫描、适用检查、推送结果分支都由脚本做。`accept: auto` 的 a1dbv `build` 任务在审查和检查都通过后合入 main，每单元一次；其余标 `review_ready` 等负责人接收。
4. 同时最多 4 个任务；单元超过 2 小时或连续两次失败标 `blocked` 并写恢复条件。别处在执行的 `running`（如 dot 直接执行）不碰，空队列只 fetch。

有 `ready` 任务超过 40 分钟没被领取时，dot 在 TASKS“分工”一节标出，并通知用户检查本机是否开机、已登录。

**减少等待**：常规的 GitHub 提交与推送由用户在各账号的 Custom rules（Settings → Personalization → Custom rules，插件权限另设）里设为无需询问。写法要列出仓库、文件类型和连接器操作，两个账号相同：“无需询问：向我本人拥有的 GitHub 仓库 dbvv1/a1dbv、dbvv1/MOBA-Like、dbvv1/Star-Rush-Reborn、dbvv1/FPS-Like 和我账号下的 fork 提交代码、脚本、文档、图片、音频、3D 模型等文件，包括 git 命令行快进推送，和 GitHub 连接器创建 blob、tree、commit、新建分支或快进更新分支；不含凭据和私人数据，推送前跑公开扫描；不强推、不删除分支、不改仓库设置与权限。”用户改过规则后，只对新增授权明确覆盖、且已确认没有执行的原动作重试；仍被拒就保留原恢复条件，不换通道或请另一端绕过。向开源项目上游开 PR 属于真正的外部操作，用户在对话里预先批准，平台仍要求确认时就停下来问。GitHub 集成在别人的仓库上创建 PR 或评论会返回 403（集成只能写装了它的仓库）：遇到时把分支推到 fork，在 TASKS“需要用户决定”写一行 compare 链接和拟定标题，由用户点开创建，不重试、不换凭据。

**额度**：暂不作为约束（2026-10-26 用户决定）。遇到平台的休息提示时，在 TASKS 记下恢复时间，期间由本机模型继续。

**静默检查**：按实际心跳、执行观察、可恢复产物和验收结果看推进，不以提交数或计划唤醒时间代替工作。有可做单元却长等待、结果已回却无人接收、只有临时目录没有可恢复版本，均在当前轮纠正；连续两次实际心跳确实无法推进按既有通知规则说明阻塞。长单元仍有真实进展时不算失败。平台休息／断连时记录已知恢复提示，未知就写未知；本机制不保证持续在线或自动唤醒一定成功。

### 3.1 交付单元与等待前检查

- 先接收已交回的结果（验收、返工或退回），再开新单元：核原调用和产物，失败、结果不明与已完成分列，无法确认记未知，不盲重试。实施、审查、返工、发布是同一单元的阶段，不换新编号。
- 一个动作受阻（GPU、浏览器、上传、等批准）只停这个动作，不依赖它的工作照常推进。
- 回执只记实际发生的时间与证据，不按计划时间补写执行；没有完整记录的时长写未知。
- 源码单元通过检查后，在已有授权内推到远端候选分支或做可离线恢复的完整归档；只留临时目录、补丁或提交号不算保全，保全也不等于合入或发布。待批产物不换通道保全。
