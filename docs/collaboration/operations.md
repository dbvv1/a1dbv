# 运行细则

> 2026-10-17 从[运行手册](LONG-TERM-PLAN.md)移出，开工、恢复和选择下一单元时读第 2.1 节；发布、交付检查或统计运行信号时再读对应章节。

## 1. 发布与恢复

- **首选 `git push`**：授权和写认证可用时，本地提交后整批推送；shell 缺写认证则用既有授权连接器，不反复试推、不自行新增凭据；
  提交身份元数据与远端写认证分开处理：缺作者时，内容执行者可交固定的受检索引树、基线 SHA 和变更文件，由串行发布者接手；需要本地 commit 时，用本次命令的 `-c user.name=… -c user.email=…` 如实标识实际执行者，不改全局配置、不冒用用户或厂商身份。缺作者本身不是用户授权缺口，也不需要新建凭据。[一手，2026-10-17（UTC+8）核实：[身份配置](https://git-scm.com/docs/git-config#Documentation/git-config.txt-username)、[命令级配置](https://git-scm.com/docs/git#Documentation/git.txt--cltnamegtltvaluegt)] [经验，2026-10-17（UTC+8），Git 2.47.3] 隔离临时仓库、`user.useConfigOnly=true` 禁用身份猜测时，未配置身份的 commit 退出128，本次命令提供执行者身份后退出0且未持久化身份；仅证明本地提交行为，未验证 push 授权或认证。
- **增量发布**：固定最新远端 `main` SHA，只上传变化文件；已确认成功的对象可复用，在工具上限内批量写入，最后以该 SHA 为预期旧值更新分支（CAS）。发布前发现基线已前进，或更新被拒后确认远端旧值已变，先停发、整合并重验；其他拒绝按失败恢复核因，不强推；
  TASKS 交接超过约10行时，后续移出的原文按归档当日（UTC+8）追加至既有 `archive/` 的当日日档；旧 `completed-through-2026-10-16.txt` 保持原样，不按文件名重切历史。新日档创建时同步 TASKS 与既有归档索引的链接，增量发布只提交变化文件，避免反复上传封存历史。
- **失败恢复**：记录失败阶段和成功回执；对象创建成功不等于分支发布成功。超时、断连或 `user cancelled` 只表明结果待核，不足以判定人工取消或审批超时。先读远端分支、目标提交及文件内容；确认已生效就不重发，未生效才从断点恢复。明确拒绝权限时停止该动作，不换路绕过；
- **续接本地操作**：开始操作前保存预期分支和本地 HEAD；恢复时及暂存／提交前逐一核对，不符或缺失就保留改动、先对账，不把当前值直接重记为旧操作的预期值。连接器发布可能生成不同 commit SHA，结合发布回执、tree 与内容确认原成果；已发布且没有实质增量时，不重复追加状态或提交。这些检查不是并发锁，仍须串行整合；发布前逐个核对新生成提交的直接父与构造时指定值、最终 tree 与受检树一致。分支快进检查预期旧 SHA 是否为目标提交的祖先，允许中间有多次提交：`git merge-base --is-ancestor <旧SHA> <目标SHA>` 返回 0 表示是祖先，1 表示不是，其他非零值表示检查出错；远端旧值核对（CAS）是独立条件，仍须保留。见 [20 的恢复边界](../20-codex-long-horizon.md#9-超时后动作究竟发生了吗)；
  [一手，2026-10-18（UTC+8）核实：[快进定义](https://git-scm.com/docs/git-push#_note_about_fast_forwards)、[祖先检查](https://git-scm.com/docs/git-merge-base)、[旧值核对](https://git-scm.com/docs/git-update-ref)] [经验，Git 2.52.0] 隔离无远端仓库中，两跳祖先检查返回 0、分叉检查返回 1，匹配旧值更新成功、陈旧旧值更新失败且 ref 不变；仅验证本地 Git 行为，未验证连接器、发布权限或远端更新。
- **无人值守时**：开跑前确认发布授权、认证和审批路径；确需人工确认时保存断点，转做不依赖该确认的工作。汇报分别写远端 SHA、内容核对和 hosted CI 状态；
- **研究与发布分开**：研究并行，合入和发布串行、小批量进行。[经验，单仓单例] `c9e71c7` 发布前整合了前进到 `244bc9f` 的远端；`7a475db` 的发布回执核实了分支更新和五文件内容一致，hosted CI 未运行。这些记录支持恢复步骤，不证明失败率下降。

## 2. 分支与交付树检查

- **分支**：每个执行者用自己的分支，例如 `<执行者>/<主题>`；小步提交，合入前读取远端 `main`；检查 fetch refspec，若未跟踪 `main`，用 `git fetch origin main` 后立即固定 `FETCH_HEAD` 的 SHA，不把旧 `origin/main` 当最新。整合并重验后再发布。不强推，不改写已发布的历史，不覆盖他人的提交；
- **检查实际交付树**：先用 `git status --short` 核对新增文件；`git diff --check` 不覆盖未跟踪文件，暂存本单元后还要跑 `git diff --cached --check`。并行脏工作树不能代表待交付内容：固定索引树并导出到隔离目录运行离线入口，记录树 SHA；提交树须一致，整合或改动后重验。不要暂存其他执行者的文件。[经验，单仓单例] E4 日志的公开复演记录保留了去尾空格说明；2026-10-16 离线 Git 行为检查也复现了未跟踪文件漏检、暂存后检出尾空格；

### 2.1 跨执行者的发现与交接

以下是本仓库对 Git 分支和 GitHub PR 的使用约定，适用于人及任何 Agent，不依赖特定模型或聊天转发：

- **主动发现**：每次开工、恢复、选择下一单元和合入前，读取最新远端 `main`、未合入分支及开放 PR；不能只看 `main` 的 TASKS。先核对 `git config --get-all remote.origin.fetch`；可用 `git fetch origin '+refs/heads/*:refs/remotes/origin/*'` 更新远端跟踪分支（不改本地工作分支），用 `git branch -r --no-merged origin/main` 找候选，再用 `git show <远端分支>:docs/collaboration/TASKS.md` 看认领及交接。远端已删除分支以 `git ls-remote --heads origin` 核对，PR 状态从托管平台读取；读不到时记录发现范围，不假定没有别人工作。
- **按任务和文件分工**：把需要共同决定的结论先交一个写作者收敛；不同正文／研究文件可并行，同一文件的资料调查也可并行，但编辑由一个执行者汇总。既有A／B等标签只标识执行者，不绑定账号或永久职责；每项认领明确接收／整合者，临时换人先在同一记录更新并核对未完成写入，避免两个发布者同时接管。
- **先认领再修改**：认领仍只写 TASKS 自己的一行，包含执行者、分支、基线 SHA、主要文件、问题和当前状态，推到自己的远端分支供其他执行者读取。认领及必要状态更新是手册“共享文件只在最后一个提交修改”的例外，仅限自己一行。先检查其他分支和 PR 的认领，正文文件重叠时先通过 Git 记录协调结果或换到无冲突任务；同时认领不构成互斥锁。认领的有效期沿用手册第 4.6 节；有效认领、最近提交都不能证明执行者此刻在线或正在运行，排队、执行中、待审、阻塞应如实填写。
- **用已有载体交回**：结果留在该分支，TASKS 自己一行写交付 SHA（同提交可写“本提交”）、改变的结论、验证范围、阻塞和下一步；有 PR 权限时以草稿 PR 交给整合者审查，PR 指向同一分支，不另建交接文档。没有 PR 工具时保留可发现的远端分支及该行，整合者从 Git 取回，不要求用户复制聊天。仅本地保存仍未交接，权限阻塞须明确记录。
- **串行整合并留回执**：按当前授权明确一个 `main` 整合者，其余执行者交分支／PR；角色不绑定工具。整合者读固定交付 SHA 的 diff、检查及独立评审结果，整合最新 `main` 后重验；保留他人 TASKS 行，只更新本单元的认领和交接。经授权合入并核对远端后，在 TASKS 最近交接记录结果与可定位提交（同提交可写“本提交”，由远端日志解析），走 PR 合并时，草稿须先经授权转为可评审状态，不能直接合并；用其他获准路径整合时，核对内容后更新 PR 说明及状态，避免把关闭误报成已合并；需返工则在该单元 Git 记录中说明问题。执行者下次检查远端回执即可续接，不靠用户转述，也不把仅含认领的分支当内容成果。
- **接收复用证据，队列不拖住研究**：提交过的固定SHA未变时，接收方复用该版本已有的来源、独立评审和检查记录，核关键判断及整合差异；只有新改动、新反证或未覆盖风险才追加调查，不从头重做整项研究。整合后的实际交付树仍跑完整离线入口。等待整合时直接续接同项目下一项不冲突的已授权验收工作；项目结束或调查否定后按项目板选择下一项目，不因局部等待结束整轮。待审堆积则优先接收、修订和合入，不用更多分支掩盖积压；明确拒绝只停对应动作并保断点，授权或输入没有变化时不反复重查同一阻塞。发现阶段先比上次已读SHA，只重读有变化的认领／交付；没有新状态就不提交“仍在等待”或要求用户转述。效率按既有M4的接收等待、实质返工和交付证据观察，不从账号数或提交数推定翻倍。
- **通知边界**：Git 保存可复查的状态，PR 提供提案、评审和变更对照；它们不保证唤醒另一会话。上述检查由仍在运行或按既有安排恢复的执行者完成；恢复时读取项目、断点及下一步并继续已授权工作，不把既有调度的正常续接再列为用户审批项。没有活动任务时如实记等待／结束及恢复条件；未配置并验证事件接收端时，不声称 webhook 已送达、持续在线或全天自动执行，也不因本约定新增凭据、调度或权限。[一手，2026-10-17：[GitHub PR](https://docs.github.com/en/pull-requests/reference/pull-requests)、[webhook](https://docs.github.com/en/webhooks/about-webhooks)]

## 3. M4 运行信号的统计口径

- **周报与进度**：窗口为UTC+8周一00:00至下周一00:00，未满周标截止；沿用既有周报，不以单元数衡量进度。TASKS报三项：①A／B实际在线／内容执行比例及未知覆盖，另列Git空档代理，二者不混用；运行状态仅在变化时记录时间、项目、原因、断点及下一步，未覆盖时段不插值，未设定并核实可运行窗口前不报真实百分比。②满足整体验收且有远端交付证据的项目完成数，K1–K7映射P1–P7，部分交付另列，新项目不改旧分母。③固定首尾main回执SHA，按同一分类计算协作净字节／内容净字节，同时附新增／删除行（不识别重命名）及正文／研究小计；协作为docs/collaboration含归档及AGENTS／CLAUDE，内容为README＋docs／domains扣除协作，research目录单列研究，其余路径排除并报量。内容净增≤0时报比值不适用，不把压缩当负效率；跨类移动单列。每段超过1小时的Git空档分别写A／B已知原因、证据等级和未知范围，不据共同作者名推断执行者或停机。
- **诊断与改进**：发布尝试／失败、实质返工、交接等待和无人值守中断仍作辅助诊断，不作为完成项数。分母或运行段缺失写未知，结果不明单列；自报与平台回执分开，局部阻塞不归因整段。诊断后在既有细则或执行安排中改正，只有同口径后续证据才报提效，不另增过程文档或为填信号提交空状态。
