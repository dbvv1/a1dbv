# 方向校准提示词（2026-10-13，发给 dot 和云端 Codex）

> 背景：10-13 一天内新建了 16 个分支和 20 份研究记录，多数是“一个项目一份”的单例，另外新增了 `docs/practical-tools/` 模块。内容质量不差，但有分散成案例库和工具清单的风险。这份提示词用于把工作拉回核心问题。

```text
先读 AGENTS.md 开头新增的“方向锚点”。它由我维护，优先级高于研究方向文档和另一端的建议；你只能提出修改，不能自行改写。

本轮先做方向复盘，再做新研究：

1. 归类：把 docs/research/ 中 2026-10-12、10-13 的记录逐份归到四条主线，写一张表放进 docs/research/README.md：
   - 列：记录、主线、改变或确认了哪条建议、新证据是什么；
   - 归不进任何主线、也没有改变任何建议的，标“候选合并”。
2. 收敛：
   - “候选合并”的记录，把有用的一两句并入相关记录或专题后删除原文件；
   - 同一主线下讲同一机制的多份记录，合成一份。
   目标是研究记录总数下降。完成后在回复里给出合并前后的数量。
3. 回到主线：
   - 在四条主线里挑一条当前证据最弱的，做一轮深入调查：至少一项新证据，并改进一篇专题的具体建议；
   - 不要开新的单项目调查，除非它直接回答这条主线的问题。
4. 不新建目录、模块或编号专题。docs/practical-tools/ 已决定撤销：把每个工具的采用判断并入已有专题（用量和会话 → 02 或 17；worktree → 08；代码与文档检索 → 03 或 04；浏览器反馈 → 23；评审自动化 → 09；账号与网关 → 02），每个工具只保留问题、原生基线、判断和一句局限；更新所有指向它的链接后删除整个目录。
5. 定位中性：全仓（含 README、专题、research、collaboration）去掉“作者 / 用户的习惯、主力工具、个人偏好”之类的表述。内容可以继续侧重 Codex，但理由用证据或读者需求说明。

收尾按“方向锚点”的每轮上限执行。回复用三个标题：
- 已完成（附提交 SHA 和检查）；
- 方向自检（逐条回答锚点里的四个问题）；
- 需要我决定（最多三条）。
```

## 云端 Codex（方向补充与提交评审）的提示词

> 上面的提示词只发给 dot（执行端）。云端 Codex 负责补充探索方向和评审提交，用下面这份，避免两边同时改同一批文件。

```text
先读 AGENTS.md 开头的“方向锚点”。它由我维护，优先级高于研究方向文档；你可以提出修改建议，但不能改写它。dot 本轮在做方向复盘：研究记录归类与合并、撤销 docs/practical-tools/ 并入专题、全仓中性化，以及一条主线的深入调查。这些执行工作不要重复去做。

你的两项职责：

1. 评审 dot 的提交（绑定精确 SHA，只看新增的增量）。用锚点检查：
   - 每份新增或保留的研究记录，开头是否写了“主线 / 改变的建议 / 新证据”，内容是否对得上；
   - 研究记录总数是否下降，合并时有没有丢掉真实的反证或会改变建议的限制；
   - practical-tools 是否已经完整并入专题、链接是否都已更新、目录是否已删除；
   - 是否还有“作者 / 用户的习惯、主力工具、个人偏好”这类表述；
   - 是否新建了目录、模块或编号专题，或者超过了每轮上限。
   范围内没问题，就在 TASKS 里写一行“范围内通过”；有问题，才写评审记录，每条附文件位置和修改建议。

2. 补充探索方向（只在四条主线内）：
   - 找出四条主线里证据最弱、或者最可能改变现有建议的问题，给出至多 3 个候选，每个写明主线、要回答的问题、可能的一手来源、预期会改变哪条建议；
   - 候选写进 docs/research/BACKLOG.md 对应主线下，标明“候选，未认领”；不自己开新研究记录，除非它是现有记录的追加；
   - 如果你认为锚点本身需要调整，把理由写在回复的“需要我决定”里，不要直接改。

回复用三个标题：
- 评审结论（附 SHA 和每条问题）；
- 方向候选（至多 3 个）；
- 需要我决定（最多三条）。
```
