## 链条二：固定评分通过，为什么仍不能证明测试工作流有效

### 实现与对照

`checks.py` 从 evaluator 一侧加载固定 public 测试和 held-out 测试，不读取候选的 tests/。这一设计有价值：Agent 不能靠删除自己工作区的测试使固定行为检查变绿。held-out 的小域 oracle 用整数集合重建连续段，与参考修复的区间归并算法不同；因此不是用同一个算法给自己打分。超大端点、生成器、输入不变等也有专门用例。**[一手：实现]**

本次直接运行评分器，并仅在临时副本改变输入：

| 候选 | public | held-out | accepted |
|---|---|---|---|
| 原始缺陷 | 4 方法通过 | 7 方法运行，记录 790 个失败子用例 | false |
| 只用 max 修正嵌套区间，不新增回归测试 | 4 通过 | 7 通过 | true |
| 上一修复不变，候选 tests 文件换成一个必失败测试 | 4 通过 | 7 通过 | true |

第三项另外从候选根目录执行 `python3 -m unittest discover -s tests -v`：运行 1 个测试，退出 **1**；评分器仍 accepted=true。前后 `intervals.py` SHA256 均为 `7babd93738c9bf84dd4fe73506ec495408da08317751228d152a82c9800a1fa9`。因此差异不是换了实现，也不是只看测试文件猜测结果。**[经验：本次实际运行]**

### 审计判断

这同样是**已经披露的边界**：README 说评分不自动检查新测试质量、编辑范围与过程，协议另要求人工检查；结果 schema 已分开记录 `accepted_behavior`、回归 red/green、scope 与 tests_weakened。这里不应提交“评分器必须信任候选测试”的修复，那反而会破坏固定评分的独立性。

真正需要避免的是**研究指标错位**：B 条件的两行指令要求运行项目测试、添加有效回归；固定 grader 的 accepted 却只测行为。即使 A/B 全都 accepted，也不能推断这些指令毫无收益；即使 B 更好，也不能单凭 accepted 推断改进来自新增测试。需要检查各项实际发生了什么。

在未来真实实验中，分别记录行为正确、有效回归、范围合规和人工返工；缺少后几项时，结论限于行为评分。不要临时把多个指标随意加权成一个总分，也不因这次审计就新增 runner。先人工完成少量真实产物的完整判读，才能判断值得自动化哪一段。**[研究：本仓库分析与采用判断]**

## 新发现：本侧数值校验脚本在优化模式下静默失去校验

**需要修复，优先级中。** `scripts/research/verify-catalog-compare.py` 的关键比较均使用 Python `assert`。`python -O` 或环境变量 `PYTHONOPTIMIZE` 会删除这些语句，但循环计数与 JSON 输出继续执行。于是“检查行/字段数”看似正常，实际没有执行关键相等性判断。这段脚本由方向端在 `401829f` 引入，另一端只是保留整合；责任不是另一端新增的回归。**[一手：实现；经验：复现]**

本次对同一份 Catalog Compare 报告副本运行两次。该副本把 `exact-default` 的 key `0007` 的 delta 从 `1` 改为 `1.00000000000000001`，CSV 原输入不变：

| 运行方式 | 退出码 | 输出 |
|---|---|---|
| `python3 scripts/research/verify-catalog-compare.py CHECKOUT BAD_RESULTS` | 1 | `AssertionError: ('exact-default', '0007', 'delta')` |
| `python3 -O scripts/research/verify-catalog-compare.py CHECKOUT BAD_RESULTS` | 0 | 仍输出 41 行、102 数字字段，未报告 delta 错误 |

两次都是本次执行；未调用模型。`CHECKOUT` 使用固定 `c5e645fefff8b80a4634777c91776fe9ca3ed187` 的公开合成输入，`BAD_RESULTS` 为已有报告的临时副本，不修改上游仓库。原始普通模式验证并未因此失效，也没有证据表明历史运行开启了优化。

**最小修复要求（D8）**：验收比较改为优化模式下也执行的显式失败，或者在任何数据处理前明确拒绝优化模式；不要只在 README 写“请不要用 -O”。好输入正常通过，坏 delta 在普通与优化模式均不得输出成功计数并退出 0；`PYTHONOPTIMIZE=1` 路径也检查。使用可公开的最小合成夹具做回归，不依赖审阅者的临时下载目录。无需新增验证框架。

为何完整离线入口没有发现它：入口运行的基础与实验套件没有覆盖这个研究脚本的优化模式。128 项测试通过与这条具体失败并不矛盾。D3 的合并过程本身未制造这个问题，但“整合后所有校验都可靠”的更宽结论应被拒绝。

## 这次审计怎样改变方向

“流程是否有效”必须拆成它试图改变的具体行为：补测试、避免乱改、获取新知识、减少等待，不能只看最终测试绿不绿。强 Agent 在简单任务上可能已达到行为评分上限，这时重复该任务只会再次看到全绿，不能回答用户是否该加 Superpowers。

因此下一步更值得投入的是 D4/D6 中的真实决策链：实际失败是什么，原生能否自行纠正，某项知识/工具/规则改变了哪一步，是否同时增加了人的等待和后续维护成本。任务记录与离线夹具仍可作为辅助，但不继续把扩大它们的规模当作研究主线。

反证条件也明确：若后续真实任务显示没有结构化记录就反复漏验，而轻量记录稳定减少漏项且维护成本可接受，应提高采用建议；若原生已稳定完成同样验收，新增记录只是重述，便应省掉。当前没有该对照，不能以本次合成探测预判收益。
