# Audit Protocol

## 0. 先理解项目，再审计项目（强制前置门）

任何领域正式审计前，必须先重建“项目意图与当前阶段”，不得直接从缺失功能清单开始。

先交叉核对：
1. 用户明确确认的项目目标、范围和阶段决定（以仓库当前有效文件为准）。
2. 对应产品/领域 brief、设计任务书、阶段路线和验收标准。
3. 当前 TASKS、项目板、质量标准和最近有效决策。
4. 产品案例的 README、docs/brief.md、docs/quality.md（若适用）。
5. 最近审计报告及已接受/已拒绝/延期的意见。

开始技术审计前，报告必须先写“审计前置理解”：
- 产品/领域使命；
- 当前阶段/里程碑；
- 本阶段必须交付；
- 本阶段明确不做；
- 当前技术、平台和制作范围；
- 质量标杆及具体比较维度；
- 本阶段完成条件。

每项都要给出仓库路径或明确用户决定作为依据。关键范围无法确认时标记冲突/unknown，并向项目责任人提出针对性问题；不得用行业常见产品形态填补。

**禁止：**
- 把路线图未来阶段的功能缺失直接列为当前 P0/P1。
- 把目录存在某技术专题推断为当前必须采用该技术。
- 把商业标杆完整产品范围当成当前阶段验收范围。
- 把功能数量、模式数量、地图/英雄/引擎覆盖面当成质量本身。
- 未理解用户明确的品类变体前套用泛化模板（例如将单线大乱斗 MOBA 按传统三路 MOBA 审计）。
- 只列缺少什么，不检查已有实现的正确性、手感、质量、稳定性和实际效果。

若 Brief 与用户决定、产品仓库 brief、TASKS 或其他权威文件冲突，必须列出冲突及依据，不得静默择一。

## 1. 开始前
1. 读取最新 main，记录 commit SHA、日期和仓库。
2. 读取 README、对应 brief、Wave Register、上一轮报告及相关 TASKS。
3. 产品案例读取产品仓库最新 main 和当前设计/质量 brief。
4. 说明审计边界、工具权限和无法访问的内容。
5. 不将聊天记忆或旧报告当作当前仓库事实。

## 2. 证据等级
- 源码/文档：当前仓库文件和路径。
- 自动测试：命令、结果、覆盖范围。
- 实际运行：版本、环境、操作和观察。
- 人工体验：试玩、画面、声音或可用性评价。
- 外部参照：官方文档、源码、论文、产品或社区实证。

未实际验证标为 unknown/未验证。源码存在不等于已运行，测试通过不等于产品质量达标。

## 3. 质量审计要求

审计必须同时回答：

### A. 已有内容/实现的具体质量
- 已实现机制是否正确、完整、稳定？
- 是否存在 bug、边界错误、性能问题、体验割裂或不一致？
- 操作、反馈、视觉、音频、AI 行为、可读性和可维护性具体怎样？
- 与当前阶段质量标杆相比，差距具体在哪里、原因是什么？
- 已有测试覆盖什么、没覆盖什么？运行/人工体验证据在哪里？

### B. 当前阶段真正需要补齐的内容
- 哪些缺口阻碍当前阶段交付？
- 哪些是质量提升而非功能缺失？
- 哪些属于未来阶段，当前应明确延期？
- 哪些现有方案应保留、修复、替换或淘汰？

每个主要发现标注类别：
- **阶段阻塞缺陷**：当前不修无法达到目标。
- **阶段内质量差距**：当前已有功能/内容质量不足。
- **未来阶段差距**：路线图后续内容，当前不作为缺陷。
- **技术债/维护风险**：当前不一定影响体验，但增加后续成本。
- **证据不足**：当前无法得出结论。

不为增加任务数量拆碎工作。每项建议尽量包含证据、影响、优先级、目标、写入范围、验收标准、依赖和风险。

## 4. Wave 1 边界
- 只读，不改生产代码、正式规范或 main。
- 可提出任务候选，但不得自行派发或声称已被接受。
- 每个领域建议 3–8 项；不足可少于 3 项，不强制造任务。
- 检查现有 TASKS/inbox，避免重复。

## 5. 报告格式
1. 元数据：波次、领域、审计者、仓库、main SHA、日期。
2. **审计前置理解**：产品目标、当前阶段、必须交付、明确不做、技术范围、质量标杆、完成条件及证据。
3. 总体判断和成熟度（仅针对当前阶段）。
4. 证据与审计范围。
5. 已有实现/内容的具体质量评价。
6. 关键发现（按严重程度，并标注发现类别）。
7. 已有成果：保留/修复/合并/淘汰。
8. 当前阶段与标杆的具体差距。
9. 未来阶段差距（单独列出，不混入当前阻塞项）。
10. 任务候选：目标、类别、优先级、写入范围、验收标准、依赖。
11. 未验证事项与证据缺口。
12. 下一次审计触发条件。

## 6. Git 交付
- 每份报告独立文件，不覆盖历史。
- 有写权限时从最新 main 创建独立分支提交；不直接写 main。
- 不修改其他审计者文件。
- 无写权限时返回完整 Markdown 和建议路径。
- 报告提交后更新 Wave Register 的状态、commit SHA 和链接。
- 建议进入正式规则或生产代码前，必须由责任人接受并形成 TASKS/local-jobs 任务。
