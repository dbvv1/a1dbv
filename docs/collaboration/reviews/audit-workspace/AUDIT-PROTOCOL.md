# Audit Protocol

## 开始前
1. 读取最新 main，记录 commit SHA、日期和仓库。
2. 读取 README、对应 brief、Wave Register、上一轮报告及相关 TASKS。
3. 说明审计边界、工具权限和无法访问的内容。
4. 不将聊天记忆或旧报告当作当前仓库事实。

## 证据等级
- 源码/文档：当前仓库文件和路径。
- 自动测试：命令、结果、覆盖范围。
- 实际运行：版本、环境、操作和观察。
- 人工体验：试玩、画面、声音或可用性评价。
- 外部参照：官方文档、源码、论文、产品或社区实证。

未实际验证的内容标为 unknown/未验证。源码存在不等于已运行，测试通过不等于产品质量达标。

## 评价要求
- 先判断真实水平，再提出改进。
- 对照 brief 目标和行业/产品参照。
- 区分核心缺陷、质量提升、可选探索。
- 指出已有成果应保留、合并、修复或淘汰的部分。
- 不为增加任务数量而拆碎工作。
- 每项建议尽量包含证据、影响、优先级、目标、写入范围、验收标准、依赖和风险。

## Wave 1 边界
- 只读，不改生产代码、正式规范或 main。
- 可以提出任务候选，但不得自行派发或声称已被接受。
- 每个领域建议 3–8 项；不足可少于 3 项，不强制造任务。
- 检查现有 TASKS/inbox，避免重复。

## 报告格式
1. 元数据：波次、领域、审计者、仓库、main SHA、日期。
2. 总体判断和成熟度。
3. 证据与审计范围。
4. 关键发现（按严重程度）。
5. 已有成果：保留/修复/合并/淘汰。
6. 与标杆的差距。
7. 任务候选表：目标、优先级、写入范围、验收标准、依赖。
8. 未验证事项与证据缺口。
9. 下一次审计触发条件。

## Git 交付
- 每份报告独立文件，不覆盖历史。
- 有写权限时从最新 main 创建独立分支提交；不直接写 main。
- 不修改其他审计者文件。
- 无写权限时返回完整 Markdown 和建议路径。
- 报告提交后更新 Wave Register 的状态、commit SHA 和链接。
- 建议进入正式规则或生产代码前，必须由责任人接受并形成 TASKS/local-jobs 任务。
