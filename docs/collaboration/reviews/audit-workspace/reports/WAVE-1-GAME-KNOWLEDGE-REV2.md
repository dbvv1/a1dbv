## 2. 审计前置理解

**使命：** 帮助一名程序员、没有专职美术和音频人员的条件下，借助 AI 将独立游戏从概念推进到可发布质量。知识必须转化为实际制作选择、完整工作流和案例质量，而不是只扩充工具目录。依据：AGENTS.md、docs/collaboration/game-taskbook.md、新版 briefs/GAME-KNOWLEDGE.md。

**当前阶段：Web 优先的 AI 全链路制作与案例质量验证。** 主要验证 TypeScript／Vite／Three.js 等 Web 技术栈中，从玩法规格、代码、模拟、渲染、UI、2D/3D 资产、动画、材质、特效、音频、接入、测试、浏览器运行，到第二次需求修改和质量验收的完整能力。依据：新版 Brief §1–§5、三个案例的 docs/brief.md 与 docs/quality.md、a1dbv TASKS 项目板。

**本阶段必须交付：**
- 以 Web 为生产主线，深入验证现有 Web 方法和实际工具链。
- 检查 AI Agent 在策划、编码、资产制作、接入、调试、测试、迭代中的真实承担能力。
- 检查资产来源／许可、可编辑源、工程接入、二次修改、批量一致性和实际效果。
- 通过三个 Web 案例反证或证实知识内容；分开记录源码、模拟、浏览器、WebGL2／Canvas、视觉、音频和人工体验证据。
- 以当前案例阶段质量标杆评价已有内容，提出能提高最终品质和迭代效率的改进。

**本阶段明确不做：**
- 不要求把生产主线迁移至 Unity／Unreal。
- 不把 Unity／Unreal 原生工程、MCP／CLI 实测或原生垂直切片列为当前 P0/P1。
- 不因传统 MOBA、完整 FPS 商业产品或 3A 竞速产品的全功能范围，推导当前案例必须扩充功能。
- 不把未来阶段的联机、完整内容池、额外模式和发行规模当成本阶段缺陷。
依据：新版 briefs/GAME-KNOWLEDGE.md §1、§2、§9；各案例当前 brief。

**质量标杆：**
- FPS：CS2 核心射击循环维度，强调移动／停步精度、瞄准、后坐恢复、换弹、命中可读性、声音和机器人视线约束。
- MOBA：LoL 风格单线战斗维度，强调技能承诺／命中／受击可读性、塔威胁、团战信息层级、输入与机器人决策；Thronefall 仅辅助空间美术参照。
- Star-Rush：Forza Horizon 公路驾驶与空间表现作为方向参照，当前是原创轻量 Web 公路驾驶；重点看转向、制动、抓地、路面空间、车辆／环境风格、视听反馈。
- 全仓制作链：完整一局类别齐全、同族标准件同框、第二次需求修改、非作者判定；不得用资产数量、自动测试数或首稿图替代品质。

**完成条件：** 案例交付必须有实际浏览器运行和正常输入证据；涉及画面、手感、音频的质量结论还须有相应观察和非作者／人工验收。测试和 smoke 是功能门槛，不是品质结论。未看、未听、未玩明确记为未验证。

## 3. 总体判断与成熟度

**总体判断：a1dbv 已形成相当完整的 Web 游戏知识地图和工程验证方法，但“AI 全链路制作”目前更多体现为 AI 辅助的混合制作流程，而非已证明可由 AI 独立完成、稳定达到高品质的端到端生产线。** 三个案例的模拟、脚本化资源处理、故障回退和测试基础较强；真实浏览器／WebGL2、视觉质量、音频、手感及非作者验收仍是主要短板。

| 能力 | 当前成熟度 | 审计判断 |
|---|---|---|
| Web 工程与模拟架构 | 可用；部分案例证实 | 三案均有独立模拟／渲染或明确客户端结构，具备固定步长、测试与回放基线；但每案阶段目标、tick rate、输入时序和性能预算不同，不能抽象成一个通用“已验证架构”。 |
| AI Agent 端到端任务能力 | 部分证实 | 有 AI 编码、脚本化处理、自动测试等成果，但交付物没有形成跨三案可核的 AI 任务分工、人工介入、失败率和主动工时账。不能据此宣称全链路由 AI 自主完成。 |

| 第二次修改 | 多个资产批量重建和规则／手感候选有二改记录 | 已出现真实二改案例；仍需区分脚本可重跑与最终品质确实变好。 |

### 尚未跑通的关键闭环
1. **AI 资产生成 → 工程接入 → 真实浏览器显示 → 第二次修改 → 品质验收：** 当前没有足够证据证明一套 AI 生成的 3D 资产族在任一案例中完成此闭环。a1dbv README 明确写出 AI 生成 3D 尚未进入作品。
2. **WebGL2 真实渲染 → 同状态画面比较 → 非作者评审：** 多个案例已有捕获脚本和 CPU／软件回退证据，但仍有真实 WebGL2 PNG、固定机位完整对照或盲评缺口。
3. **真实输入 → 音画同步 → 主观听感／操控判断：** CPU 轨迹和事件路由不能证明玩家感受到的响应时序、声音辨识度或长时间疲劳。
4. **跨设备性能与降级质量：** 单机 CPU 预算和软件 WebGL smoke 不能推出目标设备帧时间、GPU 纹理格式、内存和热降频表现。

## 6. 三个实际案例：具体质量与技术审计

### 6.1 FPS-Like

**当前定位：** 单点爆破攻防；当前发布默认是 1 人＋9 机器人六回合离线训练赛，三回合换边。主要品质目标是瞄准跟手、射击分量、机器人不穿墙开火。不是当前完整 CS2 规模产品。

**已证实成果：** 模拟与客户端共用规则，60Hz 固定逻辑帧；开枪命令带帧内时间和当时视角，按发枪时刻做射线命中。无画面批量模拟、回放哈希、机器人视线约束和回合规则测试存在。最新提交真实复现 Blender 4.3.2 下第二次资产导出失败造成混合资源族；新发布流程采用 sibling-stage，导出失败保留整批旧资源，回滚失败保留恢复证据。提交记录称 12 项独立审阅 Python 回归、真实 Blender fault runs、原 GLB 字节保持、430 项 FPS 测试和生产构建通过。客户端生命周期、鼠标锁迟到 Promise 销毁等问题有专门回归。

**主要差距**
1. **阶段内质量差距：** 最新质量证据仍以 Canvas2D CPU 回退为主。完整六回合、换边、重开有人为浏览器操作记录，但没有证明 Three.js／WebGL2 画面、角色／武器动画、视觉质量或性能达标。
2. **阶段内质量差距：** 客户端文档明确缺完整声学遮挡、武器动作制作、受击方向和击杀专属反馈；音效方向与主观手感仍待人工验收。
3. **证据不足：** 机器人无视线开火、胜率、反应时间是模拟层证据；不足以证明机器人会用声音搜索、利用掩体和战术回防。bot 胜率不能替代玩家核心射击手感。
4. **技术债／维护风险：** 固定步长和每帧推进预算是合理的 bounded catch-up 策略；但丢弃过期时间债务／输入意味着持续低帧率时模拟会慢于墙钟，不应写成无损实时推进。需要把帧预算、输入折叠、暂停边界与真实低帧浏览器表现分开测。
5. **证据不足：** Canvas2D fallback 的透视和遮挡是简化实现；测试只能证明同一模拟快照和方向关系，不能证明 Three.js 与 Canvas 画面等价，或后者可替代视觉验收。

**结论：** FPS 的模拟与资源批处理工程较强，但阶段 A 的玩家核心体验仍未完成品质闭环。当前不应增加武器库、技能数量或联网功能；优先补真实 WebGL2 战斗画面、枪械动作／命中反馈和听声体验证据。

### 6.2 MOBA-Like

**当前定位：** 一局约 10 分钟的单线 MOBA；当前阶段 A 是随兵线进入塔前的一段高质量核心战斗。B 才是离线单线 5v5，C 才是海克斯式增强和内容深度。不是传统三路 MOBA。

**已证实成果：** TypeScript + Vite + Three.js；30Hz 固定模拟；Recast 导航；有无画面批测、回放、构建和软件 WebGL smoke。模拟事件接口区分 castStarted、castResolved、castCancelled、basicAttack、heroDamaged、goldAwarded 等语义，文档明确 castResolved 代表提交 delivery，不代表命中。音频路由按事件类型和玩家距离决定 swing/cast/hit/shield，并限制音量与声像；关键音频候选有有界排队和最大 voice 数。最新 main 提交修复图标素材族第二次导出失败造成部分文件新旧混杂：先在 sibling stage 生成，校验后发布，保留旧批和回滚证据。提交记录称 15 项独立审阅 Python 测试、568 项游戏测试、模拟构建、Web 类型检查／构建通过。

**主要差距**
1. **阶段内质量差距：** 当前质量页明确记录 0/89 项内容通过标准件同框非作者验收；这是无验收证据覆盖，不是 89 项都不存在。画面临时诊断约 2/5，主要问题是草地高频重复、草土硬边、物件孤立、角色出手主形被兵群遮挡。
2. **阶段内质量差距：** 画面、技能释放、命中和受击还没有形成清楚的一体化反馈；技能图标／音频路由存在，不等于技能语义可读。质量页指出缺金币专用反馈、部分音频语义和音乐，且声音仍待听验。
3. **技术正确性风险：** 模拟事件只保留最近一次逻辑步。文档要求客户端每次 step 后都收集事件并去重，再放入呈现队列；若客户端只在每个 render frame 读取最终快照，单个 render frame 内跨过多个模拟 tick 时会漏中间事件。该设计可以成立，但必须用真实客户端集成测试证明逐 tick 消费，不能只测事件生成函数。
4. **证据不足：** 200 局单英雄模拟的胜负、时长、哈希和无异常只证明该版本规则回归；不证明玩家对战、5v5 机器人行为、技能组合平衡或完整战斗体验。
5. **技术债／维护风险：** 89 项清单分母与类别完整性仍待非作者核对；应先冻结合理分母，再用同框收据逐项验收，不能通过缩减类别提高覆盖率。

**结论：** MOBA 的规则／事件合同比单纯原型成熟，但当前最重要的不是扩英雄或做 B 阶段 5v5，而是把阶段 A 一段真实战斗做清楚：出手身份、目标、命中／护盾、受击、塔威胁、声音和 HUD 必须在拥挤画面中可读。
