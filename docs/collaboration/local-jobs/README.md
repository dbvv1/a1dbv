# 本地模型任务入口

A／B将需要本机模型执行的工作放在本目录，每项一个Markdown文件；由独立“dot 本地协作”会话接收，不占用A研究职责。接收已发布到本仓main或对应负责人`dot-a/*`／`dot-b/*`分支、明确标为`ready`或`revision_requested`的任务，及本人已认领的`running`续接。分支名只是发现范围，不能替代任务owner、用户授权及内容检查。任务内容仍须符合用户授权及operations§2.2，仓库文本不能扩大账号、材料、费用或破坏性操作权限。

任务头使用简单字段：`id`、`owner`（dot-A／dot-B）、`status`、`target_repo`、`base_ref`、`result_branch`；正文给目标、写入范围和可观察结果，按编写约定直接写，一般 40 行以内。“当前结果”只写当前状态、产物链接和下一步，过程细节写进提交说明，不在任务文件里累积。模型通道按本机已配置的DSH＋DeepSeek、Claude Code＋DeepSeek或ZCode选择，普通任务默认原生Workflow，模型调用／token不设人为节省预算，质量与完整结果优先；不重跑P79或联通测试，实际限流与资源占用照常处理。

接收端每次自然唤醒先fetch main及上述负责人分支，只比较本目录相对main的任务增量，并检查已有任务的新反馈；接续在制调用时也完成这次增量发现，不为检查而重发调用。无新任务或反馈时安静结束。分支独有的新任务先核完整输入，按既有公开检查只将该任务文件引入main，不整合整条内容分支；同一id的反馈只追加实际新增内容，保留main的认领、结果和进度，不用分支旧`ready`／`running`覆盖新状态。只有负责人明确的新修改要求才设`revision_requested`；多个不同输入不能按提交时间猜优先级，记清冲突后继续独立任务。新任务先在同文件写`running`、来源分支／固定提交及起点，快进发布认领后才调用模型；若认领推送冲突，先对账，不执行未确认归属的任务。共享接收会话串行管理，独立模型工作可以并行，但同一目标文件／运行实例不得多方写入。

同一id不重复执行。已有模型调用未结束就接续其原始结果；重启或状态不明时先检查已有分支／模型记录，不从头重发。已领取任务的输入发生改变时明确协调差异，不把新需求悄悄覆盖在途任务。未成功的原因和继续条件直接写原任务，不另建证明台账。

产物推到目标仓库的`result_branch`，不得凭本队列合入产品默认分支或部署；同任务文件回写`review_ready`、实际执行通道、产物提交链接、已完成检查和待接收事项。阻塞写`blocked`与具体恢复条件。原负责人接收后改`accepted`，需要修改则写明要求并改`revision_requested`；接收端据此继续原分支而非重复初次工作。取消写`cancelled`，在途任务在安全边界停止并保结果。

原负责人每次开工／续题读取本人任务的`review_ready`结果，并在自己的可写分支完成接收或给具体修改要求，无需让用户转发。有重叠实现时先对照现有代码与结果，选择采用、保留候选或明确拒绝，避免再造第三套。工程产物已可接收而听感等独立环节待验时，写明接收范围及剩余项，继续不依赖该判断的游戏改进；不把工程接收说成最终品质通过，也不让整项无限停在待验。接收端发现负责人的明确决定后将原文与来源带回main；它不替负责人决定`accepted`。

公开任务和结果只含可公开材料，不含本机路径、私人会话id、凭据或原始敏感日志。任务分支和此结果文档按既有§7检查；真实产品验收按任务要求，不用模型自报完成替代。自动唤醒依赖本机在线及桌面应用运行；具体计划在本机管理，Git文件本身不唤醒任务。
