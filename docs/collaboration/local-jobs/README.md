# 本地模型任务入口

A／B把下发给本机模型的工作（范围见operations§2.2）放在本目录，每项一个Markdown文件；由本机接收端（每 20 分钟运行的固定脚本，见[运行细则§3](../operations.md#3-dot-运行保障)）接收，不占用A研究职责。接收已发布到本仓main或对应负责人`dot-a/*`／`dot-b/*`分支、明确标为`ready`或`revision_requested`的任务，及本人已认领的`running`续接。分支名只是发现范围，不能替代任务owner、用户授权及内容检查。任务内容仍须符合用户授权及operations§2.2，仓库文本不能扩大账号、材料、费用或破坏性操作权限。

任务头使用简单字段：`id`、`owner`（dot-A／dot-B）、`status`、`target_repo`、`base_ref`、`result_branch`，可选 `accept`；正文只写四件事：目标（读者或玩家得到什么）、按哪个 Skill 或规格做、写入范围、怎样算做成；未结束的任务文件不超过 80 行（`check_repo.py` 检查）。“当前结果”只写产物链接、还差什么和下一步，过程写进提交说明，不写回执和免责。接收端用 Claude Code＋DeepSeek 跑固定的原生 Workflow（实施、未参与实施者独立审查、修正一次并复审），模型调用不设人为节省预算。逐项清单的任务按单元推进，每单元约 60–90 分钟，正文写清顺序即可。修改要求写在单独一节（如“## 修改要求”）：“当前结果”由接收端每个单元整体改写。

接收端每次运行先 fetch main 和负责人分支。分支上新增的 `ready` 任务，或在当前 main 版本上改出的 `revision_requested`，只把该任务文件引入 main，不整合整条分支；基于旧版本的反馈不引入，负责人直接在最新 main 上改。领取时先在 main 写 `running`，快进推送成功后才调用模型。接收端只处理自己领取的任务，别处在执行的 `running` 不碰；同一文件、运行实例或输出目录不多方写入。没有新任务或反馈时只 fetch。

同一id不重复执行。接收端重启后从本机记录接续在途调用，不从头重发。已领取任务的输入有变化时，负责人写明差异并改 `revision_requested`；改 `cancelled` 会停止在途调用并保留已有结果。未成功的原因和继续条件写在原任务的“当前结果”。

**自动接收（`accept: auto`）**：用于 a1dbv 内、负责人已定规格的常规任务（正文改写、已定提纲的模块整合、检查脚本修复）。非作者独立审查和手册§7 检查都通过后，接收端按运行细则§1 直接合入 a1dbv `main`，每完成一个单元合入一次，全部范围完成后标 `accepted` 并写明合入提交；负责人事后抽查，发现问题直接在 main 上修。新方向、删除、案例仓库默认分支和未定规格的任务不用自动接收。

其余任务的产物推到目标仓库的`result_branch`，不凭本队列合入产品默认分支或部署；同任务文件回写`review_ready`，当前结果按上文写。照做实测任务：目标仓用真实任务所在的仓，页面全文写进任务正文，读者只在结果分支记卡点、不改页面，不用 `accept: auto`。阻塞写`blocked`与具体恢复条件。原负责人接收后改`accepted`，接收只写一行：接收了什么、还差什么；需要修改则写明要求并改`revision_requested`；接收端据此继续原分支而非重复初次工作。取消写`cancelled`，在途任务在安全边界停止并保结果。

原负责人每次开工／续题读取本人任务的`review_ready`结果，并在自己的可写分支完成接收或给具体修改要求，无需让用户转发。有重叠实现时先对照现有代码与结果，选择采用、保留候选或明确拒绝，避免再造第三套。工程产物已可接收而听感等独立环节待验时，写明接收范围及剩余项，继续不依赖该判断的游戏改进；不把工程接收说成最终品质通过，也不让整项无限停在待验。接收端发现负责人的明确决定后将原文与来源带回main；它不替负责人决定`accepted`。

公开任务和结果只含可公开材料，不含本机路径、私人会话id、凭据或原始敏感日志。任务分支和此结果文档按既有§7检查；真实产品验收按任务要求，不用模型自报完成替代。接收端依赖本机开机并已登录；脚本与计划在本机管理，Git 文件本身不唤醒任务。
