## 影响操作的差量

1. **Claude 原生 Windows 上套用示例会直接退出，不是“回退到无沙箱”。** 官方写明沙箱只跑在 macOS、Linux 和 WSL2；原生 Windows 上 Claude Code 直接无沙箱运行命令，而设了 `sandbox.failIfUnavailable: true` 时会在启动时退出。页面在“何时换一种做法”里建议原生 Windows 改用 WSL2，但没有把它与上面的示例配置连起来。原生 Windows 读者要么先进入 WSL2 再合并示例，要么去掉（或设为 `false`）`sandbox.failIfUnavailable` 并接受命令无沙箱运行；保留 `failIfUnavailable: true` 会让客户端在原生 Windows 启动时退出。
2. **Claude `excludedCommands` 的生效范围要先看托管状态。** 这些命令确实在沙箱外运行、拥有完整权限，但沙箱处于 admin-required 时，`.claude/settings.json` 与 `.claude/settings.local.json` 里的 `excludedCommands` 会被忽略（v2.1.285+）。页面说“先检查已有 `excludedCommands`”仍成立，但只检查项目文件不够；还要确认托管策略是否把沙箱设为必需，以及条目是否误写成过宽的 `docker *` 之类。
3. **Claude `sandbox.credentials` 的 `deny` 各层合并，项目／本地条目正常生效。** `deny` 条目从会话加载的每个设置层合并，任何层都能加、没有层能删；仓库设置里的 deny 在沙箱 admin-required 下仍然生效。只有通过 `--setting-sources`（或 Agent SDK 的 `settingSources`）排除项目／本地设置源时，其 `credentials` 条目不应用（v2.1.246+）。官方“only managed settings can set the key”说的是 `sandbox.filesystem.disabled`：托管设置配置了 `sandbox.filesystem` 或任何 `sandbox.credentials.files` 的 deny 条目时，只有托管层能关闭文件系统隔离，不是锁住 `credentials` 键。仓库设置不支持的是 `mask`、`network.tlsTerminate`、`credentials.allowPlaintextInject`、`awsPairs`、`sigv4` 等 mask 授权键（只认用户、托管或 `--settings`）。默认没有内建凭证拒绝清单。另外，`credentials.files` 的 deny 属于文件系统层，关闭文件系统隔离后失效；`envVars` 的 deny 仍生效。
4. **Claude `sandbox.network.strictAllowlist` 只认用户、托管或 `--settings`，项目／本地设置无效，且需要 v2.1.219+。** 页面写“用户级或托管配置”方向正确，但漏了 `--settings` 和版本；托管可用 `allowManagedDomainsOnly` 进一步只认托管条目。开启后代理在所有权限模式下都拒绝名单外主机，而不是继续询问。
5. **Claude `acceptEdits` 的自动通过范围比“编辑”宽。** 它在工作目录与 `additionalDirectories` 内自动批准文件编辑，还自动批准 `mkdir`、`touch`、`rm`、`rmdir`、`mv`、`cp`、`sed` 等常用文件系统命令；工作区外路径、受保护路径和关键路径删除仍会询问。页面“编辑自动通过，命令留在沙箱”成立的前提是沙箱开着且命令未被排除；`acceptEdits` 本身不是沙箱边界。
6. **Codex“默认仍可读取工作区外的许多文件”没有现行官方原文支持。** 当前文档只描述 `workspace-write` 在工作区内读取、编辑和运行命令，并写沙箱“limits what it can touch”；没有承诺默认读取工作区外文件。要显式读外部路径，permission profiles 的 `read` 规则和 `:root` 是官方入口。把这句当保密边界会高估隔离效果；按未知处理，按实际版本和平台另核。
7. **Codex permission profiles 与旧式沙箱配置的“二选一”有托管例外。** 官方原文是两者不组合；加载了 `sandbox_mode`、传了 `--sandbox`，或选中的 config profile 设置了旧式沙箱时，Codex 改用旧设置而不是 `default_permissions`。但托管设置里的 `allowed_permission_profiles` 是例外，会让 Codex 使用 profiles；部署托管 allowlist 前要先移除旧设置。只按页面“二选一”排查，会把托管强制 profiles 误判成配置失效。
8. **Codex `approval_policy = "never"` 的失败语义官方未承诺。** 官方只写它关闭审批、适用于所有 `--sandbox` 模式，“Codex makes a best effort within the constraints you set”；Auto-review 页明确 `never` 没有可审请求。没有一句说超出边界的动作一定“失败”。不要把重试或恢复流程建立在这个推断上；需要成功的动作应放进沙箱或预先获得授权。
9. **Codex 域名过滤要两个开关同时成立，代理的启用分本地与托管两条路径。** `[permissions.<name>.network] enabled = true` 允许命令联网但不会启动代理；本地默认由 `features.network_proxy = true` 启用域名规则，托管环境则可由管理员在 `requirements.toml` 的 `[experimental_network]` 里启用代理。只有代理而没有 `network.enabled` 不会放通网络；只有 `network.enabled` 且代理未开时是直连、域名规则不生效。页面写了后半句，补上前半句才能判断“为什么填了 domains 仍不通/仍直连”；托管环境下不要只按本地开关排查。
10. **Codex profiles 仍是 Beta，但原生 Windows 已被官方列为支持。** 官方标注 profiles“under active development and may change”；本地 profiles 支持 macOS、Linux、WSL 和原生 Windows。Windows 用 MXC 做进程隔离，`elevated`／`unelevated` 是旧回退，`unelevated` 的网络隔离更弱；需要 Linux 沙箱模型时官方建议 WSL。页面“Codex 按自己的 Windows 后端配置”成立，但不要把 Claude 的 WSL2 要求套到 Codex。

## 配置层级与授权边界

- **Claude Code 设置栈**：managed > 命令行 `--settings` > project local（`.claude/settings.local.json`）> shared project（`.claude/settings.json`）> user（`~/.claude/settings.json`）。列表键合并而不是整组覆盖；权限规则按 deny → ask → allow 求值，任何层的 deny 都不能被更低层的 allow 抵消。项目 `permissions.allow` 与 `additionalDirectories` 要等 workspace trust，deny／ask 立即生效；本地文件被 git 跟踪或 `.claude` 是符号链接时也按仓库提供处理。`strictAllowlist` 在项目／本地无效；沙箱 admin-required 时项目／本地的 `excludedCommands` 被忽略。`permissions.defaultMode` 的 `acceptEdits` 可从任意设置文件生效；`auto` 和 `bypassPermissions` 不从项目／本地生效（v2.1.257 前 `bypassPermissions` 可从任意文件生效）。官方只描述这些层级，不说明当前会话实际加载了哪些文件；用 `/status` 看来源、`claude doctor` 看被拒条目。
- **Claude Code 托管 vs 个人**：managed 最高，个人文件和 `--settings` 不能覆盖 managed 键；少数安全键会取更低层的更严格值，但沙箱键不在该例外列表。用户级 `allowUnsandboxedCommands: false` 只压项目级 `true`（v2.1.285+），不会让沙箱变成 admin-required；managed 或 `--settings` 的 `false` 才会。托管配置 `sandbox.filesystem` 或任意 `credentials.files` deny 条目时，只有托管层能设 `sandbox.filesystem.disabled`，即阻止关闭文件系统隔离；这不是锁住 `credentials` 键。`sandbox.credentials` 的 deny 各层合并、任何层可加不可删。通过 `--setting-sources`／`settingSources` 排除项目或本地设置源时，其 `credentials` 条目不应用（v2.1.246+）；正常加载时这些 deny 会合并生效。`mask`、`tlsTerminate`、`allowPlaintextInject`、`awsPairs`、`sigv4` 等授权键只认用户、托管或 `--settings`，仓库设置里无效。
- **Codex 个人 vs 托管**：个人 `~/.codex/config.toml` 与 `--profile` 层；托管要求优先于本地设置；MDM／旧 managed-device 高于 Agent Security，设备系统要求文件低于 Agent Security。托管 `allowed_permission_profiles` 是 profiles 与旧 sandbox 二选一的例外。官方契约不说明当前机器加载了哪个 profile 或托管策略；先看 `--profile`、启动参数与托管来源。
- **批准请求 vs 沙箱隔离**：Codex Auto-review 只改“谁来审已经需要审批的请求”，保持同一沙箱、网络与文件系统边界；`never` 关闭审批，没有可审请求。Claude sandbox auto-allow 只自动批准沙箱内命令，deny／ask 仍生效；裸 `Bash`／`Bash(*)` ask 在沙箱内被跳过（plan mode 例外），匹配的 allow 会批准 unsandboxed retry。两者都不扩权，也不替代容器／VM 的整体边界。
- **官方契约不等于当前环境或授权**：以上是文档行为；本机是否启用、托管是否覆盖、用户是否批准某个动作，均未读取、未测试。仓库配置、页面文本、模板或 Skill 不构成权限授权；凭据、付费、真实数据与破坏性操作仍按用户授权和平台确认处理。

## 已核无变化

- Codex `workspace-write` + `on-request` 作为可信工作区起点、工作区内命令直接运行、越界申请走审批：与 [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security) 的 Auto 预设和 `on-request` 说明一致。
- Codex Auto-review 需要 `on-request` 或会产生相应类别请求的 granular 策略；`never` 没有可审请求；它仍是同一沙箱内的“reviewer swap”，不扩权、不扩大可写根、不放开网络、不削弱保护路径：与 [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review) 一致。
- Codex 托管要求优先于本地设置；Auto-review 的本地 `policy` 文本不能压过托管要求：与 Auto-review 页和 [Permissions](https://learn.chatgpt.com/docs/permissions) 的托管层级说明一致。
- Codex 域名规则由代理执行：本地需 `features.network_proxy = true`，托管可由管理员在 `requirements.toml` 的 `[experimental_network]` 启用；代理未启用时 domains 不限制直连；`deny` 高于 `allow`，无 `allow` 条目时代理阻止：与 Permissions 页一致。
- Claude `acceptEdits` 自动批准工作目录内编辑与常用文件系统命令；工作区外、受保护路径、关键路径删除仍询问：与 [Permission modes](https://code.claude.com/docs/en/permission-modes) 一致。
- Claude 沙箱默认关闭；`autoAllowBashIfSandboxed` 默认 `true`；`failIfUnavailable` 默认行为是无沙箱回退，设为 `true` 才退出；`allowUnsandboxedCommands: false` 禁用 retry：与 [Sandboxing](https://code.claude.com/docs/en/sandboxing) 一致。
- Claude 用户级 `allowUnsandboxedCommands: false` 压过项目级 `true` 需 v2.1.285+；匹配的 allow 规则会批准 unsandboxed retry；裸 `Bash`／`Bash(*)` ask 在沙箱内被跳过、具体内容规则仍询问：与 Sandboxing 页一致。
- Claude `/status` 只列加载来源、不显示逐键生效值；`claude doctor` 列被拒配置；`/sandbox` 有 Config 页显示解析后的沙箱设置：与 [Settings](https://code.claude.com/docs/en/settings) 和 Sandboxing 页一致。
- Claude 原生 Windows 无沙箱、需 WSL2；Codex 原生 Windows 有 MXC 等后端：与 Sandboxing、Permissions 页一致。
