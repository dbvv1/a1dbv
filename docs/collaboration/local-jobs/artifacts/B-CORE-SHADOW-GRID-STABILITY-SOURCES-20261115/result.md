# 相机平移时的阴影格稳定：来源清单与单灯取舍

**在 MOBA 这种单方向光、固定 1024 阴影图、固定 ±22 正交盒、near 1/far 70、灯光位置与 target 随 focus 同向量平移且方向不变的用法里，来源支持的最小一步是：保持盒尺寸、方向、近远裁和 bias 不变，只把光源空间的平移量取整到整纹素；不要为此引入级联。** 这是“锁投影平移”，不是改玩法规则：焦点、光照方向、相机、bias、级联／分割和输入都不动。该做法成立的前提是光相机 x／y 投影尺寸和方向逐帧不变。对 MOBA 的固定 ±22 正交盒，主相机旋转、FOV、near／far 都不改变 x／y 投影尺寸与方向（near／far 只改深度范围与覆盖）；会破坏稳定的是改光相机 ortho 盒尺寸、把盒子按视锥或场景紧贴拟合（CSM／FIT_TO_CASCADES／动态深度包围）、改灯光方向，以及远原点浮点精度和晚一帧／更新顺序这类实现边界。是否真的需要做，要 dot 在真实机位先证实可见抖动；本卡只查源，不预设当前已发生。

**floor 还是 round，来源没有统一答案。** three.js／Bevy 用 floor，Godot 的 `Math::snapped` 是 round（`floor(x/step + 0.5) * step`），Babylon／PlayCanvas／three.js SunLightShadow 也用 round；两者都能把相位锁成常数网格，差别在 floor 对齐边、round 最大位移更小。关键是同一基准、同一单位、跨一格只动一步，不能在同一盒上混用；都要带 guard band，且盒尺寸不能变。

**清单边界。** 以下 175 条来自工作流六个角度的收集与追链，均经过一次链接可达性核对；可达不等于正文逐句复核。S 级逐行核对过（2026-11-18；Filament／PlayCanvas 用 main，其余为固定 commit 或官方文档），A 级多数打开了行号、个别只核到文件或接口；main/master 链接会移动。未运行浏览器、GPU、Unity、three.js 或 MOBA；不判断性能、画质或“抖动已修复”。

## 筛选标准与排序

排序按五个条件，依次降低：

1. **直接性：** 是否给出锁原点、投影偏移或包围球的具体做法，且能落到单灯固定尺寸盒。
2. **可核性：** 是否有源码行、官方文档或可运行示例，单位与近远裁能复算。
3. **条件与边界：** 是否写明旋转／缩放／FOV／远原点／更新顺序／精度失效。
4. **区分度：** 是否把“栅格取整”和“级联包围盒稳定”分开。
5. **消费者：** 是否直接对应 MOBA `world.ts` 或 three.js `LightShadow` 路径。

没有任何一项同时满足全部；S 级满足 1+2+5 或 1+2+4，B 级补 3，C 级防止误诊，D 级用于对照和排除干扰。

## 前几项为什么最值得深挖

1. **MOBA `world.ts` + Three.js `LightShadow`（S 级前两条）——先确认相位从哪进来。** 前者给出真实参数：单个 DirectionalLight、1024×1024、±22 正交盒、near 1/far 70、bias -0.0004／normalBias 0.035，`light.position` 与 `target` 每帧按 focus 平移，没有任何取整；后者是这盏灯每帧实际走的矩阵更新路径，shadow camera 位置直接取灯光世界位置、`lookAt` 目标。两条合起来说明：要锁的就是这条连续平移；不看这两条，后面的引擎实现都只是抽象公式。它们也给出小测试的固定输入（44 世界单位 ÷ 1024 = 0.04296875 世界单位／texel）。

2. **Microsoft《Common Techniques》+ DirectX 示例（S 级 Microsoft 两条）——最接近“单灯一步”的官方公式。** MSDN 把单位写成 `vWorldUnitsPerTexel = cascadeBound / bufferSize`，对 ortho min/max 做 divide→floor→multiply，并明确前提是光源投影尺寸逐帧不变；示例代码同时给出 `FIT_TO_SCENE`（先 pad 成恒定尺寸再取整）和 `FIT_TO_CASCADES`（紧贴时旋转仍 shimmer）的对照，以及 `m_bMoveLightTexelSize` 对应的 divide→floor→multiply 代码（示例 atlas 每级宽高即 `m_iBufferSize`，没有 +1；宽高各多 1 像素（英文原文“1 pixel larger in width and height”）是 MSDN 正文的说明）。它不含级联依赖，最适合直接翻成单灯实现。

3. **Godot `renderer_scene_cull.cpp` + PR #82974（S 级 Godot 条 + B 级 #82974）——生产引擎的常量与一个现成的单位反例。** 源码把 8 个视锥角点包成球、半径乘 `texture_size/(texture_size-2)` 各留 1 texel，再用 `unit=(radius+soft_shadow_expand)*4.0/texture_size` 对 x/y min/max 做 `Math::snapped`，注释原文就是“This trick here is what stabilizes the shadow”。#82974 把同一段的 `*2.0` 改成 `*4.0` 修 2-split 不稳定——这是“单位／相位算错就会抖”的现成负例，正好用来设计“跨格只移动一次”的断言。

4. **Babylon `cascadedShadowGenerator.ts`（S 级 Babylon 条）——把两层拆得最清楚。** `stabilizeCascades` 先把视锥角点包成球、半径 ceil 到 1/16 后取 ±radius 作为级联范围（消除旋转引起的尺寸变化）；再用 rounding matrix 把世界原点投到光空间、取 texel 小数偏移后 `Math.round`，把 `2/mapSize` 的平移加进投影矩阵，z 不动。它默认关闭、并明确损失精度，适合回答“为什么稳定化是有代价的选项，不是免费开关”。

5. **PlayCanvas 固定 `shadowBounds`（S 级 PlayCanvas 条）——最接近“同尺寸盒常向量平移”的现成实现。** `texelSize=2*halfSize/texels`，中心 x/y 用 `Math.round` 吸到整纹素；先把 `halfSize` 乘 `texels/(texels-1)` 补偿吸附最多移动半个纹素（`halfSize` 增量 = `texelSize/2`），另留 `BOUNDS_BORDER` 个空 texel；源码注释写明目的是静态 caster 的阴影不随 bounds 移动而 shimmer。它只覆盖固定 bounds 路径，正好对应 MOBA 的单灯盒，而不是级联。

6. **Bevy `cascade.rs`（S 级 Bevy 条）——数值稳定的前置条件写得最直白。** light 只用旋转构造正交基；`cascade_diameter` 取视锥体对角线最大值后 `ceil` 成整数，`texel_size=diameter/texture_size`；near-plane center 按 texel 整数倍 `floor`，并直接构造 `cascade_from_world` 而不求逆。注释点名“near_plane_center 必须在 texel 整数倍上才可精确表示”——这解释了为什么“看起来只是取整”的改动在浮点下仍可能抖。

7. **Stride 的两种模式 + Filament 的 `stable` 契约（S 级 Stride／Filament 四条）——产品级取舍的词汇表。** Stride 把 `ProjectionSnapping` 和 `ViewSnapping` 做成两个显式选项，各自有实现和“降低阴影图质量”的注释；Filament 的 `stable=true` 直接写明会关闭所有影响稳定性的分辨率增强（含 LiSPSM），换来显著更低分辨率但稳定的阴影，并记录远原点、相机与场景一起移动、不能旋转 light frustum 等失效边界。它们适合回答“固定分辨率下先保稳定，还是先保清晰”。

8. **The Witness 2010 + MJP（B 级）——方法出处与失效边界的一手叙述。** The Witness 明确写“把 shadow map 世界坐标吸附到 texel 大小的整数倍”，并用 Valient 的视锥切片包围球；MJP 把做法总结为“按 split 拟合球固定投影尺寸，再把投影按 texel 增量吸附”，并指出只在级联分区不变时有效，改 FOV 或 near/far 会失效。它们补上官方源码不解释的“为什么”和“什么时候不成立”。

**值得先读的反例。** [Bevy #7393](https://github.com/bevyengine/bevy/issues/7393) 说明“看到的抖动”可能只是低分辨率下 texel 明暗跳，不是相位漂移；[Babylon 23766](https://forum.babylonjs.com/t/jitter-in-shadow-map-while-moving-light/23766) 是渲染顺序／晚一帧；[Unity 887059](https://discussions.unity.com/t/intense-shadow-flickering-only-when-camera-moves/887059) 是透明材质与 near clip；[Babylon 39767](https://forum.babylonjs.com/t/shadow-jitter-but-only-on-intel-and-intermittently/39767) 是驱动；[GameDev.SE 148943](https://gamedev.stackexchange.com/questions/148943/shadow-shimmering-when-moving-objects) 是只动场景物体。先排除这些，再谈锁投影。

## 同尺寸阴影盒常向量平移：待执行的小测试

**目的：** 只验证“相机焦点在固定盒内做亚 texel 平移时，阴影投影的纹素相位是否锁住”，不验证画质、性能或玩法。测试基于 MOBA `world.ts` 的现成参数；不改产品行为，先作为独立的最小复现。

**固定输入（先记录，后执行；不得随结果改）：**

- 代码版本：MOBA-Like `79bdb57`（package.json 固定 three `0.186.1`，即 r186）；消费者路径按 r186 `LightShadow.js` L213-L226 复核（本卡早期引用的 `0af9729` 为 r180，对应 L194-L207）；记录 renderer 类型。
- 单个 DirectionalLight；shadow map 1024×1024；ortho left／right／top／bottom = ∓22（宽高各 44 世界单位）；near 1／far 70。
- 灯光：`position = focus + (-12, 26, 12)`，`target = focus`；方向为 `(12, -26, -12)` 归一化，逐帧不变。
- `bias = -0.0004`，`normalBias = 0.035`；相机 FOV 45；阴影过滤类型按实际记录。
- 单位：一个 shadow texel 在光空间覆盖 `44/1024 = 0.04296875` 世界单位。
- 吸附基准（先选定，三种不混用）：本测试只覆盖 **floor 光空间中心**（three.js CSM 路径），中心 x／y 除以 texel 后 floor 再乘回，跨格步长恰为 1 texel（0.04296875 世界单位）。round 中心（Babylon／PlayCanvas／Stride）步长也是 1 texel，但跨格采样要取 0.4→0.6（0.9→1.1 在 round 下同格、0 步）。对 min/max 分别 snap 时步长取决于网格单位：Godot 的 `unit=(radius+soft)*4/texture_size` 是 2 texel，跨一格移动 2 texel（0.0859375 世界单位），且它的 `Math::snapped`（round）网格单位是 2 texel、边界落在 1 texel 的奇数倍，采样取 0.9→1.1（一步 2 texel）；MS 示例的 floor min/max 网格是 1 texel，采样 0.9→1.1 只移动 1 texel。同一断言不能共用一套采样点。

**步骤：**

1. 固定一个机位，记录 shadow camera 的 view／projection 矩阵、光空间中心 `(x, y)`、bias／near／far、盒子半尺寸。
2. 只在光空间 x／y 方向平移 focus（`d = a·right + b·up`，保证光空间 z 不变），按上面的 floor 中心基准，依次把相位设为 0.1、0.25、0.5、0.9、1.0、1.1 个 texel（1.0 正好落在格线上；这些点在 floor 下含义明确，0.5 不是边界）；每步把 `light.position` 与 `light.target.position` 同向量平移，不改方向。snapped 中心可先在离线脚本或临时分支算出，不要求产品先改。
3. 记录每一步的 snapped 中心或投影平移量，以及组合 shadow 矩阵（view × projection）。
4. 断言：
   - **亚格内（<1 texel）：** 组合 shadow 矩阵相同（浮点容差事前设定为 0 或 1e-6），阴影采样相位不变；若实现是移动光源原点，view 矩阵也应不变；若是加投影偏移，projection 会随 view 连续变化，但组合矩阵不变；
   - **跨格（floor 中心，0.9 → 1.1）：** 恰好一步 1 texel（0.9→1.0 跨过格线，1.0→1.1 不再移动），不是 0 步也不是 2 步；若改用 round 中心，跨格断言必须改成 0.4→0.6（一步 1 texel）；Godot 的 min/max snap 用 2 texel 网格（round），对应 0.9→1.1 一步 2 texel；
   - **连续平移 N 个 texel：** 恰好 N 次阶跃，单调、无来回；
   - **不变量：** 光空间 z、near／far、盒子半尺寸、bias／normalBias 均不变。
5. 反向走同一路径，阶跃次数相同，无滞后。

**反例（单独记录，不能算通过）：**

- 只转灯、相机不动：纹素网格相位变 → [godot-skydome #5](https://github.com/GamesNotDeveloped/godot-skydome/issues/5)、[Godot 论坛 104449](https://forum.godotengine.org/t/shadows-from-directionallight3d-are-jittery-depending-on-global-position/104449)。
- 改光相机 ortho 盒尺寸，或把盒子改为随视锥／场景紧贴、级联或动态深度包围拟合：texel 世界尺寸或覆盖变 → [MSDN 常量前提](https://learn.microsoft.com/en-us/windows/win32/dxtecharts/common-techniques-to-improve-shadow-depth-maps#moving-the-light-in-texel-sized-increments)、[MJP](https://mynameismjp.wordpress.com/2013/09/10/shadow-maps/)、[Unity FOV 843824](https://discussions.unity.com/t/shadows-buzz-when-camera-fov-changes/843824)。相机旋转、FOV、near／far 对当前固定 ±22 盒不改 x／y texel 尺寸（near／far 只改深度精度与覆盖），不能单独列为失效条件；只有盒随视锥拟合时，这些参数才连带改变投影尺寸。
- 紧贴场景或级联深度包围逐帧变：包围尺寸变 → [MS 示例 FIT_TO_CASCADES](https://github.com/walbourn/directx-sdk-samples/blob/1ad8f0f6a3e4d9be7e54ca52640ac12b6565ab0c/CascadedShadowMaps11/CascadedShadowsManager.cpp#L878-L955)、[Babylon 50011](https://forum.babylonjs.com/t/why-does-the-shadow-edge-will-keep-shaking-as-long-as-the-camera-moves-when-the-autocalcdepthbounds-set-to-true-in-cascaded-shadows/50011)、[Filament #6130](https://github.com/google/filament/pull/6130)。
- 远原点：半径随微动变化或浮点精度不足 → [Godot #84510](https://github.com/godotengine/godot/issues/84510)、[Godot #72015](https://github.com/godotengine/godot/issues/72015)、[Filament #7149](https://github.com/google/filament/pull/7149)、[MJP #6](https://github.com/TheRealMJP/Shadows/issues/6)。

## 偏差、近裁白边与不随呈现改变的输入／规则

- **bias 是独立规则。** MOBA 的 `bias=-0.0004`／`normalBias=0.035` 不要因为加吸附而改。[DigitalRune](https://digitalrune.github.io/DigitalRune-Documentation/html/3f4d959e-9c98-4a97-8d85-7a73c26145d7.htm) 说明 bias 以 shadow-map texel 计、随分辨率与距离缩放；[Unity URP ShadowUtils](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Runtime/ShadowUtils.cs#L476-L520) 也把 depth／normal bias 按 texel 换算。吸附改变采样位置，不改变深度比较的偏移规则；调 bias 也不能消除网格相位漂移。
- **近裁白边先查覆盖，不要用吸附掩盖。** 屏幕边缘或近处出现无阴影白边时，先查 near／far 与 caster 是否被裁：[MS 示例](https://github.com/walbourn/directx-sdk-samples/blob/1ad8f0f6a3e4d9be7e54ca52640ac12b6565ab0c/CascadedShadowMaps11/CascadedShadowsManager.cpp#L878-L955) 单独计算 near／far，[Godot](https://github.com/godotengine/godot/blob/b070e63b161aa816afac71dcfc9d60859d38f220/servers/rendering/renderer_scene_cull.cpp#L2329-L2359) 用 `z_min_cam` 与 far+1e6，[three.js SunLightShadow](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/lights/SunLightShadow.js#L250-L288) 把 near 放到 caster ceiling。改 near／far 会改变深度精度与稳定前提，必须作为输入记录并重新基线。
- **guard band 是取整的一部分。** MSDN 说贴图宽高各比投影覆盖的 texel 数多 1 像素防索引越界；[GameDev.SE 86107](https://gamedev.stackexchange.com/questions/86107/shadow-map-shimmering-indexing-outside-the-shadow-map) 的实测是 min 减 1、max 加 1 texel 才消除黑角；Godot 用 `texture_size-2` 各留 1 texel；three.js 用 `radius/(1-1/resolution)` pad 半 texel；PlayCanvas 留 `BOUNDS_BORDER`。若盒边缘看到缺阴影或白边，先补 guard band，不要改玩法或悄悄放大盒子。
- **呈现只改投影平移。** 世界坐标、focus、灯光方向、相机、盒子尺寸、near／far、bias、级联／分割和玩法输入都不随呈现改。three.js 的 CSM 是移动 `light.position`／`target`（两者同向量，方向不变）；Babylon／Stride／Filament 是加投影偏移（z 不动）；[Wicked Engine](https://github.com/turanszkij/WickedEngine/blob/b96676a414f47eb6866c8db56102336fa2849032/WickedEngine/wiRenderer.cpp#L2988-L3070) 的注释明确光源 view 矩阵保持原点、吸附只发生在投影矩阵。若采用 three.js 路径，必须确认没有别的系统把 `light.position` 当玩法输入。
- **测试规则先定后跑。** “亚格内矩阵相同、跨格恰好一步”是事前断言；看到结果后不得放宽容差、删采样点或改步长。输入版本、机位、灯参数和过滤类型都要在跑之前写死。
