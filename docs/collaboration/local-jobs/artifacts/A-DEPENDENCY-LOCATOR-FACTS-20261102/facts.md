## 读者入口

只拿本卡找操作入口时，按这个顺序做：

1. 用与构建相同的 manifest、target、features、锁文件和本地缓存跑一次 `cargo metadata`；`--manifest-path`、`--filter-platform`、`--locked`／`--offline` 按构建条件取舍。`$manifest` 必须是消费包自己的 `Cargo.toml`（含 `[package]`），不能是只有 `[workspace]` 的虚拟工作区根：对虚拟根 `cargo metadata` 能正常返回，但 `packages[]` 只含成员、没有虚拟根，后续 `manifest_path` 相等匹配必然零结果；工作区先列成员 `cargo metadata --format-version 1 --no-deps | jq -r '.packages[] | [.name,.manifest_path] | @tsv'`，选定消费包再传它的 manifest。`$target` 必须写实际 triple：`dep_kinds[].target` 只会是 manifest 里的字面量 triple、`cfg(...)` 或表示不限平台的 null，不会出现 `--filter-platform` 接受的 `host-tuple`。要少写一次 host triple，先取 `target=$(rustc -vV | sed -n 's/^host: //p')`，再让 `--filter-platform`、jq 和 `rustc --print cfg` 用同一实际 triple；或只在 `--filter-platform` 传 `host-tuple`，jq 与 rustc 用实际 triple。本卡命令只查该消费包的直接依赖边。
2. `$dep` 用 crate 名：lib target 的 `-` 换成 `_`，重命名依赖用新名，不是包名。本命令只查消费包的直接依赖边；`$dep` 是传递依赖时不会命中，处理见第 5 步。
3. 读结果的 `manifest_path` 和 lib target 的 `src_path`，沿调用进入实际模块；`cfg_to_check` 非空时在与 metadata 相同的 cfg 集合下核对：`rustc --print cfg --target "$target"` 后追加实际生效的那组 rustflags（rustc 不读 Cargo 的配置，要显式展开）。Cargo 的 rustflags 来源互斥，按 `CARGO_ENCODED_RUSTFLAGS` > `RUSTFLAGS` > 所有匹配的 `target.<triple>`／`target.<cfg>.rustflags`（彼此合并）> `build.rustflags` 只取第一组（`CARGO_ENCODED_RUSTFLAGS` 按 `0x1f` 分隔展开）；不要合并不同来源，否则会把构建未使用的 `--cfg`／`-C target-feature` 算进去。确认这些边在目标平台成立。
4. metadata 只解析、不编译；API 兼容性仍要跑消费包当前 target／feature 的 `cargo check`／`cargo build`／测试。
5. 无结果按 feature、crate 名、普通边是否在当前 target 激活（`cfg_to_check` 里的 `cfg(...)` 要人工核对，不能只看条目存在）、`manifest_path` 是否匹配、`$manifest` 是否为消费包而非虚拟工作区根、`$dep` 是否为消费包的直接依赖排查；本命令只查普通依赖，dev/build 边被有意排除。查 dev 边时把 `select(.kind == null` 里的 `.kind == null` 换成 `.kind == "dev"`，保留 `select(` 与其后的 target 条件后重跑，仍按构建 target 核对。查 build 边时同样只换 `.kind == null`，但不要沿用 `--filter-platform "$target"` 收窄的图：它可能已丢掉只在 host 激活的 build 边，改用不带 `--filter-platform` 的 metadata 取 `dep_kinds[].target` 后按 host cfg 核对（jq 的 `$target` 传 host triple；host 取 `rustc -vV` 的 `host:`，`rustc --print cfg` 不带 `--target` 或传该 triple），或看实际构建／`cargo tree --edges build`（默认按 host；见「不确定项」的 build-dependencies 条）；路径还要核格式、盘符大小写与 `\\?\` 前缀（Git Bash 的 `/c/...` 与 `C:\...` 不同）。**本命令只遍历消费包的直接依赖边**（先 `select(.id == $consumer)` 再取 `.deps[]`），传递依赖的 crate 名不会出现在这里：先用 `cargo tree -i <crate>`，或从 `resolve.nodes` 找到引入它的直接依赖所在包，换该包的 manifest 重跑；也可去掉 `select(.id == $consumer)`，在全部 `resolve.nodes[].deps[]` 中按 `.pkg`／包名查传递边。另核 `--filter-platform` 与 jq 的 `$target` 是否为同一实际 triple（`host-tuple` 只在 Cargo 内部替换，JSON 不会出现，传错会丢掉所有字面量 triple 的边）。

修正后的 jq 保留三类普通边：`target` 为 null、`target` 等于 `$target` 的字面量 triple，以及 jq 无法求值但可能对目标激活的 `cfg(...)`；后一类列进 `cfg_to_check`，要人工核对后才算命中。**以下 manifest／dep／target 是本仓 opensrc 示例**；换项目时替换为你的**消费包** manifest（含 `[package]`，不能是虚拟工作区根）、crate 名和构建 target，`target` 不要沿用示例的 Linux triple（用 `build.target`，或取 `rustc -vV` 的 `host`）。工作区先列成员再选消费包：`cargo metadata --format-version 1 --no-deps | jq -r '.packages[] | [.name,.manifest_path] | @tsv'`；也可把 jq 的 `select(.manifest_path == $manifest)` 换成按包名／`id` 选。先把 manifest 路径转成与 Cargo 输出相同的格式，否则 Git Bash 的 `/c/...` 与 Windows 的 `C:\...` 直接比较会零结果：

```bash
set -o pipefail
# 以下 manifest/dep/target 是本仓 opensrc 示例：换项目时替换为消费包的 manifest（含 [package]，不能是虚拟工作区根）、crate 名和构建 target。
# 本命令只遍历消费包的直接依赖边（.deps[]）；查传递依赖见第 5 步。
manifest=packages/opensrc/cli/Cargo.toml       # 换成消费包（含 [package]）的 Cargo.toml，不能是虚拟工作区根
dep=reqwest                                  # crate 名（lib target 名），不是包名
target=x86_64-unknown-linux-gnu              # 示例的 Linux triple，务必换成你的构建 target
# 按构建追加 feature 开关，例如 features=(--features 'pkg/feat')、features=(--all-features) 或 features=(--no-default-features)。
features=()
# 仅当构建实际由 RUSTFLAGS 提供 flags 时，运行前 export RUSTFLAGS="<与构建相同的 rustflags>"（含 --cfg、-C target-feature），Cargo 的平台过滤会带上它；构建用的是 CARGO_ENCODED_RUSTFLAGS，或 target.<triple>/<cfg>.rustflags、build.rustflags 时，让 metadata 与构建在同一 Cargo 配置下运行，不要另设 RUSTFLAGS（来源互斥且 RUSTFLAGS 优先，会覆盖构建实际使用的那组）。
# --locked --offline 按第 1 步取舍：无锁文件或本地缓存未备齐时删掉这两项，否则 metadata 会直接失败。
manifest_abs=$(realpath "$manifest")
if command -v cygpath >/dev/null 2>&1; then
  manifest_abs=$(cygpath -w "$manifest_abs")   # Git Bash/MSYS: /c/... → C:\...
fi
cargo metadata --format-version 1 --locked --offline \
  --manifest-path "$manifest" --filter-platform "$target" "${features[@]}" |
  jq -e --arg manifest "$manifest_abs" --arg dep "$dep" --arg target "$target" '
    . as $m
    | $m.packages[] | select(.manifest_path == $manifest)
    | .id as $consumer
    | $m.resolve.nodes[] | select(.id == $consumer)
    | .deps[] | select(.name == $dep)
    | . as $edge
    | [.dep_kinds[]
       | select(.kind == null
           and (.target == null or .target == $target
                or ((.target // "") | startswith("cfg("))))]
    | select(length > 0)
    | . as $kinds
    | $edge.pkg as $id
    | $m.packages[] | select(.id == $id)
    | {name, version, source, manifest_path,
       lib_src: [.targets[] | select(.kind | index("lib")) | .src_path],
       dep_kinds: $kinds,
       cfg_to_check: [$kinds[] | select(.target != null and .target != $target) | .target]}
  '
```

原生 Windows 的 PowerShell 没有 `realpath`，用 `(Resolve-Path $manifest).Path` 得到 `C:\...` 再传给 jq；不要拿 Git Bash 的 `/c/...` 去比。先看一条 `manifest_path` 的实际格式再决定是否转换：若 Cargo 本身在 Cygwin／WSL 里运行并输出 POSIX 路径，就不转。盘符大小写或 `\\?\` 前缀不同仍会让 `==` 失败；Windows 上可先去掉 `\\?\` 前缀、对两边 `ascii_downcase` 后再比，或改用包名＋版本定位。

`$target` 必须是实际 triple：`--filter-platform` 只在 Cargo 内部把 `host-tuple` 替换成 host triple，JSON 的 `dep_kinds[].target` 仍是 manifest 里的实际 triple、`cfg(...)` 或无平台限制的 null，不会写 `host-tuple`。要少写一次时先 `target=$(rustc -vV | sed -n 's/^host: //p')`，再让 `--filter-platform`、jq 和 `rustc --print cfg` 用同一实际 triple；或只在 `--filter-platform` 传 `host-tuple`，jq 与 `rustc --print cfg` 仍用实际 triple（rustc 不接受 `host-tuple`）。`target: null` 表示不限平台，字面量 triple 可直接与 `$target` 比较；`cfg(...)` 不能由 jq 求值，上面的 jq 会保留并列入 `cfg_to_check`，仍要在与 metadata 相同的 cfg 集合下逐条核对：`rustc --print cfg --target "$target"` 后只追加实际生效的那组 rustflags（rustc 不读 Cargo 配置，裸跑只覆盖 target 内置 cfg）。Cargo 的 rustflags 来源互斥，按 `CARGO_ENCODED_RUSTFLAGS` > `RUSTFLAGS` > 所有匹配的 `target.<triple>`／`target.<cfg>.rustflags`（彼此合并）> `build.rustflags` 只取第一组；`CARGO_ENCODED_RUSTFLAGS` 按 `0x1f` 分隔展开，不要合并不同来源（同时设 `RUSTFLAGS` 与 `build.rustflags` 时 Cargo 只用 `RUSTFLAGS`），否则会把构建未使用的一组 `--cfg`／`-C target-feature` 算进去；核对前不能把该边当作已激活（[配置文档](https://doc.rust-lang.org/cargo/reference/config.html#buildrustflags)）。复现构建 feature 时，`--features` 可用 `member/feature` 按工作区成员指定，也可用 `dep/feature` 开所选成员直接依赖的 feature（可选依赖会一并激活）；`--all-features`／`--no-default-features` 都是全局开关，不能只对单个成员开关：`--all-features` 作用于全部选中成员，`--no-default-features` 在 resolver v2/v3 或虚拟工作区下作用于全部选中成员，resolver v1 非虚拟工作区只作用于当前 manifest 所在成员（源码见 [workspace.rs 第 1715–1800 行](https://github.com/rust-lang/cargo/blob/5f94df4789f005f9a352888e8355ffc645b7ed0e/src/workspace/workspace.rs#L1715-L1800)，关键 1780–1794）。若构建只对某个成员用了 `--no-default-features`，metadata 无法精确复现：需用 `--features <其他成员>/default` 显式补回其默认 feature（该成员定义了 `default` 时），或把结果当近似并用实际构建复核。

## 会改变读者操作的差量

**1. `dep` 传的是 Rust 里的 crate 名，不是包名。** `resolve.nodes[].deps[].name` 是依赖的库 target 名；lib target 的 `-` 会换成 `_`，重命名依赖则用重命名后的名字（源码把 rename 里的 `-` 也换成 `_`）。页面的 `dep=reqwest` 能命中，是因为它无连字符；改成 `tokio-util` 会零结果，应传 `tokio_util`。要按包名查，应从 `.pkg` 到 `packages[]` 比较 `name`，或看 `packages[].dependencies[]` 的 `name`（包名）与 `rename`（新名），不要混用两个命名空间。Zed 例：manifest 键是 `reqwest`，包名是 `zed-reqwest`；`.deps[].name` 是 `reqwest`，`packages[].name` 才是 `zed-reqwest`。页面命令输出的 `{name,version,source}` 取自 `packages[]`，所以能看到 fork 的真实包名。

**2. 可选依赖未激活时完全不在 `resolve.deps`，而命令块没有 feature 参数。** 官方写明 “Inactivated optional dependencies are not listed”；不给 feature 选项时，所选工作区成员按 `default` feature 解析，依赖的 feature 仍由各 manifest 的 `features`／`default-features` 合并启用。页面正文说“给 metadata 带上与构建相同的 feature 参数”，但代码块没有 `--features` / `--all-features` / `--no-default-features`，照抄只能看到默认 feature 的图。

复现某次构建时按 flag 的作用域传：`--features` 可给 `package/feature` 按工作区成员指定，也接受 `<所选成员的直接依赖声明名>/<feature>`（重命名依赖用新名；依赖为可选时会一并激活），构建里用了这种写法就要同样传给 metadata；`--all-features`／`--no-default-features` 是不可按成员拆分的全局开关，对每个选中的工作区成员生效，不会开启依赖自己的全部/默认 feature（resolver v1 非虚拟工作区例外，`--no-default-features` 只对当前 manifest 所在成员生效）。单成员 `--no-default-features` 无法精确复现，补回办法见上文；否则可选依赖可能整条不出现。“无结果”应逐项排查：feature 是否激活、`$dep` 是否用了 crate 名、`$dep` 是否消费包的直接依赖（命令只遍历 `select(.id == $consumer)` 后的 `.deps[]`；传递依赖先用 `cargo tree -i <crate>` 或从 `resolve.nodes` 找到引入它的直接依赖所在包，换该包 manifest 重跑，也可去掉该 `select` 在全部 `resolve.nodes[].deps[]` 中按 `.pkg`／包名查）、该普通边是否在当前 target 激活（jq 已保留 `target` 为 null、字面量相等和 `cfg(...)` 三类；`cfg_to_check` 非空时要在与 metadata 相同的 cfg 集合下人工核对，不能只看条目存在）、`manifest_path` 是否匹配（还要核路径格式与大小写，见差量 6）、`$manifest` 是否消费包而非虚拟工作区根（工作区先按 `.packages[]` 的 `name`／`manifest_path` 列成员选消费包）；`--filter-platform` 与 jq 的 `$target` 是否为同一实际 triple（`host-tuple` 只在 Cargo 内部替换，JSON 的 `dep_kinds[].target` 不会出现它）。本代码块的 `select(.kind == null` 只保留普通依赖，dev/build 边被有意排除；查它们把 `.kind == null` 换成 `.kind == "dev"`／`.kind == "build"`，保留 `select(` 与其后的 target 条件。两类边的平台不同：dev 边按构建 target 核对；build 边按 host 核对（`rustc --print cfg` 不带 `--target`，或传 host triple），且 `--filter-platform "$target"` 收窄后的 resolve 可能已丢掉只在 host 激活的 build 边，不能用于判定；应改用不带该 flag 的 metadata 取 `dep_kinds[].target` 后按 host cfg 核对（jq 的 `$target` 传 host triple），或看实际构建／`cargo tree --edges build`（默认按 host；原理见「不确定项」的 build-dependencies 条）。

**3. metadata 的 feature 是全工作区并集，且包含 dev 依赖，不等于这次 build 的 feature 集。** 实现把 `Packages::All`（全部 workspace 成员）和 `HasDevUnits::Yes` 交给 resolver，后者把各成员的 feature 求并集；Cargo Book 的字段注释却写 “based on the enabled features for the 'current' package”，两者不一致。issue #7754（仍在 open，标签含 `S-needs-design`）记录的正是 `cargo metadata` 按工作区解析 feature。因此 `resolve.nodes[].features` 与“某个可选依赖是否出现”可能是消费包实际构建集的超集：别用它判断某 feature 在本次 build 中是否生效；`--locked` 也不锁定 feature 选择。

**4. `--filter-platform` 只筛解析图，而且不会替你读 `build.target`。** 不给该 flag 时，resolve 默认包含所有 target 平台的依赖；给了才按该 triplet 的 rustc cfg 过滤。过滤是**包对级**的：`(pkg, dep_pkg)` 中任一条 `Dependency` 对目标平台激活就保留整个包对，`dep_kinds` 仍写入该包对的全部 `Dependency` 并保留各自原始 `target`；所以条目存在只说明该包对至少一条边对目标激活，`dep_kinds` 可能含其他 target 的边。例如同一 manifest 写 `[target.'cfg(unix)'.dependencies] foo = "1"` 和 `[dev-dependencies] foo = "1"`，在 `--filter-platform x86_64-pc-windows-msvc` 下，包对因 dev 边被保留，`foo` 的 `dep_kinds` 仍是 `{kind:null, target:"cfg(unix)"}` 与 `{kind:"dev", target:null}`；页面的 `select(any(.dep_kinds[]; .kind == null))` 会把 `foo` 误选为 Windows 的普通依赖。本卡的 jq 会保留该 `cfg(unix)` 边并列入 `cfg_to_check`，在 Windows 上核对后排除。`packages` 数组也随解析图收窄，但每个包的 `dependencies` 字段仍是 manifest 的全量声明。实现用 `CompileKindFallback::JustHost`，故意不读 `$CARGO_BUILD_TARGET` / `build.target`，所以必须显式传 target。它还会改变 feature 解析：无 flag 时 `ForceAllTargets::Yes` 让各 target 的 feature 也合并；有 flag 时关闭，resolver v2/v3（2021/2024 edition 默认）下 target 不活跃的 feature 不启用（resolver v1 本来就不区分 target 与 cfg feature）。cfg 表达式按 rustc 的 cfg 求值，官方测试显示 `RUSTFLAGS=--cfg=foobar` 会让 `cfg(foobar)` 依赖进入过滤结果，因此 metadata 要和构建跑在同一 RUSTFLAGS 下。Cargo 求值平台 cfg 时正是把 rustflags 传给 `rustc --print=cfg`（[target_info.rs 第 177–224 行](https://github.com/rust-lang/cargo/blob/5f94df4789f005f9a352888e8355ffc645b7ed0e/src/compiler/build_context/target_info.rs#L177-L224)），所以人工核对 `cfg_to_check` 也要带上同一组 `--cfg`／`-C target-feature`；裸跑 `rustc --print cfg` 只覆盖 target 内置 cfg，会把构建里由自定义 cfg 激活的边误判为未激活。`cfg(feature = ...)`、`cfg(test)` 等本来就不能用于依赖条件。即使过滤正确，也没有安装 target、运行 build script 或检查链接器。

**5. `--locked --offline` 只保证“不联网且不改锁文件”，前提是锁和本地缓存都齐。** `--locked` 在锁文件缺失或解析需要改动时直接报错（exit 101）；`--offline` 只用本地已下载的 crate，官方明确可能得到与在线不同的解析，缺包时失败。在线运行 metadata 会下载依赖（官方测试会显示 `DOWNLOADING`/`DOWNLOADED`），离线时不会。“缺包先补齐锁定依赖”应理解为先用有网方式 `cargo fetch` 或 vendored source 备齐，再离线运行；`--locked` 校验的是依赖与版本解析，不校验 feature、profile、RUSTFLAGS 或构建目标。

**6. `source` / `manifest_path` 定位来源，不证明 API；`lib_src` 是页面自拼的字段。** `source` 对 path 依赖和 workspace 成员都为 null（两者不能只靠它区分），其余为 `registry+` / `git+` / `sparse+URL`；官方说明 `+` 后的值未定义、可能随 Cargo 版本变化，不能当稳定解析规则。`manifest_path` 是解析后包在本机的 manifest 绝对路径（registry 解包目录、git checkout 或 path 目录），`[patch]` 生效时指向 patch 源；它给出“Cargo 实际会编译的那份源码”的入口，不是上游仓库根。`lib_src` 不是 Cargo 字段，而是从 `targets[].src_path`（target 根源文件）拼出来的；`targets[].kind` 对 lib 列的是 crate-type（默认 `["lib"]`），`index("lib")` 会漏 `proc-macro`、纯 `cdylib`/`staticlib`/`rlib` 等非默认 crate-type。且 `src_path` 是 crate 根（通常 `lib.rs`），不是被调用的模块；`mod`/`#[path]`/`include!`、`#[cfg]` 分支和 build.rs 写入 `OUT_DIR` 的生成代码都可能让实际实现不在这份源文件里。`manifest_path` 官方只承诺“绝对路径”，未承诺 canonical；页面用 `realpath` 做字符串相等，在符号链接路径下可能对不上（源码的路径处理不保证 canonical）。原生 Windows 还多一层格式差：Git Bash 的 `realpath` 返回 `/c/...`，Cargo 的 `manifest_path` 以 `C:\...`（或带 `\\?\` 前缀）形式给出，直接比较必然零结果；先按上文命令块转成 Windows 形式（PowerShell 用 `(Resolve-Path).Path`），并核盘符大小写与 `\\?\` 前缀。

**7. 找到已解析包 ≠ 目标筛选 ≠ 验证真实调用兼容。** 三层分别回答不同问题，不能互相替代：

| 层次 | 能拿到什么 | 仍缺什么 |
|---|---|---|
| 找到已解析包 | 精确的包 ID、版本、`source`、`manifest_path`、库根 `src_path`、依赖边类别 | 只说明“这次解析选中了谁”；不说明该包在当前 target/feature 下实际编译哪些代码 |
| 目标筛选 | `--filter-platform` 按 rustc cfg 收窄解析图（包对级：任一条边激活即保留整对，`dep_kinds` 仍含其他 target 的边），并让 target 不活跃的 feature 不参与 | 没有 build；不读 `build.target` 配置；RUSTFLAGS/custom cfg 要对齐；host 侧 build-dependencies 的判定与 target 过滤不完全一致（见未知项）；target 工具链、链接器、build script 都未检查 |
| 验证调用兼容 | 读 `manifest_path` / `src_path` 指向的源码，沿调用查实现 | 不编译、不做类型检查；feature/cfg 分支、模块路径、宏与生成代码会改变实际实现；符号是否存在、签名是否匹配只能由消费包当前的 `cargo check` / `cargo build` / 测试接收 |

## 不确定项与未保证

- **工作区级 feature 解析是否算预期行为未定。** Cargo Book 的字段注释写“当前包”，实现和 issue #7754 显示按整个 workspace 解析；issue 仍 open 且标 `S-needs-design`。在维护者定论前，把 `resolve.nodes[].features` 当作可能偏大的并集，不要当本次 build 的精确 feature 集。
- **直接依赖的 `--features dep/feature` 只在源码与官方测试中有据。** `cargo metadata`／`build` 的命令文档只写 `package-name/feature-name` 用于工作区成员；固定 SHA 的 `collect_matching_features` 与官方测试 `slash_optional_enables`、`required_features_host_dep` 证明所选成员的直接依赖也接受该写法（可选依赖一并激活），但命令文档未承诺，后续版本需复核。
- **`source` 的具体字符串不是稳定接口。** 官方明确说 `+` 后的值未定义、可能变化、可能不直接对应配置或索引定义；`source=null` 同时覆盖 path 依赖与 workspace 成员。要稳定区分来源，用 `id` 与 `manifest_path`，不要解析字符串。
- **`dep_kinds` 的起始版本官方说法冲突。** 当前 Cargo Book 的 schema 注释写 “Added in Cargo 1.40.”，但 `rust-1.40.0` tag 的 `struct Dep` 只有 `name`/`pkg`，`rust-1.41.0` tag 才加入 `dep_kinds`，Cargo 1.41 changelog #7132 也记为 1.41 新增（PR 2019-11-14 合入）。按 tag 源码取 1.41 起；未找到解释或更正这条文档注释的官方说明，引用时保留这一冲突。
- **`manifest_path` 未承诺 canonical 路径，且 Windows 有路径格式差。** 页面用 `realpath` 做字符串相等；源码的路径处理不保证 canonical（parser 明确 path 依赖返回的路径不 canonicalize），符号链接目录下可能不相等。原生 Windows 下 Git Bash 的 `realpath` 给 `/c/...`，Cargo 给 `C:\...`（或带 `\\?\` 前缀），直接比较必然零结果；需 `cygpath -w` 或 PowerShell `(Resolve-Path).Path`，并核盘符大小写与前缀。本轮只在 Git Bash 观察了两种格式，无 cargo 可核 Cargo 的实际输出。
- **build-dependencies 的平台过滤与 target 过滤不完全同构。** Cargo Book 说明 target-specific build-dependencies 只在 host 匹配时构建（[平台特定依赖](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#platform-specific-dependencies)：只会 “be built when the host platform matches the specified target”）；metadata 的实现对同一条边按请求的 target 统一调用 `dep_platform_activated`。因此别用同一张过滤图判断 build-dependency 在构建时是否激活；这是源码与文档交叉推出，未实跑。读者入口与差量 2 的 dev/build 排查据此分开：dev 边按构建 target，build 边按 host，且 `--filter-platform "$target"` 收窄的图不能判定 build 边。
- **没有本地 Cargo／jq 运行。** 本机无 `cargo`/`rustc`/`jq`，任务也要求不安装；命令边界依据官方 stable 文档、固定稳定 tag SHA 源码与 Cargo 官方测试，不等于在真实项目上复现。修正后的 jq 只按 jq 语义人工核对，未执行；`lib_src` 漏 `proc-macro`/`cdylib` 的结论来自 target-kind 文档与源码，未在真实 crate 上验证。
- **页面引用的 opensrc 实试未复核。** `reqwest 0.12.28`、blocking 与异步 `timeout` 签名差异是本仓既有实试记录；本轮按任务要求不重做 opensrc 修复，也不把它当 Cargo 字段能自动证明的事实。
- **Vite 部分只核引用行。** 未展开 pnpm alias/patch 的解析与构建语义，也不与 Cargo 的 `[patch]` 做等价性结论。

## 本轮核过但无需改页面的部分

- `dep_kinds` 的 `kind`/`target` 字段语义：成立。`dep_kinds` 在 1.41.0 tag 才出现（1.40.0 的 `struct Dep` 只有 `name`/`pkg`，1.41.0 加入），但 Cargo Book 注释写 1.40，冲突见“不确定项”；`resolve.nodes.deps` 自 Cargo 1.30 起有（[changelog #5871](https://github.com/rust-lang/cargo/blob/rust-1.41.0/CHANGELOG.md#cargo-130-2018-10-25)）。`any(... .kind == null)` 只能说明该包对存在普通边；是否对当前 target 激活要保留 null、字面量相等和 `cfg(...)` 三类，cfg 再人工核对（见差量 4）。
- 用 `id`/`pkg` 在 `packages` 与 `resolve` 间做相等匹配：符合 Package ID 规范，且源码会归一化两边的 ID。
- `--locked` 与 `--offline` 的核心语义、`--format-version 1`、`packages[].dependencies` 保持 manifest 全量：与官方一致。
- Zed 的 `reqwest` 重命名 fork、Vite 的 alias/patch、页面“查实际行为先于查文档”的路线：引用行均能在固定 SHA 找到；示例结论本身未重新跑构建。
