# 覆盖地图

> 2026-10-21 建立（Claude 阶段审计，用户要求）。这是**规划单元的固定来源**：游戏客户端／gameplay 和 AI coding 社区实践都是可以长期增长的领域，规划时从这里找覆盖最浅、读者最需要的格子立项，而不是临时想题。各格的“现状”由执行者在立项或交付时更新，一格一行，不写叙述。
>
> **优先级（2026-10-21 用户决定）**：重心是 AI coding 主干，以及游戏开发全流程（G1：资产 → 引擎可用 → 代码与验证）和 AI coding 的结合；第四节属于这个重心。游戏客户端／gameplay（第一至三节）**先只覆盖最核心、最通用的机制**（第二节为主），按类型的系统和高质量专题作为**长期兜底方向**：主干和 G1 的任务不够时，再从这里持续立项。
>
> 地图只列维度，**不是待办清单**：哪一格值得先做，按读者需求、可得证据和与 AI 的关联来排，不按表格顺序，也不要求填满。

## 深度等级

| 等级 | 含义 |
|---|---|
| 0 | 未覆盖 |
| 1 | 提到，或只有零散单例 |
| 2 | 有机制与条件选择，主要来自开源实现或官方文档 |
| 3 | **高质量参照**：有已发行优秀作品（含 AAA 和优秀独立游戏）的公开做法，例如开发者演讲（GDC 等）、复盘、技术分析、官方样例工程；写到关键参数、手感或体验标准、常见失败；并写明 AI 能承担什么、怎么验证 |
| 3+ | **当前最高水平**：在 3 级之上，写明近一两年的最新做法（新引擎功能、近期演讲与论文、头部团队技术博客、近期获奖或口碑最好作品的技术分析；AI coding 则是前沿团队的工程文章、近期论文与评测、头部实践者的公开做法），并判断它对目标读者是否值得采用。**必须是同一问题的对照**，只列出新做法不算；“新”或“实测过”都不自动等于最好 |
| 4 | 有本仓库的可复查实测，写明测的对象、模型和范围 |

**三个不同的问题**：已发行作品和开源实现证明“**可行**”；社区和调查说明“**主流**”；只有近期的最高水平来源能说明“**当前最好**”。前两者不能代替第三者，旧作品的做法可能已被更好的方法取代。

**“高质量”的标准**：只靠读源码得到的机制最多算 2 级，即使是知名开源游戏也一样：源码说明“怎么实现”，不说明设计取舍、调参过程和玩家感受。要到 3 级，必须回答“优秀作品实际怎么做到的、做到什么程度、玩家感受到的差别在哪”。

## 五、使用方式

- **规划单元**：先看本页，从浅的格子里选读者最需要、证据可得、和 AI 关联最强的立项；一个项目覆盖一个格子的一个深度台阶，例如从 1 升到 3。
- **交付时**：把对应格子的“现状”改成新等级，并附一处正文或研究链接。
- **页面放不下时**：由执行者按可读性决定是否按类型或机制拆出新页面，没有硬性篇幅上限；新建目录仍需要用户决定。
