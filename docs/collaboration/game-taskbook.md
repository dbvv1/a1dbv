## 1. 总目标

产出一套关于“只有一名程序员、没有美术和音频人员时，如何借助 AI 把独立游戏做到可发布质量”的**前沿、可直接采用、有证据**的指导，覆盖：

- **G1 资产管线**：各类美术与音频资源的生成方法，以及接入引擎的方式；
- **G2 客户端核心模块与 gameplay 架构**；
- **从概念到发布的路线图**。

当前阶段以**调查、比较、整理结论**为主，真实引擎测试放到后续阶段（见第 6 节）。

## 2. 每个 WP 的统一要求

1. **来源**：
   - 优先读官方文档、GitHub 源码（固定到 SHA）、论文、开发者复盘和 devlog；
   - 商业服务和开源方案都要覆盖；
   - 社区讨论要读原帖。
2. **评估维度**（按资源或模块取舍，不必每项都填）：
   - 质量上限；
   - 可控性与一致性；
   - 引擎可用性；
   - 授权（代码、权重、生成结果，以及地域或营收限制）；
   - 成本；
   - 维护状态；
   - 真实游戏采用；
   - 离可发布还差什么、程序手段能否补上。
3. **结论形式**：
   - 每类资源或每个模块给出**分档推荐**：最佳质量 / 最佳性价比 / 本地或免费；
   - 每档写明“采用 / 改造 / 不用”及理由；
   - 写清这个推荐**取代了什么**、**什么情况下会过时**。
4. **借鉴**：
   - 别人已经写得好的，直接引用或摘录，注明出处和许可；
   - 我们的价值在横向比较、提炼机制和给出判断，不做资料汇编。
5. **写到哪里**：
   - 结论写进专题正文：建议 → 主要依据 → 一句局限；
   - 来源清单、比较细节和反证写进该 WP 的**一份**研究记录，后续轮次追加，不另建；
   - 候选问题回填到 BACKLOG 的“游戏开发方向”。
6. **验收**：
   - 云端 Codex 评审通过，在 TASKS 写“范围内通过”；
   - 离线检查（`python3 scripts/check_offline.py`）和 `git diff --check` 通过。

## 5. 节奏与协作

### 5.1 持续运行（无人值守）

dot 可以长时间连续运行，不需要每完成一个 WP 就等用户。

**并行**：在满足第 4 节依赖表的前提下，可以同时推进多个 WP，例如用后台 Agent 或子 Agent 分成几条线：
- 资产线：WP1、WP2–WP8；
- 引擎接入线：WP9；
- 核心模块线：WP10、WP11。

**鼓励大胆并行、深入探索**：
- 并行数量由 dot 自行决定，能保证质量就尽量多开。大的 WP 可以继续拆开并行，例如 WP3 拆成静态道具、角色、减面与 LOD 三路，WP10 按模块拆；
- 探索要深：多读来源，顺着线索追到一手资料，比较足够多的方案，不满足于第一个看起来能用的答案；
- 调查中发现的重要新方向，可以在任务书范围内直接展开；超出范围的登记到 BACKLOG；
- 速度不是目标，覆盖面和深度才是。并行带来的风险主要在整合，所以下面的整合规则必须遵守。

并行时遵守：
- **每条线只改自己的文件**。共享文件（TASKS、BACKLOG、game-dev README、03 总览的汇总表）只追加自己的行，或者由主会话统一更新，不同时改同一段；
- 每个并行 Agent 都按下面同样的循环执行，各自提交；合回 `main` 前先合并最新的 `main`；
- 主会话负责分配 WP、检查子 Agent 交回的结论和来源，再标“待评审”。不能直接采纳子 Agent 的结论。

每个 WP 按下面的循环执行：

1. **开始**：`git fetch`，把最新的 `main` 合并进来；先处理云端 Codex 对已完成 WP 的评审意见（有就先修），再在 TASKS 把下一个 WP 标为“进行中”；
2. **执行**：调查、比较、写结论，遵守第 2 节的统一要求；
3. **自检**：回答锚点的四个自检问题；对照第 2 节逐条检查；跑离线检查和 `git diff --check`；
4. **交付**：一个 WP 至少一个结果提交（大的 WP 可以分几次提交），合回 `main` 并推送；在 TASKS 标为“待评审”，写一行摘要：改了哪些文件、主要结论、遗留问题；
5. **继续**：进入下一个 WP，不等评审结果。评审意见在下一个 WP 开始时处理。

**遇到需要用户决定的事**（安装、付费、下载大模型、运行引擎、新建任务书以外的目录，或者方向上的取舍）：
- 写进 TASKS 的“需要用户决定”一节，说明选项和你的建议；
- 跳过受影响的部分，继续做不受影响的工作或下一个 WP，**不要停下整个运行**；
- 不要自行做出这些决定。

**防止长时间运行后质量下滑**：
- 每完成 3 个 WP，回头通读一次已完成 WP 的结论：前后是否矛盾、推荐是否因为新发现需要更新、有没有偏离方向锚点；把结果写成 TASKS 里的一段简短复盘；
- 宁可一个 WP 做透，也不要为了推进速度浅尝辄止。WP 没达到完成标准，就不要标“待评审”；
- 新发现的重要问题不在本任务书范围内的，登记到 BACKLOG，不顺手展开。

**什么时候停下**：
- 阶段 A–E 全部达到“待评审”或“通过”；
- 或者连续两个 WP 都因为等待用户决定而无法推进；
- 或者发现方向锚点或任务书本身有问题，需要用户先改。

停下时在 TASKS 顶部写一段总结：完成了哪些 WP、待评审的有哪些、需要用户决定的有哪些。
