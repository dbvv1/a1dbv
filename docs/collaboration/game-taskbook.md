# 游戏开发方向任务书（dot 执行）

> 2026-10-13 起草，用户授权。依据 [AGENTS.md 方向锚点](../../AGENTS.md)“重点领域：游戏开发”。本任务书规定**做什么、按什么顺序、做到什么程度算完成**；具体结论由 dot 调查后独立判断。
> 进度记录在 [TASKS.md](TASKS.md)，每个工作包（WP）一行。云端 Codex 负责评审每个 WP 的交付，并补充方向候选。

## 1. 总目标

产出一套关于“只有一名程序员、没有美术和音频人员时，如何借助 AI 把独立游戏做到可发布质量”的**前沿、可直接采用、有证据**的指导，覆盖：

- **G1 资产管线**：各类美术与音频资源的生成方法，以及接入引擎的方式；
- **G2 客户端核心模块与 gameplay 架构**；
- **从概念到发布的路线图**。

当前阶段以**调查、比较、整理结论**为主，真实引擎测试放到后续阶段（见第 6 节）。

## 2. 每个 WP 的统一要求

1. **来源**：
   - 优先读官方文档、GitHub 源码（固定到 SHA）、论文、开发者复盘和 devlog；
   - 商业服务和开源方案都要覆盖；
   - 社区讨论要读原帖。
2. **评估维度**（按资源或模块取舍，不必每项都填）：
   - 质量上限；
   - 可控性与一致性；
   - 引擎可用性；
   - 授权（代码、权重、生成结果，以及地域或营收限制）；
   - 成本；
   - 维护状态；
   - 真实游戏采用；
   - 离可发布还差什么、程序手段能否补上。
3. **结论形式**：
   - 每类资源或每个模块给出**分档推荐**：最佳质量 / 最佳性价比 / 本地或免费；
   - 每档写明“采用 / 改造 / 不用”及理由；
   - 写清这个推荐**取代了什么**、**什么情况下会过时**。
4. **借鉴**：
   - 别人已经写得好的，直接引用或摘录，注明出处和许可；
   - 我们的价值在横向比较、提炼机制和给出判断，不做资料汇编。
5. **写到哪里**：
   - 结论写进专题正文：建议 → 主要依据 → 一句局限；
   - 来源清单、比较细节和反证写进该 WP 的**一份**研究记录，后续轮次追加，不另建；
   - 候选问题回填到 BACKLOG 的“游戏开发方向”。
6. **验收**：
   - 云端 Codex 评审通过，在 TASKS 写“范围内通过”；
   - 离线检查（`python3 scripts/check_offline.py`）和 `git diff --check` 通过。

## 4. 工作包

顺序按依赖和价值排列。每轮做一个 WP，大的 WP 可以分两轮。

### 阶段 A：基础

**WP0 盘点与缺口表**
- 对照本任务书，检查 `domains/game-dev/` 和 BACKLOG“游戏开发方向”的现有内容，在 game-dev README 写一张缺口表：WP、现有内容、缺口、优先级；
- 吸收云端 Codex 已做的开源摸底，不重做；
- 完成标准：缺口表覆盖所有 WP，没有重复的调查计划。

**WP1 授权与商用门槛总表**（后续所有资产 WP 的前置条件）
- 范围：主流图像、3D、动作、音频、视频模型和服务；
- 每项分开写代码、权重、生成结果三层的许可，是否可商用，有没有地域或营收限制，平台披露要求（如 Steam 的 AI 内容披露）；
- 写进 03 总览的“授权”一节；
- 完成标准：后续 WP 推荐的每个方案，都能在这张表里查到授权结论。

### 阶段 B：G1 资产管线（理论与开源探索）

每个资产 WP 都要回答四个问题：
- 当前最前沿的方法是什么（模型、服务、工作流）；
- 零人工美术修补时能做到什么质量；
- 离可发布还差什么，程序手段能补多少；
- 分档推荐。

| WP | 资源 | 必须覆盖的要点 |
|---|---|---|
| WP2 | 2D：概念图、精灵、图标、UI、瓦片 | 风格锁定方法（参考图、LoRA、IP-Adapter 类、调色板）；透明边缘与锚点；精灵表和逐帧动画的连续性；UI 文字为什么应交给引擎绘制 |
| WP3 | 3D：道具、场景、角色 | 图生 3D 与文生 3D；减面、重拓扑、UV、LOD、碰撞代理；静态道具和变形角色分开评估 |
| WP4 | 动画与绑定 | 自动绑定、文本生成动作、视频动捕、重定向；2D 骨骼动画与逐帧动画的路线；root motion 和首尾衔接 |
| WP5 | 材质与特效 | 程序化或参数化材质与生成贴图的分界；PBR 一致性；特效运行时与 flipbook 生成的取舍 |
| WP6 | 音频：音效、音乐、配音 | 参数化合成与生成模型的分界；循环与状态切换；配音的声音授权；离线预生成与运行时推理的取舍 |
| WP7 | 视频与过场 | 先回答“是否需要预渲染视频”；引擎内镜头的替代方案；版本修改的成本 |
| WP8 | 跨资源：风格一致性与美术方向 | 几百个资产怎样保持一致；哪些风格对单人程序可行，各自限制哪些玩法；成套生产的工作流（ComfyUI 等），以及版本和种子管理 |

WP2 和 WP8 价值最高、联系最紧，建议先做 WP2，再做 WP8，然后按 3 → 4 → 6 → 5 → 7 的顺序推进。

### 阶段 C：G1 引擎接入（理论）

**WP9 从生成结果到引擎资产**
- Unity：官方 AI 功能、社区 MCP 和编辑器插件、导入自动化（AssetPostprocessor、预设）、Addressables；
- Unreal：官方 MCP、Python 编辑器脚本、Interchange；
- 重点：批量导入规范、命名和引用稳定性、重生成后的替换流程；
- 写进 01 和 unity/、unreal/ 对应页面。

### 阶段 D：G2 核心模块（理论与开源借鉴）

**WP10 客户端核心模块**（写进 04-client-modules.md）
- 模块：渲染与性能、资源加载与内存、动画系统、物理与碰撞、输入、UI、音频、存档、本地化、平台适配与发布、编辑器扩展；网络同步只在玩法需要时写；
- 每个模块回答：
  - 独立游戏要做到什么程度，什么可以不做；
  - 推荐借用的成熟开源框架或官方样例（如 UniTask、Addressables 样例、Lyra 等，均需核实）；
  - AI 写这个模块时的典型失败；
  - 用什么验证；
- 优先写跨模块行为：场景切换与异步取消、资源释放、旧存档升级、输入与暂停、目标设备性能。

**WP11 gameplay 架构**（写进 05-gameplay-architecture.md）
- 内容：游戏循环、状态机与行为树、数据驱动配置、组件与 ECS 的取舍、事件、战斗与技能（如 GAS）、相机、关卡；
- 参考优秀开源游戏和模板，写清哪些结构对单人项目值得、哪些是过度设计；
- 写清 AI 生成 gameplay 代码时，怎样保持架构一致。

### 阶段 E：综合

**WP12 独立游戏路线图**（写进 06-indie-roadmap.md）
- 阶段：概念、原型、垂直切片、内容生产、打磨、发布、上线后；
- 每个阶段写清：质量标准、AI 可承担的部分、人必须做的决定、对应的 WP 结论链接；
- 这是整个方向的读者入口，需要等前面的 WP 有结论后再写，可以先搭骨架。

**WP13 游戏项目的 Agent 配置**
- 结合 G1、G2 的结论，更新 unity/、unreal/ 的模板（AGENTS.md、Skill、Hook）；
- 改脚本时按仓库约定加回归测试。

## 5. 节奏与协作

- 每轮开始时，在 TASKS 认领一个 WP；结束时附提交 SHA、实际运行的检查，以及下一轮计划；
- 云端 Codex 评审每个 WP 的交付，重点检查：
  - 是否前沿（有没有漏掉近几个月的重要方法）；
  - 分档推荐是否有依据；
  - 授权是否核对；
  - 是否变成了资料汇编；
- 发现主干 AI coding 的通用结论时，写回 docs/ 对应专题；
- 遇到需要安装、付费、下载大模型或运行引擎的事，先列方案和成本问用户。
