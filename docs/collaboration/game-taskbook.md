## 1. G1 全 AI 流程管线（端到端，按瓶颈排序）

1. **美术与音频资产**：可能是当前最大的瓶颈，按资源类型分别评估：
   - 2D：概念图、UI、图标、精灵、瓦片；
   - 3D 模型：拓扑、UV、面数与 LOD；
   - 贴图与材质：PBR；
   - 绑定与动画：文本或视频生成动作、动捕清理、重定向；
   - 特效；
   - 音效、音乐、配音；
   - 视频与过场。

   每类回答四件事：
   - 不经人工美术修补，现成、程序化与生成路线分别能做到什么质量（资源来源沿用方向锚点）；
   - 离可发布还差什么：规格、风格一致性、引擎可用性；
   - 差距能否只靠程序手段补上，补不上的就明确写出来；
   - 授权和平台披露要求。

   **美术风格选择本身是一项决策，但“哪种风格更友好”是待验证的条件判断**：
   - 要分开看静态像素图与逐帧动画、刚体道具与变形角色，难度差别很大；
   - 减色、减面修不了姿态、轮廓和蒙皮错误；
   - 结论要说明这种风格会限制哪些玩法和题材。

   **同一款游戏几百个资产的风格一致性**单独研究。
2. **从生成结果到引擎可用资产**：导入设置、材质、Prefab / Blueprint、命名和引用，以及引擎官方的 Agent 接口。Unity 优先，Unreal 作对照。
3. **代码与玩法逻辑**：按具体任务研究实现、设计取舍与迭代质量；验证包括规则、运行状态、性能和玩家体验，自动试玩只能覆盖其中一部分。能力判断以该任务的证据为准。
4. **最好的证据形式**（后续阶段）：用一个可玩的垂直切片走通全流程，并且**必须经历第二次需求修改**。首次能跑、画面好看，证明不了后续内容能持续生产；第二次修改才会暴露风格一致性、资源引用、存档兼容和重生成成本。记录每个环节的耗时、淘汰样本、重生成次数和主动工时。

## 2. G2 游戏核心模块

以商用引擎上的客户端为主，不研究自研引擎；引擎原理只在影响 AI 协作或性能决策时深入。

- **客户端**：渲染与性能、资源加载与内存、动画、物理与碰撞、输入、UI、音频、存档、本地化、平台适配与发布、编辑器扩展；网络同步只在玩法需要时研究；
- **Gameplay 架构**：游戏循环、状态机与行为树、数据驱动配置、组件与 ECS 的取舍、战斗与技能、相机、关卡。

每个模块回答三件事：
- 当前玩法与设备下要做到什么程度，优秀独立游戏的质量参照是什么，哪些提升值得做、哪些可以不做；
- AI 在这个模块能承担什么，典型失败是什么；
- 用什么验证：profiler、自动测试或试玩。

模块内部的实现与质量取舍继续深入；跨模块行为优先关注场景切换与异步取消、资源释放、旧存档升级、输入与暂停、目标设备性能。WP首轮覆盖不代表模块研究结束，按玩法、设备与质量目标继续发展。

## 3. 借力与借鉴

**先找、读、比较，再决定写什么，不从零自建**。重点来源：
- 资产生成管线与 ComfyUI 工作流；
- Unity / Unreal 的 MCP 和编辑器插件；
- 开源游戏和模板项目；
- 独立团队公开的复盘与 devlog。

评估一个项目时看四点：是否还在维护、是否有真实游戏在用、产物质量怎样、接入成本多高。研究产出是“采用 / 改造 / 不用”的判断加上证据。只有在现成方案都不满足时，才自己写最小的补充，并说明为什么现成的不行。

**借鉴与原创的分寸**：
- 不重复造轮子；
- 别人的内容确实优秀、许可允许时，可以直接引用或摘录，注明出处和许可；
- 更多的价值在我们自己的整理：横向比较多个方案，提炼机制，结合场景下判断，组合成比任何单一来源更完整、更新、更可靠的建议；
- 不做转述搬运，也不为了“原创”而回避已有的好答案；
- 分析他人的游戏只提炼机制和规则，不提取、不分发代码和资产。

## 4. 每项研究的统一要求

1. **来源**：优先读官方文档、GitHub 源码（固定到 SHA）、论文、开发者复盘和 devlog；商业服务和开源方案都要覆盖；社区讨论要读原帖。
2. **评估维度**（按资源或模块取舍，不必每项都填）：质量上限；可控性与一致性；引擎可用性；授权（代码、权重、生成结果，以及地域或营收限制）；成本；维护状态；真实游戏采用；离可发布还差什么、程序手段能否补上。
3. **结论形式**：
   - 资源与产品路线给出**分档推荐**：最佳质量（含付费服务）/ 最佳性价比 / 本地或免费；模块机制按适用条件、质量与维护代价比较，不硬套产品档位。不追求绝对质量第一，但思路和方法必须保持前沿；
   - 每档写明“采用 / 改造 / 不用”及理由；
   - 写清这个推荐**取代了什么**、**什么情况下会过时**，动态事实带日期和版本。
4. **写到哪里**：结论写进专题正文（建议 → 主要依据 → 一句局限）；来源清单、比较细节和反证写进该主题的**一份**研究记录，后续追加，不另建；候选问题回填到 BACKLOG 的“游戏开发方向”。
5. **长期交付**：一份“独立游戏从概念到发布”的路线图（`domains/game-dev/06-indie-roadmap.md`），逐步用证据填充。每个阶段写清：必要的质量标准、AI 可以承担的部分、人必须做的决定。

**领域范围外**：
- 通用引擎教程和 API 百科，只写和 AI 协作、质量门槛相关的部分；
- 不说明质量差距的资产工具名单；
- 只有宣传、没有可见产物的“AI 做出整款游戏”的说法。
