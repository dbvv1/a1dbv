# 游戏方向细则

> 本页是 [AGENTS 方向锚点](../../AGENTS.md)“游戏”一条的展开，规定**研究什么、每项回答什么、做到什么程度**；冲突时以锚点和[运行手册](LONG-TERM-PLAN.md)为准，当前状态见 [TASKS](TASKS.md)。

## 1. G1 全 AI 流程管线（端到端，按瓶颈排序）

1. **美术与音频资产**：可能是当前最大的瓶颈，按资源类型分别评估：
   - 2D：概念图、UI、图标、精灵、瓦片；
   - 3D 模型：拓扑、UV、面数与 LOD；
   - 贴图与材质：PBR；
   - 绑定与动画：文本或视频生成动作、动捕清理、重定向；
   - 特效；
   - 音效、音乐、配音；
   - 视频与过场。

   每类回答四件事：
   - 不经人工美术修补，现成、程序化与生成路线分别能做到什么质量（资源来源沿用方向锚点）；
   - 离可发布还差什么：规格、风格一致性、引擎可用性；
   - 差距能否只靠程序手段补上，补不上的就明确写出来；
   - 授权和平台披露要求。

   **美术风格是一项决策**：分开看静态像素与逐帧动画、刚体道具与变形角色；减色、减面修不了姿态、轮廓和蒙皮错误；写明风格会限制哪些玩法和题材。

   **同一款游戏几百个资产的风格一致性**单独研究。
2. **从生成结果到引擎可用资产**：导入设置、材质、Prefab / Blueprint、命名和引用，以及引擎官方的 Agent 接口。Unity 优先，Unreal 作对照。
3. **代码与玩法逻辑**：按具体任务研究实现、设计取舍与迭代质量；验证包括规则、运行状态、性能和玩家体验，自动试玩只能覆盖其中一部分。能力判断以该任务的证据为准。
4. **作品制作与知识研究同步推进**：用一个可玩的垂直切片走通全流程，并且**必须经历第二次需求修改**。首次能跑、画面好看，证明不了后续内容能持续生产；第二次修改才会暴露风格一致性、资源引用、存档兼容和重生成成本。利用自然产生的记录说明关键返工、品质与投入；不为补全每项数字延迟制作。

## 2. G2 游戏核心模块

以商用引擎上的客户端为主，不研究自研引擎；引擎原理只在影响 AI 协作或性能决策时深入。

先覆盖最核心、最通用、最重要的模块，每个先做出完整可用的一版，再按案例反馈深入。

- **客户端**：渲染与性能、资源加载与内存、动画、物理与碰撞、输入、UI、音频、存档、本地化、平台适配与发布、编辑器扩展；
- **引擎**（Unity 优先，Unreal、Godot 对照）：项目结构与资源管线、编辑器工具与引擎官方 Agent 接口、构建与发布、性能剖析，写在 `unity/`、`unreal/` 与 01 引擎接入；
- **服务端（独立游戏常用部分）**：联网模型选型（帧同步、状态同步、回滚）、房间与匹配、账号与云存档、排行榜、在线配置与遥测，优先给托管服务和开源服务端的接入起点；
- **Gameplay 架构**：游戏循环、状态机与行为树、数据驱动配置、组件与 ECS 的取舍、战斗与技能、相机、关卡。

模块以完整开发问题交付，复用已有材料并给出实现／接入起点和明确默认；独立研究与作品实现可并行，不按新增段落交差。每个模块回答：
- 当前玩法与设备下要做到什么程度，优秀独立游戏的质量参照是什么，哪些提升值得做、哪些可以不做；
- AI 在这个模块能承担什么，典型失败是什么；
- 用什么验证：profiler、自动测试或试玩。

模块内部的实现与质量取舍继续深入；正向体验、视觉表现、开发周转与正确性共同决定优先级。跨模块整合围绕当前作品与读者问题，不长期只补取消、恢复和防错边界。

## 3. 借力与借鉴

**先找、读、比较，再决定写什么，不从零自建**。重点来源：
- 资产生成管线与 ComfyUI 工作流；
- Unity / Unreal 的 MCP 和编辑器插件；
- 开源游戏和模板项目；
- 独立团队公开的复盘与 devlog；
- 用 AI 全程或大规模开发的游戏，及作者分享与社区讨论。

评估一个项目时看四点：是否还在维护、是否有真实游戏在用、产物质量怎样、接入成本多高。比较最相关的现成强方案后，按品质、适配和维护成本选择复用、改造或自研；不要求穷尽所有方案才允许制作。

**借鉴与原创的分寸**：
- 不重复造轮子；
- 别人的内容确实优秀、许可允许时，可以直接引用或摘录，注明出处和许可；
- 更多的价值在我们自己的整理：横向比较多个方案，提炼机制，结合场景下判断，组合成比任何单一来源更完整、更新、更可靠的建议；
- 不做转述搬运，也不为了“原创”而回避已有的好答案；
- 分析他人的游戏只提炼机制和规则，不提取、不分发代码和资产。

## 4. 每项研究的统一要求

1. **来源**：优先读官方文档、GitHub 源码（固定到 SHA）、论文、开发者复盘和 devlog；商业服务和开源方案都要覆盖；社区讨论要读原帖。
2. **评估维度**（按资源或模块取舍，不必每项都填）：质量上限；可控性与一致性；引擎可用性；授权（代码、权重、生成结果，以及地域或营收限制）；成本；维护状态；真实游戏采用；离可发布还差什么、程序手段能否补上。
3. **结论形式**：
   - 资源与产品路线给出**分档推荐**：最佳质量（含付费服务）/ 最佳性价比 / 本地或免费；模块机制按适用条件、质量与维护代价比较，不硬套产品档位。不追求绝对质量第一，但思路和方法必须保持前沿；
   - 每档写明“采用 / 改造 / 不用”及理由；
   - 写清这个推荐**取代了什么**、**什么情况下会过时**，动态事实带日期和版本。
4. **写到哪里**：结论写进专题正文（建议 → 主要依据 → 一句局限）；来源清单、比较细节和反证写进该主题的**一份**研究记录，后续追加，不另建；候选问题回填到 BACKLOG 的“游戏开发方向”。
5. **长期交付**：一份“独立游戏从概念到发布”的路线图（`domains/game-dev/06-indie-roadmap.md`），逐步用证据填充。每个阶段写清：必要的质量标准、AI 可以承担的部分、人必须做的决定。

**领域范围外**：
- 通用引擎教程和 API 百科，只写和 AI 协作、质量门槛相关的部分；
- 不说明质量差距的资产工具名单；
- 只有宣传、没有可见产物的“AI 做出整款游戏”的说法。

## 6. 作品案例

作品在真实开发里用上并检验主线知识，暴露只写文档发现不了的问题，同时做成高质量的游戏。三个案例各管一类问题，一直同时推进。

| 案例 | 仓库 | 检验什么 |
|---|---|---|
| 星跃飞车 | [Star-Rush-Reborn](https://github.com/dbvv1/Star-Rush-Reborn) | 驾驶手感、竞速 AI、AI 美术与音频接入 |
| MOBA-Like | [MOBA-Like](https://github.com/dbvv1/MOBA-Like) | 技能／Buff、属性、英雄与小兵 AI、寻路、成长、技能特效 |
| FPS-Like | [FPS-Like](https://github.com/dbvv1/FPS-Like) | 瞄准、镜头、武器动画与换弹、命中与后坐、射击 AI、听声辨位 |

新案例按以下做法建；Star-Rush 是早于本约定的存量作品，第 2 条只在它重构时适用：

1. **新案例一次只开一个，已开的并行推进**。先在 brief 选品类标杆作参照（玩法用品类标准做法，不求创新），再做纵切片：一张图、一种模式、少量角色，走到“可玩 → 第二次需求修改”（§1 第 4 条），再扩内容。
2. **模拟与渲染分离**。玩法跑在固定步长、按种子可复现的模拟层，渲染和界面只读状态、只发输入命令。同一份逻辑能在 Node 里无画面批量运行，机器人对战、数值回归和回放都能自动验收。
3. **功能是门槛，质量要评估**。单元测试、无画面模拟断言和无头浏览器 smoke 是合入门槛；完成看质量评估：与参照并排对比，先补玩家一眼可见的大差距，专门优化到差距明显缩小（dot-B 提示词）。需要人听、看、玩的记入“待人工验收”，不阻塞后续工作。
4. **知识双向流动**。模块线做出的实现接进案例的可玩版本；案例跑通、推翻或改写了某个模块的做法，就更新该模块页正文，附案例提交链接。案例仓库只记作品，不记研究结论。
5. **只借玩法**。品类机制可以借鉴；名字、角色、地图布局、美术和音效原创，或使用许可清楚的素材。每个素材目录写明来源与许可。
6. **网页实现的适用范围**。网页案例能检验玩法规则、AI 行为、确定性模拟与联网、测试方法和资源制作前半段；编辑器与场景序列化、导入设置、动画状态机、材质光照、引擎物理、构建与剖析证明不了，这部分写在 `unity/`、`unreal/` 时以官方文档与工具为据，本机接收端能跑引擎时补小工程实测。网页同样能做到高品质。

每个案例仓库的指导只有三份，工具说明另放 `docs/`：`AGENTS.md` 写执行约定（`CLAUDE.md` 用 `@AGENTS.md` 引用同一份），`docs/brief.md` 写设计任务书（体验目标、切片范围、要跑通的模块、里程碑），`README.md` 面向玩家，`docs/quality.md` 放当前片段截图、参照链接与差距清单（每轮替换）。进度与阻塞只写在本仓库 TASKS，不在案例仓库另建任务板；开发经过写进提交说明。
