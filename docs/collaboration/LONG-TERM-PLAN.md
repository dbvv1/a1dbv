# 运行手册

> 方向见 [AGENTS](../../AGENTS.md)，本文维护执行规则；Git与调度见[运行细则](operations.md)，当前工作见[TASKS](TASKS.md)。

## 1. 核心思想

**找到真实技术人员正在用的、当前最好的 AI coding 做法、工具和开源项目，亲手试过，提炼成读者马上能用的东西；再留一点空间给有新意的尝试。**

选题看读者能采用什么；亲手试用、形成明确选择，把时间用在实际成果与前沿缺口上。

## 2. 每次交付前问五个问题

独立审查也按这五问审。

1. **前沿**：去了最强做法实际所在的地方吗（官方与做事的人的原文、真实使用反馈、开源项目）？是不是近 3–6 个月、当前一代的做法（游戏看近两年）？决定性来源是不是做事的人写的原文，而不是官方介绍或转述？
2. **增量**：读者原本不知道、或会做错的是什么？这次告诉了他什么？说不出来就不交付。
3. **实证**：装过、跑过、试过吗？没有就写“未试用”。
4. **诚实**：结论与来源、数据、核实日期及实际适用条件一致吗？按 CLAUDE 编写约定集中说明一次。
5. **好懂**：读者能迅速找到选择、开始步骤和关键取舍吗？限定语淹没结论与事实夸大都须修正；新的默认做法和模板按§7 做读者实测。

## 3. 怎么探索

**按 M6 方法探索**：先写要做的决定，再去最强做法实际所在的地方找（官方文档与工程文章、官方团队与高质量项目自己的配置和流程、Skill 与工具生态、社区原帖与高赞评论（至少一个中文渠道）、使用中的问题），读代码和设计，不只看 README；最后转化成可直接用的做法。方法写成了 [explore-frontier Skill](../../templates/generic/.claude/skills/explore-frontier/SKILL.md)，所有会话共用；来源名册见[探索证据](../research/2026-10-15-exploration-evidence.md#p46按团队追踪来源与漏检校准)。交付里写一行**探索回执**：查了哪些渠道、截止日期、哪些读不到。

**收件箱**：用户在 X、linux.do 等处看到的链接贴进 [inbox.md](inbox.md)，dot-A 24 小时内处理。用户贴来、本仓此前没发现的，记一次漏检，并把它的原始渠道补进来源名册。dot-A 每周再拿一份外部参照（当周社区热门讨论、主要 newsletter）对照一次，漏检数和发现时差记进[探索证据](../research/2026-10-15-exploration-evidence.md)的校准记录，25 只保留方法结论。

## 4. 做什么

**产能分配**（按周粗算）：A 的发现、试用与写作由 dot-A 按上周哪些来源产出了被采用的做法来分配，新意实验控制在小份额（新意实验标 🧪 或“观点”，和推荐默认分开写，失败照实记）；B 的四条长线一直同时推进（[B 提示词](prompts/dot-b.md)、[游戏方向细则](game-taskbook.md)）。

**分工**：dot-A 做 AI coding 与 M6；dot-B 做游戏知识（AI 全链路，以及客户端／gameplay、引擎与部分服务端的核心模块），三个作品案例在真实开发里用上并检验这些知识。A 不转向游戏开发，也不代管 B 的工作。

**完成看成品**：A 的完成是读者能照着用的选择或资产，并在本仓的真实 AI 开发里用过；B 的完成是模块与制作链知识被案例用上、证实并串联进正文，案例随之进入公开站点、向参照作品的品质靠近。功能跑通、文字写完只是一半，完成要经过专门的质量评估与针对差距的优化。研究记录、检查回执和待验说明是支撑，不是交付本身。

**自主选题**：完成、受阻或收益下降时，读最新 main、在制分支和 TASKS，选最重要的可执行缺口，不等队列清空，也不等用户派题。以完整能力、模块或可玩改进组织工作；同一窄题收益已低就收口。受阻只停依赖环节，在 TASKS 留恢复条件，转做独立工作；明确拒绝不换路绕过。地图和收件箱都没有可做项才算无事可做；空档时去广扫前沿或做地图的下一项。运行状态以 Dot 平台实际为准，Git 更新不保证唤醒；每个 dot 保留一个心跳定时任务（[细则§3](operations.md#3-dot-运行保障)），不另建其他调度。

**产能**：dot 自己的后台代理和云电脑与本机接收端（[local-jobs](local-jobs/README.md)）同时用，最后才是计入额度的 Codex 任务，并行开满可独立的工作；在途、并行与自动接收见[细则§3](operations.md#3-dot-运行保障)。

**项目**：写进 [TASKS 项目板](TASKS.md#项目板)，先用一句话写清读者或玩家得到什么；执行者可以自己开项目。编号取项目板与归档中最大编号加一，推送前与最新 `main` 核对，撞号时后到者改号。同一项目的小步改动攒成一次交付。

## 5. 写成什么样

**三层内容**（见锚点）：值得一试（[13 前沿雷达](../13-frontier-radar.md)）、当前最佳做法（决策页）、直接可用（`templates/`）。正文写法以 [CLAUDE 编写约定](../../CLAUDE.md#编写约定)为准。存量按读者问题整节重写，保留关键事实与操作入口；已改善页面直接接收，不为统一模板再次改写。

**可视化**（读者没耐心读长文，图是主要呈现方式之一）。按这个顺序选：
1. **真实截图**：上手试用时截下界面、终端输出或产物，这是最有说服力的图，“值得一试”里试过的项目尽量每项一张；
2. **代码生成的图**：结构、流程、决策树和对比用 Mermaid 或 SVG；数据用脚本画图。只把文字排成表格的 SVG 不算可视化；
3. **生图模型**：只在确有助理解具体知识且有授权时配图，不为简报或凑画面制造工作。知识图解默认二次元／ACG 表达，先画真实对象、因果和对照。生图负责画面，**准确的文字和数字用代码叠加**（SVG 或图片处理脚本），不让模型自己写字；生成后检查读者能否据图复述具体机制或下一步动作，生成性质在邻近说明中交代。

知识漫画按[短提示词](prompts/acg-knowledge-comic.md)：先写问题→动作→结果的分镜，人物参与因果，每格补足实际知识。

图片放 `docs/img/`，单张尽量不超过 300 KB（优先 WebP），附替代文字。

**后台减负**：
- 研究记录只为支撑正文而写，开头三行写结论；
- 实验脚本和夹具只在真正运行时写；
- 验证细节（树 SHA、检查命令、回执）写进提交说明，不写进正文和 TASKS；
- TASKS 保持 10 KB 以内，只放当前重点、分工、项目板和需要用户决定的事，其余移入归档。

## 6. 节奏与反馈

**简报暂停（2026-10-24 用户要求）**：停止每日／定时简报、digest 更新及配图整理。重要发现直接回流主专题、可用模板或清晰采用建议；何时通知用户见[细则§3](operations.md#3-dot-运行保障)。

**方向纠偏**：每次选下一项前，既看第2节五问，也看最近一组交付是否增强主线能力与作品品质、是否进入读者入口或可玩版本、下一题是否只是惯性扩题。发现偏题立即调整。

**每周独立审计**：由未参与本周写作的新上下文审方向和关键增量，抽读必要正文与未合分支，对照外部强实践，也检查指导本身是否导致偏题、正文是否被限定语淹没、台账是否压过正文；不重复已审内容。既有外部十件事每两周继续，用于发现漏项。

**指导层（2026-10-25 用户指定）**：Claude 核心方向会话负责方向与原则、dot-A 与仓库整体，游戏指导会话负责 dot-B；Codex 审计会话负责增量审计和仓库整理；增量审计把新增内容里的防御式写法（限定语淹没结论、连叠否定、逐句免责）当缺陷，退回负责人改。两边经 Git 交接，同一批指导文件不同时修改。指导按变化频率分三层：

| 层 | 内容 | 修改方式 |
|---|---|---|
| 锚点 | `AGENTS.md` 方向锚点 | 用户维护 |
| 长期规则 | 本手册、[细则](operations.md)、长期提示词 [A](prompts/dot-a.md)／[B](prompts/dot-b.md) | 只在方向层问题时修订，每周最多一次（用户直接指示除外）；替换旧文字而非追加，修订后总量不增加；提示词固定文件名就地更新 |
| 当前重点 | [TASKS](TASKS.md)“当前重点”与项目板 | 每轮纠偏和局部欠项只改这里，当前重点最多三条 |

一次纠偏不新建审计报告或提示词文件；需要留档的理由写进提交说明。

## 7. 交付流程

1. 在自己的分支完成一个可接收结果，整合最新 `main` 后核实际交付差量。新的默认做法、模板和作品版本由非作者审查：答案页按 write-task-guide 照做实测，其他新默认和模板由非作者只读新文回答真实读者问题，答不出就修；作品对照参照评估。其他单元自查。结论写进提交说明。
2. 按下表选检查，在最后一次相关修改后通过即可。源码、依赖、运行配置、检查器或所验行为变了，重验受影响路径；明确失败必须修复，不能用缩小范围掩盖失败。

| 改动范围 | 适用检查 |
|---|---|
| 纯正文、审计、任务／指导文档 | `python3 scripts/check_repo.py`、来源与关键结论核查、实际读者入口；不跑无关Hook／实验套件 |
| 某个实验、模板或产品代码 | 上述文档检查及该模块相关测试／类型／构建检查，真实消费者和直接失败路径；页面改动回真实浏览器，音频改动实际试听 |
| 共享检查器、Hook基础设施、跨套件公共依赖或影响范围无法确定 | `python3 scripts/check_offline.py` 完整入口，加该变化需要的真实行为验证；完整入口不是产品验收的替代 |

3. 发布按[运行细则§1](operations.md#1-发布与恢复)：每个执行者把自己的成果直接快进推送到 `main`，不开 PR、不强推、不互相代合。CI 配置保持原样，如实报告实际运行范围。
4. 真实搭建／运行单次最多2小时。受阻记录具体入口、原因、未完成结果和恢复条件到既有TASKS，转做独立项；下一次选题先核条件是否恢复，不能用新题默默覆盖旧验收。已有明确拒绝保持停止，不换入口绕过。
5. 本地模型协作按[运行细则§2.2](operations.md#22-本地模型协作)，不另造验证体系。检查摘要写进现有提交／研究记录，不加证明账本。

## 8. 边界

授权范围见锚点“自主与边界”：默认直接做，只有那几条红线写进 TASKS“需要用户决定”，然后立刻转做其他项；已经问过的不重复问。公开仓库的安全要求见 `AGENTS.md` 的“公开仓库安全”。

## 9. 长期方向与当前承接

> 持续职责，不是做完即停的清单；当前承诺与阻塞在 TASKS。高质量指做出更强的能力与更好的成品，高效率指走到可用结果的投入，前沿指相对强替代的优势；材料新鲜或边界说明多都不能代替它们。

**dot-A** 与 **dot-B** 的长期方向、地图、工作线和完成标准写在各自[长期提示词](prompts/dot-a.md)（[B](prompts/dot-b.md)）；地图分别是根 README 的“读者问题 → 答案”和游戏分支的“模块与制作链地图”。以下是两边共同的长期约定：

- **试验场**：本仓里真实的 Agent 编码任务（案例仓库的开发、a1dbv 的脚本与模板）和两个 dot 自己的运行。A 的候选做法经 TASKS“共同”交 B 在案例的日常编码里用；A 不验证游戏玩法和品质。
- **案例默认分支**：B 负责；能玩、测试与构建通过即以旁置入口合入并发布，换默认入口要真 GPU 或操控证据加非作者盲判，见[游戏方向细则§6](game-taskbook.md#6-作品案例)。
- 验收受限只停对应环节：能独立完成的部分先做成可用版本，需要人听、看、玩的记入 TASKS“待人工验收”；感知结果直接决定实现时不盲调。
- 潮汐邮差保留为窄例。

两边长期无人值守时持续发现、取舍、实施和回流；当前承诺优先，探索不必等欠项清零。
