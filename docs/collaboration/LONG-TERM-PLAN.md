# 运行手册（长期计划）

> 2026-10-16 重构，用户授权。适用于任何接手本仓库的 Agent（dot、Claude、Codex 等）和人。
> **分工**：方向以 [AGENTS.md 方向锚点](../../AGENTS.md) 为准；本手册规定怎样干活；当前状态只看 [TASKS](TASKS.md)。游戏领域的方向细则见 [游戏方向细则](game-taskbook.md)。
> 本手册取代原 `docs/maintenance-roadmap.md`、`docs/research/STATE.md` 和协作入口里的旧职责说明。这些文件的历史内容保留在 Git 历史中。

## 0. 开工

**新会话只需读三份文件**：
1. AGENTS.md 方向锚点；
2. 本手册；
3. TASKS.md：需要用户决定的事、进行中的认领、最近一次交接。

其他文件按任务需要再读，例如对应工作线的专题页、BACKLOG 里该线的条目、相关研究记录，不要求通读仓库。这三份文件合计控制在约 35 KB 以内；超出时，下一次编辑轮先压缩它们。

**交接只依赖 Git**：结论、状态和下一步都写进仓库文件和提交，不依赖聊天记录、本机目录或另一个 Agent 的记忆。没有写进仓库的事，对下一位接手者等于没有发生。另一端的建议是补充证据，不是命令；意见冲突时按直接证据、反例、成本和读者价值判断。

## 1. 角色（不绑定具体 Agent）

| 角色 | 职责 | 目前通常由谁担任 |
|---|---|---|
| **执行者** | 认领工作单元：调查、写作、自审、合入 `main` | dot 为主；Claude、Codex 会话也可以，并行规则见第 4.6 节 |
| **阶段审计** | 按第 6 节质量清单审查一段时间内的增量，结论写在 `docs/collaboration/reviews/` | 用户发起的 Claude 会话；其他 Agent 也可以担任，但不审自己执行的工作 |
| **抽审与方向补充** | 抽查已合入 `main` 的单元；在 BACKLOG 对应工作线下登记候选 | 云端 Codex，间歇参与 |

任何角色缺席都不阻塞其他工作。角色变化不扩大操作授权。

**自审**：每个工作单元标“完成”之前，执行者启动一个**独立的评审子 Agent**：
- 给它全新的上下文，只提供本单元的 diff、对应的验收标准和第 6 节的质量清单，不给写作过程中的推理；
- 它只报告“会改变读者选择”或“事实错误”的问题，每条附位置和依据；
- 执行者逐条处理（修改，或写明不改的理由），然后在 TASKS 对应行写一句自审结论。

自审不能替代阶段审计。阶段审计和抽审发现的问题优先处理。

## 2. 长期目标

**主干**：成为开发者在使用 Codex、Claude Code 等 Agent 时，能直接拿来做决定的中文参考：按任务给出建议、说明依据、写清何时失效，并保持时效。

**游戏领域**：成为“单人程序、无人工美术修补，借助 AI 做出可发布独立游戏”这一场景下最完整、最前沿、可直接采用的参考，覆盖资产管线、引擎接入、客户端模块、gameplay 架构和从概念到发布的路线。

**当前阶段重点（2026-10-16）**：按[BACKLOG阶段指导](../research/BACKLOG.md#本阶段重点把研究积累变成更好的选择)，把已有研究转成更清楚的方案取舍，并补会改变取舍的关键证据；重要新任务、技术能力与质量机会可以扩展范围，收敛不等于冻结方向。对外按读者任务组织入口，工作线仅用于内部执行；同时追求质量上限、持续可改与合理总投入，不以加流程代替可靠性、以新增案例代替深度。具体优先问题和完成信号只在该指导维护，不另建计划或扩大实测授权。

**阶段校正（2026-10-17，依据 [Claude 阶段审计](reviews/2026-10-17-claude-stage-audit.md)，优先于上段所指的 BACKLOG 指导）**：
1. **先提读者最多的 L2 页**：01 Agent 选型、Codex、Claude Code、02 模型与成本、12 资源索引、13 前沿雷达。这些页面达到 L3 之前，主干内容单元至少一半落在它们上面。**2026-10-18 状态核对：六页已在成熟度表达到 L3，这项阶段配额已结束；按实际内容缺口继续维护，不重复评级任务**；
2. **L3 页提高修改门槛**：已到 L3 的页面，新证据改变“30 秒结论”、某一行推荐、撤回某项建议，或支持此前未覆盖的重要读者任务时改正文（与 BACKLOG 的扩展原则一致）。只补充边界情况的发现写进研究记录，正文最多在页尾“边界情况”里加一行；
3. **篇幅预算**：单个专题正文约 30 KB 以内，超出的在下一个编辑轮按模块拆分或压缩，按当前篇幅与阅读负担选页。2026-10-18 核对：游戏 04／05 已分别约 32／32 KB，03 约 29 KB，Codex 约 31 KB；前轮主要压缩已完成，不继续使用旧超长名单。研究记录按证据价值收敛，不再把约 2 MB 作为总量硬上限：删除重复内容和被取代的推理，保留决定性来源、反证与版本限制；每周净增仍不超过约 100 KB。篇幅不衡量质量，正文预算服务于可读性，研究记录取舍服务于判断的可核查性（2026-10-17 更新）；
4. **可读性**：按第 6 节第 9 条写作。

## 3. 内容成熟度

每个专题页按四级评估，长期目标是让核心页面都达到 L3：

| 级别 | 标准 |
|---|---|
| L1 覆盖 | 主要方案都列到了，有来源 |
| L2 可采用 | 有分档推荐或条件选择、撤回条件、“30 秒结论” |
| L3 权威 | 关键事实交叉核对；写明反证和失效条件；动态事实带核实日期；和其他页面的核心建议一致；读者不需要读研究记录就能做决定 |
| L4 实证 | 有本仓库的可复查实验支持（属于第 7 节的后续阶段） |

`docs/README.md` 维护一张**成熟度表**：每个核心页面一行，写当前级别、差距和下一步。选择工作时，优先把差距最大、读者最多的页面往上提一级。

## 4. 工作线：唯一的任务编号

**工作线是唯一的顶层任务编号**，TASKS 的每一行都以工作线开头，例如 “GA：……”。其他编号的地位：
- 锚点的**四条主线**是研究方向，不是任务，由 M3 承接；
- BACKLOG 的 **R01–R16** 是工作线下的问题条目，编号只作索引；
- 游戏的 **WP0–WP13** 已完成理论交付，编号只作研究记录的索引，后续工作按 GA–GF 进行。

新方向必须挂到某条工作线下；挂不上的登记在 BACKLOG，等用户决定。各条线可以并行，没有固定的完成日期。

### 主干线

| 线 | 持续做什么 | 阶段性完成的标志 |
|---|---|---|
| M1 入口与核心建议 | 维护首页、docs/README 的阅读路径和核心建议一致性清单；专题结论变化时同步入口 | 任意入口进入，同一个问题得到一致的建议 |
| M2 时效 | 每周更新 Codex、Claude Code 和主要模型的变化，以及 13 号前沿雷达；只写改变建议的内容 | 13 号的核实时间不超过 7 天 |
| M3 四条主线 | 按 BACKLOG 的四条长期任务持续深化，每次至少一项新证据 | 每条主线都有一份 L3 的主专题 |
| M4 方法与机制 | 20 长程执行、22 评估、23 浏览器验证等方法页：整理成可复用的流程和检查清单；包括长程执行者（如 dot）自身的用法和运行改进，见下 | 方法页达到 L3，能直接指导一次评估或长程任务 |
| M5 模板 | templates/ 和各引擎模板与最新结论保持一致；改脚本必须带回归测试 | 模板里没有和正文矛盾的默认做法 |
| M6 AI 探索任务 | 加强 Agent 做开放式探索的通用能力，主专题是 [25](../25-ai-exploration.md)；本仓库的待验证流程按这套方法运行 | 25 达到 L3；同一套方法在至少三类不同案例上走通（纸面），并给出探索质量的评估方式；探索 Skill 的设计可以直接落地 |

**M6 覆盖探索的全过程**：
1. **定义**：需求卡，写明要解决什么、硬约束、判断标准、预算和停止条件；
2. **检索**：按任务类型选择一手渠道（代码平台、社区原帖、官方文档、论文、设计参照库等）和工具（搜索与抓取、深度调研产品、GitHub 和社区 API），以及按渠道并行；
3. **甄别**：质量信号，反广告、反 SEO 信号，交叉核对，独立的核查子 Agent；
4. **收敛**：带证据列的候选表，最后给出“采用 / 改造 / 自建 / 放弃”的判断；
5. **转化**：把选中的参照提炼成约束和验收标准，交给生成任务；
6. **评估**：衡量一次探索的质量，例如是否找到已知的好答案、引用是否支持结论、广告和过时结果占多少。

先调查现有的深度调研产品、开源调研 Agent 和评测方法，再决定本仓库补什么。案例只用来检验方法，不为单个案例写专题。

**M4 的长程执行者改进**（2026-10-16 提高优先级）：主要执行者的效率决定整个仓库的推进速度，所以作为一条**常驻并行线**持续做，和内容线同时推进，不替代内容线。分两部分：
- **运行改进**：发布失败、审批超时、返工、上下文不够、并行冲突等问题，诊断后直接改本手册、[运行细则](operations.md)或执行者的工作流，不另写过程文档。每周在 TASKS 交接里汇总四个信号：发布失败率、无人值守中断次数、退回比例、单元从认领到合入的时长；统计口径见运行细则第 3 节；
- **读者内容**：长程 Agent（Dots、Codex 云端任务、Claude Code 后台任务等）怎样用得好，写进 [Codex 页](../01-agents/codex.md) 的长时运行一节和 [20 长程执行](../20-codex-long-horizon.md)。本仓库的持续运行是一手案例，可以引用汇总后的事实（失败类型、修复办法、前后对比），但不写账号、用量或费用数据；单个仓库的经验按单例标注，推广前要找其他来源。

## 4.5 发布方式（避免逐文件审批）

- **首选 `git push`**：本地提交后整批推送；shell 没有写认证时用已授权的连接器，不自行新增凭据；
- **增量发布**：固定最新远端 `main` 的 SHA，只上传变化的文件，在工具上限内批量写入，最后以该 SHA 为预期旧值更新分支；基线前进或更新被拒时先整合再发；
- **失败恢复**：超时、断连或 `user cancelled` 只说明结果待核。先读远端确认是否已生效，已生效不重发，未生效从断点继续；
- **无人值守**：开跑前确认发布授权和审批路径；需要人工确认时保存断点，转做其他工作。

完整步骤见[运行细则](operations.md)第 1 节。

## 4.6 并行与认领

多个执行者可以同时工作，按下面的规则避免互相覆盖：
- **TASKS 的写法**：“进行中”每个单元一行；“最近交接”每个单元一行（工作线、SHA、读者能看到的改进、验证范围），最多保留约 10 行，不写叙述段落，更早的搬到 `archive/`；
- **认领**：开工、恢复和选择下一单元前，按[运行细则第 2.1 节](operations.md#21-跨执行者的发现与交接)核对远端分支认领与开放 PR；在 TASKS 的“进行中”写一行，包括工作线和问题、执行者、分支、主要改动的文件、开始日期。超过 24 小时没有新提交，认领自动失效，其他人可以先读该分支再接手；
- **同一页面的正文同一时间只由一个执行者修改**。不同工作线、不同页面可以随意并行；
- **分支**：每个执行者用自己的分支，例如 `<执行者>/<主题>`；小步提交，合入前先读取并整合最新的远端 `main`（细节见[运行细则](operations.md)第 2 节）。不强推，不改写已发布的历史，不覆盖他人的提交；
- **共享文件只做小改**：首页 README、`docs/README.md`（成熟度表、核心建议一致性清单）、TASKS、BACKLOG、`12-resources`、`13-frontier-radar`。每个单元只在最后一个提交里追加或修改自己那一行；需要大改的交给 M1 或编辑轮，并先在 TASKS 认领；
- **冲突**：合并冲突时先保留双方内容再整理；结论冲突无法调和的，写进 TASKS 的“需要用户决定”；
- **子 Agent**：执行者可以开子 Agent 并行调查，但子 Agent 交回的结论必须核对来源后才能采用。

## 5. 运行节奏

| 频率 | 做什么 |
|---|---|
| 每个工作单元 | 开始前合并最新 `main` 并在 TASKS 认领；执行；独立子 Agent 自审；提交并合回 `main`；在 TASKS 写结果：提交 SHA、读者能看到的改进、实际验证范围、阻塞 |
| 每周 | M2 时效更新；更新成熟度表 |
| 每完成约 10 个工作单元 | 编辑轮：统一做措辞类修订；检查入口一致性；检查篇幅预算，处理超出的页面；压缩研究记录（开头摘要，移出被取代的推理）；把 TASKS 里已完成的行搬到 `archive/`；在 TASKS 写一段复盘 |
| 每月 | 复核游戏动态事实表；检查研究记录总量和开工三件套的篇幅；重新评估各条线的优先级 |

**单元完成不等于长期维护结束。** 发布核验后先按现有队列选择下一项有价值且可执行的工作；其他线仍在运行时串行合入即可，不能把“已排队”写成“正在执行”。临时问答不默认取消维护，处理完应回到未完成单元；独立调查可继续并行，避免所有内容线都依赖主对话当下是否在处理仓库。

**等待必须有具体对象。** 长时间等待前核对是否有实际运行的工作、外部结果或明确阻塞。仅某项缺权限／证据时转做独立可完成项；确无有价值可执行项时，按第8节记录已查缺口、接续条件并简短告知，不能静默把维护当结束，也不制造任务或提交来填空。平台中断后的恢复仍按第0、4.5节核状态；以上是执行约定，不是24小时不断运行的保证。

**选题顺序**：用户和阶段审计的待办 > 阻塞执行者运行的问题（例如发布失败、无人值守中断）> 时效（M2）> 成熟度差距最大的核心页面 > 新方向。这是同一条线内的先后；不同工作线照常并行。

## 6. 质量清单（自审和阶段审计都按这张表）

1. **前沿**：有没有漏掉近几个月的重要模型、服务、版本或做法？
2. **一手**：关键事实是否来自官方文档、源码、论文或开发者原文？动态事实是否带核实日期？
3. **可采用**：读者只读“30 秒结论”能否做出第一个选择？有没有撤回条件？
4. **一致**：是否和核心建议一致性清单、相关专题矛盾？入口是否已同步？
5. **价值**：这次修改是否改变了读者的选择，还是只改了措辞（只改措辞的留到编辑轮）？
6. **简洁**：正文是否把细节和限定语留给了研究记录？
7. **不以偏概全**：单个游戏或项目的结论是否只用来支持它的具体机制？引擎相关的结论是否分别核实了 Unity 和 Unreal？
8. **合规**：许可、来源、公开仓库安全要求（无密钥、无本机路径、无私人内容）。
9. **可读**：先写结论，再写条件；一段最多一个关键限定，其余限定放进研究记录；不用连串的“不以……代替……”“不推……”式否定句；按读者是开发者来写，不按审计者来写。

## 7. 后续阶段（实测，暂不执行）

## 8. 什么时候停下来问用户

不停止整体运行，只把问题写进 TASKS 的“需要用户决定”，然后继续做其他线：
- 需要安装、付费、下载大模型、运行引擎、联系外部的人；
- 想新建目录、模块或编号专题；
- 认为方向锚点需要修改，或本手册修改超出已授权的 M4 运行改进范围；
- 两条线的结论出现无法自行调和的冲突。

**整体停下的条件**：连续多个工作单元都被等待用户决定卡住，或者发现方向性问题需要用户先改锚点。停下时在 TASKS 顶部写总结。

## 9. 验证与平台

- **统一离线入口**：`python3 scripts/check_offline.py`，CI 的仓库检查工作流复用同一入口。它只做离线文档、配置检查和单元测试，不运行模型或引擎；
- **检查实际交付树**：只检查本单元要交付的内容，不让并行的未提交改动混进来；具体做法见[运行细则](operations.md)第 2 节；
- **结论的边界**：“范围内通过”不等于已合并、hosted CI 已通过或已部署；工作流文件存在也不等于 CI 跑过，以 GitHub 上对应提交的实际结果为准；
- **平台检查不可用时**：继续做研究和离线验证，不自行修改账户设置或付费。为避免触发无效运行，期间的提交可以标 `[skip ci]`，并记录 CI “未运行”；平台恢复后用不带跳过标记的新提交触发真实检查。
