# 长期推进计划（dot 持续运行）

> 2026-10-15 起生效，用户授权。适用于主干 AI coding 和游戏领域两条线的长期、可能无人值守的推进。方向以 [AGENTS.md 方向锚点](../../AGENTS.md) 为准；游戏线的工作包定义见 [游戏任务书](game-taskbook.md)。
> 本计划取代游戏任务书第 6 节和原“阶段 G”的实验安排：**当前不做实测**，先把机制、文档和内容做到高质量。实测放到第 7 节的后续阶段，由用户决定何时开始。

## 1. 协作方式

| 角色 | 职责 |
|---|---|
| **dot** | 主要执行端：调查、写作、修订、自审、合并到 `main` |
| **本 Claude 会话** | 方向指导和阶段审计，由用户发起；审计结论写在 `docs/collaboration/reviews/` |
| **云端 Codex** | 间歇参与（额度不稳定）：有额度时由用户分派抽审、方向补充，或认领一项与 dot 不重叠的独立任务；不承担必经的评审，缺席时不阻塞任何工作 |

**自审取代原来的云端评审**：每个工作单元标“完成”之前，dot 启动一个**独立的评审子 Agent**：
- 给它全新的上下文，只提供本单元的 diff、对应的验收标准和第 6 节的质量清单，不给写作过程中的推理；
- 它只报告“会改变读者选择”或“事实错误”的问题，每条附位置和依据；
- dot 逐条处理（修改，或写明不改的理由），然后在 TASKS 对应行写一句自审结论。

自审不能替代用户和 Claude 的阶段审计。阶段审计和云端 Codex 抽审发现的问题优先处理。

**云端 Codex 参与时**：
- 抽审：在已合入 `main` 的工作单元里抽查，按第 6 节质量清单写结论；
- 方向补充：在 BACKLOG 对应工作线下登记候选；
- 独立任务：在 TASKS 认领，只改自己认领范围内的文件，避免和 dot 同时改同一段。

## 2. 长期目标

**主干**：成为开发者在使用 Codex、Claude Code 等 Agent 时，能直接拿来做决定的中文参考：按任务给出建议、说明依据、写清何时失效，并保持时效。

**游戏领域**：成为“单人程序、无人工美术修补，借助 AI 做出可发布独立游戏”这一场景下最完整、最前沿、可直接采用的参考，覆盖资产管线、引擎接入、客户端模块、gameplay 架构和从概念到发布的路线。

## 3. 内容成熟度

每个专题页按四级评估，长期目标是让核心页面都达到 L3：

| 级别 | 标准 |
|---|---|
| L1 覆盖 | 主要方案都列到了，有来源 |
| L2 可采用 | 有分档推荐或条件选择、撤回条件、“30 秒结论” |
| L3 权威 | 关键事实交叉核对；写明反证和失效条件；动态事实带核实日期；和其他页面的核心建议一致；读者不需要读研究记录就能做决定 |
| L4 实证 | 有本仓库的可复查实验支持（属于第 7 节的后续阶段） |

dot 在 `docs/README.md` 维护一张**成熟度表**：每个核心页面一行，写当前级别、差距和下一步。选择工作时，优先把差距最大、读者最多的页面往上提一级。

## 4.5 发布方式（避免逐文件审批）

- **首选 `git push`**：本地 `git commit` 后一次推送整批提交。一次发布只需要一次推送，不会因为逐个文件的审批而中断；
- **不能直接推送时**：只上传相对 `main` 有变化的文件，不重传整棵目录树；在连接器允许的范围内尽量一次调用写完多个变更文件，不设固定文件数；只有工具本身有上限或调用失败时才拆分，核对成功回执后从断点继续；
- **无人值守时**：需要人工确认的审批弹窗没人处理，会超时并显示为“user cancelled”。长期运行前，先在 Codex 的审批规则里放行对本仓库的 `git push`，或者提前确认发布方式；
- **研究与发布分开**：研究可以并行；合入和发布串行、小批量、及时进行，不要攒大量未发布的历史；
- 发布失败时从断点继续：记录已经成功写入的文件，不从头重来。
- **dot 在云端 shell 运行时的情况**（2026-10-15 核实）：shell 里没有 Git 写入凭据，GitHub 授权只能通过连接器使用。两种做法：
  - 用连接器按增量发布：只传变更文件，已经上传过的文件对象直接复用；调用次数尽量少，不设固定批量，最后一次更新 `main`；
  - 在 dot 的云端环境设置里配置环境密钥：一个**只授权本仓库、只有 contents 读写权限、设了过期时间**的细粒度 token，再配上 git credential helper。token 不要贴进对话或写进仓库。

## 5. 运行节奏

| 频率 | 做什么 |
|---|---|
| 每个工作单元 | 开始前合并最新 `main`；执行；独立子 Agent 自审；提交并合回 `main`；在 TASKS 记录 |
| 每周 | M2 时效更新；更新成熟度表 |
| 每完成约 10 个工作单元 | 编辑轮：统一做措辞类修订；检查入口一致性；压缩研究记录（开头摘要，移出被取代的推理）；在 TASKS 写一段复盘 |
| 每月 | 复核游戏动态事实表；检查研究记录总量和正文规模是否失控；重新评估各条线的优先级 |

**选题顺序**：用户和阶段审计的待办 > 时效（M2）> 成熟度差距最大的核心页面 > 新方向。新方向必须能归到第 4 节的某条线，否则登记到 BACKLOG，等用户决定。

## 6. 质量清单（自审和阶段审计都按这张表）

1. **前沿**：有没有漏掉近几个月的重要模型、服务、版本或做法？
2. **一手**：关键事实是否来自官方文档、源码、论文或开发者原文？动态事实是否带核实日期？
3. **可采用**：读者只读“30 秒结论”能否做出第一个选择？有没有撤回条件？
4. **一致**：是否和核心建议一致性清单、相关专题矛盾？入口是否已同步？
5. **价值**：这次修改是否改变了读者的选择，还是只改了措辞（只改措辞的留到编辑轮）？
6. **简洁**：正文是否把细节和限定语留给了研究记录？
7. **不以偏概全**：单个游戏或项目的结论是否只用来支持它的具体机制？引擎相关的结论是否分别核实了 Unity 和 Unreal？
8. **合规**：许可、来源、公开仓库安全要求（无密钥、无本机路径、无私人内容）。

## 8. 什么时候停下来问用户

不停止整体运行，只把问题写进 TASKS 的“需要用户决定”，然后继续做其他线：
- 需要安装、付费、下载大模型、运行引擎、联系外部的人；
- 想新建目录、模块或编号专题；
- 认为方向锚点或本计划需要修改；
- 两条线的结论出现无法自行调和的冲突。

**整体停下的条件**：连续多个工作单元都被等待用户决定卡住，或者发现方向性问题需要用户先改锚点。停下时在 TASKS 顶部写总结。
