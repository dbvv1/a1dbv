# 运行手册（长期计划）

方向以 [AGENTS 用户锚点](../../AGENTS.md) 为准，状态看 [TASKS](TASKS.md)，游戏细则见 [game-taskbook](game-taskbook.md)。本手册取代旧 maintenance-roadmap／STATE／职责说明，历史保留在 Git。

## 0. 开工

先读AGENTS、本手册、TASKS的待决定／认领／交接，其余按任务读取。三份合计约35KB，超出先在下一编辑轮压缩。交接只依赖Git，记结论、证据、状态与下一步；外部意见是补充，分歧按证据、反例、成本和读者价值判断。

## 1. 角色（不绑定具体 Agent）

执行者认领、调查、写作、整合；阶段审计按§6审增量并写reviews；抽审抽查已合入main的单元并在BACKLOG补候选。通常dot执行、用户发起Claude审计、Codex间歇抽审，其他Agent也可阶段审计，但不得审自己执行的工作；角色不绑定工具，缺席不阻其他工作、不扩授权。

单元完成前全新上下文独审，只给diff、验收和§6，不给作者推理；逐项处理附位置／依据的实质问题，不改须写理由，TASKS留结论。无独审则留待审并做独立只读研究，不称通过。自审不替代阶段审计；阶段审计和抽审发现的问题均优先。

## 2. 长期目标

**主干**：成为开发者在使用 Codex、Claude Code 等 Agent 时，能直接拿来做决定的中文参考：按任务给出建议、说明依据、写清何时失效，并保持时效。

**游戏领域**：成为“单人程序、无人工美术修补，借助 AI 做出可发布独立游戏”这一场景下最完整、最前沿、可直接采用的参考，覆盖资产管线、引擎接入、客户端模块、gameplay 架构和从概念到发布的路线。

**当前阶段重点（2026-10-16）**：按[BACKLOG阶段指导](../research/BACKLOG.md#本阶段重点把研究积累变成更好的选择)，把已有研究转成更清楚的方案取舍，并补会改变取舍的关键证据；重要新任务、技术能力与质量机会可以扩展范围，收敛不等于冻结方向。对外按读者任务组织入口，工作线仅用于内部执行；同时追求质量上限、持续可改与合理总投入，不以加流程代替可靠性、以新增案例代替深度。具体优先问题和完成信号只在该指导维护，不另建计划或扩大实测授权。

**阶段校正（2026-10-20 修订，依据 [Claude 阶段审计](reviews/2026-10-20-claude-stage-audit.md)，优先于上段所指的 BACKLOG 指导）**。本段只由用户或阶段审计修改；其他执行者或审计有异议，写进 TASKS“需要用户决定”，不直接改写。

**项目板**：大任务统一放在 [TASKS 的“项目板”](TASKS.md#项目板)，原 K1–K7 已移入。规则如下：
- **项目**：一项 0.5–3 天、能改变读者某个重要选择或完成一项交付的工作，带验收标准。类型包括补强、探索、优化、结构和时效。每个工作单元都属于某个项目，执行者做完一个项目再换，不在零散小题之间跳；
- **执行者可以自己开项目**：锚点范围内、不需要新目录、安装、付费或运行引擎的项目，直接加到项目板，标“提议：执行者名”，不用等审计或用户。验收里必须写明：主干项目改变哪条 **Agent 使用**建议，游戏项目回答 AI 能承担多少。只讲通用 Web 或工程做法的不立项。阶段审计每周删减和排序；
- **TASKS 只放状态**：项目板、进行中、最近交接和周信号摘要（约 10 行）。空档表、统计推导等分析写进 `reviews/`，TASKS 只放链接。开工三件套合计约 35 KB 以内；
- **自己合入，不走 PR（2026-10-20 用户决定）**：每个执行者完成一个项目就自己合入 `main`，不开 PR、不设专门整合者，步骤见[运行细则 §2.1](operations.md#21-跨执行者的发现与交接)第一条。每个执行者待合入的成果不超过 2 份，超过就先合入再开新项目；
- **项目要够大**：一个“项目”二三十分钟就完成，说明它其实是单元。规划时把同一读者问题下的几个单元合成一个项目，验收写到可交付的产物（例如一条完整的二改链），不按条目数计；
- **规划提醒**（2026-10-20 由硬水位改为提醒，采纳[云端 Codex 核心审计](reviews/2026-10-20-core-value-2653cbb.md)建议）：有值得做且能执行的项目时先推进；剩余项目不够接续时，才做约 1 小时的**规划单元**，不为凑数量立项。补项目的来源：
  - **重心**（2026-10-21 用户决定）：AI coding 主干，以及游戏开发全流程（G1）与 AI coding 的结合，优先从这里立项，包括[覆盖地图](coverage-map.md)第四节的社区实践和开源项目；
  - 游戏客户端／gameplay：先补覆盖地图第二节里最核心、最通用的机制；按类型的系统和高质量专题是长期兜底方向，主干和 G1 任务不够时再立项；
  - 前沿扫描：Codex／Claude Code 的 changelog 和发布、新模型、主要社区讨论、Agent coding 论文、游戏资产生成工具的新版本与授权变化；
  - 核心审计和用户提出的问题；
  - 首页读者任务表中答得不好的问题；
  - 游戏路线图 06 各阶段的缺口；
  - dot 自身的运行问题（M4）。
- **兜底顺序**：项目板上的项目都被阻塞时，按 M2 时效扫描 → 编辑轮 → M4 运行优化 → 规划单元 → 覆盖地图里的 gameplay／客户端长期方向的顺序做。“没有可做的事”不再是停下的理由；只有全部工作都卡在用户授权上时才停，并按第 8 节记录。

**写作与选题规则**：
1. **AI 关联**：主干正文单元要说明 Agent 在这个选择里做什么、会错在哪、人要检查什么。游戏客户端和 gameplay 的领域质量知识属于 G2 范围，单条不必提 AI，但所在模块要有 项目板 P2 的“AI 一行”。单个作品或项目的机制细化不单独作为一个单元；
2. **给默认**：按第 6 节第 3 条，结论要有当前默认，不能只写“按任务比较”；
3. **L3 页提高修改门槛**：新证据改变“30 秒结论”、某一行推荐、撤回某项建议，或支持此前未覆盖的重要读者任务时才改正文；只补边界的发现写进研究记录；
4. **篇幅**：单页正文约 30 KB 以内。研究记录不设总量上限，每周净增约 100 KB 以内（10-17 至 10-20 三天多增加约 235 KB，超出预算）；P3 完成、周增量回到预算之前，每个单元的研究净增约 10 KB 以内；
5. **可读**：按第 6 节第 9 条，审计报告也一样：先写结论，正文约 10 KB；
6. **流程减负**：不在 `main` 上单独做认领提交（本期第一父链 189 个提交中有 40 个只是认领）。需要占位时推到自己的分支，否则认领行与内容同一提交。整合者合入后，删除自己创建的已合分支。

## 3. 内容成熟度

L1有方案与来源；L2有默认、分档、撤回及30秒结论；L3关键事实交叉核对、反证／日期／入口一致，正文可独立决策；L4有本仓可复查实验（§7后续阶段）。目标核心页L3；docs/README表记级别、差距和下一步，优先读者多且差距大的页。

## 4.5 发布方式（避免逐文件审批）

本地commit后优先git push，缺认证用既有连接器、不新凭据；环境未变不重复已核失败。固定main，仅批量差异／复用对象，以旧SHA作预期、非强推；main变先整合重验。超时／断连／取消先核结果，成功不重发、不明不盲试；明确拒绝不换路。待批保断点，只停依赖动作。授权、增量和恢复步骤见[细则§1](operations.md)。

## 4.6 并行与认领

- 开工／恢复／选题按[细则§2.1](operations.md#21-跨执行者的发现与交接)查分支和PR；认领不等于活跃。TASKS写问题、执行者、分支、文件、起点；24小时无新提交失效，接手先读旧分支。
- 同页单作者、独立文件并行、main串行；各用分支，保双方历史不覆盖，结论冲突写待决定。子Agent结果核源后用。
- README、docs/README、TASKS、BACKLOG、12／13只在最终交付改必要行；M1／编辑轮大改先认领，禁止main单独认领见§2。
- 进行中／交接各单元一行，含线、SHA、改进、验证；最近约10行，其余原样归档。

## 5. 运行节奏

- 单元：核状态／认领→执行→独审→整合验证→交接续做。问答后回当前单元，独立调查可并行，不把排队称运行。
- 每天UTC+8首单元由dot-A按最新分工更新项目板状态／阻塞／水位；每周：M2、成熟度、M4。每周或约100提交由阶段审计核默认／前沿、规则效果、方向和项目，事实约抽10单元。
- 每约10单元编辑轮：措辞、入口、篇幅、摘要／旧推理、TASKS归档与简短复盘；每月复核游戏动态、研究总量、开工篇幅和优先级。
- 等待前核真实工作、外部结果及独立项，缺权限／证据只停相关项并按§2兜底；恢复按§0／4.5。同行优先：用户／审计→运行阻塞→M2→项目板→规划，不阻其他线。

## 6. 质量清单（自审和阶段审计都按这张表）

1. **前沿**：有没有漏掉近几个月的重要模型、服务、版本或做法？
2. **一手**：关键事实是否来自官方文档、源码、论文或开发者原文？动态事实是否带核实日期？
3. **可采用**：读者只读“30 秒结论”能否做出第一个选择？有没有当前默认（✅）和不推荐项（⛔）？有没有撤回条件？证据有限时给当前最佳默认并写明撤回条件，不能只写“按任务比较”。
4. **一致**：是否和核心建议一致性清单、相关专题矛盾？入口是否已同步？
5. **价值**：这次修改是否改变了读者的选择，还是只改了措辞（只改措辞的留到编辑轮）？
6. **简洁**：正文是否把细节和限定语留给了研究记录？
7. **不以偏概全**：单个游戏或项目的结论是否只用来支持它的具体机制？引擎相关的结论是否分别核实了 Unity 和 Unreal？
8. **合规**：许可、来源、公开仓库安全要求（无密钥、无本机路径、无私人内容）。
9. **可读**：先写结论，再写条件；一段最多一个关键限定，其余限定放进研究记录；不用连串的“不以……代替……”“不推……”式否定句；按读者是开发者来写，不按审计者来写。
10. **AI 关联**：主干：这个选择里 Agent 做什么、典型会错在哪、人要检查什么？答不上来的不写进主干正文。游戏：领域质量知识可以写，但所在模块或资源类别要回答 AI 能承担多少、瓶颈在哪、怎么验证。

## 7. 后续阶段（实测，暂不执行）

用户决定后才按GF预注册：G3静态3D（约0美元）→G1像素二改（API上限5美元）→G2 Unity内置／外部导入→G4玩法生命周期→含第二次需求修改的完整垂直切片。不是现行授权；真实客户端／权限／恢复、原生OS／引擎兼容、模型／成本优势、Hook全路径隔离均不能由离线检查推定。

## 8. 什么时候停下来问用户

安装、付费、大模型下载、引擎、外部联系、新目录／模块／编号专题、锚点或超M4授权的手册修改、不可调和结论，写TASKS待决定并继续其他线，已问不重复。整体停止依§2；留总结、缺口、Git可接手结果和恢复条件，不承诺持续在线。

## 9. 验证与平台

独审修复定树后跑 `python3 scripts/check_offline.py` 与 `git diff --check`；定点检查可先做，别混未交付改动，变树重验，脚本补最小复现／回归（细则§2）。发布核远端tree／父链／文件及精确CI。

离线、源码、真实客户端／模型／引擎／OS、hosted CI分报，工作流存在不算执行。平台不可用不改账号或付费，继续授权内研究／离线；可 `[skip ci]` 并记未跑，恢复后用未跳过提交触发真实检查。
