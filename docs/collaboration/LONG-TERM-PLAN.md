## 运行卡（先读这一节；与下文冲突时以本节为准）

> 2026-10-22 加。前几天的教训：规则奖励“能被证明正确”，指标一个个被刷满，内容却不够前沿、不够有用，偏差都要靠用户指出。本节把目标、检查和产能分配压成一页，下文各节只作参考和操作细则。

**目标**：读者（用户就是代表读者）读完，能用上**当前最强、而且他原本不知道**的 AI coding 做法和工具；游戏开发全流程与 AI coding 的结合是第二重心。可靠是底线，不是目标。

**每次交付自问三件事**（独立审查也按这三条审）：
1. **前沿**：是否同题对照了近 3–6 个月最强的做法？决定性来源是不是做事的人写的原文（团队复盘、作者、论文、实际项目），而不是官方介绍或转述？
2. **增量**：读者、或者不看本仓的强模型，原本会怎么做？这次交付改变了什么、多告诉了什么？说不出增量就不交付。
3. **实证**：自己装过、跑过、试过吗？没有的，结论里写明“未试用”。AI coding 的工具和做法默认先试再写。

**每次探索的最低覆盖**（前沿不能保证一直赶上，但每次找的时候要找到当时能找到的最前沿；用 [25 探索提示词](prompts/2026-10-21-exploration-self-use.md)）：
- **做事的人**：前沿团队和头部实践者近 3–6 个月的原文（按[来源名册](../research/2026-10-15-exploration-evidence.md#p46按团队追踪来源与漏检校准)扫，不只搜关键词）；
- **研究**：近期论文与评测，读到方法和结果部分；
- **社区**：至少两个讨论渠道，其中一个是中文社区（HN、Reddit、GitHub issue／discussion、linux.do、V2EX、掘金等），读原帖和高赞评论，看正反意见；X 抓不到就看[收件箱](inbox.md)和转引原帖；
- **开源**：GitHub 上同题的热门和新晋项目，看 star 增长、近期提交和 issue 里的真实问题；
- 交付里写一行**探索回执**：查了哪些渠道、截止日期、读不到的渠道。四类缺一类，就在回执里说明原因。

**产能分配**（按周粗算，不逐日计较）：
- 约 70% **核心**：计分板队列（核心页、M6、游戏按页收口）和 P79 这类验证；
- 约 20% **前沿发现**（C5）：收件箱、社区和开源热门项目、上手试用；
- 约 10% **新意实验**：有创意的组合、原型、跨领域想法、本仓自己的观点（例如一个新的工作流组合、一个自制 Skill、一个 AI coding 与游戏结合的新玩法）。标 🧪 实验或“观点”，和推荐默认分开写，失败也照实记录。

**主指标是用户的判断**：dot-A **每天**（UTC+8 21:00 前）在[简报](digest.md)最上面新增当天一节，汇总两个 dot 当天最值得看的 3–5 条（发现、改动、实验），每条一句“为什么值得看”加链接；末尾写**三问自查**（当天哪项交付没过前沿、增量或实证，明天怎么改）和**互审结论**（见下）。用户有空时标“有用／没用”或写一句话，dot 第二天按反馈调整。一天里没有一条说得出增量的交付，本身就是跑偏信号。辅助指标：计分板、独立审计、漏检率、发现时差、P79 的增量。**辅助指标在涨、主指标不动，就是跑偏信号**，下周换做法，而不是继续刷辅助指标。

**效率**：dot 全天运行，24 小时都应在做有增量的工作，不按“一天几件”限速；队列空了就按计分板、收件箱、沉淀回看、新意实验的顺序补，不停下等指示。等用户的事（授权、开中转、填反馈）只记进 TASKS“需要用户决定”，立刻转做下一项；研究可以用子 Agent 并行；同一项目的小步改动攒成一次交付再审（见第 2 节交付粒度）。

**dot 也参与审计**（2026-10-22 用户要求；占核心产能的一部分，每天做）：
- **互审**：dot-A 审 dot-B 当天的 1–2 项交付，dot-B 审 dot-A 的，按三问和锚点工作原则 0–8 逐条看；自己的交付不算审计。小问题直接告诉对方由对方改，涉及方向的写进 TASKS。
- **沉淀回看**：每天各挑 1 个 10-21 之前完成的页面或研究记录（研究目录约 3.6 MB、52 个文件），问三件事：①按当前一代还成立吗，过时的改或删；②里面有没有埋着、但正文没用上的好东西（新工具、反直觉的发现、可试的做法），有就提到正文或“值得一试”表；③有没有可以合并或删掉的重复内容。
- **原则回看**：每周一各写 3 行：上周哪条规则帮了忙、哪条在拖后腿、建议怎么替换。作为运行卡周修订的输入。
- 互审和回看的结论写进当天简报的“互审结论”一行；改动照常走交付流程。

**外部校准**（防止自己看不见自己的盲区）：
- 每周一次独立质量审计（[提示词](prompts/2026-10-22-calibration-audit.md)）；
- 每两周一次**外部十件事对照**（[提示词](prompts/monthly-top10.md)）：不看本仓的独立会话列出当前 AI coding 最重要的 10 件事，对照本仓覆盖，漏掉的直接立项。

**不做**：为登记而登记；打磨读者用不上的细节（例如 IDE 子页的权限差异）；只读 README 就下评价；堆限定语（每条结论最多一句关键局限）。

**原则跟上，但不零碎**：阶段审计每天看一次简报、计分板和两个 dot 的交付，按三问抽查两三项，偏差当天写进 TASKS 给出指导；**运行卡本身每周修订一次**，依据是这一周的用户反馈、互审与回看、漏检和独立审计结果。运行卡只有这一页，新增规则必须替换或删掉一条旧规则；操作步骤放[运行细则](operations.md)。用户提出的调整随时生效。

## 2. 长期目标

**主干**：成为开发者在使用 Codex、Claude Code 等 Agent 时，能直接拿来做决定的中文参考：按任务给出建议、说明依据、写清何时失效，并保持时效。

**游戏领域**：成为“单人程序、无人工美术修补，借助 AI 做出可发布独立游戏”这一场景下最完整、最前沿、可直接采用的参考，覆盖资产管线、引擎接入、客户端模块、gameplay 架构和从概念到发布的路线。

**当前阶段重点（2026-10-16）**：按[BACKLOG阶段指导](../research/BACKLOG.md#本阶段重点把研究积累变成更好的选择)，把已有研究转成更清楚的方案取舍，并补会改变取舍的关键证据；重要新任务、技术能力与质量机会可以扩展范围，收敛不等于冻结方向。对外按读者任务组织入口，工作线仅用于内部执行；同时追求质量上限、持续可改与合理总投入，不以加流程代替可靠性、以新增案例代替深度。具体优先问题和完成信号只在该指导维护，不另建计划或扩大实测授权。

**阶段校正（2026-10-20 修订，依据 [Claude 阶段审计](reviews/2026-10-20-claude-stage-audit.md)，优先于上段所指的 BACKLOG 指导）**。本段只由用户或阶段审计修改；其他执行者或审计有异议，写进 TASKS“需要用户决定”，不直接改写。

**长程推进：战役、计分板、泳道**（2026-10-21 加；这是项目的主要来源，取代靠审计或用户逐个补项目）：
- **战役**：长期目标拆成有数字终点的几项战役，执行者从计分板差距自己生成项目：
  - **C1 AI coding 主干前沿化**（**最优先**）：第一阶段（核心 12 页差距≤1）10-22 达成。**第二阶段**：Codex、Claude Code 专题到≤1；**次要页（计分板 SECONDARY：01 下的 Gemini／IDE／开源 Agent 子页、04、06、10、11、13、16–18、21、23、24）保持≤2 即可，只在出现改变读者选择的新证据时再改**（10-22 用户决定：VS Code 权限、Kiro 云会话这类细节对目标读者价值低）；核心 12 页（00、01、02、03、05、07、08、09、14、15、20、22）向 0 推进，每页的主要选择写清当前最高水平是什么、本仓是否采用，有第二个独立来源，漏检回扫没有重要遗漏；覆盖地图第四节升到 3；标记 90 天内复核；
  - **C2 游戏 G1 × AI coding**：游戏 01–06 与资产各页同上，差距≤1；
  - **C3 来源与探索（M6）**（与 C1 同为最优先）：25 页本身到差距≤1；每两周一份漏检统计（第一份用 10-22 校准审计的 6 项），漏检率逐期下降并据此改 25 的步骤；来源名册覆盖 C1、C2 各主线；
  - **C5 前沿发现（AI coding，2026-10-22 加）**：让读者在这里第一时间看到值得一试的新东西，而不只是保守的默认。
    - **渠道**：用户收件箱 [inbox.md](inbox.md)（用户在 X、linux.do 等处看到的链接直接贴进去，24 小时内处理，这是最高信号的渠道）；GitHub 新晋热门项目（按 claude-code、codex、mcp、agent 等主题）；HN（含 Show HN，Algolia API）；Reddit r/ClaudeAI、r/ChatGPTCoding、r/LocalLLaMA；linux.do、V2EX、掘金等中文社区；前沿团队和头部实践者的帖子。抓不到的平台如实记“读取缺口”，靠收件箱补。
    - **读者形式**：[13 前沿雷达](../13-frontier-radar.md)页首维护“值得一试”表，每项写：是什么、亮点（为什么值得看）、热度证据（star 与增长、讨论原帖）、本仓试用结果、适合谁、坑和评级（🧪／👀）。放不下就拆新页。这里允许写“新、有意思、值得试”，不要求先证明是最优，但要标清证据等级。
    - **上手试用**：入选项在工作区里装起来，用一个固定小任务试 15–30 分钟，记录装没装上、做成了什么、哪里卡住；需要模型的走本地中转。只看 README 不算试用。
    - **度量**：发现时差（社区开始热议到本仓收录的天数）和收件箱命中率（用户贴来的链接里，本仓已经收录的比例）；收件箱里本仓没发现的条目计入 M6 漏检。
  - **C4 兜底：gameplay／客户端**：覆盖地图第二节的核心机制升到 3 级；C1、C2 没有可做项目时才做。
- **计分板**：开工先跑 `python3 scripts/scoreboard.py`，看各战役的登记数、差距、过期页和待推进队列。标记写在页面“当前最高水平”一节里：`<!-- frontier: status=已比较 gap=1 gen=2026-09 checked=2026-10-21 -->`（status 为已比较／仅候选／未知，gap 0–3，gen 是复核时的模型与工具代际）。“当前最高水平”一节推荐写成短表：主要选择 → 领先替代 → 决定（采用／保留／未覆盖），详细证据放研究记录；差距按整页的主要选择打分，局部比较不能代表整页。只有完成同题比较才能登记或调小差距；计分板会列出审计分比自评差的页面，执行者按证据改标记，或补比较后在标记里加 `audit=<审计日期>` 表示已回应，两种分数都不自动覆盖对方；**历史完成不豁免**：10-21 以前完成的项目和 L3 页面只按当时标准核对了事实，不算前沿验收，没有自己标记的页面按[独立审计基线](frontier-baseline.tsv)计，未审计的按差距 2 排队。执行者自评最低到 1，**0 只能由独立审计给出**。差距要调到 ≤1，决定性来源里至少有一个读过原文的近期最高水平来源（前沿团队的工程复盘、近期论文或演讲、头部作品的技术分析）；只靠官方文档、源码或已发行作品的，差距不低于 2。独立审查核对标记与正文一致，双周质量审计抽查，发现虚高就改回并记入 TASKS。
- **泳道与队列**：当前分工见 TASKS“战役与泳道”：dot-A 负责 C1、C3、C5，dot-B 负责 C2、C4。**重心是 AI coding 主干和 M6**（2026-10-22 用户决定）：C1、C3 的第二阶段完成前，dot-A 不转去支援游戏；C2 落后由 dot-B 按页收口解决。每个执行者在 TASKS 保持约 3 个排队项目，少于 3 个时从计分板队列补，不等审计；补的必须是能改变读者选择的真实缺口，没有就转做核心页深化或兜底方向，不为凑数立项。项目按“把某页从差距 X 降到 ≤1”或“把某格升一级”定义，通常 0.5–2 天。
- **度量**：周报只报计分板变化（新登记、差距下降、过期数）和漏检率，不报提交数。阶段审计看趋势、抽查标记、调整战役终点，不再逐个补项目。

**项目板**：大任务统一放在 [TASKS 的“项目板”](TASKS.md#项目板)，原 K1–K7 已移入。规则如下：
- **项目**：一项 0.5–3 天、能改变读者某个重要选择或完成一项交付的工作，带验收标准。类型包括补强、探索、优化、结构和时效。每个工作单元都属于某个项目，执行者做完一个项目再换，不在零散小题之间跳；
- **执行者可以自己开项目**：锚点范围内、不需要新目录、安装、付费或运行引擎的项目，直接加到项目板，标“提议：执行者名”，不用等审计或用户。验收里必须写明：主干项目改变哪条 **Agent 使用**建议，游戏项目回答 AI 能承担多少。只讲通用 Web 或工程做法的不立项。阶段审计每周删减和排序；
- **TASKS 只放状态**：项目板、进行中、最近交接和周信号摘要（约 10 行）。空档表、统计推导等分析写进 `reviews/`，TASKS 只放链接。开工三件套合计约 35 KB 以内；
- **自己合入，不走 PR（2026-10-20 用户决定）**：每个执行者完成一个项目就自己合入 `main`，不开 PR、不设专门整合者，步骤见[运行细则 §2.1](operations.md#21-跨执行者的发现与交接)第一条。每个执行者待合入的成果不超过 2 份，超过就先合入再开新项目；
- **项目要够大**：一个“项目”二三十分钟就完成，说明它其实是单元。规划时把同一读者问题下的几个单元合成一个项目，验收写到可交付的产物（例如一条完整的二改链），不按条目数计；
- **规划提醒**（2026-10-20 由硬水位改为提醒，采纳[云端 Codex 核心审计](reviews/2026-10-20-core-value-2653cbb.md)建议）：有值得做且能执行的项目时先推进；剩余项目不够接续时，才做约 1 小时的**规划单元**，不为凑数量立项。补项目的来源：
  - **重心**（2026-10-21 用户决定）：AI coding 主干，以及游戏开发全流程（G1）与 AI coding 的结合，优先从这里立项，包括[覆盖地图](coverage-map.md)第四节的社区实践和开源项目；
  - 游戏客户端／gameplay：先补覆盖地图第二节里最核心、最通用的机制；按类型的系统和高质量专题是长期兜底方向，主干和 G1 任务不够时再立项；
  - 前沿扫描：Codex／Claude Code 的 changelog 和发布、新模型、主要社区讨论、Agent coding 论文、游戏资产生成工具的新版本与授权变化；
  - 核心审计和用户提出的问题；
  - 首页读者任务表中答得不好的问题；
  - 游戏路线图 06 各阶段的缺口；
  - dot 自身的运行问题（M4）。
- **交付粒度**：一次交付至少包含一处读者可见的正文变化；同一项目的小步改动在本地或自己的分支累积，攒成一次交付再做独立审查、更新 TASKS 和归档。公开扫描和离线检查每次推送照常跑。
- **编号**：新项目取项目板与归档中最大编号加一；推送前与最新 `main` 核对，撞号时后到者改号。
- **兜底顺序**：项目板上的项目都被阻塞时，按 M2 时效扫描 → 编辑轮 → M4 运行优化 → 规划单元 → 覆盖地图里的 gameplay／客户端长期方向的顺序做。“没有可做的事”不再是停下的理由；只有全部工作都卡在用户授权上时才停，并按第 8 节记录。

**写作与选题规则**：
1. **AI 关联**：主干正文单元要说明 Agent 在这个选择里做什么、会错在哪、人要检查什么。游戏客户端和 gameplay 的领域质量知识属于 G2 范围，单条不必提 AI，但所在模块要有 项目板 P2 的“AI 一行”。单个作品或项目的机制细化不单独作为一个单元；
2. **给默认**：按第 6 节第 3 条，结论要有当前默认，不能只写“按任务比较”；
3. **L3 页提高修改门槛**：新证据改变“30 秒结论”、某一行推荐、撤回某项建议，或支持此前未覆盖的重要读者任务时才改正文；只补边界的发现写进研究记录； 例外：还没和领先路线比较过的问题，可以直接立项比较；比较后仍选旧方案的，写明比较过和理由。
4. **篇幅**：单页正文不设硬上限（2026-10-21 用户决定），由执行者按可读性判断：读者在页内找不到要的结论，或一页装了几个独立的读者问题，就拆成新页面并保留旧链接；约 30 KB 只作提醒。研究记录不设总量上限，每周净增约 100 KB 以内（10-17 至 10-20 三天多增加约 235 KB，超出预算）；P3 完成、周增量回到预算之前，每个单元的研究净增约 10 KB 以内；
5. **可读**：按第 6 节第 9 条，审计报告也一样：先写结论，正文约 10 KB；
6. **流程减负**：不在 `main` 上单独做认领提交（本期第一父链 189 个提交中有 40 个只是认领）。需要占位时推到自己的分支，否则认领行与内容同一提交。整合者合入后，删除自己创建的已合分支。
7. **最高水平卡**（2026-10-21 加，落实锚点原则 0）：每个内容项目先做一张卡，写进该主题的研究记录开头或项目交接：问题；**当前最高水平**（做法、出处、日期、是谁）；主流做法；可行做法；本仓推荐属于哪一层、为什么。没有这张卡的项目不算完成验收。找最高水平的来源：
   - 主干：前沿实验室和工具厂商的工程文章、近期论文与评测、顶尖实践者的公开做法、社区高赞讨论（HN、Reddit、中文社区）、头部开源项目及其 issue；
   - **按人和团队找，不只按关键词找**：前沿做法先出现在少数团队和实践者的工程博客、演讲、访谈和帖子里（AI coding 首先是 Anthropic、OpenAI 等工具团队对自身使用的复盘），搜索引擎和转载往往滞后。维护一份来源名册（P46），按名册定期扫描；精选者和转载（含中文公众号）只作雷达，回到原文。读这类来源时记下团队规模、模型与算力、代码库类型、度量口径和人工审查方式，区分可迁移的机制和依赖其条件的部分；自报的产量数字不说明质量；
   - **记录漏检**：重要内容若先由用户或外部转载带来、而不是本仓扫描发现，记为一次漏检，并把它的原始来源补进名册；
   - 游戏：近两年 GDC、SIGGRAPH 等演讲，引擎最新功能与官方样例工程，头部工作室技术博客，口碑最好作品的技术分析，优秀独立开发者的分享与复盘；
   - 来源要尽量新：AI coding 以近 3–6 个月、当前一代模型和工具为准，更早的要说明在当前一代上仍然成立；游戏超过两年的要说明为什么仍代表最高水平。时效有三层：事实（版本、价格、参数）、做法（某个问题的最好做法）、范式（人和 Agent 怎么分工、自主到什么程度、瓶颈在哪）。只更新事实不算跟上前沿；
   - **代际复核**：核心推荐写明基于哪一代模型和工具。新一代主力模型或 Agent 工具发布后两周内，复核 00、14 和核心页的 30 秒结论，逐条确认、修正或撤回。

## 6. 质量清单（自审和阶段审计都按这张表）

1. **前沿**：有没有漏掉近几个月的重要模型、服务、版本、做法或范式变化？这条结论代表的是**可行**（有人做到过）、**主流**（多数人这样做），还是**当前最高水平**？核心页要写明当前最高水平是什么、出自哪里、多新，再说它对目标读者是否值得采用；成熟的旧方案可以胜出，但要说明比较过。
2. **一手**：关键事实是否来自官方文档、源码、论文或开发者原文？动态事实是否带核实日期？
3. **可采用**：读者只读“30 秒结论”能否做出第一个选择？有没有当前默认（✅）和不推荐项（⛔）？有没有撤回条件？证据有限时给当前最佳默认并写明撤回条件，不能只写“按任务比较”。
4. **一致**：是否和核心建议一致性清单、相关专题矛盾？入口是否已同步？
5. **价值**：这次修改是否改变了读者的选择，还是只改了措辞（只改措辞的留到编辑轮）？
6. **简洁**：正文是否把细节和限定语留给了研究记录？
7. **不以偏概全**：单个游戏或项目的结论是否只用来支持它的具体机制？引擎相关的结论是否分别核实了 Unity 和 Unreal？
8. **合规**：许可、来源、公开仓库安全要求（无密钥、无本机路径、无私人内容）。
9. **可读**：先写结论，再写条件；一段最多一个关键限定，其余限定放进研究记录；不用连串的“不以……代替……”“不推……”式否定句；按读者是开发者来写，不按审计者来写。
10. **AI 关联**：主干：这个选择里 Agent 做什么、典型会错在哪、人要检查什么？答不上来的不写进主干正文。游戏：领域质量知识可以写，但所在模块或资源类别要回答 AI 能承担多少、瓶颈在哪、怎么验证。
