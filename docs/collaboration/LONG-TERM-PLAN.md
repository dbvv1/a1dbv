# 运行手册

> 方向见 [AGENTS](../../AGENTS.md)，本文维护执行规则；Git与调度见[运行细则](operations.md)，当前工作见[TASKS](TASKS.md)。

## 1. 核心思想

**找到真实技术人员正在用的、当前最好的 AI coding 做法、工具和开源项目，亲手试过，提炼成读者马上能用的东西；再留一点空间给有新意的尝试。**

选题看读者能采用什么；亲手试用、形成明确选择，把时间用在实际成果与前沿缺口上。

## 2. 每次交付前问五个问题

独立审查和 dot 互审也按这五问审。

1. **前沿**：官方、社区、开源三方都看了吗？是不是近 3–6 个月、当前一代的做法（游戏看近两年）？决定性来源是不是做事的人写的原文，而不是官方介绍或转述？
2. **增量**：读者原本不知道、或会做错的是什么？这次告诉了他什么？说不出来就不交付。
3. **实证**：装过、跑过、试过吗？没有就写“未试用”。
4. **诚实**：结论与来源、数据、核实日期及实际适用条件一致吗？按 CLAUDE 编写约定集中说明一次。
5. **好懂**：读者能迅速找到选择、开始步骤和关键取舍吗？限定语淹没结论与事实夸大都须修正；用实际复述检查，不以删词数量判通过。

## 3. 怎么探索

**前沿比较项目的最低覆盖**（每次找的时候，要找到当时能找到的最前沿；按 [25 探索提示词](prompts/2026-10-21-exploration-self-use.md)执行。精确 API 查询和已有研究续接按缺口取资料，不重复全渠道回扫）：
- **官方**：Anthropic、OpenAI 等的文档、工程文章、changelog 与发布说明；
- **做事的人**：前沿团队和头部实践者近 3–6 个月的原文，按[来源名册](../research/2026-10-15-exploration-evidence.md#p46按团队追踪来源与漏检校准)扫，不只搜关键词；近期论文读到方法和结果；
- **社区**：至少两个讨论渠道，其中一个中文（HN、Reddit、GitHub issue／discussion、linux.do、V2EX、掘金等），读原帖和高赞评论，正反都看；X 抓不到就看用户[收件箱](inbox.md)和转引的原帖；
- **开源**：GitHub 上同题的热门和新晋项目，看 star 增长、近期提交和 issue 里的真实问题；
- 交付里写一行**探索回执**：查了哪些渠道、截止日期、哪些读不到。

**从社区和开源项目提炼精华，不是列链接。** 每个值得看的项目或讨论回答五件事：解决什么问题；关键机制是什么（读代码和设计，不只看 README）；谁在用、反馈如何（issue、讨论、复盘，正反都有）；本仓试用结果；可以借用的精华是什么、适合谁、坑在哪。

**收件箱**：用户在 X、linux.do 等处看到的链接贴进 [inbox.md](inbox.md)，dot-A 24 小时内处理。用户贴来、本仓此前没发现的，记一次漏检，并把它的原始渠道补进来源名册。

## 4. 做什么

**产能分配**（按周粗算）：约 70% 核心（A：前沿强方法的选择、组合与真实采用；B：完整模块深化与高质量作品并行）；约 20% 前沿发现；约 10% 新意实验（标 🧪 或“观点”，和推荐默认分开写，失败照实记）。

**分工**：dot-A 做 AI coding 与 M6；dot-B 做游戏知识（AI 全链路与客户端／gameplay 核心模块），作品是其验证支线。A 不转向游戏开发，也不代管 B 的工作。

**完成看成品**：A 的完成是读者能照着用的任务路线或资产，并在一次真实开发中用上；B 的完成是知识进入模块正文、作品改进进入可玩的默认分支。研究记录、检查回执和待验说明是支撑，不是交付本身。

**自主选题**：完成、受阻或收益下降时，读最新 main、在制分支和 TASKS，选最重要的可执行缺口，不等队列清空，也不等用户派题。以完整能力、模块或可玩改进组织工作；同一窄题收益已低就收口。受阻只停依赖环节，在 TASKS 留恢复条件，转做独立工作；明确拒绝不换路绕过。确无值得做的题时如实说明，不制造忙碌。运行状态以 Dot 平台实际为准，Git 更新不保证唤醒；每个 dot 保留一个心跳定时任务（[细则§3](operations.md#3-dot-运行保障)），不另建其他调度。

**本地模型是主要产能**：dot 负责方向、拆分、取舍和接收，把目标清楚、可独立检查的调查、实现、测试、资源制作与初稿持续派给本地模型（[local-jobs](local-jobs/README.md)，规则见[细则§2.2](operations.md#22-本地模型协作)）。独立任务可以同时在途多项；长期只有一项在途、其余都由 dot 亲手做，通常说明拆分不够。

**项目**：写进 [TASKS 项目板](TASKS.md#项目板)并带验收；执行者可以自己开项目。编号取项目板与归档中最大编号加一，推送前与最新 `main` 核对，撞号时后到者改号。同一项目的小步改动攒成一次交付。

**计分标记**：核心页“当前最高水平”一节写成短表（主要选择 → 领先替代 → 决定），节内放 `<!-- frontier: status=已比较|仅候选|未知 gap=0-3 gen=<代际> checked=<日期> -->`。只有做完同题比较才能登记或调小差距；自评最低到 1，0 只能由独立审计给出；回应过某次审计的，在标记里加 `audit=<审计日期>`。计分板只是辅助指标。

## 5. 写成什么样

**三层内容**（见锚点）：值得一试（[13 前沿雷达](../13-frontier-radar.md)）、当前最佳做法（决策页）、直接可用（`templates/`）。正文写法以 [CLAUDE 编写约定](../../CLAUDE.md#编写约定)为准。存量按读者问题整节重写，保留关键事实与操作入口；已改善页面直接接收，不为统一模板再次改写。

**可视化**（读者没耐心读长文，图是主要呈现方式之一）。按这个顺序选：
1. **真实截图**：上手试用时截下界面、终端输出或产物，这是最有说服力的图，“值得一试”里试过的项目尽量每项一张；
2. **代码生成的图**：结构、流程、决策树和对比用 Mermaid 或 SVG；数据用脚本画图。只把文字排成表格的 SVG 不算可视化；
3. **生图模型**：只在确有助理解具体知识且有授权时配图，不为简报或凑画面制造工作。知识图解默认二次元／ACG 表达，先画真实对象、因果和对照，趣味来自发现与转折；保留解释为什么、怎么做所需的文字，不用栏目图标或装饰背景代替知识。生图负责画面，**准确的文字和数字用代码叠加**（SVG 或图片处理脚本），不让模型自己写字；生成后自己看一遍成品，并检查读者能否据图复述具体机制或下一步动作；字准但没有知识仍须返工；生成性质在邻近说明中交代，不在画面里追加水印式提示。

知识漫画先写问题→动作→结果的分镜，再选 ACG 画风；人物要参与因果，不站在说明栏旁；每格补足实际问题、动作、观察或下一步决定，不靠少字掩盖知识不足。标题、对白与术语分别设计字形和位置，准确排字不等于裸贴文字。复用[短提示词](prompts/acg-knowledge-comic.md)，只保留帮助读者理解的标注。

图片放 `docs/img/`，单张尽量不超过 300 KB（优先 WebP），附替代文字。

**后台减负**：
- 研究记录只为支撑正文而写，开头三行写结论；
- 实验脚本和夹具只在真正运行时写；
- 验证细节（树 SHA、检查命令、回执）写进提交说明，不写进正文和 TASKS；
- TASKS 保持 10 KB 以内，只放当前重点、分工、项目板和需要用户决定的事，其余移入归档。

**取舍**：优先保留能改变开发选择、指导实现的知识；链接清单、重复过程和对读者无用的细节退出正文。

## 6. 节奏与反馈

**简报暂停（2026-10-24 用户要求）**：停止每日／定时简报、digest 更新及配图整理。重要发现直接回流主专题、可用模板或清晰采用建议；只在有重要成果、需要决定或阻塞时简短通知。

**互审与方向纠偏**：沿每日互审检查对方的重要新增，既看第2节五问，也看最近一组交付是否增强主线能力与作品品质、是否进入读者入口或可玩版本、下一题是否只是惯性扩题。发现偏题立即调整。

**每周独立审计**：由未参与本周写作的新上下文审方向和关键增量，抽读必要正文与未合分支，对照外部强实践，也检查指导本身是否导致偏题、正文是否被限定语淹没；不重复已审内容。既有外部十件事每两周继续，用于发现漏项。

**指导层（2026-10-25 用户指定）**：Claude 核心方向会话负责方向与原则；Codex 审计会话负责增量审计、本地执行接线和仓库整理。两边经 Git 交接，同一批指导文件不同时修改。指导按变化频率分三层：

| 层 | 内容 | 修改方式 |
|---|---|---|
| 锚点 | `AGENTS.md` 方向锚点 | 用户维护 |
| 长期规则 | 本手册、[细则](operations.md)、长期提示词 [A](prompts/dot-a.md)／[B](prompts/dot-b.md) | 只在方向层问题时修订；替换旧文字而非追加，修订后总量不增加；提示词固定文件名就地更新 |
| 当前重点 | [TASKS](TASKS.md)“当前重点”与项目板 | 每轮纠偏和局部欠项只改这里，当前重点最多三条 |

一次纠偏不新建审计报告或提示词文件；需要留档的理由写进提交说明。

## 7. 交付流程

1. 在自己的分支完成一个可接收结果，整合最新 `main` 后核实际交付差量。一次独立审查覆盖内容、事实和集成，已有有效审查可复用。正文改写由非作者先读新文复述选择与步骤，再对照原文核关键结论、数据、来源与必要条件；遗漏或方向改变就修对应段，改完收口。篇幅和限定词密度只用于发现冗余，不设压缩比例，不以链接数或结构逐字相同代替语义核对。
2. 按下表选检查，在最后一次相关修改后通过即可。源码、依赖、运行配置、检查器或所验行为变了，重验受影响路径；仅提交SHA变化、无关文档合入或移交执行者，不使结果失效。明确失败必须修复，不能用缩小范围掩盖失败。

| 改动范围 | 适用检查 |
|---|---|
| 纯正文、审计、任务／指导文档 | `python3 scripts/check_repo.py`、来源与关键结论核查、实际读者入口；不跑无关Hook／实验套件 |
| 某个实验、模板或产品代码 | 上述文档检查及该模块相关测试／类型／构建检查，真实消费者和直接失败路径；页面改动回真实浏览器，音频改动实际试听 |
| 共享检查器、Hook基础设施、跨套件公共依赖或影响范围无法确定 | `python3 scripts/check_offline.py` 完整入口，加该变化需要的真实行为验证；完整入口不是产品验收的替代 |

3. 每次发布保留公开文件扫描 `python3 scripts/check_public.py`、提交身份扫描 `python3 scripts/check_public.py --commits origin/main..HEAD`，暂存本次新增文件后跑 `git diff --cached --check`，人工审差量。已通过的同一受检版本可复用；提交扫描在提交后运行。简单合并只补整合差量与上述发布检查，不重跑所有未受影响实验。CI配置保持原样，准确报告实际运行范围。
4. `git push origin HEAD:main` 只允许快进，不开PR、不强推；按[运行细则](operations.md#21-跨执行者的发现与交接)核发布结果。B无法写main时由A接收；A复用B的有效审查／检查，只核新增整合影响。
5. 真实搭建／运行单次最多2小时。受阻记录具体入口、原因、未完成结果和恢复条件到既有TASKS，转做独立项；下一次选题先核条件是否恢复，不能用新题默默覆盖旧验收。已有明确拒绝保持停止，不换入口绕过。
6. 本地模型协作按[运行细则§2.2](operations.md#22-本地模型协作)，不另造验证体系。检查摘要写进现有提交／研究记录，不加证明账本。

## 8. 边界

授权范围见锚点“自主与边界”和 `AGENTS.md` 的“公开仓库安全”。未被授权覆盖的事（付费、大模型下载、运行引擎、新建目录）写进 TASKS“需要用户决定”，立刻转做其他项；已经问过的不重复问。

## 9. 长期方向与当前承接

> 持续职责，不是做完即停的清单；当前承诺与阻塞在 TASKS。高质量指做出更强的能力与更好的成品，高效率指走到可用结果的投入，前沿指相对强替代的优势；材料新鲜或边界说明多都不能代替它们。

**dot-A：前沿强方法的选择、组合与真实采用**

- 面向完整功能交付、已有项目连续修改、复杂诊断与优化、多 Agent 整合、长任务接续这些真实目标，找当前强实践，比较原生基线与强替代，给明确的条件推荐和可用起点。资料充分就给选择，不等全行业最优证明。
- 主要交付是**任务路线**：某类任务现在推荐什么组合、为什么胜过可信替代、从哪里开始、何时不值得用。已有的符号编辑、运行态取证、堆分析、工作树与分支接续、框架反馈等是组合材料，不逐工具造案例。
- **真实采用**：让实际编码 Agent（含本地模型）带着所选知识与工具完成真实开发，由实际消费者检查结果。任务来自开源项目、用户的其他仓库和自身工具开发；Star-Rush 只是可选载体之一，不作默认，冲突时 B 优先。
- 正式方法对照只在用户明确要求时开展。M6 主动寻找更强的正向做法，不只补故障与安全边界。通用库修复系列、逐工具边界小试、只研究他人案例都不做成惯性系列。

**dot-B：完整模块深化与高质量游戏制作并行**

- 主线是游戏 AI 全链路（2D、3D、动画、材质特效、音乐音效、场景的制作与接入）与客户端／gameplay 核心知识。按完整开发问题写模块：体验目标、核心机制、强参照与默认选择、实现起点、关联模块、AI 怎样实施；把已有分散研究合并进模块正文，不再逐条新增小研究项。
- **作品是验证支线（三个案例合计约三成精力，2026-10-26 用户决定扩展）**：Star-Rush-Reborn 进入维护期，只做品质提升；MOBA-Like 是当前主案例；FPS-Like 排队。统一做法见[游戏方向细则§6](game-taskbook.md#6-作品案例)。作品检验主线方法并做出可体验成品，不让 B 变成单款游戏开发者；把已写模块在案例里跑通算主线验证。B 负责各案例默认分支：自测通过即合入，许可清楚、工程验证通过的素材默认启用，感知未定的调参留开关，不长期停在临时分支。部署按已有授权。
- 验收受限只停对应环节：能独立完成的源资产、代码、加载与构建先做成可用版本；需要人听、看、玩的验收记入 TASKS“待人工验收”由用户统一处理，执行者转做其他工作；感知结果直接决定实现时不盲调。
- 一次只推进一个新案例，走到第二次需求修改再开下一个；不以多开项目代替完成作品。潮汐邮差保留为窄例；Game-Core-Knowledge 按原分工。

两边长期无人值守时持续发现、取舍、实施和回流；当前承诺优先，探索不必等欠项清零。判断方向时看正向能力与成品提升，不只看是否避免错误。
