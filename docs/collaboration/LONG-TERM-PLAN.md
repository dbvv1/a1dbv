# 运行手册

> 2026-10-22 重写（用户批准，Claude 起草）。方向和原则见 [AGENTS 方向锚点](../../AGENTS.md)，本手册是**唯一的执行规则**；操作步骤（Git 发布、恢复、本地中转）见[运行细则](operations.md)。旧版手册（战役、写作规则 1–7、质量清单、工作线 M1–M6／GA–GF 等）已并入本手册或删除，见 Git 历史。状态见 [TASKS](TASKS.md)。

## 1. 核心思想

**找到真实技术人员正在用的、当前最好的 AI coding 做法、工具和开源项目，亲手试过，提炼成读者马上能用的东西；再留一点空间给有新意的尝试。**

前几天走偏的三种方式，以后一律当作跑偏信号：
- **只求“可证明正确”**：挑容易核实的窄题、多引官方文档、堆限定语，结果可靠但没人觉得有用；
- **刷指标**：单元数、L3、差距分、登记数一个个被刷满，读者价值没涨；
- **只读不用**：没装过、没跑过就评价工具。

## 2. 每次交付前问五个问题

独立审查和 dot 互审也按这五问审。

1. **前沿**：官方、社区、开源三方都看了吗？是不是近 3–6 个月、当前一代的做法（游戏看近两年）？决定性来源是不是做事的人写的原文，而不是官方介绍或转述？
2. **增量**：读者原本不知道、或会做错的是什么？这次告诉了他什么？说不出来就不交付。
3. **实证**：装过、跑过、试过吗？没有就写“未试用”。
4. **诚实**：事实有证据等级和日期；单个案例只证明它自己；效果没测过不写成已验证。
5. **好懂**：结论放第一句；一条结论最多一句关键局限；能用图表说清的用图表。

## 3. 怎么探索

**前沿比较项目的最低覆盖**（每次找的时候，要找到当时能找到的最前沿；按 [25 探索提示词](prompts/2026-10-21-exploration-self-use.md)执行。精确 API 查询和已有研究续接按缺口取资料，不重复全渠道回扫）：
- **官方**：Anthropic、OpenAI 等的文档、工程文章、changelog 与发布说明；
- **做事的人**：前沿团队和头部实践者近 3–6 个月的原文，按[来源名册](../research/2026-10-15-exploration-evidence.md#p46按团队追踪来源与漏检校准)扫，不只搜关键词；近期论文读到方法和结果；
- **社区**：至少两个讨论渠道，其中一个中文（HN、Reddit、GitHub issue／discussion、linux.do、V2EX、掘金等），读原帖和高赞评论，正反都看；X 抓不到就看用户[收件箱](inbox.md)和转引的原帖；
- **开源**：GitHub 上同题的热门和新晋项目，看 star 增长、近期提交和 issue 里的真实问题；
- 交付里写一行**探索回执**：查了哪些渠道、截止日期、哪些读不到。

**从社区和开源项目提炼精华，不是列链接。** 每个值得看的项目或讨论回答五件事：解决什么问题；关键机制是什么（读代码和设计，不只看 README）；谁在用、反馈如何（issue、讨论、复盘，正反都有）；本仓试用结果；可以借用的精华是什么、适合谁、坑在哪。

**收件箱**：用户在 X、linux.do 等处看到的链接贴进 [inbox.md](inbox.md)，dot-A 24 小时内处理。用户贴来、本仓此前没发现的，记一次漏检，并把它的原始渠道补进来源名册。

## 4. 做什么

**产能分配**（按周粗算）：
- 约 70% **核心**：AI coding 的当前最佳做法页（计分板队列）、M6 探索能力、验证（吸取测试 P79、本地中转对照）；游戏由 dot-B 推进 G1 实战与核心模块；
- 约 20% **前沿发现**：收件箱、社区和开源热门项目，上手试用 15–30 分钟，结果进“值得一试”；
- 约 10% **新意实验**：有创意的组合、原型、自制 Skill、AI coding 与游戏结合的新玩法、本仓自己的观点；标 🧪 实验或“观点”，和推荐默认分开写，失败也照实记。

**分工**：dot-A 做 AI coding（核心页、M6、前沿发现、验证）；dot-B 做游戏。可以互助，但 AI coding 和 M6 的核心目标完成前，dot-A 不转去做游戏。

**持续推进与自主选题**：在执行平台可运行且授权有效时，完成一项接下一项，不按每天数量限速。自主选题从每次选题开始，不等队列清空：先读最新要求、在制分支和 TASKS，选择最重要的可执行缺口。A说明要增强哪项Agent能力、真实任务检验什么；B说明要改善哪段AI制作链或哪个客户端／gameplay问题。用一句话写进既有项目描述，不另建选题表。

优先接完有价值的在制成果，再从§9近期方向、核心页未决问题、收件箱与社区／开源发现续题；发现更重要的问题可调整顺序并简述原因。每次交付或受阻时顺手更新 TASKS 的下一步：有现成高价值候选就选，不为凑备用数量制造题目。等待权限只停依赖动作，转做独立工作；同一窄题收益已低就收口。候选用完先做一次有边界的探索，仍无值得做的题则如实说明缺口，不用重复检查填时间。

**执行状态**：仓库规则表达工作方向，Git更新不保证唤醒Dot。运行、排队、等待输入和停止以平台实际状态为准；只在能读取时确认已有续跑安排与实际恢复记录，取不到写未知。沿现有安排续接，不重复创建调度；具体通知边界见[运行细则](operations.md#21-跨执行者的发现与交接)。

**项目**：围绕读者问题交出可用结果；0.5–3 天只作估时，范围由内容和验证需要决定，写进 [TASKS 项目板](TASKS.md#项目板)并带验收；执行者可以自己开项目，写明增量是什么。编号取项目板与归档中最大编号加一，推送前与最新 `main` 核对，撞号时后到者改号。同一项目的小步改动攒成一次交付再审。

**计分标记**：核心页“当前最高水平”一节写成短表（主要选择 → 领先替代 → 决定），节内放 `<!-- frontier: status=已比较|仅候选|未知 gap=0-3 gen=<代际> checked=<日期> -->`。只有做完同题比较才能登记或调小差距；自评最低到 1，0 只能由独立审计给出；回应过某次审计的，在标记里加 `audit=<审计日期>`。计分板只是辅助指标。

## 5. 写成什么样

**三层内容**（见锚点）：值得一试（[13 前沿雷达](../13-frontier-radar.md)页首的表，放不下就拆新页）；当前最佳做法（各决策页）；直接可用（`templates/` 的模板、Skill 和配置）。

**可视化**（读者没耐心读长文，图是主要呈现方式之一）。按这个顺序选：
1. **真实截图**：上手试用时截下界面、终端输出或产物，这是最有说服力的图，“值得一试”里试过的项目尽量每项一张；
2. **代码生成的图**：结构、流程、决策树和对比用 Mermaid 或 SVG；数据用脚本画图。只把文字排成表格的 SVG 不算可视化；
3. **生图模型**：每日21:00前的简报配图围绕当日实质内容，阶段总结或具体知识也可配图，不为凑画面编造进展。知识图解默认二次元／ACG 表达，先画真实对象、因果和对照，趣味来自发现与转折；保留解释为什么、怎么做所需的文字，不用栏目图标或装饰背景代替知识。生图负责画面，**准确的文字和数字用代码叠加**（SVG 或图片处理脚本），不让模型自己写字；生成后自己看一遍成品，并检查读者能否据图复述具体机制或下一步动作；字准但没有知识仍须返工；生成性质在邻近说明中交代，不在画面里追加水印式提示。

知识漫画先写问题→动作→结果的分镜，再选 ACG 画风；人物要参与因果，不站在说明栏旁；每格补足实际问题、动作、观察或下一步决定，不靠少字掩盖知识不足。标题、对白与术语分别设计字形和位置，准确排字不等于裸贴文字。复用[短提示词](prompts/acg-knowledge-comic.md)，只保留帮助读者理解的标注。

图片放 `docs/img/`，单张尽量不超过 300 KB（优先 WebP），附替代文字。

**后台减负**：
- 研究记录只为支撑正文而写，开头三行写结论；
- 实验脚本和夹具只在真正运行时写；
- 验证细节（树 SHA、检查命令、回执）写进提交说明，不写进正文和 TASKS；
- TASKS 保持 10 KB 以内，只放分工、项目板和需要用户决定的事，其余移入归档。

**不做**：没有试用、没有判断的链接堆和新闻转述；为指标而做的登记和打磨；读者用不上的细节（例如 IDE 子页的权限差异）；与 AI coding 无关的通用工程内容；连串的“不以……代替……”式否定句。

## 6. 节奏与反馈

**每日简报（主指标）**：dot-A 每天 UTC+8 21:00 前在[简报](digest.md)最上面新增当天一节，汇总两个 dot 当天最值得看的 3–5 条（发现、改动、实验），每条一句“为什么值得看”加链接，尽量配一张图；简报只写读者结论、链接和必要的试用范围；调试、执行注释、自查与互审过程留在既有研究／审查记录或提交说明，不混入阅读正文。用户有空时标“有用／没用”，dot 第二天按反馈调整。一天里没有一条说得出增量的交付，就是跑偏信号。

**互审与方向纠偏**：沿每日互审检查对方的重要新增，既看第2节五问，也看最近一组交付是否持续增强主线能力、成果是否进入读者入口、下一题是否只是惯性扩题。各自发现偏题立即调整，不等第二天。通用修复连做、孤立实验增多或主专题长期没变时，查具体价值，不以文件比例、篇数或固定天数裁决。

**每周独立审计**：由未参与本周写作的新上下文审方向和关键增量，抽读必要正文与未合分支，并对照外部强实践；不重复已审内容。审计者同时检查指导本身是否导致偏题，交具体纠正建议；执行者在本轮直接同步 TASKS、手册可编辑节和相关读者入口，不停在报告。范围涉及锚点或第1–2节时才提请用户。只有重新判断过的页面才更新既有基线，不按抽样数量或升分推进；历史校准提示词只作参考，不沿用其中固定日期、报告篇幅和仅报告不整改的旧交付限制。

沉淀回看、规则修订和外部漏检调查并入上述选题与审计：有新证据就修过时结论、提取有用发现、合并重复；替换导致问题的旧规则，不另交每日自检或每周三行报告。既有外部十件事每两周继续，用于发现漏项，不要求十项都立题。已有审计安排正常运行时无需再建一套；用户最新要求优先。

## 7. 交付流程

1. 在自己的分支完成；交付前用全新上下文做一次独立审查（只给 diff、验收和第 2 节五问，不给作者推理），自己的交付不能自审；
2. 合并最新 `main`，跑 `python3 scripts/check_offline.py` 和 `python3 scripts/check_public.py --commits origin/main..HEAD`，读一遍 `git diff`；
3. 自己合入：`git push origin HEAD:main`，只允许快进，不开 PR、不强推；细节和失败恢复见[运行细则 §1–§2.1](operations.md#21-跨执行者的发现与交接)。dot-B 推不了 `main` 时推自己的分支，由 dot-A 代合；
4. 真实搭建和运行单次最多 2 小时，受阻记下原因就换下一项；
5. 本地模型验证按[运行细则 §2.2](operations.md#22-本地薄中转验证优化的真实效果已获启用授权)：本地模型只当被测对象，硬限制只有三条（每题全新进程且吸取测试不给工具、只在临时目录运行、回传过公开扫描），其余只记录。

## 8. 边界

授权范围见锚点“自主与边界”和 `AGENTS.md` 的“公开仓库安全”。未被授权覆盖的事（付费、大模型下载、运行引擎、新建目录）写进 TASKS“需要用户决定”，立刻转做其他项；已经问过的不重复问。

## 9. 两周路线（10-23 至 11-06）

> 长程持续推进方向，不是做完即停的有限清单。按近乎全天工作的容量安排，完成一项接下一项；清单用完后从新发现、真实失败与核心知识缺口自主续题。独立调查／试用可并行，同一文件与集成交付明确归属；受阻只停依赖动作，不以排期或下一次审计为等待理由。

**dot-A（AI coding 与 M6）**
- **近期重点是 Agent 能力与做法**：先找值得用的当前工具、知识加载、反馈、取证或接续方式，再选真实任务检验。前一轮“完整编码示范”已偏成通用修复系列，到此收口；保留已有产物，把改变 Agent 操作或实现选择的机制回流主专题。候选试用有明确用途和边界即可分享，不强制补大型对照实验。
- 沿最近的 Agentation、原生 pdb／DebugMCP、会话恢复选题继续：有自然任务时让接手 Agent 据批注实际改页面、用断点解决未知分支；同时探索语义编辑、依赖自带 Skill、并行整合与长期接续的新做法。没有自然任务就保留现有结论，转向下一个有价值的能力缺口。
- 持续处理收件箱，探索成熟强方案与新冒头；按读者价值选择试用对象，不凑固定项目数。截图用于呈现实际发现，机制图用于解释为什么、怎样用。
- P79 按已冻结子批次和既有中转继续，当前执行条件见 TASKS；受阻时先推进上述能力试用与研究。可吸取包沿既有三任务对照，不另造评价体系。
- 核心页把试用发现提到首屏，用短结论和必要的图帮助读者操作；沿既定节奏做外部十件事对照，并将漏检用于改善探索。新意实验选择有价值的组合，失败也保留可借用的发现。

**dot-B（游戏）**
- **主线始终是 a1dbv 的游戏 AI 全链路与客户端／gameplay 核心模块**（2026-10-23 用户重申）。Star-Rush 是研究和验证的支线，任务从主线知识问题与产品真实缺口共同选取；案例成果及时回流，持续推进其他核心专题，不将全部精力转成单款赛车开发。
- **实战支线：[Star-Rush-Reborn](https://github.com/dbvv1/Star-Rush-Reborn)**（2026-10-23 用户指定）：把已有 Web 竞速项目持续做精，兼作 AI 全链路与客户端模块实测。先读目标仓库的约定、当前版本与在制工作，实际试玩后选最影响体验的问题；优先打磨驾驶／漂移、镜头与视听反馈，再沿真实瓶颈做输入、性能、资源、幽灵与联机。代码和资产在游戏仓库维护，经过实际任务验证的方法与取舍回流 a1dbv，不另建通用框架或为了覆盖知识点硬加玩法。Web 可验证通用客户端机制，Unity／Unreal 特有结论仍回对应引擎验证。
- **Star-Rush 的资源链也要实际做**：当前程序化美术／合成音频是基线，不是长期限制。按品质需要接入 AI 生成或许可清楚的现成美术、音乐与音效，跑通候选制作、格式处理、加载／打包、真实画面／试听和后续修改；保留有效的程序化部分，不为生成而全量替换。具体入口见游戏仓库 README“美术与音频的后续制作”，结果回流 G1 对应专题。
- **本轮实战续接（10-24）**：先接收赛车分支中的提示同步与 AI 卡片，并把提示的路段预览／动作优先级回流赛车专题。下一项优先完成真实音频资源链，或完整实操同弯入弯—抓地／漂移—出弯恢复，按观察修实际问题；两项都持续推进。音频从一个有用事件或一段音乐开始，比较可用候选、接入、听验并二改，沿已有生成权限推进 AI 音乐／音效；缺权限只停该生成入口。Blender 往返候选已撤回，保留作者路径发现，待真实构图需求再续，不扩建验证工具。
- **收口已有 G1 小样**：潮汐邮差保留为资产与二改的窄示例，完成已承诺的版本接收和知识回流，不并行扩建另一款长期游戏。其他环境的旧版通过可复用其范围，不能代替新版验收；受阻只停依赖动作，继续 Star-Rush 或核心模块。
- **知识参考：[Game-Core-Knowledge](https://github.com/dbvv1/Game-Core-Knowledge)**：先了解已有客户端知识与面经，可补充相关纠错、来源和实测案例；尊重已有维护分工，不接管面经主线，不把 a1dbv 全文复制成第二份。仓库内容未就绪时不阻塞实战。
- **核心模块围绕一个完整的读者问题做深**：从优秀作品的公开实践中提炼机制、关键参数、体验标准和失败，再比较现成实现与引擎方案（Unity 优先、Unreal 对照），说明 AI 怎样实施和验证，并给可用示例或清单。来源按能否支撑选择来取，不凑代表作数量。
