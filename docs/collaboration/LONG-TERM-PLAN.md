# 运行手册

> 2026-10-22 重写（用户批准，Claude 起草）。方向和原则见 [AGENTS 方向锚点](../../AGENTS.md)，本手册是**唯一的执行规则**；操作步骤（Git 发布、恢复、本地中转）见[运行细则](operations.md)。旧版手册（战役、写作规则 1–7、质量清单、工作线 M1–M6／GA–GF 等）已并入本手册或删除，见 Git 历史。状态见 [TASKS](TASKS.md)。

## 1. 核心思想

**找到真实技术人员正在用的、当前最好的 AI coding 做法、工具和开源项目，亲手试过，提炼成读者马上能用的东西；再留一点空间给有新意的尝试。**

前几天走偏的三种方式，以后一律当作跑偏信号：
- **只求“可证明正确”**：挑容易核实的窄题、多引官方文档、堆限定语，结果可靠但没人觉得有用；
- **刷指标**：单元数、L3、差距分、登记数一个个被刷满，读者价值没涨；
- **只读不用**：没装过、没跑过就评价工具。

## 2. 每次交付前问五个问题

独立审查和 dot 互审也按这五问审。

1. **前沿**：官方、社区、开源三方都看了吗？是不是近 3–6 个月、当前一代的做法（游戏看近两年）？决定性来源是不是做事的人写的原文，而不是官方介绍或转述？
2. **增量**：读者原本不知道、或会做错的是什么？这次告诉了他什么？说不出来就不交付。
3. **实证**：装过、跑过、试过吗？没有就写“未试用”。
4. **诚实**：事实有证据等级和日期；单个案例只证明它自己；效果没测过不写成已验证。
5. **好懂**：结论放第一句；一条结论最多一句关键局限；能用图表说清的用图表。

## 3. 怎么探索

**前沿比较项目的最低覆盖**（每次找的时候，要找到当时能找到的最前沿；按 [25 探索提示词](prompts/2026-10-21-exploration-self-use.md)执行。精确 API 查询和已有研究续接按缺口取资料，不重复全渠道回扫）：
- **官方**：Anthropic、OpenAI 等的文档、工程文章、changelog 与发布说明；
- **做事的人**：前沿团队和头部实践者近 3–6 个月的原文，按[来源名册](../research/2026-10-15-exploration-evidence.md#p46按团队追踪来源与漏检校准)扫，不只搜关键词；近期论文读到方法和结果；
- **社区**：至少两个讨论渠道，其中一个中文（HN、Reddit、GitHub issue／discussion、linux.do、V2EX、掘金等），读原帖和高赞评论，正反都看；X 抓不到就看用户[收件箱](inbox.md)和转引的原帖；
- **开源**：GitHub 上同题的热门和新晋项目，看 star 增长、近期提交和 issue 里的真实问题；
- 交付里写一行**探索回执**：查了哪些渠道、截止日期、哪些读不到。

**从社区和开源项目提炼精华，不是列链接。** 每个值得看的项目或讨论回答五件事：解决什么问题；关键机制是什么（读代码和设计，不只看 README）；谁在用、反馈如何（issue、讨论、复盘，正反都有）；本仓试用结果；可以借用的精华是什么、适合谁、坑在哪。

**收件箱**：用户在 X、linux.do 等处看到的链接贴进 [inbox.md](inbox.md)，dot-A 24 小时内处理。用户贴来、本仓此前没发现的，记一次漏检，并把它的原始渠道补进来源名册。

## 4. 做什么

**产能分配**（按周粗算）：
- 约 70% **核心**：A推进前沿强方法的选择、组合和真实模型采用，M6持续改善发现与转化；B并行深化完整模块与高质量游戏制作。既有计分板和实验辅助定位，不决定工作粒度；
- 约 20% **前沿发现**：追当前高手如何做出更好成品、缩短完整交付周期，比较重要替代并试用；短试可分享发现，有价值的路线继续采用，不以固定试用时长切碎任务；
- 约 10% **新意实验**：有创意的组合、原型、自制 Skill、AI coding 与游戏结合的新玩法、本仓自己的观点；标 🧪 实验或“观点”，和推荐默认分开写，失败也照实记。

**分工**：dot-A 做 AI coding（核心页、M6、前沿发现、验证）；dot-B 做游戏。可以互助，但 AI coding 和 M6 的核心目标完成前，dot-A 不转去做游戏。

**持续推进与自主选题**：在执行平台可运行且授权有效时，完成一项接下一项，不按每天数量限速。自主选题从每次选题开始，不等队列清空：先读最新要求、在制分支和 TASKS，选择最重要的可执行缺口。A说明要增强哪项Agent能力、真实任务检验什么；B说明要改善哪段AI制作链或哪个客户端／gameplay问题。以完整能力、模块或可玩的品质改进组织工作，局部查证服务该结果。小改可以及时交付，但不能长期以补一句边界代替完整推进；不另建选题表。

优先接完有价值的在制成果，再从§9近期方向、核心页未决问题、收件箱与社区／开源发现续题；发现更重要的问题可调整顺序并简述原因。每次交付或受阻时顺手更新 TASKS 的下一步：有现成高价值候选就选，不为凑备用数量制造题目。验收或权限受限只停依赖环节；先完成可独立实施的部分，交可运行版本、素材或接入产物及准确待验项，再由已有授权且具备能力的执行端接收，新增权限才询问。明确拒绝不得换路绕过；同一窄题收益已低就收口。候选用完先做一次有边界的探索，仍无值得做的题则如实说明缺口，不用重复检查填时间。

**本地执行扩产**：A／B主动将明确且可独立接收的调查、实现、测试、资源处理与初稿交给已配置的DSH／Claude Code＋DeepSeek／ZCode，dot负责方向和整合。普通协作不套P79实验限制、不逐任务重测通道。跨账号时沿共享Git与独立本地协作会话交接；B任务不由A研究主任务代管，实际接收另核；见[运行细则§2.2](operations.md#22-本地模型协作普通生产与专项验证)。

**执行状态**：仓库规则表达工作方向，Git更新不保证唤醒Dot。运行、排队、等待输入和停止以平台实际状态为准；只在能读取时确认已有续跑安排与实际恢复记录，取不到写未知。沿现有安排续接，不重复创建调度；具体通知边界见[运行细则](operations.md#21-跨执行者的发现与交接)。

**项目**：围绕读者问题交出可用结果；0.5–3 天只作估时，范围由内容和验证需要决定，写进 [TASKS 项目板](TASKS.md#项目板)并带验收；执行者可以自己开项目，写明增量是什么。编号取项目板与归档中最大编号加一，推送前与最新 `main` 核对，撞号时后到者改号。同一项目的小步改动攒成一次交付再审。

**计分标记**：核心页“当前最高水平”一节写成短表（主要选择 → 领先替代 → 决定），节内放 `<!-- frontier: status=已比较|仅候选|未知 gap=0-3 gen=<代际> checked=<日期> -->`。只有做完同题比较才能登记或调小差距；自评最低到 1，0 只能由独立审计给出；回应过某次审计的，在标记里加 `audit=<审计日期>`。计分板只是辅助指标。

## 5. 写成什么样

**三层内容**（见锚点）：值得一试（[13 前沿雷达](../13-frontier-radar.md)页首的表，放不下就拆新页）；当前最佳做法（各决策页）；直接可用（`templates/` 的模板、Skill 和配置）。

**可视化**（读者没耐心读长文，图是主要呈现方式之一）。按这个顺序选：
1. **真实截图**：上手试用时截下界面、终端输出或产物，这是最有说服力的图，“值得一试”里试过的项目尽量每项一张；
2. **代码生成的图**：结构、流程、决策树和对比用 Mermaid 或 SVG；数据用脚本画图。只把文字排成表格的 SVG 不算可视化；
3. **生图模型**：只在确有助理解具体知识且有授权时配图，不为简报或凑画面制造工作。知识图解默认二次元／ACG 表达，先画真实对象、因果和对照，趣味来自发现与转折；保留解释为什么、怎么做所需的文字，不用栏目图标或装饰背景代替知识。生图负责画面，**准确的文字和数字用代码叠加**（SVG 或图片处理脚本），不让模型自己写字；生成后自己看一遍成品，并检查读者能否据图复述具体机制或下一步动作；字准但没有知识仍须返工；生成性质在邻近说明中交代，不在画面里追加水印式提示。

知识漫画先写问题→动作→结果的分镜，再选 ACG 画风；人物要参与因果，不站在说明栏旁；每格补足实际问题、动作、观察或下一步决定，不靠少字掩盖知识不足。标题、对白与术语分别设计字形和位置，准确排字不等于裸贴文字。复用[短提示词](prompts/acg-knowledge-comic.md)，只保留帮助读者理解的标注。

图片放 `docs/img/`，单张尽量不超过 300 KB（优先 WebP），附替代文字。

**后台减负**：
- 研究记录只为支撑正文而写，开头三行写结论；
- 实验脚本和夹具只在真正运行时写；
- 验证细节（树 SHA、检查命令、回执）写进提交说明，不写进正文和 TASKS；
- TASKS 保持 10 KB 以内，只放分工、项目板和需要用户决定的事，其余移入归档。

**不做**：没有试用、没有判断的链接堆和新闻转述；为指标而做的登记和打磨；读者用不上的细节（例如 IDE 子页的权限差异）；与 AI coding 无关的通用工程内容；连串的“不以……代替……”式否定句。

## 6. 节奏与反馈

**简报暂停（2026-10-24 用户最新要求）**：停止每日／定时简报、digest更新及配图整理，不为包装成果投入工作。继续AI coding与M6主线，重要发现直接回流主专题、可用模板或清晰采用建议；只在有重要实质成果、需要决定或阻塞时简短通知。不据此暂停持续维护、前沿收件箱或互审。

**互审与方向纠偏**：沿每日互审检查对方的重要新增，既看第2节五问，也看最近一组交付是否持续增强主线能力、成果是否进入读者入口、下一题是否只是惯性扩题。各自发现偏题立即调整，不等第二天。通用修复连做、孤立实验增多或主专题长期没变时，查具体价值，不以文件比例、篇数或固定天数裁决。

**每周独立审计**：由未参与本周写作的新上下文审方向和关键增量，抽读必要正文与未合分支，并对照外部强实践；不重复已审内容。审计者同时检查指导本身是否导致偏题，交具体纠正建议；执行者在本轮直接同步 TASKS、手册可编辑节和相关读者入口，不停在报告。范围涉及锚点或第1–2节时才提请用户。只有重新判断过的页面才更新既有基线，不按抽样数量或升分推进；历史校准提示词只作参考，不沿用其中固定日期、报告篇幅和仅报告不整改的旧交付限制。

沉淀回看、规则修订和外部漏检调查并入上述选题与审计：有新证据就修过时结论、提取有用发现、合并重复；替换导致问题的旧规则，不另交每日自检或每周三行报告。既有外部十件事每两周继续，用于发现漏项，不要求十项都立题。已有审计安排正常运行时无需再建一套；用户最新要求优先。

## 7. 交付流程

1. 在自己的分支完成一个可接收结果，整合最新 `main` 后核实际交付差量。一次全新上下文独立审查覆盖内容、证据和必要集成；已有可信独审可由接收者复用，不再例行叠加根审、第二轮同题审查。修订仅复核受影响部分；冲突、共享契约变化或已发现缺陷才扩大范围。
2. 按下表选检查，在最后一次相关修改后通过即可。源码、依赖、运行配置、检查器或所验行为变了，重验受影响路径；仅提交SHA变化、无关文档合入或移交执行者，不使结果失效。明确失败必须修复，不能用缩小范围掩盖失败。

| 改动范围 | 适用检查 |
|---|---|
| 纯正文、审计、任务／指导文档 | `python3 scripts/check_repo.py`、来源与关键结论核查、实际读者入口；不跑无关Hook／实验套件 |
| 某个实验、模板或产品代码 | 上述文档检查及该模块相关测试／类型／构建检查，真实消费者和直接失败路径；页面改动回真实浏览器，音频改动实际试听 |
| 共享检查器、Hook基础设施、跨套件公共依赖或影响范围无法确定 | `python3 scripts/check_offline.py` 完整入口，加该变化需要的真实行为验证；完整入口不是产品验收的替代 |

3. 每次发布保留公开文件扫描 `python3 scripts/check_public.py`、提交身份扫描 `python3 scripts/check_public.py --commits origin/main..HEAD`，暂存本次新增文件后跑 `git diff --cached --check`，人工审差量。已通过的同一受检版本可复用；提交扫描在提交后运行。简单合并只补整合差量与上述发布检查，不重跑所有未受影响实验。CI配置保持原样，准确报告实际运行范围。
4. `git push origin HEAD:main` 只允许快进，不开PR、不强推；按[运行细则](operations.md#21-跨执行者的发现与交接)核发布结果。B无法写main时由A接收；A复用B的有效审查／检查，只核新增整合影响。
5. 真实搭建／运行单次最多2小时。受阻记录具体入口、原因、未完成结果和恢复条件到既有TASKS，转做独立项；下一次选题先核条件是否恢复，不能用新题默默覆盖旧验收。已有明确拒绝保持停止，不换入口绕过。
6. 本地模型普通生产与专项验证沿[运行细则§2.2](operations.md#22-本地薄中转验证优化的真实效果已获启用授权)，不另造验证体系。检查摘要写进现有提交／研究记录，不加证明账本。

## 8. 边界

授权范围见锚点“自主与边界”和 `AGENTS.md` 的“公开仓库安全”。未被授权覆盖的事（付费、大模型下载、运行引擎、新建目录）写进 TASKS“需要用户决定”，立刻转做其他项；已经问过的不重复问。

## 9. 长期方向与当前承接

> 持续职责，不是做完即停的清单。当前承诺和阻塞在TASKS，长期方向指导自主选题；高质量包括创造更强能力与更好成品，高效率看走到可用结果的投入，前沿看相对强替代的优势，不以材料新鲜或边界说明多代替。

**dot-A：前沿强方法的选择、组合与真实采用**

- 面向完整功能交付、已有项目连续修改、复杂诊断、开发周转等真实目标，主动找当前强实践，比较原生基线与有竞争力的替代，给明确的条件推荐和可用起点。知识、工具、反馈与并行怎样组合，以任务需要决定；资料充分即可给选择，不等全行业最优证明，也不强制包装成新框架。
- **真实模型联动是核心工作的一部分。** 让实际可用的编码Agent读取知识、调用工具、实施和二改，由实际消费者检查结果；核使用的模型／客户端、关键介入与结果。工具接口测试和他人案例可以支撑选择，不能长期替代本仓采用。沿现有授权入口推进，原生当前Agent真实实施也算采用但不是独立效果对照；需要调用对照组时用已配置通道，失败保留状态，不能让P79或单个中转故障挡住其他已授权采用。实际步骤见[运行细则§2.2](operations.md#22-本地薄中转验证优化的真实效果已获启用授权)。
- 有关键选择值得比较时做有针对性的原生／候选对照；普通知识更新不强配模型调用。说明具体提升、返工与代价，取不到的消耗不编造。M6保持主动发现强方案，不能变成只补故障和安全边界；新工具值得试，已有有用能力也要持续进入实际任务。
- 当前复用已交付诊断、反馈和分支接续能力，Posts／P24限定接收不重验；QMD等窄试用按已有结论收口，欠项和自然需求按TASKS处理。不再把通用修库、工具小试或外部案例研究任一种做成惯性系列。

**dot-B：完整模块深化与高质量游戏制作并行**

- 主线是游戏AI全链路与客户端／gameplay核心知识。按完整开发问题深化：体验与质量目标、核心机制、强参照与默认选择、实现／接入起点、关联模块和AI实施方法。复用分散材料、补决定性缺口、整合进正文；不要连续只补小段边界。独立模块研究可并行，涉及共享状态与实现的工作明确归属再集成；不要求每个知识模块先在一款游戏里实现。
- 作品制作同步推进，用玩法、操控、画面、视听、内容节奏和性能的整体品质选择下一步。Star-Rush是现有重要载体；沿已具备的完整玩法做精，组合代码、AI生成、程序化与许可清楚的现成资源，迭代到可体验、可继续修改的结果。研究从作品获得问题，作品使用研究成果；两者都不能成为延后另一条工作的理由。
- **验收限制不扩大成制作禁令。** 当前声音听验／生成、WebGL或精细输入能力不足时，先核已有授权的可用接收端；能独立完成的规格、候选、源资产、代码、加载和构建先做到可交接版本。准确留下未试听／未目检等欠项，不宣称品质已通过，也不因未验就合入要求已验的版本。若感知结果直接决定实现，就停该依赖选择、推进其他品质工作；不盲调物理或美术。需要人或外部权限时提出具体产物与所缺动作，不只交“缺工具”的状态。
- **案例可扩展，赛车不是永久题材边界。** 后续可借鉴英雄联盟式MOBA的技能／战斗／成长，或CS式FPS的枪感／命中／回合机制，选择可完成的原创垂直切片，使用原创或许可清楚的代码和资产。先判断已有作品／工程能否验证目标；新案例应补现有载体覆盖不了的重要问题，并有实现、集成和接收能力。当前不自动启动两款完整复刻或新仓库；具体开题、引擎、资源与权限按届时用户范围和已有授权处理，不以多开项目代替完成作品，也不要求赛车全部完成才允许研究其他类型。
