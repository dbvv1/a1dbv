# 03 · 上下文工程

> 核实 2026-10-24（UTC+8）。**一句话：先区分需求、环境、模型能力、上下文和验证器问题；上下文应提供必要信息，而非尽可能堆满。** 依据范围见[此前证据范围](research/2026-10-13-context-tool-choice.md#p73定点原文与摘要委派)、[旧页首范围](research/2026-10-13-context-study-reassessment.md#历史页首核实范围)；本仓实试未测模型收益。

## 30 秒选择：开始一个具体修改任务

**✅〔跨代保留〕先补齐这次修改的必要上下文**：写清目标与验收，让 Agent 读取项目指令、定位相关实现与可复用示例；其余资料按需取回。人核目标和检查覆盖，不替 Agent 预先整理全仓材料。依据见 §2–3。

**✅〔2026-10 修订〕升级模型时，先审旧规则，不整套照搬。** 把“每次编辑前读全部设计文档”改成按任务指向相关文档；对 Astra 这类当前强模型，先撤掉重复教它如何探索、反复催测试的提示，保留项目特有命令、不可猜的契约和完成标准。删后漏了约束、相关测试或停在半成品，就补回具体缺口；混合模型团队不按 Astra 的能力统一删规则。

**〔跨代保留；命令按宿主版本〕同一任务仍需前文、只是历史占空间时，才选压缩**，保留目标、约束、已验证结论与未完成检查。Claude Code 可先用 `/context` 看来源，再按需 `/compact`；Codex 单独见 [§3](#3-会话层面的上下文管理)，不照搬 Claude 操作。

**⛔〔跨代保留〕不为“最小上下文”删必要信息，也不先堆满、清空或加检索框架。** 缺权威源或缓存已旧，先补信息并核当前状态；自动压缩正常时，无需按时长手动压缩，丢了关键约束就取回原始依据。依据见 §2.3–4。

**✅〔2026-10 补充〕已知修改位置，先定点读原文；大批量事实定位才试摘要委派。** 摘要帮 Agent 缩小候选，不能独自承担并发约束判断或编辑依据；先确认委派成功且答案可回查，再比较节省。强制摘要路由暂不默认安装，见 [§2.6](#26-大文件先定点原文还是摘要委派)。

**依据**：[一手] Claude Code／Codex 命令契约、近期团队实践；[经验] 采用判断、条件默认；核实 2026-10-24。

## 当前最高水平与比较范围

**当前跨任务最优配置未知；可行默认是先分清问题、按需取回必要上下文，不把他人的删减比例当通用目标。** Cursor 的 Katz、O’Keefe、Yee（9-23）用生产 A/B 比较提示删减、按需工具、缓存与委派调整，组合自报 token 成本降 7%、质量不降；同时撤掉强烈鼓励探索委派的提示，保留高频读、搜、改和 shell 工具的静态入口。它比较的是可控制的产品 harness，不是证明用户删掉任意规则都省 7%；这是团队自报，缺完整样本与质量量表。

OpenAI 的 Eric Provencher（9-11）对 Astra 同样把全仓预读改为按任务路由文档，但保留明确完成状态，并提醒适合 Sol／Luna 的指导可能过度约束 Astra。因此本页**确认必要上下文与原生检索起点，修正旧提示的继承方式**：Agent 自主定位和检查，人保留无法从代码推知的约束；不把所有模型改成同一份“极简”配置。

**近期论文要按实验代际解读。** §2.2 的 AGENTS.md v3 虽更新于 9 月，实验仍是 Sonnet 4.5、GPT-5.2 等；附录 B 在人为移除文档后反而看到生成上下文有益。这限制“少给一定更好”，不能作为当前模型配置的胜负证明。主流参照是规则文件、搜索与摘要续接（采用率未知），本页推荐属于比较前沿后的可行默认；最优上下文量与专用引用图净收益仍未知。详见[代际比较](research/2026-10-13-context-tool-choice.md#p52上下文代际复核)。

**大文件委派仍是候选优化，不是当前代际胜出方案。** 下文把近期原生按需读取与 Spotify 的摘要路由放在同一读者任务下比较；后者使用旧工作模型，公开复测还暴露宿主协议和路径解析维护成本。最优总投入未知，现有 gap1 保持条件范围，详见[固定证据链](research/2026-10-13-context-tool-choice.md#p73定点原文与摘要委派)。

**依据**：[一手] Cursor 团队自报（[博文](https://cursor.com/blog/improved-token-efficiency)）、OpenAI 厂商实践（[博文](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)）；[研究] AGENTS.md v3 与代际比较、Spotify 公开实践及公开复测；核实 2026-10-21。

## 1. 原理与使用边界

**先按任务价值分配上下文，不追求填满，也不为“最小”删必要信息。** Anthropic《Effective context engineering》（2025-09）给出旧代设计参照；按需取回等思路经近期做法确认，但不是所有模型与宿主的统一操作规范；具体动作见 §3。

| 概念 | 含义 | 实践 |
|---|---|---|
| **Context rot** | 长输入可能降低相关信息的利用效果，程度依模型、任务与内容而变 | 上下文是有限资源，要“花得值” |
| **注意力预算** | 更多内容会占用上下文；注意力计算的规模不能直接推出任务质量 | 每加一段内容，都要问它值不值 |
| **系统提示的“高度”** | 太具体（if-else 式）会脆弱，太抽象又没有指导性 | 给启发式规则和原因，不要给死规则 |
| **工具** | 自包含、容错、用途清晰；工具集要精简 | 见 [04 MCP](04-mcp.md#4-写好给-agent-用的工具) |
| **示例** | 几个多样、典型的示例胜过一长串规则 | 给 Agent 指一个“照着这个写”的现成文件 |
| **即时检索** | 只保存轻量的标识（路径、查询、链接），需要时再加载 | `@file` 精确引用；LSP 定位符号后读相关实现，字符串／配置另做文本搜索 |
| **压缩** | 同任务腾出空间时总结历史，但可能丢失细节 | `/compact 保留XX`；在 CLAUDE.md 里写明压缩时要保留什么 |
| **结构化笔记** | 把进度和决策写到上下文之外的文件 | `PROGRESS.md`、feature 清单（JSON） |
| **子 Agent** | 隔离专项工作的过程输出；是否继承历史取决于宿主与启动方式 | 有独立调查才拆，返回结论、依据和未解决项；不为节省上下文强制每次探索都委派 |

**依据**：[一手] Anthropic《Effective context engineering》（[原文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）；[经验] 采用边界；核实 2026-10-24。

### 2.1 各工具的加载规则（[一手]）

**✅ 共享内容可以只维护一份，但是否只留 `AGENTS.md`，要按实际加载入口决定。** Claude Code 的默认发现会被项目路径中的 `CLAUDE.local.md` 等文件抑制；需要兼容这些会话时，保留同目录 `CLAUDE.md` 的显式 `@AGENTS.md` 导入，比要求每位使用者改个人设置更易随仓库交付。没有这些条件、且已确认原生加载时，可只保留 `AGENTS.md`。

| 工具 | 文件 | 会改变选择的加载条件 |
|---|---|---|
| Claude Code | `CLAUDE.md`、`AGENTS.md`、`.claude/rules/*.md` | 原生 AGENTS 入口从 v2.1.277 起提供，部分 provider／禁遥测会话到 v2.1.281 才支持。默认检查当前目录及祖先：有 `CLAUDE.md`、`.claude/CLAUDE.md` 或 `CLAUDE.local.md` 就不走 AGENTS 回退；用户级 `~/.claude/CLAUDE.md` 不触发这个抑制。子目录按需发现，不能假定所有指令已在开场加载 |
| Codex | `AGENTS.md`、`AGENTS.override.md` | 每次运行启动时建立指令链；全局先选首个非空 override／AGENTS，项目从根到当前目录逐层选择 override、AGENTS、备用文件名，每层最多一份；项目文档默认总预算 32 KiB。单包任务可用 `--cd` 在目标包启动并带入根到 cwd 链；根会话跨兄弟包仍缺自动发现。不能把 Claude 的 `@` 导入或子目录按需发现直接移植过来。codex-cli 0.154.0 fixture 只核对上下文组装（根启动根 1／包 0，包目录启动根 1／包 1），不证明模型遵守 |
| Gemini CLI | `GEMINI.md`（可配置文件名） | 未重核，按目标客户端文档确认 |
| OpenCode V2 | `AGENTS.md`（workspace 内嵌套） | 读文件或列目录时发现 workspace 内嵌套 AGENTS，nearest-first、去重；compaction／revert 可重载，已加载规则文件被改后不自动重载。只核官方文档契约，未实跑采用，不证明模型效果 |
| Cursor / Copilot 等 | 各自规则格式或 AGENTS 入口 | 文件同名不证明发现、合并和刷新规则相同，未重核 |

**✅ 已有 AGENTS 跨包需求且客户端可选时，优先采用现成的动态发现，不默认自研 Codex。** Claude Code 的既有原生规则仍保留；OpenCode V2 在读取文件／列目录时发现 workspace 内嵌套 AGENTS，是现成候选；单包任务沿用 Codex 原生 `--cd` 链。本仓当前没有真实跨包采用成果，不能把文档／源码契约写成已采用或模型已遵守。

- **有抑制项时还想统一入口**：除仓库内显式导入，也可在支持的用户／托管设置中选 `claude-md-and-agents-md`；不能把该选项写进项目 settings 就当全队生效。共同加载是拼接上下文，不是权限规则的确定性覆盖。
- **跨仓库时**：`--add-dir` 只增加可访问目录，不默认加载其指令；额外目录加载开关覆盖 CLAUDE 文件与 rules，不覆盖原生 AGENTS 发现。确实需要共享约定时，选择相应 CLAUDE 入口或显式导入，并核实外部导入批准状态，不能只看目录可读。
- **验证加载时**：新版本用 `/memory` 核对原生 AGENTS 路径，导入入口也核对 `/context`；`InstructionsLoaded` 不报告原生 AGENTS，但会报告 CLAUDE 导入（`include`）。没有该事件不能证明 AGENTS 没读，事件存在也不证明模型遵守了规则。

**关键局限**：以上是官方加载契约、发布记录与一次 codex-cli fixture 的上下文组装核对，不是模型效果实测；详细优先级、版本差异及反例见[共享指令加载证据](research/2026-10-13-context-tool-choice.md#共享指令发现导入与加载证据)。需要多工具生成配置时可评估 [rulesync](https://github.com/dyoshikawa/rulesync)，但生成文件仍须通过目标客户端的加载检查。

### 2.2 指令文件到底有没有用？（研究证据）

**指令文件不是越多越好；先保留可验证改变行为的项目特有信息，再比较有无配置的效果。**

| 研究 | 主要依据与选择边界 |
|---|---|
| **Evaluating AGENTS.md v3**（2026-09） | Claude Code（Sonnet 4.5）、Codex（GPT-5.2／5.1 mini）及 Qwen Code 的 Python issue 修复中，生成文件增加成本，成功率未显著改善；手写文件平均收益不显著，但显著优于生成文件，除 Claude Code 外均有提升，成本也增加。指令改变了测试和探索行为；仓库概览未显示可靠收益，长度影响也不显著。不能外推到其他语言和当前模型。 |
| **Do Context Files Help Coding Agents?**（2026-07） | Sonnet 4.6／GPT-5.5、三个 Python 仓库的小样本未检测出正确率收益；语料与注入渠道不同，描述性等价区间不证明普遍无效。详见[全文及公开数据复核](research/2026-10-13-context-study-reassessment.md#context-files失败解释与分析参数)。 |
| **On the Impact of AGENTS.md Files on Efficiency v2**（2026-03） | GPT-5.2-Codex 在十仓小 PR 任务中，运行时间和输出 token 中位数下降；人工合理性检查不能证明同等正确性下提效。详见[有效样本、配对版本与复算](research/2026-10-13-context-study-reassessment.md#agents-效率耗时与正确性的边界)。 |
| **Configuration Smells in AGENTS.md Files**（2026-07） | 灰色文献与 100 个热门仓库归纳六种配置坏味道，见 §2.3；出现率不是删减后的效果证据。 |
| **A Few Pages of Markdown v2**（2026-09） | 企业仓库用于开发 RAMP；开源仓库的 agent-first 分层中，有配置组的认知复杂度增幅较小，但配置按观察终点分组，多数后于或同期于 Agent 采用，不能推出预先写文件的因果收益。agent-first 仅指未检出 AI IDE 配置痕迹。详见[分组、换算与维护边界](research/2026-10-13-context-study-reassessment.md#a-few-pages分组时间与维护)。 |
| **Agent READMEs v2**（2026-08） | 文件历史与内容抽样说明指令会被维护，但相邻提交间隔不是全部文件的维护周期；安全、性能主题出现率不衡量效果，也不能判定项目缺少其他治理。详见[维护与内容口径](research/2026-10-13-context-study-reassessment.md#agent-readmes维护与内容口径)。 |

**综合结论**：
1. 评估**效率、行为约束与长期质量**，同时比较正确性、返工和成本。已有正面线索及相关性证据，不足以承诺等质量提效，也不能排除其他任务的收益。
2. **把 `/init` 当草稿，不原样提交**：保留可验证改变行为的项目特有信息，再做有无配置的对照；生成文件增加成本的结论限于上述 Python、模型和任务样本。
3. **不自动复制完整概览、目录树和逐文件说明**；有任务价值、难以发现的信息仍应保留，研究并未否定所有架构地图。
4. 小众语言或工具链（如 Unity 编辑器和序列化约定）更值得补充项目知识，因为模型先验可能较少。
5. **安全和性能按任务需要补充**：写具体边界与验证方式，不按类别凑齐，也不以一句“注意安全／性能”代替已有文档或 CI。
6. **🧪 从短配置试用，按事实变化维护**：命令、权限、架构变化或出现失败反例时修订并验证；不以文件数量或编辑频率作目标，少修改也不证明无需维护。

**本仓历史实验**：同一 bug 任务各组均成功；短指令改善了回归测试与项目命令使用，长指令也改变行为但成本更高。样本很小、原始产物待补齐，未复现；无独立消融，不能把收益只归给某段指令。统计与设置见 [19 §4](19-experiments.md#4-e3指令文件长短)。

**依据**：[研究：原文] [Evaluating AGENTS.md v3](https://arxiv.org/html/2602.11988v3)、[Configuration Smells in AGENTS.md Files](https://arxiv.org/abs/2606.15828)、表内各研究的复查记录与公开数据；[经验：历史实测] 本仓历史实验；[经验] 建议；核实 2026-10-24。

### 2.3 写什么、不写什么（官方最佳实践 [一手]）

**只写 Agent 难以自行发现、且会改变定位或执行选择的项目信息。**

| ✅ 写 | ❌ 不写 |
|---|---|
| Agent 难以确定的项目命令（构建、测试、单测怎么跑） | 不改变定位或执行选择的重复代码说明 |
| 与默认习惯不同的代码风格 | 语言的标准约定 |
| 测试方式与首选的测试运行器 | 详细 API 文档（给链接） |
| 仓库礼仪（分支命名、PR 约定） | 易过期的配置值副本（给当前权威来源） |
| 项目特有的架构决策 | 长篇解释、教程 |
| 开发环境的坑（必需的环境变量等） | 文件逐个说明 |
| 常见陷阱、反直觉的行为 | “写干净的代码”这类空话 |

- **检验标准**：保留能改善定位、行为或质量目标的信息，删除重复、失效内容；功能不报错仍可补领域依据，增量条件见 [05](05-skills-and-plugins.md)。
- **规则被忽略**：先按 §2.1 查加载与冲突，再查表述、相关性和行为；不能直接归因于长度，也不靠加粗代替执行边界。
- **何时加一行**：发现可定位错误或改变当前选择的领域依据时；不设错误次数门槛，也不把所有资料常驻。
- 可机械检查的规则可以接入 Hook，但要验证匹配、错误和替代路径；硬权限由沙箱等运行时边界执行，见 [06](06-hooks-and-guardrails.md)。
- 用 `/doctor prompt-audit` 排查旧提示写法；过度强调、全大写警告可能让较强的指令遵循反应过度。

**✅ 清理陈旧指令时，保留默认行为与生效条件，不把“代码如此”直接改写成“需求应当如此”。** 让 Agent 先区分已证实的旧路径／状态与尚未解决的规格冲突；前者可在授权范围内继续清理，后者先标出双方依据，由负责人确认哪条契约有效，再做语义改写。压成表格后，人仍要核对“可解锁”是否被写成“默认开启”、条件和例外是否丢失。doc-cleanup 的作者报告与实际配方修订提供了这一反例，详见[指令清理核查](research/2026-10-12-community-source-records.md#指令清理保留条件与契约意图)。**局限：这是历史自报与公开修订，未证明安装清理 Skill 提高正确率；路径检查通过也不证明语义保留。**

推荐延伸阅读：HumanLayer 的《Writing a good CLAUDE.md》，讨论了“指令预算”和渐进式披露。

**依据**：[一手] Claude Code 官方最佳实践与 `/doctor prompt-audit` 契约；[社区／一手] doc-cleanup 作者报告与公开修订；[经验] 建议；延伸阅读 [Writing a good CLAUDE.md（HumanLayer）](https://www.humanlayer.dev/blog/writing-a-good-claude-md)；核实 2026-10-24。

#### 六种“配置坏味道”（arXiv 2606.15828 [研究：原文]）

**按任务价值处理六种坏味道，出现率只作线索。**

| 坏味道 | 表现 | 怎么改 |
|---|---|---|
| **Lint 泄漏**（62%） | 命名、格式、import 顺序、行宽这类 linter 和 formatter 能检查的规则 | 先确认现有检查的触发与覆盖，再删除重复规则；保留运行入口、必要原因和例外说明 |
| **上下文膨胀**（42%） | 文件过长、塞满低优先级细节 | 行数建议和缩短个案只作线索；按任务价值删除重复／失效内容，必要资料按需读，不设通用门槛 |
| **Skill 泄漏**（35%） | 只在特定场景用的流程写进了常驻指令 | 先用按需参考资料；确需复用配方时再按 [05](05-skills-and-plugins.md) 选择窄 Skill |
| **盲引用** | 只写“见 docs/xxx.md”，不说明用途 | 写清楚**为什么、什么时候**去读，否则“Claude 经常会忽略” |
| **初始化化石** | `/init` 生成后从没改过 | 事实改变、评审发现缺失约束或出现可定位失败时修订；不以错误次数定门槛 |
| **指令冲突** | 前后矛盾 | 定期通读，用 `/doctor prompt-audit` 或社区 linter（agnix、ctxlint）检查 |

**依据**：[研究：原文] [arXiv 2606.15828](https://arxiv.org/abs/2606.15828)；核实 2026-10-24。

### 2.4 大仓库 / Monorepo（Claude Code 配置及检索选择）

**按任务选择加载范围与检索方式：能缩小到当前模块就缩小，已知符号用语义检索，未知入口再用 map 或文本搜索。**

| 需求 | 做法 |
|---|---|
| 只加载当前模块的约定 | 子目录 CLAUDE.md，或 `.claude/rules/` 加 `paths:` |
| 排除无关包的 CLAUDE.md | `claudeMdExcludes` |
| 限制受覆盖入口读取构建产物、生成代码、第三方依赖 | Claude Code 的 `Read(...)` deny 只覆盖内置文件工具及受支持命令；不能阻止任意子进程间接读取，完整路径隔离按 [10 的沙箱边界](10-security.md#3-防护原则)落实 |
| 符号定位 | 按所需语言和操作选可用 LSP；语义引用与文本搜索互补，仍需读相关实现 |
| worktree 太大 | `worktree.sparsePaths` 稀疏检出 |
| 跨仓库 | `--add-dir` / `additionalDirectories` |
| 规模化分发约定 | 做成内部插件市场里的插件 |

**✅ 按问题获取上下文，结果异常时先核对版本。** 不知入口可用 repo map 缩小候选；已知符号用能解析本项目的 LSP 查语义引用；字符串、配置与动态注册则搜索并追构造规则。Aider 的固定测试明确覆盖保存后仍复用旧 map、强刷才更新；clangd 对当前文件缓冲与跨文件头文件的默认读取来源不同。因此刚改过代码却零命中时，先确认读取的是 buffer、磁盘还是缓存，不能直接断言目标不存在。详见[固定机制与原帖](research/2026-10-13-context-tool-choice.md#源码检索map语义引用与当前状态)。

**局限**：map 排名不是精确调用关系，LSP 也不保证覆盖运行时动态关系或全部未保存文件；这些选择对模型正确率或费用的净影响未测。

**命中生成代码后，先找持久修改源。** 沿文件来源标记和构建规则回到源文件／模板，修改后按项目入口重生成并核对产物；运行文件可能正是生成物，不能据此认定它也是编辑源，也不宜为减少上下文一概排除读取。fullsend-ai 的风险标签功能曾只改入运行 bundle，后来回源修改，并由原评审者确认重生成一致。详见[固定补丁与复测范围](research/2026-10-13-context-tool-choice.md#生成代码运行产物与持久修改源)。**局限**：这支持追查生成关系，不证明新增语义索引或更多上下文有收益。

#### 资料检索：已知关键词先 `rg`，跨篇排序再试 QMD

**资料很多、只想先找到相关原文？** 已知关键词仍先用 `rg`；需要跨多篇 Markdown 排序并按行取回时，可选试 QMD 的纯词法 `search`。本仓 2.8.3 索引 207 份公开资料，用 `页面 批注` 返回了导出实验、实际改稿与主专题，随后按返回 docid 取回原文，分清“导出过批注”和“确实改过页面”。同题原生搜索也能找到，增量是排序与取回入口，不是语义理解或模型提效。详见[最短操作与范围](research/2026-10-22-frontier-trials.md#qmd纯词法检索先找到原文再判断证据)。

已安装对应版本后，先对授权的资料目录执行 `qmd collection add ./docs --name docs --mask '**/*.md'`，用 `qmd search '页面 批注' --json -n 5` 取候选，再复制返回的 docid 执行 `qmd get '#实际ID:起始行:行数'`。本次完整中文问句零命中，改为关键词才找到；没有使用向量或下载模型，别把 `search` 换成另一条混合检索命令而仍沿用本次范围。只有少量文件或已知路径就不必建索引。

文档修改后先检查集合是否配置了会执行额外命令的更新钩子，再运行 `qmd update`，并回当前源文件确认决定性内容。本仓一次真实改稿后，旧索引仍返回已停用的简报要求；更新后才返回新规则与 QMD 入口。可取回的旧原文不是当前指令。

**索引与所选快照一致，也不代表每段历史记录仍生效；按要回答的断言取原文，不整篇选新弃旧。** 将“补丁在哪里”“目前验过什么”“现在允许做什么”分开：固定补丁回到其版本与应用入口，验证状态回到对应版本的最新接收结果，执行边界回到当前任务及有效约定。每项保留路径、行号和版本；旧记录里的可用产物可以继续复用，已被替换的等待或限制不随产物一起继承。本仓在同一固定快照的 11 份完整文档中实际运行混合检索，旧任务过程排第一，现行路线排第二；接收时仍从旧任务取补丁校验值与应用入口、从路线取真实验证范围、从当前约定核执行边界，不能让相关性分数代替有效性判断。已知入口仍沿用原生搜索／纯词法，不据这次有界接收改成默认 CPU 混合检索。

**本次接收依据**：[本仓实试与原文消费](research/2026-10-22-frontier-trials.md#qmd-hybrid-intake)；核实 2026-10-25。

**依据**：[一手] Claude Code 权限契约、Aider 固定测试与 clangd 读取来源；[社区] fullsend-ai 补丁与复测（2026-10-18 UTC+8）；[经验] 选型判断；本仓 QMD 2.8.3 实试（未测模型收益）；核实 2026-10-24。

### 2.5 跨文件符号检索：何时补 Serena

**🧪 Agent 缺少可调用的符号检索／编辑入口时，再补 Serena；已有原生搜索、IDE／语言工具够用就沿用。** 搜索帮助找到实现，符号编辑让 Agent 指定“文件里的哪个方法”来替换或相邻插入；本仓 Python/Jedi 实试已跑通，最短用法见下。语言后端和版本决定能力，跨文件引用仍先对照已知调用点和目标配置。

**跨平台或构建配置修改，先补目标配置的核查。** 同一后端、同一构建下与 IDE 结果一致，仍可能共同漏掉其他配置。gopls 的引用查询只查所选文件的默认构建；这类任务先据目标配置核对相关文件清单，必要时补局部文本搜索，再在对应配置中核验调用点。详见[固定版本契约与真实需求](research/2026-10-13-context-tool-choice.md#跨配置修改原生引用也有构建范围)。**局限**：文本同名不证明语义身份；配置范围缺口本身不构成新增检索框架的理由。

**语义查询慢时，先定位再补详情。** 批量引用先取身份、位置及附近代码，再为选中目标请求正文、文档或签名。Serena 的 C++ 反馈促成减少附加请求及详情预算，参数须按版本选择；预算跳过与无文档可能同样缺省，查契约时应缩小目标。详见[反馈、修订与反证](research/2026-10-13-context-tool-choice.md#serena定位与附加详情的成本取舍)。**局限**：预算只限后续附加请求，不是调用硬时限，也未证明模型净收益。

**源码存在、语义查询为空时，先查项目导入。** 用文件／文本搜索确认目标，再核构建配置和依赖解析；索引过文件、旧 workspace 健康检查通过，不证明当前导入正确。Serena 的 Java 多模块报告涉及 Maven 配置与父 POM 解析；修正导入后先核已知定义和调用点，不靠扩大查询或无差别清缓存。详见[报告与修复](research/2026-10-13-context-tool-choice.md#serena语义检索为空时先核项目导入)。**局限**：修复进入 v1.6.0，但缺原任务修复后编辑验收；文本命中不证明语义引用完整。

**原生查询有、封装工具却漏掉时，先查过滤层。** 在相同文件状态和配置下对照调用点；原生 LSP 已找到时，核封装版本与过滤规则，临时沿用已核验的原生结果，不盲目扩上下文或重建索引。Serena 曾误过滤同名调用者，修复进入 v2.0.0。详见[Gleam 报告与回归机制](research/2026-10-13-context-tool-choice.md#serena原生引用存在但封装过滤漏掉)。**局限**：缺原任务修复后编辑验收，不能推广为所有后端正确。

**依据**：[一手] [Serena README](https://github.com/oraios/serena/blob/main/README.md) 与版本契约、gopls 引用查询范围（2026-10-17 UTC+8）；[社区] Serena C++ 反馈、Java 多模块报告、Gleam 回归；[本仓实试] Python/Jedi（2026-10-24）；[经验] 选择；核实 2026-10-24。

#### 用在真实修改：分清同名后端，再保原生路径

**先定位导入别名指向谁，再决定哪些适配器需要改。** cattrs 的五个后端都有 `make_converter`／`configure_converter`；本仓实际用 Jedi 的 goto 与文件内 references 定位声明，再追 msgspec 按 hook 身份选择原生编码的分支。详见[完整示范与导航入口](../experiments/cattrs-decimal/README.md)，它把 Decimal 支持做成可复制产物，没有安装或声称实测 Serena／LSP。

真正改变选择的是：ujson 会静默变浮点数，而 msgspec 已能原生编码精确字符串。前者补字符串编码，后者只补结构化；动态注册最终选了哪个 hook，另用实际后端及 `get_dumps_hook` 验收。静态定位不是运行时调用图，也不证明比 rg 更快。

**依据**：[本仓实试] cattrs-decimal 确定性示范（2026-10-23）；[一手] msgspec 源码；核实 2026-10-24。

#### 从查符号到按符号编辑

**实际用处是把编辑目标从旧位置换成文件＋符号路径。** 本仓的[Serena 2.1.0 实试](../experiments/serena-symbol-edit.md)显示：读取后在文件前方插行仍命中原方法，缺失／歧义名拒绝写入；正确替换与相邻插入通过解析、import 和窄行为检查。

**按任务选，不把所有改动都交给符号工具。** 找字符串／配置继续用搜索，改方法内一两行继续用局部文本补丁，重命名优先现有 IDE／语言工具；本次原生 Jedi rename 也已跑通。经常需要替换整方法或相邻新增定义、宿主又没有对应接口时，Serena 才值得接入。

**最短用法**：初始化后，`find_symbol` 指定文件和完整符号路径并读取正文 → `replace_symbol_body` 提交完整方法（相邻新增用 `insert_after_symbol`）→ 核对差量并跑相关测试；[固定参数与首次接入](../experiments/serena-symbol-edit.md#最短用法查当前方法--按符号改--验结果)可照着替换。

**关键限制：符号定位不是版本锁。** 外部修改过的同名方法会被旧准备正文覆盖；多人改同一方法先协调归属，写前重读也不构成原子保护。现有五场景足以支持上述窄采用结论，不证明真实业务修改更快或模型修复率更高。

历史适配问题仍按后端核对：Windows 初始化反例不能靠关闭防护解决；main 能力与 v1.7/v2 许可不可混用，本地索引返回的代码仍进入模型上下文。

**依据**：[本仓实试] Serena 2.1.0 Python/Jedi 符号编辑（2026-10-24）；[一手／社区] [Windows 初始化反例](https://github.com/oraios/serena/issues/2069)、[v1.7/v2 许可](https://github.com/oraios/serena/blob/main/LICENSE)、版本契约；[经验] 采用判断；核实 2026-10-24。

### 2.6 大文件：先定点原文还是摘要委派

**✅ 编辑、调试和约束判断，默认让承担判断或修改的 Agent 读定位后的原文及必要周边。** 大文件也按需要的范围读；摘要器只用于缩小候选，不承担编辑依据。先检索符号、调用点与契约，再决定所需范围；发现关联跨出片段就继续追原文。当前原生参照见页首。

| 同一任务中的需要 | 选择 | 接收与撤回 |
|---|---|---|
| 已知目标，需改代码或判断细微约束 | 原生搜索后定点原文 | 人核契约、相关调用点和实际修改检查；缺上下游时扩大相关范围 |
| 多个大文件，只想缩小事实候选 | 🧪 按需摘要委派，返回文件位置与可回查依据 | 承担判断或修改的 Agent 回读决定性原文；遗漏、往返重传或延迟抵消节省时退回原生 |
| 想用 Hook 强制所有大读取改道 | ⛔ 暂缓默认安装 shunt 或其未合修复分支 | 先核目标宿主兼容、放行语义及实际路径；已有有效接入不因本例一概拆除 |

Spotify 的公开实践报告摘要遗漏线程安全问题、编辑仍需读原文；示例工作模型是 Gemini 2.5 Flash。它为候选定位提供机制，不证明当前模型上摘要与原文等质。

**先验结果，再看节省数字。** 固定版本的评估脚本按 Shell 字符串长度估 token，委派失败后仍继续计算，未断言答案质量。接收时先核成功状态和关键答案，再把主／工作模型、失败重试及回读算入总投入；空回答不能算优化成功。

**节省上下文的路由器不应顺带替人批准操作。** 外部使用者对 shunt 的复测区分了“旧 block 仍有效”和“allow 格式报错”；修复分支改成显式批准后，又留下权限语义和路径解析问题。未命中成本路由条件时，保留宿主正常权限流；兼容性与回归未闭合就沿用原生读取。详见[版本、二改与采用状态](research/2026-10-13-context-tool-choice.md#p73定点原文与摘要委派)。

**程序卡与文档摘要分工，不互相替代。** 摘要帮定位规则，程序卡保存会改变执行顺序的前提与不变量，两者都要能回查当前依据。已知修改位置仍先读相关原文；跨步骤知识需复用才补卡，不为更短而删失败分支、并发约束或消费者。计划／评审放置详见[05 §2.5](05-skills-and-plugins.md#25-codexskill-应补什么又可能增加什么)。

Code2Skill §5.5 压缩的是代码 Skill，不是文档摘要，也不证明编辑可以只看摘要。若卡导致反复回读、漏约束或额外等待，恢复直接资料路径。

**依据**：[一手] Spotify 作者自报（[公开实践](https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90)）、[固定版本评估脚本](https://github.com/spotify/portal-ai-plugins/blob/cd5f40fb98a2c61c6041b228d11766a5318dc312/plugins/shunt/evals/run.sh)；[社区／一手] shunt 外部复测与版本状态；[研究／经验] [Code2Skill §5.5](https://arxiv.org/html/2609.05571v1#S5.S5)；[经验] 条件默认与接收判断；核实 2026-10-24。

### 2.7 终端输出：先辨过滤、恢复与重新执行

**✅ 保留项目已有命令；重复日志确实妨碍定位时，再定向试输出过滤，而非全局套一层“省 token”插件。** RTK 能把测试输出整理成计数与失败摘要，适合评估高噪声回归场景；是否值得保留，要看完成同一任务的质量、回读与总投入。详见[采用与对照](research/2026-10-22-frontier-trials.md#rtk输出变短与恢复能力分开选)。

**失败只剩计数且有恢复提示时，先取回日志，不先让 Agent 重跑。** 本仓用 RTK OSS 1.0.1 回放一次真实的历史测试失败输出：通用 `rtk test` 将约 285KB 缩成 280 字节，却藏掉了“磁盘已满”这个根因；返回的 `rtk recall HASH --full` 无需重跑便完整取回净化后的输入。本例不采用通用包装器作为 unittest 默认，保留项目原命令；已使用过滤器时，把“先 recall 定位，再决定是否重跑”交给 Agent。详见[回放范围与记录](research/2026-10-22-frontier-trials.md#rtk输出变短与恢复能力分开选)，这是非模型收益比较。

| 已安装 RTK 后的动作 | 实际得到什么 | 选择时注意 |
|---|---|---|
| 复制结果中的 `rtk recall HASH` | 读取此前保存的内容，不重跑测试 | 普通成功摘要不保证有恢复记录 |
| 给 recall 加 `--full` | 返回该记录已保存的全部内容 | 不会补回未生成、未保存或被容量截掉的部分 |
| 用 `rtk bypass` 运行原命令 | 发起一次新的未过滤执行 | 不是回放，不为找日志盲目重做有副作用的动作 |

**“取回原始输出”不等于恢复原命令会给出的全部诊断。** RTK v1.0.1 的 pytest 封装在没有对应参数时添加 `--tb=short`、`-q`、`-rxX`，然后才捕获和过滤；未生成的长 traceback 无法事后找回，显式 `--tb=long` 可覆盖短 traceback 默认但仍会经过过滤。恢复分支、recall 实现与 bypass 定义同样以固定源码为准；pytest 路径仍返回子进程退出码，不能把摘要变短直接说成失败被掩盖。以上来自固定源码，未运行。

Agent 交回实际命令、退出状态和所用恢复记录；人核本题需要的失败细节是否还在。需要完整诊断的下一次运行先选原生输出；反复回读或重试抵消收益，就撤回该命令的过滤。`rtk gain` 只是工具侧输出估计，不是整项费用或订阅额度的实测节省。详见[同题对照与当前版本边界](research/2026-10-22-frontier-trials.md#rtk输出变短与恢复能力分开选)。

**依据**：[本仓工具实试] RTK OSS 1.0.1 历史失败回放（约 285KB→280 字节；非模型收益比较）；[一手] RTK 固定源码与 pytest 封装（未运行）：[pytest封装](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/cmds/python/pytest_cmd.rs#L21-L74)、[恢复分支](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/core/tee.rs#L17-L105)、[recall实现](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/core/retriever.rs#L637-L727)、[bypass定义](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/lib.rs#L812-L842)、[退出码](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/core/runner.rs#L284-L367)；[经验] 采用判断；核实 2026-10-24。

<a id="rtk-uv-short-failure"></a>
**🧪 已用 RTK 的 `uv run` 失败却没有恢复提示，先核落盘结果；下一次确需执行时保留原生输出。** 真实用户 #4860 的 Linux 重现中，OSS 1.1.0 把普通结果与 `warn` 合并后只选中后者；24／499-byte 的短失败没有 tee 或 recall，500-byte 对照才完整留档，读取记录不增加执行次数。门槛看 RTK 捕获的合并 raw，本例输入均有完整换行；不是把所有非零退出都丢掉 stdout——只有普通结果、没有诊断关键词的控制仍保留结果，退出码也保留。

有当次恢复提示就沿提示读取；没有时先查程序自己的日志、产物与操作状态，不能靠反复 `recall` 补回从未保存的内容。准备下一次已确认可重做的执行时，沿用原生 `uv run …`，或使用 `rtk bypass uv run …` 取消这一层过滤；后者会真正再次执行命令。`tee=always` 也不能补上短失败的保存门槛。

若已装 RTK 自动改写，在其既有 `config.toml` 的 `[hooks].exclude_commands` 数组**加入** `"uv"`，不覆盖其他项：

```toml
[hooks]
exclude_commands = ["uv"]
```

这只排除普通 `uv run script.py` 的外层改写；实际 Hook JSON 对照中，`uv run pytest …` 仍变成 `uv run rtk pytest …`，显式 `rtk uv …` 也不受该设置影响。完整命令、有效配置、反例及恢复记录见[实际执行入口](../experiments/rtk-uv-recovery/README.md)；需要保留完整 traceback 的任务仍选原生输出，不把这一项排除当成关闭全部过滤。

**依据**：[真实使用者 #4860](https://github.com/rtk-ai/rtk/issues/4860)、[1.1.0 uv 实现](https://github.com/rtk-ai/rtk/blob/753a3b0e939f2e4490fc24e3a1984010f40a103c/src/cmds/python/uv_cmd.rs)、[保存前门槛](https://github.com/rtk-ai/rtk/blob/753a3b0e939f2e4490fc24e3a1984010f40a103c/src/core/tee.rs#L60-L66)。本仓 Linux 实跑与非作者独立复跑：2026-10-31；原用户 Windows／Claude 会话和模型收益未验。此处补充 1.1.0 的当前执行边界，不改变上面 1.0.1 历史回放的原日期与结果。

### 2.8 外部文档：先沿索引选页，不默认整站灌入

**✅ 已有官方文档入口时，先读其语言／任务索引，再取实现与前提页；不为一次查 API 先装 MCP 或下载整站。** `llms.txt` 是导航线索，不是版本锁或完整性证明；找不到适用页就回官方网页／固定源码，已有 Context7 精确版本入口也可沿用。详见[公开取回实试](research/2026-10-22-frontier-trials.md#llmstxt沿发布者索引选页再核适用范围)。

给 Agent 的具体任务可以是：“从发布者索引找 TypeScript 收消息并回复的例子，交回 API、运行前提、适用版本和未解链接。”本次 Teams SDK 路径取到了 `app.on('message', …)` 与 `send`／`reply` 的区别，但 `docs_typescript` 下的 App Basics 首段仍是明确标注的 .NET 2.1；全文包也保留同段。**按正文语言与版本选用，不能拿 URL 的语言名替代判断。** 这是本仓文档取回实试，未运行 SDK／模型。

关键前提链接失效时，补查对应官方入口，不靠改读 full 文件宣布完成：本次选页的部署下一步返回 404，全文也未补上对应部署正文。人接收的是适用于当前工程的调用与未解前提，不是文件更短；若选页不断漏掉依赖，就扩大相关章节而非机械坚持最小上下文。

**依据**：[经验] 采用判断；[本仓文档取回实试] Teams SDK、`llms.txt` 选页与 404 前提核查（未运行 SDK／模型）；核实 2026-10-24。

### 2.9 重复改法：让 Agent 交规则，不逐处自由改写

**🧪 多处相同语法改动，先比较现成重构与可测试的结构规则；已有 IDE／LSP 能准确完成就沿用。** ast-grep 适合按调用形状、参数或语法位置找目标，普通字符串仍用文本搜索；VT Code 作者实际把两路按查询类型分开，而非所有查询都先做结构扫描。本仓迁移规则实试见下。

给 Agent 的任务可写成：“把目标 API 的旧调用改为新形式，先交应命中和不应命中的代码实例、规则与预期清单；通过规则测试后只读扫工程，核准差量再修改并跑原生回归。”ast-grep 官方 Skill 采用例子→规则→测试→扫描；规则测试的 `invalid` 是应报告例子，`valid` 是不应报告例子，不是指测试文件能否编译。

**人核的是改动集合，而不只是规则跑通。** 把相似但不该改的调用也放进反例，检查漏项与多改；需要确定同一符号的所有引用时仍回语义工具，结构相似不能代替符号身份。规则越来越多才能覆盖少量个例时，退回局部修改；机械变化完成后仍验项目行为。详见[真实需求、采用与未验范围](research/2026-10-22-frontier-trials.md#ast-grep先验规则再批量定位)。

**把旧 API 批量迁到新形式，可以先借维护者的规则。** 本仓实际跑了 Pinia Colada 的 `useQuery(factory, () => value)` → `useQuery(() => factory(value))` 迁移，并收窄了会误改副作用块的匹配；空格、换行与注释不必逐处手改。详见[固定规则、返工与范围](research/2026-10-22-frontier-trials.md#ast-grep先验规则再批量定位)。

复用 [迁移重放入口](../experiments/replay_astgrep_migration.py)，准备它要求的固定上游 checkout 和 ast-grep 版本后，在临时副本中先跑原测试、修正负例字段，再应用收窄规则并检查差量。取其输出规则用到自己的项目时，先只读列出命中，核对导入身份与回调语义，再改写并跑本项目测试。

**先确认反例真的运行，再相信绿灯。** 上游两处把 `valid` 拼为 `vaild`，原本全绿却没测到这些负例；改正后，原规则把只有副作用的箭头函数改成了语法错误。同名局部函数仍可能被误改，普通函数转箭头也可能改变 `this`／`arguments`，所以结构规则不能替代语义接收。范围限固定规则与夹具，未做整应用迁移或模型效果比较。

**依据**：[一手／经验] VT Code 作者 [HN 讨论](https://news.ycombinator.com/item?id=47898384)、ast-grep [官方 Skill](https://github.com/ast-grep/agent-skill/blob/main/ast-grep/skills/ast-grep/SKILL.md)与[规则测试文档](https://ast-grep.github.io/guide/test-rule.html)；[本仓确定性实试] Pinia Colada 迁移与反例；核实 2026-10-24。

### 2.10 页面批注：交意图，也要交当前对象

**先用客户端原生元素／区域评论；需要跨客户端交接多条反馈，再试可复制批注。** Agentation 3.1.2 的[真实浏览器实试](../experiments/agentation-feedback.md)跑通双条导出与刷新保留，但一个列表路径匹配四行，排序后标记仍留在旧坐标。让 Agent 对照对象文字、当前页面状态和组件源码再修改，不把保存的 Source 当作当前构建重新识别的结果。本仓实试未测模型改稿收益。

**让反馈进入修改，至少交清“对象、变化、保留行为”。** [Posts 实际改稿](../experiments/tanstack-url-state/README.md#接收页面反馈让已应用条件可见)把“分不清输入草稿与已生效条件”转为结果摘要，并限定摘要只读 URL、保留原导航；接手者据此修改并通过 DOM／路由测试。采用源码审查反馈后，新版已补真实浏览器接收，草稿／提交和历史恢复符合预期；未发现新页面问题，不把此前定位批注说成修改需求。

**依据**：[本仓实试／研究] Agentation 3.1.2 浏览器实试与 Posts 改稿（2026-10-24；未测模型改稿收益）；[经验] 采用判断；核实 2026-10-24。

## 3. 会话层面的上下文管理

**✅ 先决定要解决什么，再选当前宿主的动作。** 不按聊了多久、纠正几次或剩余百分比自动清空、压缩或拆子任务。下表命令仅指核实日的 **Claude Code**；不是通用 Agent 命令。

| 当前问题 | 选择与条件 |
|---|---|
| 同一任务仍需前文，只是历史占空间 | 先用 `/context` 看来源；需要腾出空间再 `/compact <保留重点>`。自动压缩已正常工作时，不为“长任务中途”额外手动压缩 |
| 只有一段调查过程不再需要逐条保留 | `/rewind` 中选对应方向的 Summarize；这是历史摘要，不是文件回滚 |
| 任务无关，或错误思路已需要舍弃 | `/clear` 开新对话；同任务先保留已验证结论。压缩后立刻填满、工具失败或结果未知，先走 [17 的故障分流](17-troubleshooting.md#26-越聊越笨上下文腐化与压缩丢失)，而非重复清空 |
| 只想解释会话已有信息，不需要新查询 | `/btw` 读当前历史但无工具，问答不加入主历史；需要查当前文件／最新事实或据答复继续工作，就在主会话明确提出或交给能用工具的子任务 |
| 调查可独立完成，过程输出不值得留在主会话 | 可用子 Agent；普通子 Agent 从委派输入起步，fork 则继承全历史。要隔离旧假设不能靠 fork；工作强依赖共享背景或频繁往返时，保留主会话可能更合适 |
| 继续一个已保存的任务 | resume 取回历史；执行前仍核对当前文件和外部结果，沿用 [20 §4](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史)，不另造交接格式 |

**Codex CLI 要单独核对**：原生 `/compact` 总结上下文，`/new` 开新聊天，`/resume` 续接保存会话；`/fork` 复制聊天并保留原会话，不能当成 Claude 的 fork 子 Agent。压缩失败或历史显示缺失按 [20](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史)处理，不因同名命令假定恢复保证相同。

**关键局限**：以上是文档契约，不保证摘要无损或拆分后省时省钱；§4.2 的收益与反例仍须按各自模型、任务和 harness 解读。核查记录保留版本与读取范围，见[会话动作按问题与宿主选择](research/2026-10-13-context-tool-choice.md#会话动作按问题与宿主选择)。

**依据**：[一手] Claude Code 与 Codex 官方命令契约、checkpointing、子 Agent 与侧问答契约；[研究] §4.2 的收益与反例；[经验] 边界判断；核实 2026-10-24。

| 方式 | 说明 | 评级 |

| 进度文件 + git log | 同任务续接先复用已有任务记录与版本证据；Anthropic harness 的进度文件／JSON 清单是一个实现，机器消费时再选结构化格式 | ✅ |
| Claude Code auto memory | Claude 自动记录偏好和纠正；默认机器本地，同机器同仓库的 worktree 共享，不自动跨机器／云同步 | 🧪（定期审阅它记了什么） |

**独立记忆失效时，先回可读记录，不把“未检索到”当“从未发生”。** 升级时核实际安装来源，再验新捕获与后续检索；claude-mem 同号 marketplace 与 npm 曾有不同产物状态。Agent 整理来源与受影响范围，人判断是否停用该层及接收修订；详见[实际回退、维修与采用对照](research/2026-10-12-community-source-records.md#p82独立层的采用与维护责任)，不证明当前所有分发物已可靠。

**Claude 的共享范围要另查**：启动只加载 `MEMORY.md` 前 200 行或 25KB（先到为准），主题文件按需读；普通子 Agent 不加载主会话 auto memory，继承全历史的 conversation fork 例外。子 Agent `memory` 使用独立目录，`project` 范围可随版本控制共享；目录可配置，默认本地不等于无法共享。跨机器／云环境或委派时，沿用恢复记录，交接必要事实与来源，不为续接同步全部私人记忆。详见[官方契约与开关边界](research/2026-10-10-audit.md#s2c--2026-10-16-auto-memory-的共享与交接边界)，核实于 2026-10-16（UTC+8），未运行客户端。

**优先把工程经验沉淀成可评审的文档、测试或 lint 规则。** Kevin Liao 的文章及 HN 讨论强调文档、解释性 lint 错误与 ADR；这是作者实践和社区观点，不是独立比较试验。

导入纠错先分判据：静态包名／导入名限制可复用 `no-restricted-imports`，目录依赖则核解析器与 `import/no-restricted-paths`；后者未解析出目标会跳过该次检查，零报告不能当依赖合规。详见[固定配置与选择边界](research/2026-10-13-context-tool-choice.md#导入纠错先选已有规则能判断的对象)。

自动记忆也可保存有来源、范围和失效条件的经验，先做对照，不把一次成功升格为永久规则。Markdown 和数据库都可能陈旧，也都可以被审计，取决于实现；采用判断详见[14 规律二](14-synthesis.md#2-规律二按任务选择预先提供与按需获取)。

**依据**：[一手] Anthropic harness 案例、Claude Code auto memory 契约；[社区] [Kevin Liao 文章](https://liao.gg/blog/agents-dont-need-memory)与 [HN 讨论](https://news.ycombinator.com/item?id=49945933)；[经验] 建议；核实 2026-10-24。

### 4.1 先区分三种干预

**先确定要解决的是跨任务迁移、同任务压缩还是新上下文恢复，再分别验证。**

| 干预 | 保存什么 | 主要验证问题 |
|---|---|---|
| 跨任务记忆 | 以前任务的经验，用于新任务 | 是否真正迁移、是否污染未来任务、维护成本何时回本 |
| 同任务压缩/观察遮蔽 | 当前轨迹的摘要或部分观察 | 约束是否仍在、缓存影响、失败轨迹是否被拖长 |
| 新上下文恢复 | 当前代码 + 权威需求 + 恢复包 | 是否漏掉依赖、重复工作或沿用过期证据 |

三者可以同时存在，不能用其中一项的收益证明另外两项有效。新上下文不等于丢弃代码和证据，数据库也可以给新上下文提供可审计事实。

### 4.3 实际运行中的反例

**验收要检查规则实际可见、可重载，以及最新取消仍生效。** OpenHands SDK #4544（1.42.1）报告：规则激活标记保留，承载正文的事件却被压缩删除，因会话去重无法再次注入。issue 因不活跃关闭不等于修复。这是社区单例，未复测。

截至观察版本 `c4b93299`，故障链仍在：路径规则在事件 `extended_content` 中，observation 字符串转换不带正文，condenser 却用字符串摘要，移出事件也未重置激活标记。日志表示不一定等于模型输入。以上来自 2026-10-10 UTC 源码复核，未运行当前 SDK。

PR #4565 核实时未合并；作者真实模型失败报告针对旧 commit，不能当当前 main 复测或已发布修复。固定回归测试要求先证明承载事件确实移出，再区分注入通道的标记与摘要偶然回显。**场景未建立应判无效；标记保留不等于完整正文保留。**

真实验收核对实际模型输入或权威来源重载，不直接把特定注入通道的测试套给所有 harness。复用现有恢复清单，不另加规则登记框架或合成探针。

**把来源信任、授权和记忆召回分开处理。** PMPA 与 SkillJack v2 分别展示了跨会话恶意规则持久化及由污染轨迹产生技能后删除源仍留衍生物的故障方式；这些故障方式支持上述分工。PMPA 使用替代后端模型和模拟工作区；SkillJack 主要统计路由层面的策略违规代理指标，不是实际外部服务被攻破。不可把这些数字外推为默认 Codex/Claude 产品事故率。以上研究限定 harness/模型/合成任务，非本仓复现。

### 4.4 最小生命周期，而不是无限追加

**复用的工程经验至少带来源、适用仓库/模块、观察版本、验证状态和失效条件。** 发现相反证据时记录替代关系。记忆中的事实不提供新权限，最新的不可信文本也不能覆盖用户约束。

删除/纠正一条事实时，检查派生的摘要、索引和 Skill 是否仍保留旧结论，并测试重启后不会从旧轨迹复活。保持当前任务状态、可复用经验、验收证据和授权依据的区别。

采用门槛：在同模型、工具、预算与时间顺序下，和“新上下文 + 当前仓库 + 短恢复包”比较；把提取、整理、检索、缓存、重试、失败和人工维护全计入。任务完成率不降且总成本确有收益，关键权限/隔离/删除反例通过，才逐步自动化。检索命中率只是诊断指标，不是最终效果。

### 4.5 候选记忆与预算配置

**候选记忆先进入待审队列，上下文预算配置只解决空间，不保证压缩后的事实仍然正确。** 2026-10-10 补核：Gemini CLI 的 Auto Memory 文档把候选记忆/Skill 放入待审 inbox，明确标记实验性、默认关闭；Claude Code 2.1.296 增加子 Agent 的 `autoCompactWindow`。两者分别解决记忆晋升和上下文预算问题。详见 [S1/S3 来源](research/2026-10-10-audit.md)。

恢复任务时核对当前文件、服务和外部操作状态；记录来源、适用范围与失效条件，其余按 [4.4](#44-最小生命周期而不是无限追加) 与 [20 可靠的长任务](20-codex-long-horizon.md) 处理。

**依据**：[一手] Gemini CLI Auto Memory 文档、Claude Code 2.1.296 变更记录（未运行）；[经验] 工程建议；核实 2026-10-24。

### 4.6 独立记忆层：先验信息价值，再验自动供给

**✅ 默认保留当前代码、短恢复包和原生检索，不给每次修改强制注入旧任务记录。** 先比较相关历史信息是否改善实际代码结果，再比较服务的提取、更新与检索能否保住这份帮助；后者还要覆盖额外费用和人工维护。VibeMemBench 的直接 coding 对照说明“存在有用经验”不等于现成系统能有效供给；其任务经过筛选，不能当所有记忆服务的排名。详见[论文与公开产物比较](research/2026-10-13-context-tool-choice.md#p44独立记忆层的两类coding比较)（研究，2026-10-21）。

**👀 状态对齐恢复值得追，但不默认安装整套图系统。** MemTrace 在特定 DeepSeek 模型与两种 harness 上有正面质量结果，但 Codex 分支更慢、mini-swe-agent 分支反而更快；它研究同任务恢复，不是上一种跨任务检索的冠军。

**恢复时先核有效性。** Agent 保留证据来源、适用版本和替代关系，人检查测试及其依赖是否仍有效；条件改变或无法确认就回查当前状态。

**收益消失就撤回。** 若服务不能保持任务质量，或维护与等待超过目标收益，撤回外部层。这一原生起点是当前可行默认，尚非经上述论文证明的最优。

**依据**：[研究] VibeMemBench 直接 coding 对照、MemTrace 质量结果与恢复实验、公开产物比较（2026-10-21）；核实 2026-10-24。

## Codex 续接：压缩后保留目标，不等于目标继续支配行动

**✅ 保存当前目标、用户最新变更、实际产物、已知失败及下一动作，并在恢复时检查文件与执行事实。** 官方压缩提示要求记录进度、决定、约束、剩余动作，但它是期望行为，不是无损保证。近期使用报告同时存在“压缩后回旧任务”和“仍准确记得未完成范围却结束”两类现象，不能合并为遗忘。另有长会话延迟报告在高缓存命中与零 reasoning token 下仍慢，也不能靠上下文压缩次数判断问题已经解决。详见[固定来源与审查](research/2026-10-10-codex-continuity.md)。

当记录已经完整，仍只总结而不行动，应检查续接/停止行为，不继续盲目扩大记忆文档。🧪 只有出现具体跨会话检索问题时才考虑额外记忆服务。

**依据**：[一手／社区] Codex 连续性报告与审查记录；[研究] 采用判断；核实 2026-10-24。
