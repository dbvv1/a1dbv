# 03 · 上下文工程

> 编辑更新：2026-10-23（UTC+8）；新增终端输出过滤与恢复的源码核查，RTK未试用；此前定点原文与摘要委派仍限资料，未运行当前模型；[此前证据范围](research/2026-10-13-context-tool-choice.md#p73定点原文与摘要委派)；[旧页首范围](research/2026-10-13-context-study-reassessment.md#历史页首核实范围)。
> 一句话：**先区分需求、环境、模型能力、上下文和验证器问题；上下文应提供必要信息，而非尽可能堆满。**

## 30 秒选择：开始一个具体修改任务

**✅〔跨代保留〕先补齐这次修改的必要上下文**：写清目标与验收，让 Agent 读取项目指令、定位相关实现与可复用示例；其余资料按需取回。人核目标和检查覆盖，不替 Agent 预先整理全仓材料。**[经验：采用判断，依据见 §2–3]**

**✅〔2026-10 修订〕升级模型时，先审旧规则，不整套照搬。** 把“每次编辑前读全部设计文档”改成按任务指向相关文档；对 Astra 这类当前强模型，先撤掉重复教它如何探索、反复催测试的提示，保留项目特有命令、不可猜的契约和完成标准。删后漏了约束、相关测试或停在半成品，就补回具体缺口；混合模型团队不按 Astra 的能力统一删规则。**[一手：近期团队实践；经验：条件默认，见下节]**

**〔跨代保留；命令按宿主版本〕同一任务仍需前文、只是历史占空间时，才选压缩**，保留目标、约束、已验证结论与未完成检查。Claude Code 可先用 `/context` 看来源，再按需 `/compact`；Codex 单独见 [§3](#3-会话层面的上下文管理)，不照搬 Claude 操作。**[一手：既有命令契约；经验：选择]**

**⛔〔跨代保留〕不为“最小上下文”删必要信息，也不先堆满、清空或加检索框架。** 缺权威源或缓存已旧，先补信息并核当前状态；自动压缩正常时，无需按时长手动压缩，丢了关键约束就取回原始依据。**[经验：采用边界，依据见 §2.3–4]**

**✅〔2026-10 补充〕已知修改位置，先定点读原文；大批量事实定位才试摘要委派。** 摘要帮 Agent 缩小候选，不能独自承担并发约束判断或编辑依据；先确认委派成功且答案可回查，再比较节省。强制摘要路由暂不默认安装，见 [§2.6](#26-大文件先定点原文还是摘要委派)。**[经验：条件默认]**

**近期论文也要看实验代际。** §2.2 的 AGENTS.md v3 虽更新于 9 月，实验仍是 Sonnet 4.5、GPT-5.2 等；附录 B 在人为移除文档后反而看到生成上下文有益。这限制“少给一定更好”，不能作为当前模型配置的胜负证明。主流参照是规则文件、搜索与摘要续接（采用率未知），本页推荐属于比较前沿后的可行默认；最优上下文量与专用引用图净收益仍未知。[研究：原文与边界，详见[代际比较](research/2026-10-13-context-tool-choice.md#p52上下文代际复核)]

**大文件委派仍是候选优化，不是当前代际胜出方案。** 下文将近期原生按需读取与 Spotify 的摘要路由放在同一读者任务下比较；后者使用旧工作模型，公开复测还暴露宿主协议和路径解析维护成本。最优总投入未知，现有 gap1 保持条件范围，见[固定证据链](research/2026-10-13-context-tool-choice.md#p73定点原文与摘要委派)。**[一手／社区；研究：比较定位]**

## 1. 原理与使用边界

Anthropic《Effective context engineering》（2025-09）是旧代设计参照；按需取回等思路经上述近期做法确认，但不是所有模型与宿主的统一操作规范；具体动作见 §3。**[一手；经验：采用边界]**

| 概念 | 含义 | 实践 |
|---|---|---|
| **Context rot** | 长输入可能降低相关信息的利用效果，程度依模型、任务与内容而变 | 上下文是有限资源，要“花得值” |
| **注意力预算** | 更多内容会占用上下文；注意力计算的规模不能直接推出任务质量 | 每加一段内容，都要问它值不值 |
| **系统提示的“高度”** | 太具体（if-else 式）会脆弱，太抽象又没有指导性 | 给启发式规则和原因，不要给死规则 |
| **工具** | 自包含、容错、用途清晰；工具集要精简 | 见 [04 MCP](04-mcp.md#4-写好给-agent-用的工具) |
| **示例** | 几个多样、典型的示例胜过一长串规则 | 给 Agent 指一个“照着这个写”的现成文件 |
| **即时检索** | 只保存轻量的标识（路径、查询、链接），需要时再加载 | `@file` 精确引用；LSP 定位符号后读相关实现，字符串／配置另做文本搜索 |
| **压缩** | 同任务腾出空间时总结历史，但可能丢失细节 | `/compact 保留XX`；在 CLAUDE.md 里写明压缩时要保留什么 |
| **结构化笔记** | 把进度和决策写到上下文之外的文件 | `PROGRESS.md`、feature 清单（JSON） |
| **子 Agent** | 隔离专项工作的过程输出；是否继承历史取决于宿主与启动方式 | 有独立调查才拆，返回结论、依据和未解决项；不为节省上下文强制每次探索都委派 |

## 2. 指令文件：CLAUDE.md / AGENTS.md / 规则文件

**保留能减少定位或集成错误的信息，不按“代码可推知”一刀切删除。** Cloudflare Workers SDK 用短表导航任务目录，将版本交回 `package.json`，跨工具功能需检查 Miniflare、Wrangler、Vite、Vitest，并先跑最小相关测试。可借鉴“定位入口 + 行为边界”，不复制目录树与配置值；[固定源码对照](collaboration/reviews/2026-10-13-331e093.md#新增来源怎样改变模板建议)只证明项目已采用，不证明模型收益。**[一手；经验：采用判断，2026-10-13]**

### 2.1 各工具的加载规则（[一手]）

**✅ 共享内容可以只维护一份，但是否只留 `AGENTS.md`，要按实际加载入口决定。** Claude Code 的默认发现会被项目路径中的 `CLAUDE.local.md` 等文件抑制；需要兼容这些会话时，保留同目录 `CLAUDE.md` 的显式 `@AGENTS.md` 导入，比要求每位使用者改个人设置更易随仓库交付。没有这些条件、且已确认原生加载时，可只保留 `AGENTS.md`。**[一手：官方契约；经验：采用判断]**

| 工具 | 文件 | 会改变选择的加载条件 |
|---|---|---|
| Claude Code | `CLAUDE.md`、`AGENTS.md`、`.claude/rules/*.md` | 原生 AGENTS 入口从 v2.1.277 起提供，部分 provider／禁遥测会话到 v2.1.281 才支持。默认检查当前目录及祖先：有 `CLAUDE.md`、`.claude/CLAUDE.md` 或 `CLAUDE.local.md` 就不走 AGENTS 回退；用户级 `~/.claude/CLAUDE.md` 不触发这个抑制。子目录按需发现，不能假定所有指令已在开场加载 |
| Codex | `AGENTS.md`、`AGENTS.override.md` | 每次运行启动时建立指令链；全局先选首个非空 override／AGENTS，项目从根到当前目录逐层选择 override、AGENTS、备用文件名，每层最多一份；项目文档默认总预算 32 KiB。不能把 Claude 的 `@` 导入或子目录按需发现直接移植过来 |
| Gemini CLI | `GEMINI.md`（可配置文件名） | 此轮未重核，按目标客户端文档确认 |
| Cursor / Copilot / OpenCode 等 | 各自规则格式或 AGENTS 入口 | 文件同名不证明发现、合并和刷新规则相同，此轮未重核 |

- **项目路径有 `CLAUDE.local.md` 等抑制项时**：可保留仓库内显式导入，或在支持的用户／托管设置中选 `claude-md-and-agents-md`；不能把该选项写进项目 settings 就当全队生效。共同加载是拼接上下文，不是权限规则的确定性覆盖。**[一手；经验：建议]**
- **跨仓库时**：`--add-dir` 只增加可访问目录，不默认加载其指令；额外目录加载开关覆盖 CLAUDE 文件与 rules，不覆盖原生 AGENTS 发现。确实需要共享约定时，选择相应 CLAUDE 入口或显式导入，并核实外部导入批准状态，不能只看目录可读。**[一手；经验：建议]**
- **验证加载时**：新版本用 `/memory` 核对原生 AGENTS 路径，导入入口也核对 `/context`；`InstructionsLoaded` 不报告原生 AGENTS，但会报告 CLAUDE 导入（`include`）。没有该事件不能证明 AGENTS 没读，事件存在也不证明模型遵守了规则。**[一手；经验：建议]**

**关键局限**：以上是指定日期的官方加载契约与发布记录，不是本仓客户端实测；详细优先级、版本差异及反例见[共享指令加载证据](research/2026-10-13-context-tool-choice.md#共享指令发现导入与加载证据)。需要多工具生成配置时可评估 [rulesync](https://github.com/dyoshikawa/rulesync)，但生成文件仍须通过目标客户端的加载检查。**[一手：README；经验：建议]**

### 2.2 指令文件到底有没有用？（研究证据）

| 研究 | 主要依据与选择边界 |
|---|---|
| **[Evaluating AGENTS.md v3](https://arxiv.org/html/2602.11988v3)**（2026-09） | Claude Code（Sonnet 4.5）、Codex（GPT-5.2／5.1 mini）及 Qwen Code 的 Python issue 修复中，生成文件增加成本，成功率未显著改善；手写文件平均收益不显著，但显著优于生成文件，除 Claude Code 外均有提升，成本也增加。指令改变了测试和探索行为；仓库概览未显示可靠收益，长度影响也不显著。不能外推到其他语言和当前模型 **[研究：原文]** |
| **Do Context Files Help Coding Agents?**（2026-07） | Sonnet 4.6／GPT-5.5、三个 Python 仓库的小样本未检测出正确率收益；语料与注入渠道不同，描述性等价区间不证明普遍无效。[全文及公开数据复核](research/2026-10-13-context-study-reassessment.md#context-files失败解释与分析参数) **[研究；经验：数据与源码复核]** |
| **On the Impact of AGENTS.md Files on Efficiency v2**（2026-03） | GPT-5.2-Codex 在十仓小 PR 任务中，运行时间和输出 token 中位数下降；人工合理性检查不能证明同等正确性下提效。[有效样本、配对版本与复算](research/2026-10-13-context-study-reassessment.md#agents-效率耗时与正确性的边界) **[研究；经验：数据复算]** |
| **[Configuration Smells in AGENTS.md Files](https://arxiv.org/abs/2606.15828)**（2026-07） | 灰色文献与 100 个热门仓库归纳六种配置坏味道，见 §2.3；出现率不是删减后的效果证据 **[研究：原文]** |
| **A Few Pages of Markdown v2**（2026-09） | 企业仓库用于开发 RAMP；开源仓库的 agent-first 分层中，有配置组的认知复杂度增幅较小，但配置按观察终点分组，多数后于或同期于 Agent 采用，不能推出预先写文件的因果收益。agent-first 仅指未检出 AI IDE 配置痕迹。[分组、换算与维护边界](research/2026-10-13-context-study-reassessment.md#a-few-pages分组时间与维护) **[研究／一手；经验：复核]** |
| **Agent READMEs v2**（2026-08） | 文件历史与内容抽样说明指令会被维护，但相邻提交间隔不是全部文件的维护周期；安全、性能主题出现率不衡量效果，也不能判定项目缺少其他治理。[维护与内容口径](research/2026-10-13-context-study-reassessment.md#agent-readmes维护与内容口径) **[研究；一手：公开源码]** |

**综合结论**：
1. 评估**效率、行为约束与长期质量**，同时比较正确性、返工和成本。已有正面线索及相关性证据，不足以承诺等质量提效，也不能排除其他任务的收益。
2. **把 `/init` 当草稿，不原样提交**：保留可验证改变行为的项目特有信息，再做有无配置的对照；生成文件增加成本的结论限于上述 Python、模型和任务样本。
3. **不自动复制完整概览、目录树和逐文件说明**；有任务价值、难以发现的信息仍应保留，研究并未否定所有架构地图。
4. 小众语言或工具链（如 Unity 编辑器和序列化约定）更值得补充项目知识，因为模型先验可能较少。**[经验：建议]**
5. **安全和性能按任务需要补充**：写具体边界与验证方式，不按类别凑齐，也不以一句“注意安全／性能”代替已有文档或 CI。**[研究；经验：建议]**
6. **🧪 从短配置试用，按事实变化维护**：命令、权限、架构变化或出现失败反例时修订并验证；不以文件数量或编辑频率作目标，少修改也不证明无需维护。**[经验：建议]**

**本仓历史实验**：同一 bug 任务各组均成功；短指令改善了回归测试与项目命令使用，长指令也改变行为但成本更高。样本很小、原始产物待补齐，本轮未复现；无独立消融，不能把收益只归给某段指令。统计与设置见 [19 §4](19-experiments.md#4-e3指令文件长短)。**[经验：历史实测]**

### 2.3 写什么、不写什么（官方最佳实践 [一手]）

| ✅ 写 | ❌ 不写 |
|---|---|
| Agent 难以确定的项目命令（构建、测试、单测怎么跑） | 不改变定位或执行选择的重复代码说明 |
| 与默认习惯不同的代码风格 | 语言的标准约定 |
| 测试方式与首选的测试运行器 | 详细 API 文档（给链接） |
| 仓库礼仪（分支命名、PR 约定） | 易过期的配置值副本（给当前权威来源） |
| 项目特有的架构决策 | 长篇解释、教程 |
| 开发环境的坑（必需的环境变量等） | 文件逐个说明 |
| 常见陷阱、反直觉的行为 | “写干净的代码”这类空话 |

- **检验标准**：保留能改善定位、行为或质量目标的信息，删除重复、失效内容；功能不报错仍可补领域依据，增量条件见 [05](05-skills-and-plugins.md)。
- **规则被忽略**：先按 §2.1 查加载与冲突，再查表述、相关性和行为；不能直接归因于长度，也不靠加粗代替执行边界。**[经验]**
- **何时加一行**：发现可定位错误或改变当前选择的领域依据时；不设错误次数门槛，也不把所有资料常驻。
- 可机械检查的规则可以接入 Hook，但要验证匹配、错误和替代路径；硬权限由沙箱等运行时边界执行，见 [06](06-hooks-and-guardrails.md)。
- 用 `/doctor prompt-audit` 排查旧提示写法 **[一手]**；过度强调、全大写警告可能让较强的指令遵循反应过度 **[经验]**。

**✅ 清理陈旧指令时，保留默认行为与生效条件，不把“代码如此”直接改写成“需求应当如此”。** 让 Agent 先区分已证实的旧路径／状态与尚未解决的规格冲突；前者可在授权范围内继续清理，后者先标出双方依据，由负责人确认哪条契约有效，再做语义改写。压成表格后，人仍要核对“可解锁”是否被写成“默认开启”、条件和例外是否丢失。doc-cleanup 的作者报告与实际配方修订提供了这一反例，见[指令清理核查](research/2026-10-12-community-source-records.md#指令清理保留条件与契约意图)。**局限：这是历史自报与公开修订，未证明安装清理 Skill 提高正确率；路径检查通过也不证明语义保留。** **[社区／一手；经验：窄采用建议，2026-10-21 UTC+8]**

推荐延伸阅读：[Writing a good CLAUDE.md（HumanLayer）](https://www.humanlayer.dev/blog/writing-a-good-claude-md)，讨论了“指令预算”和渐进式披露。

#### 六种“配置坏味道”（arXiv 2606.15828 [研究：原文]）

| 坏味道 | 表现 | 怎么改 |
|---|---|---|
| **Lint 泄漏**（62%） | 命名、格式、import 顺序、行宽这类 linter 和 formatter 能检查的规则 | 先确认现有检查的触发与覆盖，再删除重复规则；保留运行入口、必要原因和例外说明 |
| **上下文膨胀**（42%） | 文件过长、塞满低优先级细节 | 行数建议和缩短个案只作线索；按任务价值删除重复／失效内容，必要资料按需读，不设通用门槛 |
| **Skill 泄漏**（35%） | 只在特定场景用的流程写进了常驻指令 | 先用按需参考资料；确需复用配方时再按 [05](05-skills-and-plugins.md) 选择窄 Skill |
| **盲引用** | 只写“见 docs/xxx.md”，不说明用途 | 写清楚**为什么、什么时候**去读，否则“Claude 经常会忽略” |
| **初始化化石** | `/init` 生成后从没改过 | 事实改变、评审发现缺失约束或出现可定位失败时修订；不以错误次数定门槛 |
| **指令冲突** | 前后矛盾 | 定期通读，用 `/doctor prompt-audit` 或社区 linter（agnix、ctxlint）检查 |

### 2.4 大仓库 / Monorepo（Claude Code 配置及检索选择）

| 需求 | 做法 |
|---|---|
| 只加载当前模块的约定 | 子目录 CLAUDE.md，或 `.claude/rules/` 加 `paths:` |
| 排除无关包的 CLAUDE.md | `claudeMdExcludes` |
| 限制受覆盖入口读取构建产物、生成代码、第三方依赖 | Claude Code 的 `Read(...)` deny 只覆盖内置文件工具及受支持命令；不能阻止任意子进程间接读取，完整路径隔离按 [10 的沙箱边界](10-security.md#3-防护原则)落实 **[一手：权限契约]** |
| 符号定位 | 按所需语言和操作选可用 LSP；语义引用与文本搜索互补，仍需读相关实现 **[经验：选型判断]** |
| worktree 太大 | `worktree.sparsePaths` 稀疏检出 |
| 跨仓库 | `--add-dir` / `additionalDirectories` |
| 规模化分发约定 | 做成内部插件市场里的插件 |

**✅ 按问题获取上下文，结果异常时先核对版本。** 不知入口可用 repo map 缩小候选；已知符号用能解析本项目的 LSP 查语义引用；字符串、配置与动态注册则搜索并追构造规则。Aider 的固定测试明确覆盖保存后仍复用旧 map、强刷才更新；clangd 对当前文件缓冲与跨文件头文件的默认读取来源不同。因此刚改过代码却零命中时，先确认读取的是 buffer、磁盘还是缓存，不能直接断言目标不存在。[固定机制与原帖](research/2026-10-13-context-tool-choice.md#源码检索map语义引用与当前状态) **[一手：源码／测试；经验：采用判断]**

**局限**：map 排名不是精确调用关系，LSP 也不保证覆盖运行时动态关系或全部未保存文件；本轮未测这些选择对模型正确率或费用的净影响。

**命中生成代码后，先找持久修改源。** 沿文件来源标记和构建规则回到源文件／模板，修改后按项目入口重生成并核对产物；运行文件可能正是生成物，不能据此认定它也是编辑源，也不宜为减少上下文一概排除读取。fullsend-ai 的风险标签功能曾只改入运行 bundle，后来回源修改，并由原评审者确认重生成一致。[固定补丁与复测范围](research/2026-10-13-context-tool-choice.md#生成代码运行产物与持久修改源) **[一手／社区；经验：选择，2026-10-18（UTC+8）]** **局限**：这支持追查生成关系，不证明新增语义索引或更多上下文有收益。

### 2.5 跨文件符号检索：何时补 Serena

**🧪 原生搜索、IDE 或现有 LSP 不足以定位跨文件引用／重命名时，再试 [Serena](https://github.com/oraios/serena/blob/main/README.md)。** 先只读对照 IDE 引用、目标配置与已知调用点，再限定编辑并编译测试；维护耗时超过收益就退回原生。**关键局限**：语言后端和版本决定能力，[Windows 初始化反例](https://github.com/oraios/serena/issues/2069)不能靠关闭防护解决；main 能力与 [v1.7/v2 许可](https://github.com/oraios/serena/blob/main/LICENSE)不可混用，本地索引返回的代码仍进入模型上下文。**[一手／社区；经验：选择，2026-10-12，未安装]**

**跨平台或构建配置修改，先补目标配置的核查。** 同一后端、同一构建下与 IDE 结果一致，仍可能共同漏掉其他配置。gopls 的引用查询只查所选文件的默认构建；这类任务先据目标配置核对相关文件清单，必要时补局部文本搜索，再在对应配置中核验调用点。[固定版本契约与真实需求](research/2026-10-13-context-tool-choice.md#跨配置修改原生引用也有构建范围) **[一手；社区；经验：选择，2026-10-17（UTC+8）]** **局限**：文本同名不证明语义身份；配置范围缺口本身不构成新增检索框架的理由。

**语义查询慢时，先定位再补详情。** 批量引用先取身份、位置及附近代码，再为选中目标请求正文、文档或签名。Serena 的 C++ 反馈促成减少附加请求及详情预算，参数须按版本选择；预算跳过与无文档可能同样缺省，查契约时应缩小目标。[反馈、修订与反证](research/2026-10-13-context-tool-choice.md#serena定位与附加详情的成本取舍) **[社区／一手；经验：选择]** **局限**：预算只限后续附加请求，不是调用硬时限，也未证明模型净收益。

**源码存在、语义查询为空时，先查项目导入。** 用文件／文本搜索确认目标，再核构建配置和依赖解析；索引过文件、旧 workspace 健康检查通过，不证明当前导入正确。Serena 的 Java 多模块报告涉及 Maven 配置与父 POM 解析；修正导入后先核已知定义和调用点，不靠扩大查询或无差别清缓存。[报告与修复](research/2026-10-13-context-tool-choice.md#serena语义检索为空时先核项目导入) **[社区／一手；经验：选择，2026-10-16（UTC+8）]** **局限**：修复进入 v1.6.0，但缺原任务修复后编辑验收；文本命中不证明语义引用完整。

**原生查询有、封装工具却漏掉时，先查过滤层。** 在相同文件状态和配置下对照调用点；原生 LSP 已找到时，核封装版本与过滤规则，临时沿用已核验的原生结果，不盲目扩上下文或重建索引。Serena 曾误过滤同名调用者，修复进入 v2.0.0。[Gleam 报告与回归机制](research/2026-10-13-context-tool-choice.md#serena原生引用存在但封装过滤漏掉) **[社区／一手；经验：选择，2026-10-16（UTC+8）]** **局限**：缺原任务修复后编辑验收，不能推广为所有后端正确。

### 2.6 大文件：先定点原文还是摘要委派

**✅ 编辑、调试和约束判断，默认让承担判断或修改的 Agent 读定位后的原文及必要周边。** 大文件不等于必须整文件读取，也不等于适合交给摘要器。先检索符号、调用点与契约，再决定所需范围；发现关联跨出片段就继续追原文。**[经验：条件默认，当前原生参照见页首]**

| 同一任务中的需要 | 选择 | 接收与撤回 |
|---|---|---|
| 已知目标，需改代码或判断细微约束 | 原生搜索后定点原文 | 人核契约、相关调用点和实际修改检查；缺上下游时扩大相关范围 |
| 多个大文件，只想缩小事实候选 | 🧪 按需摘要委派，返回文件位置与可回查依据 | 承担判断或修改的 Agent 回读决定性原文；遗漏、往返重传或延迟抵消节省时退回原生 |
| 想用 Hook 强制所有大读取改道 | ⛔ 暂缓默认安装 shunt 或其未合修复分支 | 先核目标宿主兼容、放行语义及实际路径；已有有效接入不因本例一概拆除 |

[Spotify 的公开实践](https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90)报告摘要遗漏线程安全问题、编辑仍需读原文；示例工作模型是 Gemini 2.5 Flash。它为候选定位提供机制，不证明当前模型上摘要与原文等质。**[一手：作者自报]**

**先验结果，再看节省数字。** 固定版本的[评估脚本](https://github.com/spotify/portal-ai-plugins/blob/cd5f40fb98a2c61c6041b228d11766a5318dc312/plugins/shunt/evals/run.sh)按 Shell 字符串长度估 token，委派失败后仍继续计算，未断言答案质量。接收时先核成功状态和关键答案，再把主／工作模型、失败重试及回读算入总投入；空回答不能算优化成功。**[一手：源码；经验：接收判断]**

**节省上下文的路由器不应顺带替人批准操作。** 外部使用者对 shunt 的复测区分了“旧 block 仍有效”和“allow 格式报错”；修复分支改成显式批准后，又留下权限语义和路径解析问题。未命中成本路由条件时，保留宿主正常权限流；兼容性与回归未闭合就沿用原生读取。[版本、二改与采用状态](research/2026-10-13-context-tool-choice.md#p73定点原文与摘要委派) **[社区／一手；经验：维护取舍]**

**程序卡与文档摘要分工，不互相替代。** 摘要帮定位规则，程序卡保存会改变执行顺序的前提与不变量，两者都要能回查当前依据。已知修改位置仍先读相关原文；跨步骤知识需复用才补卡，不为更短而删失败分支、并发约束或消费者。计划／评审放置见[05 §2.5](05-skills-and-plugins.md#25-codexskill-应补什么又可能增加什么)。[经验]

[Code2Skill §5.5](https://arxiv.org/html/2609.05571v1#S5.S5)压缩的是代码Skill，不是文档摘要，也不证明编辑可以只看摘要。若卡导致反复回读、漏约束或额外等待，恢复直接资料路径。[研究／经验]

### 2.7 终端输出：先辨过滤、恢复与重新执行

**✅ 保留项目已有命令；重复日志确实妨碍定位时，再定向试输出过滤，而非全局套一层“省token”插件。** RTK能把测试输出整理成计数与失败摘要，适合评估高噪声回归场景；是否值得保留，要看完成同一任务的质量、回读与总投入。[经验：采用判断；[采用与对照](research/2026-10-22-frontier-trials.md#rtk输出变短与恢复能力分开选)]

**“取回原始输出”不等于恢复原命令会给出的全部诊断。** RTK v1.0.1的[pytest封装](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/cmds/python/pytest_cmd.rs#L21-L74)在没有对应参数时添加`--tb=short`、`-q`、`-rxX`，然后才捕获和过滤；未生成的长traceback无法事后找回。显式`--tb=long`可覆盖短traceback默认，但仍会经过过滤。[一手：固定源码，未运行]

| 已安装RTK后的动作 | 实际得到什么 | 选择时注意 |
|---|---|---|
| 复制结果中的`rtk recall HASH` | 读取此前保存的内容，不重跑测试 | 普通成功摘要不保证有恢复记录 |
| 给recall加`--full` | 返回该记录已保存的全部内容 | 不会补回未生成、未保存或被容量截掉的部分 |
| 用`rtk bypass`运行原命令 | 发起一次新的未过滤执行 | 不是回放，不为找日志盲目重做有副作用的动作 |

[恢复分支](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/core/tee.rs#L17-L105)／[recall实现](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/core/retriever.rs#L637-L727)／[bypass定义](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/lib.rs#L812-L842)。pytest路径仍[返回子进程退出码](https://github.com/rtk-ai/rtk/blob/4ef8730cf3a0dea11c8d64a9b90bc0616fe52100/src/core/runner.rs#L284-L367)，不能把摘要变短直接说成失败被掩盖。[一手：源码]

Agent交回实际命令、退出状态和所用恢复记录；人核本题需要的失败细节是否还在。需要完整诊断的下一次运行先选原生输出；反复回读或重试抵消收益，就撤回该命令的过滤。`rtk gain`只是工具侧输出估计，不是整项费用或订阅额度的实测节省。[经验；[同题对照与当前版本边界](research/2026-10-22-frontier-trials.md#rtk输出变短与恢复能力分开选)]

## 3. 会话层面的上下文管理

**✅ 先决定要解决什么，再选当前宿主的动作。** 不按聊了多久、纠正几次或剩余百分比自动清空、压缩或拆子任务。下表命令仅指核实日的 **Claude Code**；不是通用 Agent 命令。**[经验：采用判断]**

| 当前问题 | 选择与条件 |
|---|---|
| 同一任务仍需前文，只是历史占空间 | 先用 `/context` 看来源；需要腾出空间再 `/compact <保留重点>`。自动压缩已正常工作时，不为“长任务中途”额外手动压缩 |
| 只有一段调查过程不再需要逐条保留 | `/rewind` 中选对应方向的 Summarize；这是历史摘要，不是文件回滚 |
| 任务无关，或错误思路已需要舍弃 | `/clear` 开新对话；同任务先保留已验证结论。压缩后立刻填满、工具失败或结果未知，先走 [17 的故障分流](17-troubleshooting.md#26-越聊越笨上下文腐化与压缩丢失)，而非重复清空 |
| 只想解释会话已有信息，不需要新查询 | `/btw` 读当前历史但无工具，问答不加入主历史；需要查当前文件／最新事实或据答复继续工作，就在主会话明确提出或交给能用工具的子任务 |
| 调查可独立完成，过程输出不值得留在主会话 | 可用子 Agent；普通子 Agent 从委派输入起步，fork 则继承全历史。要隔离旧假设不能靠 fork；工作强依赖共享背景或频繁往返时，保留主会话可能更合适 |
| 继续一个已保存的任务 | resume 取回历史；执行前仍核对当前文件和外部结果，沿用 [20 §4](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史)，不另造交接格式 |

**Codex CLI 要单独核对**：原生 `/compact` 总结上下文，`/new` 开新聊天，`/resume` 续接保存会话；`/fork` 复制聊天并保留原会话，不能当成 Claude 的 fork 子 Agent。压缩失败或历史显示缺失按 [20](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史)处理，不因同名命令假定恢复保证相同。**[一手：官方命令；经验：边界判断]**

主要依据是官方命令、checkpointing、子 Agent 与侧问答契约；[核查记录](research/2026-10-13-context-tool-choice.md#会话动作按问题与宿主选择)保留版本与读取范围。**关键局限**：这些是文档契约，不保证摘要无损或拆分后省时省钱；§4.2 的收益与反例仍须按各自模型、任务和 harness 解读。**[一手；研究；经验]**

## 4. 跨会话记忆

| 方式 | 说明 | 评级 |
|---|---|---|
| 进度文件 + git log | 同任务续接先复用已有任务记录与版本证据；Anthropic harness 的进度文件／JSON 清单是一个实现，机器消费时再选结构化格式 **[一手：案例；经验：建议]** | ✅ |
| Claude Code auto memory | Claude 自动记录偏好和纠正；默认机器本地，同机器同仓库的 worktree 共享，不自动跨机器／云同步 | 🧪（定期审阅它记了什么） |
| Gemini CLI 的 memory 收件箱 | 记忆要经人审阅后才生效 | 🧪 |
| 第三方记忆 MCP | 先分信息有用与服务能保住收益，见[直接coding比较](#46-独立记忆层先验信息价值再验自动供给)；接入边界仍见[04](04-mcp.md#跨会话记忆先区分检索与当前状态) | 👀 |

**独立记忆失效时，先回可读记录，不把“未检索到”当“从未发生”。** 升级时核实际安装来源，再验新捕获与后续检索；claude-mem同号marketplace与npm曾有不同产物状态。Agent整理来源与受影响范围，人判断是否停用该层及接收修订；[实际回退、维修与采用对照](research/2026-10-12-community-source-records.md#p82独立层的采用与维护责任)不证明当前所有分发物已可靠。[一手／社区／研究]

**Claude 的共享范围要另查**：启动只加载 `MEMORY.md` 前 200 行或 25KB（先到为准），主题文件按需读；普通子 Agent 不加载主会话 auto memory，继承全历史的 conversation fork 例外。子 Agent `memory` 使用独立目录，`project` 范围可随版本控制共享；目录可配置，默认本地不等于无法共享。跨机器／云环境或委派时，沿用恢复记录，交接必要事实与来源，不为续接同步全部私人记忆。[官方契约与开关边界](research/2026-10-10-audit.md#s2c--2026-10-16-auto-memory-的共享与交接边界)核实于 2026-10-16（UTC+8），未运行客户端。**[一手；经验：采用判断]**

**优先把工程经验沉淀成可评审的文档、测试或 lint 规则。** Kevin Liao 的 [文章](https://liao.gg/blog/agents-dont-need-memory)及 [HN 讨论](https://news.ycombinator.com/item?id=49945933)强调文档、解释性 lint 错误与 ADR；这是作者实践和社区观点，不是独立比较试验。**[社区]**

导入纠错先分判据：静态包名／导入名限制可复用 `no-restricted-imports`，目录依赖则核解析器与 `import/no-restricted-paths`；后者未解析出目标会跳过该次检查，零报告不能当依赖合规。见[固定配置与选择边界](research/2026-10-13-context-tool-choice.md#导入纠错先选已有规则能判断的对象)。**[一手；经验]**

自动记忆也可保存有来源、范围和失效条件的经验，先做对照，不把一次成功升格为永久规则。Markdown 和数据库都可能陈旧，也都可以被审计，取决于实现；采用判断见 [14 规律二](14-synthesis.md#2-规律二按任务选择预先提供与按需获取)。**[经验]**

### 4.1 先区分三种干预

| 干预 | 保存什么 | 主要验证问题 |
|---|---|---|
| 跨任务记忆 | 以前任务的经验，用于新任务 | 是否真正迁移、是否污染未来任务、维护成本何时回本 |
| 同任务压缩/观察遮蔽 | 当前轨迹的摘要或部分观察 | 约束是否仍在、缓存影响、失败轨迹是否被拖长 |
| 新上下文恢复 | 当前代码 + 权威需求 + 恢复包 | 是否漏掉依赖、重复工作或沿用过期证据 |

三者可以同时存在，不能用其中一项的收益证明另外两项有效。新上下文不等于丢弃代码和证据，数据库也可以给新上下文提供可审计事实。**[经验：实验分类]**

### 4.3 实际运行中的反例

**验收要检查规则实际可见、可重载，以及最新取消仍生效。** [OpenHands SDK #4544](https://github.com/OpenHands/software-agent-sdk/issues/4544)（1.42.1）报告：规则激活标记保留，承载正文的事件却被压缩删除，因会话去重无法再次注入。issue 因不活跃关闭不等于修复。**[社区：单例，未复测]**

截至观察版本 [`c4b93299`](https://github.com/OpenHands/software-agent-sdk/commit/c4b93299cf2b31c8b5d0b2c5a89965ccc5ff24f9)，故障链仍在：路径规则在事件 `extended_content` 中，[observation 字符串转换](https://github.com/OpenHands/software-agent-sdk/blob/c4b93299cf2b31c8b5d0b2c5a89965ccc5ff24f9/openhands-sdk/openhands/sdk/event/llm_convertible/observation.py#L68-L86)不带正文，[condenser](https://github.com/OpenHands/software-agent-sdk/blob/c4b93299cf2b31c8b5d0b2c5a89965ccc5ff24f9/openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py#L247-L251)却用字符串摘要，移出事件也未重置激活标记。日志表示不一定等于模型输入。**[一手：2026-10-10 UTC 源码复核，未运行当前 SDK]**

[PR #4565](https://github.com/OpenHands/software-agent-sdk/pull/4565)核实时未合并；作者真实模型失败报告针对旧 commit，不能当当前 main 复测或已发布修复。[固定回归测试](https://github.com/OpenHands/software-agent-sdk/tree/86e067dadd0a2398f6140c9f16220790be38af35/tests/integration/tests)要求先证明承载事件确实移出，再区分注入通道的标记与摘要偶然回显。**场景未建立应判无效；标记保留不等于完整正文保留。** **[社区：历史实测；一手：未合并测试]**

真实验收核对实际模型输入或权威来源重载，不直接把特定注入通道的测试套给所有 harness。复用现有恢复清单，不另加规则登记框架或合成探针。**[经验：采用判断]**

[PMPA](https://arxiv.org/html/2609.13889v1) 与 [SkillJack v2](https://arxiv.org/html/2608.03509v2) 分别展示了跨会话恶意规则持久化及由污染轨迹产生技能后删除源仍留衍生物的故障方式。**[研究：原文，限定 harness/模型/合成任务]** PMPA 使用替代后端模型和模拟工作区；SkillJack 主要统计路由层面的策略违规代理指标，不是实际外部服务被攻破。不可把这些数字外推为默认 Codex/Claude 产品事故率；但这些故障方式支持将来源信任、授权和记忆召回分开处理。

### 4.4 最小生命周期，而不是无限追加

**[经验：设计建议]** 复用的工程经验至少带来源、适用仓库/模块、观察版本、验证状态和失效条件；发现相反证据时记录替代关系。记忆中的事实不提供新权限，最新的不可信文本也不能覆盖用户约束。

删除/纠正一条事实时，检查派生的摘要、索引和 Skill 是否仍保留旧结论，并测试重启后不会从旧轨迹复活。保持当前任务状态、可复用经验、验收证据和授权依据的区别。

采用门槛：在同模型、工具、预算与时间顺序下，和“新上下文 + 当前仓库 + 短恢复包”比较；把提取、整理、检索、缓存、重试、失败和人工维护全计入。任务完成率不降且总成本确有收益，关键权限/隔离/删除反例通过，才逐步自动化。检索命中率只是诊断指标，不是最终效果。

### 4.6 独立记忆层：先验信息价值，再验自动供给

**✅ 默认保留当前代码、短恢复包和原生检索，不给每次修改强制注入旧任务记录。** 先比较相关历史信息是否改善实际代码结果，再比较服务的提取、更新与检索能否保住这份帮助；后者还要覆盖额外费用和人工维护。VibeMemBench的直接coding对照说明“存在有用经验”不等于现成系统能有效供给；其任务经过筛选，不能当所有记忆服务的排名。[论文与公开产物比较](research/2026-10-13-context-tool-choice.md#p44独立记忆层的两类coding比较)。[研究，2026-10-21]

**👀 状态对齐恢复值得追，但不默认安装整套图系统。** MemTrace在特定DeepSeek模型与两种harness上有正面质量结果，但Codex分支更慢、mini-swe-agent分支反而更快；它研究同任务恢复，不是上一种跨任务检索的冠军。[研究]

**恢复时先核有效性。** Agent保留证据来源、适用版本和替代关系，人检查测试及其依赖是否仍有效；条件改变或无法确认就回查当前状态。[研究]

**收益消失就撤回。** 若服务不能保持任务质量，或维护与等待超过目标收益，撤回外部层。这一原生起点是当前可行默认，尚非经上述论文证明的最优。[研究]

## Codex 续接：压缩后保留目标，不等于目标继续支配行动

官方压缩提示要求记录进度、决定、约束、剩余动作，但它是期望行为，不是无损保证。近期使用报告同时存在“压缩后回旧任务”和“仍准确记得未完成范围却结束”两类现象，不能合并为遗忘。另有长会话延迟报告在高缓存命中与零 reasoning token 下仍慢，也不能靠上下文压缩次数判断问题已经解决。**[一手/社区：见固定来源与审查](research/2026-10-10-codex-continuity.md)**

✅ 保存当前目标、用户最新变更、实际产物、已知失败及下一动作；恢复时检查文件与执行事实。当记录已经完整，仍只总结而不行动，应检查续接/停止行为，不继续盲目扩大记忆文档。🧪 只有出现具体跨会话检索问题时才考虑额外记忆服务。**[研究：采用判断]**
