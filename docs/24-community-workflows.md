# 24 · 社区开发者怎样使用 AI：工作流、分歧与失败案例

> 调查时间：配置与社区调查 2026-10-10，h3o 10-11，BAML/alchemy-utils/VibeTunnel/Codex 交付案例 10-12，SlopCodeBench 10-13。阅读建议在正文；固定来源、完整反证与检查范围见各节研究链接。
> 评级表示试用价值，不是性能排名；配置与作者经验不能独立证明工作流提效。**[经验：证据使用原则]**

## 1. 先看分歧：不存在一种适合所有人的工作流

**按实际缺口选一项能力，避免把几套完整流程同时放进全局指令。** 小修复可用轻量循环，复杂跨系统改动再补前置研究与关键接口验证。主要依据是 C1–C7 的固定配置与文档，详见[来源记录](research/2026-10-12-community-source-records.md#项目固定快照)。**[经验：选型判断]**

| 路线 | 代表 | 人主要做什么 | 值得借鉴 | 代价与适用边界 | 评级 |
|---|---|---|---|---|---|
| 流程完整的开发方法 | Superpowers | 对齐目标、审设计与最终结果 | 计划、分任务执行、验证与评审的衔接 | 与强 Agent 原生能力重叠时可能增加等待和成本 | ⛔ 暂缓全局强制；🧪 针对明确失败试用 |
| 小而可组合的 Skills | Matt Pocock Skills | 选择过程、定义领域语言与测试边界 | 访谈、术语表、ADR、公共接口测试 | 需要使用者判断何时调用，约定可能与现有团队冲突 | 🧪 按需试用 |
| 复杂仓库的上下文工程 | HumanLayer | 审研究、计划、架构与切片 | 先研究依赖再实现，有意识压缩和交接 | 前期阅读成本高；收益为作者案例，非普遍倍数 | ✅ 借鉴方法 |
| 可定制的轻量 harness | Pi | 自己决定流程并选择扩展 | 工具组合、可检查的会话与扩展 | 权限隔离与扩展维护由使用者承担 | 🧪 适合愿意定制的人 |
| 人在循环中的结对 | Aider | 选择文件、讨论方案、审 diff | ask/code、repo map、测试反馈 | 需要主动引导，文档里的旧模型建议需另核实 | ✅ 借鉴结对方式 |
| 常驻任务控制台 | OpenHands Agent Canvas | 管后端、触发器、权限和结果 | 多 Agent 后端、定时/事件驱动自动化 | 要负责服务运维与自动写入边界 | 🧪 有重复任务再部署 |
| 规格驱动与过程模板 | Spec Kit | 审规格、技术计划和验收 | 可追踪产物，区分新功能、修 bug、想法评估 | 文档同步成本；不能让形式上的一致代替功能验证 | 🧪 中大型改动试用 |

**局限**：这些路线可以组合，适用性取决于任务与实际触发路径，不能由项目热度排序。

## 2. Superpowers：重点看 Skill 之间怎样衔接

**🧪 只借用能纠正具体失败的环节。** 缺需求就澄清，调试先取证，完成前读当前验证结果；大块独立任务再拆子 Agent。固定 Skill 文件确实衔接了访谈、计划、执行与评审，也允许简单清楚的任务直接执行及 inline 路径。**[一手：C1；经验：采用判断]**

**局限**：强 Agent 已能完成这些步骤时，全套串行流程可能只增加等待，收益须连同上下文与审查成本一起算，见[配置记录](research/2026-10-12-community-source-records.md#2-superpowers重点看-skill-之间怎样衔接)。

### 社区暴露的两个失败模式

**✅ 评审计划的假设，接口改变时同步剩余计划。** #2470 报告代码、测试和评审共用计划盲点；#2450 报告修好脚本参数后，待执行计划仍调用旧接口。因此针对权限、空值、异步与跨模块交界加反例，并把待派发 brief 当作接口消费者。**[社区：C8 原帖；经验：采用判断]**

**局限**：这是用户报告而非本仓库复现，完整描述与来源见[两个失败模式](research/2026-10-12-community-source-records.md#社区暴露的两个失败模式)。

## 3. Matt Pocock：控制权与领域语言

**🧪 先尝试短术语表或公共边界测试。** 给反复混淆的 5–10 个概念配代码位置/例子；测试独立预期，一次实现一个纵向行为。依据是 `grill-with-docs` 和 `tdd` 的实际配置，见[来源与约定](research/2026-10-12-community-source-records.md#3-matt-pocock控制权与领域语言)。**[一手：C2；经验：采用建议]**

**局限**：其 TDD Skill 另要求先由用户确认测试边界，已有明确验收与授权的任务不应因此重复等待。

## 4. HumanLayer：从研究与计划，到把人的评审重新放回来

**✅ 把调查对准会改变实现的决定。** 缺调用关系、兼容契约或架构边界时先研究，把结果压缩成实施所需材料；局部问题已清楚就直接做。HumanLayer 的 research → plan → implement 与后来的切片建议提供了这种实践线索。**[社区：作者经验；研究：采用判断]**

**局限**：作者同时经营协作工具，单例与假设时间模型不能当作普遍提速证据，见[原文与推理复核](research/2026-10-12-baml-and-review.md#6-重读作者的后来复盘哪里值得借哪里不能跟随)。

### BAML 双 PR：研究帮助选位置，实施仍需纠正计划

**✅ 保存选择实现位置的理由，允许运行与代码反馈推翻计划。** #2259 在已有 test validator 只拒绝相关断言，被合并；#2258 在 visitor 额外禁止其他属性，被关闭。但有研究的原计划也把测试属性放错位置，实施中才改正，而且两 PR 自动评审都给了肯定意见。**[一手：原始补丁与计划；研究：采用判断]**

**局限**：这是有人工纠正的历史单例，不能隔离 RPI 对当前模型的净收益，完整父提交、测试和归属见[BAML 记录](research/2026-10-12-baml-and-review.md)。

### 前沿评估线索：连续需求比单题更接近日常维护

**✅ 评估连续需求时，分别看新增退化、持续遗漏与 Agent 得到的反馈。** SlopCodeBench 的固定默认路径保留代码、重置会话，只提供新规格且不自动回传隐藏评分；Regression 也不要求旧测试以前通过。对端局部探测还发现 meshctl 的错误顺序断言过窄、复制函数漏掉普通拆分模块。**[一手：固定 runner；经验：对端局部执行]**

**局限**：这些问题既不能证明日常项目必须装记忆服务，也不足以量化已发表分数受影响程度或否定全部模型结果，计数、反例与成本口径见[专页](research/2026-10-13-slopcodebench.md)。

## 5. Pi：少预设流程，开放可组合能力

**🧪 适合愿意维护扩展与隔离的人。** Pi 的 minimal/extensible 路线不内置子 Agent 或 plan mode，当前文档已有 MCP 与 codemode；脚本可组合工具、并行读取、过滤大结果，开发者需检查每项错误与截断。**[一手：C4；经验：选型判断]**

**局限**：codemode 失败不会回滚已发生的副作用，Pi 也不内置文件/进程/网络/凭证权限隔离，部署边界须另设，见[机制记录](research/2026-10-12-community-source-records.md#5-pi少预设流程开放可组合能力)。

### 三个近期使用者帖子

**借鉴可检验的运行条件。** Orbi 记录 reviewed head、attempt 与阻塞；网关硬预算帖子提出预留费用；pi-trim 的十题对照却出现输入减少、估计费用增加，提醒同时看缓存与定价。**[社区：C10；研究：采用判断]**

**局限**：三个首帖不是采用率或可靠性证明，完整表与待核问题见[原帖记录](research/2026-10-12-community-source-records.md#三个近期使用者帖子)，pi-trim 另有[离线复算](research/2026-10-10-pi-trim.md)。

## 6. Aider、OpenHands、Spec Kit：三种不同的控制位置

**按人要控制的位置选择做法。** Aider 的 ask/code、repo map 与测试反馈适合短循环结对；OpenHands Agent Canvas 的后端/触发器适合有重复任务且能承担服务运维的人；Spec Kit 按新功能、bug、想法提供不同入口，小修复无需全套 SDD。**[一手：C5–C7；经验：选型建议]**

**局限**：常驻自动化增加权限与运维责任，能访问 OpenHands agent server 的人可借它操作机器，完整配置来源见[控制位置记录](research/2026-10-12-community-source-records.md#6-aideropenhandsspec-kit三种不同的控制位置)。

## 7. 真实人类仍在承担的工作

**✅ 人负责取舍和交付责任，Agent 用真实反馈推进。** 明确什么值得做、哪些风险不可接受；用产品试用、具体错误和关键接口纠偏；将重复知识变成测试/短 Skill，发布时交付可解释的改动。Ghostty 维护者在 #8289 要求贡献者能审查 AI 生成代码并尊重接收方的维护时间，见[原帖范围](research/2026-10-12-community-source-records.md#7-真实人类仍在承担的工作)。**[社区：维护者反馈；经验：综合判断]**

**局限**：快速原型的可体验路径不能替代真实用户、数据或收费前的权限、持久化与恢复验证，具体做法见 [15](15-task-playbooks.md)。

### 接收方如何接管：Immich 的删除同步补丁

**✅ 交接说明跟随最终接口，而非最早的审查回复。** Immich #26070 披露 Codex 辅助 SQL 核对与测试；维护者两轮审查后，补丁先移除查询 helper，再统一为 remote ID 输入。作者曾解释保留双方法更合理，但最终代码已变，接管者应以合并实现理解 Android、权限、选中备份相册与移入回收站的边界。来源与对应补丁见[接管记录](research/2026-10-13-immich-handover.md)。**[社区：作者披露；一手：审查与源码；研究：采用建议]**

**局限**：这是历史辅助开发单例，接口测试与成功的 Mobile unit / Dart analysis 不证明真机不再重传，也没有审查工时或发布后支持数据。

### 本仓库判断：强 Agent 的默认基线应更轻

**✅ 原生能规划、实现并验证就先用原生；出现具体失败，再补一项能力。** **[经验：条件建议]**

| 观察到的问题 | 最小改变 |
|---|---|
| 清楚的小修复或文案被流程拖慢 | 直接做，保留相关检查 |
| 经常做错需求 | 短需求对齐 |
| 猜修复或误报完成 | 系统性调试或当前验证证据 |
| 跨系统错误假设代价高 | 前置研究、接口审查与独立验证 |
| 独立任务大、上下文拥挤 | 子 Agent，并计入整合成本 |

依据是实际 Skill 入口：Superpowers 的低触发阈值与原生探索存在重叠，官方 Skill 也可能带额外确认关口；同时 Superpowers 允许简单任务直做，不能把所有版本概括成强制全套。详细来源与净收益口径见[记录](research/2026-10-12-community-source-records.md#本仓库判断强-agent-的默认基线应更轻)。**[一手：配置；研究：判断]**

**局限**：尚无 Astra 组合对照，只有在质量相当且总时间/费用/人工返工更差时，才能对该任务判断负收益。

### 不同作者的实践补充：把新知识交给 Agent，再检查实际产物

**🧪 Skill 优先补版本知识；优化提示前先审评分器。** Starlette 1.0 案例给了领域知识、短需求与 demo；同仓库 DSPy/Datasette 报告却出现训练分上升、留出集下降，并暴露“语义上的零”和并列排名误判。**[一手：公开文件；社区：AI 生成研究报告]**

**局限**：生成报告与汇总 JSON 不能替代逐题验证，未证实长 Skill 优于简短参考资料，完整来源与读取范围见[案例记录](research/2026-10-12-community-source-records.md#不同作者的实践补充把新知识交给-agent再检查实际产物)。

### Codex 实际开发：需求、纠正与本机验证是不同的工作

**✅ 给清楚的产物与范围，在使用环境验兼容性。** h3o 绑定案例中，人补充不提交上游源码与控制 PR 大小，并实际测试 Python 3.12 成功、3.14 失败；源码却声明 `>=3.8`，坐标注释约 100 米而断言允许约 1.1 公里。**[社区：作者反馈；一手：固定源码；研究：反例审查]**

**局限**：这是 2025 年 Codex Cloud 历史案例，完整过程表、面积预期疑点和未读取范围见[h3o 记录](research/2026-10-12-community-source-records.md#codex-实际开发需求纠正与本机验证是不同的工作)，不能作为当前 Astra 能力测试。

### 从原型到第二次修改：alchemy-utils 的真实 CSV 改变了什么

**✅ 把实际规模、运行命令与必须保留的语义一起交给 Agent。** 初始引擎边界后来用于 CSV 分批优化；作者报告导入从接近一小时到约 35 秒，但逐批字段并集也让稀疏输入在不同批大小下使用默认值/保留旧值或写 NULL。先确定缺失字段契约，再测跨批失败回滚、schema 推断与默认值，并更新旧说明。**[社区：作者耗时；一手：源码；经验：对端 SQLite 运行报告、本侧源码核查]**

**局限**：真实反例不等于本侧重跑，性能也未消融；30 次调用的完整材料缺口与全部历史 CI/版本见[原研究页](research/2026-10-12-alchemy-utils-evolution.md)。

### 不同作者的后续维护：VibeTunnel 的内存所有权修复

**✅ 跨内存管理模型移植时沿“分配 → 返回 → 最后消费 → 清理”检查一条完整路径。** 公开快照返回已释放的字符串切片；外部贡献者修为 arena 后，还需绑定到真正负责清理的对象。无 upstream 仓库的失败条件成为回归，外部 session/IPC 契约仍可保留。**[一手：固定源码与维护提交；经验：采用判断]**

**局限**：项目报告的测试通过不等于独立复跑，精确 head CI 的 Node/Mac/iOS 均 skipped，完整时间线和后来 Rust 迁移的归因边界见[原研究页](research/2026-10-12-vibetunnel-maintenance.md)。

### 2026-10-12：当前 Codex 的交付与使用案例

**✅ 将产品承诺变成对应运行状态；🧪 交付失控时先恢复一个可追踪闭环。** Ra & Apep 用原生锚点替代按钮后，对端六场景记录显示无 JS 路径恢复导航；KPI 项目作者却自述做了三四个月仍无可靠应用、不清楚哪个版本权威，宜先核部署提交、走一条跨角色业务路径，再判断修复或平台选择。**[一手：补丁；经验：对端浏览器记录；社区：项目自述]**

**局限**：网页复测只覆盖记录中的状态，KPI 建议也尚无执行后结果，具体场景、12 项自检、许可与维护约束见[案例研究](research/2026-10-12-codex-delivery-cases.md)。

## 9. 下一轮怎么继续探索

**沿具体失败追下一次变更。** 比较原生、单项 Skill、完整流程时计入质量、总费用、人工打断和返工；对已读案例继续看维护者修复与实际交付。已有 pi-trim 离线复算，其他候选和未覆盖范围保留在[来源记录](research/2026-10-12-community-source-records.md#9-下一轮怎么继续探索)。**[经验：研究建议]**
