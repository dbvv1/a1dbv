# 22 · 评估 Agent：证明配置带来了什么

> 核实时间：2026-10-10；连续开发的测量、判定器、契约变更与生成测试边界于 2026-10-14 补核，同日按既有研究同步质量目标的评估与采用条件；2026-10-15 补核大补丁与连续交付的边界、游戏移植评分的证据条件。2026-10-20 补核双实现入口与后续维护取舍；2026-10-21 补公开同模型对照的指标／配置对账、连续升级规格比较、十轮产物接受实例及P48选型／终评分离；2026-10-22补生产采用代理与质量判定分流。适用：更换模型、修改指令、引入 Skill、增加工具或并行编排之前。
> 评级：✅ 采用“小型任务集 + 对照 + 原始证据”；🧪 试用模型裁判，先校准再用于放行。

## 30 秒结论

- **✅〔跨代保留〕先写要采用什么，再比旧方案与候选的合格交付和完整投入。** Agent保留产物、运行与失败证据，人核任务及判定器是否代表真实目标。
- **✅〔2026-10修订〕采用整套配置可以先做包级对照；解释哪项起效再做单因素或消融。** 不为拆清每个机制拖延可逆试用，也不把整包收益归给某一条提示。
- **⛔〔2026-10修订〕不只用旧模型失败集评新一代，也不让优化器边改评分边报提升。** 真实失败保留为回归，另核代表性正常任务；判定标准改了，重新对齐基线。差异小于波动、必要行为退步或总投入不值得，就保留旧配置。[一手／研究：近期比较见下节]

## 1. 要回答的是一个决策

“这个配置很先进”不可验收。把问题改为：**在修 bug 任务上，补充短契约是否减少漏测？功能已正确时，补充领域依据是否让目标操作更易理解或完成？** 两种都可成为比较起点，不要求先出现失败，也不默认加 Skill。判断单项贡献时只改变一个主要因素；决定整套方案是否采用时可直接对照整包，但分别记录差异。先写出旧方案、候选方案、必须保留的行为、质量标准和费用／等待／人工投入的可接受取舍及停止条件；质量目标的依据见 [05](05-skills-and-plugins.md#25-codexskill-应补什么又可能增加什么)。**[经验：工程建议]**

Agent Skills 官方指南要求比较带 Skill 和不带 Skill，或新旧版本；同时保存输出、断言结果、耗时与 token，并结合人工反馈和执行轨迹改进。它建议初期从 2–3 个真实用例开始。这是寻找问题的起点，不足以证明普遍优势。**[一手：S2]**

| 要做的决定 | 对照设计 | 最容易误判的地方 |
|---|---|---|
| 换模型 | 同一任务、工具、权限和验收；记录各自推理设置 | 把工具变化的收益算到模型上 |
| 加 Skill | 相同任务，带与不带 Skill；任务验收不变 | 给新方案更多提示或隐藏答案 |
| 加 MCP / CLI | 比较完成目标所需的完整过程 | 只比较单次工具调用 token |
| 开子 Agent | 同一交付物，串行与并行；包括整合成本 | 只算主 Agent 的成本 |
| 调整记忆 | 新会话、固定可见记忆，含过时信息用例 | 前一次运行留下答案或缓存文件 |

## 2. 分开记录四层结果

**[经验：工程建议，行为评估思路参考 S3]**

1. **运行是否有效**：依赖安装、认证、服务和测试数据是否就绪。认证失败记为环境失败，不记为模型不会编程。
2. **任务是否完成**：业务结果、回归测试、边界条件是否通过。测试未收集到用例不能算通过。
3. **过程是否合规**：是否修改验收测试、越界写文件、访问禁用服务、执行了未授权副作用。
4. **交付是否值得**：目标质量、总费用、实际等待、人工主动工时与返工程度分别记录；功能通过不等于质量已无改进空间，质量改善也不自动抵消其他代价。

Gemini CLI 的 EDK 会检查工具调用和参数等行为，而不依赖最终回复的精确措辞；其文档区分结构校验和真正的模型行为运行，也要求处理模型带来的不稳定性。**[一手：S3]**

注意：某个项目要求特定工具调用，不代表所有评估都应该强制固定轨迹。若两条执行路径都正确、安全且高效，就不应因 Agent 没按预想顺序工作而判错。**[经验：工程建议]**

### 生产采用信号不能直接充当正确答案

**默认并列看实际采用与独立质量判断，不把它们合成一个“通过率”。** Cloudflare的上述生产复盘结合作者下一次修改与跨提供方盲评，判断少发意见是在减噪还是漏检；同一次整体优化，各审查角色也有不同结果。具体升档选择见[02](02-models-and-cost.md)。[一手：10-19复盘]

Agent可整理哪些意见被处理、被拒或仍不可验证；人抽核它们是否符合真实需求，并核裁判分歧。改行不保证改对，不改也不必然无用；跨模型一致只能作为另一信号，不能直接当正确答案。必要行为退步就撤回候选，不等总分把它平均掉。[研究：采用建议]

整包比较回答“是否保留”，单项归因回答“为什么”。不同时间窗口、角色或判据的数据分开看，不能把组合优化的总节省归给某一项变化。[研究；[本次来源与边界](research/2026-10-12-experiment-records.md#p72生产采用代理与评估修订)]

## 3. 如何选任务

先从最近真实发生的任务抽样，覆盖正常路径、边界情况、已知失败模式，以及功能正确但有明确质量目标的任务：**[经验：工程建议]**

| 类型 | 示例 | 能判定什么 |
|---|---|---|
| 局部修复 | 日期解析边界错误 | 能否定位、修复并添加有效回归测试 |
| 跨模块修改 | 新字段贯穿存储、API、界面 | 能否发现依赖与保持兼容 |
| 代码理解 | 找出某个权限检查的全部入口 | 是否有源码位置和反例，是否遗漏 |
| 故障恢复 | 测试服务启动失败、工具暂时不可用 | 会不会重复无效重试或谎报完成 |
| 上下文变化 | 旧记忆与当前配置冲突 | 是否重新读取事实并修正假设 |
| 浏览器任务 | 提交表单并确认持久化 | 能否超越截图，验证实际行为 |
| 质量改进 | 改善已有界面的信息关系或任务引导 | 必要行为保留时，目标操作是否更易理解或完成 |

保留一部分未用于调提示词的任务作为留出集。若见到失败就把标准答案写进 Skill，随后只重跑原题，测到的是对题目的适配。小样本用来发现差异；推广前再扩展到实际任务分布。不要为了漂亮的总分剔除难例。**[经验：工程建议]**

### 并行配置：按集成依赖接收，不只看测试总分

**✅ 比较单体与团队时，在同一最终集成树上核关键生产者—消费者关系。** 复用现有验收中的跨接口断言，缺口才补：上游提供了什么、下游是否使用、合起来是否符合目标。Agent整理依赖及实际结果，人核关系是否代表业务；不是额外要求每题装一套benchmark。[经验]

[AsynCodeBench](https://arxiv.org/html/2609.32662v1)发现较高测试通过比例仍可伴随依赖未闭合；[NP-Bench](https://arxiv.org/html/2610.07261v1)则用实际合并核契约迁移。它们支持补集成判据，不证明固定多人拓扑或新协调工具最优。分支各自的绿灯也可能来自不同测试集，不能直接据此归因于交接。[研究]

**整合失败先定位归属，再决定修哪里。** 在同一基线与环境下，将同一适用断言用于基线、各份固定补丁和组合；区分原有失败、单支引入的失败及组合后才新增的失败。缺少另一分支新功能的预期失败，不当作单支回归；只有各单支通过而组合失败，才据此检查交接或收窄并行。最终树仍须通过完整验收，不以诊断替代接收。[研究：独立stale判定器反例及采用推论，见[共同测试条件](research/2026-10-12-experiment-records.md#p81整合失败先排除测试条件不同)]

**首次通过不等于最后仍通过，步骤也不等于时间。** 过程里的首次依赖通过只用于定位何时形成接收条件；最终改变后要再核最终状态。比较等待、费用和人的返工另留实际记录，不能把逻辑checkpoint提前当交付提速。明确关系无法稳定保持，或整合成本抵消收益，就收窄并行，保留可独立完成的部分。口径与反例见[研究记录](research/2026-10-12-experiment-records.md#p72审计补强并行结果按依赖接收)。[研究／经验]

### 自动优化后，先区分选型分数与独立终评

✅ **优化Skill描述时可复用已有迭代流程；要据分数换掉正式默认，先冻结胜出版本，再做未参与选择的终评。** Anthropic的现行[指南](https://github.com/anthropics/skills/blob/dbd4588f9e1033efb41dad4bef2f7947c8993d44/skills/claude-api/shared/evals/eval-hillclimb.md)已提供两分与可选三分路径，不必自建平台。样本不足以同时支持稳定调优和终评时，先保试点结论，不靠再切小数据集制造可信度。[一手；研究：采用默认]

**不读题目正文，也可能用过它的分数。** 每轮用test决定留退或选择最终版本时，该集合已参与选型；只有标签叫“test”不够。Agent整理反馈去向和候选账，人核哪些结果实际影响了下一次修改。因旧终评结果再改描述后，应补新的独立终评，或把旧结果降为开发证据；不能再换一个旧test更高的候选当作独立验收通过。[研究：选择过程判断]

**报告先核齐套与分母，再读best标记。** 本仓用人工账本运行固定官方lite报告器：best读取外部指定轮次；缺失重复次数不补零，部分失败状态不进分数均值。报告展示本身不负责证明所有预定调用已经完成。缺运行账或有效终评就延后推广，已有默认仍能满足需求时保留。原脚本复核、数据角色与投入取舍见[P48证据](research/2026-10-12-experiment-records.md#p48优化skill描述后如何接受收益)。[经验：限定离线复核，非模型效果]

## 4. 一次可复查的运行

记录只需包含用例、基线与候选、仓库/模型/配置版本、每次尝试的结果、费用、耗时和证据位置；先复用项目现有报告，不必引入新模板或平台。

1. 固定仓库提交、输入数据、Agent/模型版本、工具与配置；记录预算和超时。
2. 为每次运行准备独立目录和外部测试数据命名空间；新会话并不自动隔离数据库、浏览器 profile 或后台进程。
3. 先验证基线：环境有效；修 bug 时验收能发现目标缺陷，质量改进时保存当前产物与实际操作结果，预先确定比较标准，不要求基线先失败。
4. 在相同验收下运行对照和候选；交错或随机安排顺序，记录缓存、限流和服务变化。
5. 保存 diff、退出码、测试数量、日志和人工评语。对有敏感信息的轨迹保存访问受控的原件与可公开摘要，不提交凭证。
6. 失败分类后再重试；保存原失败记录，不用最后一次成功覆盖它。

以上是 **[经验：工程建议]**。官方 Skill 指南也要求干净上下文与具体评分证据，但工作区和外部服务的隔离需要执行方另外落实。**[一手：S2]**

### 修 bug 的强验证

**先确认预期结果从哪里来，再做红绿验证。** 把断言追到原需求、已确认复现中的正确结果或独立计算，不只照抄待修实现的输出；现有测试已能区分目标缺陷时直接复用，只补未覆盖的行为。在独立测试副本里，确认同一测试在修复前因目标缺陷失败、修复后通过，排除导入或依赖错误；不要在有未保存改动的工作目录直接还原文件。**[经验：工程建议]**

生成测试失败时，先判断错的是实现还是预期，不要为了全绿自动改断言。一项沿真实 PR 历史传播人工变异的研究发现，按当前实现通过来筛选测试，会留下持续认可错误行为的断言；原生测试已经检出的变异则在生成前排除。**局限**：这是特定模型与筛选条件下的机制证据，不是当前 Codex／Claude 的真实缺陷率或新增测试的净收益。[方法、原生基线与反证](research/2026-10-12-development-conditions.md#生成回归测试先保留预期再决定是否新增)。**[研究：采用判断]**

“新测试通过”只能证明当前代码符合断言；修复前失败、修复后通过，仍要核对断言是否覆盖用户目标。[oMLX 的独立局部执行](research/2026-10-13-omlx-postmerge.md#7-云端独立执行相同测试与实际渲染路径)把旧版的一个断言失败与一个新增参数不兼容错误分开；再走两版共有接口，确认修订避免了不支持模板的渲染错误。补丁还覆盖位置保留和能力隔离，但合法降级仍会改变已有前缀。因此涉及性能或兼容性时，要保留受影响配置的实际结果，不能把正确降级算成完整恢复。**[一手：固定补丁与测试；经验：局部执行；研究：采用建议]**

**局限**：本仓执行的是抽取的原函数与上游测试类，并非完整服务或真实 tokenizer；未运行模型或重测缓存收益。

## 5. 如何计分而不自欺

**[经验：工程建议]**

- **主结果按任务算**：所有必要条件通过才算该任务完成；断言通过率用于诊断。不能用九个容易的断言抵消一次越权或数据丢失。
- **目标质量单列**：两边功能都通过时，仍按预设标准比较目标操作与产物；保留必要行为的回归检查，不把减少错误设为唯一收益，也不把审美偏好写成普遍改善。
- **展示分母**：例如完成 7/10，另有环境失败 2 次、超时 1 次。若只报告有效运行，也同时列出总尝试数和排除原因。
- **重试单独计费**：报告首次成功比例、预算内最终成功比例、总尝试费用。最佳一次的结果不代表稳定性。
- **展示分布**：按任务类型列结果，附中位数和长尾。样本很小时直接展示每次运行，不用不稳定的 p95 制造精确感。
- **等待与人工成本分开**：分别记录实际等待和澄清、审查、整合、修复的主动工时。机器运行快，未必减少人的工作；可先做一次固定时长的盲审，记录阻塞问题和返工。
- **未知值保持未知**：费用没有遥测时填 `null`，不要填 0；跳过的检查标为 skipped，不能冒充 passed。

总尝试费用 / 成功交付数可以作为单位交付成本，但必须包括失败尝试，且在成功数为零时标为不可计算。它也不能取代质量门槛。

### 公开对照先对账，再决定是否迁移

**✅ 默认保留现有入口，先核目标指标与完整尝试；账目或必要结果不齐时，将新 harness 留作候选。** 同一公开 Codex 评测有160次结束、159次有 reward、摘要158次 completed；异常行仍显示费用。另有一条列表首显1.00，详情却是ux=1、correctness=0、reward=0。Agent 应绑定 job、数据集版本与指标键，分别列运行状态、异常、评分缺失和任务通过，人核实际验收规则；不要把多指标单元格的首个数当成功率。[公开两臂与判定](research/2026-10-10-codex-continuity.md#p44公开同模型对照先核指标与实际配置)。[一手：公开运行记录；研究：采用]

**同模型不等于只改变一个配置。** 该对照还改变 harness、并发数，且候选臂包含两个版本；现有资料不足以将成本差异单归因于压缩。若目标任务结果和完整费用可复核，再做有停止条件的窄试；没有新增有效收益就保留旧入口。本次未运行模型，也未完成后续修改比较。[研究]

### 两种实现都能用：用下一项确定修改决定保留谁

**✅ 默认保留能沿现有公共路径承接下一项确定修改、并保住必要旧行为的实现。** 先确认对照真走两个实现入口，再追同一新需求要改哪些规则、错误定位和消费者。CPython 的旧新解析器对照曾误测新实现自身；后续 f-string 并入公共语法，又须补公开 tokenize 消费链，说明通过旧测试并未替维护取舍作答。[固定维护链](research/2026-10-12-development-maintenance.md#cpython两种解析路径之后保留哪条维护路径)。**[一手：源码与维护记录；研究：采用判断]**

**⛔ 不为“更新、更快或少几行”单独更换已经满足目标的实现。** 原实现能局部承接下一需求、迁移反而增加接口和接管责任时就保留原实现；若公共路径丢失必要行为，或迁移负担超过已确认收益，撤回替换建议。此历史链解释修改传播，没有同条件维护工时数据。**[研究／经验：取舍与边界]**

**Agent 负责把下一需求追到改动落点，人决定哪些表现值得改、哪些契约必须保留。** 让 Agent 分列旧行为回归、新目标和下游接口，并标出未覆盖处；典型误判是把同入口自比当双实现验证、把新需求当旧版缺陷。人核对实际入口、诊断位置及消费者变化，不能仅凭“都通过”接收迁移。**[研究／经验：评估建议]**

### 比较规格优化：别让未到达步骤消失

**✅ 按 [07 的行为约束起点](07-workflows.md#3-大功能访谈式-spec-)做窄对照，并让下一次修改继承各自产物。** SWE-Chain 提供同模型、同升级链的规格粒度比较，但参考差分辅助生成的输入不等于现实用户能低成本写出的提示。[对照、成本和范围](research/2026-10-13-slopcodebench.md#p44连续升级先补行为约束不自动补整套解法2026-10-21)。[一手；研究]

**完整链验收同时看计划、到达和有效评分步骤。** 固定实现只汇总已有评分，恢复后的最终 chain 文件也不是全部失败尝试账。Agent 保留原始尝试及未到达项，人核完整链的分母，再判断保留、撤回或证据不足；本仓未运行该模型对照，P44完整验收仍未完成。[一手：固定源码；研究]

### 连续需求：先分清旧债、新回归与测量问题

**先确认测的是连续修改，而非一次更大的补丁。** 第二次、第五次需求从 Agent 上一轮实际产物继续，附上当时的验收结果；若评测协议允许失败后续接，仍记录未通过状态，不称为已验收交付。人工修复或换回参考实现须单列。SWE-EVO 的多 PR 发布差分仍从独立起点提交一个补丁，回归集合也不等于完整旧功能；版本相邻、测试多，不能证明自己的代码能承接下一需求。[固定方法与反例](research/2026-10-13-slopcodebench.md#7-swe-evo大补丁与连续交付的边界)。**[一手；研究：采用建议]**

**先核judge到达的功能，再决定修代码。** EvoWeb同一应用的十轮公开产物中，唯一no在错误的Stock Search页面搜财报词；源码有正确Earnings入口与徽标接线，但不能据此改判yes。默认保留原产物，先在正确路径复验。末轮五项yes也未覆盖删除观察项后的两处持仓汇总：代码使用不同集合，需先确认保留／隐藏政策，再补集成验收，而非让Agent盲删持仓。人核需求，Agent追输入、实际产物与judge观察；本次只有静态／算术复核，没有独立运行应用。[完整十轮决策账](research/2026-10-13-slopcodebench.md#evoweb十轮产物怎样决定先重评补验还是修代码)。[一手；研究：采用判断]

**代码与会话另核恢复证据。** 另一应用的日志显示源码恢复后丢失会话历史；请求resume不等于历史已到达。[恢复记录](research/2026-10-13-slopcodebench.md#同一代码留下了不代表会话到达)。[一手；研究]

**✅ 对齐同一验收行为的前后状态和可见反馈。** SlopCodeBench 的 Regression 分类不要求此前通过；固定默认路径保留代码但重置会话，只给当前规格，不自动反馈隐藏评分。区分以前通过现在失败、一直失败、规格主动改变、测试／环境改变；同名测试也须核输入与断言。比较记忆时固定反馈，比较反馈时固定可见知识，否则只报告整套方案结果；隐藏验收不必开放答案。**[一手：源码；研究：采用建议]**

**有意改变一条契约时，给相邻保留行为配一条验收。** Pydantic AI 为取消清理移除共享排空后，未读完流但正常返回的 handler 也丢失完整响应；最终修复把排空放在 driver 的正常返回路径，并同时保留取消不继续消费的测试。让 Agent 区分“哪些退出方式要改变、哪些结果仍必须保留”，再决定改断言、窄修或重构；不能为恢复旧行为而直接撤掉新需求。共享抽象无法区分两种合法契约时，先局部调整职责归属，保留无关接口。见[固定演化链与 AI 评审反馈](research/2026-10-12-development-conditions.md#pydantic-ai取消契约改变不代表正常完成也应改变)。**[一手：补丁与测试；研究：采用判断]** 关键局限：原用户示例曾不匹配故障路径，本仓未执行上游，新增测试定义与第三方复演不等于本仓取得历史红绿结果。

**判定器也可能把好改变判坏。** 本仓库局部执行 meshctl 原复制函数：单文件与拆模块的合成程序原本都成功，复制后只有拆模块版因 helper 未被带入而失败；另一个错误顺序断言拒绝了规格允许的排列。它们是局部设施／契约问题，未证明已发表模型分数受了多少影响，也不构成整个 benchmark 失效。对临时评估或团队 CI，先确认验收执行的是完整提交产物、断言确由需求要求，再用其分数决定模型、Skill 或代码结构。**[经验：局部实测；研究：范围判断]**

**涉及单位或坐标转换时，让断言与实际消费者使用同一表示。** PDF 表单的像素框高不能直接和点字号比较；先按每页实际图像／PDF 尺寸换算，再检查高度，不能在缩图后仍套渲染时的固定 DPI。[固定检查器与填充器](research/2026-10-13-domain-skill-contract.md#pdf-表单验收按消费者的坐标与单位判定)使用不同单位，源码推导的示例会被检查器接受，却不满足换算后的高度条件。**局限：这是源码与示例算术核对，未实际渲染；原工作流已有最终图像检查，几何断言不能替代它，也不证明文字已被裁切。** **[一手：源码；研究：采用判断]**

**评估修正后，先选重做哪一层。** 只算错且原始报告可追溯，先重算；只修评估环境且完整产物已保存，可重评固定产物。若改了规格或 Agent 当时看到的环境／反馈，要比较新条件下的行为就须重新生成；旧产物仍可按新规格评分，但不能代表 Agent 获知新规格后的表现。产物缺失且无法追回时重跑或标无效，重评补不出缺失事实。[SWE-Milestone 的维护修订](research/2026-10-13-slopcodebench.md#8-swe-milestone评估修正后重做哪一层)支持这一分流，不证明模型能力或节省幅度；判定器有错也不抹去真实功能失败。**[一手：固定源码／维护记录；研究：采用判断]**

### 游戏移植：先核分数证明了什么

**✅ 选游戏 Agent／移植方案时，先读评分项的证据条件，再决定还缺哪种试玩；不要按 `Visual` 名称或加权总分验收画质与可玩性。** SWE-Game 的公开移植评估将运行、Editor、静态支持和文件存在按不同系数计分；其 Visual 测实现对应关系，明确不测感知／审美相似。保留严格运行完成结果，动作应引起的进度用匹配无输入对照核查，连续画面、声音和操作感受仍按目标游戏观察。**局限：论文与公开发行版的任务清单和评分设置不同，不能把论文成绩当作当前默认配置的复测。** [固定源码、负对照和评分边界](research/2026-10-12-development-conditions.md#swe-game游戏移植的-visual-分不等于体验质量)。**[一手：论文与源码；研究：采用判断]**

## 6. 模型裁判怎么用

官方 Skill 指南建议用具体断言、证据和盲评；机械检查优先用脚本，主观质量补人工评审。**[一手：S2]**

**[经验：工程建议]**：

- 隐去候选方案名称，交换展示顺序，观察判定是否翻转。
- 提供评分准则和待评产物，不把被评 Agent 的“已经完成”当事实。
- 用人工标注的失败案例校准误报和漏报；另一个模型也可能共享盲点。
- 将“可验证的正确性”和“风格偏好”分开。风格更好不等于功能正确。
- 记录裁判版本、提示词与输入；更换裁判后重算一部分旧样本，检查可比性。

## 7. 何时推广，何时停止

先在低风险任务中试用。必要行为与授权边界不退步，目标缺口得到改善或目标质量按预先约定的标准有可复查改善，再分别判断费用、实际等待与人工主动工时是否符合预设取舍，决定是否扩大使用；不要求必须降低错误率。没有目标收益或代价不可接受时，缩减补充、删除 Skill 或恢复旧配置。不要把不断增加指令当作唯一优化方向。**[经验：工程建议]**

本仓库的 [19 历史实验](19-experiments.md) 已补交提示、精简轨迹、脚本及逐次汇总，可核对主要汇总算术；模型运行尚未由本侧独立重现，完整产物范围以 19 为准。不能把已有记录说成没有，也不能把算术复核当成重新运行模型。新实验按本章保存输入与产物，才便于后续复查。
