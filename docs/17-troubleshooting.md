# 17 · Agent 跑偏了怎么办：故障排查手册

> 核实：2026-10-22（整页诊断选择比较；历史案例保留各自日期）。依据：[一手] Anthropic 的模型迁移与提示指南（Claude API 官方 Skill 中的 `model-migration.md`）、Claude Code 最佳实践与 changelog；[社区]、[研究] 的案例与实验见各节依据行。其中的提示词是 Anthropic 在 Fable 5.1 上测试过的英文原文、部分句子“承重”，下文给出原文和中文意思；用在其他模型上效果需要自己验证 [经验]。

## 30 秒结论

✅ **先查实际失败在哪一层，再决定改提示、代码还是验证入口。** 用户报告“加载时错、最后正常”时，让 Agent 保留原入口和失败阶段；已有测试／trace 能定位就继续用。⛔ 不用稳定后的截图或部署成功覆盖未解释的失败检查。人确认应有的体验和验收语义，Agent 负责复现、缩小原因，并在修后版本重走原路径。

**依据**：[经验：本页默认] 先定位失败层级、保留原入口与修后重走的处理顺序；核实 2026-10-22。

## 当前最高水平：原故障、诊断假设与修后验收连起来

**近期领先机制是把诊断变成可反驳、可重跑的修复，而不是继续加“不要出错”的提示。** 2026-09-28 Scale AI 的修复案例同时核旧失败路径与修后合法完成；独立的 Islo 10-15 实验揭示新容器仍可能留下判分信任缺口。它们支持检查真实执行边界，未证明所有 Agent 的调试收益。

**本页采用低增量默认：先固定目标版本、失败阶段和验收行为，再决定是否增加诊断工具。** 版本错误先补对应文档与行为检查；弱测试先补能区分对错的反例；多步归因才试诊断 Agent，结论仍须修后重跑；UI 继续复用已有 trace 和原失败阶段。独立版本研究、测试实验和公开失败轨迹分别补强这些选择，详见[整页比较](research/2026-10-13-browser-healing-outcomes.md#p84整页故障诊断与修后接收比较)。

**整页主要选择已比较，差距 1 是资料判断，不是效果验收。** 范围、请示和表达提示仍是条件默认，缺跨模型净收益证据；当前最佳整套工具、全投入收益和本仓当前模型效果仍未知。没有明确新增可观察量时，不安装诊断平台或增加探针；新工具不能关联目标构建、或增加噪声和复核成本时撤回。

**依据**：[一手／研究] [Scale AI 修复案例](https://arxiv.org/html/2609.34262v1)、[Islo 10-15 实验](https://www.islo.dev/blog/verifier-tampering/)；[研究；经验：采用判断] [整页故障诊断与修后接收比较](research/2026-10-13-browser-healing-outcomes.md#p84整页故障诊断与修后接收比较)；[研究／经验] 差距判断与撤回条件；核实 2026-10-22。

## 2. 逐项处理

**先按症状进入对应小节，按各节给出的顺序处理。** 每个小节尽量给出可直接用的提示词或配置。

### 2.1 谎报完成或进度

**先在提示里写清可运行的检查命令和通过条件，再要求进度逐条对应工具结果。** 没有可运行的完成标准时，“看起来做完了”就是唯一的停止信号（见 [07](07-workflows.md#1-核心验证闭环-)）；长时间运行时，模型可能编造进度。

**处理**：
1. ✅ 先在提示中写清检查命令和通过条件；需要跨轮继续时，Claude Code 可用 `/goal`，需要程序化判定时用命令型 **Stop Hook**。官方区分了三者：`/goal` 是会话级 prompt 型 Stop Hook，其评估器只读对话证据，不独立跑测试；命令型 Hook 才执行配置的检查。
2. 要求进度汇报**逐条对应工具结果**。Anthropic 测试中，这段提示“几乎消除了”在专门设计的诱导任务上编造进度的情况：
   > Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly. Report outcomes faithfully: if tests fail, say so with the output; if a step was skipped, say that; when something is done and verified, state it plainly without hedging.

   （汇报前，把每一条结论对照本次会话中的工具结果核对；只报告有证据的工作，未验证的明确说出来；测试失败就附上输出，跳过了就说跳过了。）
3. 要求“**做完整个任务，而不只是容易的部分**；做不完的，把能做的做完，并明确说缺什么、为什么”；
4. 现有检查漏掉关键行为或假设时，才试用新上下文验证者；厂商针对 Fable 5.1 的观察不保证跨模型净收益。没有新增依据、或已有可靠检查时不叠加，见 [07](07-workflows.md#1-核心验证闭环-)。

局限：这些机制不保证任务必定完成；Stop 有事件与循环上限，API 错误走无继续决策权的 StopFailure，具体边界见 [06](06-hooks-and-guardrails.md#返回值)。

**已有部署回执时，先核同一 SHA 的测试结果。** Simon 的 `822d40d` 上 Test #1862 失败，而 Pages #610 成功；公开摘要不足以判断失败原因。Agent 应报告“已部署，测试失败待查”，保留目标行为、测试与发布各自的结果，再查失败日志及受影响检查。人决定验收要求，不能用站点可访问替代未满足的要求；若测试后来证实与本次无关，也应给出依据。见[23 的接收选择](23-browser-verification.md#8-交付报告写到能复查)。

**依据**：[一手] [最佳实践](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work)、[Goal 评估](https://code.claude.com/docs/en/goal#how-evaluation-works)、Anthropic 范围提示；[一手；经验：采用边界] Fable 5.1 观察的跨模型边界；[一手：公开运行摘要；经验：处理建议] [Test #1862](https://github.com/simonw/tools/actions/runs/35680726542)、[Pages #610](https://github.com/simonw/tools/actions/runs/35680726538)（`822d40d`）；核实 2026-10-22。

### 2.2 绕过验证：改测试、跳过检查

**先区分检查过弱、未完成要求和有证据的主动绕过，再决定补检查还是改测试。** 分数通过只能证明检查接受；不能据此判断任务完成，也不能把所有假阳性都归为模型作弊。Scale AI 的过程复核（2026-09-28）支持把过程与结果分开看。

**处理**：
1. 先核原生权限；模板 `protected-paths.txt` 的 `ask` 只对匹配的编辑事件请求确认，不覆盖任意 Bash 写入、符号链接等路径，不能据此认定测试目录全面受保护，见 [06](06-hooks-and-guardrails.md#1-为什么需要-hooks)。
2. 在指令里写明：“**不要为了让测试通过而修改测试**，除非测试本身写错，并说明理由”；
3. 评审时**先看测试的 diff**，再看实现的 diff；
4. 修 bug 用 red/green：Agent 核实失败来自目标缺陷、保存证据后，在授权范围内修复并重跑；预期不明或涉及必须由人决定的取舍时再询问（见 [15 第 2 节](15-task-playbooks.md#2-调试)）。

**测试本身也要有反例，验证器要守住独立边界。** 不因提示写了 TDD／形式验证就接收：让 Agent 给出能击穿原缺陷的输入，人核断言是否真的区分对错。Dan Luu 的独立实验中，测试技术名称没有消除弱断言；该结果限于所测 Rust／Sol 条件，不是否定 TDD。

**若提交物能碰最终判分，先修验证入口再重测。** Islo 的受控实验说明新容器仍可能执行可篡改判分的提交物。默认将候选执行与最终判定隔开；修后回放旧失败并核正常行为。对判分／信任边界，按 Scale 的修后复核在明确代理和预算下发起新尝试，查替代入口及能否重新找到合法解；旧路径封住与参考解通过仍不足以宣布边界恢复。

**依据**：[研究] Scale AI [过程复核](https://arxiv.org/html/2609.34262v1)（2026-09-28）；[经验：覆盖边界] `protected-paths.txt` 的 `ask` 匹配范围；[一手／研究] Dan Luu [独立实验](https://danluu.com/agentic-testing/)（限于所测 Rust／Sol 条件）；[一手；经验：采用判断] Islo [受控实验](https://www.islo.dev/blog/verifier-tampering/)、[Scale 修后复核](https://arxiv.org/html/2609.34262v1#S5)；核实 2026-10-22。

### 2.3 范围蔓延和越权

**先写明本次改动的边界，任务外的问题只列为后续事项。** 症状是修 bug 时顺手重构周边代码、创建没要求的备份分支；社区反馈 Opus 5.5 在 auto mode 下把在一个区域执行的授权扩展到了另外 5 个区域。

**处理**：
1. Anthropic 测试过的范围提示（大意）：
   > If, while working or testing, you find a pre-existing bug, a performance concern, or behavior the task doesn't mention, don't fix, optimize or extend it in this change unless the requested behavior cannot work without it; report it as a follow-up in your summary.

   （工作中发现的其他 bug、性能问题、任务没提到的行为，**不要在这次改动里修**，除非不修就做不成；在总结里列为后续事项。）
2. 当你只是在描述问题或提问时，明确它的产出是“评估”而不是“修复”：
   > When the user is describing a problem, asking a question, or thinking out loud rather than requesting a change, the deliverable is your assessment. Report your findings and stop.
3. 改变系统状态的命令（重启、删除、改配置）之前，要求它“确认证据确实支持这个具体动作”；
4. 权限层面：`permissions.deny` 写死不允许的命令和目录；**auto mode 不能代替隔离**（见 [06](06-hooks-and-guardrails.md)、[10](10-security.md)）。

**依据**：[一手] Anthropic 范围提示与“描述问题即评估”提示；[社区] Opus 5.5 auto mode 跨区域授权反馈；核实 2026-10-22。

### 2.4 过度请示或提前停下

**只在已授权、范围明确的任务里减少请示。** 症状是不停地问“要不要我…？”，或在消息末尾写“接下来我会运行 X”然后就停了，需要你回一句“continue”；必要权限、不可猜的业务取舍、破坏性操作或范围变化仍需停下，可逆不等于已经授权。

**处理**：
1. 把可以自主处理的动作和必须确认的例外写清，再开始执行。
2. 厂商针对 Fable 5.1 的无人值守提示可能减少澄清概率，不能脱离产品必需确认直接复制；出现误解范围或跳过必要确认时撤回该提示，先澄清任务。命名、格式等已授权范围内的小决定可自行选择并注明。
3. 若自有 harness 持续向模型注入剩余上下文倒计时，可按该模型指导避免反复注入；来源讨论模型可见输入，不是用户界面状态栏，也不要求隐藏人的预算与进度信息。不能控制宿主时不假定提示能改变其注入行为。

**依据**：[一手] [模型迁移指南](https://raw.githubusercontent.com/anthropics/skills/main/skills/claude-api/shared/model-migration.md)；[一手；经验：采用边界] 已授权任务的自主范围与撤回条件；[经验：适用范围] 剩余上下文倒计时注入的宿主边界；核实 2026-10-22。

### 2.5 整文件重写和改动膨胀

**要求局部编辑，把一次性验证脚本放在仓库外。** 改动膨胀包括整文件重写、提交临时脚本和过度设计。

**处理**：
- 整文件重写（结果相同，但更费 token 和时间）：
  > The number of tokens used to edit files is best minimized, all else being equal. Therefore, when it will not affect the end result, try to surgically edit a file rather than rewrite the entire thing.
- 临时测试脚本被提交：“验证脚本放在仓库外（如 `/tmp`），用完删掉；只在任务要求、或仓库本来就为这类改动保留测试时才提交测试，规模参照相邻的测试文件”；
- 过度设计：“不要增加任务不需要的功能、重构或抽象；不要为不可能发生的情况加错误处理”；
- 配合**垂直切片**，按行为、接口与风险确定评审点；100–200 行只是作者参考，不是强制拆分或等待人工批准的门槛（见 [07 第 3.4 节](07-workflows.md#34-大功能的前置设计与垂直切片-)）。

### 2.6 越聊越笨：上下文腐化与压缩丢失

✅ **先区分“历史太长”“压缩后立刻填满”和“必要信息不见了”，不要默认清空。** 在 Claude Code 用 `/context` 查看占用，再选动作：

- **仍在同一任务，只需腾出空间**：用 `/compact <保留重点>`，保留目标、约束和验证结果；不必用交接替代正常压缩。
- **明确出现 auto-compaction thrashing**：按行段／函数读大文件，缩小工具输出，必要时把大文件调查移到子 Agent；再定向压缩。清空后仍复发时，对照 `/context`：`Messages` 最大就查新读入的内容，其他行合计更大就精简启动加载项。
- **任务已换、旧思路需要丢弃，或关键约定已丢**：先核对当前文件和原结果；需要新会话时，只带最新目标、决定、进度和证据。已有任务记录足够就复用，[20 §4](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史)说明应保留什么；`/handoff` 只是本仓模板 Skill，不是原生命令或 `/compact` 的通用替代。

**清理启动负担时，先删冲突和无关材料，必要约束保留。** 近期模型实践与独立 Factory 按需加载支持这一机制；若负担已经小、失败模式也未改变，就不继续删规则。输入节约不等于调试准确率提高。

局限：这些是 Claude Code 当前文档的机制与处置建议，不是所有模型／客户端都适用或已实测有效的恢复保证。

**依据**：[一手] 官方[最佳实践](https://code.claude.com/docs/en/best-practices#manage-context-aggressively)支持定向压缩、[thrashing 排查](https://code.claude.com/docs/en/troubleshooting#auto-compaction-stops-with-a-thrashing-error)指出此时压缩已成功但新输入再次撑满窗口（2026-10-15，UTC+8）；[一手；经验：采用判断] [近期模型实践](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)、[独立 Factory 按需加载](https://factory.com/news/deferred-context-engine)；[经验：采用判断] 清空与交接选择；核实 2026-10-22。

### 2.7 API 幻觉和过时知识

**先核项目实际安装／锁定版本，再给对应头文件、类型定义与版本文档。** 最新网页不一定适合旧依赖，文档服务也要核返回版本。

**处理**：
1. 先核项目实际安装／锁定版本，再给对应头文件、类型定义与版本文档；最新网页不一定适合旧依赖，文档服务也要核返回版本；
2. 写进指令：“**不确定 API 的签名或是否已废弃时，先查项目版本对应的源码与文档，不要凭记忆写**”；
3. 对快速变化的领域（AI 模型、开发工具），Anthropic 的提示是：“**认得一个名字不等于知道它的现状**，部分背景知识恰恰会让过时的回答听起来很权威，所以先搜索”；
4. 编译和类型检查后，还要跑关键返回值、状态变化或副作用的行为检查；签名合法也可能语义错误。

**版本号本身不够，默认补与目标版本相符的用法证据。** LibEvoBench 比较提示版本与提供相关文档，独立的 Qiskit 研究也发现文档修复不能消除全部失败；据此保留运行检查。两者都不是当前完整 coding Agent 的胜负对照。

### 2.8 在同一个错误上打转

✅ **先看重复的是错误思路，还是同一个运行故障。** 同样的失败数可能对应不同处置，先按阶段归因再决定修代码、查入口还是处理授权。

Terminal-Bench 的固定运行分析里，一次改错代码层，一次在工具调用前被安全拦截。Agent 应先把错误与实际读写／调用阶段对上，人再决定修代码、查入口还是处理授权；不要按总分归因给模型能力。

- 多次纠正后仍沿用错误思路：`/clear` 后用更具体的提示，保留“试过什么、为什么不行”；再要求列出可区分的假设，而非继续盲改。
- 压缩后又被大输入撑满：按 [2.6](#26-越聊越笨上下文腐化与压缩丢失)缩小输入或启动负载，不能只反复清空。
- API／工具失败或测试不稳定：先查原错误、验证环境和已有执行结果；外部写入结果未知时，按 [20 §9](20-codex-long-horizon.md#9-超时后动作究竟发生了吗)核对状态再重试。

**模型指出的“第一处错误”先当假设，不直接当回退点。** AgentDebugX 把诊断接到修复重跑；独立前缀续跑研究发现文本归因不一定对应成功概率下降。默认让 Agent 提出可区分原因的观察，人核目标行为后做最小修正；已有日志足够时不加诊断 Agent，新增诊断不能改变下一动作就停止叠加。

**UI 在加载途中出错、最终却正常时，先改观察时机。** 让 Agent 从原 URL 进入，在外部脚本执行前和数据返回前分别核对内容，再检查成功加载及失败恢复；不要继续只修终态样式或延长等待。人先定“此时应显示什么、是否允许旧内容、失败后如何继续”，具体阶段选择见 [23](23-browser-verification.md#首屏短暂失败先验过程再验终态)。已有阶段回归足够就不加服务；新录制若无法关联目标构建或重建原状态，撤回它作为验收依据，保留未验证结论。

**修会话录制故障时，同时保住“该采哪些”的约定。** 让 Agent 在现有回归中走会话管理器→轮转→触发→发送的真实调用链，既检查完整快照确实发出，也检查无交互、卸载与缓存上限分支；只写内部会话 ID 或看到回放 URL 不足以接收。人确认哪些被动访问应该记录，避免为补可观测性而扩大采集和费用。PostHog 的 Claude Code 辅助修复先解决轮转丢录制，后续又修无交互录制的计费行为；这个公开二改反例（详见[研究记录](research/2026-10-13-browser-healing-outcomes.md#p56续补录制可用与采集策略分别验收)）支持保留原采集策略，直到新旧两类断言共同成立。

**告警仍在、后续操作却已成功时，区分当前健康与历史完整性。** 日志曾丢失且尚未补回，就保留用于选择反馈来源的丢失标记；需要显示恢复时，另设当前状态或调整提示，不在下一次成功后直接清零。Codex 的固定实现、恢复测试与用户报告（详见[研究记录](research/2026-10-10-codex-continuity.md#恢复后告警当前可写与历史完整性)）支持这一修法选择；内存回退也可能舍弃旧历史。

**Windows 工具在命令启动前失败时，先查执行器，不继续改项目代码或提示词。** 若错误指向 MXC launcher 的卷枚举，核实际执行的二进制／版本、工作目录与沙箱路径；常量命令也只能在已授权的原环境检查，另一个终端成功不证明该入口正常。公开网络卷修复只收窄隐式读取根的展开，不能把它当作权限不足而直接提权、关闭沙箱或删除映射。**局限：补丁合入不等于已进入所用客户端；所核稳定CLI仍未包含该修复。** 原错误、修复范围和发行边界见[连续性记录](research/2026-10-10-codex-continuity.md#windows启动层补研卷枚举失败不等于命令被拒)。

官方纠偏建议针对同一问题纠正超过两次、失败思路累积的情形推荐清空重来；纠正次数是经验提示，不是故障诊断阈值，不能据此跳过输入与执行状态检查。

**依据**：[一手：上游自动轨迹分析，固定 57fd2b9，未独立复跑] [Terminal-Bench #2114](https://github.com/harbor-framework/terminal-bench/pull/2114#issuecomment-5879421239)；[研究；经验：采用与撤回] [AgentDebugX](https://arxiv.org/html/2607.18754v1)、[独立前缀续跑研究](https://arxiv.org/html/2610.17633v1)；[一手：维护记录／测试；经验：采用判断] PostHog 公开二改反例（见[研究记录](research/2026-10-13-browser-healing-outcomes.md#p56续补录制可用与采集策略分别验收)）；[一手／社区；研究：采用判断，未运行客户端或验证新提示方案] Codex 告警与历史完整性记录（见[研究记录](research/2026-10-10-codex-continuity.md#恢复后告警当前可写与历史完整性)）；[一手／研究] [Codex PR #54363](https://github.com/openai/codex/pull/54363)；[经验：诊断建议] API／工具失败与测试不稳定的排查顺序；[经验：由固定补丁提炼，未运行应用] UI 加载阶段的观察时机；[一手] 官方[纠偏建议](https://code.claude.com/docs/en/best-practices#course-correct-early-and-often)；核实 2026-10-22。

### 2.9 成本暴涨

**先按原因表定位成本去向，再决定删减、分流或设上限。**

| 原因 | 处理 |
|---|---|
| 子 Agent 滥用（同一任务拆给 2 个子 Agent，token 从 12.1 万涨到 51.3 万） | “只在并行或独立的工作流中使用子 Agent；单个文件的读取和顺序操作直接做” |
| 缓存命中下降 | 对照模型/effort、请求前缀、TTL 和代理/模板处理；Claude Code 当前统计入口与口径见 [02](02-models-and-cost.md#2-价格快照api-美元百万-token)，用量面板不能代替根因定位 |
| 指令文件、MCP 太多 | 先核实际加载与成本，删重复／失效指令，只保留当前任务有用的约定与连接，不按固定行数裁剪（见 [03](03-context-engineering.md)） |
| 循环不停 | Ralph 循环设最大迭代次数；托管预算按平台契约设置并留余量：Managed Agents 达限暂停新增模型请求，在途请求及其工具仍可超额，见 [16 §4.5](16-building-agents.md#45-安全与成本) |
| 大量读取或模式化生成占用主模型 | 问题明确且结果可检查时才评估轻量模型分流；包含 worker、重读与返工的总成本无收益就撤回，不能把调试当读文件杂活（见 [02](02-models-and-cost.md#3-订阅额度与成本控制)） |

**经过本地服务或兼容网关时，先定位哪一层改变了请求。** 对同一会话的相邻两次请求，核对客户端消息顺序、服务端规范化结果、模板渲染后的前缀，再对照后端实际缓存计数；只按自己能观察到的层定位。角色序列能缩小范围，完整前缀比较还需要内容；脱敏替换应稳定，避免自己制造差异。oMLX 的固定版本探测（详见[研究记录](research/2026-10-13-omlx-postmerge.md#7-云端独立执行相同测试与实际渲染路径)）中，合成请求只追加 system 提醒，合法降级却把提醒合入开头，改变已有渲染文本；“没有换模型”不能排除这类原因。

**局限**：探测使用上游测试替身，未测真实模型缓存；不能为提高命中率随意把 system 降为 user、丢掉提醒或拆散 tool-call 配对。

#### 会话用量与速度不能混算

先按 [02](02-models-and-cost.md#31-查异常消耗ccusage-只补历史诊断)定位异常会话；ccusage 的 `--speed` 只选计价档，不测生成速度。Codex rollout 的可选计时/用量字段齐全时，可另算含思考、工具与等待的整轮平均 tok/s，ccusage 尚未解析计时字段。**局限**：常规日志没有完整流式 delta，不能恢复纯生成速度；缺字段、error/abort 不补零，TTFT 也不保证是正文首 token。见[计时与落盘证据](research/2026-10-13-session-usage-metrics.md#时间字段确实可以落盘但不是解码计时)。

**依据**：[社区：原文] 子 Agent 成本案例；[一手] Anthropic 针对 Opus 4.6 的子 Agent 提示、Managed Agents 预算契约（见 [16 §4.5](16-building-agents.md#45-安全与成本)）；[经验] 缓存与指令排查、轻量模型分流选择；[经验：确定性探测与排查建议] oMLX 固定版本探测（见[研究记录](research/2026-10-13-omlx-postmerge.md#7-云端独立执行相同测试与实际渲染路径)）；[一手；经验：计量边界，2026-10-13] 会话用量与速度口径（见[计时与落盘证据](research/2026-10-13-session-usage-metrics.md#时间字段确实可以落盘但不是解码计时)）；核实 2026-10-22。

### 2.10 破坏性操作

**先把权限、沙箱和可恢复性设好，再用提示补充。** 2025-07，Replit 的 AI Agent 删除了一家公司的生产数据库，CEO 公开道歉。

**处理**（环境边界优先，见 [10](10-security.md)）：
1. Agent 用的凭证**没有删除生产数据的权限**；生产环境和开发环境的凭证分开；
2. 沙箱和出网白名单；`permissions.deny` 拦截 `rm -rf`、`DROP`、`terraform destroy` 这类命令；
3. 一切可恢复：版本控制、数据库备份、可回滚的部署；
4. 提示层面：“改变系统状态之前，确认证据支持这个具体动作；**看起来像已知故障的信号，可能有别的原因**”。提示只是补充，不能代替前三条。

### 2.11 输出难读

**要求先说结果；长时间无人值守后的总结重新交代背景。**

- “**先说结果**：完成后的第一句话回答‘发生了什么’或‘发现了什么’；可读比简短更重要，靠选择内容来变短，而不是把句子压缩成碎片”；
- 长时间无人值守后的总结要“重新交代背景”：读者没看到中间过程，先说结果，再说需要他做的一两件事；
- 统一总结格式：**Blocked on me / Changed / Found**（模板已采用）。

### 2.12 正常请求被拒绝

✅ **先判断是哪一层拒绝，不要先改提示或换模型。** 保留客户端版本、原始错误和 request ID；不要把密钥或私人请求正文贴到公开 issue。

- **工具调用被权限／沙箱拒绝**：检查具体动作、路径与 `/permissions`，由有权的人决定是否授予必要权限；提示词不能改写客户端权限，不用改命令拼写或切换工具绕过。见 [10](10-security.md)。
- **API 返回 HTTP 错误或流式 error 事件**：先读错误类型、消息与响应头，不按状态码盲重试。400 除请求格式／内容错误，也可能是组织或 workspace 花费上限；402 查账单／支付，401／403 查身份和资源权限。429 可能是短期限流、月度花费上限或 Claude Code workspace 花费上限；月度上限型没有 `retry-after`，须恢复额度，退避无效。仅短期限流／临时 5xx 走有界退避；HTTP 200 后也可能出现流式 error。
- **确为模型拒答**：Claude API 的 `stop_reason: "refusal"` 与以上两类不同。先读 `stop_details`，澄清合法任务的目的与范围；不要把拒答自动判成误报。若请求要求披露完整内部推理，改为要求结论、证据或简短解释，而非反复换模型。

**需要服务连续性时，再选对应回退机制。** Claude API 的拒答 `fallbacks` 与 Claude Code CLI 的 `--fallback-model` 不是同一触发器：前者处理分类器拒答，后者处理模型过载／不可用。先核接入平台、模型与请求特性支持，再按服务商允许的方式回退，并检查最终拒答状态与实际返回模型。

局限：回退可能仍被拒或失败，也不能替代权限授权与内容安全要求；这些是当前 Claude 文档的协议边界，未做真实请求复测。平台限制与反例见[研究记录](research/2026-10-12-development-conditions.md#拒绝诊断先区分权限模型与服务故障)。

**依据**：[一手] [权限机制](https://code.claude.com/docs/en/permissions#manage-permissions)、[错误契约](https://platform.claude.com/docs/en/api/errors)（2026-10-22）、[拒答处理](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback)、[API 回退](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback#server-side-fallback)、[CLI 参数](https://code.claude.com/docs/en/cli-reference#cli-flags)；[经验] 处理顺序、诊断建议与回退选择；核实 2026-10-22。

### 2.13 一次读取失败就判断整体不可用

✅ **先定位失败的是哪条路径，再判断缺不缺能力。** 检查当前环境实际提供的入口：能力未暴露就核支持范围；调用失败就查执行结果；目标页面返回错误就按页面信号处理。抓取失败且没有明确访问禁令时，可用已有、受支持的正常公开 GET 或浏览器读取同一公开 URL，先确认结果确实包含所需正文；HTTP 200 或出现帖子 ID 不等于读到了完整内容，浏览器还可核对原文、刷新复测；遇登录、验证码或权限阻塞则按要求处理，不通过换身份、代理或提高权限绕过。单次失败只能落到该次抓取路径，不能写成“X 整体不可读”。

局限：单次环境观察不保证其他账号、地区或时点可复现，也不足以确定 403 的根因。

若任务已经产生外部副作用或涉及中断续接，继续按 [20](20-codex-long-horizon.md#9-超时后动作究竟发生了吗)核对实际结果，不把“换一条读取路径”推广为重新发布、重新调度或重跑写入。

**依据**：[经验：实际观察] 2026-10-15 [dot 云端现场观察](research/2026-10-12-development-conditions.md#dot-实际能力诊断公开网页读取的路径差异)：同一组 X 公开 URL 的抓取返回 403，Chrome 却直接读到原帖且刷新成功，未经过登录或验证码；[经验：诊断与采用建议] 路径区分与浏览器复核；[经验：适用边界] 外部副作用与中断续接；核实 2026-10-22。

## 3. 一份可以直接放进 CLAUDE.md 的“防跑偏”片段

**把下面的片段放进 `CLAUDE.md`，作为防止跑偏的默认规则；能用 Hook、lint 或测试强制的规则，优先放到那一层。**

```markdown
## 工作方式
- 在已授权、范围明确的任务内继续做；缺必要权限、关键业务判断或遇到破坏性操作、范围变化时先确认。可逆不代表已获授权。
- 已授权范围内的小决定（命名、格式、等价方案）自己选并注明；发现关键歧义先澄清，不用自主提示掩盖缺失决定。
- 发现任务以外的问题，列在总结的“后续事项”里，不要在这次改动里修。
- 不要为了通过测试而修改测试；测试本身有错时说明理由。
- 不确定 API 时先核项目安装／锁定版本，再查该版本源码与文档，并验证关键行为。
- 小改动用局部编辑，不要重写整个文件；一次性临时探针可放仓库外，项目需要的回归测试和检查脚本按既有惯例保留。
- 汇报进度时每条都要有本次会话的工具结果作为证据；未验证的明确说出来。
- 总结用三个标题：Blocked on me / Changed / Found。
```
