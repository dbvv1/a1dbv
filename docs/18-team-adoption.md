# 18 · 团队落地与治理

> 更新：2026-10-20（UTC+8；补 Agent 更新前端时的旧会话验收输入）
> 面向**在团队或公司推广 AI coding 的人**：推进路线、准入规则、成本、效果与人的成长。
> 依据：
> - 厂商文档 [一手]：Claude Code changelog 和文档、Claude API 官方 Skill 中的 Admin API 和数据保留说明、OpenAI DevDay 2026 企业功能；
> - 研究和报告 [研究 / 一手：厂商报告]：METR、Faros、GitClear；
> - 实践者文章和社区讨论 [社区]。

## 1. 先看结论

1. **按实际缺口推进**：先让任务有可运行反馈；按收益／成本加并行、Skill 或自动评审，不按安装阶段推进（见 [14 第 8 节](14-synthesis.md#8-成熟度路线)）。
2. **规则写在仓库里、像代码一样评审**：AGENTS.md、`.claude/settings.json`、Skill、Hook 进版本控制；组织策略托管下发，核组织、入口与执行边界（见 §4）。
3. **成本可归属，停用规则按实际风险决定**：按全任务投入／收益设预算、提醒与必要停用条件，核覆盖和停用影响，不凭其他公司新闻统一降档／设硬上限，见§5。[研究]
4. **衡量结果而不是产出**：METR 历史实验的实测与自评方向相反，不能用主观感受代替测量或预测当前团队收益，见 [11 的证据范围](11-community-pulse.md#4-生产力证据来源范围见各行)。[研究：原文]。
5. **代码的责任人永远是提交的人**：Godot 基金会在[政策公告](https://godotengine.org/article/contribution-policy-2026/)中强调贡献者须承担后续解释与修复责任 [一手：项目立场]。

## 2. 推广路线

以下仅为试点参考；单 Agent 满足交付目标就可长期保持。[经验]

| 阶段 | 目标 | 进入下一阶段的条件 | 常见失败 |
|---|---|---|---|
| **0. 试点** | 2–5 名志愿者用真实任务记录适用性 | 列出适合／不适合 AI 的任务 | 让最不情愿的人先用；只在玩具任务上试 |
| **1. 基础设施** | 可靠测试／构建／lint、AGENTS.md 和保护规则 | Agent 能在每个仓库里自己跑通验证 | 无测试却称 Agent 做完 |
| **2. 推广** | 全员可用；培训验证／切片／评审，共享 Skill／插件 | 评审时间和缺陷率没有恶化 | 只发账号不教方法；没有评审规范 |
| **3. 自动化** | CI 自动评审／升级／补测试，后台／云端 Agent | 成本可归属、有预算，PR 质量可控 | 自动化 PR 淹没评审者 |
| **4. 目标驱动的循环** | 只在验证器锐利的模块尝试“软件工厂”式循环 | 有可观测的指标和快速回滚 | 在可维护性没有保障的模块上“熄灯” |

Will Larson 的 Imprint 路线是依赖各环节配合的案例，不是通用前置条件。[社区：原文]

## 3. 准入与数据政策

| 问题 | 建议 |
|---|---|
| **允许用哪些 Agent 和插件** | 维护允许清单；闭源行为可能需逆向核实（隐写标记事件），开源也查遥测／自更新（DeepSeek Harness 桌面版默认遥测）[社区] |
| **哪些数据可以发给云端模型** | 区分公开／内部代码、客户数据与密钥；密钥留在获准认证边界。Read deny 不覆盖任意子进程间接读取，凭证代理不保证绝对保密，按 [10](10-security.md#3-防护原则) 核实际入口与隔离。[一手；经验] |
| **数据保留** | ✅ 按实际登录组织、服务入口、模型和功能放行；商业条款下默认不训练不等于零保留，购买 Enterprise 也不自动启用 ZDR。见下方已核边界 [一手；研究] |
| **数据驻留** | 分别核存储、推理、端点／第三方地区；Anthropic `inference_geo`（`us`／`global`）与 workspace geo 分开。OpenAI GPT-6.1 Sol 的 US／EU 支持仍受组织、协议及项目／端点约束，见下方 [一手；研究] |
| **隐私预期** | 2026-10，Anthropic 向警方报告了用户对话中的威胁内容，HN 上的提醒是“你不是在和秘密好友聊天” [社区]。敏感内容不要放进云端对话 |
| **本地模型** | 强合规先核模型、harness、搜索／MCP、遥测外发；再按量化、上下文与任务比本地／自托管质量和总成本，不预设能力差距（见 [02 第 5 节](02-models-and-cost.md#5-本地--开源权重模型)）。[研究] |

**地区边界（2026-10-15，UTC+8 核对）**：[Anthropic 官方](https://platform.claude.com/docs/en/manage-claude/data-residency)当前 workspace geo 仅有 US，US-only 推理按标准 token 费率的 1.1 倍计费；`inference_geo` 不能配置 EU 驻留。[OpenAI 官方](https://developers.openai.com/api/docs/guides/your-data)要求非 US 地区获批滥用监控控制并签适用的 Modified Retention amendment，按实际模型、端点和功能核地区支持。**局限：这些 API 条件不能直接外推到聊天产品、整个 Agent 工具链或第三方处理；不替代自身合同审核。** [一手；研究]

### 需要零保留时，先选可覆盖的工作方式

**✅ 若组织要求 ZDR，先核准入再传内部数据，不为使用新模型直接放宽保留。** 2026-10-15（UTC+8）核对的 Anthropic 官方边界如下：

- **本地 Claude Code**：商业 API key 的 API ZDR 与 Enterprise Code ZDR 分属两种安排，均须实际组织已启用，个人／另一组织不能继承。后者可托管登录组织，但不覆盖 claude.ai Chat、Cowork、第三方 MCP，禁用云端会话／Remote Control。[一手：[Code ZDR](https://code.claude.com/docs/en/zero-data-retention)、[Privacy Center](https://privacy.claude.com/en/articles/8956058-i-have-a-zero-data-retention-agreement-with-anthropic-what-products-does-it-apply-to)]
- **API 自动化**：按端点／功能核资格；Files、Batch、服务端 code execution 等不在 ZDR 内却未必自动拒绝请求。零保留任务须避开，成功不代表合规。[一手：[API 数据保留](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)；研究]
- **Covered Models**：Fable 5／5.1 等默认至少保留30天，第三方云不自动豁免；合资格内部业务有临时 ZDR 过渡，须自身组织明确授权，非长期通用权限。无授权又不能接受保留就选现有 ZDR 下可用模型。[一手：[2026-09-01 Covered Models 政策](https://support.claude.com/en/articles/15425695-covered-models)；研究]

**局限：ZDR 不是所有数据都不留存的承诺，仍有本地记录、管理数据、第三方处理及法律／安全例外；换组织、模型或功能时重核。** [来源、反证与复核触发](research/2026-10-13-cloud-spend-boundaries.md#补充团队准入的数据保留边界)保留完整范围；本轮不替代具体合同审核。[一手；研究]

### 模型与输出许可

**✅ 引入模型或生成内容时，按实际用途分开核对代码、权重与输出许可。** 准入记录写明版本／计划、输入及依赖授权、地域、营收／主体、署名与终止条件；云服务按适用合同核查。代码可商用不自动放行权重，输出可商用不能反推模型可用于商业生产。[游戏授权核查](research/2026-10-14-game-wp1-licensing.md)与[阶段 F 图像复核](research/2026-10-14-game-wp2-2d-assets.md#9-阶段-f-b图像动态事实表)有具体反例；2026-10-14 重读的 [FLUX.2-klein-9B 许可 §2](https://huggingface.co/black-forest-labs/FLUX.2-klein-9B/blob/main/LICENSE.md)仍分别约束模型用途与输出。**局限：分层核查是准入依据，不保证输出独占、不侵权或接收平台批准。** [一手：许可原文；经验]

## 4. 配置治理

| 层级 | 放什么 | 机制 |
|---|---|---|
| **组织级**（策略） | 禁止的命令、网络限制、允许的插件来源、沙箱设置 | Claude Code 的托管设置（managed settings / policy，Team 和 Enterprise 由组织下发）；Codex 的托管配置和 **Agent Security**（统一管控本地和云端执行时的工具、文件和网络访问）[一手] |
| **仓库级**（共享） | AGENTS.md、`.claude/settings.json`、Skill、Hook、插件启用列表 | 进版本控制，**像代码一样评审**；插件可以锁定到某个提交 |
| **个人级** | 个人偏好、快捷键、输出风格 | `~/.claude`、`settings.local.json`（不提交） |

**托管下发不等于安全边界（2026-10-15，UTC+8 核对）**：Claude 的 [server-managed settings](https://code.claude.com/docs/en/server-managed-settings)按实际认证的 Team／Enterprise 组织分发，Console API key CI 不继承 claude.ai 策略；强制约束须核入口并落实到受管端点、沙箱和网络（见 [10](10-security.md)）。**局限：服务端分发仍是客户端控制，未受管设备可绕过；第三方入口另核策略交付方式。** [一手；研究]

**配置迁移保住作用范围。** 先用现成分层、优先级与选择性同步：共享格式／检查契约，允许个人编辑体验不同；跨设备偏好与本机衍生值分开，不广播个人覆盖或机器默认。[Ruff、Firefox 与 Prettier 的取舍](research/2026-10-12-development-conditions.md#配置迁移保留作用阶段与设备边界)支持按语义选择；局部历史反馈不证明所有配置都应同步或隔离。[一手／社区；经验]

**维护节奏**：模型或宿主升级后，只试撤无必要的可选步骤，比较行为、质量与总投入并保留恢复路径；保留稳定契约与必要回归。官方提示审计和 Claude Code `/skill-doctor` 只提供候选／调用／成本线索，少用不等于无效。方法与命令范围见 [09 §3–4](09-review-and-quality.md#3-给自己的-ai-配置做评估)及 [05](05-skills-and-plugins.md)。[一手；研究]

## 5. 成本治理

| 做法 | 说明 |
|---|---|
| **选对计费方式** | 交互开发比较订阅额度与实际投入；CI 和自动化优先比较可归属的 API 计费。订阅赠额按下方运行入口与超额规则核算 [一手；研究] |
| **按项目和人归属** | 项目分 API Key／工作区；Code 用 OpenTelemetry，Anthropic Admin API 管成员／工作区／Key／限速，用量成本报告须直接调 HTTP [一手] |
| **预算与停用边界** | 云服务配置适用的 spend limit / spend cap，并确认超限后的停用行为；托管 Agent 按会话设美元上限；Ralph 循环设最大迭代次数 |
| **按任务算成本** | 衡量“完成一个任务花多少”，而不是单次请求的价格 |
| **先定位负担** | 查缓存、无用指令／工具；明确且可验任务再比轻量模型分流，worker 计入全任务质量、等待与总成本（见 [02](02-models-and-cost.md#3-订阅额度与成本控制)、[17 第 2.9 节](17-troubleshooting.md#29-成本暴涨)） |

**订阅赠额按运行入口核算（2026-10-15，UTC+8 核对）**：[官方资格说明](https://support.claude.com/en/articles/17154008-monthly-api-credits-for-max-and-team-plans)保留 Max 5x／20x 每月 100／200 美元、Team 按席位共享最多 500 美元；须合资格订阅满七天、关联单个 Console 组织；该组织 key 自行运行的 `claude -p`／Agent SDK 可覆盖，交互 Code、GitHub Action、IDE／桌面 Code 及第三方云不覆盖。**局限：赠额不结转，也不是账单上限；耗尽后仍可能消耗已购余额、自动充值或按发票计费。** [研究记录](research/2026-10-13-cloud-spend-boundaries.md#补充地区策略交付与订阅赠额)保存具体条件与反证。[一手；研究]

**云预算要区分产品与范围**（2026-10-13 核对）：AWS 新体验 Paid Plan 项目的 spend limit 提供月度税前费用上限；GCP 原生 spend cap 在单个项目的合资格服务上阻止新增用量。采用前确认覆盖范围、停用后果和恢复安排，详见[官方来源核对](research/2026-10-13-cloud-spend-boundaries.md)。[一手：AWS、Google Cloud；研究]

**局限**：这些能力不能推广为所有账户和服务通用的账单封顶；尤其 GCP 的延迟超额、执行中请求和持续固定费用仍可能计费。

## 6. 怎么衡量效果

| 衡量 ✅ | 不要只看 ⚠️ | 原因 |
|---|---|---|
| 交付周期（从开始到上线） | 代码行数、PR 数 | AI 让产出变便宜，数量指标会虚高 |
| 变更失败率、事故率、缺陷逃逸率 | token 用量 | Faros 的观察性结果提示同时看可靠性与评审负担；定义和倍数见 [09](09-review-and-quality.md#1-质量数据ai-代码的真实代价)，不作本团队预测。[一手：厂商公开资料，观察性] |
| 评审时间、返工率、PR 体积 | 开发者自评的提速 | METR：主观感受和实测方向都可能相反 [研究：原文] |
| 重复代码、重构比例 | 测试覆盖率 | GitClear 公开材料只作抽检线索；移动占比不等于全部重构量，不设固定配额，见 [09](09-review-and-quality.md) [一手／研究] |

这些结果支持同时跟踪交付、评审和可靠性，不能预测本团队会恶化多少，也未证明某项治理措施有效。

**做法**：
- 在固定的任务集上做小规模对比（同一批任务，用和不用，或新旧配置）；
- 看趋势，不看单点；把指标和团队一起解读，不用来考核个人。

🧪 **交接试点让下一位维护者完成真实小变更，分记熟悉环境、理解、修改与返工投入。** 按行为验证与耗时决定是否补解释或缩小范围。耗时比较注明有效计时人数、来源与排除规则，不用成功提交者耗时代表完成率，见[固定数据复算](research/2026-10-13-immich-handover.md#公开数据复算计时分母与来源)。[Echoes of AI](research/2026-10-13-immich-handover.md#补充证据接管后实际修改的受控实验)未检出明确时间差异；小任务的不确定估计不证明长期维护等价或试点有效。[研究：原文；经验：试用建议与复算]

## 7. 评审与协作规范

以下按接收者当前任务查用，不要求逐项完成；PR 准入与协作约定在本节末尾。

### 首次启动：从实际宿主和目标环境验收

**安装、启动或构建通过后，按接收方实际用法验收：**

| 交接问题 | 采用／验收动作 | 主要依据与关键局限 |
|---|---|---|
| **终端成功，桌面集成也通过了吗？** | 从实际宿主入口验收，注明包装和权限上下文；分清 OS 拒绝与应用安全检查，不一律重置权限 | [CBM 宿主对照](research/2026-10-13-immich-handover.md#接收入口增量同机终端成功仍未验收桌面宿主)：终端与 MSIX 宿主结果不同；跨版本恢复自报不能归因于单补丁或证明安全性／全部业务。[社区：接收者报告；研究] |
| **构建通过，接收环境能加载吗？** | 含原生依赖时写清系统／架构／运行库，复用发布检查，在目标环境验最终产物加载和关键功能；读嵌套原因区分缺包与无法加载，再修解析或构建配置，不默认删锁文件重装 | [Rollup 维护链](research/2026-10-13-immich-handover.md#补充证据构建成功与接收环境的原生依赖)仅特定 Linux 原生包案例，静态符号检查不替代目标环境运行。[一手：固定源码与 CI；社区：用户报告；经验] |

### 识别权威版本：以实际采用的补丁和交付产物为准

在已有 PR 中写清最终方案、理由及未验证场景，更新被后续补丁推翻的解释。[Immich 两轮修改](research/2026-10-13-immich-handover.md)能核对意见与代码，但未量化接收成本收益。[一手：审查与补丁；研究]

| 交接问题 | 采用／验收动作 | 主要依据与关键局限 |
|---|---|---|
| **上游停止发行，接管构建就够了吗？** | 分清缺二进制发行还是源码维护；前者评估窄构建接管，后者先明确修复来源，再决定保留、换源或缩小支持。镜像日期、标签和构建成功不代替修复来源与宿主验收 | [MinIO接管链](research/2026-10-13-immich-handover.md#补充证据接管构建不等于接管源码维护)：只核停发／停维护声明、固定实现及宿主差异自报，不推荐该镜像或证明持续维护。[一手／社区；研究] |
| **上游已修，下游能直接交付吗？** | 按接收方包装、工具链配置和下游补丁组合重建；旧补丁失配先核上下文及剩余职责。报告真实命令与固定版本，分开构建、启动和核心业务验收 | [Handy Nix/Darwin 接收链](research/2026-10-13-handy-retest-adoption.md#接收方重建上游修复还要穿过下游包装)仅局部运行自报，普通构建不能记成指定验收工具已运行。[一手：固定补丁；社区：回执；研究] |

### 理解必要取舍：能解释最终行为，也核对修复依据

**作者对代码负责**：应能解释行为变化、设计取舍、风险与验证依据；权限、持久数据、接口及后续维护边界须定向走读，关键依据不清时不合并，不统一要求逐行讲解，见 [14](14-synthesis.md#74-人的注意力花在哪里)；

**接管持久化临时绕过的补丁前，核原故障阶段、实际参数与补丁范围。** 参数未启用或补丁仅影响故障后的阶段，测试通过也不能证明原问题已修；独立需求另验。 [Anaconda 的接收与撤回](research/2026-10-13-immich-handover.md#补充证据解释完整仍须核对原故障阶段)仅一次维护链，AI 归属仍为维护者怀疑，不证明安全事故或长期维护收益。[一手／社区；研究]

### 完成下一修改：决定保留、替换或删除哪些实现

| 交接问题 | 采用／验收动作 | 主要依据与关键局限 |
|---|---|---|
| **职责已交给依赖，旧实现能删吗？** | 核最低支持版本、保存后恢复及删掉的公开接口；[本地退出条件误判](research/2026-10-12-development-conditions.md#上游接管后的退出条件aiohttp-误判修复版本)时，先修判定、保留受影响环境的补偿；删除旧层仍保留异常诊断和预算决策 | [Pydantic AI 下游接管](research/2026-10-12-development-conditions.md#接收者接下来做了什么删除补偿层而非恢复旧测试期待)仅历史确定性框架测试；真实重启、外部旧导入迁移未验，跨仓说明未全同步。[一手：源码与 CI；研究] |
| **已有用户收益，可以替换旧功能吗？** | 🧪 按使用场景限定试用；旧平台与设置迁移未覆盖时，先做局部补充，不用新交互替换全部旧路径。新增权限与原生依赖也计入采用条件 | [Handy 暂停／降音量比较](research/2026-10-13-handy-retest-adoption.md#体验升级局部补充还是替换旧功能)：暂停已有非作者使用；两份降音量 PR 均未合并，固定实现不等于运行验收或授予权限的建议。[一手：固定源码；社区：反馈；研究] |

交接是否足以支持真实小变更，可按[§6 的接管试点](#6-怎么衡量效果)观察熟悉环境、理解、修改与返工投入；该试点本身尚未证明有效。

### Agent 交付桌面更新：先保住旧工作

**✅ 旧入口或恢复未证时，默认同安装身份的人工包与明确延期。** 给 Agent 旧安装、锁文件和未完成工作，先修保存／停机结果，再考虑受支持的稳定更新器。

- **编辑器**：Agent逐文档核保存结果与revision；取消、写失败或再编辑即撤销全窗退出。人定不可丢全文与草稿承诺。
- **托盘后台**：Agent冻结队列入口、保运行／暂停／取消意图，等待保存和进程退出；恢复未知就延期。人定可中断粒度与权限。

**⛔ Promise完成、会话存在、安装器启动都不是交付完成。** 恢复不符或下一跳不可达即撤回自动更新；部分安装失败须保数据、核实际版本并走可信修复，不保证旧版可继续。

见[两份任务包](research/2026-10-13-immich-handover.md#agent桌面原型的连续交付项目提议2026-10-20)。旧样本仅作兼容研究，非2026推荐；原生更新与AI净收益未测。[一手；研究]

### Agent 更新前端：先给旧用户的验收输入

**✅ 首次交付没有旧用户时，本项沿用新用户路径。已有用户的更新，给 Agent 发布前已开始的任务及实际部署入口，要求验旧页继续操作，而不只打开新版页面。**

- **状态允许丢弃**：可沿用框架恢复／安全刷新；仅缺旧静态资源时优先保留不可变资源，不默认自建 Service Worker。
- **草稿或进行中任务不可丢**：让 Agent 盘点请求与状态、核原生锁版覆盖，准备保存／恢复与安全换版回归；人定不可丢内容和安全更新优先级。保护期限或请求覆盖不足时缩小承诺。

[两条维护链](research/2026-10-12-development-feedback.md#agent更新前端旧会话是验收输入)解释新页检查的缺口，非 Agent 失败率证据。按[23](23-browser-verification.md#5-浏览器状态也是测试输入)分核原始版本、实际路由和用户写入；检测后刷新不等于保住旧工作。[一手／社区；研究，未做客户端或模型实测]

### 失败恢复：按入口、实例权限和数据产物查用

**迁移／恢复先定目标，再验数据和运行状态：**

| 交接问题 | 采用／验收动作 | 主要依据与关键局限 |
|---|---|---|
| **绕过问题后成功，算修好了吗？** | 回到原接收者的原触发条件复测；错误说明写清被拒对象和规则，安全边界改变由维护者决定 | [CBM 原用户复测](research/2026-10-13-immich-handover.md#补充证据原用户恢复原触发条件后升级成功)仅单一 WSL2 用户恢复原条件后的自报，不代表全部客户端或安全性已验证。[社区：复测；一手：固定补丁；经验] |
| **恢复入口失败，要重做全量吗？** | 分清入口／参数与归档／版本问题；受支持窄通道覆盖所需组件就先补操作、验结果。长期图形用户须修入口，不覆盖必要能力才缩承诺／换方案 | [Home Assistant 两条恢复路径](research/2026-10-13-immich-handover.md#补充证据恢复入口失败先保住所需恢复范围)：回执仅无业务数据的 AirCast 插件，不证明完整实例恢复。[一手／社区；研究] |
| **接替旧实例，还是保留旧实例试用？** | 分别决定凭据、身份与业务／进度数据保留；接替按产品机制退旧实例，并存的新身份不代表数据隔离。身份／凭据／配对按授权，不一律重建 | [两种恢复目标的回执](research/2026-10-13-immich-handover.md#补充证据接替恢复与并存试用的身份取舍)：历史自报与固定实现不证明跨实例互斥或 AI 净收益。[社区：回执；一手：源码；研究] |
| **恢复到新实例后，能直接交给 Agent 吗？** | 先复用原生恢复，再核并隔离对源库和恢复归档的写权限，才开放任意执行能力；隔离做不到时保持受限操作路径 | [Railway 恢复凭据修订](research/2026-10-13-immich-handover.md#恢复副本的归档写权限)新实例、恢复程序只读均不等于凭据只读；仅官方契约与固定修订，未做真实恢复实测。[一手；研究] |
| **空库能重建，已有库也能升级吗？** | 分验两条路径；压缩迁移保留必要初始数据、实例配置及防重复初始化的执行身份，写清不迁移数据与失败恢复状态。复用测试验业务读写／登录，不只看退出码 | [PocketBase 接收者升级](research/2026-10-13-immich-handover.md#补充证据结构快照不能代替已有数据的升级交接)：结构快照可能漏业务记录／实例配置，回退函数可能为空操作；历史源码和单一回执不是通用恢复步骤。[一手：源码；社区：回执；研究] |
| **恢复后能登录，旧数据就回来了吗？** | 验已知旧记录及文件，不只验新建／登录；空数据先核目标、备份和原状态再决定重导／清空。分清容器名、逻辑库名与卷，按备份版本选命令 | [Immich 恢复重试](research/2026-10-13-immich-handover.md#补充证据恢复成功但应用连接了另一数据库)仅单一回执；原库是否曾删除仍未知，不能断言恢复本可省略。[社区：前后回执；一手：固定配置与当前文档；经验] |
| **重建命令跑过，旧对象为什么仍不能修改？** | 按数据库清单重建须在清单／目标配置恢复后执行；优先原生维护入口，再验旧对象写入，不默认新写批修或重导全库 | [Gitea 恢复顺序与原生入口](research/2026-10-13-immich-handover.md#补充证据派生入口重建依赖恢复后的对象清单)：两次历史自报，非同一完整验收；未测总投入或 AI 收益。[社区：回执；一手：固定源码；研究] |
| **新对象成功，原失败对象也恢复了吗？** | 保原失败对象，在接收环境重试并开／下载文件；已同步、duplicate 或成功不证明实体可用，确认副本前不据标记删原件 | [Immich旧失败照片回执](research/2026-10-13-immich-handover.md#补充证据新对象通过不等于原失败对象已恢复)：后续错误补偿不清理历史残留；仅同一操作者报告，非跨人接管或 AI 收益证据。[社区／一手／研究] |

**修复版仍失败，先确认有没有进入新逻辑。** 若持久失败状态挡住重试，交付应补上保住原数据、按产品支持路径重新进入恢复流程的办法，而非默认清标记或全量重置。[Nextcloud AIO 原用户重试](research/2026-10-13-immich-handover.md#补充证据修复逻辑前的持久失败守卫)回执未报告完整旧数据验收。[一手／社区；研究]

**交付双向同步脚本，先选保留历史的恢复，还是重建双方文件基线。** 已有可信同步历史时，优先用受支持的恢复路径；首次初始化或历史不可用时，另定重建保留规则并预览差异。[rclone 维护链](research/2026-10-13-immich-handover.md#补充证据双向同步中断后恢复还是重建基线)显示，自动重建可能复活已删除文件、覆盖另一侧更新版本。正常运行后持续冲突则先核状态记录缺陷，别用固定偏向某侧掩盖错误。同步历史不是备份；这些具体机制不外推其他工具，后续完整可靠性仍未验证。[一手／社区；研究]

**导出器修复不等于旧备份已修复。** 确认导出覆盖关联文件后，保留现有备份，从完好来源生成独立新产物并核记录与文件对应；升级接收端或重压旧目录不能补回覆盖内容。允许重建派生件时可保留原件重建，但不等于恢复原字节。[Paperless 维护链](research/2026-10-13-immich-handover.md#补充证据修复导出器不等于修复已存备份)的修复于2026-10-17核实已进入 [v3.3.2](https://github.com/paperless-ngx/paperless-ngx/releases/tag/v3.3.2)，可用该稳定版重新导出；仍无原用户修订后恢复回执。[一手／社区；研究]

### PR 准入与协作约定

1. **PR 应可独立理解与验证**：按行为和依赖切片；100–200 行是实践者参考，不能让机械行数迫使关联改动拆散或新增审批（见 [07 第 3.4 节](07-workflows.md#34-大功能的前置设计与垂直切片-)）；
2. **PR 要附证据**：跑过的命令和结果、截图、手工测试记录。别把没审过的 AI 代码丢给同事 [社区：Willison]；
3. **先确认贡献准入，再说明 AI 参与程度**：团队内部约定披露；对外按接收渠道核对。Godot 禁止实质 AI 代码、代理代投和 AI 生成人际沟通，有限补全附条件允许；披露不代替准入，见[政策与关闭案例](research/2026-10-13-godot-contribution-policy.md)。[一手；经验]；
4. **按验收与整合能力安排并行**：独立只读调查可交回来源核对，可执行任务提供相应检查；涉及人工决定的部分仍需留出真实审阅能力，不用一个人数上限覆盖所有任务（见 [14 规律三](14-synthesis.md#3-规律三按实际接收能力安排产出)）。

## 8. 人的成长

| 风险 | 表现 | 应对 |
|---|---|---|
| **技能退化** | 有人发现“连一个很小的项目都突然想不清架构”；团队里出现“离开 AI 就定位不了问题，说不清组件的输入输出” [社区：HN、V2EX] | 关键模块保持亲手写、亲手读；定期“无 AI”的设计讨论；有人用间隔重复的工具专门对抗这种退化 [社区] |
| **新人成长 / 陌生模块学习** | 完成当前任务后，还需确认能否运用新概念 | 🧪 以学习为目标时，可在按需提问、解释后，选一个相关小变更由学习者自己修改并测试，先不让 AI 直接给出完整补丁；卡住再求助，观察正确性、所需提示和投入。不把此练习设为日常交付必经步骤。[经验：试用建议] |
| **职业倦怠** | “Agent 不在干活就觉得浪费时间”的焦虑 [社区] | 不以 token 或并行数衡量人；按自己的交付、返工和主动投入比较，不设未经测量的提速倍数目标 |
| **乐趣和认同** | 社区两极分化：有人觉得讨厌的部分消失了，有人觉得编程不再好玩 [社区] | 允许个人选择 AI 的参与程度；把 AI 当结对伙伴而不是代写 |

[现有学习实验](research/2026-10-13-immich-handover.md#补充证据陌生模块学习与下一次修改)尚未证明这一练习本身能提升职业开发者的后续维护能力。[研究]

## 9. 检查清单

**组织**
- [ ] 允许使用的 Agent、模型和插件清单
- [ ] 数据分级：哪些代码和数据可以发给哪些服务
- [ ] 托管设置：核认证组织、部署入口及实际执行边界，再配置命令、网络和插件来源限制
- [ ] 成本：按项目归属、预算与停用边界、月度复盘
- [ ] 度量：交付周期、事故率、评审时间的基线

**每个仓库**
- [ ] 测试、构建、lint 命令能一键运行
- [ ] 项目指令保留有用的定位与行为边界，删重复／失效内容并核目标客户端加载，不按行数或“能否猜到”一刀切（见 [03](03-context-engineering.md)）
- [ ] 保护规则（生成目录、密钥、迁移脚本）
- [ ] 评审规范：PR 大小、证据要求

**每个人**
- [ ] 会用验证闭环：让 Agent 自己跑检查并出示证据
- [ ] 会用垂直切片：按未决需求与接口决定设计深度，逐片验证可运行路径（见 [15 §3](15-task-playbooks.md)）
- [ ] 知道什么时候不用 AI（见 [15](15-task-playbooks.md)、[14 第 7.1 节](14-synthesis.md#71-这个任务该给-agent-多大自主权)）
