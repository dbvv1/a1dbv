# 18 · 团队落地与治理

> 更新：2026-10-20（UTC+8；本次仅同步凭证准入边界）
> 面向**在团队或公司推广 AI coding 的人**：推进路线、准入规则、成本、效果与人的成长。
> 依据：
> - 厂商文档 **[一手]**：Claude Code changelog 和文档、Claude API 官方 Skill 中的 Admin API 和数据保留说明、OpenAI DevDay 2026 企业功能；
> - 研究和报告 **[研究 / 一手：厂商报告]**：METR、Faros、GitClear；
> - 实践者文章和社区讨论 **[社区]**。

## 1. 先看结论

1. **按实际缺口推进**：先让当前任务有可运行反馈；是否增加并行、Skill 或自动评审，由任务收益与成本决定，不要求依次通过工具安装阶段（见 [14 第 8 节](14-synthesis.md#8-成熟度路线)）。
2. **规则写在仓库里、像代码一样评审**：AGENTS.md、`.claude/settings.json`、Skill、Hook 进版本控制；组织级策略用托管配置下发，并核实际组织、入口与执行边界（见 §4）。
3. **成本可归属，停用规则按实际风险决定**：看完整任务的投入与收益，再设预算、提醒及必要停止条件；先核产品机制覆盖什么、停用会影响什么，不凭其他公司的新闻统一降档或设硬上限，见下文成本治理。**[研究：采用判断]**
4. **衡量结果而不是产出**：主观感受不能代替任务测量。METR 2025 年 2–6 月的资深开源开发者实验中，实测耗时增加 19%，参与者事后却自评提速约 20%；这是历史样本，不能预测当前团队收益，见 [11 的证据范围](11-community-pulse.md#4-生产力证据来源范围见各行)。**[研究：原文]**。
5. **代码的责任人永远是提交的人**：Godot 基金会在[政策公告](https://godotengine.org/article/contribution-policy-2026/)中强调贡献者须承担后续解释与修复责任 **[一手：项目立场]**。

## 2. 推广路线

以下是组织试点的参考顺序，不是每个团队必须逐级通过的成熟度模型；单 Agent 已满足交付目标时可以长期保持。**[经验：采用判断]**

| 阶段 | 目标 | 进入下一阶段的条件 | 常见失败 |
|---|---|---|---|
| **0. 试点** | 2–5 个志愿者在真实任务上使用，记录哪些任务好用、哪些不好用 | 有一份“适合 / 不适合交给 AI 的任务”清单 | 让最不情愿的人先用；只在玩具任务上试 |
| **1. 基础设施** | 每个仓库有可靠的测试、构建、lint 命令；写好 AGENTS.md；统一保护规则 | Agent 能在每个仓库里自己跑通验证 | 没有测试的仓库直接上 Agent，结果“看起来做完了” |
| **2. 推广** | 全员可用；培训“验证闭环、垂直切片、评审规范”；共享 Skill 和插件 | 评审时间和缺陷率没有恶化 | 只发账号不教方法；没有评审规范 |
| **3. 自动化** | CI 中的自动评审、依赖升级、测试补全；后台和云端 Agent | 有成本归属和预算；自动化产出的 PR 质量可控 | 自动化 PR 淹没评审者 |
| **4. 目标驱动的循环** | 只在验证器锐利的模块尝试“软件工厂”式循环 | 有可观测的指标和快速回滚 | 在可维护性没有保障的模块上“熄灯” |

Will Larson 的 Imprint 路线从日常使用扩到多工作区、统一任务状态与编排，再尝试软件工厂；这是依赖各环节配合的实践者案例，不是通用前置条件。**[社区：原文]**

## 3. 准入与数据政策

| 问题 | 建议 |
|---|---|
| **允许用哪些 Agent 和插件** | 维护一份允许清单。闭源 harness 的行为要靠逆向才能知道（隐写标记事件），开源 harness 也要看遥测和自更新机制（DeepSeek Harness 桌面版默认开启遥测）**[社区]** |
| **哪些数据可以发给云端模型** | 按数据分级：公开代码／内部代码／客户数据／密钥。真实密钥留在获准认证边界；Read deny 不覆盖任意子进程的间接读取，凭证代理也不是绝对保密保证，按 [10](10-security.md#3-防护原则) 核实际入口与隔离。**[一手；经验：采用边界]** |
| **数据保留** | ✅ 按实际登录组织、服务入口、模型和功能放行；商业条款下默认不训练不等于零保留，购买 Enterprise 也不自动启用 ZDR。见下方已核边界 **[一手；研究：采用判断]** |
| **数据驻留** | 分别核存储、推理和端点／第三方处理地区，不凭模型或参数支持直接放行。Anthropic 直连 API 的 `inference_geo` 仅有 `us`／`global`，与存储及端点处理的 workspace geo 分开；OpenAI API 的 GPT-6.1 Sol 支持 US／EU，EU 仍需组织资格、适用保留协议与正确项目／端点。见下方地区边界 **[一手；研究：采用判断]** |
| **隐私预期** | 2026-10，Anthropic 向警方报告了用户对话中的威胁内容，HN 上的提醒是“你不是在和秘密好友聊天” **[社区]**。敏感内容不要放进云端对话 |
| **本地模型** | 有强合规要求时，先核模型、harness、搜索／MCP 与遥测的完整外发路径；再按具体量化、上下文和任务比较本地／自托管方案的质量与总成本，不预设统一能力差距（见 [02 第 5 节](02-models-and-cost.md#5-本地--开源权重模型)）。**[研究：采用边界]** |

**地区边界（2026-10-15，UTC+8 核对）**：[Anthropic 官方](https://platform.claude.com/docs/en/manage-claude/data-residency)当前 workspace geo 仅有 US，US-only 推理按标准 token 费率的 1.1 倍计费；`inference_geo` 不能配置 EU 驻留。[OpenAI 官方](https://developers.openai.com/api/docs/guides/your-data)要求非 US 地区获批滥用监控控制并签适用的 Modified Retention amendment，按实际模型、端点和功能核地区支持。**局限：这些 API 条件不能直接外推到聊天产品、整个 Agent 工具链或第三方处理；不替代自身合同审核。** **[一手；研究：采用判断]**

### 需要零保留时，先选可覆盖的工作方式

**✅ 若组织要求 ZDR，先核准入再传内部数据，不为使用新模型直接放宽保留。** 2026-10-15（UTC+8）核对的 Anthropic 官方边界如下：

- **本地 Claude Code**：商业组织 API key 的 API ZDR 与 Enterprise 的 Claude Code ZDR 是两种安排，均须对应组织已获启用；个人账号或另一组织的 key 不能继承。后者可用托管登录设置约束组织，但不覆盖 claude.ai Chat、Cowork 或第三方 MCP；云端会话与 Remote Control 在该安排下禁用。**[一手：[Code ZDR](https://code.claude.com/docs/en/zero-data-retention)、[Privacy Center](https://privacy.claude.com/en/articles/8956058-i-have-a-zero-data-retention-agreement-with-anthropic-what-products-does-it-apply-to)]**
- **API 自动化**：按实际端点与功能核对资格；Files、Batch、服务端 code execution 等不在 ZDR 内，而且不合资格功能并不因此自动拒绝请求。需要零保留的任务应避开这些功能，不能以“请求成功”验收合规。**[一手：[API 数据保留](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)；研究：采用判断]**
- **Covered Models**：Fable 5／5.1 等默认要求至少 30 天保留，换到第三方云不自动豁免；官方有面向合资格内部业务用途的限时 ZDR 过渡安排，须有适用于自身组织的明确授权，不能当长期通用权限。未获授权且不能接受保留时，选现有 ZDR 条件下可用的其他模型。**[一手：[2026-09-01 Covered Models 政策](https://support.claude.com/en/articles/15425695-covered-models)；研究：采用判断]**

**局限：ZDR 不是所有数据都不留存的承诺，仍有本地记录、管理数据、第三方处理及法律／安全例外；换组织、模型或功能时重核。** [来源、反证与复核触发](research/2026-10-13-cloud-spend-boundaries.md#补充团队准入的数据保留边界)保留完整范围；本轮不替代具体合同审核。**[一手；研究]**

### 模型与输出许可

**✅ 引入模型或生成内容时，按实际用途分开核对代码、权重与输出许可。** 在已有准入记录中标明精确版本／服务计划、输入素材与必需依赖的授权，以及会影响部署或交付的地域、营收／主体、署名和终止条件；没有权重开放的云服务按适用服务合同核查。代码可商用不自动放行权重，输出可商用也不能反推模型可用于商业生产。[游戏授权核查](research/2026-10-14-game-wp1-licensing.md)与[阶段 F 图像复核](research/2026-10-14-game-wp2-2d-assets.md#9-阶段-f-b图像动态事实表)提供具体反例；2026-10-14 重读的 [FLUX.2-klein-9B 许可 §2](https://huggingface.co/black-forest-labs/FLUX.2-klein-9B/blob/main/LICENSE.md)仍分别约束模型用途与输出。**局限：分层核查是准入依据，不保证输出独占、不侵权或接收平台批准。** **[一手：许可原文；经验：采用判断]**

## 4. 配置治理

| 层级 | 放什么 | 机制 |
|---|---|---|
| **组织级**（策略） | 禁止的命令、网络限制、允许的插件来源、沙箱设置 | Claude Code 的托管设置（managed settings / policy，Team 和 Enterprise 由组织下发）；Codex 的托管配置和 **Agent Security**（统一管控本地和云端执行时的工具、文件和网络访问）**[一手]** |
| **仓库级**（共享） | AGENTS.md、`.claude/settings.json`、Skill、Hook、插件启用列表 | 进版本控制，**像代码一样评审**；插件可以锁定到某个提交 |
| **个人级** | 个人偏好、快捷键、输出风格 | `~/.claude`、`settings.local.json`（不提交） |

**托管下发不等于安全边界（2026-10-15，UTC+8 核对）**：Claude 的 [server-managed settings](https://code.claude.com/docs/en/server-managed-settings)支持 Team／Enterprise，但随实际认证组织分发；Console API key 的 CI 不继承 claude.ai 组织策略。需要强制约束时，核目标入口并在受管端点、沙箱与网络边界落实（见 [10](10-security.md)）。**局限：服务端分发仍是客户端控制，未受管设备可绕过；第三方入口另核策略交付方式。** **[一手；研究：采用判断]**

**配置迁移保住作用范围。** 团队共享的格式与检查契约应一致，个人编辑期体验可以不同；可跨设备复用的偏好也要与本机系统衍生值分开。先用现成分层、优先级与选择性同步，不把个人覆盖推成团队规则，或把机器默认广播到别处。[Ruff、Firefox 与 Prettier 的取舍](research/2026-10-12-development-conditions.md#配置迁移保留作用阶段与设备边界)支持按语义选择；局部历史反馈不证明所有配置都应同步或隔离。**[一手／社区；经验：采用判断]**

**维护节奏**：模型或宿主升级后复核配置，只试撤回已无必要的可选步骤，比较行为、质量与总投入并保留恢复路径；稳定契约与必要回归继续保留。官方提示审计只是候选发现入口；Claude Code 可用时，`/skill-doctor` 提供调用与上下文成本线索，少用不等于无效，不据此全删旧指令。方法与命令范围见 [09 §3–4](09-review-and-quality.md#3-给自己的-ai-配置做评估)及 [05](05-skills-and-plugins.md)。**[一手；研究：采用判断]**

## 5. 成本治理

| 做法 | 说明 |
|---|---|
| **选对计费方式** | 交互开发比较订阅额度与实际投入；CI 和自动化优先比较可归属的 API 计费。订阅赠额按下方运行入口与超额规则核算 **[一手；研究：采用判断]** |
| **按项目和人归属** | 不同项目用不同的 API Key 或工作区；Claude Code 支持 OpenTelemetry 指标和事件；Anthropic 的 Admin API 可以管理成员、工作区、API Key 和速率限制，用量和成本报告目前需要直接调 HTTP 接口 **[一手]** |
| **预算与停用边界** | 云服务配置适用的 spend limit / spend cap，并确认超限后的停用行为；托管 Agent 按会话设美元上限；Ralph 循环设最大迭代次数 |
| **按任务算成本** | 衡量“完成一个任务花多少”，而不是单次请求的价格 |
| **先定位负担** | 检查缓存、无用指令与工具；任务明确、结果可检查时，再评估轻量模型分流。新增 worker 调用不是免费优化，是否保留看全任务质量、等待与总成本（见 [02](02-models-and-cost.md#3-订阅额度与成本控制)、[17 第 2.9 节](17-troubleshooting.md#29-成本暴涨)） |

**订阅赠额按运行入口核算（2026-10-15，UTC+8 核对）**：[官方资格说明](https://support.claude.com/en/articles/17154008-monthly-api-credits-for-max-and-team-plans)保留 Max 5x／20x 每月 100／200 美元、Team 按席位共享最多 500 美元；需合资格订阅满七天并关联单个 Console 组织。自行用该组织 API key 运行的 `claude -p`／Agent SDK 可覆盖，交互 Code、GitHub Action、IDE／桌面发起的 Code 运行及第三方云不覆盖。**局限：赠额不结转，也不是账单上限；耗尽后仍可能消耗已购余额、自动充值或按发票计费。** [研究记录](research/2026-10-13-cloud-spend-boundaries.md#补充地区策略交付与订阅赠额)保存具体条件与反证。**[一手；研究：采用判断]**

**云预算要区分产品与范围**（2026-10-13 核对）：AWS 新体验 Paid Plan 项目的 spend limit 提供月度税前费用上限；GCP 原生 spend cap 在单个项目的合资格服务上阻止新增用量。采用前确认覆盖范围、停用后果和恢复安排，详见[官方来源核对](research/2026-10-13-cloud-spend-boundaries.md)。**[一手：AWS、Google Cloud；研究：采用建议]**

**局限**：这些能力不能推广为所有账户和服务通用的账单封顶；尤其 GCP 的延迟超额、执行中请求和持续固定费用仍可能计费。

## 6. 怎么衡量效果

| 衡量 ✅ | 不要只看 ⚠️ | 原因 |
|---|---|---|
| 交付周期（从开始到上线） | 代码行数、PR 数 | AI 让产出变便宜，数量指标会虚高 |
| 变更失败率、事故率、缺陷逃逸率 | token 用量 | Faros 的观察性结果提示同时看可靠性与评审负担；定义和倍数见 [09](09-review-and-quality.md#1-质量数据ai-代码的真实代价)，不作本团队预测。**[一手：厂商公开资料，观察性]** |
| 评审时间、返工率、PR 体积 | 开发者自评的提速 | METR：主观感受和实测方向都可能相反 **[研究：原文]** |
| 重复代码、重构比例 | 测试覆盖率 | GitClear 公开材料只作抽检线索；移动占比不等于全部重构量，不设固定配额，见 [09](09-review-and-quality.md) **[一手／研究]** |

这些结果支持同时跟踪交付、评审和可靠性，不能预测本团队会恶化多少，也未证明某项治理措施有效。

**做法**：
- 在固定的任务集上做小规模对比（同一批任务，用和不用，或新旧配置）；
- 看趋势，不看单点；把指标和团队一起解读，不用来考核个人。

🧪 **交接试点让下一位维护者完成真实小变更，分记熟悉环境、理解、修改与返工投入。** 按行为验证与耗时决定是否补解释或缩小范围。比较耗时须注明有效计时人数、记录／自报来源及排除规则，成功提交者耗时不代表完成率，见[固定数据复算](research/2026-10-13-immich-handover.md#公开数据复算计时分母与来源)。[Echoes of AI](research/2026-10-13-immich-handover.md#补充证据接管后实际修改的受控实验)未检出明确时间差异；任务小、估计不确定，不证明长期维护等价或该试点有效。**[研究：原文；经验：试用建议与复算]**

## 7. 评审与协作规范

以下按接收者当前任务查用，不要求依次完成五类检查；PR 准入与协作约定在本节末尾。

### 首次启动：从实际宿主和目标环境验收

**安装、启动或构建通过后，按接收方实际用法验收：**

| 交接问题 | 采用／验收动作 | 主要依据与关键局限 |
|---|---|---|
| **终端成功，桌面集成也通过了吗？** | 从实际宿主入口验收，注明包装和权限上下文；分清 OS 拒绝与应用安全检查，不一律重置权限 | [CBM 宿主对照](research/2026-10-13-immich-handover.md#接收入口增量同机终端成功仍未验收桌面宿主)：同机同用户同一二进制在终端成功、MSIX 宿主失败，升级后连接恢复。跨版本自报不能归因于单补丁，也未验证安全性或全部业务。**[社区：接收者报告；研究：采用判断]** |
| **构建通过，接收环境能加载吗？** | 含原生依赖时写清系统／架构／运行库，复用发布检查，在目标环境验最终产物加载和关键功能；读嵌套原因区分缺包与无法加载，再修解析或构建配置，不默认删锁文件重装 | [Rollup 维护链](research/2026-10-13-immich-handover.md#补充证据构建成功与接收环境的原生依赖)中构建通过仍产出旧系统不能加载的包。仅特定 Linux 原生包案例；静态符号检查不替代目标环境运行。**[一手：固定源码与 CI；社区：用户报告；经验：采用判断]** |

### 识别权威版本：以实际采用的补丁和交付产物为准

在已有 PR 中写清最终方案、理由及未验证场景，更新被后续补丁推翻的解释。[Immich 两轮修改](research/2026-10-13-immich-handover.md)能核对意见与代码，但未量化接收成本收益。**[一手：审查与补丁；研究：采用建议]**

| 交接问题 | 采用／验收动作 | 主要依据与关键局限 |
|---|---|---|
| **上游停止发行，接管构建就够了吗？** | 分清缺二进制发行还是源码维护；前者评估窄构建接管，后者先明确修复来源，再决定保留、换源或缩小支持。镜像日期、标签和构建成功不代替修复来源与宿主验收 | [MinIO接管链](research/2026-10-13-immich-handover.md#补充证据接管构建不等于接管源码维护)：2025年停发官方二进制后出现第三方构建，2026年上游声明不再维护；2025年版本元数据修订后，原用户仍报宿主差异。只核声明、固定实现和历史自报，不推荐该镜像或证明持续维护。**[一手／社区；研究：采用判断]** |
| **上游已修，下游能直接交付吗？** | 按接收方包装、工具链配置和下游补丁组合重建；旧补丁失配先核上下文及剩余职责。报告真实命令与固定版本，分开构建、启动和核心业务验收 | [Handy Nix/Darwin 接收链](research/2026-10-13-handy-retest-adoption.md#接收方重建上游修复还要穿过下游包装)修启动入口、刷新包装补丁后才获成功回执。仅局部运行自报，普通构建不能记成指定验收工具已运行。**[一手：固定补丁；社区：回执；研究：采用判断]** |

### 理解必要取舍：能解释最终行为，也核对修复依据

**作者对代码负责**：应能解释行为变化、设计取舍、风险与验证依据；权限、持久数据、接口及后续维护边界须定向走读，关键依据不清时不合并，不统一要求逐行讲解，见 [14](14-synthesis.md#74-人的注意力花在哪里)；

**接管持久化临时绕过的补丁前，先核原故障阶段、实际参数与补丁范围。绕过参数未启用，或补丁只影响故障之后的阶段时，测试通过与解释完整仍不能证明原问题已修；独立需求另验。** [Anaconda 的接收与撤回](research/2026-10-13-immich-handover.md#补充证据解释完整仍须核对原故障阶段)有 smoke 成功和固定撤回依据；仅一次维护链，AI 归属仍为维护者怀疑，不证明安全事故或长期维护收益。**[一手／社区；研究：条件建议]**

### 完成下一修改：决定保留、替换或删除哪些实现

| 交接问题 | 采用／验收动作 | 主要依据与关键局限 |
|---|---|---|
| **职责已交给依赖，旧实现能删吗？** | 核最低支持版本、保存后恢复及删掉的公开接口；[本地退出条件误判](research/2026-10-12-development-conditions.md#上游接管后的退出条件aiohttp-误判修复版本)时，先修判定、保留受影响环境的补偿；删除旧层仍保留异常诊断和预算决策 | [Pydantic AI 下游接管](research/2026-10-12-development-conditions.md#接收者接下来做了什么删除补偿层而非恢复旧测试期待)在上游修复中断历史后，提高依赖下限、删 healing 层，以新 agent 的 JSON 往返检查下一轮工具返回。仅历史确定性框架测试；未验真实重启、外部旧导入迁移，跨仓说明未全同步。**[一手：源码与 CI；研究：采用建议]** |
| **已有用户收益，可以替换旧功能吗？** | 🧪 按使用场景限定试用；旧平台与设置迁移未覆盖时，先做局部补充，不用新交互替换全部旧路径。新增权限与原生依赖也计入采用条件 | [Handy 暂停／降音量比较](research/2026-10-13-handy-retest-adoption.md#体验升级局部补充还是替换旧功能)：暂停已有非作者使用；降音量补丁删除非 Windows 旧静音路径，macOS 局部方案保留其他平台，但增加音频捕获权限与桥接成本。固定实现不等于运行验收，两份降音量 PR 均未合并；不据此推荐授予权限。**[一手：固定源码；社区：反馈；研究：采用判断]** |

交接是否足以支持真实小变更，可按[§6 的接管试点](#6-怎么衡量效果)观察熟悉环境、理解、修改与返工投入；该试点本身尚未证明有效。

### 失败恢复：按入口、实例权限和数据产物查用

**迁移／恢复先定目标，再验数据和运行状态：**

| 交接问题 | 采用／验收动作 | 主要依据与关键局限 |
|---|---|---|
| **绕过问题后成功，算修好了吗？** | 回到原接收者的原触发条件复测；错误说明写清被拒对象和规则，安全边界改变由维护者决定 | [CBM 原用户复测](research/2026-10-13-immich-handover.md#补充证据原用户恢复原触发条件后升级成功)先调整环境安装，再恢复原条件确认修订版可运行。仅单一 WSL2 用户自报，不代表全部客户端或安全性已验证。**[社区：复测；一手：固定补丁；经验：交接建议]** |
| **恢复入口失败，要重做全量吗？** | 先分清入口／选择参数与归档内容／版本兼容问题；若已有受支持的窄恢复通道能覆盖所需组件，先补清操作并验结果。长期交给图形界面用户时修入口；窄通道不覆盖必要能力才缩小承诺或另选恢复方案 | [Home Assistant 两条恢复路径](research/2026-10-13-immich-handover.md#补充证据恢复入口失败先保住所需恢复范围)：同一接收者先用显式组件CLI成功，前端URL修复后恢复界面操作。回执仅无业务数据的AirCast插件，不证明完整实例恢复。**[一手／社区；研究：条件选择]** |
| **接替旧实例，还是保留旧实例试用？** | 分开决定凭据、实例身份与业务／进度数据的保留；接替按产品机制处理旧实例退出，并存的新身份不等于数据隔离。身份／凭据变更及配对另按授权执行，不一律重建身份 | [两种恢复目标的回执](research/2026-10-13-immich-handover.md#补充证据接替恢复与并存试用的身份取舍)：Syncthing Tray 选择性导入保留目标身份、暂停同步，需对端重接共享；Tailscale 克隆手机重建身份才恢复并用，容器接替则改回受支持入口后成功。历史自报与固定实现不证明跨实例互斥或 AI 净收益。**[社区：回执；一手：源码；研究：采用判断]** |
| **恢复到新实例后，能直接交给 Agent 吗？** | 先复用原生恢复，再核并隔离对源库和恢复归档的写权限，才开放任意执行能力；隔离做不到时保持受限操作路径 | [Railway 恢复凭据修订](research/2026-10-13-immich-handover.md#恢复副本的归档写权限)明确恢复实例仍持有源归档的读写凭据。新实例、恢复程序只读均不等于凭据只读；仅官方契约与固定修订，未做真实恢复实测。**[一手；研究：采用判断]** |
| **空库能重建，已有库也能升级吗？** | 分验两条路径；压缩迁移保留必要初始数据、实例配置及防重复初始化的执行身份，写清不迁移数据与失败恢复状态。复用测试验业务读写／登录，不只看退出码 | [PocketBase 接收者升级](research/2026-10-13-immich-handover.md#补充证据结构快照不能代替已有数据的升级交接)：结构快照不含业务记录、排除特定实例配置，生成的回退函数可能为空操作。历史固定源码和单一回执不能推广为统一数据库恢复步骤。**[一手：源码；社区：回执；研究：采用建议]** |
| **恢复后能登录，旧数据就回来了吗？** | 验一条已知旧记录及关联文件，不只验新建或登录；空数据时先核连接目标、备份内容和原持久状态，再决定重导入／清空重建。区分容器名、逻辑库名和持久卷，恢复命令按备份生成版本选择 | [Immich 恢复重试](research/2026-10-13-immich-handover.md#补充证据恢复成功但应用连接了另一数据库)导入无报错且可登录，改正逻辑库名后才见原照片。仅单一回执；原库是否曾删除仍未知，不能断言恢复本可省略。**[社区：前后回执；一手：固定配置与当前文档；经验：采用判断]** |
| **重建命令跑过，旧对象为什么仍不能修改？** | 重建若按数据库清单枚举对象，应在恢复该清单及目标配置后执行；优先复用原生维护入口，再验旧对象的必要写入，不默认另写批量修复脚本或重导全库 | [Gitea 恢复顺序与原生入口](research/2026-10-13-immich-handover.md#补充证据派生入口重建依赖恢复后的对象清单)：旧 Wiki 迁移者用已有维护功能解除写入阻塞；另一恢复者将 hooks 重建移到 SQL 恢复之后才解决 push 报错。两次历史自报，非同一完整验收；未测总投入或 AI 收益。**[社区：回执；一手：固定源码；研究：采用判断]** |
| **新对象成功，原失败对象也恢复了吗？** | 上传／导入曾失败时，保留一个原失败对象，在接收环境重试并打开或下载关联文件；已同步、duplicate或成功状态不能代替实体可用，确认接收副本前不据标记删除原件 | [Immich旧失败照片回执](research/2026-10-13-immich-handover.md#补充证据新对象通过不等于原失败对象已恢复)：修好约束后新照片正常，旧照片仍只剩记录；后续错误补偿不清理历史残留。仅同一操作者的维护报告，不是跨人接管或AI收益证据。**[社区／一手／研究]** |

**修复版仍失败，先确认有没有进入新逻辑。** 若持久失败状态挡住重试，交付应补上保住原数据、按产品支持路径重新进入恢复流程的办法，而非默认清标记或全量重置。[Nextcloud AIO 原用户重试](research/2026-10-13-immich-handover.md#补充证据修复逻辑前的持久失败守卫)在升级后仍受阻，按维护者指导重做迁移后确认解决；回执未报告完整旧数据验收。**[一手／社区；研究：交付建议]**

**交付双向同步脚本，先选保留历史的恢复，还是重建双方文件基线。** 已有可信同步历史时，优先用受支持的恢复路径；首次初始化或历史不可用时，另定重建保留规则并预览差异。[rclone 维护链](research/2026-10-13-immich-handover.md#补充证据双向同步中断后恢复还是重建基线)显示，自动重建可能复活已删除文件、覆盖另一侧更新版本。正常运行后持续冲突则先核状态记录缺陷，别用固定偏向某侧掩盖错误。同步历史不是备份；这些具体机制不外推其他工具，后续完整可靠性仍未验证。**[一手／社区；研究：交付选择]**

**导出器修复不等于旧备份已修复。** 确认导出覆盖关联文件后，保留现有备份，从完好来源生成独立新产物并核记录与文件对应；升级接收端或重压旧目录不能补回覆盖内容。允许重建派生件时可保留原件重建，但不等于恢复原字节。[Paperless 维护链](research/2026-10-13-immich-handover.md#补充证据修复导出器不等于修复已存备份)已有固定补丁与维护者重做备份的建议；2026-10-17 核实修复已进入 [v3.3.2](https://github.com/paperless-ngx/paperless-ngx/releases/tag/v3.3.2)，可用该稳定版从完好来源重新导出独立新产物；仍无原用户修订后恢复回执。**[一手／社区；研究：条件建议]**

### PR 准入与协作约定

1. **PR 应可独立理解与验证**：按行为和依赖切片；100–200 行是实践者参考，不能让机械行数迫使关联改动拆散或新增审批（见 [07 第 3.4 节](07-workflows.md#34-大功能的前置设计与垂直切片-)）；
2. **PR 要附证据**：跑过的命令和结果、截图、手工测试记录。别把没审过的 AI 代码丢给同事 **[社区：Willison]**；
3. **先确认贡献准入，再说明 AI 参与程度**：团队内部约定披露；对外按接收渠道核对。Godot 禁止实质 AI 代码、代理代投和 AI 生成人际沟通，有限补全附条件允许；披露不代替准入，见[政策与关闭案例](research/2026-10-13-godot-contribution-policy.md)。**[一手；经验：采用判断]**；
4. **按验收与整合能力安排并行**：独立只读调查可交回来源核对，可执行任务提供相应检查；涉及人工决定的部分仍需留出真实审阅能力，不用一个人数上限覆盖所有任务（见 [14 规律三](14-synthesis.md#3-规律三按实际接收能力安排产出)）。

## 8. 人的成长

| 风险 | 表现 | 应对 |
|---|---|---|
| **技能退化** | 有人发现“连一个很小的项目都突然想不清架构”；团队里出现“离开 AI 就定位不了问题，说不清组件的输入输出” **[社区：HN、V2EX]** | 关键模块保持亲手写、亲手读；定期“无 AI”的设计讨论；有人用间隔重复的工具专门对抗这种退化 **[社区]** |
| **新人成长 / 陌生模块学习** | 完成当前任务后，还需确认能否运用新概念 | 🧪 以学习为目标时，可在按需提问、解释后，选一个相关小变更由学习者自己修改并测试，先不让 AI 直接给出完整补丁；卡住再求助，观察正确性、所需提示和投入。不把此练习设为日常交付必经步骤。**[经验：试用建议]** |
| **职业倦怠** | “Agent 不在干活就觉得浪费时间”的焦虑 **[社区]** | 不以 token 或并行数衡量人；按自己的交付、返工和主动投入比较，不设未经测量的提速倍数目标 |
| **乐趣和认同** | 社区两极分化：有人觉得讨厌的部分消失了，有人觉得编程不再好玩 **[社区]** | 允许个人选择 AI 的参与程度；把 AI 当结对伙伴而不是代写 |

[现有学习实验](research/2026-10-13-immich-handover.md#补充证据陌生模块学习与下一次修改)尚未证明这一练习本身能提升职业开发者的后续维护能力。**[研究：证据边界]**

## 9. 检查清单

**组织**
- [ ] 允许使用的 Agent、模型和插件清单
- [ ] 数据分级：哪些代码和数据可以发给哪些服务
- [ ] 托管设置：核认证组织、部署入口及实际执行边界，再配置命令、网络和插件来源限制
- [ ] 成本：按项目归属、预算与停用边界、月度复盘
- [ ] 度量：交付周期、事故率、评审时间的基线

**每个仓库**
- [ ] 测试、构建、lint 命令能一键运行
- [ ] 项目指令保留有用的定位与行为边界，删重复／失效内容并核目标客户端加载，不按行数或“能否猜到”一刀切（见 [03](03-context-engineering.md)）
- [ ] 保护规则（生成目录、密钥、迁移脚本）
- [ ] 评审规范：PR 大小、证据要求

**每个人**
- [ ] 会用验证闭环：让 Agent 自己跑检查并出示证据
- [ ] 会用垂直切片：按未决需求与接口决定设计深度，逐片验证可运行路径（见 [15 §3](15-task-playbooks.md)）
- [ ] 知道什么时候不用 AI（见 [15](15-task-playbooks.md)、[14 第 7.1 节](14-synthesis.md#71-这个任务该给-agent-多大自主权)）
