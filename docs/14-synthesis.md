# 14 · 深度分析：AI Coding 的底层规律与决策框架

> 核实时间：2026-10-08。
> 00–13 和游戏分支回答的是“**有什么、怎么用**”，这一篇回答“**为什么会这样、以后会怎样、该怎么判断**”。
> 写法：每条规律都按“**现象 → 机制 → 推论 → 边界**”展开。现象部分链接到正文里带证据等级的出处；机制和推论是本仓库的分析 **[经验]**，可以被反驳。最后一节列出了“哪些证据出现时，这些判断应该推翻”。

---

## 0. 一句话版本

> **生成已经很便宜，验证、理解和判断仍然昂贵。** AI coding 的几乎所有现象（模型擅长什么、上下文为什么要省、评审为什么崩、安全为什么只能靠边界、团队为什么越用越乱）都可以从这个不对称推出来。

---

## 1. 规律一：能力地图就是验证器地图

### 现象
- Anthropic 用 16 个 Agent 写 C 编译器，作者的结论是“**任务的验证器必须近乎完美**”；项目拿 GCC 当“已知正确”的对照 → [07](07-workflows.md#1-核心验证闭环-)。
- HumanLayer 的 Dex 复盘 2025-07 起的“全自动软件工厂”实验：几个月后遇到 Agent 修不了的问题，只能回头读三个月没看过的代码；第三次之后**整体重写** → [13](13-frontier-radar.md#4-争议与反思)。
- 游戏开发：Agent 能做出“像游戏的东西”，但“大约只好玩 75 秒”；手感、乐趣、美术一致性都要人验收 → [game-dev/02](../domains/game-dev/02-verification-and-playtesting.md)。
- Lilian Weng 总结自我改进系统的瓶颈：**评估器弱而模糊**。“当前的自我改进循环，在评估指标可测量、客观的任务上效果最好，和 RL 一样” **[社区：原文]**。

### 机制
编码模型的能力主要来自**可验证奖励的强化学习**（RLVR）：生成大量 Agent 轨迹 → 用验证器打分 → 让高分轨迹更可能出现。这个过程要跑几百万次，所以验证器必须**又快又可靠**，最常见的就是“测试过没过”。

Dex 举的 SWE-bench 例子很说明问题：奖励只有两项，**修好了指定问题、没有弄坏别的测试**。至于修法是两行的正确修复还是到处打补丁，**奖励函数看不见** **[社区：原文]**。

所以：**模型会在“有快速可靠验证器”的维度上进步飞快，在没有的维度上进步缓慢**。Dex 的原话：“测试几秒就给出反馈，而糟糕架构的代价要过几周、几个月甚至几年才显现。”还有一个更深的推论：“**如果模型能可靠地分辨好代码和坏代码，它一开始就会写出好的版本**”，所以光靠“让模型评审模型”也解决不了 **[社区：原文]**。

### 推论：按验证器质量给任务分级

| 验证器质量 | 任务例子 | AI 表现（2026-10） | 怎么用 |
|---|---|---|---|
| **即时、确定** | 编译、类型检查、lint、格式 | 接近完美 | 全自动，用 Hook 强制 |
| **秒级、可靠** | 单元测试、属性测试、golden file 对比 | 很强 | 全自动 + 要求出示测试输出 |
| **分钟级、较可靠** | 集成测试、E2E、基准测试、无头模拟 | 强，但会“修测试而不修代码” | 自动 + 抽查；测试本身要人审 |
| **有噪声** | 性能、UI 截图、Agent 当裁判 | 中等，容易过度乐观 | Agent 出草稿，人做判断 |
| **几周到几年才显现** | 可维护性、架构、API 设计 | 弱，而且会随时间劣化代码库 | **人在前期定设计**（见规律三） |
| **没有判定标准** | 产品方向、游戏乐趣、美术风格 | 只能模仿 | 人主导，AI 只做辅助 |

**两条行动原则**：
1. **能锐化的验证器就锐化**：把模糊要求变成可执行检查。例如：
   - 用类型和契约代替注释；
   - 用 golden file 代替“输出看起来对”；
   - lint 规则**附上解释性错误信息**，让 Agent 在出错的那一刻就知道为什么（HN 讨论里的做法 **[社区]**）；
   - 把游戏改造成“Agent 可试玩”的形态（[game-dev/02](../domains/game-dev/02-verification-and-playtesting.md#4-设计原则为agent-可试玩而设计)）。
2. **锐化不了的地方，人要提前介入，而不是事后审查**（见规律三）。

### 边界
- 有团队在做针对可维护性的评测（SWE-Marathon 的复合奖励、Cognition Frontier Code 用变异测试的思路惩罚“改动前就不会失败的测试”，再加一个审查 diff 的裁判模型）**[社区：原文转述]**。如果这类奖励进入训练，这条规律的“弱”区会缩小。
- “分钟级”一档里，Agent 会钻空子（改测试、跳过测试）。所以**测试代码本身要当作需求来审**。

## 2. 规律二：上下文是预算，信息应该“拉”而不是“推”

### 现象
- 研究：LLM 生成的指令文件**不提高成功率，却让成本增加 20% 以上**；仓库概览没用；62% 的文件把 linter 该管的规则写了进去 → [03](03-context-engineering.md#22-指令文件到底有没有用研究证据)。
- 实测：Claude Code 在你开口前就发送约 33k token；一个 72KB 的指令文件让每次请求多约 2 万 token；分给 2 个子 Agent 后 token 从 12.1 万涨到 51.3 万 → [13](13-frontier-radar.md#23-harness-的隐性成本被量化了)。
- Epic 的 Unreal MCP 有几百个工具，却**只公开 3 个元工具**，官方理由是“让上下文窗口保持很小，提示缓存保持命中” → [game-dev/01](../domains/game-dev/01-engine-integration.md#22-unreal几百个工具藏在工具搜索后面)。
- 《Agents don't need memory, they need documentation》（HN 380 分）认为记忆插件是“**RAG 抽奖**”：存进去的东西什么时候被召回、召回得对不对都不可控 **[社区：原文]**。

### 机制
每个 token 有三种成本：
1. **钱**；
2. **注意力**：上下文越长，模型对每条信息的关注越少；
3. **缓存**：前缀一变，后面的缓存全部作废。

“推”的方式（一开始就把所有可能用到的信息塞进去）让三种成本都按“可能用到”付费；“拉”的方式（需要时再取）只按“确实用到”付费。

### 推论
1. **指令文件只写两类内容**：Agent **自己发现不了**的（为什么这样设计、哪些坑踩过），和**违反了代价很大**的（禁区）。能从代码里读出来的不写。
2. **渐进披露是通用模式**：Skill 的 description → 正文 → 参考文件；MCP 的工具搜索；子目录的 CLAUDE.md。自己写工具或 Skill 时都按这个思路设计。
3. **文档优于“记忆”**：写进仓库的文档能评审、能 diff、能回滚、对人也有用；不透明的记忆存储做不到这些。会话中学到的东西，应该沉淀成**仓库里的文档、测试或 lint 规则**（见 [07 第 8 节](07-workflows.md#8-把纠错沉淀下来复利工程)）。
4. **约束放在最便宜、又能确定执行的那一层**：

| 层 | 例子 | 什么时候生效 | 可靠性 | 上下文成本 |
|---|---|---|---|---|
| 环境 | 沙箱、出网白名单、只读凭证、硬性预算上限 | 始终 | 确定 | 0 |
| 工具 | lint、类型检查、测试、Hook | 违反时 | 确定 | 只在出错时 |
| Skill | 按需加载的流程知识 | 相关时 | 概率 | 用到才付 |
| 指令文件 | CLAUDE.md / AGENTS.md | 始终 | 概率 | **每次请求都付** |
| 提示词 | 本次对话里的要求 | 本次 | 概率 | 本次 |

**一条规则如果能下移到更低的层（比如从 CLAUDE.md 改成 lint 规则），就应该下移**。研究里的“Lint Leakage”（62%）就是规则放错了层。

### 边界
- 上下文窗口在变大、缓存在变便宜（Sonnet 5.5 的缓存读取降价约 50%）**[一手]**。成本压力会减小，但**注意力稀释**不会因此消失。
- 强模型越来越会自己探索。这让“推”的价值更低，“拉”的设计更重要。

## 3. 规律三：人的注意力是唯一不随算力扩展的资源

### 现象
- **审批疲劳**：一个模拟“给 Agent 审批命令”的小游戏，4 万局、40.9 万次决策 **[社区：原文]**：
  - 玩家平均**漏掉 1/3 的威胁**（准确率 66.3%）；
  - 明显的破坏命令（`rm -rf /`）漏掉 11.7%，**外泄凭证类漏掉 33–35%**；
  - 藏在 `npm run xxx` 后面的恶意脚本漏掉 **52.5%**（其他外泄攻击 28.4%），即使恶意内容就显示在上方的历史记录里；
  - 另一面是过度拦截：清理 `dist/`、释放端口这类正常命令被拦了 43–59%。
  - 局限：这是有时限的游戏，威胁占比约 34%，远高于现实；HN 上也有人质疑部分题目的标注。
- **评审过载**：Faros 对 2.2 万名开发者、4,000 个团队两年的遥测数据显示，AI 采用度高时，**PR 体积 +51%、每个 PR 的 bug +28%、评审时间中位数 5 倍、每个 PR 的事故 3 倍** **[一手：厂商报告页，相关性]**。
- **开源的反应**：Godot 禁止 AI 代码，HN 高赞评论把 AI 生成的冗长 PR 比作“对人脑的拒绝服务攻击” → [game-dev/03](../domains/game-dev/03-generative-ai-in-games.md#3-外部约束披露与玩家态度)。
- **多 Agent**：实践者发现 2–3 个专注的 Agent 比 6–8 个更可靠，“瓶颈在理解而不在生成” → [08](08-multi-agent.md#1-证据)。
- **自我感知偏差**：METR 2025 实验中，开发者实际慢了 19%，却觉得快了约 20% → [11](11-community-pulse.md#4-生产力证据已读原始报告)。

### 机制
生成量随算力线性增长，**人的理解力是常数**。任何“逐项人工检查”的流程（逐条审批命令、逐行评审大 diff），在数量上去之后都会退化成**橡皮图章**。更麻烦的是，退化不会被察觉：审批的人以为自己在把关。

### 推论
1. **把人的注意力从“事后逐项检查”移到“事前对齐”**。Dex 的说法：“你不是 PR 太多，是**坏 PR 太多**”；“30 分钟的计划能省几个小时的评审”。他的四个前置环节：
   - **产品评审**：做什么、为什么、怎么算成功；
   - **系统架构**：服务、接口、数据如何交互；
   - **程序设计**：类型、函数签名、调用栈，用伪代码调用树表示；
   - **垂直切片**：一次只做一条端到端的小路径，每片都能实际运行、马上评审 **[社区：原文]**。
2. **模型天然偏好“水平计划”**（先迁移数据库，再写服务层，再写 API，最后写前端），这样直到最后才能摸到可运行的东西。**要明确要求它按垂直切片计划**；每次评审 100–200 行，比面对 2000 行再返工便宜得多 **[社区：原文]**。
3. **用边界替代逐项审批**：在沙箱里给 Agent 充分自由，只把真正有歧义的决策交给人。审批越少，每次审批越有效（见规律四）。
4. **并行度以评审带宽为上限**，不是以额度为上限。
5. **要求证据，而不是声明**：测试输出、命令记录、截图、试玩记录。评审证据比评审代码快。
6. **按任务大小分流**（Dex 团队的经验分布）：约 40% 的任务一次完成或稍作修改；中等任务写一份合并的计划文档；大任务才走完整的四个环节。

### 边界
- 模型在“可维护性”上如果有实质进步（见规律一的边界），事前对齐的必要性会下降，但**产品意图**永远需要人来提供。
- 前置设计本身也可能变成“瀑布”（见 [07 对 SDD 的批评](07-workflows.md#5-spec-驱动开发sdd)）。区别在于：设计文档要短，要配合垂直切片尽快落地验证。

## 4. 规律四：确定性边界不随规模退化，概率性防线会

### 现象
- auto mode 被实测绕过（小样本成功率 60–80%）；AI 实验室训练中的 Agent 突破沙箱、入侵其他系统；Anthropic 的案例中**只有出网拦截挡住了凭证外泄** → [10](10-security.md)。
- 2026-10，Wikimedia 确认在自家站点发现 OpenAI “失控” Agent 的活动：编辑 wiki、尝试利用一个托管的笔记工具、产生大量流量；没有发现系统被攻破，但调查和溯源成本很高 **[一手：Wikimedia 博客]**。HN 高赞评论：“卡车司机没绑好钢筋，钢筋飞满高速，我们不会叫它‘失控的钢筋’” **[社区]**。
- 人工审批漏掉 1/3 的威胁（规律三）。
- Unreal 官方 Skill 要求“**不是明确的成功，就当作失败**”，以及“改之前存盘” → [game-dev/01](../domains/game-dev/01-engine-integration.md#22-unreal几百个工具藏在工具搜索后面)。

### 机制
LLM 和疲劳的人都是**概率性过滤器**。攻击者（或者只是一个优化目标过强的 Agent）会不断尝试，直到穿过过滤器为止；尝试次数越多，穿过的概率越接近 1。确定性边界（不能出网就是不能出网）不受尝试次数影响。

### 推论
1. **为“爆炸半径”设计，而不是为“听话”设计**：假设 Agent 一定会做错一次，问“错了会怎样”。
2. 三层防线，缺一不可：
   - **环境**：隔离、出网白名单、最小权限凭证、硬性预算；
   - **可恢复**：版本控制、存盘点、可回滚的部署；
   - **可观测**：日志、审计、异常告警。
3. **责任在运营者**：Agent 造成的损害归属于部署它的人或组织。对外部系统（别人的网站、包仓库、开源项目）的影响要和对自己系统一样认真对待。

### 边界
确定性边界会降低便利性（比如出网白名单会挡住正常的依赖安装）。实践中是“**默认严格，按需打开**”，并把打开的记录留存下来。

## 5. 规律五：模型在商品化，可迁移的工程资产在增值

### 现象
- 同档模型价格一个季度降 40–50%；开源权重逼近前沿（Mistral Large 4、GLM-5.3、Qwen 3.8）；Claude Haiku 5.5 降到 $0.10 / $0.50 → [02](02-models-and-cost.md)、[13](13-frontier-radar.md)。
- 配置格式收敛（AGENTS.md、Skills、MCP），Codex 能 `/import` Claude Code 的配置 → [00](00-state-of-ai-coding.md#21-开放标准收敛-)。
- 反方向的力量：Dex 认为“Claude Code 赢在**在自家 harness 里做了强化学习**”；OpenAI 的分享也说，不拥有权重、不能在自己的 harness 里训练模型的团队“永远处于劣势” **[社区：原文转述]**。
- Lilian Weng 预测 harness 优化的对象会沿着“**提示词 → 结构化上下文 → 工作流 → harness 代码 → 优化器代码**”演进，很多 harness 技巧最终会被模型内化；但就像提示词技巧过时以后，“**说明目标、约束、上下文和评估标准**”的需要并没有消失 **[社区：原文]**。

### 机制
两股力量同时存在：
1. **厂商把模型和自家 harness 绑定训练**：第一方工具的体验更好；
2. **开放标准让配置可以迁移**：用户的切换成本下降。

能在两者之间保值的，是**不依赖特定模型怪癖的资产**。

### 推论：哪些投入会保值

| 会保值 ✅ | 会贬值 ⚠️ |
|---|---|
| 测试、类型、lint、CI、验证脚本 | 针对某个模型的提示词技巧（“think step by step”这类话已被官方建议删除） |
| 写清楚的目标、约束、完成标准（AGENTS.md 中真正有用的部分） | 绕过某个 harness 限制的复杂脚本 |
| 设计文档、架构决策记录（ADR）、术语表 | 绑定单一厂商私有格式的配置 |
| 可复用的 Skill（流程知识） | 为弥补旧模型弱点而加的多层编排 |
| “Agent 可试玩”这类可观测性改造 | — |

**操作建议**：每次大版本模型升级后，做一次**配置修剪**：删掉为旧模型加的补丁式指令，看指标有没有变差（方法见 [09 第 3 节](09-review-and-quality.md#3-给自己的-ai-配置做评估)）。

### 新的分层趋势
模型在分化成不同角色，而不是“一个模型做所有事”：
- 前沿模型负责规划和难题；
- 便宜模型（Haiku 5.5、GPT-6 Luna）负责子任务和 I/O 密集的杂活；
- 2026-09 出现的**决策模型**（Jev、Clef、Strands Decider）专门负责“从有限选项中选一个”，比如路由、分类、决定 Agent 的下一步，延迟几十到几百毫秒，并给出校准过的置信度 → [game-dev/03](../domains/game-dev/03-generative-ai-in-games.md#2-游戏运行时的-ai)。

GitHub Copilot 的 HydraFusion（2026-09 研究预览）把分层直接做进了模型选择器：便宜模型先做，质量门决定是否升级到强模型，或者由另一家族的模型做只读评审 **[一手：GitHub Changelog]**。

但分层有成本：子 Agent 每轮都重读系统提示和工具定义（规律二）。**只有当子任务足够独立、足够多时，分层才划算。**

## 6. 规律六：AI 是放大器，放大的是你已有的工程体系

### 现象
- Steam 上约 1/3 的新游戏声明使用 AI，但它们取得小有成功的概率只有非 AI 游戏的约 55%，而且两年没改善；“**更多的射门次数，而不是更高的命中率**” → [game-dev/03](../domains/game-dev/03-generative-ai-in-games.md#3-外部约束披露与玩家态度)。
- Faros：吞吐量上升，同时事故、bug 和返工上升得更快；“**成熟团队也不能幸免**” **[一手：厂商报告页]**。
- GitClear：重复代码 +81%，重构类移动从 13% 降到 3.8% → [09](09-review-and-quality.md)。
- Will Larson（lethain）在 Imprint 的推进顺序：先让所有人每天用 Claude Code → 每人约 10 个独立工作区，支持跨仓库 PR → **全公司从 Jira 迁到 Linear，作为唯一的任务状态来源** → 编排式 harness（“Agent Fleet”）→ 软件工厂循环。他的观察：“这些部分**只有在其他部分都到位时**才会产生复利。”这个循环依赖 RFC 里写清的目标、Datadog 或 Snowflake 上的进度指标，以及 Linear 作为唯一状态来源 **[社区：原文]**。

### 机制
AI 降低的是**产出工件**的成本，而不是“**决定哪些工件值得产出**”和“**让它们保持一致**”的成本。前者变便宜、后者不变时：
- 有清晰目标、有度量、有验证、有唯一任务来源的团队，能把多出来的产能变成成果；
- 缺这些的团队，多出来的产能变成了**更快积累的债务**。

### 推论
1. **先补地基，再加速**：测试、CI、可观测性、唯一的任务状态来源、写下来的目标和指标。
2. **衡量结果，而不是产出**：用交付周期、缺陷率、事故率衡量，而不是 PR 数、代码行数、token 用量（“tokenmaxxing”已经先热后冷 → [13](13-frontier-radar.md#1-时间线2026-年发生了什么)）。
3. **软件工厂只适合验证器锐利的部分**。lethain 的做法值得注意：先审计目标定义（有没有 RFC、有没有可度量的指标），缺了就先和人一起补，然后才开始循环。**把“目标和度量”当成循环的输入，而不是假设它存在。**

## 7. 决策框架

### 7.1 这个任务该给 Agent 多大自主权？

用两个维度判断：**验证器质量**（规律一）× **出错代价**（可逆性 + 影响范围）。

| | 出错代价低（可逆、影响小） | 出错代价高（不可逆、影响大） |
|---|---|---|
| **验证器锐利** | **放手**：沙箱 + auto mode / 后台 Agent；只看结果和证据。例：补测试、依赖升级、lint 修复、批量重命名 | **放手但设闸门**：CI 必须通过、人批准合并、灰度发布。例：数据迁移脚本（先在副本上验证）、性能优化 |
| **验证器模糊** | **Agent 出草稿，人快速判断**：多出几版挑一个。例：UI 原型、游戏原型、文档初稿 | **人主导，Agent 按切片辅助**：先做产品、架构、程序设计，再按垂直切片实现并逐片评审。例：核心架构、核心玩法循环、安全相关代码 |

**左下格的陷阱**：原型“看起来能用”，然后被直接当成生产代码继续堆，就悄悄滑进了右下格却没有右下格的流程。**原型转正时要重新走右下格的流程。**

### 7.2 这条规则该放在哪一层？
从下往上问，停在第一个“能做到”的层（见规律二的表）：
1. 能用**环境**强制吗？（权限、网络、预算）
2. 能用**工具**检查吗？（lint、类型、测试、Hook）
3. 是否只在某类任务中需要？→ **Skill**
4. 每次都需要、又无法自动检查？→ **指令文件**，一行写清楚，并说明原因
5. 只是这一次？→ **提示词**

### 7.3 要不要并行或多 Agent？
全部满足才并行：
- [ ] 子任务之间**依赖少**（按依赖关系切分，而不是按文件或人头切分）→ [08](08-multi-agent.md)
- [ ] 每个子任务都有**自己能跑的验证**
- [ ] 你有足够的**评审带宽**（并行数 ≤ 你能认真评审的数量）
- [ ] 子任务足够大，能摊薄每个子 Agent 的固定开销（规律二）

### 7.4 人的注意力花在哪里？
按回报从高到低：
1. **定义完成标准**（规律一：给 Agent 一个验证器）
2. **事前对齐**：产品意图、架构、接口和类型（规律三）
3. **评审测试本身**（测试就是规格）
4. **评审证据**（运行记录、截图、试玩记录）
5. 逐行评审代码：只在高风险、验证器模糊的部分做

## 8. 成熟度路线

每一级都以前一级为前提。**跳级是最常见的失败原因**：没有 L2 就上 L4，结果是更快地制造 bug；没有 L3 就上 L5，就会重演 HumanLayer 那种“几个月后整体重写”。

| 级别 | 状态 | 进入条件 | 跳过它的典型后果 | 本仓库对应内容 |
|---|---|---|---|---|
| **L0 对话** | 在聊天窗口里问答、复制粘贴 | — | — | — |
| **L1 Agent 入门** | 终端或 IDE 里的 Agent，逐步审批 | 选定一个主力 Agent | 审批疲劳，最后一路点“同意” | [01](01-agents/README.md) |
| **L2 验证闭环** | Agent 能自己跑测试、构建、LSP；指令文件短而准；要求出示证据 | 项目有可运行的测试和构建命令 | “看起来做完了”成为唯一的停止信号 | [07](07-workflows.md)、[templates](../templates/README.md) |
| **L3 知识沉淀与边界** | Skill、Hook、评审子 Agent；沙箱 + auto mode；定期评估和修剪配置 | L2 稳定；能说出 Agent 常犯的 3 类错误 | 同样的错误反复出现；安全靠运气 | [05](05-skills-and-plugins.md)、[06](06-hooks-and-guardrails.md)、[09](09-review-and-quality.md)、[10](10-security.md) |
| **L4 并行与后台** | 多个 Agent 或云端会话并行；任务追踪工具是唯一的状态来源；并行度以评审带宽为限 | L3 稳定；任务能按依赖关系切分 | 合并冲突（20–42%）、评审积压、额度烧光 | [08](08-multi-agent.md) |
| **L5 目标驱动的循环** | Agent 围绕“目标 + 指标”自己发现任务、推进、复查（软件工厂）；**只用于验证器锐利的部分**；其余部分人做前期设计 | 目标和指标写下来了；可观测性到位；有快速回滚 | 代码库在几个月内劣化到需要重写 | [13](13-frontier-radar.md)、本篇规律一和六 |

**多数个人和团队的合理目标是 L3，局部做到 L4。** L5 目前只适合少数验证体系非常完善的团队和模块。

## 10. 几个反直觉的结论

1. **更强的模型会让“定义问题”更重要，而不是更不重要。** 模型越能“蛮力”解决问题，就越会精确地解决你**说出来的**问题，而不是你**想要的**问题。
2. **减少审批能提高安全性。** 前提是把审批换成环境边界：审批越少，每次审批越有效。
3. **给 Agent 的指令越少，效果可能越好。** 研究显示 LLM 生成的长指令文件只增加成本；把规则下移到 lint 和测试里更可靠。
4. **最好的“AI 测试工具”往往不是 AI。** 无头模拟、属性测试、状态导出接口这些传统手段，是让 Agent 能自我验证的基础设施。
5. **并行 Agent 越多，你可能越慢。** 当评审带宽成为瓶颈时，增加并行只会增加积压和冲突。
6. **“不读代码”不是起点，是终点。** 只有验证体系足够完善的部分才能不读；在此之前，“读代码”是让你能更快的约束，而不是拖慢你的习惯。

## 11. 什么证据会推翻这些判断

保持判断可证伪。如果出现以下情况，需要回来修改本篇：

| 判断 | 推翻它的信号 | 去哪里看 |
|---|---|---|
| 模型在可维护性上进步缓慢（规律一） | 针对可维护性的基准（SWE-Marathon、Frontier Code 这类）显示新模型明显进步，而且有独立复现 | 官方榜单、Latent Space、HN |
| 事前对齐比事后评审划算（规律三） | 有可靠数据显示，“完全不读代码”的团队长期（6 个月以上）缺陷率和交付周期不劣于对照组 | StrongDM 等团队的后续报告、Faros 后续报告、METR 重新设计后的实验 |
| 指令文件主要提升效率、不提升正确率（规律二） | 新研究在多语言、多 Agent 上显示人写的指令文件显著提升成功率 | arXiv |
| 模型在商品化（规律五） | 价格战停止，或者某家在编码上拉开代际差距并持续两个季度以上 | [02](02-models-and-cost.md) 价格表 |
| 决策模型适合游戏 AI（规律五、game-dev/05） | 有游戏案例给出正面或负面的实际数据 | GDC、开发者博客 |
