# 14 · 深度分析：AI Coding 的底层规律与决策框架

> 核实时间：2026-10-15（UTC+8）。全文核心建议独立审阅；重点补核生产力、历史输入开销、决策概率与延迟，其他依据按各主专题已核范围继承。历史收窄见[审计](collaboration/reviews/2026-10-13-331e093.md)；未重新认证全部外部材料或运行模型实验。
> 00–13 和游戏分支回答的是“**有什么、怎么用**”，这一篇回答“**为什么会这样、以后会怎样、该怎么判断**”。
> 写法：每条规律都按“**现象 → 机制 → 推论 → 边界**”展开。现象部分链接到正文里带证据等级的出处；机制和推论是本仓库的分析 **[经验]**，可以被反驳。最后一节列出了“哪些证据出现时，这些判断应该推翻”。

## 0. 一句话版本

> **生成速度的提升，可能让需求判断、运行反馈、审查与维护成为新的限制。** 这是一条选题假设，不是解释几乎所有 AI Coding 现象的定律；有些任务仍受推理或执行能力限制，Agent 也可以帮助人理解与评审。应沿实际任务判断限制在哪里。**[研究：本仓库判断]**

**先选当前行动**：目标、授权和检查已明确，就继续实现并验证；缺不可猜的契约先澄清，需要看效果才能判断时先做可撤回样品。已有工具和资料够用就保留；额外流程、并行或配置只在补足具体缺口或质量目标时试用，以结果、等待和人工投入决定保留或撤回。依据与局限分别见 [07](07-workflows.md)、[05](05-skills-and-plugins.md) 和 [08](08-multi-agent.md)。**[经验：采用判断]**

## 1. 规律一：验证覆盖与自主权分开判断

### 现象
- Anthropic 用 16 个 Agent 写 C 编译器，作者的结论是“**任务的验证器必须近乎完美**”；项目拿 GCC 当“已知正确”的对照 → [07](07-workflows.md#1-核心验证闭环-)。
- HumanLayer 的 Dex 复盘 2025-07 起的“全自动软件工厂”实验：几个月后遇到 Agent 修不了的问题，只能回头读三个月没看过的代码；第三次之后**整体重写** → [13](13-frontier-radar.md#4-争议与反思)。
- 游戏开发：Agent 能做出“像游戏的东西”，但“大约只好玩 75 秒”；手感、乐趣、美术一致性都要人验收 → [game-dev/02](../domains/game-dev/02-verification-and-playtesting.md)。
- Lilian Weng 总结自我改进系统的瓶颈：**评估器弱而模糊**。“当前的自我改进循环，在评估指标可测量、客观的任务上效果最好，和 RL 一样” **[社区：原文]**。

### 机制
快速可靠的检查能给训练和推理中的迭代提供反馈，但本仓库没有证明“验证器质量决定全部能力”或“可维护性进步慢只因缺少 RL 奖励”。[Dex 的解释](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)是实践者假设，原文也承认长期质量判断尚无法证明。独立评审可能发现遗漏，需用检出率、误报和总成本验证。**[社区：作者判断；经验：采用边界]**

[Anthropic 编译器实验](https://www.anthropic.com/engineering/building-c-compiler)在较高测试通过率下仍报告兼容性、性能、质量和回归问题；[METR 维护者研究](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)也区分测试通过与可合并性，方法和局限见 [09](09-review-and-quality.md#3-给自己的-ai-配置做评估)。以下是验证方式与采用边界，**不是跨模型能力排名或生产就绪认证**。**[一手：实验报告；研究]**

### 推论：按当前检查覆盖选择反馈

| 验证方式 | 任务例子 | 怎么用 |
|---|---|---|
| **即时、可程序检查** | 编译、类型检查、lint、格式 | 自动检查，确认实际执行和覆盖 |
| **秒级、覆盖有限** | 单元测试、属性测试、golden file 对比 | 自动迭代 + 独立验收，不能据全绿直接上线 |
| **分钟级、集成验证** | 集成测试、E2E、基准测试、无头模拟 | 验证整合结果，审查测试与风险边界 |
| **有噪声** | 性能、UI 截图、Agent 当裁判 | 结合重复测量、校准与人工判断 |
| **长期才显现** | 可维护性、架构、API 设计 | 补未定契约，按风险评审，并观察后续真实修改 |
| **依赖人的目标和偏好** | 产品方向、游戏乐趣、美术风格 | 人定义目标并验收，AI 辅助探索 |

**两条行动原则**：
1. **先复用能检出目标缺陷的检查，只补覆盖缺口**：能明确预期的行为可转成可执行检查。例如：
   - 用类型和契约检查可表达的不变量，保留必要的设计原因；
   - 用 golden file 代替“输出看起来对”；
   - lint 规则**附上解释性错误信息**，让 Agent 在出错的那一刻就知道为什么（HN 讨论里的做法 **[社区]**）；
   - 按待验证的游戏行为复用现有测试与操作入口，只补缺少的状态观察（[game-dev/02](../domains/game-dev/02-verification-and-playtesting.md#4-如何验证第二次修改给已有动作加入暂停菜单)）。
2. **按未知选择人的介入时机**：业务与兼容契约不能猜时先澄清；布局、手感等必须看效果才能判断时，先做可撤回样品。两者都保留实施后的反馈，不因已有测试就跳过授权、兼容或维护判断，见 [07](07-workflows.md#30-秒先解决哪一种不确定性) 与 [09](09-review-and-quality.md)。

### 边界
- 有团队在做针对可维护性的评测（SWE-Marathon 的复合奖励、Cognition Frontier Code 用变异测试的思路惩罚“改动前就不会失败的测试”，再加一个审查 diff 的裁判模型）**[社区：原文转述]**。这些方向是否改善长期质量，仍须用后续修改和独立复现判断，不能由奖励形式直接推出。
- “分钟级”一档里，Agent 会钻空子（改测试、跳过测试）。所以**测试代码本身要当作需求来审**。

## 2. 规律二：按任务选择预先提供与按需获取

### 现象
- 研究：在指定 Python 任务/模型样本中，LLM 生成的指令文件**未显著提高成功率，成本增加 20% 以上**；不构成所有概览无效的证明；62% 的文件把 linter 该管的规则写了进去 → [03](03-context-engineering.md#22-指令文件到底有没有用研究证据)。
- [Systima 的 2026-07 历史实测](https://systima.ai/blog/claude-code-vs-opencode-token-overhead)：Claude Code 2.1.207／Sonnet 4.5 的首请求底座约 33k token，72KB 指令文件增加约 2 万，同一小任务分给 2 个子 Agent 后累计输入从 12.1 万增至 51.3 万；这些是含缓存输入量，不是费用倍数或当前固定开销。同文多步任务也有 Claude Code 总输入低于 OpenCode 的反例，换模型后结果又改变，须比较整项任务。**[社区：作者实测；2026-10-15 原文复核，未重跑]**
- 本仓库历史报告（原始产物待补齐，本轮未复现）：长指令文件（LLM 生成、526 行）让同一个修 bug 任务的成本变成 1.6–2.7 倍，过程差异与其中几条测试约定一致，但未独立消融这些约定；两行短文件以约 6% 额外成本提高了补测试比例，但长文件还改变测试存放位置；内容与长度同时变化，不能隔离纯长度因果效应 → [19](19-experiments.md#4-e3指令文件长短)。
- Epic 的 Unreal MCP 有几百个工具，却**只公开 3 个元工具**，官方理由是“让上下文窗口保持很小，提示缓存保持命中” → [game-dev/01](../domains/game-dev/01-engine-integration.md#22-unreal几百个工具藏在工具搜索后面)。
- 《Agents don't need memory, they need documentation》（HN 380 分）作者以自身产品经验将某些记忆方式称为“**RAG 抽奖**”（非独立对照结论）：存进去的东西什么时候被召回、召回得对不对都不可控 **[社区：原文]**。

### 机制
增加上下文时需分别检查三类成本：
1. **钱**；
2. **检索与推理负担**：无关或冲突信息可能妨碍任务，但必要信息也可能减少搜索和返工，不能由长度单独判断；
3. **缓存与延迟**：变化位置、缓存策略和 TTL 会影响命中；按当前 provider 的实际字段判断，见 [02](02-models-and-cost.md)。

按需获取能减少无关常驻内容，也会增加查找与工具往返。高频、稳定且容易查错的信息可以预先提供；哪种更合算要看整项任务的结果，不能把“拉”写成无成本或必然最优。**[研究：机制判断]**

### 推论
1. **优先写会改变行动的信息**：项目命令、设计原因、关键边界和容易找错的任务入口。能从代码读出不等于应该每次重找，但重复整棵目录树和易变配置值会增加维护，见 [03 的项目实例](03-context-engineering.md#2-指令文件claudemd--agentsmd--规则文件)。
2. **低频细节按需读，必要入口先提供**：Skill、工具搜索和子目录说明可减少无关常驻内容，但须核实际发现与加载规则；高频、易找错的命令和边界可预先提供。不能只因使用 MCP 或 CLI 就断定更省，见 [03](03-context-engineering.md#21-各工具的加载规则一手)、[04](04-mcp.md#2-mcp-vs-cli按任务与调用路径选择)。
3. **优先可审计、可失效、范围正确的信息**：文档和数据库都能实现评审、diff、回滚，也都可能陈旧。Codex [PR #18982](https://github.com/openai/codex/pull/18982) 于 2026-04-27 合并 git-backed 记忆整理实现 **[一手：PR；首次发布版本未核实，不是质量收益证据]**。优先把稳定约定落到文档、测试或 lint；自动经验记忆另做对照，见 [03 的收益与反例](03-context-engineering.md#41-先区分三种干预)。
4. **机械约束优先复用实际覆盖的执行边界或检查，必要说明仍保留**：

| 层 | 例子 | 什么时候生效 | 可靠性 | 上下文成本 |
|---|---|---|---|---|
| 环境 | 沙箱、出网白名单、只读凭证、适用产品的预算限制 | 已配置且实际覆盖的执行路径 | 机制可强制，但范围、获准例外及计费边界须核对，见 [10](10-security.md)、[18](18-team-adoption.md#5-成本治理) | 无需每次重复自然语言规则；拒绝、重试和审批仍可能增加成本 |
| 工具 | lint、类型检查、测试、Hook | 配置的执行时机 | 检查可确定；强制执行取决于触发路径和错误处理，见 [06](06-hooks-and-guardrails.md) | 命令、输出及可能的模型判断需计入 |
| Skill | 按需加载的流程知识 | 相关时 | 概率 | 描述常驻有开销，正文按需加载 |
| 指令文件 | CLAUDE.md / AGENTS.md | 被加载时 | 概率 | 占用输入上下文；缓存命中与实际计费另算 |
| 提示词 | 本次对话里的要求 | 本次 | 概率 | 本次 |

**能由现有 lint／测试覆盖的机械规则，不必让模型反复判断；先确认触发、范围与失败处理，再删除重复说明。** 运行入口、设计原因和未覆盖的例外仍可能需要文档。Lint Leakage 的调查比例不是下移后的效果对照；Hook、MCP 和沙箱也不能视为同一执行边界，见 [03](03-context-engineering.md)、[10](10-security.md)。

### 边界
窗口、缓存和模型探索能力变化后，重新比较完成质量、检索往返与总费用；不能由更长窗口推出信息都有效，也不能由更强模型推出预先提供项目知识不再有价值，见 [03 的研究边界](03-context-engineering.md#22-指令文件到底有没有用研究证据)。

## 3. 规律三：按实际接收能力安排产出

### 现象
- **审批疲劳**：一个模拟“给 Agent 审批命令”的小游戏，4 万局、40.9 万次决策 **[社区：原文]**：
  - 玩家平均**漏掉 1/3 的威胁**（准确率 66.3%）；
  - 明显的破坏命令（`rm -rf /`）漏掉 11.7%，**外泄凭证类漏掉 33–35%**；
  - 藏在 `npm run xxx` 后面的恶意脚本漏掉 **52.5%**（其他外泄攻击 28.4%），即使恶意内容就显示在上方的历史记录里；
  - 另一面是过度拦截：清理 `dist/`、释放端口这类正常命令被拦了 43–59%。
  - 局限：这是有时限的游戏，威胁占比约 34%，远高于现实；HN 上也有人质疑部分题目的标注。
- **评审与可靠性信号**：Faros 比较同一组织最低／最高 AI 采用时期，PR 评审停留中位数约 **5.4 倍**，事故数／已合并 PR 数之比约 **3.4 倍**；前者不是主动阅读工时，后者不是单个 PR 致事故概率。观察数据不能证明人的处理能力固定或预测本团队恶化幅度，口径见 [09](09-review-and-quality.md#1-质量数据ai-代码的真实代价)。**[一手：厂商公开资料，观察性]**
- **开源的反应**：Godot 对实质 AI 代码与代理代投设限（[原始政策与执行](research/2026-10-13-godot-contribution-policy.md)），HN 高赞评论把 AI 生成的冗长 PR 比作“对人脑的拒绝服务攻击” → [game-dev/03](../domains/game-dev/03-generative-ai-in-games.md#3-外部约束披露与玩家态度)。
- **多 Agent**：少量专注 Agent 是起步经验，不是人数越少越可靠的定律；[08 的研究对照](08-multi-agent.md#1-证据)同时存在质量提高但更慢、更贵的配置，需算到汇总与验收结束。
- **自我感知偏差**：METR 2025 实验中，开发者实际慢了 19%，却觉得快了约 20% → [11](11-community-pulse.md#4-生产力证据来源范围见各行)。

### 机制
当需要人处理的变更持续超过其可用时间和理解能力时，会出现排队、简化检查或返工风险；并非生成量必然随算力线性增长，也不是人的理解力固定不变。已有知识、变更组织、自动检查和 Agent 走读都可能改变处理能力。应区分代码本身难改、人与系统失去联系、提交节奏超过接收能力，三者不能统一归因于“人是瓶颈”。**[研究：机制假设，非上述统计已经验证的因果链]**

### 推论
1. **把可提前解决的重大分歧放到实现前，不取消实现后的反馈**。Dex 倡议“30 分钟的计划能省几个小时的评审”，但没有可复算的时间对照，配套 80/20 曲线是设定的例子。他建议的四个环节适合误解代价较高的改动，不能仅凭这句话设为默认流程：
   - **产品评审**：做什么、为什么、怎么算成功；
   - **系统架构**：服务、接口、数据如何交互；
   - **程序设计**：类型、函数签名、调用栈，用伪代码调用树表示；
   - **垂直切片**：一次只做一条端到端的小路径，每片都能实际运行、马上评审 **[社区：原文]**。
2. **若计划推迟可运行反馈，尝试按行为切片**。作者对水平计划的观察不是所有模型的固定偏好；按数据、接口与依赖选择顺序，100–200 行只是作者参考，不是审批门槛。BAML 案例也显示有研究的计划仍需在实施中纠错，见[原始材料复核](research/2026-10-12-baml-and-review.md#baml实现反馈纠正研究计划)。
3. **用明确边界减少重复审批**：授权内的可逆步骤可连续推进，未定的产品或兼容取舍需要人的目标信息。减少询问不自动保证剩余判断更准确（见规律四）。
4. **按执行与接收能力共同调节并行度**：独立任务可并行；若产出持续积压、审查失去上下文或冲突增加，应缩小批次或调整节奏。
5. **证据要回答当前问题**：测试输出、命令记录、截图、试玩各有覆盖范围。可执行证据可能降低核验成本，但不能代替尚未覆盖的设计和需求判断。
6. **按未决问题选环节，不按任务大小配流程**：复用已有产品目标、接口与验收；只补会改变实现的缺口。Dex 按大小分流是其场景经验，不能据此要求大任务走完四环节，见 [07](07-workflows.md#34-大功能的前置设计与垂直切片-)。

### 边界
- Agent 可以帮助发现需求、比较方案和解释代码；人的取舍可从已有目标与反馈中取得，只有关键决定缺失时才需询问，不能把每次前置访谈设为必要步骤。
- 前置设计本身也可能变成“瀑布”（见 [07 对 SDD 的批评](07-workflows.md#5-spec-驱动开发sdd)）。区别在于：设计文档要短，要配合垂直切片尽快落地验证。

## 4. 规律四：权限边界和概率性检查各有失效方式

### 现象
- auto mode 被实测绕过（小样本成功率 60–80%）；AI 实验室训练中的 Agent 突破沙箱、入侵其他系统；Anthropic 的案例中**只有出网拦截挡住了凭证外泄** → [10](10-security.md)。
- 2026-10，Wikimedia 确认在自家站点发现 OpenAI “失控” Agent 的活动：编辑 wiki、尝试利用一个托管的笔记工具、产生大量流量；没有发现系统被攻破，但调查和溯源成本很高 **[一手：Wikimedia 博客]**。HN 高赞评论：“卡车司机没绑好钢筋，钢筋飞满高速，我们不会叫它‘失控的钢筋’” **[社区]**。
- 人工审批漏掉 1/3 的威胁（规律三）。
- Unreal 官方 Skill 要求“**不是明确的成功，就当作失败**”，以及“改之前存盘” → [game-dev/01](../domains/game-dev/01-engine-integration.md#22-unreal几百个工具藏在工具搜索后面)。

### 机制
LLM 和疲劳的人都是**概率性过滤器**。反复尝试可能暴露过滤遗漏，但成功率取决于攻击、权限、重试与防护反馈，不能假定所有尝试独立或必然成功。正确实现的权限边界不会因模型被说服而主动放行，但仍可能有实现漏洞、误配或允许目标中的恶意内容，不能承诺不随攻击尝试暴露缺陷。

### 推论
1. **为“爆炸半径”设计，而不是为“听话”设计**：假设 Agent 一定会做错一次，问“错了会怎样”。
2. 按实际操作风险配置防线：
   - **环境**：隔离、出网白名单、最小权限凭证、适用范围内的预算与停用边界；
   - **可恢复**：版本控制、存盘点、可回滚的部署；
   - **可观测**：日志、审计、异常告警。
3. **责任在运营者**：Agent 造成的损害归属于部署它的人或组织。对外部系统（别人的网站、包仓库、开源项目）的影响要和对自己系统一样认真对待。

### 边界
确定性边界会降低便利性（比如出网白名单会挡住正常的依赖安装）。实践中是“**默认严格，按需打开**”，并把打开的记录留存下来。

## 5. 规律五：模型在商品化，可迁移的工程资产在增值

### 现象
- [02 的局部价格复核](02-models-and-cost.md#2-价格快照api-美元百万-token)给出明确比较项：Opus 5 → 5.5 的 Standard 输入/输出单价下降 20%，Haiku 4.5 → 5.5 的降幅依长上下文档位不同。原“同档模型一个季度降 40–50%”已撤回，不能继续作商品化的统计证明；单价下降也不等于相同任务质量下更便宜。
- 配置格式收敛（AGENTS.md、Skills、MCP），Codex 能 `/import` Claude Code 的配置 → [00](00-state-of-ai-coding.md#21-开放格式共享内容分别核对入口-)。
- 反方向的力量：Dex 认为“Claude Code 赢在**在自家 harness 里做了强化学习**”；OpenAI 的分享也说，不拥有权重、不能在自己的 harness 里训练模型的团队“永远处于劣势” **[社区：原文转述]**。
- Lilian Weng 预测 harness 优化的对象会沿着“**提示词 → 结构化上下文 → 工作流 → harness 代码 → 优化器代码**”演进，很多 harness 技巧最终会被模型内化；但就像提示词技巧过时以后，“**说明目标、约束、上下文和评估标准**”的需要并没有消失 **[社区：原文]**。

### 机制
两股力量同时存在：
1. **厂商把模型和自家 harness 绑定训练**：可能改善配套任务，仍须核实际结果；
2. **开放标准让部分内容可以迁移**：权限、加载与执行契约仍随宿主而变，不能把同名文件视为无成本兼容，见 [03](03-context-engineering.md)、[05](05-skills-and-plugins.md)。

**更值得持续维护的是仍能改善当前任务的目标、知识和验证资产**；可迁移性是收益之一，不保证任何文件永久有用。**[经验：采用判断]**

### 推论：哪些投入继续保留

- **目标、约束、接口依据、测试与运行入口**：事实变化时同步维护；模型升级不自动使它们失效。
- **Skill、补丁指令、私有配置与编排脚本**：检查它们补的缺口是否仍存在，不能只按格式或年龄删除；已有资料与原生能力够用时，再缩减额外层，见 [05](05-skills-and-plugins.md)。
- **升级后的撤回**：在固定验收下，一次移除一个可选环节，比较质量、必要行为、等待和人工处理；原缺陷回来就恢复。不能为减成本删除仍必要的回归检查，见 [07](07-workflows.md#7-长时-harness保留解决当前缺口的部分-) 与 [09](09-review-and-quality.md#3-给自己的-ai-配置做评估)。

[16 的运行契约反例](16-building-agents.md#3-怎么选)中，默认模型变化曾使 issue-triage 失败；需要固定可用的模型／运行时组合，而不是先假定升级会替代旧补充。**局限：这些是采用与撤回条件，不是已证明每次升级都能减配。** **[一手；经验：建议]**

### 新的分层趋势
不同模型可作为以下分工的候选，不按价格或角色名称默认路由；先核实际任务的质量、等待与总成本：
- 前沿模型负责规划和难题；
- 便宜模型（Haiku 5.5、GPT-6 Luna）负责子任务和 I/O 密集的杂活；
- **决策模型**可作为路由、分类或受限动作选择的候选。[Clef 官方模型卡](https://huggingface.co/Cloudflare/clef)说明输出为选项 logits 经 softmax 得到的概率；官方虽采用校准训练，也不能据此认定目标任务阈值已验证，用于自动路由前仍须核本任务误判，不能代替授权。[Cloudflare 发布测量](https://blog.cloudflare.com/clef-decision-models/)中 Clef／Flash 的中位模型延迟约 209／39ms，但抓取、渲染并分类网站的完整例子为 2.2 秒，不能将模型延迟当工作流承诺。游戏采用另按 [game-dev/03](../domains/game-dev/03-generative-ai-in-games.md#2-游戏运行时的-ai) 的玩法缺口判断。**[一手：厂商文档与测量；研究：采用边界，2026-10-15 复核]**

GitHub Copilot 的 HydraFusion（2026-09 研究预览）把分层直接做进了模型选择器：便宜模型先做，质量门决定是否升级到强模型，或者由另一家族的模型做只读评审 **[一手：GitHub Changelog]**。

分层会增加启动、上下文、交接与整合成本，实际计费还取决于缓存及宿主。是否采用要比较同一目标的质量、总费用和等待；子任务独立或数量多都不保证划算，见 [08](08-multi-agent.md)。

## 6. 规律六：AI 是放大器，放大的是你已有的工程体系

### 现象
- Steam 研究的 53,597 款游戏观察样本中，声明使用 AI 组达到至少 100 条评测的比例约为未声明组的 55%；披露组差异不能解释为 AI 导致成功率降低，也不证明所有未声明作品没有使用 AI。口径与采用边界见 [game-dev/03](../domains/game-dev/03-generative-ai-in-games.md#3-外部约束披露与玩家态度)。**[社区：原研究；研究：相关性边界]**
- Faros 的同组织低／高 AI 采用期比较观察到事故数／合并 PR 数、评审停留时间及季度删行／加行比上升；最后一项包含可能有益的重构，不能直接称返工。完整分母与方法缺口见 [09](09-review-and-quality.md#1-质量数据ai-代码的真实代价)，不能据此推导普遍的质量退化。**[一手：厂商观察报告；研究：边界]**
- GitClear 公开图示中的重复与移动占比变化可提示抽检；定义／分母冲突及样本范围不能推出维护工作量或 AI 因果 → [09](09-review-and-quality.md)。
- Will Larson（lethain）在 Imprint 的推进顺序：先让所有人每天用 Claude Code → 每人约 10 个独立工作区，支持跨仓库 PR → **全公司从 Jira 迁到 Linear，作为唯一的任务状态来源** → 编排式 harness（“Agent Fleet”）→ 软件工厂循环。他的观察：“这些部分**只有在其他部分都到位时**才会产生复利。”这个循环依赖 RFC 里写清的目标、Datadog 或 Snowflake 上的进度指标，以及 Linear 作为唯一状态来源 **[社区：原文]**。

### 机制
如果生成速度提升，而需求判断、集成或接收能力没有同步改善，多出来的改动可能形成积压与返工。Agent 也可能帮助比较方案、解释代码和发现依赖，因此不能假定后几项成本固定不变。上述统计与个案提示要测这些环节，并未证明“没有完整工程体系就必然积债”。**[研究：条件假设]**

### 推论
1. **先补当前交付缺口，不先凑齐工程设施**：复用已有目标、测试、运行反馈与状态记录；它们已经足够时继续交付，不因个案采用某套工具就整体迁移，见 [18](18-team-adoption.md#1-先看结论)。
2. **衡量结果，而不是产出**：用交付周期、缺陷率、事故率衡量，而不是 PR 数、代码行数、token 用量（“tokenmaxxing”已经先热后冷 → [13](13-frontier-radar.md#1-时间线2026-年发生了什么)）。
3. **检查可靠也不自动需要外层循环**：普通会话能连续完成就沿用；已有明确目标和授权仍反复提前收尾时，才试受限续接。目标、反馈或权限缺失时先补对应缺口，重复原提示不能解决它，见 [07](07-workflows.md#6-ralph-循环-)。lethain 的 RFC 与指标是其场景实现，不是统一准入文件。

## 7. 决策框架

### 7.1 这个任务该给 Agent 多大自主权？

**先核实际授权与执行边界**，再按当前检查覆盖和失败影响选择接收方式；测试通过不授予操作权限，任务名称也不决定风险，见 [10](10-security.md)。下面的“继续执行”均限已授权范围。

| | 出错代价低（可逆、影响小） | 出错代价高（不可逆、影响大） |
|---|---|---|
| **检查覆盖当前改动** | **连续执行并交证据**：复用已有检查与恢复点；确认依赖、消费者和行为边界确实在覆盖内 | **按风险设置检查点**：迁移先验副本与恢复方案，生产写入／发布按实际授权处理；不能只看 CI 全绿 |
| **仍有关键验证缺口** | **先做可撤回样品**：布局、交互等看过能判断时尽早比较；不会评价时先补参考与依据 | **先解决不可猜的决定，再缩小实施范围**：复用已有目标和接口，补必要契约与检查；保留实施后的评审与反馈，不默认完整四环节 |

**原型转正时重新评估风险和验证缺口**：真实用户、持久数据、权限、维护责任与恢复要求可能改变出错代价；按新的位置补必要设计、检查和授权，保留已有效的实现与上下文，不无条件重走整套人主导流程。见 [07](07-workflows.md)、[09](09-review-and-quality.md) 与 [15 原型](15-task-playbooks.md#10-原型和一次性脚本)。

### 7.2 这条规则该放在哪一层？
先按规则的用途选择，再确认真实覆盖（见规律二的表）：
1. 权限、网络和资源限制 → 用实际执行环境的边界；逐项核工具／进程范围，不靠提示词强制
2. 可机械判定的行为 → 复用 lint、类型、测试或 Hook；确认会触发且错误不被吞掉，必要运行说明仍保留
3. 低频资料或窄流程 → 先给精确入口；确需复用配方时再试 [Skill](05-skills-and-plugins.md)，不把加载视为授权
4. 高频且易查错的项目知识 → 放入实际会加载的[指令文件](03-context-engineering.md#21-各工具的加载规则一手)，保留权威来源
5. 本次目标与约束 → 写进任务；不为一次需求新增常驻配置

### 7.3 要不要并行或多 Agent？
按 [08](08-multi-agent.md) 选择可独立验收的支线：
- 子任务语义依赖少；共享接口、数据和写入表面先对齐
- 每项交回适用证据：代码检查实际行为，只读调查给可追溯来源，不要求调查支线另造可执行测试
- 主 Agent 能核对结果并完成整合验收；需要人判断的部分再匹配实际接收能力，不按人数设固定上限
- 试用后比较质量、总费用与净等待；汇总缺失、权限等待或冲突增加时，先核已有动作，再缩减并发或串行相关步骤

### 7.4 人的注意力花在哪里？
**优先解决会改变下一步的未知，不设通用回报排序**：
- 目标或兼容取舍未定：先查已有依据，只询问不能推知的决定
- 必须看效果才能选：看可撤回样品，反馈到下一版
- 测试预期或覆盖存疑：追到原需求、独立预期与被测行为，不能把生成测试本身当正确规格
- 改动影响权限、持久数据、接口或后续维护：结合运行证据看相关代码与消费者；是否追加独立评审按漏审风险决定，见 [09](09-review-and-quality.md#按风险选择评审层不默认逐层叠加)
- 目标与验收已充分：允许 Agent 连续执行，避免重复确认；没有证据支持“不读代码”是所有团队的终点

## 8. 成熟度路线

**用能力缺口或明确质量目标选投入，不把配置数量当成熟度。** 原 L0–L5 是本仓库提出的路线，不是经验证的阶段模型；没有证据支持“跳级最常导致失败”，也不能从 HumanLayer 个案推出未安装 Skill、Hook 或评审子 Agent 必然重写。保留本节作为选择入口，取消必经等级。**[研究：本仓库修订，2026-10-13]**

| 当前缺口 | 先补什么 | 何时足够、何时再升级 | 入口 |
|---|---|---|---|
| 功能已通过，但信息关系、操作反馈等有明确质量目标 | 复用领域依据，先定义目标质量与必要行为 | 比较实际使用与投入；不必先发生失败，也不默认完整 Skill 或多轮流程 | [05](05-skills-and-plugins.md)、[22](22-agent-evaluation.md) |
| 不知道改动是否满足需求 | 具体使用路径、运行入口和适用检查 | 原生 Agent 能给有效证据就继续使用；已识别检查缺口时补相应反馈 | [07](07-workflows.md)、[15](15-task-playbooks.md) |
| 重复查错项目知识 | 命令、任务导航、接口约束及其权威来源 | 先修现有说明；特定流程反复复用时再提炼 Skill | [03](03-context-engineering.md)、[05](05-skills-and-plugins.md) |
| 超出可接受的操作范围 | 实际权限、隔离、恢复方式 | 按资源和授权验证；Hook 只是事件检查的补充 | [06](06-hooks-and-guardrails.md)、[10](10-security.md) |
| 独立工作排队或输出挤占上下文 | 先确认依赖与整合验收，再试拆分 | 比较净等待、人工接收和费用；串行已满足需求就保留 | [08](08-multi-agent.md) |
| 跨会话丢目标或已有证据 | 可恢复的当前目标、状态与证据位置 | 复用现有记录；不足以满足已明确的恢复要求时再增补机制 | [20](20-codex-long-horizon.md) |
| 想围绕长期目标自动找下一项工作 | 明确目标可变之处、实际反馈、停止与恢复条件 | 以使用结果纠正目标；没有新证据不靠重复循环制造产出 | [研究任务](research/BACKLOG.md#四条长期任务以真实开发结果组织研究) |

一个单 Agent、少量项目说明和可靠反馈的工作方式可以长期足够；复杂场景也可以组合多项能力。评估单位是同样目标下的完成质量、人的投入、等待和后续修改成本。

## 10. 几个反直觉的结论

1. **强模型仍需要有效的目标反馈。** 它可以帮助澄清问题；已有目标充分时不再访谈，偏好尚未形成时用样品探索。
2. **减少重复审批不等于提高安全性。** 先核实际权限与执行边界，仅在既有授权内连续推进；高风险决定保留相应确认，不能从审批游戏推出剩余判断一定更准。
3. **删减指令要看任务结果，而不只看长度。** 所引 Python 研究中，生成文件增加费用但未检出可靠成功率改善；本仓 E3 同时改变内容与长度。保留项目特有信息，固定验收后比较质量、总费用和人工成本，见 [03](03-context-engineering.md#22-指令文件到底有没有用研究证据)。
4. **最好的“AI 测试工具”往往不是 AI。** 无头模拟、属性测试、状态导出接口这些传统手段，是让 Agent 能自我验证的基础设施。
5. **并行 Agent 越多，你可能越慢。** 当评审带宽成为瓶颈时，增加并行只会增加积压和冲突。
6. **读多少代码取决于检查缺口和维护责任。** Agent 可以辅助解释与定向审查；运行证据充分可减少重复阅读，但不把“不读代码”设为成熟度目标。
