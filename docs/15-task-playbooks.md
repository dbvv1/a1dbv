# 15 · 按任务类型的打法

> 更新：2026-10-16（UTC+8）。本页给任务起点；Codex 的[五情境入口](01-agents/codex.md#五种情境先做最小改变)说明何时再加知识、工具或流程。来源、版本与验证范围见各节研究链接。
> 依据包括 Anthropic 官方最佳实践与 Opus 5.5 指南 **[一手]**、Willison 与 HumanLayer 的公开实践 **[社区]**；没有单一出处的组合方法标为 **[经验]**，案例来源与审计范围链接到研究页。

## 0. 总表

| 任务 | 最大的风险 | 关键动作 | 验证手段 | 自主度（见 [14 第 7.1 节](14-synthesis.md#71-这个任务该给-agent-多大自主权)） |
|---|---|---|---|---|
| [理解陌生代码](#1-理解陌生或遗留代码) | 自信地讲错 | 只读探索 + 要求引用文件和行号 | 抽查引用 | 高（只读） |
| [调试](#2-调试) | 修症状不修根因、改测试让它通过 | 先收集失败证据，能复现就复现；已定位且获授权则修复 | 相关回归测试与实际路径，说明未验证项 | 按风险与授权 |
| [新功能](#3-新功能) | 方向错、堆出难维护的代码 | 按未决需求、接口与验证缺口选择计划；用可运行的**垂直切片**提早反馈 | 每片都能实际运行 | 按授权推进，关键需求取舍由人定 |
| [重构](#4-重构) | 行为悄悄改变 | **先写特征测试** | 重构前后测试一致 | 中高 |
| [大规模迁移](#5-大规模迁移与升级) | 统一改法漏例外，或跨依赖／状态受损 | 先选现成迁移器或 Agent 补丁，再按机制试点扩量 | 跨文件消费者、重跑与恢复边界 | 按风险、覆盖与授权 |
| [补测试](#6-补测试) | 写出永远不会失败的测试 | 区分 bug 回归与既有行为保护 | 回归 red/green；关键断言用反例或变异检查 | 高 |
| [性能优化](#7-性能优化) | 凭感觉改、没有数据 | 测量瓶颈并确定不能改变的行为 | 基准数据 + 语义对照 | 按影响与授权 |
| [代码评审](#8-代码评审) | 挑刺、过度设计 | 新会话 + 只报阻断性问题 | 每条都要说明如何证明 | — |
| [文档与杂活](#9-文档提交信息发布说明) | 事实、权限或兼容说明写错 | 按推理需求和错误代价选模型 | 核对来源、命令和相关行为 | 按风险 |
| [原型和一次性脚本](#10-原型和一次性脚本) | 造完整替代却没人改用，或把原型直接当生产代码 | 比较现成方案、局部补充与完整替代，再按真实使用补差距 | 试验目标；真实用户或数据另需安全与恢复检查 | 高（限已授权范围） |

## 1. 理解陌生或遗留代码

**✅ 先只读走通一条实际调用路径。** 用 Plan 模式或只读探索，明确不要改文件；要求每个结论引用文件与行号，分开确认与推断。按请求的执行顺序写线性走读，术语混乱时再维护带代码例子的 `GLOSSARY.md`。**[经验：采用判断；社区：Willison 的 linear walkthrough]**

```
阅读 src/billing，按一次“月度结算”的执行顺序讲解调用链。
每一步给出文件:行号；分开标注“读代码确认的”和“推断的”。
不要修改任何文件。最后列出需要我确认的关键问题。
```

**局限**：面向人的走读不应自动变成常驻指令，仓库概览对 Agent 的收益需另验，见 [03 的研究](03-context-engineering.md#22-指令文件到底有没有用研究证据)。

## 2. 调试

**✅ 已有明确失败就复现、定位、修复、重跑；缺什么证据再补什么。** **[经验：采用判断]**

1. 优先用稳定失败的测试或脚本；无法本地复现时核对日志的版本、输入与环境，必要时加最小诊断
2. 根因不明就做能区分候选原因的小实验；已定位的小问题不必凑假设数量
3. 过滤日志后再读；稳定的回归脚本可交给 `git bisect run <复现脚本>`
4. 补回归，测试本身有独立错误才修测试；禁止为变绿削弱断言、删除用例或改变未授权的行为
5. 先跑相关检查，再按影响扩展集成/全测；仓库必跑入口照做，实际路径可用 curl、短脚本或浏览器补验

主要依据是 [BAML 双 PR](research/2026-10-12-baml-and-review.md#baml实现反馈纠正研究计划)：调查帮助选择更窄的修改位置，但有研究的计划也把测试输入写错，实施时仍需纠正。研究应回答修哪层、保留什么，而非每次先写全仓报告。**[一手：历史补丁；研究：采用判断]**

**兼容修复按输入机制选范围，不只按版本高低。** 某版本修好一类数据，仍可能损坏另一类；升级消费者或全局关闭能力前，先判断哪些输入需要该能力。OCRmyPDF 对超长映射块修生产端格式，对不可见拉丁文本跳过可选连字，但为复杂文字保留必要整形，见[两种故障与修复取舍](research/2026-10-12-development-conditions.md#ocrmypdf兼容修复按输入机制分流)。**局限**：这是特定文字处理链的固定修订，不证明所有输入或已交付旧文件已恢复，也不量化 AI 收益。**[社区／一手；经验：修复选择]**

**局限**：无法复现时的局部修复仍有验证缺口；预期冲突、关键输入或权限缺失须说明具体阻塞并询问。

## 3. 新功能

**✅ 按不确定性决定计划深度，先交付一条可运行路径。** **[经验：采用判断]**

| 尚未确定什么 | 做法 |
|---|---|
| 目标、接口和验收已有依据 | 在授权内直接做并验证，不因规模大补齐流程 |
| 业务规则或兼容契约未明确 | 先澄清会改变实现的取舍，再更新已有计划 |
| 跨层依赖或可运行反馈路径未清楚 | 梳理必要接口／调用关系，选能尽早试用的垂直切片 |

按真实接口与依赖打通一条最小路径，每片可运行，不统一规定前端与数据库的实施顺序；100–200 行可供拆分参考，不是等待人批准的门槛。一次给出任务、完成标准与需询问的取舍；跨会话在已有记录保存最新目标、约束、结果与下一步。**[一手：Opus 5.5 指南；社区：HumanLayer；经验：切片建议，见 [07](07-workflows.md#34-大功能的前置设计与垂直切片-)]**

**✅ 新增视图先复用语义相同的业务组件，等具体需求出现再补窄扩展点。** 让 Agent 说明下一需求落在哪层、哪些旧调用者要一起检查。Discourse 的 AI 参与 nested replies 实现复用了 TopicCategory；四个月后，另一贡献者为客户插件增加扩展点，只改共享分类组件与 docked header，保留两种视图共用路径，见[前后源码与交付边界](research/2026-10-12-development-conditions.md#discourse共享组件承接后续需求)。**[一手：公开源码与后续 PR；研究：采用建议]** 这是一次局部扩展落地的证据，尚无客户上线复测或维护时间收益。

**局限**：旧计划不能锁住新反馈，恢复时须核对当前代码与授权，见 [20](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史)。

## 4. 重构

**✅ 先锁定行为，再做小步等价修改。** 补特征测试，包括看起来奇怪但需保留的行为；每步之后运行相关检查。机械改名先用已有 IDE／语言重构；同一调用规则重复多处且现成 codemod 已覆盖时优先复用，少量异质调用或业务含义需逐项判断时由 Agent 直接补丁。评审专查是否复制了已有实现。**[经验：采用判断]**

**清 lint 时，先确认诊断适用于真实调用契约。** 即使没有 `await`，异步测试仍可能依赖运行器提供的上下文，JavaScript 调用者也可能依赖 Promise 拒绝处理；有这种明确需要时，保留边界并说明原因、窄范围豁免对应规则，不机械删 `async` 或为消警告加入无业务需要的等待。确属无意保留且调用者不依赖异步契约时，再改为同步并验证。Ruff 的 RUF029 只报诊断、不提供自动修复；其用户报告与文档修订、ESLint 的反例支持这种选择，见[原始报告与实现边界](research/2026-10-12-development-conditions.md#清-lint保留异步调用契约还是删除-async)。**局限：规则豁免不能代替行为验证，这些材料不证明 Agent 净收益。** **[社区／一手；经验：采用判断]**

GitClear 公开材料的重复与移动占比信号可提示检查复用和结构；不能据此设重构配额，也不证明某个项目维护成本上升，定义／分母冲突见 [09](09-review-and-quality.md)。**[一手：厂商公开材料；研究：采用边界]**

**局限**：群体相关性不能证明当前 Agent 必然倾向复制，重构是否正确仍由本项目行为对照决定。

## 5. 大规模迁移与升级

**✅ 先选改法，再试点扩量。** 已有工具覆盖同类调用时优先复用；语法规则适合来源和调用形状明确的重复变换，跨文件引用、继承或类型缩窄优先现成的类型／框架迁移器，例外交 Agent 补丁。试点按这些差异选样，不把前几个文件通过当全量覆盖。TanStack 的真实迁移既有省重复劳动的报告，也有成功退出却漏改；Angular 则会保守跳过不兼容情形，见[维护链与固定源码](research/2026-10-12-development-conditions.md#重复代码迁移语法规则类型分析与第二次执行)。**[一手／社区；经验：采用判断]**

**依赖与数据边界明确后，再选批处理方式。** 需要脚本调度可用 `claude -p`；并行或 `/batch` 只拆可独立验收的单元，共享接口、分析范围或持久状态相关的步骤先按依赖处理，再验整合结果。worktree 隔离不等于语义独立；有检查也不自动授权高影响操作，恢复条件见本节下文，并行取舍回 [08](08-multi-agent.md)。官方的小批试跑是配方，不是通用样本门槛，见[入口收敛依据](research/2026-10-12-development-conditions.md#批量入口先选改法再选执行方式)。**[一手：官方契约；经验：采用判断]**

**准备重试或复用时，检查第一次产物再跑是否还会变。** 同时核对分片文件归属与调用次数，保留已迁移调用和跳过原因；一次性迁移器从固定可恢复起点重做，不盲重跑。出现重复变换、覆盖不清或例外过多就暂停扩量，修规则或退回局部补丁。第二次需求改变契约时须更新规则并复验旧行为，重跑零 diff 不等于语义正确。**局限：上述历史修复与源码机制不证明当前 Agent 的同任务净收益，也不表示已修复缺陷仍存在。** **[一手／社区；经验：采用与停止条件，证据同上]**

**交互试点转脚本时，先保住迁移所需的项目知识。** 普通 `claude -p` 会加载项目上下文；可选的 `--bare` 会跳过 `CLAUDE.md`、Skill 等自动发现，两者不是等价启动方式。在已审查的可信项目中，需要这些约束时保留普通模式，或只显式提供本次必需的上下文与工具；不要为减少启动开销漏掉项目约定，也不必复制全部指令。`--bare` 自 2.1.286 起不再启动后台任务，超时命令会停止；依赖后台构建结果的迁移应保留支持该路径的运行方式。外来仓库先按 [10 的配置来源边界](10-security.md#3-防护原则)限制启动配置；上下文选择见[官方契约与采用边界](research/2026-10-12-development-conditions.md#交互试点转脚本bare-不是等价加速)。**[一手：官方文档与固定发布说明；经验：采用判断，未运行客户端]**

跨语言还应沿一条真实路径检查“谁分配 → 返回后谁用 → 何时释放”，把真实失败转成内容与清理回归。[VibeTunnel](research/2026-10-12-vibetunnel-maintenance.md) 的无 upstream 仓库暴露了返回切片过早释放，第一次 arena 修复还需纠正 allocator 绑定对象。**[一手：公开维护补丁；经验：采用判断]**

混用版本或需要降级时，让旧版本读取新版本实际写过的状态，并检查恢复后后台任务会不会再生成不兼容产物。[Git MIDX 的默认格式回退](research/2026-10-12-vibetunnel-maintenance.md#持久状态回退git-midx-的旧读取者边界)源于 rc2 的 fetch 使旧 Git 无法读取同仓库；最终保留显式 compact 的新格式能力，收窄普通写入默认值。**[一手：原始讨论与固定补丁；经验：迁移验收建议]** 这是非 AI 项目的机制证据，未取得最终修订后的原用户复测。

**配置回退设计应保留既有数据的读取能力。** 关闭新格式写入后，用开启前、开启后和关闭后写入的混合数据，分别验正常服务及实际用于导出／恢复的一次性命令；同版本关闭开关不等于旧版本可读。n8n 先拆开读写开关，随后才把读取依赖初始化提前到所有命令入口，见[固定修订与作者运行报告](research/2026-10-12-development-conditions.md#n8n配置回退与独立导出入口)。**[一手：补丁；社区：作者报告；研究：采用建议，导出路径测试未独立运行]**

**迁移后的回退，还要验升级期间的业务变更。** 若回退会恢复旧快照或删除新系统数据，先查明恢复时间点、哪些新增和修改会丢失，在隔离数据上验证恢复方案，再由负责人决定保留、转换或接受损失；只有损失已被明确接受、恢复方案已验证时，才有条件使用强制回退，不能仅为恢复启动绕过保护。[Grafana 的历史回退记录](research/2026-10-12-development-conditions.md#grafana回退的恢复时间点与保护性拒绝)中，维护者保留阻断并澄清删除后果，另有用户清表后能启动却已无警报。局限是非 AI 项目的历史机制与用户报告，未独立运行。**[一手：固定源码与文档；社区：用户报告；经验：采用判断]**

试点还应覆盖跨文件行为与资源契约；系统职责改变时，确认事实现在应向哪个服务查询，避免结果相同却仍在旧层扫描或重建状态。[Scion 迁移复盘与兼容反例](research/2026-10-12-development-conditions.md#迁移后的事实归属与旧调用方式)支持这项窄检查，不要求机械改名套用全部检查。**[经验：采用判断；一手：团队自述，未独立复测]**

## 6. 补测试

**✅ 用独立的预期保护行为，再确认测试能发现相关错误。** **[经验：采用判断]**

- 保护既有正确行为的测试可以直接通过，预期来自契约或独立依据
- 修 bug 优先 red/green：旧版本失败、修复后通过；关键断言可用反例或变异检查
- 通过公共接口观察结果，测试名写行为，避免断言 mock 返回值或照抄实现算法

主要依据是 Willison 的 red/green TDD 实践与[公共边界测试 Skill](research/2026-10-12-community-source-records.md#3-matt-pocock控制权与领域语言)。**[社区；一手：配置]**

**✅ 测试能失败，还要确认本次确实选中了相关消费者。** 依赖关系、预打包配置或非模块夹具改变时，显式运行已知消费者测试，或使用项目已有的触发映射；不能只凭 `changed`／`related` 成功退出收尾。选择与预期一致时保留原生增量运行，无须另加 reviewer、自建依赖图或默认跑全套。Vitest 的原生记录能力与漏选报告说明了这一区别，见[证据与选择边界](research/2026-10-12-development-conditions.md#增量验证已有回归测试是否真的被选中)。**局限**：选择器只覆盖它能看到的关系，选中并通过也不证明尚未表达的兼容要求。**[一手／社区；经验：条件建议]**

**🧪 新增选测能力前，先看实际慢在哪、常改什么。** 保留已经可靠的原生选择器；若准备为了提速再引入一套，先比较慢夹具／重复扫描的修复，以及项目已支持且能安全使用的并行。测试仍是瓶颈、常见改动能缩小到有意义的范围，才计入映射建立／刷新和漏选补跑成本后试用；不要只凭一次叶函数改动的快结果采用。remote-store 的公开试验选择暂缓引入，见[采用成本与反例](research/2026-10-12-development-conditions.md#新增选测能力先比较改动类型与完整运行成本)。**局限**：单仓种子试验不代表日常改动分布；不据此撤掉检查、放宽隐私规则或默认并行全部测试。**[一手：使用方报告；经验：采用判断，2026-10-16 UTC]**

接入外部格式或协议时，用目标版本生产者的公开、可脱敏产物校准预期；有独立证据时允许修正旧断言。RTK 的 Windows 编码修订同时纠正了实现与旧测试，不能拿本仓注释和测试的一致性替代外部兼容依据，见[维护链与局部模型](research/2026-10-12-development-conditions.md#外部生产者校准错误预期)。**[一手：修订；经验：采用建议]**

**预演还要保住下一次正式执行的边界。** 修改 dry-run／预演入口时，除业务数据不变，还要确认它不会悄悄更新下一轮接受配置或判定进度所用的状态；从已有基线连续验“修改→预演→普通执行”，该拒绝的仍应拒绝。日志和隔离的预演产物可以保留，不要求所有写入都消失。rclone 曾因预演更新过滤规则的接受 hash，使后续普通运行越过原有拒绝；修复保留预演列表，只阻止提交该 hash，见[固定修订与后续入口差异](research/2026-10-12-development-conditions.md#rclone预演不能替下一轮提交控制状态)。**局限**：历史测试预期与贡献者使用报告不是本仓复测，也不能把 CLI 修复推广为所有 API 传参方式已生效。**[一手／社区；经验：采用判断]**

新增写入路径时，同时验业务行与派生的版本／审计状态；若用序列化结果判等，既测它能接受哪些类型，也测业务上不同的值是否仍可区分。[sqlite-chronicle 的连续修订与固定 SQL 实测](research/2026-10-12-development-conditions.md#写入路径扩展与序列化判等sqlite-chronicle)中，BLOB 修复恢复写入，却让含 NUL 文本的 REPLACE 漏报版本变化；只看最终行正确或新类型不报错都不够。**[一手：修订；经验：本轮局部实测与采用建议，未运行包 CLI]**

**🧪 输入组合多、契约可表达且单次执行便宜时，补小范围属性测试。** 让 Agent 从文档和真实调用找不变量，用已有测试环境搜索反例；失败后先核对属性及有效输入域，再把具体输入、版本和随机条件固化为回归。NumPy 的 Wald 案例确实找到缺陷，但仍需人工数值分析及跨构建修订回归参数；dateutil 则因日历语义产生误报。[证据与局部实测](research/2026-10-12-development-conditions.md#属性测试搜索反例不等于确认或修好缺陷)。**[一手：维护链；经验：采用判断]**

**局限**：不能运行旧版本时保留回归缺口，但不要求每个新增测试都先在正确代码上失败；属性自身可能错误，属性通过也不证明所有精度、分布或业务要求。

## 7. 性能优化

**✅ 先给 profiler/基准、实际规模输入与完整命令，写清不能改变的行为。** 一次改一项，保留前后数据，多次运行看中位数；运行正确性测试，并按改动机制补旧测试漏掉的行为。**[经验：采用判断]**

**正确加速仍未达目标时，按新热点与剩余预算续改；只见 native 入口则先补内部耗时证据。** 保留各轮补丁与验证，最终选满足必要行为与目标负载的候选，不自动交末版或追单负载最高数；目标满足、无新依据或预算到限就停。依据见 PerfAgent 的[候选、最终评估与反例](research/2026-10-13-domain-skill-contract.md#性能续改观测层与候选选择)；局限是不同发布材料的运行身份未完全对齐，不证明当前客户端净收益。**[一手：保存产物；研究：采用判断]**

**需要探索不同实现时，先比较轻量候选搜索，不因候选多就接入完整进化框架。** 比较成本要包含未形成候选的生成、失败重试及复评；保存候选的费用汇总未必覆盖全部尝试。评分有波动时，先用较便宜的检查筛候选，再独立重测有竞争力的版本，并把未参与选择的输入留作验收；不要把预算全用来增加候选。依据见[轻量搜索比较与公开记账边界](research/2026-10-13-domain-skill-contract.md#竞争实现先比较轻量搜索并为复评留预算)。**局限：数学与AIME作者实验及源码支持这种比较，不证明生产软件收益，也没有完成单线续改与多候选的同条件净收益验证。** **[一手：论文与源码；研究：采用建议]**

**✅ 搜索赢家交付后，保留算法内核与扩大快路径适用范围是两项决定。** 接收方新增类型、比较器或输入规模时，先按其实际负载选择：适用范围明确且收益成立就保留窄快路径，其他输入走已有实现；共享分派重构引起回退时，拆开内核与入口变化再判断回滚，不用大输入收益抵消接收方只处理小输入的损失。libc++ 接收 AlphaDev 排序及后续重构的[审阅、回滚与重投链](research/2026-10-13-domain-skill-contract.md#搜索赢家接管后保内核还是扩大分派)支持这一区分。**局限：这是历史 RL 搜索与人工接管，不是当前 LLM 搜索的净收益验证；没有新负载或入口变化时，不为此重建搜索流程。** **[一手／社区；研究：采用判断]**

**功能已正确，且 profiler／调用链显示转换、分配或复制占比明显时，先查能否消除多余工作，再考虑缓存或特殊快路径；算法或 I/O 才是瓶颈时先处理那里。** pandas 的历史补丁通过已有后端避开含缺失值时的 object 数组转换、利用已有隔离避免重复复制，同时保留缺失掩码与复制／别名语义。见[前后产物与反例](research/2026-10-13-domain-skill-contract.md#性能质量先消除表示转换与重复复制)；这些机制与历史模型比较不证明当前 Agent 或完整 Skill 净收益。**[一手：补丁与作者测量；研究：采用判断]**

**批处理优化先确认：只改批大小，结果是否应相同？** [alchemy-utils](research/2026-10-12-alchemy-utils-evolution.md) 的真实稀疏 CSV 在 `batch_size=1/2` 下出现默认值／保留旧值与 NULL 差异，源码支持逐批字段并集这一机制。先定缺失与显式 NULL 契约，再验跨批回滚、schema 推断、默认值与旧文档；全局推断和立即流式写入冲突时，让人选择预扫、缓冲或接口变化。已有明确目标即可优化，无需先装完整工作流。局限：[程序与30条输出](../experiments/alchemy-batch-semantics/README.md)虽已核对，运行仍属对端报告，不是本侧独立 API 或性能复测。**[经验：对端运行报告；一手：源码核查；研究：采用判断]**

## 10. 原型和一次性脚本

**✅ 先验证一条值得完成的任务，再决定补哪里、保留多少。** 以下四步是从研究与案例提炼的采用建议；按当前问题选用，不必给每个原型加齐所有检查。**[经验]**

1. **定核心任务、推翻条件与替代范围。** 明确谁需要什么结果、什么观察会推翻想法；给 Agent 现有任务、必须保留的系统与输入输出，比较直接复用、补脚本／接口和完整替代，再做能独立完成有用一步的最小产物。看使用者实际接入哪一段，而非只看抱怨或功能请求；若补充层丢必要语义、仍让错误角色承担操作，或补齐整条流程才有用，就重划范围。[Segment 与 Tract](research/2026-10-13-product-feedback-contract.md#替换哪一段工作流segment与tract的范围选择)支持这种比较，不支持“越小越好”。**[一手／社区；经验：采用判断]**

   一次性任务完成一次可能就够，重复任务再看下次是否值得使用；没迁移或没付费不能单独判无价值。原型也可发现新需求，一次负反馈不自动要求放弃，更早停止也未必更好。比较结果、可用性、数据边界与运行责任，不把删代码当作降低总成本。依据：[创业试验及反例](research/2026-10-13-product-feedback-contract.md#需求成立与否试用也可以导向停止)、[Jules 自建与复用](research/2026-10-13-product-feedback-contract.md#jules从自建常驻服务到现成运行能力)。**[研究：RCT；一手／社区：历史替换与使用报告]**

2. **用真人任务区分反馈。** 请试用者解释结果并完成任务；复访时，“尚无机会”延后判断，“没理解”核对含义，“运行失败”复现故障，“没有价值”检查是否减少负担或拿走必要选择，别统一当作需求不存在。[Motif 复访](research/2026-10-13-product-feedback-contract.md#原型复访尚无机会不等于不值得使用)是短期自报，不能代替长期留存。Agent 可提出反例和安排试用顺序，[模拟反馈](research/2026-10-13-product-feedback-contract.md#模拟用户可以帮助选测试不能单独否决需求)不能单独否决必要功能或产品。**[研究；经验：采用判断]**

3. **围绕明确收益改进，再跑真实输入与连续操作。** 功能正确时也可改善信息层级、引导与响应；先说明哪个操作会更易理解或完成，复用已有状态和版面，不为“更高级”扩功能。按实际输入规模与依赖关系分别验“看懂”和“完成任务”；真实步骤关系要可见，并列能力不因装饰而编号，品牌独特性另判。依据：[CodeAid 修改后使用](research/2026-10-13-product-feedback-contract.md#修改版再使用可见性改善仍须通过真实任务)、[CodexBar 符号理解](research/2026-10-13-product-feedback-contract.md#codexbar发布后的理解反馈)、[领域质量反例](research/2026-10-13-domain-skill-contract.md#质量提升领域依据目标与过程分开判断)。**[研究／一手／社区；经验：采用判断]**

   - **结果不对或确认了旧对象**：选项可见仍错，先核[后端参数与默认值](research/2026-10-13-product-feedback-contract.md#openwhispr选项出现后仍须核对实际参数)；搜索分清不该入选、排序靠后和输入次序被打乱，再选现成的场景排序、保序或查询放宽规则，全词命中不必关闭拼写容错。已有候选过滤与整库检索分别选延迟，按正常速度验“输入→确认”，再选缩短等待、提示或提交保护，不靠放慢测试掩盖错选。见[搜索取舍](research/2026-10-13-product-feedback-contract.md#搜索改进结果准入排序与输入次序)、[KeePassXC 连续操作](research/2026-10-13-product-feedback-contract.md#keepassxc连续筛选后确认的是哪个对象)；具体延迟不能照搬。**[一手／社区；经验]**
   - **看得见却不好用**：先分清任务是辨认对象、核对输出还是编辑数据，比较紧凑摘要、结果预览与原编辑入口，不把改善一种任务变成所有人的默认。短查找与持续处理结果集可保留不同入口，但要能交接查询、结果和未完成搜索；只读预览改为可编辑时，另定保存、退出与撤销契约，不能把关闭当作放弃修改。见[Zed 的原型收窄与自用后续](research/2026-10-13-product-feedback-contract.md#zed查找与编辑共用结果不等于共用退出语义)；后续 fork 只有单人自用报告。持续对照所需的条件与结果保持可见；真正有阶段依赖可分步，但须说明预览范围、更新状态和返回路径，局部预览不能替代完整结果核查，自动图表也未必适合先查数据。让熟悉后的原使用者重做任务：字段保留不等于原路径无损。见[Zotero](research/2026-10-13-product-feedback-contract.md#zotero结果预览与原编辑入口如何取舍)、[Metabase 的分步取舍](research/2026-10-13-product-feedback-contract.md#metabase同屏条件与分步预览的竞争取舍)及[Home Assistant 的路径反例](research/2026-10-13-product-feedback-contract.md#home-assistant字段保留与原操作路径是两回事)。**[一手／社区；经验]**
   - **连续输出跟不上**：先分清用户要追最新状态还是按序消费结果，再选合并过时进度，或保留队列、分批处理与用户取消；后者仍需验证积压和取消后的新输出。内容可回看不等于原自动阅读路径无损，跳过提示也不能替代必要结果。分别验短结果紧跟提示符、大量输出和中断后继续到来的内容；漏掉普通任务结果或无法及时中断时，撤回统一策略，按任务与宿主重选。见[NVDA 的相反使用反馈与回滚](research/2026-10-13-product-feedback-contract.md#nvda追最新状态还是按序消费输出)；保留队列是待验证候选，不是该项目已成功交付的替代。**[一手／社区；经验：选择与撤回条件]**
   - **往返时反复找位置**：比较保留任务位置、显式跳转与改布局；可滚到、可聚焦和有快捷键不是同一体验。分别定首次进入、重访和返回的落点，不因追加或刷新抢焦点；按目标浏览器／读屏组合连续验收，换浏览器成功不能替代原环境。见[Joplin 与 Discourse](research/2026-10-13-product-feedback-contract.md#joplin与discourse导航可达之后保留任务位置)。**[一手／社区；经验]**
   - **省步后仍有重复负担或不能恢复**：自动结束分别验成功后能开始下一次、失败后能继续恢复；抢走重试机会就按结果状态收窄自动化。每次都需补同一步时，先区分一次性操作、持久偏好与全局默认，改善入口和保存范围，用新对象、连续操作及重开验收，不必整项回滚。见[LocalSend](research/2026-10-13-product-feedback-contract.md#localsend省掉完成点击后为何收窄自动结束)、[GIMP](research/2026-10-13-product-feedback-contract.md#gimp一次性合并与记住工作流选择)；后者只确认找到已有选项后恢复并重开记住，未覆盖全部工具，也不是新补丁效果。**[一手／社区；经验]**
   - **重复提交或编辑后想反悔**：同一对象的再次表达意图、重试重投与明确重新入队分别处理，先核应保留的状态与排序，不按调用来源猜目的。防丢失、稳定检查点、可放弃试改也分别选择：命名版本或保存确认不能等价替代“试运行后再决定”，须核画布、持久化草稿与发布边界，连续验“修改→试运行→放弃或保留”。[Karakeep](research/2026-10-13-product-feedback-contract.md#karakeep重复对象不等于重复意图)保留对象和底层创建时间仍改变归档／排序含义；[n8n](research/2026-10-13-product-feedback-contract.md#n8n自动保存稳定检查点与可放弃的试改)避免运行旧定义仍未恢复未保存试运行。两者都不支持一律加设置或关闭自动保存。**[一手／社区；经验]**
   - **协作中只想撤回自己的操作**：复用本地历史入口，保留不相关远端贡献，另定同对象同属性冲突；验“本地改→远端改→撤销→重做”。本地历史不等于完全隔离，仍可能覆盖同属性或组合对象的远端值；单人需要整体回退时快照仍可用，不默认另加协作框架。见[Excalidraw 的实现与反例](research/2026-10-13-product-feedback-contract.md#excalidraw撤销自己的操作与恢复整份旧文档)。**[一手／社区；经验]**

4. **由负责人决定保留、缩小、复用或停止。** 需求仍在而维护条件不成立，可以暂停当前实现；现成能力变化后再比较外部处理、窄集成与重建。先核替代覆盖目标人的平台、输入格式、任务数量、结果时效和失败可见性，一张样本成功不等于整批被替代。见[Mealie 的退出与重接](research/2026-10-13-product-feedback-contract.md#mealie撤掉实现不等于撤掉需求)。**[一手／社区；经验]**

   - **要退休旧实现**：默认采用新能力与删除旧路径分开决定。交互和后台／批量走不同组件时分别验，兼容开关仍在不等于还能回旧实现；必要能力缺失时比较窄适配、必要兜底或明确缩小支持，既不凭局部成功退休，也不据此默认永久保留双实现。真实负反馈也不自动要求恢复旧绕路：先保住必要结果；回退会重引已确认的工作不可达问题时，比较修复加取回入口、窄适配或缩小支持，明确额外负担，不能把关闭反馈当迁移成功。见[GitHub Desktop 的改名取舍](research/2026-10-13-product-feedback-contract.md#github-desktop保住工作与保留旧绕路)、[VS Code 的历史反例](research/2026-10-13-product-feedback-contract.md#vs-code默认采用与退休旧实现分开)。**[一手／社区；经验]**
   - **要减少组件**：核可选能力是否变成基础运行硬依赖。仍需支持不开该功能的使用者时，验安装、启动与升级再选合并、隔离或缩小支持；功能开关不一定隔离数据迁移。见[Immich 的历史依赖变化](research/2026-10-13-product-feedback-contract.md#immich减少同步层也改变基础运行的依赖)，不是当前部署指南。**[一手／社区；经验]**
   - **要保留窄适配**：目录缺项先比较配置更新或动态发现；参数、返回值或流式行为变化仍需维护和验证代码，目录更新不等于协议兼容。必要任务反复要求接收者手改、又无人承担更新时，重比受维护连接、集中适配或缩小支持，不凭少一个容器判断总负担下降。见[Open WebUI 的窄替代与接手链](research/2026-10-13-product-feedback-contract.md#open-webui少一个服务之后谁维护协议适配)；不同使用者与后续镜像不是同人长期对照。**[一手／社区；经验]**

   接入真人或持久化前补身份权限、数据隔离、迁移兼容、备份恢复、错误处理和回归；交付前核许可、持续成本与接手人员。交付失控先核部署版本，用虚构数据走通跨角色路径；试用遵守隐私和数据授权，超授权操作先问。依据：[KPI 交付反例](research/2026-10-12-codex-delivery-cases.md)；前端验证见 [23](23-browser-verification.md)。**[社区；经验]**

**证据边界**：这些是不同年代、不同项目的局部机制与使用报告，不是当前产品推荐或本仓新实测。部分有修改后使用回执（如 fzf、OpenWhispr、Mealie），不等于全路径或长期收益；Meilisearch、LocalSend 最终修订、Karakeep opt-in、n8n 最终选择仍缺对应复测，不能用别案补齐。各链具体版本、回执归属与反例留在研究链接；不据此证明四步整体有效、AI／固定 Skill 净收益或维护总成本下降。**[研究：范围限定]**

## 11. 一个通用的提示骨架

```
目标：<一句话，用户可见的结果>
完成标准：<可以运行的检查：哪些测试通过、哪个命令输出什么>
约束：<不能改的文件、不能引入的依赖、性能或兼容要求>
上下文：<相关文件、已知的坑、之前试过什么>
停下来问我的条件：<破坏性操作、需要我做决定的地方>
汇报格式：Blocked on me / Changed / Found；列出无法确认的内容和查过的地方
```

按任务删减使用；完成标准对应验证器，约束与停止条件对应边界，汇报对应证据，见 [14](14-synthesis.md)。**[经验：采用建议]**

**局限**：提示骨架不替代具体产品决定或工具权限，已有明确输入时不必重新填写一次。
