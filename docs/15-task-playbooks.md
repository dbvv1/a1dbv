# 15 · 按任务类型的打法

> 核实时间：2026-10-12。任务关口、BAML 实现决策、真实输入优化与迁移所有权建议已补核；其余事实未全量重验。
> 前面的章节按“机制”组织（上下文、工作流、多 Agent、评审）。这一篇按**你手上的任务**组织：每类任务的主要风险是什么、怎么做、用什么验证、提示词怎么写。
> 依据：Anthropic 官方最佳实践和 Opus 5.5 使用指南 **[一手]**、Simon Willison《Agentic Engineering Patterns》**[社区：原文]**、HumanLayer《Why Software Factories Fail》**[社区：原文]**、GitClear 和 Faros 的质量数据 **[一手：厂商报告]**。没有单一出处的组合做法标为 **[经验]**。

## 0. 总表

| 任务 | 最大的风险 | 关键动作 | 验证手段 | 自主度（见 [14 第 7.1 节](14-synthesis.md#71-这个任务该给-agent-多大自主权)） |
|---|---|---|---|---|
| [理解陌生代码](#1-理解陌生或遗留代码) | 自信地讲错 | 只读探索 + 要求引用文件和行号 | 抽查引用 | 高（只读） |
| [调试](#2-调试) | 修症状不修根因、改测试让它通过 | 先收集失败证据，能复现就复现；已定位且获授权则修复 | 相关回归测试与实际路径，说明未验证项 | 按风险与授权 |
| [新功能](#3-新功能) | 方向错、堆出难维护的代码 | 按规模选择计划；大功能用设计与**垂直切片** | 每片都能实际运行 | 按授权推进，关键需求取舍由人定 |
| [重构](#4-重构) | 行为悄悄改变 | **先写特征测试** | 重构前后测试一致 | 中高 |
| [大规模迁移](#5-大规模迁移与升级) | 前几个文件对、后面全错 | 先试点 2–3 个，再批量 | 文件检查 + 跨文件行为与资源契约 | 高（有验证时） |
| [补测试](#6-补测试) | 写出永远不会失败的测试 | 区分 bug 回归与既有行为保护 | 回归 red/green；关键断言用反例或变异检查 | 高 |
| [性能优化](#7-性能优化) | 凭感觉改、没有数据 | 测量瓶颈并确定不能改变的行为 | 基准数据 + 语义对照 | 按影响与授权 |
| [代码评审](#8-代码评审) | 挑刺、过度设计 | 新会话 + 只报阻断性问题 | 每条都要说明如何证明 | — |
| [文档与杂活](#9-文档提交信息发布说明) | 事实、权限或兼容说明写错 | 按推理需求和错误代价选模型 | 核对来源、命令和相关行为 | 按风险 |
| [原型和一次性脚本](#10-原型和一次性脚本) | 原型被直接当成生产代码 | 先跑通，再按真实使用约束补差距 | 试验目标；真实用户或数据另需安全与恢复检查 | 高（限已授权范围） |

## 1. 理解陌生或遗留代码

**风险**：模型会用很自信的语气讲出错误的结论，尤其是代码和常见模式不一样的时候。

**打法**：
1. 用 Plan 模式或只读的探索子 Agent，**明确说不要改代码**；
2. 要求每个结论都**引用文件和行号**，并标出“推断”和“确认”的区别；
3. 让它写一份**线性走读**：按执行顺序逐段讲解一个请求或一个功能的完整路径（Willison 的 linear walkthrough）**[社区：原文]**；
4. 让它列出自创的术语，你确认或改名后维护 `GLOSSARY.md` **[社区]**。

**注意**：这份理解是写给**人**看的。研究显示，把仓库概览写进 AGENTS.md 对 Agent 没有帮助 **[研究：原文]**（见 [03](03-context-engineering.md#22-指令文件到底有没有用研究证据)）。

```
阅读 src/billing，按一次“月度结算”的执行顺序讲解调用链。
每一步给出文件:行号；分开标注“读代码确认的”和“推断的”。
不要修改任何文件。最后列出你不确定、需要我确认的 3 个问题。
```

## 2. 调试

**风险**：修了症状而不是根因；为了让测试通过而改测试；在没复现的情况下“猜着修”。

**何时值得先研究**：缺失信息会改变修复位置、兼容边界或验收时，先围绕该决策调查。例如 BAML 的历史双 PR 在 test visitor 与 test validator 两处修同一问题；有研究路线范围更窄，但原计划的测试输入也在实施中被纠正。因此让 Agent 查相关调用链、已有同类校验和测试约定，比笼统要求“深入分析整个仓库”更有针对性；已定位的问题可直接修，计划可随新证据调整，不新增人工审批关口。见[原始补丁与计划复核](research/2026-10-12-baml-and-review.md) **[经验：由历史案例形成的建议，非当前模型效果实验]**。

**打法**：
1. **先收集失败证据，能复现就复现**：优先写能稳定失败的测试或脚本。无法本地复现时，核对生产日志对应的版本、输入和环境，缩小范围，必要时补最小诊断；证据足以支持局部修复时可在授权内继续，但要说明验证缺口，不能把推断说成已确认 **[经验：采用判断]**；
2. 根因不明时列出有依据的候选原因，做能区分它们的最小实验；已定位的小问题不必凑够 2–3 个假设；
3. 日志要过滤后再读（`grep` 错误关键词），不要把整个日志读进上下文；
4. 有稳定复现脚本的回归问题可用 `git bisect run <复现脚本>`，让 Agent 写复现脚本，二分交给 git **[经验]**；
5. 可以新增回归测试、补覆盖或修正有独立依据的测试错误；不要为了变绿而放宽断言、删除用例或改写未获授权的行为约定。预期行为不清楚时询问，并说明具体分歧；
6. 修完先跑相关检查，再按影响范围扩展到集成或完整测试；仓库规定的必跑检查不能省略。实际运行能补足测试盲区时，再用 curl、`python -c` 或浏览器验证。报告跑过、失败和未运行的范围 **[经验：采用判断；实际运行方式参考 Willison]**。

```
这个 bug 的现象是……，预期行为是……。在已授权范围内定位、修复并验证。
优先补能复现问题的回归测试；无法本地复现时，结合日志、版本和代码继续调查，区分确认与推断。
不要为通过测试而削弱断言。预期行为不清、需要越过授权范围或缺少关键输入时，说明具体阻塞再问我。
完成后给出改动、验证结果和仍未验证的范围。
```

## 3. 新功能

**风险**：方向理解错；一次生成 2000 行难以评审的代码；代码库在几个月内变得难以维护 **[社区：HumanLayer]**。

**打法**（按功能大小选择，见 [07 第 3.4 节](07-workflows.md#34-大功能的前置设计与垂直切片-)）：

| 大小 | 做法 |
|---|---|
| 一句话说得清的改动 | 直接做 |
| 中等 | 一份合并的计划文档：做什么、改哪些文件、怎么验证 |
| 大 | 访谈式 Spec → 系统架构 → **程序设计**（类型、函数签名、调用树）→ **垂直切片** |

- 明确要求**垂直切片**：先打通一条端到端的最小路径（接口返回假数据 → 前端接上 → 再接服务层和数据库），每片都能实际运行。按行为、接口和风险确定检查点，保持 diff 可评审；100–200 行可作拆分参考，不是必须等待人工批准的门槛 **[经验：采用判断]**；
- 一条消息里给出完整任务、完成标准和什么时候停下来问 **[一手：Opus 5.5 指南]**；
- 长任务可在 `TASKS.md` 或已有记录中维护最新目标、约束、进度、验证结果和下一步；恢复时重读并核对当前代码与授权。文件存在不保证已加载或仍有效，见 [20 恢复边界](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史)。

## 4. 重构

**风险**：行为悄悄改变；而且 AI 默认**倾向于复制而不是复用**。GitClear 数据显示，AI 时代重构类的代码移动从 13% 降到 3.8%，重复代码块增加 81% **[一手：厂商报告，相关性]**。

**打法**：
1. **先写特征测试**（characterization test）：锁定当前行为，包括看起来奇怪的行为；
2. 让它先列出重构步骤，**每步都是保持行为不变的小改动**，每步之后跑测试；
3. 机械性的大范围改名或签名修改，优先用 IDE 重构、codemod 或 LSP 的重命名，而不是让模型逐个文件改 **[经验]**；
4. 明确要求“**复用已有的实现，不要复制**”，评审时专门检查新增的重复代码。

## 5. 大规模迁移与升级

**风险**：前几个文件做得很好，后面因为上下文漂移或模式不同而出错；单个文件通过不保证跨文件契约保持。**[经验]**

**打法** **[一手：官方最佳实践]**：
1. 让 Agent 先**列出所有要改的文件**，按依赖顺序排列；
2. 在 2–3 个有代表性的文件上调好提示词和验证脚本；
3. 用 `claude -p` 循环或 `/batch`（拆给 5–30 个 worktree 子 Agent）批量处理，**每个文件都要过同一个验证**（编译、测试、lint）；
4. 失败的文件单独收集，人工看过模式后再处理。

**参考**：Anthropic 提到有测试者用 Opus 5.5 在不到一天内完成了 68 万行代码的迁移 **[一手：官方发布页的用户反馈]**。该用户反馈不能推出所有迁移都可逐文件验收；编译和 lint 之外，还应验证受影响的完整行为。**[经验：适用边界]**

**跨语言迁移的最小补充（✅ 采用）**：外部 API／文件／协议可保持不变，内部所有权却可能变化。让 Codex 沿一条真实路径检查“谁分配、返回后谁使用、何时释放”，把失败输入变成同时检查内容与清理的回归；例如 [VibeTunnel](24-community-workflows.md#不同作者的后续维护vibetunnel-的内存所有权修复)中，无 upstream 仓库暴露了返回切片过早释放，第一次 arena 修复又需要纠正 allocator 的绑定对象。适合跨内存管理模型的移植；机械改名不必套用，局部修复也不要求整项目重写。**[经验：基于公开源码与维护记录，未复跑]**

## 6. 补测试

**风险**：写出“永远不会失败”的测试，比如断言 mock 的返回值、测试实现细节、覆盖率上去了但什么也没保护。

**打法**：
1. **保护既有正确行为**的测试可以在当前代码上通过；断言应来自行为约定或独立依据，而不是照抄实现结果；
2. **修 bug** 时优先做 red/green：确认回归测试在含 bug 的版本失败、修复后通过。无法运行旧版本时，说明这个证据缺口（Willison 的短提示“Use red/green TDD”）**[社区：原文；边界为经验判断]**；
3. 对关键行为可用有代表性的错误注入或变异测试检查测试是否有效；测试应因相关行为错误而失败，不必让每个新测试先在正确代码上变红 **[经验：采用判断]**；
4. 测试名描述行为，而不是函数名。

## 7. 性能优化

**风险**：凭直觉改，改完没有数据证明变快；为了快牺牲了正确性。

**打法**：
1. **先测量**：给 Agent profiler 的输出或基准测试数据，而不是让它“看看哪里慢”；
2. 把基准测试脚本当作验证器：每次改动后自动跑，比较前后的数字；
3. 一次只改一处，保留每次的数据；
4. 正确性测试必须同时通过；根据改变的机制补查旧测试未覆盖的行为，而非只沿用原有绿灯。

原型进入真实使用时，先补一个实际规模的输入、完整运行命令，以及优化不能破坏的行为；例如分批导入仍需检查跨批失败回滚、schema 推断与默认值，而不只是耗时。已有明确目标可直接优化并验证，不必默认安装完整工作流；改完同步旧 README 限制说明。见 [alchemy-utils 的第二次修改](24-community-workflows.md#从原型到第二次修改alchemy-utils-的真实-csv-改变了什么)。**[经验：基于公开连续变更的采用判断，非性能复测]**

**✅ 对分批优化增加一个具体问题：只改批大小，数据是否应保持相同？** alchemy-utils 的固定版本实测显示，缺字段的 insert/upsert 在批大小 1 与 2 时会分别使用默认值／保留旧值或写 NULL。给 Codex 的约束应是“先确认缺失与显式 NULL 的语义，再用跨批边界输入对照”，而非只要求性能提升和已有测试全绿。若需要全局字段推断又要求立即流式写入，应明确预扫、缓冲或接口变化的取舍；不能靠加一个通用 Skill 消除这种设计约束。见[30 次 API 调用与最小复现](research/2026-10-12-alchemy-utils-evolution.md#独立复核批大小确实改变-sqlite-数据结果)。**[经验：实测；研究：采用判断]**

这一类任务属于“验证器有噪声”（见 [14 规律一](14-synthesis.md#推论按验证器质量给任务分级)）：数字要多跑几次取中位数，结论由人判断。

## 8. 代码评审

**打法** **[一手：官方建议]**：
- **新开一个会话**，只给 diff 和评判标准，不给实现过程中的推理；
- 提示词：“**只列你会因此拒绝合并的问题**，给出文件、行号、原因，以及怎么证明它是错的”；
- 被要求找问题的评审者几乎总能找出点什么，追着每一条改会导致过度设计；
- 工具：`/code-review`（可以用 `--max-findings` 控制数量）、`/ultrareview`（云端多 Agent 深度评审）、Codex Security Cloud（仓库安全扫描）、CodeRabbit 等（见 [09](09-review-and-quality.md)）。

## 9. 文档、提交信息、发布说明

- 机械整理已核实的提交信息、格式或措辞，可先用低成本模型与非交互模式；权限、架构、兼容性和迁移说明按推理需求及错误代价选择能力，不因文件是 Markdown 就降低要求 **[经验：采用判断]**；
- 纯措辞变更可快速过目；涉及事实、命令和行为约定时，对照来源、代码或实际检查验证。不要默认把生成的仓库概览塞进指令文件，见 [03](03-context-engineering.md)。

## 10. 原型和一次性脚本

- 放手做，vibe coding 在这里完全合适（Addy Osmani：给十几个人用的业余项目和维护十年的企业系统，“几乎没有共同的约束”）**[社区：转述]**；
- **陷阱**：原型“看起来能用”，然后被直接当成生产代码继续堆。加入真实用户或持久化前，检查现有实现缺少什么：身份与权限、数据隔离、持久化与迁移、备份恢复、错误处理和回归验证。按实际缺口补设计、测试与评审；能满足要求的实现保留，有证据表明局部结构不合适时再重构。需求取舍由人决定，超出授权的数据操作先询问，不默认重写 **[经验：采用判断]**。

前端任务补充：把页面结构、用户交互、持久化、视觉与故障恢复分别验收，具体步骤见 [23 浏览器验证](23-browser-verification.md)。涉及换模型、加 Skill 或多 Agent 的工作流改动，先用 [22](22-agent-evaluation.md) 的对照方法判断收益。

**给组织实际使用前，先判断谁能接管。** 一个原型可能技术上可扩写，却不符合许可、持续成本与维护人员约束。先比较现有产品/配置能覆盖多少需求，以及保留自定义实现的必要性；若已写了很多组件仍无法交付，先确认部署对应提交，用虚构数据跑一条跨角色业务路径，从第一个具体失败继续。不要凭工具数量决定重写，也不要把增加文档当成已经完成交接。这个建议由 [KPI 项目原帖](research/2026-10-12-codex-delivery-cases.md) 暴露的问题形成，尚非已验证的项目恢复结果 **[经验：条件建议]**。

## 11. 一个通用的提示骨架

```
目标：<一句话，用户可见的结果>
完成标准：<可以运行的检查：哪些测试通过、哪个命令输出什么>
约束：<不能改的文件、不能引入的依赖、性能或兼容要求>
上下文：<相关文件、已知的坑、之前试过什么>
停下来问我的条件：<破坏性操作、需要我做决定的地方>
汇报格式：Blocked on me / Changed / Found；列出无法确认的内容和查过的地方
```

这个骨架就是 [14](14-synthesis.md) 的“定义问题”：完成标准对应验证器，约束和停止条件对应边界，汇报格式对应证据。
