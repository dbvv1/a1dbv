# 15 · 按任务类型的打法

> 核实时间：2026-10-08；任务分流与恢复于 10-11、迁移所有权/BAML/SQLite 案例于 10-12 补核，10-12 整理阅读层，10-13（UTC+8）补试用反馈、发布后理解反馈、自建/复用取舍与完整 SQLite 材料；10-13（UTC+8）补核 §3 后续扩展案例；10-14 补核 §5 持久状态回退、脚本模式上下文、跨系统事实归属与 §10 模拟反馈边界、同一用户复测和后端参数核对。本页给任务起点；Codex 的[五情境入口](01-agents/codex.md#五种情境先做最小改变)说明何时再加知识、工具或流程。
> 依据包括 Anthropic 官方最佳实践与 Opus 5.5 指南 **[一手]**、Willison 与 HumanLayer 的公开实践 **[社区]**；没有单一出处的组合方法标为 **[经验]**，案例来源与审计范围链接到研究页。

## 0. 总表

| 任务 | 最大的风险 | 关键动作 | 验证手段 | 自主度（见 [14 第 7.1 节](14-synthesis.md#71-这个任务该给-agent-多大自主权)） |
|---|---|---|---|---|
| [理解陌生代码](#1-理解陌生或遗留代码) | 自信地讲错 | 只读探索 + 要求引用文件和行号 | 抽查引用 | 高（只读） |
| [调试](#2-调试) | 修症状不修根因、改测试让它通过 | 先收集失败证据，能复现就复现；已定位且获授权则修复 | 相关回归测试与实际路径，说明未验证项 | 按风险与授权 |
| [新功能](#3-新功能) | 方向错、堆出难维护的代码 | 按规模选择计划；大功能用设计与**垂直切片** | 每片都能实际运行 | 按授权推进，关键需求取舍由人定 |
| [重构](#4-重构) | 行为悄悄改变 | **先写特征测试** | 重构前后测试一致 | 中高 |
| [大规模迁移](#5-大规模迁移与升级) | 前几个文件对、后面全错 | 先试点 2–3 个，再批量 | 文件检查 + 跨文件行为与资源契约 | 高（有验证时） |
| [补测试](#6-补测试) | 写出永远不会失败的测试 | 区分 bug 回归与既有行为保护 | 回归 red/green；关键断言用反例或变异检查 | 高 |
| [性能优化](#7-性能优化) | 凭感觉改、没有数据 | 测量瓶颈并确定不能改变的行为 | 基准数据 + 语义对照 | 按影响与授权 |
| [代码评审](#8-代码评审) | 挑刺、过度设计 | 新会话 + 只报阻断性问题 | 每条都要说明如何证明 | — |
| [文档与杂活](#9-文档提交信息发布说明) | 事实、权限或兼容说明写错 | 按推理需求和错误代价选模型 | 核对来源、命令和相关行为 | 按风险 |
| [原型和一次性脚本](#10-原型和一次性脚本) | 原型被直接当成生产代码 | 先跑通，再按真实使用约束补差距 | 试验目标；真实用户或数据另需安全与恢复检查 | 高（限已授权范围） |

## 1. 理解陌生或遗留代码

**✅ 先只读走通一条实际调用路径。** 用 Plan 模式或只读探索，明确不要改文件；要求每个结论引用文件与行号，分开确认与推断。按请求的执行顺序写线性走读，术语混乱时再维护带代码例子的 `GLOSSARY.md`。**[经验：采用判断；社区：Willison 的 linear walkthrough]**

```
阅读 src/billing，按一次“月度结算”的执行顺序讲解调用链。
每一步给出文件:行号；分开标注“读代码确认的”和“推断的”。
不要修改任何文件。最后列出需要我确认的关键问题。
```

**局限**：面向人的走读不应自动变成常驻指令，仓库概览对 Agent 的收益需另验，见 [03 的研究](03-context-engineering.md#22-指令文件到底有没有用研究证据)。

## 2. 调试

**✅ 已有明确失败就复现、定位、修复、重跑；缺什么证据再补什么。** **[经验：采用判断]**

1. 优先用稳定失败的测试或脚本；无法本地复现时核对日志的版本、输入与环境，必要时加最小诊断
2. 根因不明就做能区分候选原因的小实验；已定位的小问题不必凑假设数量
3. 过滤日志后再读；稳定的回归脚本可交给 `git bisect run <复现脚本>`
4. 补回归，测试本身有独立错误才修测试；禁止为变绿削弱断言、删除用例或改变未授权的行为
5. 先跑相关检查，再按影响扩展集成/全测；仓库必跑入口照做，实际路径可用 curl、短脚本或浏览器补验

主要依据是 [BAML 双 PR](research/2026-10-12-baml-and-review.md#baml实现反馈纠正研究计划)：调查帮助选择更窄的修改位置，但有研究的计划也把测试输入写错，实施时仍需纠正。研究应回答修哪层、保留什么，而非每次先写全仓报告。**[一手：历史补丁；研究：采用判断]**

**局限**：无法复现时的局部修复仍有验证缺口；预期冲突、关键输入或权限缺失须说明具体阻塞并询问。

## 3. 新功能

**✅ 按不确定性决定计划深度，先交付一条可运行路径。** **[经验：采用判断]**

| 大小 | 做法 |
|---|---|
| 一句话说得清的改动 | 直接做并验证 |
| 中等 | 合并记录目标、改哪些文件、如何验证 |
| 大 | 对齐需求 → 架构与类型/调用关系 → 垂直切片 |

先打通接口、前端、服务与数据库的一条最小路径，每片可运行；100–200 行可供拆分参考，不是等待人批准的门槛。一次给出任务、完成标准与需询问的取舍；跨会话在已有记录保存最新目标、约束、结果与下一步。**[一手：Opus 5.5 指南；社区：HumanLayer；经验：切片建议，见 [07](07-workflows.md#34-大功能的前置设计与垂直切片-)]**

**✅ 新增视图先复用语义相同的业务组件，等具体需求出现再补窄扩展点。** 让 Agent 说明下一需求落在哪层、哪些旧调用者要一起检查。Discourse 的 AI 参与 nested replies 实现复用了 TopicCategory；四个月后，另一贡献者为客户插件增加扩展点，只改共享分类组件与 docked header，保留两种视图共用路径，见[前后源码与交付边界](research/2026-10-12-development-conditions.md#discourse共享组件承接后续需求)。**[一手：公开源码与后续 PR；研究：采用建议]** 这是一次局部扩展落地的证据，尚无客户上线复测或维护时间收益。

**局限**：旧计划不能锁住新反馈，恢复时须核对当前代码与授权，见 [20](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史)。

## 4. 重构

**✅ 先锁定行为，再做小步等价修改。** 补特征测试，包括看起来奇怪但需保留的行为；每步之后运行相关检查。机械改名/签名修改优先 IDE 重构、codemod 或 LSP，评审专查是否复制了已有实现。**[经验：采用判断]**

GitClear 报告代码移动从 13% 降到 3.8%、重复代码块增加 81%，提示应关注复用与结构，来源讨论见 [09](09-review-and-quality.md)。**[一手：厂商报告，相关性]**

**局限**：群体相关性不能证明当前 Agent 必然倾向复制，重构是否正确仍由本项目行为对照决定。

## 5. 大规模迁移与升级

**✅ 先试点，再按依赖批量迁移。** 列出范围，在 2–3 个代表文件上调好改法和验证；可用 `claude -p` 循环或 `/batch`（5–30 个 worktree 子 Agent），逐文件跑编译、测试、lint，将失败模式收集后再处理。Anthropic 报告有测试者不到一天迁移 68 万行代码，可借鉴批处理方式。**[一手：官方最佳实践与发布页用户反馈]**

**交互试点转脚本时，先保住迁移所需的项目知识。** 普通 `claude -p` 会加载项目上下文；可选的 `--bare` 会跳过 `CLAUDE.md`、Skill 等自动发现，两者不是等价启动方式。在已审查的可信项目中，需要这些约束时保留普通模式，或只显式提供本次必需的上下文与工具；不要为减少启动开销漏掉项目约定，也不必复制全部指令。`--bare` 自 2.1.286 起不再启动后台任务，超时命令会停止；依赖后台构建结果的迁移应保留支持该路径的运行方式。外来仓库先按 [10 的配置来源边界](10-security.md#3-防护原则)限制启动配置；上下文选择见[官方契约与采用边界](research/2026-10-12-development-conditions.md#交互试点转脚本bare-不是等价加速)。**[一手：官方文档与固定发布说明；经验：采用判断，未运行客户端]**

跨语言还应沿一条真实路径检查“谁分配 → 返回后谁用 → 何时释放”，把真实失败转成内容与清理回归。[VibeTunnel](research/2026-10-12-vibetunnel-maintenance.md) 的无 upstream 仓库暴露了返回切片过早释放，第一次 arena 修复还需纠正 allocator 绑定对象。**[一手：公开维护补丁；经验：采用判断]**

混用版本或需要降级时，让旧版本读取新版本实际写过的状态，并检查恢复后后台任务会不会再生成不兼容产物。[Git MIDX 的默认格式回退](research/2026-10-12-vibetunnel-maintenance.md#持久状态回退git-midx-的旧读取者边界)源于 rc2 的 fetch 使旧 Git 无法读取同仓库；最终保留显式 compact 的新格式能力，收窄普通写入默认值。**[一手：原始讨论与固定补丁；经验：迁移验收建议]** 这是非 AI 项目的机制证据，未取得最终修订后的原用户复测。

**配置回退设计应保留既有数据的读取能力。** 关闭新格式写入后，用开启前、开启后和关闭后写入的混合数据，分别验正常服务及实际用于导出／恢复的一次性命令；同版本关闭开关不等于旧版本可读。n8n 先拆开读写开关，随后才把读取依赖初始化提前到所有命令入口，见[固定修订与作者运行报告](research/2026-10-12-development-conditions.md#n8n配置回退与独立导出入口)。**[一手：补丁；社区：作者报告；研究：采用建议，导出路径测试未独立运行]**

试点还应覆盖跨文件行为与资源契约；系统职责改变时，确认事实现在应向哪个服务查询，避免结果相同却仍在旧层扫描或重建状态。[Scion 迁移复盘与兼容反例](research/2026-10-12-development-conditions.md#迁移后的事实归属与旧调用方式)支持这项窄检查，不要求机械改名套用全部检查。**[经验：采用判断；一手：团队自述，未独立复测]**

## 6. 补测试

**✅ 用独立的预期保护行为，再确认测试能发现相关错误。** **[经验：采用判断]**

- 保护既有正确行为的测试可以直接通过，预期来自契约或独立依据
- 修 bug 优先 red/green：旧版本失败、修复后通过；关键断言可用反例或变异检查
- 通过公共接口观察结果，测试名写行为，避免断言 mock 返回值或照抄实现算法

主要依据是 Willison 的 red/green TDD 实践与[公共边界测试 Skill](research/2026-10-12-community-source-records.md#3-matt-pocock控制权与领域语言)。**[社区；一手：配置]**

接入外部格式或协议时，用目标版本生产者的公开、可脱敏产物校准预期；有独立证据时允许修正旧断言。RTK 的 Windows 编码修订同时纠正了实现与旧测试，不能拿本仓注释和测试的一致性替代外部兼容依据，见[维护链与局部模型](research/2026-10-12-development-conditions.md#外部生产者校准错误预期)。**[一手：修订；经验：采用建议]**

**🧪 输入组合多、契约可表达且单次执行便宜时，补小范围属性测试。** 让 Agent 从文档和真实调用找不变量，用已有测试环境搜索反例；失败后先核对属性及有效输入域，再把具体输入、版本和随机条件固化为回归。NumPy 的 Wald 案例确实找到缺陷，但仍需人工数值分析及跨构建修订回归参数；dateutil 则因日历语义产生误报。[证据与局部实测](research/2026-10-12-development-conditions.md#属性测试搜索反例不等于确认或修好缺陷)。**[一手：维护链；经验：采用判断]**

**局限**：不能运行旧版本时保留回归缺口，但不要求每个新增测试都先在正确代码上失败；属性自身可能错误，属性通过也不证明所有精度、分布或业务要求。

## 7. 性能优化

**✅ 先给 profiler/基准、实际规模输入与完整命令，同时写清不能改变的行为。** 一次改一项，保留前后数据，多次运行看中位数；运行正确性测试，并按改动机制补旧测试漏掉的行为。**[经验：采用判断]**

[alchemy-utils](research/2026-10-12-alchemy-utils-evolution.md) 的真实 CSV 触发了迭代读取与分批优化，也暴露兼容问题：对端报告同样稀疏输入只改 `batch_size=1/2` 就会在默认值/保留旧值与 NULL 间变化，本侧源码核查支持逐批字段并集这一机制。**[经验：对端运行报告；一手：本侧源码核查]**

因此先问“只改批大小，结果是否应相同”，确认缺失与显式 NULL 契约，再测跨批回滚、schema 推断、默认值和旧文档；如全局字段推断与立即流式写入冲突，让人选择预扫、缓冲或接口变化。已有明确目标即可优化，无需先装完整工作流。**[研究：采用判断]**

**局限**：[完整程序与 30 条输出](../experiments/alchemy-batch-semantics/README.md)已补齐并核对；运行仍属对端报告，本侧材料核对不构成独立 API 或性能复测。

## 8. 代码评审

**✅ 用独立上下文审 diff，只报会阻止合并的具体问题。** 给评判标准，不灌入实现过程中的推理；每条包括文件、行号、失败条件及证明方式。工具可选 `/code-review`（`--max-findings`）、`/ultrareview`、Codex Security Cloud 或 CodeRabbit，见 [09](09-review-and-quality.md)。**[一手：官方用法；经验：采用判断]**

[BAML 两条 PR 都获自动肯定](research/2026-10-12-baml-and-review.md#baml实现反馈纠正研究计划--4-自动评审和测试记录能证明多少)说明评审结论还需回到具体行为检查。

**局限**：追改每个挑刺会增加过度设计，评审“通过”也不能替代实际验证。

## 9. 文档、提交信息、发布说明

**✅ 按错误代价选能力，按内容核对证据。** 已核实信息的机械整理可先用低成本模型/非交互模式；涉及权限、架构、兼容或迁移时保留足够推理，核对来源、代码、命令与行为约定。**[经验：采用判断]**

依据是 [03](03-context-engineering.md) 对项目知识与生成概览的区分，以及 [19](19-experiments.md) 中正确性相同但过程不同的记录。

**局限**：Markdown 格式本身不说明风险低，生成的仓库概览也不应自动进入常驻指令。

## 10. 原型和一次性脚本

**✅ 先验证一条值得完成的任务，再决定补哪里、保留多少。** 以下是从案例提炼的采用建议，完整证据与反例见链接。**[经验]**

1. **定核心任务、推翻条件与已有替代。** 明确谁需要什么结果、什么观察会推翻想法；用同一任务比较现成方案的结果、可用性与数据边界，再做最小可体验产物。一次性脚本完成一次可能就够，重复任务看下次是否值得再用；原型也可发现新需求，一次负反馈不自动要求放弃。更早停止未必更好，删除代码也不等于降低总成本。依据：[创业试验](research/2026-10-13-product-feedback-contract.md#需求成立与否试用也可以导向停止)、[Jules 自建与复用](research/2026-10-13-product-feedback-contract.md#jules从自建常驻服务到现成运行能力)。**[研究：RCT；一手：补丁；社区：使用报告]**

2. **用真人任务区分反馈。** 请试用者解释结果并完成任务；复访分清“尚无机会”“没理解”“运行失败”“没有实际价值”。分别延后判断、核对含义、复现故障、检查是否减少负担或拿走必要选择，别统一归因于需求不存在。Agent 可提出反例和安排试用顺序，但模拟反馈不能单独否决必要功能或产品，短期意愿也不代表长期留存。依据：[Motif 复访](research/2026-10-13-product-feedback-contract.md#原型复访尚无机会不等于不值得使用)、[模拟与真人对照](research/2026-10-13-product-feedback-contract.md#模拟用户可以帮助选测试不能单独否决需求)。**[研究]**

3. **只改障碍，再跑真实输入。** 复用已有状态、版面和真实数据，保留有效实现，有结构问题再重构，别逐条扩成控件。用实际规模与依赖关系的输入，分开验“看懂”和“完成任务”；前者改善而后者失败时，检查缺失的上下文或操作能力；选项已出现却仍做错任务时，先核对它是否传到后端及默认值，再判断模型不够或增加控件。改显示语义须保住旧配置与默认行为、保留回退路径；不能把同期模型或任务变化的效果归给改版。依据：[CodeAid 更新后使用](research/2026-10-13-product-feedback-contract.md#修改版再使用可见性改善仍须通过真实任务)、[CodexBar 兼容取舍](research/2026-10-13-product-feedback-contract.md#codexbar发布后的理解反馈)、[OpenWhispr 同一用户复测](research/2026-10-13-product-feedback-contract.md#openwhispr选项出现后仍须核对实际参数)。**[研究：使用报告；一手：补丁]**

4. **由负责人决定保留、缩小、复用或停止。** 复用前先验替代路径的结果时效、可用性与失败可见性，再退休重复实现。接入真人或持久化前补身份权限、数据隔离、迁移兼容、备份恢复、错误处理和回归；交付前核许可、持续成本与接手人员。交付失控先核部署版本，用虚构数据走通跨角色路径；试用也须遵守隐私和数据授权，超授权操作先问。依据：[KPI 交付反例](research/2026-10-12-codex-delivery-cases.md)；前端分层验证见 [23](23-browser-verification.md)。**[社区：作者复盘；经验：采用建议]**

**局限**：各案例只覆盖部分决策链，四步整体及修改后的长期收益尚未经这些材料证实。
