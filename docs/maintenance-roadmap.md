# 持续维护路线：AI coding 为主，游戏为辅

> 更新：2026-10-11（UTC+8）。这是工作方向和待验证假设，不是已完成结果。

## 目标与取舍

主线是提高 AI coding 的可靠性、任务完成质量、恢复能力和单位成果成本。游戏开发是检验这些机制的补充案例，不让引擎细节取代通用研究。

官方说明用于确认产品契约；社区原帖用于发现真实摩擦；GitHub 源码和测试用于理解机制；研究用于检查因果与外推范围。四者互补，任何一个都不是自动正确。

不以篇数、提交数、星数、运行时长或子 Agent 数量当成果。允许没有值得采用的新结论；删重复规则、撤回不可靠数字也算有效维护。

### 目标完成后如何继续

下一目标 **G3：社区 agent / skill 机制的最小验证**。比较少量有可读源码、活跃实际使用和反例的候选；先明确要改善的具体故障，再研究实现。至少交付一个可复现机制探针或有证据的不采用结论，注明许可证、版本、适用边界和成本。优先验证中断恢复、信息按需加载和验收约束，不按星数或宣传选型。

每轮按“具体问题 → 验收条件 → 研究/修改 → 验证 → 提交/复核 → 下一目标”推进。上一目标未完成时优先补缺口；确实被外部条件阻塞时记录原因，再推进独立问题。只有证据和收益支持才增加复杂度；允许删减、撤回或不采用。

## 当前优先问题

1. **如何证明配置/Skill 真有收益？** 分开测有用内容、额外长度、模型变化、任务分布和缓存；保留失败、超时和不可复现项。先验证评测器，再花模型额度。
2. **何时该记忆，何时该重新读取？** 分清跨任务知识、当前任务状态与上下文压缩；旧结论必须有来源和失效条件，不能越过新任务权限。
3. **怎样保持长期结果可信？** 独立的验收标准、与版本绑定的运行证据、未知外部结果核对、正确收集子任务和最终集成检查。
4. **怎样控制维护本身的成本？** 小任务轻流程、按风险评审、复用仍有效的检查结果，避免不断增加规则和重复全文阅读。

## 每轮完成标准

- 有具体问题和足够新、可核查的证据；相同新闻不重复整理
- 改进写入已有对应专题，必要时才增加新文件；保留反例、局限和不采用理由
- 改代码时有可复现的失败与回归；模拟测试、真实运行和设计建议明确分开
- 检查最终差异和适用测试，再提交独立分支/草稿 PR；不自动合并或部署
- 遇到权限、真实环境、额外费用或证据不足时记录阻塞，不扩大权限补洞

## 验证基础设施

[仓库检查工作流](../.github/workflows/repository-checks.yml) 只运行离线文档/配置检查、单元测试、评测夹具自检、合成数据审计回归和 shell 语法检查。它使用标准 Ubuntu runner、只读仓库权限、固定 checkout 提交；不运行模型、不读取个人配置、不上传构建工件、不设置秘密或持久凭据。

工作流存在不等于 CI 已跑过；每次以 GitHub 对应 commit 的实际结果为准。当前官方说明称公开仓库使用标准托管 runner 的执行时间免费；更大 runner 与其他存储计费规则不同，不因此承诺任意 CI 都免费。**[一手：[GitHub Actions 计费](https://docs.github.com/en/billing/concepts/product-billing/github-actions)，核实 2026-10-10]**
