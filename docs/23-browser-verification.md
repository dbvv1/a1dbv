## 当前最高水平：真实失败会话，还是现有阶段回归？

**默认选现有 Playwright／trace 加阶段回归；生产失败难以重建、且已有获准使用的录制时，再把 Replay 式闭环当作近期领先参照试用：把原会话送入诊断，并在修后预览重验。** Replay／Thomas Daly 的 2026-10-06 复盘自报两周在自有仓库连接 Fullstory、Replay QA 与 Obvious，前端修复依据原会话验证，人审 PR 与 QA 报告后合入。机制比“生成代码后自评正常”更接近交付，但公开文章未给单项 PR、前后录制或可独立复核的效果对照。

| 同一个选择：怎样证明原 UI 故障修好 | 适用条件与增量 | 本页判断 |
|---|---|---|
| 原失败会话驱动诊断与修后验证 | 难以重建的生产状态，且已有获准使用的录制；需核目标构建、状态重建、数据权限及持续接入成本 | 🧪 试用领先闭环的机制，不默认复制整套服务；无法在新版重走原失败就撤回验收依据 |

## 1. 为什么编译通过仍然不够

**前端交付按“用户能否完成目标、数据是否正确、异常时能否恢复”验收，编译、截图与 HTTP 200 都不够。** 类型检查发现不了按钮被遮挡；截图证明不了点击后的数据保存；HTTP 200 也可能携带业务错误。

| 层次 | 要拿到的证据 | 不能替代什么 |
|---|---|---|
| 构建 | 实际构建命令与结果 | 浏览器运行 |
| 结构 | 页面语义、可访问名称、可操作元素 | 布局与视觉表现 |
| 交互 | 输入、点击、导航后的断言 | 数据真实持久化 |
| 状态 | 按保存契约重新打开或独立读取后，结果仍符合预期 | 跨租户/跨账号权限测试 |
| 视觉 | 目标尺寸的截图、溢出与遮挡检查 | 功能和完整无障碍审计 |
| 异常 | 超时、拒绝、空数据、重试的行为 | 未覆盖故障的可靠性 |

**实际案例：先确认检查覆盖的是哪个使用状态。** Ra & Apep 承诺无 JavaScript 可阅读，但旧版重启按钮依赖脚本。对端记录的本地前后对照显示：原有 12 项自检只覆盖滚动计算，旧版启用 JS 时全过，禁用 JS 时重启仍无效；换成原生锚点后，无 JS 场景恢复。动画、静态场景也复测通过。检查不必无限增加，应针对产品承诺选择状态；此处无需新工作流，关键是识别脚本依赖与原生功能。详见[固定版本和六场景记录](research/2026-10-12-codex-delivery-cases.md)。

**依据**：[经验：对端本地功能实测记录，本侧未独立复跑，未全面视觉验收] 固定版本和六场景记录（见上）；核实 2026-10-21。

## 2. MCP、CLI 与测试代码各做什么

**先按缺失的观察选工具，默认复用项目现有 Playwright 配置与测试代码。** Playwright MCP 通过结构化 accessibility snapshot 暴露页面，常规操作不要求视觉模型；其 README 也建议 coding agents 考虑 CLI + Skills，并说明 MCP 适合需要持续浏览器上下文、结构探索和迭代操作的场景。

**浏览器是运行环境；DOM／可访问性树、截图、动作与事件时间线提供不同证据。** 下表是按验收缺口选择的工程建议，不是通道效果排名。

| 需要判断的问题 | 最小反馈与实施选择 | 何时已有测试足够；仍缺什么 |
|---|---|---|
| 选中、禁用、保存结果是否正确 | 用现有浏览器输入/点击路径，读 DOM/可访问性状态，并断言保存后的业务结果 | 已稳定触发并验证相关结果时，不必为该语义判断增加截图循环；不能据此宣布布局或整体 UI 质量通过 |
| 间距、裁切、遮挡、素材或画布是否符合要求 | 查看当前构建在目标视口、目标状态的截图；指定需修正的区域，并保留功能断言 | 已有视觉基线能覆盖并判定该要求时，复用它；结构树不能替代视觉验收，截图不能证明保存与后续交互 |
| 加载时点击无效、输入被重置或状态先后不对 | 保留真实输入发生时刻、动作前后状态及相关请求/事件顺序，先读已有 trace，必要时加定向日志 | 原测试能触发时序并验证结果时，复用测试；最终截图或最终 DOM 都可能漏掉中途丢失的输入 |
| 路径能完成，但用户找不到入口、误解结果或觉得难用 | 请代表用户完成具体任务，观察选择、误解和恢复，再把明确要求补进验收 | 自动检查继续覆盖客观要求；视觉相似度或模型评分不能独自替用户接受体验 |

**✅ 改表单、弹窗或展开菜单时，复用现有语义与键盘回归；需要补查标签、对比度等自动可检问题，再把 axe 接入已有浏览器测试。** 扫描前实际触发并等到待验状态，首页初态扫描不覆盖未激活或未渲染的菜单、弹窗等内容。已有违规暂不能修时，可记录“规则＋目标元素”的窄基线，避免为一处问题排除整个容器；按既定验收级别关闭不适用规则仍合理。role 定位成功和零违规都不能代替焦点、键盘及辅助技术实际使用检查。详见[固定官方机制与 GOV.UK 采用](research/2026-10-12-development-conditions.md#无障碍反馈扫描当前状态与保留必要检查)。

**稳定视觉基线继续用，过渡和暂停路径先验真实状态。** 未由项目配置或调用参数覆盖时，Playwright `toHaveScreenshot()` 默认 `animations: 'disabled'`，而 `page.screenshot()` 默认 `allow`；前者会结束有限动画并触发回调，或取消后重播无限动画，并非暂停当前帧。把终态视觉比较放在相关输入、暂停后恢复／取消后重开检查之后；已有测试能验证这些行为就复用。若所需状态本来已稳定，却被截图准备改变，可只对这一处设 `animations: 'allow'`，保留现有视觉基线。要判断过渡中的操作则复用 trace 或定向事件记录；`allow` 仍不保证捕获调用瞬间，稳定图比较也不能替代时序证据。详见[固定源码、官方回归与 Ionic 历史报告](research/2026-10-12-development-conditions.md#截图稳定化结束动画不是保留当前状态)。

**原生 `<select>` 的展开菜单可能未被网页截图如实捕获，别仅据截图缺失就让 Agent 重写控件。** 只验选值与应用结果时优先用 `selectOption()` 并断言结果；要验展开层的可读性或遮挡时，再查看目标浏览器／系统的实际屏幕，语义选择不证明展开外观。详见[维护者说明与复现边界](research/2026-10-12-development-conditions.md#原生下拉菜单的截图与语义验收)。

**截图显露偏差，不保证下一次修改更好。** Design2Code-HARD 的同类视觉自修订在 GPT-4o 与 Claude 3.5 Sonnet 上方向不同；较新的 Sonnet 4.5 研究报告视觉与代码联合 critique 有收益，也有明显 token 增量，未隔离截图贡献。先针对缺口修一轮，对照前版与原断言，再决定是否继续；不默认固定三轮。详见[比较条件与限制](research/2026-10-12-development-conditions.md#交互界面按缺失观察选择反馈)。

不熟悉的页面可先探索真实结构和路径，稳定后写回现有测试。测试应通过浏览器输入接口执行点击、键盘等用户动作；直接用页面脚本设置组件状态或调用内部保存函数，只能辅助准备或诊断，不能代替该用户路径验收。不需要同时安装三套工具；优先复用项目 Playwright 配置、浏览器依赖与认证夹具，大量重复操作再比较 CLI/脚本的成本与日志完整性。

**依据**：[一手：S7] Playwright MCP README 的 accessibility snapshot 与 CLI／Skills 建议；[经验：采用判断] 按验收缺口选择反馈；[一手；经验：采用判断，未运行浏览器] GOV.UK 无障碍扫描采用；[一手／社区；经验：最小选择，未运行浏览器] 截图稳定化行为；[一手／社区；经验：验收选择] 原生下拉菜单截图边界；[一手：论文报告；经验：接入与撤回条件] Design2Code-HARD 自修订比较；[经验：工程建议] 探索后写回测试、复用现有配置；核实 2026-10-21。

### 先让真实组件接住续改，再验完整应用

**已有 Storybook 的项目，默认用“当前组件源码＋直接行为测试＋目标 story play”接收复杂 UI 续改。** 比只构建或只测通用控件多一步：让真实 Panel／hook 走到新增状态；若项目没有这套入口且现有测试足够，不为它另建工具链。

1. 让 Agent 复用组件和应用端口，写出目标状态：正常选择、提交中、失败后恢复；保留用户真实输入与等待顺序。
2. 对新增路径补断言，运行选定故事并等待 play 完成、收集浏览器错误；反馈回同一实现，修后只重验受影响路径。
3. 用旧候选核关键回归确实失败，再接收修订；假服务验的是组件交互，持久化、真实后端和桌面宿主另回应用验收。

Maka 侧聊模型选择的独审发现两个问题：无效模型同时禁用了恢复选择器，发送又未等待模型写入。Agent 分开发送与选择就绪状态、让写入进入发送结算；同组测试旧候选 5 项失败、修后 82 项通过，四个目标 play 也在 Chrome 中通过。**可借用的是实际状态反馈，不是“装 MCP 就会更好”**：本次未调用 MCP，复用现有故事和测试即可完成这段接收。

**🧪 页面请求失败或卡顿，现有证据不足时，再试 Chrome DevTools MCP。** 基线是项目 Playwright 测试/trace 与人工 DevTools；增量是把实时控制台、网络与性能诊断交给 Agent。只有找到原先难获的原因或减少抄日志才保留，稳定路径仍写回归。**关键局限**：浏览器内容可被读取/修改，localhost 不代表零外发；须用隔离测试 profile，核对统计、CrUX 与请求头脱敏开关，脱敏不保护全部正文、URL 或截图。

## 3. 给 Agent 一个可验收的任务

**把“做好看一点”改成可验收的行为约定，并给每项标注检查方式。** 以“增加收货地址表单”为例，约定下面的行为：

1. 已登录测试用户可以输入地址并保存；保存后列表出现新条目。
2. 刷新页面后条目仍存在；若承诺服务端已保存，另用独立 API 读取核对本次条目；清理时只删除本次测试创建的数据。
3. 必填字段缺失时有可理解的提示，焦点能到达需要修正的字段。
4. 保存失败保留输入并允许重试；不显示错误的成功提示。
5. 提交中重复点击不造成重复记录；服务端也要有对应约束。
6. 在桌面与目标手机视口下，按钮可见、没有阻止操作的横向溢出。
7. 键盘可以完成主要路径；错误信息与字段关联。此检查不能替代完整无障碍审计。

对每项注明是人工检查、浏览器断言、API 检查还是数据库测试。不要让同一个截图承担全部验收。

**依据**：[经验：工程建议] 可验收行为清单与检查方式分工；核实 2026-10-21。

## 4. 一次完整验证的顺序

**按本次交付选需要验证的路径，再依准备、就绪、用户操作、数据与视觉的顺序取证。** 复用已有有效检查；局部交互改动不自动扩成整个产品的验收。

1. **准备**：确认工作目录、启动命令、端口、测试账号、数据隔离和依赖服务。创建本次运行标识。
2. **就绪**：从实际浏览器访问当前构建的代表页面，再核相关 API。服务端自检成功不保证浏览器所在环境可达；遇到差异先核执行位置与服务入口，不先改产品代码。若待验的是加载过程，另从原入口保留数据尚未返回的阶段，不先把目标页面等到终态。
3. **走用户路径**：按角色/可访问名称或项目稳定 test ID 定位，用浏览器输入接口执行操作，并等待业务结果断言；若控件已向用户呈现为可操作，也要覆盖此刻的输入，不能统一推迟到加载完成。避免用固定 sleep 掩盖竞争条件。
4. **查运行故障**：检查 console error、失败请求、关键响应内容；第三方遥测失败与业务失败分开记录。
5. **验证数据与权限**：先明确保存承诺。本地保存（含偏好）验重新打开后的数据；服务端同步用绕过页面缓存的 API 读回本次记录，再按任务切换角色。只读展示承诺不改原文时，核业务写入请求及独立数据前后比较；读取 RPC 也可能用 POST，“无 POST”不是判据。Service Worker 可直接返回页面，新标签页不证明已同步，API 读回也不等于数据库耐久性；见[响应来源与固定回归](research/2026-10-12-development-conditions.md#service-worker响应来源决定保存与故障验收入口)。
6. **检查视觉**：按 §2 的反馈选择复用已有验收；布局、样式、遮挡或视觉质量属于要求时，仍保存必要尺寸与关键状态的截图，记录 viewport、主题、数据和浏览器版本。
7. **固化与清理**：将有价值的复现变成回归测试；保留运行报告，清理本次运行的数据和自己启动的进程。

**Memos 的实际接收分开用了这几种证据。** 前后端构建与 API 已通，早期执行入口却未能把页面交给浏览器；后来用受支持的正常桌面入口启动同一构建，才实际接收匿名过滤、键盘开关及刷新／导航偏好，产品代码未变。网络记录和 SQLite 原文比较支持“阅读不写 memo”；实际导出的 PNG 另核分享仍含完整原文，不能用 API 或页面截图代替导出文件。

**依据**：[经验：工程建议] 七步顺序、就绪与数据检查；[研究] Service Worker 响应来源（正文链接），原核实 2026-10-21；[本仓实际采用] [Memos 真实匿名页面接收](collaboration/local-jobs/A-MEMOS-BUILT-SMOKE-001.md#当前执行)（2026-10-25 UTC 运行，2026-10-26 回流；仅匿名阅读，owner 写入／写后焦点及完整应用未验）。

### 首屏短暂失败：先验过程，再验终态

**用户报告“打开链接时闪出错内容”，先把该时段纳入测试。** Simon 的 Markdown 渲染工具收到这类投诉后，固定补丁在外部库之前根据 URL 选布局，并加入加载、Retry 和 Edit URL。新增 Playwright 测试分别暂停首个 CDN 脚本与 Gist 响应，检查 1280／390 宽、新 query／旧 hash 入口的中间状态，再检查成功输出与 503 恢复出口。源码支持这套测试设计，实际通过状态见 §8。

让 Agent 用已有路由控制重建阶段，结合 trace 核对顺序，保留四项检查；人确认每项预期，而非把“没有闪烁”当作完整目标：

1. **脚本前**：外部库尚未执行时，应该隐藏的编辑器、默认示例或旧内容是否已经露出；加载布局本身是否正确。
2. **数据前**：脚本可运行、业务数据仍在途时，占位是否可理解，可见控件是否按承诺可用。
3. **成功后**：放行数据，核最终文档与布局，以及原交互仍可完成。
4. **错误与恢复**：确认故障响应确实命中，再验错误提示、重试及修改输入后能继续；不能用一直隐藏内容换取“不闪错”。

**接收与撤回**：修后仍从原入口进入，阶段断言和恢复路径通过才接收对应范围；等待更久才绿、原触发条件被删除，或恢复出口丢失，就撤回“已修好”并恢复原检查。上述公开测试使用模拟 Gist 响应，390 宽也不是移动设备实测；真实服务和目标设备依产品承诺另验，详见[来源与范围](research/2026-10-13-browser-healing-outcomes.md#p56真实失败阶段与同版本验收)。

**依据**：[一手：固定补丁与测试，见研究记录] Simon 的固定修订与新增 Playwright 测试；[经验：由案例提炼] 四项阶段检查；[研究：边界] 公开测试使用模拟 Gist 响应，390 宽不是移动设备实测；核实 2026-10-21。

### 其他交互失败的分流

**点击被拦截时，先区分选错目标、真实遮挡和工具误报。** 优先点用户实际操作的控件，例如样式开关的可见 label；保持原业务断言，不为通过而删除遮罩或换成内部函数。若匹配已知浏览器／DOM 命中缺陷，核工具修复版本，再在原结构用普通点击复测。Keycloak 与 Playwright 的维护链分别支持这两种选择，详见[维护链](research/2026-10-13-browser-healing-outcomes.md#点击补研目标遮挡与命中检查误报分流)。**局限：force 仍是坐标输入，会跳过多项等待与命中检查；正常返回也不保证原目标收到点击。** 有依据地用于局部诊断时仍核目标响应，不作为统一修复开关。

**弹窗内现成控件失效，先核底层组件与 Portal 的挂载位置。** 如果任务仍需模态隔离，优先比较局部接回弹窗容器与换用兼容组件，再走选值、键盘切换、关闭后焦点返回的完整路径；只为点中选项设置 `modal={false}` 会同时改变其他行为。shadcn 的 Base UI Combobox 与 Radix Dialog 混用案例中，用户分别采用容器补丁或替换 Dialog；另有人撤掉模态后发现背景效果消失。需求本就允许操作背景时，非模态仍是合理选择。详见[固定补丁与不同用户回执](research/2026-10-13-product-feedback-contract.md#shadcn弹层组合先保所需模态行为再选局部修复)。**局限：容器补丁尚未合入，回执未覆盖完整键盘与恢复路径。**

**控件可见、启用，不等于监听器已经就绪。** Playwright 官方 hydration 说明指出：过早启用的控件可能吞掉点击，输入也可能随后被重置；可在慢网络下于控件出现时操作以复现。修复方向是让应用在功能就绪前禁用控件，而不是给测试增加等待来避开用户会遇到的窗口。截图和可操作性检查都不能单独证明输入已被业务处理。

**已复现旧状态停滞、根因仍不明时，补关键状态的时间线。** 保留实际失败构建，复用现有浏览器和临时日志，只记录能区分假设的事件顺序；确认触发条件后写入回归，移除日志再复测原路径。React 的历史 `useDeferredValue` 在生产／开发构建表现不同；作者记录 Claude 以生产构建复现、阅读相关源码并加日志定位后修复，详见[原帖、固定补丁与证据边界](research/2026-10-12-development-conditions.md#react生产构建故障中的定向日志)。**关键局限**：这是专家引导的单例，不能证明日志的独立收益，日志也可能改变时序。

截图与日志必须来自当前构建和本次运行，不能引用旧产物作为验收。无法启动后端时，mock 可以验证前端分支，但报告应明确未覆盖真实集成。

**故障注入要验实际命中。** `page.on('request')` 收到事件，不代表 `page.route()` 回调能拦截该请求；在支持 worker 请求观测／路由的 Chromium 上，可用 context 路由处理 Service Worker 发出的可拦截网络请求，并核对归属、命中及故障响应。普通 API mock 可考虑禁用 worker，但产品承诺离线功能时应保留。只注册 500／断网规则不算覆盖恢复路径。详见[官方测试与工具反例](research/2026-10-12-development-conditions.md#service-worker响应来源决定保存与故障验收入口)。

**修改输入控件时，把候选确认与业务提交分开验。** Agent 可查事件与写状态竞争回归；人用目标 OS／输入法确认候选不误发、随后提交正文完整，取消后保留约定草稿。文本注入适合查值，却不经过真实候选窗。涉及富文本时同时核文档结构；承诺持久草稿时再验重开。原有保存、权限、重复提交与视觉检查仍适用。详见[Hermes／Lexical 的固定修复与验证边界](research/2026-10-12-development-feedback.md#输入控件修改后先分开组合输入与业务提交2026-10-20)。

**依据**：[一手／社区／研究] Keycloak 与 Playwright 的点击命中维护链；[一手／社区；经验：交付选择] shadcn 弹层组合的固定补丁与不同用户回执（容器补丁尚未合入）；[一手：官方机制说明；经验：验收边界，未做本页应用实测] [Playwright hydration 说明](https://playwright.dev/docs/navigations#hydration)；[一手：作者记录与补丁；经验：最小接入建议] React 生产构建定向日志单例；[一手：机制；经验：验收选择] Service Worker 故障注入与路由；[一手；经验：验收建议，未做原生 IME 实测] Hermes／Lexical 输入控件修复与验证边界；核实 2026-10-21。

## 5. 浏览器状态也是测试输入

**把浏览器会话状态当作测试输入，固定来源再验收。** Playwright MCP 支持持久化 profile，也支持 `--isolated` 在内存中保留 profile；`--storage-state` 可为隔离会话提供初始存储状态。

**给 Agent 明确的会话输入**：首次访问用干净会话，已有用户用指定测试状态；新页面不等于干净会话。记录登录、cookies、local storage、service worker 及测试数据来源。无人值守试验不用真实个人 profile；可能含凭证的 storage-state 须受控保存，不提交公开仓库。

**已有用户的前端更新，验收输入还要包含发布前的旧页。** 详见[18的任务分流](18-team-adoption.md#agent-更新前端先给旧用户的验收输入)：让 Agent 准备“旧页开始任务→发布新版→继续操作→新旧标签并存→安全换版”的回归，分别核原始响应版本、真实路由和草稿／写入结果，补保护到期及未覆盖请求。人确认哪些状态不可丢。**✅ 交付入口优先复用应用已有浏览器任务回归**：只读任务在明确允许刷新时验恢复后可继续；草稿不可丢时验原文保留／按约定恢复及提交后读回。上游单 ID 传播或模拟版本检测测试适合机制诊断，不替代这两类业务断言，测试专用开关也不照搬到生产。详见[固定测试入口与两种任务卡](research/2026-10-12-development-feedback.md#跨发布判定器诊断入口与交付入口)。

**依据**：[一手：S7] Playwright MCP 持久化 profile、`--isolated` 与 `--storage-state`；[经验：工程建议] 会话输入与凭证保存；[一手；研究：验收选择，任务卡未运行] 跨发布旧页验收与两种任务卡；核实 2026-10-21。

## 6. 自修复测试的边界

**Agent 可以探索新的元素定位方式，但先按失败性质决定改定位器、改断言、修应用还是报告歧义。**

| 失败 | 允许的处理 | 不应做的处理 |
|---|---|---|
| 无害的 DOM 重构 | 调整定位器，保留业务断言 | 删除检查以恢复绿色 |
| 按钮名称有意变更 | 对照需求同步断言 | 仅因测试失败就接受任意文案 |
| 一个入口拆成不同业务动作 | 用原需求区分目标，补能区分结果的验收；意图仍不明才询问 | 任挑一个能让旧断言通过的新按钮 |
| 提交不再保存数据 | 修复应用或报告缺陷 | 把“保存成功”改成“按钮存在” |
| 用例间数据冲突 | 隔离夹具并重跑 | 无限增加重试次数 |
| 动画或异步竞争 | 等待明确业务状态 | 统一加入长 sleep |

**页面迁移后，先确认测试实际进入新版，再核本次记录的完整结果。** 新旧页面并存时，同样的环境标签可能落到不同版本；按页面实际状态适配定位器，继续检查本次提交的数据及后续操作。列表切换若改变搜索范围，应重新搜索并等待目标记录，不能把旧计数或控件恢复可用当作业务完成。WordPress Forms 的真实迁移修订保留了提交、查收、垃圾箱与恢复路径。详见[固定补丁、评审和回执](research/2026-10-13-browser-healing-outcomes.md#真实页面迁移先核实际分支与本次记录)。**局限：修后回执只确认工作正常，未提供最终跨浏览器完整矩阵；后续页面变化再次打断了覆盖。**

**保留原断言，也可能选错任务。** E2E-Self-Heal 的受控场景把一个提交按钮拆成 Save draft 与 Publish，两者都满足旧的 Thanks! 断言；公开修后运行仍将歧义场景修成绿色。先核原需求能否区分新动作，已有依据时据此修定位器与验收，没有依据就报告歧义，不能靠定位唯一或测试变绿替人选业务。详见[固定场景与修后证据](research/2026-10-13-browser-healing-outcomes.md#保留断言之后动作含义仍可能改变)。**局限：这是人工变更的 demo 与作者运行报告，不是生产误修率。**

**修测试前，连同结果写清必要的前置状态；修后仍走这个状态。** 公开受控运行中，Agent 能修正错误定位器并继续检出计数不增，也会保留账号名断言、却删掉触发登录故障的导航条件而通过。合法的地址修复应保留所需状态，不必锁死无关 URL；已有故障复现可复用来检查修后测试是否仍能检出原问题。详见[原任务、补丁与前后报告](research/2026-10-13-browser-healing-outcomes.md#修后仍走原状态而非只保留结果断言)。**局限：该合成夹具的提示只锁定结果，未明确锁定场景条件，不能据此认定 Agent 明知违令；补写条件的效果也未实测。**

生成测试与评判测试不能共享“无论如何让 CI 变绿”的目标。关键流程由人确认验收语义，Agent 可以修改实现与定位细节。

Playwright 官方 healer 允许修正断言与预期值，也允许在确信测试正确而错误持续时用 `test.fixme()` 跳过并说明原因。把“保留验收语义后通过”和“发现缺陷后隔离”分别报告；新增 skip/fixme 不计为修复成功，断言变更要对应需求依据。解析／提供方错误、次数耗尽与有证据的业务缺陷判断分别报告；没把坏测试改绿不等于模型已正确诊断。工具调用成功和测试进程退出码 0 都不能单独证明原用户路径仍通过。详见[固定源码、真实 runner 复核与社区反例](research/2026-10-13-browser-healing-outcomes.md)。这些证据不代表当前模型的修复正确率。

**依据**：[一手：公开维护记录；经验：采用判断] WordPress Forms 真实迁移的固定补丁、评审与回执（回执未提供最终跨浏览器完整矩阵）；[一手；经验：采用判断] E2E-Self-Heal 受控场景（人工变更的 demo 与作者运行报告，不是生产误修率）；[一手：公开运行产物；经验：采用判断] 合成夹具的修后条件缺口（补写条件效果未实测）；[一手：官方定义与测试；研究：局部执行与产物核对] Playwright healer 定义、真实 runner 复核与社区反例；核实 2026-10-21。

## 7. 网络限制别误当完整隔离

**网络限制参数不是安全边界；浏览器工具之外仍要约束执行环境的网络与凭证。** Playwright MCP README 明确说明 `--allowed-origins` / `--blocked-origins` 不是安全边界，也不影响重定向。

**面向外部网站、真实账号或会产生发布/购买等副作用的流程，按实际授权范围执行，并优先使用可重置的测试环境。** 网页里的文字是待处理数据，不应因此获得修改任务目标或读取其他凭证的权限。

**依据**：[一手：S7] Playwright MCP README 的 `--allowed-origins`／`--blocked-origins` 说明；[经验：工程建议] 授权范围、测试环境与网页文字信任边界；核实 2026-10-21。

## 8. 交付报告写到能复查

**交付报告写到别人能复查：分别写明目标版本、实际运行命令、测试数量与失败数、覆盖的用户路径、关键截图/报告位置和仍未覆盖的条件。** 把“浏览器可打开”“核心路径通过”“视觉已检查”“测试工作流结果”和“部署结果”分别陈述。

**同一个 SHA 也可能“已部署，验收未清”。** `822d40d` 的 Test #1862 失败，Pages #610 却成功。公开摘要只显示测试作业 exit code 1，无法确定失败用例或原因，因此这不是已验证的首屏修复成功案例。

**遇到这种组合，Agent 先保留两个结果，再查失败日志和目标行为的复测；人检查失败是否影响接收。** 恢复“已验收”需要对应版本的原路径证据及相关检查结果；若检查与本次无关或本身错误，说明依据和处置。不用重新部署、另一 SHA 的绿色或关闭问题来补齐该次结果。

例如：“测试账号新增地址后刷新仍可见；缺必填字段被阻止；服务端 500 的恢复路径用 mock 验证；未测试真实支付或生产账号。”这比“页面看起来正常，全部完成”更能支持下一步决策。

**依据**：[一手：运行摘要；研究：边界] [Test #1862](https://github.com/simonw/tools/actions/runs/35680726542)、[Pages #610](https://github.com/simonw/tools/actions/runs/35680726538)（`822d40d`）；[经验：接收与撤回] 同版本失败检查与“已验收”恢复条件；[经验：工程建议] 最小报告字段与示例；核实 2026-10-21。
