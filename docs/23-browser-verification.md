# 23 · 前端与浏览器验证：从可见到可用

> 编辑：2026-10-20（仅补无障碍反馈选择，其余事实沿用各项日期）；适用：Agent 实现 Web 页面、修交互 bug、生成端到端测试。
> 评级：✅ 采用真实用户路径和多层证据；🧪 试用浏览器 Agent 探索，稳定流程沉淀为回归测试。
> 工具事实来自 Microsoft Playwright MCP 官方仓库 [S7](research/2026-10-10-audit.md)；测试设计为 **[经验：工程建议]**。本仓库没有 Web 应用；Ra & Apep 为对端实测记录，React 案例为外部历史修复；其余未标来源的示例仍是测试设计。

## 1. 为什么编译通过仍然不够

类型检查发现不了按钮被遮挡；截图证明不了点击后的数据保存；HTTP 200 也可能携带业务错误。前端交付至少要回答：**用户能否完成目标，数据是否正确，异常时能否恢复？**

| 层次 | 要拿到的证据 | 不能替代什么 |
|---|---|---|
| 构建 | 实际构建命令与结果 | 浏览器运行 |
| 结构 | 页面语义、可访问名称、可操作元素 | 布局与视觉表现 |
| 交互 | 输入、点击、导航后的断言 | 数据真实持久化 |
| 状态 | 按保存契约重新打开或独立读取后，结果仍符合预期 | 跨租户/跨账号权限测试 |
| 视觉 | 目标尺寸的截图、溢出与遮挡检查 | 功能和完整无障碍审计 |
| 异常 | 超时、拒绝、空数据、重试的行为 | 未覆盖故障的可靠性 |

**实际案例：先确认检查覆盖的是哪个使用状态。** Ra & Apep 承诺无 JavaScript 可阅读，但旧版重启按钮依赖脚本。对端记录的本地前后对照显示：原有 12 项自检只覆盖滚动计算，旧版启用 JS 时全过，禁用 JS 时重启仍无效；换成原生锚点后，无 JS 场景恢复。动画、静态场景也复测通过。检查不必无限增加，应针对产品承诺选择状态；此处无需新工作流，关键是识别脚本依赖与原生功能。见[固定版本和六场景记录](research/2026-10-12-codex-delivery-cases.md) **[经验：对端本地功能实测记录，本侧未独立复跑，未全面视觉验收]**。

## 2. MCP、CLI 与测试代码各做什么

Playwright MCP 通过结构化的 accessibility snapshot 暴露页面，常规操作不要求视觉模型；其 README 也建议 coding agents 考虑 CLI + Skills，并说明 MCP 适合需要持续浏览器上下文、结构探索和迭代操作的场景。**[一手：S7]**

**先选择缺失的观察，再决定是否加工具。** 浏览器是运行环境；DOM/可访问性树、截图、动作与事件时间线提供不同证据。下表是按验收缺口选择的工程建议，不是通道效果排名。**[经验：采用判断]**

| 需要判断的问题 | 最小反馈与实施选择 | 何时已有测试足够；仍缺什么 |
|---|---|---|
| 选中、禁用、保存结果是否正确 | 用现有浏览器输入/点击路径，读 DOM/可访问性状态，并断言保存后的业务结果 | 已稳定触发并验证相关结果时，不必为该语义判断增加截图循环；不能据此宣布布局或整体 UI 质量通过 |
| 间距、裁切、遮挡、素材或画布是否符合要求 | 查看当前构建在目标视口、目标状态的截图；指定需修正的区域，并保留功能断言 | 已有视觉基线能覆盖并判定该要求时，复用它；结构树不能替代视觉验收，截图不能证明保存与后续交互 |
| 加载时点击无效、输入被重置或状态先后不对 | 保留真实输入发生时刻、动作前后状态及相关请求/事件顺序，先读已有 trace，必要时加定向日志 | 原测试能触发时序并验证结果时，复用测试；最终截图或最终 DOM 都可能漏掉中途丢失的输入 |
| 路径能完成，但用户找不到入口、误解结果或觉得难用 | 请代表用户完成具体任务，观察选择、误解和恢复，再把明确要求补进验收 | 自动检查继续覆盖客观要求；视觉相似度或模型评分不能独自替用户接受体验 |

**✅ 改表单、弹窗或展开菜单时，复用现有语义与键盘回归；需要补查标签、对比度等自动可检问题，再把 axe 接入已有浏览器测试。** 扫描前实际触发并等到待验状态，首页初态扫描不覆盖未激活或未渲染的菜单、弹窗等内容。已有违规暂不能修时，可记录“规则＋目标元素”的窄基线，避免为一处问题排除整个容器；按既定验收级别关闭不适用规则仍合理。role 定位成功和零违规都不能代替焦点、键盘及辅助技术实际使用检查。见[固定官方机制与 GOV.UK 采用](research/2026-10-12-development-conditions.md#无障碍反馈扫描当前状态与保留必要检查)。**[一手；经验：采用判断，未运行浏览器]**

**稳定视觉基线继续用，过渡和暂停路径先验真实状态。** 未由项目配置或调用参数覆盖时，Playwright `toHaveScreenshot()` 默认 `animations: 'disabled'`，而 `page.screenshot()` 默认 `allow`；前者会结束有限动画并触发回调，或取消后重播无限动画，并非暂停当前帧。把终态视觉比较放在相关输入、暂停后恢复／取消后重开检查之后；已有测试能验证这些行为就复用。若所需状态本来已稳定，却被截图准备改变，可只对这一处设 `animations: 'allow'`，保留现有视觉基线。要判断过渡中的操作则复用 trace 或定向事件记录；`allow` 仍不保证捕获调用瞬间，稳定图比较也不能替代时序证据。见[固定源码、官方回归与 Ionic 历史报告](research/2026-10-12-development-conditions.md#截图稳定化结束动画不是保留当前状态)。**[一手／社区；经验：最小选择，未运行浏览器]**

**原生 `<select>` 的展开菜单可能未被网页截图如实捕获，别仅据截图缺失就让 Agent 重写控件。** 只验选值与应用结果时优先用 `selectOption()` 并断言结果；要验展开层的可读性或遮挡时，再查看目标浏览器／系统的实际屏幕，语义选择不证明展开外观。见[维护者说明与复现边界](research/2026-10-12-development-conditions.md#原生下拉菜单的截图与语义验收)。**[一手／社区；经验：验收选择]**

**截图显露偏差，不保证下一次修改更好。** Design2Code-HARD 的同类视觉自修订在 GPT-4o 与 Claude 3.5 Sonnet 上方向不同；较新的 Sonnet 4.5 研究报告视觉与代码联合 critique 有收益，也有明显 token 增量，未隔离截图贡献。先针对缺口修一轮，对照前版与原断言，再决定是否继续；不默认固定三轮。见[比较条件与限制](research/2026-10-12-development-conditions.md#交互界面按缺失观察选择反馈)。**[一手：论文报告；经验：接入与撤回条件]**

不熟悉的页面可先探索真实结构和路径，稳定后写回现有测试。测试应通过浏览器输入接口执行点击、键盘等用户动作；直接用页面脚本设置组件状态或调用内部保存函数，只能辅助准备或诊断，不能代替该用户路径验收。不需要同时安装三套工具；优先复用项目 Playwright 配置、浏览器依赖与认证夹具，大量重复操作再比较 CLI/脚本的成本与日志完整性。**[经验：工程建议]**

### 诊断缺口：Chrome DevTools MCP

**🧪 页面请求失败或卡顿，现有证据不足时，再试 [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp)。** 基线是项目 Playwright 测试/trace 与人工 DevTools；增量是把实时控制台、网络与性能诊断交给 Agent。只有找到原先难获的原因或减少抄日志才保留，稳定路径仍写回归。**关键局限**：浏览器内容可被读取/修改，localhost 不代表零外发；须用隔离测试 profile，核对统计、CrUX 与[请求头脱敏开关](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md)，脱敏不保护全部正文、URL 或截图。**[一手；经验：采用判断，2026-10-12，未连接浏览器]**

## 3. 给 Agent 一个可验收的任务

以“增加收货地址表单”为例，约定下面的行为，而不只说“做好看一点”：**[经验：工程建议]**

1. 已登录测试用户可以输入地址并保存；保存后列表出现新条目。
2. 刷新页面后条目仍存在；若承诺服务端已保存，另用独立 API 读取核对本次条目；清理时只删除本次测试创建的数据。
3. 必填字段缺失时有可理解的提示，焦点能到达需要修正的字段。
4. 保存失败保留输入并允许重试；不显示错误的成功提示。
5. 提交中重复点击不造成重复记录；服务端也要有对应约束。
6. 在桌面与目标手机视口下，按钮可见、没有阻止操作的横向溢出。
7. 键盘可以完成主要路径；错误信息与字段关联。此检查不能替代完整无障碍审计。

对每项注明是人工检查、浏览器断言、API 检查还是数据库测试。不要让同一个截图承担全部验收。

## 4. 一次完整验证的顺序

**[经验：工程建议]**：

1. **准备**：确认工作目录、启动命令、端口、测试账号、数据隔离和依赖服务。创建本次运行标识。
2. **就绪**：访问有代表性的页面/API，确认必要数据返回；PID 和开放端口不足以证明可用。
3. **走用户路径**：按角色/可访问名称或项目稳定 test ID 定位，用浏览器输入接口执行操作，并等待业务结果断言；若控件已向用户呈现为可操作，也要覆盖此刻的输入，不能统一推迟到加载完成。避免用固定 sleep 掩盖竞争条件。
4. **查运行故障**：检查 console error、失败请求、关键响应内容；第三方遥测失败与业务失败分开记录。
5. **验证持久化与权限**：先明确保存承诺。本地保存验重新打开后的数据；服务端已同步则另用绕过页面缓存的 API 读取核对本次记录，再按任务切换测试角色。Service Worker 可在未访问服务端时返回成功页面，新标签页也不能单独证明已同步；这类读取仍不等于数据库耐久性验证。见[响应来源与固定回归](research/2026-10-12-development-conditions.md#service-worker响应来源决定保存与故障验收入口)。
6. **检查视觉**：按 §2 的反馈选择复用已有验收；布局、样式、遮挡或视觉质量属于要求时，仍保存必要尺寸与关键状态的截图，记录 viewport、主题、数据和浏览器版本。
7. **固化与清理**：将有价值的复现变成回归测试；保留运行报告，清理本轮数据和自己启动的进程。

**点击被拦截时，先区分选错目标、真实遮挡和工具误报。** 优先点用户实际操作的控件，例如样式开关的可见 label；保持原业务断言，不为通过而删除遮罩或换成内部函数。若匹配已知浏览器／DOM 命中缺陷，核工具修复版本，再在原结构用普通点击复测。[Keycloak 与 Playwright 的维护链](research/2026-10-13-browser-healing-outcomes.md#点击补研目标遮挡与命中检查误报分流)分别支持这两种选择。**局限：force 仍是坐标输入，会跳过多项等待与命中检查；正常返回也不保证原目标收到点击。** 有依据地用于局部诊断时仍核目标响应，不作为统一修复开关。[一手／社区／研究]

**弹窗内现成控件失效，先核底层组件与 Portal 的挂载位置。** 如果任务仍需模态隔离，优先比较局部接回弹窗容器与换用兼容组件，再走选值、键盘切换、关闭后焦点返回的完整路径；只为点中选项设置 `modal={false}` 会同时改变其他行为。shadcn 的 Base UI Combobox 与 Radix Dialog 混用案例中，用户分别采用容器补丁或替换 Dialog；另有人撤掉模态后发现背景效果消失。需求本就允许操作背景时，非模态仍是合理选择。见[固定补丁与不同用户回执](research/2026-10-13-product-feedback-contract.md#shadcn弹层组合先保所需模态行为再选局部修复)。**局限：容器补丁尚未合入，回执未覆盖完整键盘与恢复路径。** **[一手／社区；经验：交付选择]**

**控件可见、启用，不等于监听器已经就绪。** Playwright [官方 hydration 说明](https://playwright.dev/docs/navigations#hydration)指出：过早启用的控件可能吞掉点击，输入也可能随后被重置；可在慢网络下于控件出现时操作以复现。修复方向是让应用在功能就绪前禁用控件，而不是给测试增加等待来避开用户会遇到的窗口。截图和可操作性检查都不能单独证明输入已被业务处理。**[一手：官方机制说明；经验：验收边界，非本轮应用实测]**

**已复现旧状态停滞、根因仍不明时，补关键状态的时间线。** 保留实际失败构建，复用现有浏览器和临时日志，只记录能区分假设的事件顺序；确认触发条件后写入回归，移除日志再复测原路径。React 的历史 `useDeferredValue` 在生产／开发构建表现不同；作者记录 Claude 以生产构建复现、阅读相关源码并加日志定位后修复，见[原帖、固定补丁与证据边界](research/2026-10-12-development-conditions.md#react生产构建故障中的定向日志)。**关键局限**：这是专家引导的单例，不能证明日志的独立收益，日志也可能改变时序。**[一手：作者记录与补丁；经验：最小接入建议]**

截图与日志必须来自当前构建和本次运行，不能引用旧产物作为验收。无法启动后端时，mock 可以验证前端分支，但报告应明确未覆盖真实集成。

**故障注入要验实际命中。** `page.on('request')` 收到事件，不代表 `page.route()` 回调能拦截该请求；在支持 worker 请求观测／路由的 Chromium 上，可用 context 路由处理 Service Worker 发出的可拦截网络请求，并核对归属、命中及故障响应。普通 API mock 可考虑禁用 worker，但产品承诺离线功能时应保留。只注册 500／断网规则不算覆盖恢复路径。见[官方测试与工具反例](research/2026-10-12-development-conditions.md#service-worker响应来源决定保存与故障验收入口)。**[一手：机制；经验：验收选择]**

## 5. 浏览器状态也是测试输入

Playwright MCP 支持持久化 profile，也支持 `--isolated` 在内存中保留 profile；`--storage-state` 可为隔离会话提供初始存储状态。**[一手：S7]**

**[经验：工程建议]**：新页面不等于干净会话。记录登录状态、cookies、local storage、service worker 和测试数据来源；不要使用带真实个人登录的 profile 进行无人值守试验。storage-state 可能包含会话凭证，应存于受控位置，不提交到公开仓库。

需要复现“首次访问”时使用干净会话；需要复现“已有用户”时使用明确的测试状态。两者要分别测试，而不是让缓存偶然决定结果。

## 6. 自修复测试的边界

Agent 能探索新的元素定位方式，但应先判断变化的性质：**[经验：工程建议]**

| 失败 | 允许的处理 | 不应做的处理 |
|---|---|---|
| 无害的 DOM 重构 | 调整定位器，保留业务断言 | 删除检查以恢复绿色 |
| 按钮名称有意变更 | 对照需求同步断言 | 仅因测试失败就接受任意文案 |
| 一个入口拆成不同业务动作 | 用原需求区分目标，补能区分结果的验收；意图仍不明才询问 | 任挑一个能让旧断言通过的新按钮 |
| 提交不再保存数据 | 修复应用或报告缺陷 | 把“保存成功”改成“按钮存在” |
| 用例间数据冲突 | 隔离夹具并重跑 | 无限增加重试次数 |
| 动画或异步竞争 | 等待明确业务状态 | 统一加入长 sleep |

**页面迁移后，先确认测试实际进入新版，再核本次记录的完整结果。** 新旧页面并存时，同样的环境标签可能落到不同版本；按页面实际状态适配定位器，继续检查本次提交的数据及后续操作。列表切换若改变搜索范围，应重新搜索并等待目标记录，不能把旧计数或控件恢复可用当作业务完成。WordPress Forms 的真实迁移修订保留了提交、查收、垃圾箱与恢复路径；见[固定补丁、评审和回执](research/2026-10-13-browser-healing-outcomes.md#真实页面迁移先核实际分支与本次记录)。**局限：修后回执只确认工作正常，未提供最终跨浏览器完整矩阵；后续页面变化再次打断了覆盖。** **[一手：公开维护记录；经验：采用判断]**

**保留原断言，也可能选错任务。** E2E-Self-Heal 的受控场景把一个提交按钮拆成 Save draft 与 Publish，两者都满足旧的 Thanks! 断言；公开修后运行仍将歧义场景修成绿色。先核原需求能否区分新动作，已有依据时据此修定位器与验收，没有依据就报告歧义，不能靠定位唯一或测试变绿替人选业务。见[固定场景与修后证据](research/2026-10-13-browser-healing-outcomes.md#保留断言之后动作含义仍可能改变)。**局限：这是人工变更的 demo 与作者运行报告，不是生产误修率。** **[一手；经验：采用判断]**

**修测试前，连同结果写清必要的前置状态；修后仍走这个状态。** 公开受控运行中，Agent 能修正错误定位器并继续检出计数不增，也会保留账号名断言、却删掉触发登录故障的导航条件而通过。合法的地址修复应保留所需状态，不必锁死无关 URL；已有故障复现可复用来检查修后测试是否仍能检出原问题。见[原任务、补丁与前后报告](research/2026-10-13-browser-healing-outcomes.md#修后仍走原状态而非只保留结果断言)。**局限：该合成夹具的提示只锁定结果，未明确锁定场景条件，不能据此认定 Agent 明知违令；补写条件的效果也未实测。** **[一手：公开运行产物；经验：采用判断]**

生成测试与评判测试不能共享“无论如何让 CI 变绿”的目标。关键流程由人确认验收语义，Agent 可以修改实现与定位细节。

Playwright 官方 healer 允许修正断言与预期值，也允许在确信测试正确而错误持续时用 `test.fixme()` 跳过并说明原因。把“保留验收语义后通过”和“发现缺陷后隔离”分别报告；新增 skip/fixme 不计为修复成功，断言变更要对应需求依据。解析／提供方错误、次数耗尽与有证据的业务缺陷判断分别报告；没把坏测试改绿不等于模型已正确诊断。工具调用成功和测试进程退出码 0 都不能单独证明原用户路径仍通过。见[固定源码、真实 runner 复核与社区反例](research/2026-10-13-browser-healing-outcomes.md)。这些证据不代表当前模型的修复正确率。**[一手：官方定义与测试；研究：局部执行与产物核对]**

## 7. 网络限制别误当完整隔离

Playwright MCP README 明确说明 `--allowed-origins` / `--blocked-origins` **不是安全边界，也不影响重定向**。浏览器工具参数之外仍需要执行环境的网络与凭证约束。**[一手：S7]**

面向外部网站、真实账号或会产生发布/购买等副作用的流程，要按实际授权范围执行；测试应优先使用可重置的测试环境。网页里的文字是待处理数据，不应因此获得修改任务目标或读取其他凭证的权限。**[经验：工程建议]**

## 8. 交付报告写到能复查

最小报告包括：目标版本、实际运行命令、测试数量与失败数、覆盖的用户路径、关键截图/报告位置、仍未覆盖的条件。把“浏览器可打开”“核心路径通过”“视觉已检查”分别陈述。

例如：“测试账号新增地址后刷新仍可见；缺必填字段被阻止；服务端 500 的恢复路径用 mock 验证；未测试真实支付或生产账号。”这比“页面看起来正常，全部完成”更能支持下一步决策。**[经验：工程建议]**
