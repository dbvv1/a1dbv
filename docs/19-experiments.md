## 4. E3：指令文件长短

**先写能改变行为的项目知识，用回归与过程指标检验它。** tomli 同一 off-by-one bug 在无、短、长指令三组共 **27 次全部修好**；短文件明确测试命令与回归要求，新增测试从无文件的 **2/9** 变为 **9/9**，长文件为 **8/9**；这些比例统计新增测试行为，不代表全部新增用例已证明能捕获旧 bug。长文件组按项目的数据驱动惯例加测试，历史 API 估算约为无文件组的 **1.6 倍（Haiku）/2.7 倍（Sonnet）**。**[经验：历史运行]**

保留项目特有命令与测试位置，再评估是否需要更多背景；完整 A/B/C 内容、逐项结果和反例验证见[研究记录](research/2026-10-12-experiment-records.md#4-e3指令文件长短)。

**局限**：单仓库简单任务里内容和长度同时改变，不能把差异全归因于文件长度，也不能把全成功外推为难任务无需知识。

## 5. E2：子 Agent 的成本

**一个文件、grep 能定位的小调查先直接做；真正独立或会挤占主上下文的大块工作再拆。** 在定位 tomli 的 29 处异常抛出任务中，两组各三次均找全；直接做与两子 Agent 的平均 API 等价估算分别为 **$0.0055/$0.0109**，墙钟 **17.6/47.1 秒**。单 Agent 还曾主动排除只在警告字符串中出现的异常名。**[经验：历史运行；研究：采用判断]**

完整提示、输入与轮数表见[原记录](research/2026-10-12-experiment-records.md#5-e2子-agent-的成本)，其他拆分条件见 [08](08-multi-agent.md)。

**局限**：这是同一任务的重复运行，不是 29 个独立任务，也未测不同视角或大上下文的收益。

## 6. 如何在自己的仓库复现

**固定好/坏基线，隔离运行并保留失败。** 每次用干净工作目录，只改变一项配置；跑完整相关测试，再把源码还原为有 bug 的版本，定向运行新增用例／fixture，或保存可归属的失败差异，确认失败确由新增测试捕获；保存 diff、事件与原始用量。历史命令和提取方式见[复现步骤](research/2026-10-12-experiment-records.md#6-如何在自己的仓库复现)，重新设计对照时用 [22](22-agent-evaluation.md)。**[经验：实验设计]**

**局限**：三次只是先导，同配置历史估算也曾从 $0.0055 到 $0.0120，不能据少量成功运行报告稳定倍数。
