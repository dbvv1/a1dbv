## 2. 九个关键趋势

### 2.1 开放格式：共享内容，分别核对入口 ✅

| 格式 | 值得复用什么 | 迁移前核对什么 |
|---|---|---|
| **AGENTS.md** | 项目命令、定位与行为约定 | Claude Code 的原生发现可能被项目中的 CLAUDE 文件抑制；Codex 的指令链、预算与刷新方式不同 → [03 加载规则](03-context-engineering.md#21-各工具的加载规则一手) |
| **Agent Skills** (`SKILL.md`) | 领域配方、参考资料与可靠脚本 | 宿主扩展和 `allowed-tools` 不保证可移植；能加载不等于相同的工具权限 → [05](05-skills-and-plugins.md#能加载不等于权限语义可移植) |
| **MCP** | 工具接口契约 | 客户端、SDK、服务端是否兼容；协议版本不保证凭证、隔离或业务结果 → [04](04-mcp.md#1-先决定是否需要新增连接) |

**含义**：需要共享时优先复用内容，但保留目标客户端必需的入口；不要为“开放标准”预装整套连接，也不要假定换工具后权限和行为不变。以上是已核官方契约与固定实现的采用判断，未做跨客户端运行验证。**[一手／经验：依据见各主专题]**

### 2.2 插件化：按新增能力采用 🧪

已有资料、CLI 或生成器满足任务就沿用；缺领域配方时试窄 Skill，确需共同分发多个组件时才装插件。**市场规模、官方标签和同时上架多家市场都不证明适合当前任务。** 安装前看实际包含的 Skill、MCP、Hook 与脚本，核对加载时执行和权限；目标质量或返工没有改善、反而增加等待与人工处理时缩减或撤回。依据与仍值得采用的领域反例见 [05](05-skills-and-plugins.md)。**[一手／经验：采用判断]**

### 2.3 自主性提升：审批与隔离分别判断

- Claude Code **auto mode** 的分类器仍有误差；[10 §3.1](10-security.md#31-auto-mode-能挡住多少官方公布的数字)保留官方样本、分母与局限，不能将历史测评率当作当前任务的安全保证。
- Codex **Auto-review** 选择审批者，不自动改写长期权限；获批提权仍可能使单次动作越过原沙箱，Computer Use 的 App 级审批直接交给用户 → [当前契约](01-agents/codex.md#审批沙箱与-auto-review)。
- **采用条件**：先确认实际生效的隔离、凭证与网络范围，再决定哪些动作可自动审批；Claude Code 的 MCP／Hook 不在命令沙箱内，外来仓库或带秘密的任务需要核对整个执行环境。若工具只能靠关闭防护或暴露生产凭证才能运行，暂停该步骤并换受限环境 → [10](10-security.md)。

**[一手／经验：主专题已核机制；未做本轮运行时安全验证]**

### 2.4 长时任务与多 Agent

**✅ 并行可独立验收的支线；共享接口、状态和写入面先收敛。** 并发数随可独立交付的工作与汇总／评审能力调整，不把 2–3 个或产品线程上限当最优配置；worktree 也不自动隔离服务、数据库和最终产物。**[一手／经验：依据见 08]**

🧪 需要共享协调或可重放批处理才增加 Teams／Workflow。启动前核对审批能否送达、谁收集结果和恢复是否重跑写入；出现权限等待或不明结果时先核已有动作，再缩回单层委派或串行相关步骤。**反证**：已有研究既有生成阶段更快的结果，也有质量提高却更贵、更慢的团队配置，因此比较必须算到整合与验收结束。机制、研究口径与限制统一见 [08](08-multi-agent.md)。**[一手／研究／经验：采用判断]**

### 2.5 上下文工程取代提示词工程
重点从“怎么措辞”转向“给模型看什么”：按需加载（Skills、MCP 工具搜索、LSP）、子 Agent 隔离、压缩、外置笔记 **[一手]**。→ [03](03-context-engineering.md)

### 2.6 官方接口：先核覆盖，再接入

官方 Skill、MCP 或引擎插件可以减少自建工作，但“官方”不替代当前版本、实际操作覆盖与结果回读。已有脚本／测试接口够用就沿用；缺编辑器状态或对象操作时，再按 [04 的任务选择](04-mcp.md#3-按任务选择服务与权限)与[游戏引擎接入](../domains/game-dev/01-engine-integration.md)判断。**[一手／经验：采用判断]**

### 2.7 不可信输入：可信服务也会返回外部内容

日志、Issue 与依赖中的指令不能授权后续执行。Sentry agentjacking 的原始研究支持“先诊断、另核建议命令来源与批准范围”，不证明当前各客户端均已复现或存在同等规模的真实入侵；来源与边界见 [04](04-mcp.md#日志与工单读取可信服务不等于相信内容)。具体攻击链与环境防线见 [10](10-security.md)。**[一手／经验：采用判断]**

### 2.8 从会话到常驻：完成与恢复需要证据

长时、后台与托管执行增加了续接选择，也增加了状态不明时重复写入的风险。**是否适合无人值守，要看权限、结果收集与恢复路径，而不是“常驻”标签。** 子任务能派发不等于完成，工具任务终态也不等于业务成功；没有可查的最终结果，就不交付无人值守的完成承诺 → [08](08-multi-agent.md)、[04 异步工具](04-mcp.md#异步工具完成的是哪一层)、[20 恢复与对账](20-codex-long-horizon.md#9-超时后动作究竟发生了吗)。**[一手／经验：采用判断]**

### 2.9 模型分层与“harness engineering”之争
- 模型按任务缺口选择：现有方案遇到推理或验证缺口，再试更强模型；目标清楚、结果可检查且有成本或等待缺口的子任务，可试 Haiku 5.5、GPT-6 Luna 等轻量模型，复杂调查不因委派就降档。**[研究：采用边界]** 2026-09 出现的**决策模型**（Jev、Clef 等）专做“从有限选项中选一个” → [02](02-models-and-cost.md#21-新类别决策模型2026-09-起)。
- 围绕“软件工厂能不能不读代码”的争论：验证体系重要，但现有 benchmark 不覆盖全部训练信号，也不能证明长期维护性。**先保留确定性检查和按风险的人审，额外评审看新增有效发现；缺少长期质量证明不等于模型不可能改善。** 相关假设与反证见 [09](09-review-and-quality.md#1-质量数据ai-代码的真实代价)、[14](14-synthesis.md)。**[研究：采用边界]**

## 4. 争议（看清再选）

| 争议 | 一方 | 另一方 | 本仓库判断 |
|---|---|---|---|
| MCP vs CLI | MCP 有类型契约、可隔离凭证、便于团队发现工具 | CLI 可组合（管道/jq）；成本取决于实际调用路径 | 已有授权 shell 时先用原生 CLI，按具体缺口补资料、短契约或 Skill；MCP 用于凭证隔离、受限执行或现有工具无法满足的访问需求 → [04](04-mcp.md)、[05](05-skills-and-plugins.md) |
| Spec 驱动开发 (SDD) | 先写规格再实现，减少返工 | “瀑布回归”：Spec Kit 给一个日期显示功能生成 1300 行 Markdown | 先固定会改变架构、安全或交付的不可猜契约；可观察的偏好用小样与反馈澄清，避免按功能大小套完整规格流程 → [07](07-workflows.md#5-spec-驱动开发sdd) |
| 多 Agent 并行 | 产能倍增 | 冲突、评审瓶颈、成本倍增 | 按依赖、共享状态与评审能力调并发；算到整合验收结束 → [08](08-multi-agent.md) |
| AI 到底提效多少 | METR 2026 问卷：技术人员自报价值提升 1.4–2 倍；实践者说“2 倍，不是 10 倍” | METR 2025 RCT：资深开发者慢 19%，却自认为快 20%；[2026 后续实验](https://metr.org/blog/2026-02-24-uplift-update/)有提速点估计，但选择偏差与计时问题使幅度不可靠，正在调整设计（2026-10-15 补核） | 收益高度依赖使用方式；要自己度量 → [11](11-community-pulse.md#4-生产力证据来源范围见各行) |
| 能不能不读代码（“软件工厂”） | StrongDM：代码不由人写、也不由人审，靠验证体系保证质量 | “四骑士”：slop、疏离、技能退化、团队失和；团队出现“离开 AI 就定位不了问题” | 验证体系要先于“不读代码”；关键模块必须有人真正理解 → [13](13-frontier-radar.md#4-争议与反思) |
| Claude Code vs Codex | 生态与原有工作流是否匹配 | 同一任务的质量、等待、费用与权限是否更合适 | 按同任务质量、等待与费用选择；交叉评审按新增发现评估 → [01](01-agents/README.md) |

## 5. 对个人/团队的建议

1. **先用熟一个能完成目标任务的 Agent**；按 [09](09-review-and-quality.md) 的风险与新增发现决定是否交叉评审。
2. **先建验证闭环**（测试、类型检查、LSP），再谈自主和并行。
3. **只补当前缺口**：共享指令先核实际加载；需要领域配方才试 Skill，需要工具接口才接 MCP；迁移时重核权限和宿主支持。
4. **度量到交付结束**：同时记录正确性、返工、总等待、费用与人工处理；只加流程不改善结果时缩减或撤回。
5. **安全基线**：最小权限、无秘密的受限执行环境；核对实际隔离范围，不能以审批通过或“已开启 sandbox”代替。

> 这些建议背后的“为什么”（验证不对称、上下文预算、人的注意力瓶颈等六条规律）见 [14 深度分析](14-synthesis.md)。
