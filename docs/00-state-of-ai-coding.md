## 30 秒结论

**✅ 把一个可验收的端到端结果交给 Agent，让它连续实现、自验，人按风险接收。** 给清目标、授权、关键契约和运行反馈，完整小应用或一轮产品改进都可以自主执行；体验由真实使用接收，既有产品迁移还要保住旧用户和下游消费者。

| 你现在要决定什么 | 当前默认 | 何时调整 |
|---|---|---|
| 一次交多大的任务 | 交完整、可验收的结果，不按任务体量设自主上限 | 检查不到目标行为、返工不收敛或结果不明时，补反馈、对账并收紧对应范围 |
| 要不要显式拆多个 Agent | 沿用原生按需委派 | 能扩大证据覆盖、减少主上下文或缩短关键路径时，再并行独立支线 |
| 人在哪一步介入 | 处理价值判断、关键契约、风险与真实结果 | 验收规则本身有争议时接管这个判断，解决后恢复自动实现 |

## 1. 当前最高水平：年初与 10 月到底变了什么

**现在应交完整任务，而不是逐步陪写；要补强的是运行反馈和接收能力。** 年初前沿团队就已这样工作，8–10 月的变化主要是完整产品的跨轮改进、按风险接收，以及原生编排的调整。下表比较前沿团队与实践者，不代表行业普及率；目前没有同任务、同预算的统一自主时长增益。

| 维度 | 2026 年初前沿 | 2026 年 8–10 月可核变化 | 现在的选择 |
|---|---|---|---|
| 人的角色 | OpenAI 2-11 已是“Humans steer. Agents execute.”，人构造目标、环境和反馈 | Claude Code 团队 10-15 按变更风险分审批层；Willison 10-20 少读生成代码但大量试玩 | 人集中于价值、关键契约、风险与实际结果，不必逐步陪写或逐行审完所有改动 |
| 自主时长 | OpenAI 2-11 自报单任务常达六小时以上；Cursor 1-14 的周级项目是多 Agent、多循环 | Willison 8-7 报项目用时 52 分钟，另记人工纠错提示，无人介入连续段未知；10-20 报告玩法改进、Three.js 迁移各过夜一轮 | 允许完整可验收轮次自主执行；记录时分清单次 run、无人介入段和项目日历跨度，不能概括为“小时跃升为周” |
| 并行方式 | Cursor 1-14 已有 planner／worker／judge 与数百并发，按角色选模 | Cursor 9-23 撤掉强鼓励探索子 Agent 的提示；Battle Drones 使用 Claude Code Web Ultracode 动态多 Agent | 沿用当前原生编排，显式拆分要有收益依据；固定角色数不是先进程度 |
| 瓶颈位置 | Cursor 1 月已遇协调与漂移；OpenAI 2 月已把可运行环境、UI 与日志反馈放在核心 | Claude Code 10-15 把验证、风险评审、分阶段发布与回滚连起来；Anthropic 10-16 指出人类注意力瓶颈 | 让 Agent 取得实际反馈，人处理决定与结果取舍，单催生成速度解决不了交付瓶颈 |
| 模型与工具 | Cursor 1 月比较 GPT-5.2／GPT-5.1-Codex／Opus 4.5；Anthropic 2-5 用 Opus 4.6 与 Claude Code | 公开实践用 GPT-5.6 Sol Ultra／Codex Desktop（8-7）、GPT-6 Astra High（10-9）、Opus 5.5／Claude Code Web（10-20） | 按 [02](02-models-and-cost.md) 选起点；表中是来源实际使用的代际，不是型号排名，内部模型也不是公开可用默认 |

本仓已比较代际、整轮自主与生产迁移接收，采用上述条件默认，差距记为 1。**当前最高水平整体、跨任务最优与完整投入仍未知**；领先参照是个人完整游戏的跨轮改进、团队按风险自动验收与发布。Battle Drones 仍由作者试玩修订，音频联机导致不适后加警告并改走网络联机，尚不能作为商业游戏发行认证。年初材料只作时间线基线，五页复核与撤回理由见[研究记录](research/2026-10-12-long-task-evidence.md#2026-10-21范式快照与代际复核)。

**依据**：一手团队自报——OpenAI [harness engineering（2-11）](https://openai.com/index/harness-engineering/)、Claude Code 团队 [10-15 评审](https://claude.dev/blog/solving-code-review-at-anthropic/)、Anthropic [10-16 观察研究](https://www.anthropic.com/research/employment-at-anthropic)、[C 编译器（2-5）](https://www.anthropic.com/research/building-c-compiler)、Cursor [1-14](https://cursor.com/blog/scaling-agents)、[9-23 复盘](https://cursor.com/blog/improved-token-efficiency)；社区作者原文——Willison [8-7](https://simonwillison.net/2026/Aug/7/moonlight-mayhem/)、[10-9](https://simonwillison.net/2026/Oct/9/built-using-my-voice/)、[10-20](https://simonwillison.net/2026/Oct/20/battledrones/)；层级差距为本仓原文比较，详见研究记录。核实 2026-10-15（代际复核 2026-10-21）。

### 整轮自主实现，在哪一步接管？

**✅ Agent 负责把实现修好，人确认哪些行为可以改变、哪些差异可以忽略。** 既有产品升级可以连续实现、自验和修复；一旦修绿需要改权限语义或忽略真实内容差异，就先接收契约修改。争议解决后恢复自动推进，接管的是判断，不是剩余全部编码。

近期 VS Code 的 Copilot SDK 升级给出一条具体路径：目标都是保住原审批行为，完成桌面／远端依赖及宿主验证。

| 路径 | 公开结果 | 可以照做的动作 |
|---|---|---|
| 自动升包、自动修复至可审 | preview.1 的自动 PR #341830 遇门禁／权限回放差异，未发布其候选修复 | 保留可恢复候选与失败原因；先判断权限差异，保住门禁 |
| 同目标，针对争议接管 | #341861 同样升级 preview.1；修窄路径归一化，保留正文差异的负例，最终合入 | 人确认可忽略差异，让 Agent 修实现和测试；这里是回放适配，不是放宽产品权限 |
| 下一轮恢复自动推进 | preview.2 的 #341922 再走自动修复与产品构建，之后经人审合入 | 恢复原门禁下的自动推进，以当前版本的接收结果结束 |

**把等价规则和正反样本一起交给接收器。** 文件路径分隔符可以等价，作者正文里的反斜杠或转义内容仍须区分。比较器若放过错身份、漏事件或正文变化，补上应失败的样本、修正比较器，再核最终版本；暂停使用的是这份接收结果，而不是整轮自主目标。旧版通过、PR 合入、终端用户采用要分别记录。

Shopify 的 Shop 原生迁移展示了同一原则的生产采用：运行比较允许时间戳与页面 UUID 自然变化，同时核事件与页面／实体的关系。**保留行为关系，比要求每次输出逐字相同更有用。** 与 SDK 的窄路径修复一样，可忽略差异应在实现、自验前确定，而不是失败后扩大。

**原生反馈够用就沿用；需要跨端状态与事件比较时，再补窄迁移流程。** Shop 使用定制 Pi 流程，由工程师接收需求与计划；旧用户登录、通知和下游事件连续性都在交付目标内。架构或跨端契约变化先接收设计，既定边界内连续执行。Stephen Toub 的 Copilot runtime 迁移也保留了人对设计与验收的持续判断，实际消费方反馈又触发修订。

这些案例支持“扩大自主实现，同时扩大接收能力”。VS Code SDK 链只追到主干合入；Shop 是生产采用，几者是公开路径比较，不是不同模型的随机对照。

**依据**：本仓 P61 条件默认、比较器采用与撤回判断见[最高水平卡与固定产物](research/2026-10-12-long-task-evidence.md#p61整轮交付与争议接管)；一手团队复盘——[Shop 原生迁移](https://shopify.engineering/shop-app-migration)（2026-09-10）、VS Code Copilot SDK 升级及窄路径修复、Stephen Toub 2026-09-16／09-23 复盘，固定来源见同一记录。核实 2026-10-15。

## 2. 九个关键趋势

### 2.1 开放格式：共享内容，分别核对入口 ✅

**先复用已有内容，再核目标客户端的加载与权限。** 开放格式方便共享，迁移时仍须分别验证宿主行为。

| 格式 | 值得复用什么 | 迁移前核对什么 |
|---|---|---|
| **AGENTS.md** | 项目命令、定位与行为约定 | Claude Code 的原生发现可能被项目中的 CLAUDE 文件抑制；Codex 的指令链、预算与刷新方式不同 → [03 加载规则](03-context-engineering.md#21-各工具的加载规则一手) |
| **Agent Skills** (`SKILL.md`) | 领域配方、参考资料与可靠脚本 | 宿主扩展和 `allowed-tools` 的权限语义 → [05](05-skills-and-plugins.md#能加载不等于权限语义可移植) |
| **MCP** | 工具接口契约 | 客户端、SDK、服务端兼容性，以及各自的凭证、隔离与业务结果 → [04](04-mcp.md#1-先决定是否需要新增连接) |

这里的采用判断来自已核官方契约与固定实现，未做跨客户端运行验证；按任务复用，不预装整套连接。

### 2.2 插件化：按新增能力采用 🧪

**资料、CLI 或生成器够用就沿用；缺领域配方试窄 Skill，要共同分发多个组件才装插件。** 安装前看 Skill、MCP、Hook 与脚本的实际内容、加载时执行和权限。比较目标质量、返工、等待与人工处理；新增环节没有改善结果就缩减或撤回。市场规模、官方标签与多市场上架只是来源线索，适合采用的领域反例见 [05](05-skills-and-plugins.md)。

### 2.3 自主性提升：审批与隔离分别判断

**先确认隔离、凭证和网络范围，再决定哪些动作自动审批。** 工具若要求关闭防护或暴露生产凭证，暂停该步骤，换受限环境。

- Claude Code **auto mode** 的分类器仍有误差；[10 §3.1](10-security.md#31-auto-mode-能挡住多少官方公布的数字)保留官方样本、分母与局限，历史测评率不能保证当前任务安全。
- Codex **Auto-review** 选择审批者；长期权限保持原样，单次获批提权仍可能越过原沙箱，Computer Use 的 App 级审批直接交给用户 → [当前契约](01-agents/codex.md#审批沙箱与-auto-review)。
- Claude Code 的 MCP／Hook 在命令沙箱之外。处理外来仓库或带秘密的任务时，检查整个执行环境，详见 [10](10-security.md)。

### 2.4 长时任务与多 Agent

**✅ 沿用原生按需委派，有覆盖或关键路径收益时再显式并行。** 先收敛共享接口、状态和写入面，再拆可独立验收的支线；按可独立交付的工作量及汇总／评审能力调并发。2–3 个或产品线程上限都不是通用最优；worktree 只隔开工作树，服务、数据库和最终产物仍需另行隔离。

**🧪 要共享协调或可重放批处理，才增加 Teams／Workflow。** 启动前确认审批送达、结果收集和恢复时是否重跑写入。权限等待或结果不明时，先核已有动作，再缩回单层委派或串行相关步骤。已有研究既有生成更快的结果，也有质量提高却更贵、更慢的团队配置，所以比较要算到整合验收结束。机制、口径与限制见 [08](08-multi-agent.md)。

### 2.5 上下文：按需取回，保留必要指导

**先补任务缺失的信息，让 Agent 按需检索，同时保留目标、关键约束和完成标准。** 重复预读、无关加载或约束丢失时，再调整提示与上下文组织。Cursor 的删减复盘同时调整系统提示、工具加载与委派，支持有针对性地删减，而不是以“上下文工程”替代有效提示。做法见 [03](03-context-engineering.md)。

### 2.6 官方接口：先核覆盖，再接入

**已有脚本／测试接口够用就沿用；缺编辑器状态或对象操作时，再选官方 Skill、MCP 或引擎插件。** 用官方入口减少自建工作，接入前仍核当前版本、操作覆盖与结果回读。入口见 [04 任务选择](04-mcp.md#3-按任务选择服务与权限)与[游戏引擎接入](../domains/game-dev/01-engine-integration.md)。

### 2.7 不可信输入：可信服务也会返回外部内容

**从日志或 Issue 得到建议命令，另核命令来源与批准范围再执行。** 日志、Issue 和依赖中的指令没有授权效力。Sentry agentjacking 原始研究展示了这条攻击链，尚不能据此认定当前各客户端都已复现或发生同等规模的真实入侵。来源见 [04](04-mcp.md#日志与工单读取可信服务不等于相信内容)，攻击链与环境防线见 [10](10-security.md)。

### 2.8 从会话到常驻：完成与恢复需要证据

**无人值守先接好权限、结果收集和恢复路径。** 长时、后台与托管执行提供更多续接选择；恢复前查清已有动作，避免状态不明时重复写入。接收任务要查到最终业务结果：派发成功或工具任务终态只完成了其中一层。查不到结果就保留未完成状态，详见 [08](08-multi-agent.md)、[04 异步工具](04-mcp.md#异步工具完成的是哪一层)、[20 恢复与对账](20-codex-long-horizon.md#9-超时后动作究竟发生了吗)。

### 2.9 模型分层与“harness engineering”之争

- **按任务缺口选模型。** 推理或验证不足时试更强模型；目标清楚、结果可检查，又需要降低费用或等待的子任务，可试 Haiku 5.5、GPT-6 Luna 等轻量模型。复杂调查按能力选，不因委派而降档。2026-09 出现的**决策模型**（Jev、Clef 等）专做“从有限选项中选一个” → [02](02-models-and-cost.md#21-新类别决策模型2026-09-起)。
- **先保留确定性检查和按风险的人审，再按新增有效发现决定额外评审。** 验证体系是“软件工厂能不能不读代码”争论的关键；现有 benchmark 没覆盖全部训练信号，也未证明长期维护性。缺少长期质量证明仍是未知，不代表模型不可能改善。假设与反证见 [09](09-review-and-quality.md#1-质量数据ai-代码的真实代价)、[14](14-synthesis.md)。

**依据**：2.1 的官方契约与经验见主专题；2.2、2.6–2.8 为一手材料与经验支持的采用判断；2.3 为主专题已核机制，未做本轮运行时安全验证；2.4 的原生委派、Teams／Workflow 依据及研究口径见 08；2.5 为 Cursor [删减复盘](https://cursor.com/blog/improved-token-efficiency)及本仓分析；2.9 为研究支持的模型与评审采用边界。核实 2026-10-08（代际复核 2026-10-21）。

## 3. 可直接采用的起点

**先用熟一个能完成目标任务的 Agent，接通验证闭环；再按具体缺口补能力。** 以下是对个人和团队都适用的跨代保留建议，按当前问题取用。

| 当前问题 | 直接做什么 | 从哪里继续 |
|---|---|---|
| 怎样开始完整交付 | 给目标、授权、兼容要求和可执行验证（测试／构建／类型检查／LSP／截图）；未决问题先调查与规划，明确后连续实现、自验 | 本页 Shop 运行反馈与整轮接收；[07 规划分流](07-workflows.md#2-标准节奏探索--计划--实现--提交-) |
| Agent 卡住或反复纠正 | 分辨信息缺失、工具失败还是思路错误；同任务保留有效结论，确需换题或舍弃路径才重开 | [03 会话管理](03-context-engineering.md#3-会话层面的上下文管理)，不按纠正次数自动清空 |
| 是否再加一个 reviewer | 高影响或有明确漏审风险时独立检查；是否继续加审看新增有效发现和核查负担 | [09 评审](09-review-and-quality.md#2-评审手段) |
| 指令、Skill、MCP 应该配多少 | 指令保留定位、必要命令与行为边界，先核实际加载；缺领域配方再试 Skill，缺工具接口再接 MCP。安装前读内容，迁移时重核宿主与权限 | [03 指令文件](03-context-engineering.md#2-指令文件claudemd--agentsmd--规则文件)、[04](04-mcp.md)、[05](05-skills-and-plugins.md)；不以行数或是否人工编写判断质量 |
| 哪些规则交给 Hook | 用 Hook 检查可机械判断的规则，覆盖事件、失败与替代路径；硬权限由运行时限制 | [06 防护](06-hooks-and-guardrails.md)、[10 安全](10-security.md) |
| 怎样知道新增流程值不值 | 同时记录正确性、返工、总等待、费用与人工处理，统计到交付结束；没有改善就缩减或撤回 | [11 生产力证据](11-community-pulse.md#4-生产力证据来源范围见各行) |
| 自主执行前怎样配权限 | 最小权限、无秘密的受限环境，核实际隔离范围；审批、指令、Hook 和 sandbox 标签都不能代替运行时边界 | [10 安全](10-security.md) |

**依据**：Shop 一手复盘与本仓整轮接收比较；规划、会话、评审、上下文和 Hook 的研究及经验见对应专题；安装前审查依据为官方安全指引与供应链事件（一手／二手）。核实 2026-10-08（代际复核 2026-10-21）。这些建议背后的验证不对称、上下文预算、人类注意力等六条规律，见 [14 深度分析](14-synthesis.md)。

## 4. 争议（看清再选）

**按任务和可核结果选方案，不必先站队。**

| 争议 | 一方 | 另一方 | 本仓库判断 |
|---|---|---|---|
| MCP vs CLI | MCP 有类型契约、可隔离凭证、便于团队发现工具 | CLI 可组合（管道/jq）；成本取决于实际调用路径 | 已有授权 shell 时先用原生 CLI，按具体缺口补资料、短契约或 Skill；MCP 用于凭证隔离、受限执行或现有工具无法满足的访问需求 → [04](04-mcp.md)、[05](05-skills-and-plugins.md) |
| Spec 驱动开发 (SDD) | 先写规格再实现，减少返工 | “瀑布回归”：Spec Kit 给一个日期显示功能生成 1300 行 Markdown | 先固定会改变架构、安全或交付的不可猜契约；可观察的偏好用小样与反馈澄清，避免按功能大小套完整规格流程 → [07](07-workflows.md#5-spec-驱动开发sdd) |
| 多 Agent 并行 | 产能倍增 | 冲突、评审瓶颈、成本倍增 | 按依赖、共享状态与评审能力调并发；算到整合验收结束 → [08](08-multi-agent.md) |
| AI 到底提效多少 | METR 2026 问卷：技术人员自报价值提升 1.4–2 倍；实践者说“2 倍，不是 10 倍” | METR 2025 RCT：资深开发者慢 19%，却自认为快 20%；2026 后续实验有提速点估计，但选择偏差与计时问题使幅度不可靠，正在调整设计（2026-10-15 补核） | 收益高度依赖使用方式；要自己度量 → [11](11-community-pulse.md#4-生产力证据来源范围见各行) |
| 能不能不读代码（“软件工厂”） | StrongDM：代码不由人写、也不由人审，靠验证体系保证质量 | “四骑士”：slop、疏离、技能退化、团队失和；团队出现“离开 AI 就定位不了问题” | 验证体系要先于“不读代码”；关键模块必须有人真正理解 → [13](13-frontier-radar.md#4-争议与反思) |
| Claude Code vs Codex | 生态与原有工作流是否匹配 | 同一任务的质量、等待、费用与权限是否更合适 | 按同任务质量、等待与费用选择；交叉评审按新增发现评估 → [01](01-agents/README.md) |

**依据**：METR [2026 后续实验](https://metr.org/blog/2026-02-24-uplift-update/)（2026-10-15 补核）；其余争议与采用边界见对应专题。核实 2026-10-15。
