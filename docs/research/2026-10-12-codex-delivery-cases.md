### 本轮实际运行：修复前后、三种模式

操作是打开 `index.html?selfcheck`，需要静态模式时点击 `.motion`，滚到页尾，再真实点击 `.restart__btn`。读取滚动位置与 fragment 只用于观察，没有通过脚本改状态来代替按钮/链接行为。动画场景等待进入顶部 200 像素以内即记录，未等待精确停在零点。

| 场景 | 旧版点击前 → 点击后 scrollY | 新版点击前 → 点击后 scrollY | 观察 |
|---|---|---|---|

| 开启动画 | 18155 → 192 | 18155 → 141 | 两者均进入顶部范围；数值是动画途中的采样，不能比较速度 |
| 点击关闭动画 | 12554 → 0 | 12554 → 0 | 两者均回到开头 |

六个场景的断言均达到各自预期，无捕获到的页面脚本异常。四个启用 JS 的场景都输出 `selfcheck ok: 12 calcule verificate`；禁用 JS 时不会运行 JS 自检。**[经验：本轮功能复测，非模型运行]**

独立读完整 `main.js` 可知这 12 项检查只覆盖 `getScrollProgress` 的边界和计算，不检查重启、浏览器历史或阅读位置。因此旧版有导航缺陷而自检通过并不矛盾，也不是自检没有价值：它回答了另一个问题。

### 对实际 AI Coding 的意义

这个修复的价值不在新增 Skill 或更严格的规划，而在把“无 JS 时也能读完整文章”这一产品承诺落实为对应交互。原生锚点减少了手写控制代码，也让基础行为在脚本不可用时仍成立。可借鉴的是先问现成平台能力能否直接表达目标，再决定是否自建状态和控制逻辑。不能外推为每个 Web 应用必须支持无 JS，或原生实现永远优于自定义。**[研究：从补丁形成的条件建议]**

公开回复还提出模式切换后的阅读位置与罗马数字导航是否易懂。第一位回复者自述试用了桌面 Chrome；另一位明确自称由人运营的 founder agent，并附带产品邀请。两者都是外部反馈线索，但不是两份独立的人类可用性实验；本轮未重现其位置漂移。产品使用反馈应追来源与条件，不能只计算赞同数量。**[社区：原帖回复；研究：证据区分]**

## 3. KPI 项目：更多代码不等于有人能够接管软件

[peteshop01-boop 的 #52835](https://github.com/openai/codex/discussions/52835) 于 2026-10-10 描述：自己是慈善机构运营经理，有技术项目管理经历但不是软件开发者；为约 25 名员工开发 KPI 系统三四个月，已有代码、自动测试、文档与多种构建，却没有可靠的端到端应用。他还不确定 GitHub 与本地文件是否持续保持一个权威版本。**[社区：当事人自述，未独立诊断]**

目标不只是录入表格，还包括经理审批、季度进展、组织目标关联、评级、看板、权限、审计、桌面/移动使用；约束包括复用 Microsoft 365 许可、低持续成本、员工信息保护，以及非技术人员可运营且不依赖全职开发者。列出的工具跨 Power Platform、SharePoint、自定义 Web、Workers、Node 和 MCP。

工具多可能是复杂性的信号，但仅凭列表不能判定架构错误；也不知道是否都是生产依赖。没有源码、部署记录、具体失败请求或许可细节，不能建议“改用某个平台”“全部重写”，更不能估计合格开发者几天能完成。

### 这改变了研究范围：把“是否值得自建、谁来维护”纳入主线

如果只问怎样让 Codex 更好地写代码，会遗漏该用户最重要的约束：交付后谁能确认版本、恢复数据、调整业务规则、处理权限问题？这是软件所有权与运行职责，不能靠更多自动测试或一份 AGENTS 自动产生。非开发者也能拥有这些能力，但需要可操作的交接方式和明确的维护安排，而不是要求他成为全职程序员。**[研究：基于需求的分析]**

合理的恢复顺序是先确认一个可追踪版本，并选用虚构数据走“员工建立 KPI → 提交 → 经理批准 → 更新进展 → 看板读取保存结果”的最小业务闭环；在第一个失败点取得预期、实际、版本与相关错误。公开回复也建议了类似路径，但未见作者回报执行结果，所以这仍是诊断建议，不是已成功救回项目的方法。**[社区：回复；经验：条件建议]**

据此再比较：现有配置产品能覆盖多少需求、低代码定制是否适配实际约束、现有自定义实现值得保留哪些部分、谁承担长期运营。AI 可以协助比较与迁移，但代码生成便宜并不意味着软件的持续责任免费。需要衡量被保留的功能及维护负担，而非只计算生成速度。没有当前许可和业务验证，就不列虚构的成本表。

## 5. 本轮方向变化与下一问题

BAML 案例让研究聚焦“哪项事实改变了实现决策”；当前两个案例又补上两层：**产品承诺决定应测的运行状态；维护安排决定生成出的软件是否真的适合使用者。** 它们同属 AI Coding 核心，不是额外的软件工程百科，因为会直接改变给 Agent 的任务、采用的实现方式及是否继续扩写。

一个成功小修复和一个尚未交付的自述不能用于比较作者或模型水平，任务复杂度完全不同。它们的价值在于暴露不同限制。后续应追 KPI 作者是否给出具体失败与修复，或寻找当前 Codex 项目的第二次真实需求；网页案例尚未提供长期维护收益、模型型号和完整运行成本。不要为维持“前沿”标签把旧案例的年份改掉，也不要因为新帖子提到 Codex 就称为 Astra 实验。
