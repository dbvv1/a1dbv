## 四条长期任务：以真实开发结果组织研究

用户已要求持续扩展 AI Coding 的核心认识。本节将既有 R 项组织成四条长期任务，不另外复制一套任务编号；跨端认领仍在 [TASKS](../collaboration/TASKS.md)。以下优先级和假设是 **[研究：本仓库判断，2026-10-13]**，并非已有普遍效果结论。

### 一、AI 怎样帮助发现值得做的软件（R07／R09／R14）

**本轮结果（2026-10-13）**：[跨时区试用反馈](2026-10-13-product-feedback-contract.md#reset-alerts反馈与作者修改报告)补上具体使用情境如何改变需求，15 加入让试用者解释核心结果的建议。只有作者报告已修改，没有公开补丁或修改后复测；下一步选能看到第二次使用的不同案例，不把此例当模型生产力证明。

**核心问题**：生成变便宜后，是更快得到有用的产品，还是更快堆出没人需要的功能？人的试用、Agent 的方案探索、现成产品替代、自建工具应怎样组合？这条任务覆盖个人工具、业务应用、界面和游戏，不以“提示几次就做出来”作为成功定义。

**进一步结果**：[CodexIsland](2026-10-13-product-feedback-contract.md#codexisland方案补丁与回滚)已有独立原需求、作者报告的第二轮视觉反馈、可见补丁和回滚；15/24 加入复用与信息编码取舍。仍不当作发布后独立复测；下一候选优先已使用修改版的不同用户反馈。

**实际复测增量（2026-10-13）**：[Handy](2026-10-13-handy-retest-adoption.md)取得两位非作者构建使用报告，其中一位锁定提交、输出设备与播放器并重复录音周期；18 建议先确定交互适用场景和持续支持责任，再决定主线采用。该功能仍未合并，Windows 多源修补尚无实机完成证据；不把局部好用推成跨平台就绪。

**发布后理解反馈（2026-10-13，UTC+8）**：[CodexBar](2026-10-13-product-feedback-contract.md#codexbar发布后的理解反馈)在已包含颜色选项的 0.72.0 收到另一用户的符号误读报告，后续改为保留旧默认的可选符号惯例；15 融入修改版仍需核对理解、比较具体含义再判重复的建议。未证该用户开启颜色或采取错误行动，最终符号版也无用户复测；下一候选优先不同产品的行为结果、删除功能或采用现成工具，不继续堆相似信息编码案例。

**优先追的决策**：第一次可运行后，使用者为什么改变需求、保留哪条路径、删掉哪项功能；第二次使用是否真的更顺。创造能力包括发现新方案和有理由地放弃，不只包括生成更多代码。不能用维护缺陷案例替代这一证据。

**自建/复用取舍增量（2026-10-13）**：[Jules](2026-10-13-product-feedback-contract.md#jules从自建常驻服务到现成运行能力)补作者删除常驻基础设施、采用现成云能力的固定产物与迁移成本报告。15 改为同任务比较必要能力与运行责任；Telegram 路径可用性有取舍，未证明独立复测或总成本下降。下一步仍优先真实后续使用/接管结果，不把删除文件当收益。

**下一调查**：从 Codex 的 [Show and tell](https://github.com/openai/codex/discussions/categories/show-and-tell) 与具体开源项目的 feature request／关闭 PR 找有使用者反馈的连续案例；追到原需求、实际产物和对应修改。现有 KPI 自述缺源码，Ra & Apep 复测只证明导航行为，两者都不能充当已证明的产品收益。游戏优先选择一次玩法或交互调整，区分程序正确、玩家理解和操作感受；不先扩展引擎工具大全。这些是后续检索入口，尚未全读。

**一阶段交付**：一条能解释需求为什么改变的案例，修改 15/18/24 或相应游戏页的具体建议。若只有作者宣传、没有可见反馈，记录缺口并换候选；不无限追踪同一名人。若实际使用表明现成工具更合算，也可以形成“不应继续自建”的结论。

### 二、强 Agent 还缺什么，额外能力怎样才值得（R15／R01／R05／R08／R02）

**窄配方增量（2026-10-13）**：[原生文件对象](2026-10-13-domain-skill-contract.md#6-原生文件对象创建配方与静态汇总的区别)核对同一预装库环境与 Skill 创建配方，并实际运行静态汇总/原生对象往返探测。05 改为先找已验证生成器或模板，再补缺失知识，不按重复次数机械加 Skill；未测 Excel 操作或当前模型净收益，不继续扩展合成对象用例。

**研究证据修正（2026-10-13）**：[Context Files 全文与公开数据](2026-10-13-context-study-reassessment.md#context-files失败解释与分析参数)收窄 03 的无收益概括，E5 补上作者实际 error 过滤；独立只读复算说明功效参数截断和 #907 失败归因边界。未运行新模型，不把已公开题当盲测。

**本轮结果（2026-10-13）**：[Cloudflare 窄领域契约](2026-10-13-domain-skill-contract.md)追到官方 Skill、休眠迁移修复和 10 项表达式探测；05 建议改为先核对真实回调输入及状态寿命，已有实现可用则不重复加 Skill。下一项需不同的真实任务，不能用已公开修复充当强模型盲测。

**效率证据补充（2026-10-13）**：[AGENTS 效率研究附录](2026-10-13-context-study-reassessment.md#agents-效率耗时与正确性的边界)复算 113 对有效运行，保留两组中位数变化但撤回“完成相当”可能暗示的正确性等价；部分 CLI 版本不配对、total 含额外 cached 相加，不能承诺同等质量或美元收益。

**核心问题**：Codex／Claude 已能自主做的事，哪些应交还原生能力；哪些需要领域知识、运行工具、反馈或工作顺序约束？模型／effort、Skill、搜索／LSP、浏览器与本地工具都按它们改变的决策评估，不按品牌划分阵营。

**需要区分的解释**：Skill 补了新事实；让 Agent 获得新操作；强制多花时间；改变了人的输入。若收益只是多投入，短提示或原生预算可能是更简单的替代；若工具让以前不可观察的状态可见，删除流程未必能替代它。比较总等待与人的主动投入，不能用 token 或文件长度单独代表净成本。

**下一调查**：沿现有官方 skill-creator、Matt Pocock、Superpowers 的具体入口，找一个“知识确实影响实现选择”的任务；核对模型本来是否能从仓库得到该知识，以及是否存在更窄的补充方式。先做固定内容／调用链与案例核查；模型对照需要可用环境和相应授权，不把它设为所有研究的前置条件。已经公开答案的 alchemy 例子不能再作为盲测原题。

**一阶段交付**：给 Codex 使用者一项可采用、缩减或删除的改变，说明触发条件、成本与撤回条件；Claude 只补会改变选择的差异。若没有可见使用结果，只发表机制判断。若新模型已低成本完成相同任务，允许撤回原 Skill 推荐，而非给它寻找新的强制理由。

### 三、怎样让第二次、第五次修改仍然可靠（R06／R03／R04）

**后续需求增量（2026-10-13）**：[Discourse](2026-10-12-development-conditions.md#discourse共享组件承接后续需求)连接带 AI 共同署名的初始实现、已有组件复用与另一贡献者四个月后的客户插件扩展。15 §3 补“语义相同先复用，有真实需求再加窄接口”；固定 PR 合并检查通过不代表客户插件已部署，恢复故障反例说明 UI 复用也须核对后台生命周期。下一步优先具体运行反馈或接管投入，不继续枚举 nested 缺陷。

**核心问题**：连续需求中失败来自初始遗漏、后续退化、目标变化、信息丢失，还是环境／判定器？架构边界、回归测试、恢复记录和审阅各自能解决哪一项？不预先认定“重写便宜”或“必须先设计完整架构”。

**当前证据**：alchemy 的批次语义与 VibeTunnel 的所有权链已有限定结果；[本轮 SlopCodeBench 调查](2026-10-13-slopcodebench.md)进一步确认 Regression 分类不代表以前通过、默认隐藏评估没有自动反馈，并局部复现题库夹具限制。它改变失败分类方法，尚不能量化模型维护能力。

**下一调查**：优先取得同项目／同 campaign 的固定前后产物、规格与逐测试记录，区分曾通过后失败和一直失败；同时检查需求是否有意改变。SlopCodeBench 缺原始 campaign 时转向有完整 issue→patch→后续变更的公开项目，不反复整理分数。抽象是否有价值，应由下一需求修改了哪些层、有没有减少重复决定来判断，而非只数行数或函数复杂度。

**一阶段交付**：一个可以定位原因的演化案例，更新 20/22/24 的采用判断。若拿不到历史行为，不把“当前测试失败”写成“维护造成退化”；若实际修复无需额外记忆或架构改造，也记录这个反例。运行环境和无关脚本没有变化时，不反复全量验收来代替研究。

### 四、怎样把生成结果交给真实使用者与下一位维护者（R07／R15，结合 R10／R11）

**接收渠道增量（2026-10-13）**：[Godot 一手政策与关闭案例](2026-10-13-godot-contribution-policy.md)纠正二手概括：披露、人审与少量改动不自动获得准入，Asset Store 与项目贡献不同。18、14 和游戏分支同步，不扩大为所有游戏开发限制。

**接管后修改增量（2026-10-13）**：[oMLX](2026-10-13-omlx-postmerge.md)追到维护者合并后补真实 tool 前驱探针、能力缓存键和回归覆盖；22 建议区分合法降级与用户性能目标。后来的严格模板报告没有恢复闭环，不把关闭 issue 或测试通过当作全部配置已恢复。

**独立运行后的选题收窄（2026-10-13）**：[云端审计](../collaboration/reviews/2026-10-13-b9fddfb.md)在两版原函数上运行相同 22 个测试方法，并经共有接口确认不支持模板的渲染失败变成合法降级；追加输入仍可改变旧文本前缀。机制已取得局部运行支持，下一阶段优先不同使用者在指定版本、原触发条件下的复测，或接收者第二次修改的实际投入。继续增加这两个版本的合成用例，不能回答是否恢复用户目标或减少人的工作。

**本轮结果（2026-10-13）**：[Immich 接管链](2026-10-13-immich-handover.md)追到两轮接收意见、对应补丁、批准与最终合并，18/24 建议让交接说明跟随最终接口。仍缺接管者后续修改与真实设备复测；继续追不同项目的合并后行为，不把日历等待计为审查工时。

**核心问题**：从能跑的代码到可持续使用的软件，还缺哪些工作，谁承担？观察部署一致性、数据与权限、升级／恢复、支持负担、代码理解和接管；小团队与非开发者可能需要不同方案。开源／本地模型只在实际成本、隐私或运行约束会改变选择时深入。

**不能混合的结果**：模型等待、人的审查／理解、上线后的支持、外部服务费用。五小时内产出很多修改，不一定改善其中任何一项；但某次长跑也可能完成原来做不起的任务。比较需要同样的交付目标，不能拿简单原型与完整产品相除。

**下一调查**：从已公开的交付困难、维护者接收 PR、版本回退和运行故障中找一个“下一位人如何接管”的链条。优先读接收方的具体问题与修改，不把一条反 AI 声明当成本统计。现有 KPI 案例仅是线索；官方部署文档可确认操作要求，不能代替实际接管结果。没有用户支持／时间记录时保持未知，不自行联系作者或要求公开私有日志。

**一阶段交付**：按具体项目给出补运行入口、补行为解释、缩小范围或采用现成方案的建议，并说明 Agent 可以自主完成的部分。验证的是接收方能否完成下一次变更／恢复，而非新增多少 README。若实际维护负担很低，也应保留，避免只采样事故。

### 怎样让长期任务持续产生价值

每轮选一个尚未回答、会改变推荐的问题深入；审计仅在新提交、新证据或高影响疑点出现时启动。先复用现有来源，再补不同作者、接收方、失败或中文实践；相同实验的文章、视频和仓库不算三份独立证据。社区和官方的原文都需要核查，第三方批评也一样。

每阶段留下“现在建议什么、依据、仍缺什么、下一步怎样区分解释”。阶段可以明确完成；长期任务在模型／工具能力变化、真实反例或使用条件变化时重新打开。没有新证据时允许降级候选、删除旧建议或转移研究，不以反复写方向文件保持忙碌。这份队列不创建调度、不授权付费实验，也不表示另一 dot 已接手。
