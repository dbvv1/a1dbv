## 四条长期任务：以真实开发结果组织研究

用户已要求持续扩展 AI Coding 的核心认识。本节将既有 R 项组织成四条长期任务，不另外复制一套任务编号；跨端认领仍在 [TASKS](../collaboration/TASKS.md)。以下优先级和假设是 **[研究：本仓库判断，2026-10-13]**，并非已有普遍效果结论。

### 全仓深化：可靠完成以后，怎样把结果做得更好

**[研究：2026-10-15，方向补充；不改写方向锚点]** 基于 `525f24344d216caea636e26ff3119ca94adf1d0f` 抽查主干与游戏建议。必须先更新判断：dot 后续已补镜头、动作连续性、声音、运动画面、首发反馈、菜单与重试体验，不能再说这些模块只有最低交付线；主干也已有短契约／完整 Skill、工具成本、原型复访与连续需求的比较。接下来的高价值缺口是 **功能已经正确时，Agent 怎样发现、选择并实现更好的方案**。这是对当前选题分布的分析，不是全仓事实重验或对既有成果的否定。

| 主线 | 保留已有长处 | 持续深化的具体选择 |
|---|---|---|
| 1 发现值得做的软件 | 从真实需求和再次使用修正原型 | 同样满足需求的两种交互／实现，哪种更易理解、更有用、更值得保留；Agent 怎样提出有意义的替代方案 |
| 2 额外能力何时值得加 | 原生起步，避免默认叠工具和流程 | 已能完成时，领域知识、反馈或算法能否提高结果上限；补的是知识、操作、观察能力还是单纯更多等待 |
| 3 连续修改可靠 | 明确身份、状态寿命和回归来源 | 修改之后保住响应、表现和性能目标；不能只保住“功能还在”和测试数量 |
| 4 交给使用者和维护者 | 重建、升级、恢复与接管 | 实际设备、数据量与使用路径下是否仍好用，下一位维护者能否继续改进；不把本机截图或构建成功当最终体验 |

**深度的落点是可采用的选择。** 对要深化的具体问题，追到“为什么有效”的机制，比较有竞争力的现成方案，给出约束下的选择及代价。例如，缓存是否改善真实等待而非只提高命中率；更多平滑是否改善视觉却损害操控；领域 Skill 是否提出了更好的方案而非仅增加检查。无需给每个小任务加研究仪式，也不能把“交给人判断”作为停止分析设计与体验的理由：Agent 可以形成可比较方案、解释取舍并实现，人决定目的与偏好。**[研究]**

**前沿不能用发布日期、品牌覆盖或引用数量代替。** 新方法应与仍有竞争力的旧方法比较；近期版本变化只有改变能力或取舍才值得进入建议。源码能支持机制判断，不能单独证明使用者收益；用户反馈能说明感受，不能单独解释技术因果。优先把两者连起来，不只采样事故，也找“已经可用，改后明显更好”的公开前后产物。单纯补型号、许可与摘要只能完成覆盖和可读性，不能据此宣告质量研究已经收尾。**[研究]**

本次只补下列两个候选，位于主线一、二；主线三、四继续承接已有迭代与交付研究。镜头、Motion Matching、时域渲染已在本轮新提交深化，不重复列为新任务。先追公开实现和可见结果，不以新模型／引擎实验作为理论调查的默认前提。候选可以因证据不足而撤回，不另建研究文件或任务编号。

### 一、AI 怎样帮助发现值得做的软件（R07／R09／R14）

**本轮已完成窄比较（2026-10-15）：同样能用的原型，怎样变成更值得使用的产品？**

- **整体评审后的收窄（基于 `795ec5b`）**：优先追“同屏比较与分步引导”的真实取舍：两个方案都能完成查看结果与后续操作，选择是否取决于横向比较、步骤依赖或首次理解？先沿既有 Home Assistant 改版再使用证据找原任务与替代路径，再从公开产品变更／使用者反馈补竞争方案；既有撤回案例只证明某条路径有价值，不直接证明另一设计普遍较差。预期改变15／23：将功能和回归作为底线，另说明目标体验改善、牺牲的能力及撤回条件。没有新选择证据就不再追加相似误解案例。本轮已用 [Metabase 2019 前后产物与同一使用者回执](2026-10-13-product-feedback-contract.md#metabase同屏条件与分步预览的竞争取舍)补竞争证据并修订 15；不启动新实验。后续只追同任务连续操作与实际质量差异，不再收集相似布局赞美。

- **与已完成内容的区别**：15 §10 已覆盖理解、原路径保留、再次使用和去留；本题不再收集一种相似误解或修复，而追“两个方案都正确时，为何选择其中一个，以及修改后是否值得保留”。**[研究]**
- **要回答的问题**：选择一个已有真实内容的任务界面，例如“查看结果并决定下一步”，比较信息层级、默认操作与反馈方式不同的两种方案。Agent 如何把“更高级／更好看”变成可讨论的选择？视觉辨识度、理解成本、键盘可用性和操作效率冲突时怎样取舍？研究成功使用与主动改进，避免继续只收集缺陷修复。
- **已读一手来源**：[Anthropic frontend-design 的固定指令](https://github.com/anthropics/skills/blob/dbd4588f9e1033efb41dad4bef2f7947c8993d44/skills/frontend-design/SKILL.md)要求从主题、受众与主要任务形成设计方向，比较布局，再把视觉结构用于表达信息；同时区分回答用户操作的动效与无目的装饰。官方仓库所核 HEAD 提交日为 2026-10-09；这是公开设计配方，未取得它提高实际使用效果或已发布产品采用的证明。其“独特性”目标也不天然适合高密度后台或既有设计系统，不直接整套照搬。**[一手：指令；研究：适用边界]**
- **下一手来源与证据缺口**：从 [Codex Show and tell](https://github.com/openai/codex/discussions/categories/show-and-tell) 追一个不同于既有 CodexBar／CodexIsland 的产品，核对原任务、固定前后产物、设计决策和修改版使用者反馈；也可以来自 Claude Code 实践，但须有可见变更。官方 Skill 是方案线索，不是案例效果证据；宣传截图和作者自赞不能补齐再次使用。
- **预期改变的建议**：[15 新功能与原型](../15-task-playbooks.md)、[23 浏览器验证](../23-browser-verification.md)补出“功能通过后选择性改进体验”的具体打法：先比较会改变行为的方案，再实现有理由的一种；截图检查布局，连续操作检查理解与反馈。不能把所有任务强制变成多方案设计，也不能以审美评分替代完成用户目标。第一轮理论交付只需一个可追溯选择及其改进／退步依据，落回现有产品反馈记录。

**候选，未认领（2026-10-13，云端补充）：原型之后，何时停止自建？** **[研究：d3db2c3 时点的选题建议，未认领；后续增量见本主线下文]**

- **要回答的问题**：已有可用原型、却缺权限管理／部署／维护人手时，继续让 Agent 扩写、缩成插件或脚本、采用已有产品，哪一种保住了真正需要的使用路径？现有材料有理解反馈与未交付自述，缺少实际转向后的行为结果。
- **可能的一手来源**：[Codex #52835](https://github.com/openai/codex/discussions/52835) 的后续及 [Show and tell](https://github.com/openai/codex/discussions/categories/show-and-tell) 中公开迁移／停止自建的记录；沿当事人链接查原需求、删除／替换补丁、所选产品的权限和导出文档，以及接收使用者的后续反馈。官方功能说明只证明可选能力，不能代替已完成替换的证据。
- **预期改变的建议**：[15 §10](../15-task-playbooks.md#10-原型和一次性脚本) 的“先做可体验产物、再补交付约束”，补出继续开发／缩小范围／采用现成方案的具体分界。至少需要同一组必要需求、实际替代动作和后续使用结果；只有作者说“应该换平台”时不改推荐，也不新增单项目记录。

**本轮结果（2026-10-13）**：[跨时区试用反馈](2026-10-13-product-feedback-contract.md#reset-alerts反馈与作者修改报告)补上具体使用情境如何改变需求，15 加入让试用者解释核心结果的建议。只有作者报告已修改，没有公开补丁或修改后复测；下一步选能看到第二次使用的不同案例，不把此例当模型生产力证明。

**核心问题**：生成变便宜后，是更快得到有用的产品，还是更快堆出没人需要的功能？人的试用、Agent 的方案探索、现成产品替代、自建工具应怎样组合？这条任务覆盖个人工具、业务应用、界面和游戏，不以“提示几次就做出来”作为成功定义。

**进一步结果**：[CodexIsland](2026-10-13-product-feedback-contract.md#codexisland方案补丁与回滚)已有独立原需求、作者报告的第二轮视觉反馈、可见补丁和回滚；15/24 加入复用与信息编码取舍。仍不当作发布后独立复测；下一候选优先已使用修改版的不同用户反馈。

**实际复测增量（2026-10-13）**：[Handy](2026-10-13-handy-retest-adoption.md)取得两位非作者构建使用报告，其中一位锁定提交、输出设备与播放器并重复录音周期；18 建议先确定交互适用场景和持续支持责任，再决定主线采用。该功能仍未合并，Windows 多源修补尚无实机完成证据；不把局部好用推成跨平台就绪。

**发布后理解反馈（2026-10-13，UTC+8）**：[CodexBar](2026-10-13-product-feedback-contract.md#codexbar发布后的理解反馈)在已包含颜色选项的 0.72.0 收到另一用户的符号误读报告，后续改为保留旧默认的可选符号惯例；15 融入修改版仍需核对理解、比较具体含义再判重复的建议。未证该用户开启颜色或采取错误行动，最终符号版也无用户复测；下一候选优先不同产品的行为结果、删除功能或采用现成工具，不继续堆相似信息编码案例。

**优先追的决策**：第一次可运行后，使用者为什么改变需求、保留哪条路径、删掉哪项功能；第二次使用是否真的更顺。创造能力包括发现新方案和有理由地放弃，不只包括生成更多代码。不能用维护缺陷案例替代这一证据。

**自建/复用取舍增量（2026-10-13）**：[Jules](2026-10-13-product-feedback-contract.md#jules从自建常驻服务到现成运行能力)补作者删除常驻基础设施、采用现成云能力的固定产物与迁移成本报告。15 改为同任务比较必要能力与运行责任；Telegram 路径可用性有取舍，未证明独立复测或总成本下降。下一步仍优先真实后续使用/接管结果，不把删除文件当收益。

**下一调查**：从 Codex 的 [Show and tell](https://github.com/openai/codex/discussions/categories/show-and-tell) 与具体开源项目的 feature request／关闭 PR 找有使用者反馈的连续案例；追到原需求、实际产物和对应修改。现有 KPI 自述缺源码，Ra & Apep 复测只证明导航行为，两者都不能充当已证明的产品收益。游戏优先选择一次玩法或交互调整，区分程序正确、玩家理解和操作感受；不先扩展引擎工具大全。这些是后续检索入口，尚未全读。

**一阶段交付**：一条能解释需求为什么改变的案例，修改 15/18/24 或相应游戏页的具体建议。若只有作者宣传、没有可见反馈，记录缺口并换候选；不无限追踪同一名人。若实际使用表明现成工具更合算，也可以形成“不应继续自建”的结论。

### 二、强 Agent 还缺什么，额外能力怎样才值得（R15／R01／R05／R08／R02）

### 三、怎样让第二次、第五次修改仍然可靠（R06／R03／R04）

**学习检验增量（2026-10-13）**：[陌生库与手动修改实验](2026-10-13-immich-handover.md#补充证据陌生模块学习与下一次修改)使 18 §8 改为学习场景可选的相关小变更检验；测验分数与实际编辑分别处理，不把事后高分方式当成因果干预。尚未证明这项练习改善职业维护能力；仅在取得职业开发者后续实际修改、投入及明确帮助条件的新证据时复访，不重复拼接两项实验。

**后续需求增量（2026-10-13）**：[Discourse](2026-10-12-development-conditions.md#discourse共享组件承接后续需求)连接带 AI 共同署名的初始实现、已有组件复用与另一贡献者四个月后的客户插件扩展。15 §3 补“语义相同先复用，有真实需求再加窄接口”；固定 PR 合并检查通过不代表客户插件已部署，恢复故障反例说明 UI 复用也须核对后台生命周期。下一步优先具体运行反馈或接管投入，不继续枚举 nested 缺陷。

**核心问题**：连续需求中失败来自初始遗漏、后续退化、目标变化、信息丢失，还是环境／判定器？架构边界、回归测试、恢复记录和审阅各自能解决哪一项？不预先认定“重写便宜”或“必须先设计完整架构”。

**当前证据**：alchemy 的批次语义与 VibeTunnel 的所有权链已有限定结果；[本轮 SlopCodeBench 调查](2026-10-13-slopcodebench.md)进一步确认 Regression 分类不代表以前通过、默认隐藏评估没有自动反馈，并局部复现题库夹具限制。它改变失败分类方法，尚不能量化模型维护能力。

**下一调查**：优先取得同项目／同 campaign 的固定前后产物、规格与逐测试记录，区分曾通过后失败和一直失败；同时检查需求是否有意改变。SlopCodeBench 缺原始 campaign 时转向有完整 issue→patch→后续变更的公开项目，不反复整理分数。抽象是否有价值，应由下一需求修改了哪些层、有没有减少重复决定来判断，而非只数行数或函数复杂度。

**一阶段交付**：一个可以定位原因的演化案例，更新 20/22/24 的采用判断。若拿不到历史行为，不把“当前测试失败”写成“维护造成退化”；若实际修复无需额外记忆或架构改造，也记录这个反例。运行环境和无关脚本没有变化时，不反复全量验收来代替研究。

### 四、怎样把生成结果交给真实使用者与下一位维护者（R07／R15，结合 R10／R11）

**候选，未认领（2026-10-13，云端补充；优先）：接收者第一次重建环境或恢复服务，需要什么最小交付？** **[研究：d3db2c3 时点的选题建议，未认领；后续增量见本主线下文]**

- **要回答的问题**：AI 辅助补丁合并后，另一位维护者能否在自己的环境完成首次构建、升级或故障恢复；阻塞来自没交付的依赖／状态、行为解释，还是补丁本身？现有接收链能确认审查和代码变化，几乎没有接收者实际操作负担的证据。
- **可能的一手来源**：[VibeTunnel #611](https://github.com/amantus-ai/vibetunnel/pull/611) 的构建前提与 [#709](https://github.com/amantus-ai/vibetunnel/pull/709) 后续接收问题，或 [Immich #26070](https://github.com/immich-app/immich/pull/26070) 关联的发布后反馈；只在新材料能串起接收者的失败命令／环境、对应修订和成功重试时接续。版本和现象须对应，关闭 issue、合并或不同人的另一故障不能补齐链条。
- **预期改变的建议**：[18 §7](../18-team-adoption.md#7-评审与协作规范) 的交接说明及 [15 §5](../15-task-playbooks.md#5-大规模迁移与升级) 的迁移验收：按真实阻塞选择可运行入口、状态恢复操作或关键行为解释，已有自动化足够时删去重复交接步骤。有明确操作记录才谈人工负担；日历等待不当工时。现有项目无新接收证据就换来源，追加到相应主线的现有记录。

**直接接管测量（2026-10-13）**：[Echoes of AI](2026-10-13-immich-handover.md#补充证据接管后实际修改的受控实验)补另一开发者实际增加功能的受控证据，18 §6 改为在交接试点观察真实小变更的正确性与投入。未显著差异不等于维护等价；2024年底工具、小任务和完成者选择限制外推，不能补称 Immich/oMLX 已有实际成本结果。

**接收渠道增量（2026-10-13）**：[Godot 一手政策与关闭案例](2026-10-13-godot-contribution-policy.md)纠正二手概括：披露、人审与少量改动不自动获得准入，Asset Store 与项目贡献不同。18、14 和游戏分支同步，不扩大为所有游戏开发限制。

**接管后修改增量（2026-10-13）**：[oMLX](2026-10-13-omlx-postmerge.md)追到维护者合并后补真实 tool 前驱探针、能力缓存键和回归覆盖；22 建议区分合法降级与用户性能目标。后来的严格模板报告没有恢复闭环，不把关闭 issue 或测试通过当作全部配置已恢复。

**独立运行后的选题收窄（2026-10-13）**：[云端审计](../collaboration/reviews/2026-10-13-b9fddfb.md)在两版原函数上运行相同 22 个测试方法，并经共有接口确认不支持模板的渲染失败变成合法降级；追加输入仍可改变旧文本前缀。机制已取得局部运行支持，下一阶段优先不同使用者在指定版本、原触发条件下的复测，或接收者第二次修改的实际投入。继续增加这两个版本的合成用例，不能回答是否恢复用户目标或减少人的工作。

**本轮结果（2026-10-13）**：[Immich 接管链](2026-10-13-immich-handover.md)追到两轮接收意见、对应补丁、批准与最终合并，18/24 建议让交接说明跟随最终接口。仍缺接管者后续修改与真实设备复测；继续追不同项目的合并后行为，不把日历等待计为审查工时。

**核心问题**：从能跑的代码到可持续使用的软件，还缺哪些工作，谁承担？观察部署一致性、数据与权限、升级／恢复、支持负担、代码理解和接管；小团队与非开发者可能需要不同方案。开源／本地模型只在实际成本、隐私或运行约束会改变选择时深入。

**不能混合的结果**：模型等待、人的审查／理解、上线后的支持、外部服务费用。五小时内产出很多修改，不一定改善其中任何一项；但某次长跑也可能完成原来做不起的任务。比较需要同样的交付目标，不能拿简单原型与完整产品相除。

**下一调查**：从已公开的交付困难、维护者接收 PR、版本回退和运行故障中找一个“下一位人如何接管”的链条。优先读接收方的具体问题与修改，不把一条反 AI 声明当成本统计。现有 KPI 案例仅是线索；官方部署文档可确认操作要求，不能代替实际接管结果。没有用户支持／时间记录时保持未知，不自行联系作者或要求公开私有日志。

**一阶段交付**：按具体项目给出补运行入口、补行为解释、缩小范围或采用现成方案的建议，并说明 Agent 可以自主完成的部分。验证的是接收方能否完成下一次变更／恢复，而非新增多少 README。若实际维护负担很低，也应保留，避免只采样事故。

### 怎样让长期任务持续产生价值

每轮选一个尚未回答、会改变推荐的问题深入；审计仅在新提交、新证据或高影响疑点出现时启动。先复用现有来源，再补不同作者、接收方、失败或中文实践；相同实验的文章、视频和仓库不算三份独立证据。社区和官方的原文都需要核查，第三方批评也一样。

每阶段留下“现在建议什么、依据、仍缺什么、下一步怎样区分解释”。阶段可以明确完成；长期任务在模型／工具能力变化、真实反例或使用条件变化时重新打开。没有新证据时允许降级候选、删除旧建议或转移研究，不以反复写方向文件保持忙碌。这份队列不创建调度、不授权付费实验，也不表示另一 dot 已接手。

### G1：资产供给与零手修边界

以下保留来源摸底候选；当前工作包状态以[TASKS](../collaboration/TASKS.md)为准，不重复认领。每类先回答一个会改变制作方式的问题，不能扩成安装教程或资源名单。预期建议的落点以现有[生成式 AI 页](../../domains/game-dev/03-generative-ai-in-games.md) §1、§3 和[验证页](../../domains/game-dev/02-verification-and-playtesting.md)为主。

#### 2D：能否交付同一套可替换资产，而非若干好看的图片？

已由[WP2理论结论](2026-10-14-game-wp2-2d-assets.md)接续：更新近期模型/许可、三档首试与动画反证；原始Qwen摸底仍作历史起点。真实引擎与第二次修改试验后置，不把理论交付写成实验通过。

- **要回答的问题（主线 2／3）**：概念图、UI、图标、静态精灵与逐帧精灵各自能否零手修达到实际显示尺寸下的可读性、透明边缘、锚点和成套一致性？概念图只约束方向，不能计入游戏资产合格率；UI 文字与交互布局优先由引擎绘制，避免把文字烘焙进图后难以修改和本地化。
- **一手来源／优先对象**：👀 [Qwen-Image](https://github.com/QwenLM/Qwen-Image/tree/6b5e1f5cec987d404be5ac6657db3b9aacb56a89)（最后提交 2026-02-10，代码 Apache-2.0），核对已公布的 Image-2512、Edit-2511、Layered 路径及多图编辑；不把 README 中的 2.0 发布消息直接当作已核实开放权重。真实游戏采用未核实；多图编辑能力也不证明连续动画帧稳定。
- **单人最可能卡住的地方 [研究]**：第二次换衣服、换方向或缩小到实际像素尺寸时，轮廓、视角和视觉编码改变。脚本能裁切、量化色板、打图集、检验透明区和锚点，不能保证恢复语义正确的手部、遮挡与连续姿态；反复重生成的筛选时间必须计入成本。
- **预期改变的建议（2026-10-14 校准）**：`8714a62` 已将 §1.2 的统一成熟判断收窄为静态与动画分别验收，不再把这条文字修订作为待办。下一步确定静态资源第二次修改的可用条件：哪些旧资源需重做、哪些只需改导入设置，是否真的降低总投入；若动画仍需手修，只能据实际样本推荐固定视角、纸片或刚体动画，不能继续以“换提示词”掩盖缺口。

#### 3D：静态道具能否经自动处理成为有预算的游戏资产？

- **要回答的问题（主线 2／4）**：同一生成结果在目标视距下，经过减面、UV／材质整理、碰撞代理和 LOD 后是否仍可用？先研究静态道具，再讨论需要变形的角色；两个问题不能合并计算成功率。
- **一手来源／优先对象**：👀 [TRELLIS.2](https://github.com/microsoft/TRELLIS.2/tree/75fbf0183001ed9876c8dbb35de6b68552ee08bd)（2026-06-05，MIT）；⛔ [Hunyuan3D-2.1](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/tree/82920d643c0dc2f7bfd7255f45f62d386edfe60c)（2025-10-17，社区许可证，不能归为无地域限制的开源替代）。两者真实游戏生产采用均未核实；后者的公开 Unity 集成不能证明已发行使用。
- **会改变选择的实据**：TRELLIS.2 的 [example.py](https://github.com/microsoft/TRELLIS.2/blob/75fbf0183001ed9876c8dbb35de6b68552ee08bd/example.py) 导出示例仍设百万级目标面数和 4096 贴图；README 明写 GLB 默认 OPAQUE，纹理保留 alpha 却未启用透明。导出成功因此不是游戏预算或透明效果通过。材质连接可尝试脚本修正，不能把这一局部修正推广成拓扑、背面和轮廓都可自动修好。作者要求至少 24GB NVIDIA 显存，是接入前提，不是本仓库实测。Hunyuan 的 [LICENSE](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/82920d643c0dc2f7bfd7255f45f62d386edfe60c/LICENSE) §5(c) 将地域限制延伸到 Output，全球发行不能只看“可商用”摘要。
- **预期改变的建议（2026-10-14 校准）**：§1 已由 `11c6e0a`／`4c2c408` 区分规格设置、有损处理和缺陷来源；下一项应取得处理前后产物及引擎结果，判断哪类资产值得修、值得重新生成或直接复用，不能只继续解析同一最终文件。若自动减面损坏轮廓或角色变形仍需人工修权重，收窄到静态／刚体对象，或借用已授权现成网格，不推荐先搭完整角色生成流水线。

#### PBR：可复现材质是否比图片生成更适合批量生产？

- **要回答的问题（主线 2／3）**：同一材质族改变颜色、尺度和磨损后，平铺接缝、法线方向、roughness／smoothness、通道打包及不同光照下的观感能否一致？“有几张贴图”不等于它们描述同一表面。
- **一手来源／优先对象**：👀 [Material Maker](https://github.com/RodZill4/material-maker/tree/174f15edece663bf10f78588840873fa2fd17bc7)（2026-10-07，MIT，程序化节点工具而非生成模型）；👀 [TRELLIS.2 texturing 示例](https://github.com/microsoft/TRELLIS.2/blob/75fbf0183001ed9876c8dbb35de6b68552ee08bd/example_texturing.py)（状态同上）。两者真实游戏采用本轮未核实。
- **会改变选择的实据／瓶颈**：Material Maker 的 [parse_args.gd](https://github.com/RodZill4/material-maker/blob/174f15edece663bf10f78588840873fa2fd17bc7/parse_args.gd) 有批量导出、尺寸和目标 profile，但找不到指定 profile 时会按名称相似度回退；自动化必须核对实际采用的 profile，不能只看退出成功。程序可转换通道和色彩空间，不能凭格式转换补出一致的物理材质含义；也未验证其 CLI 在目标机器无显示环境下可运行。
- **当前建议与剩余问题**：WP5已在[材质专题](../../domains/game-dev/assets/materials.md)采用共同参数图/现成材质优先，并补1.7固定源码的尺寸参数接线错误及独立CLI故障边界；上方为此前摸底快照。下一步仅在获准实验中核同题重新打光、二次修改及输出失败行为，不重复工具名单。

#### 绑定与动画：自动绑定和动作生成之间还缺多少人工？

- **要回答的问题（主线 2／3）**：自动骨架／蒙皮、文本动作、视频动捕输出能否通过统一骨架、接触约束和转场测试？必须分别检查关节位置、权重变形、脚底滑动、root motion、动作首尾和武器挂点，不能拿骨架可视化代表游戏动画可用。
- **一手来源／优先对象**：👀 [SkinTokens](https://github.com/VAST-AI-Research/SkinTokens/tree/273b691d35989d71cd17ff2895fdc735097b92d1)（2026-05-12，代码 MIT；上游 UniRig 指向的后续工作），[demo.py](https://github.com/VAST-AI-Research/SkinTokens/blob/273b691d35989d71cd17ff2895fdc735097b92d1/demo.py) 提供批量输入、已有骨架和后处理选项；⛔ [HY-Motion-1.0](https://github.com/Tencent-Hunyuan/HY-Motion-1.0/tree/4e426f5a1021cbcf7f375458c37b840ee7225229)（2026-07-18，文本动作，社区许可证同样限制地域及 Output）；⛔ [GVHMR](https://github.com/zju3dv/GVHMR/tree/ee960bb6e2ea2d381aa97f08e9b71ef320b624b1)（2026-09-15，视频恢复动作，[许可](https://github.com/zju3dv/GVHMR/blob/ee960bb6e2ea2d381aa97f08e9b71ef320b624b1/LICENSE) 限教育、研究和非营利用途）。三个项目均未核实真实游戏采用；前者代码许可不能代替具体权重及输入角色素材授权核查。
- **单人瓶颈 [研究]**：重定向能统一命名和骨架映射，不保证消除穿插与不合理受力；需要手工刷权重、逐帧修关键帧才通过的样本应记为本基准失败。可程序修正的误差与需要重新设计角色／动作的误差分开。
- **预期改变的建议**：§1 将“可导出动作”与“可发布角色动画”分离。对全球商用项目先排除许可不满足者；若仍需手修，优先现成授权动作、刚体分件或程序化运动，不强迫每款游戏承担生成式角色动画成本。

#### 特效：能否复用原生效果与运行时，而非先生成视频？

- **要回答的问题（主线 2／4）**：程序修改现成效果参数是否足以满足命中提示、危险范围和技能辨识？透明叠加、粒子数量、寿命、池化重置与目标渲染管线能否在实际战斗密度下通过？
- **一手来源／优先对象**：👀 [Effekseer](https://github.com/effekseer/Effekseer/tree/82b37081a302b9f9eff0bf14dc6c845fca8c3c54)（2026-09-14，MIT 及第三方许可）与同一生态的 [Unity 集成](https://github.com/effekseer/EffekseerForUnity/tree/ae9bd12596edb12013c98cafc06c71ccf195cc49)（2026-10-06）；这是可复用效果工具和运行时，不是 AI 模型。主仓库说明 master 为开发版本，不宜直接当生产稳定版。
- **采用证据边界**：维护者的[采用页源码](https://github.com/effekseer/effekseer.github.io/blob/c7cf8c7849c9536dda46f8493eb5c7b457cc896c/en/adoption.html) 列有 Rime Berta、Craft Warriors 等真实游戏，但本轮未取得对应游戏代码、制作者技术复盘或版本证据，故只记为采用线索；页面视频不参与质量结论。Unity 插件源码能证明有集成路径，不能证明零美术制作成本。
- **预期改变的建议**：§1 优先验证可借用、可脚本调整且许可清晰的效果资源；Agent 是否能可靠修改原生效果仍待测。若生成 flipbook，额外检查透明边缘、循环接缝和显存，不能因画面精彩就跳过运行预算。

#### 音效：哪些需求根本不需要扩散模型？

- **要回答的问题（主线 2／4）**：拾取、点击、受击等短提示能否用参数化合成满足辨识与反馈？环境声、写实 Foley 再单独研究；不能将电子音适用性扩成全部音效质量。
- **一手来源／优先对象**：👀 [jsfxr](https://github.com/chr15m/jsfxr/tree/b7b6aa27d62f8f356db267276bf54b451555c49d)（2026-05-05，Unlicense），公开参数、预设、采样与 WAV 导出接口；⛔ [TangoFlux](https://github.com/declare-lab/TangoFlux/tree/164420faa2b3f8a28bb013ccde7006422a616fc7)（2026-01-28），[许可说明](https://github.com/declare-lab/TangoFlux/blob/164420faa2b3f8a28bb013ccde7006422a616fc7/LICENSE.md) 明确非商业研究用途，且有底层数据条件，不能把注册一个上游商业许可写成已清除所有限制。两者具体真实游戏采用未核实。
- **单人瓶颈／预期改变的建议 [研究]**：先验证起音延迟、尾音截断、响度、重复疲劳和同时触发的混音，再比较生成质量；这些能部分通过程序测量，却仍需要听觉判断。§1 对风格化短音效优先试可复现的合成配方，生成模型只补确实缺少的声音；全球商用默认不采用许可未满足的模型。

#### 音乐与配音：能否交付可迭代的声音结构，而非一段试听？

- **要回答的问题（主线 3／4）**：音乐能否循环、按游戏状态切换且保持节拍和音量；配音能否在改一句文本后保持角色身份、读音和字幕时序？两个资源类型分别验收，不能用“听感好”共同通过。
- **音乐一手对象**：👀 [ACE-Step 1.5](https://github.com/ace-step/ACE-Step-1.5/tree/ca1e85fe9430179831e6bc6be790c332190a3866)（2026-08-29，MIT）。公开生成、重绘等入口；README 对速度和质量的宣传不是本轮测量，也未证明游戏中连续切换、分轨相位一致和无缝循环。真实游戏采用未核实。
- **配音一手对象**：👀 [Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS/tree/022e286b98fbec7e1e916cb940cdf532cd9f488e)（2026-03-17，代码 Apache-2.0），核对具体 checkpoint 与使用声音的授权；有声音克隆能力不等于有权使用某人的声音。真实游戏采用未核实。
- **单人瓶颈／预期改变的建议 [研究]**：裁切、淡入淡出、响度处理和批量导入可由程序完成，发音正确、音乐转场自然与角色表演仍需人选择或重生成。§1 将“离线预生成片段”作为首个候选，不因有模型就引入运行时推理；需要手工改音符、重录或逐段精修才合格的情况应记为当前基准不通过。

#### 视频与过场：生成视频值得进入这款游戏吗？

- **要回答的问题（主线 1／2／4）**：是否真的需要预渲染视频，而非引擎内镜头、静态图移动或直接删除过场？生成片段能否满足同一角色连续性、重剪、字幕本地化、跳过及跳过后的游戏状态恢复？
- **一手来源／优先对象**：👀 [Wan2.2](https://github.com/Wan-Video/Wan2.2/tree/1ea34ff48f87168174e12956e200b1d908b1c5ff)（2026-09-21，Apache-2.0）；👀 [LTX-2 仓库当前 2.5 路径](https://github.com/Lightricks/LTX-2/tree/be6d6d0a69d11a0a399c462ed92606692e5f8697)（2026-10-13，社区许可证；[LICENSE-2_x](https://github.com/Lightricks/LTX-2/blob/be6d6d0a69d11a0a399c462ed92606692e5f8697/LICENSE-2_x) 有营收门槛等条件，不能称为无条件开源）。两者未核实真实游戏采用；模型样片不证明可按游戏内容版本稳定重制。
- **当前建议与剩余问题 [研究]**：WP7已在[视频专题](../../domains/game-dev/assets/video.md)落地条件三档与成本反例；前一条Wan/LTX为此前摸底，上方现行记录补Omni、Veo与Aleph。视频一旦烘焙，改角色外观、剧情或镜头可能重做整段。§1 优先验证剧情收益是否覆盖生成、筛选、编码、下载体积与版本修改成本；短镜头生成效果不能推导成可用的交互关卡。

#### 跨资源：风格、成套一致性与“优先借力”如何一起决定范围？

- **候选，未认领；主线 1／2／3**。**要回答的问题**：固定玩法、视角和目标设备后，许可清晰的现成资源、程序化资源、生成资源三条路线各需多少主动工时和返工？不要求每类资产都使用生成模型；现成方案满足任务时就停止自建。库存、重生成成本和下一版改动比单次生成速度更可能改变选择。
- **一手来源**：👀 [ComfyUI](https://github.com/Comfy-Org/ComfyUI/tree/8010b48d2c1be986613f8e8c761527d205bd756f)（2026-10-13，GPL-3.0）及同一生态的[官方工作流模板](https://github.com/Comfy-Org/workflow_templates/tree/e28fce217e4fd410b7e782ba55e15df1c6d1f2a6)（2026-10-13）可作为编排入口；还须固定实际 workflow、节点、权重和版本，不能把安装 ComfyUI 本身当成生产管线。真实游戏端到端采用未核实；工作流文件可保存也不保证所有运行环境位级复现。
- **风格判断 [研究，待实测]**：优先试固定视角、有限配色、扁平图形／纸片和可程序变形的刚体对象，因为需要维持的视角、光照与形变关系较少；这只是降低约束的推理，不是模型质量结论。像素风须再分静态小图与逐帧动画，低多边形须再分刚体场景与变形角色；量化色板、减面并不能自动修复错误轮廓、透视或关节。写实静态背景可能单张容易，却增加角色融合和光照一致性要求。风格应按玩法取舍，不能为了减少资产难度牺牲交互可读性。
- **预期改变的建议／有效证据**：§1 的流水线应先有资产规格与失败去向，再决定工具。先用一个小批次完整保留合格、淘汰、重生成样本，记录从规格到引擎最终资源的总投入，再扩到几百个资产；不得只展示最好的一组。第二轮只改一个实际需求，观察哪些资源必须重做，并检查自动导入是否误改 GUID、pivot、碰撞体或已调好的引用。授权与平台问卷在选型时查：旧轮未能读取 Steam 官方问卷；现已由 [WP1](2026-10-14-game-wp1-licensing.md#发布渠道不能被生成许可替代)补核官方 Content Survey，沿当前政策区分玩家消费内容与开发效率工具。

**这会怎样改变第一轮，而不扩大成新平台 [研究：调查设计]**：

1. **先固定一个真实辨识需求，再选路线。** 例如外观相似的两个道具必须使玩家做出不同选择。固定实际显示尺寸、玩法用途、目标设备、视角及允许的程序操作；若现成授权资源已经满足，先检验它能否承接新增需求，不能预设生成更先进或必须生成。没有合适 Unity 工程或可用模型时，先报告具体前提，不从零造研究平台。
2. **把第二次修改拆成可判断的结果。** 保留第一版全部已接入资产；新增或改动所需资源后，分别记录生成结果是否合格、程序处理是否损坏它、引擎是否正确呈现。检查没有要求修改的旧资源、Sprite 对象对应关系、pivot／切片及使用它们的场景／Prefab 是否保持所需行为。有意重切片导致身份变化时可以迁移引用，验收的是引用正确而非所有标识永远不变。
3. **按实际错误选择观察工具。** 字体／图片源文件已经错误，就不先加 MCP；源文件正确但引擎显示错误，就优先读取导入设置与运行结果。已有编辑器脚本足以观察时不增插件；Agent 看不到决定性状态才评估接口或窄参考。这使 Codex／Claude 的研究落在“补了什么才改变结果”，而不是只比较美术模型。
4. **成本和质量分别回答。** 对整组预定资产记录通过、淘汰、重生成及处理方法，保留第二版引起的旧资源重做范围；区分程序员主动投入、模型等待与费用。打包后让人根据画面完成预定选择，分别报告选择错误与操作问题；Agent 自己生成描述再自己打分不能证明玩家辨识。没有同等需求与验收的复用基线时，只报告绝对投入，不宣称节省成本。

**什么结果会改变下一步 [研究：采用与停止条件]**：若现成资源已经满足，不继续生成；若单张合格但成套身份漂移，下一轮研究受约束编辑或缩小风格／玩法；若源图正确而重导入破坏引用，转到 G2 的导入与状态维护；若前后两版都可用，再扩大资产数量或考察动画，不能提前推成几百个资产稳定生产。修图、补帧、刷权重等人工美术操作才能通过的样本，在当前基准下判失败；人的视觉选择与试玩判定仍须记录，不能计作零人工。

**预期改变的建议**：进一步细化生成式 AI 页 §1 的“静态资产条件化采用”和程序化导入边界：何时直接复用，何时保留生成路径，何时只修程序，何时放弃当前风格。结果优先追加已有相关研究；仅在确有新结果时调整本候选，不为维持长期任务而不断新增相似条目。候选登记不自动授权安装、大模型下载或付费实验。
