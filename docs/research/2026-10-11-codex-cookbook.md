两份计划示例不构成同一上下文里的自相矛盾：一份优先持续执行，一份优先人类阶段控制。问题出在把它们一起塞进全局配置，既要求不要停，又要求每阶段批准。选择时应先决定哪些决策由人控制、哪些工作已授权 Agent 自主推进；别让文件名和模板替代这一决定。**[研究：独立分析]**

ExecPlan 中的“一份文件完全自足”也有维护成本。需要跨团队交接时有价值；同一仓库的日常小修改可以引用稳定资料，不必不断复制全部背景。原文允许按需增删章节，不应把它变成任何任务的固定长文要求。**[一手；研究：采用判断]**

## 2. Goals：官方设计与实际使用报告一起看

教程把 Goal 描述为线程范围的持久状态，而非全局记忆或项目指令。它说明只有在线程空闲、没有待处理输入等条件下才续接；Plan-only 不触发续接，中断会暂停，无工具调用的续接会抑制下一次自动继续以避免空转。预算耗尽不同于完成目标。这些是教程描述，本轮未启动 Goals 来验证各客户端。**[一手：教程设计说明]**

对“需要不断说继续”的体验，它提供了原生能力方向，但不能据此承诺修好一切。此前已读取的用户报告还涉及目标已知却停工、压缩后回旧任务；相关持久化 PR 也只修复特定路径。设计意图、实现覆盖、实际行为应分开，见 [续接核对](2026-10-10-codex-continuity.md)。**[社区/一手；研究：分析]**

对本仓库：长期方向和研究队列已经保存在 Git 工作区；用户本地会话负责唤醒。读取 Goals 教程不等于在本会话启用 Goal，也没有创建新的调度任务。每次推进仍应落实到新证据、纠错、可复核判断与实际仓库修改。**[经验：本任务安排]**

## 3. 迭代修复教程的通过曲线包含人为阶段条件

[Build iterative repair loops with Codex](https://github.com/openai/openai-cookbook/blob/5bd6cb40b6b84b69b2032d810610aa85064102df/examples/codex/Build_iterative_repair_loops_with_Codex.ipynb) 展示 review → repair → validate，保存每轮记录，将运行失败和 judge 反馈交回修复。这个结构可以借鉴，但案例使用三个特意安排深度的 notebook。源码的 `staged_delta()` 读取 metadata 的 `target_iteration`；轮数不到时，即使执行和评审已通过，`evaluate_notebook()` 仍把结果设为未通过。三个 fixture 的 target 分别为 1、2、3。**[一手：代码及 fixture metadata]**

本轮抽取这两个函数，替换执行和 judge 为始终通过的模拟结果，设置 target=3；得到三轮通过状态 **`false, false, true`**。没有运行安装单元、模型调用或真实 notebook 修复。它验证的是教程门槛逻辑，不是 Codex 的行为。**[研究：离线逻辑检查]**

因此，示例中的一、二、三轮逐步清零不能当作独立观测到的模型收敛曲线。教程公开说明 staged 意图，不应指责其隐瞒；需要避免的是读者把教学节奏当成性能证据。拿到实际项目时，应删掉教学轮数条件，凭真实失败继续，不因“设计了三轮”强制重复。**[研究：独立分析]**

另一个落差是：正文建议生产循环考虑“剩余问题不变”和“需要人判断”等停止条件，示例 `repair_until_done(max_iterations=3)` 实际只检查全部通过或次数耗尽。不能把建议列表误认为示例已实现全部判断。版本也应区分：示例安装固定 CLI 0.130.0、默认 repair model 为 GPT-5.4-mini；不据此推断当前 Astra 的最佳参数。**[一手：代码；研究：采用判断]**

## 4. 当前取舍

✅ 采用目标可核对、变更有证据、失败影响下一动作，以及可恢复的状态记录。对复杂实施或研究，允许计划随新发现调整，而不是机械忠于旧步骤。

🧪 在真实存在“单次修复留下可定位错误”时使用迭代修复，确保验证者检查的是用户关心的行为。没有新失败时不继续无变化重复验证。

⛔ 不全局复制人类阶段审批模板，不为追求多小时运行而夸大任务，不从 staged demo 推断强模型必须多轮，也不因官方示例出现多个文件就给每个项目添同样的目录树。

以上为本仓库采用判断，不是官方统一推荐，也不是新模型对照结果。**[研究]**

## 5. 插件评估：真实环境更有意义，但评分器仍要核查

同一固定提交中的合作示例 [harness_aware_plugin_evals](https://github.com/openai/openai-cookbook/tree/5bd6cb40b6b84b69b2032d810610aa85064102df/examples/partners/harness_aware_plugin_evals) 比较三层：直接调用 resolver、独立工具循环、实际 Codex SDK + 已安装插件。离线 fixture 提供少量硬编码 BLS 序列，不是实际联网统计数据库；示例把指令从独立循环移到 MCP server instructions 后，保存的 Codex 轨迹评分改善。**[一手：合作示例 README、配置、grader 与保存轨迹]**

值得借鉴的是发现测试环境遗漏：独立循环有“不能凭记忆编造 series ID、候选并列应问用户”的指令，Codex 初始没有相同指令。工具代码相同不意味着模型收到的信息相同。插件是否真正安装在本次运行环境、描述/服务器说明是否进入上下文，应当被纳入验证。**[研究：采用判断]**

本轮直接调用共享 grader 重评已提交的 15 条记录，未启动 MCP server、未安装插件、未运行 promptfoo 或模型调用：独立循环 **5/5**，原 Codex **3/5**，增加 instructions 后 **5/5**。只是重评保存数据，不是独立复现行为收益，也不是统计显著的成功率提升。**[研究：离线复算]**

源码 `eval_grading.py::grade` 用工具名集合、请求/返回的 series ID、完成标志及非空答案判分。它没有检查答案数值、调用次序，也没有要求返回序列内部的观测数组非空。对该函数直接构造了三个小反例：

| 输入改动 | 本轮实际判分 | 覆盖缺口 |
|---|---|---|
| 工具值为 4.1，最终回答改成 99.9 | 通过 | 非空答案不等于正确答案 |
| 将 fetch 放在 resolve 前 | 通过 | 使用过两个工具不等于遵循顺序约束 |
| 返回正确 series ID、无 error，但内部 data 数组为空 | 通过 | 返回序列记录不等于获得观测值 |

**[研究：直接执行评分函数，无模型调用]**

这不是说保存的 15 条轨迹都犯了这些错；反例说明当前评分器无法检出它们。`assert_codex_result.py` 确实会拒绝显式失败的 MCP 调用，所以也不能把它描述为只要调用过工具就一律通过。**[一手；研究：边界]**

✅ 在实际 Codex 环境评估插件，并分别检查安装/发现、调用参数与次序、返回数据、最终用户结果。若业务要求“先 resolve 再 fetch”，就检查轨迹先后与候选绑定；若要求回答数值，就把时间、单位、数值和依据纳入验收。不要因为额外使用了一个成熟 eval 工具，就假定这些检查已经存在。**[研究：采用判断]**
