> 核实方法：直接读取官方 GitHub 仓库中的文件；固定提交便于复查。没有调用付费模型做对照实验，没有运行真实浏览器应用或游戏引擎测试。

## 1. 整体判断与本轮改进

现有结构已覆盖选型、上下文、工具、工作流、评审、安全和游戏开发。主要缺口在于：读者看完知道“应该评估、应该验证”，但缺少完整的判定、恢复和证据保存方法。

| 问题 | 本轮处理 | 仍有边界 |
|---|---|---|
| 新功能清单多，如何判断是否有用不够明确 | 新增 [22 评估 Agent](../22-agent-evaluation.md)，说明对照、失败分类和必要记录 | 未声称这些方法已带来生产力收益 |
| 长任务偏重提示、压缩与交接，副作用恢复不足 | 新增 [20 可靠的长任务](../20-codex-long-horizon.md) | 显式状态与恢复机制为工程建议，不是已交付的编排系统 |
| 前端验证散落在工具介绍中 | 新增 [23 浏览器验证](../23-browser-verification.md) | 真实项目仍需跑浏览器验收 |
| “schema 防幻觉”“Hook 必定执行”“迁移零成本”等表述过强 | 修正为有条件的能力与责任边界 | 其余历史结论仍需逐项复核 |
| 历史实验缺少随仓库提供的原始产物 | 明示待复核，不把历史自述称为本轮复现 | 未找到原始轨迹，不能重建或补造 |
| 更新日期和证据类型不足以表示核实范围 | 增加验证状态与固定来源，更新入口和维护约定 | 历史引用未全部转换 |

### S4 · Codex app-server

## 3. 历史实验的证据缺口

当前 [19 实测记录](../19-experiments.md) 有方法、汇总表和复现说明，但未随仓库提供逐次 JSONL、运行脚本、配置快照、差异产物与测试报告。因此保留历史报告，同时标为**历史自述，原始产物待补齐**。

另外，缓存读取 token 数不等于工具定义 token 数。要得出“其中约 26k 来自工具定义”，需要可核对的上下文分项或控制其他变量的对照；缓存计数本身不能完成这种归因。跨条件开销差异也不能自动证明唯一原因是工具定义。

本轮没有判定历史数据造假，也没有把它当作已独立复现。后续优先补原始记录，或按 [22](../22-agent-evaluation.md) 重新设计并执行实验。
