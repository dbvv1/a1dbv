# Codex 正向案例：Catalog Compare 的可复核部分

> 核实时间：2026-10-10。评级：✅ 借鉴明确业务语义、可移植验收和分层证据；👀 不据此认定模型整体性能或商业价值。

当前结论：先固定业务语义和独立预期，再把验收绑定具体产物；不默认增加独立 Agent。[研究]

关键边界：旧浏览器回执的 HTML hash 与检出不同；导出命名仍有理解反馈。局部全绿不能证明当前 UI、商业价值或模型整体效果。[研究：证据边界]

## 为什么追这个案例

[Codex Discussion #51359](https://github.com/openai/codex/discussions/51359) 的发布者明确自称获授权的 Codex 助手，介绍用 CSV 对比商品目录的工具。它提供源码、合成输入、预期矩阵、运行脚本和结果，比只有演示截图的分享更便于核查。作者声称一个独立 Agent 先写 fixture 再看实现，并在验证中发现未匹配行校验与上传状态问题；本轮没有完整开发轨迹，不能独立证明这段开发顺序或缺陷修复因果。**[社区：原帖；研究：证据选择]**

固定源码：[Flickinny11/catalog-compare，c5e645fefff8b80a4634777c91776fe9ca3ed187](https://github.com/Flickinny11/catalog-compare/tree/c5e645fefff8b80a4634777c91776fe9ca3ed187)。本轮没有访问其商业服务、联系作者或改动上游。**[一手：源码]**

## 实际运行结果

读取源码与脚本后，在临时检出执行，无需依赖安装或模型调用：

```sh
node tests/acceptance/run-core.mjs dist/core.mjs RESULTS_DIRECTORY
python3 tests/acceptance/verify-exports.py RESULTS_DIRECTORY
```

核心检查 **95 通过、0 失败**；导出检查 **11 通过、0 失败**。本轮核心文件 SHA-256 为 `b4020657d8a1e7cc7b894d234c6416eb7674331eb921b991177da0b9b75d3cab`，与原项目记录一致。**[研究：本轮离线实跑]**

这不是 106 个不同用户任务成功，也不是 Codex 重新开发一次的成功率。前者涵盖解析、业务分类、边界与格式，后者对 11 份导出用 Python 标准 CSV 解析器检查行数、列宽、声明和指定公式样式文本。其行数依据部分来自同一实现导出的 JSON，不是所有导出字段都有独立业务预期。**[一手：测试源码；研究：解释]**

## 没有停在“全绿”：额外检查了什么

原核心 runner 用 `Number(actual.delta) == Number(expected.delta)` 比较差值，对精确十进制产品来说不能覆盖小于二进制浮点分辨率的错误。数字字段还采用“输出字段存在才比较”的条件。这些是测试覆盖边界，不能直接认定当前产品已经计算错误。未匹配行本来不承诺与已匹配行相同的归一化字段；核对时要按接口分支判断。**[一手：run-core.mjs；研究：分析]**

本仓库补充了一个范围明确的[独立核对脚本](../../scripts/research/verify-catalog-compare.py)：用 Python `csv` 读取原始合成 CSV，再用 1,000 位精度的 `Decimal` 核对已匹配行的归一化值、差额与 changed/unchanged 分类，并比对 authored expectation 中这些行的数字字段。**41 个已匹配行、102 个预期数字字段均通过**。它不验证重复匹配策略、整个 CSV parser 或 UI。**[研究：本轮执行]**

从本知识库根目录运行：

```sh
python3 scripts/research/verify-catalog-compare.py CHECKOUT_DIRECTORY RESULTS_DIRECTORY
```

另在生成报告的副本中，将一个正确差值 `+1` 改为 `1.00000000000000001`：JavaScript `Number` 比较会把两者视作相等，补充脚本拒绝了该结果。这是生成报告层的定向反例，不是声称上游整个测试套件在突变后的产品源码上仍通过。**[研究：定向验证]**

## 浏览器证据不能自动沿用到所有新版本

项目的浏览器记录将实际选择文件、筛选、窄屏模拟与报告回退列为通过，同时把原生下载完成列为未确认。五项 UI 状态测试只提供历史 receipt，当前无依赖命令不重跑它们。我们本轮没有进行浏览器测试。**[一手：README、tests/acceptance/README.md、docs/browser-verification.json]**

本轮把浏览器记录中的四个文件 hash 与固定检出比较：`styles.css`、`core.mjs`、`app.mjs` 相同，**`index.html` 不同**。这不证明新页面有错，但意味着那份旧记录不足以覆盖当前页面全部内容。后续应检查页面差异对应的行为，而不是继续把旧的“已验证”贴到新版本。**[研究：本轮 hash 核对]**

## 人类反馈补充了测试没回答的问题

原帖的一位回复者实际试了合成示例，指出界面写 Catalog only / Supplier only，CSV 状态却写 removed / added；说明文字虽强调不是删除/新增指令，孤立读取状态列仍可能产生误解。我们已在源码与导出中确认这组命名存在，但没有独立用户研究证明其实际误用率。该回复者也是其他两条已收录讨论的参与者，不能把多次回复算成多份独立使用者样本。**[社区：原帖回复；一手：代码/导出；研究：边界]**

这说明通过可执行测试后，仍有“用户怎样理解产物”的问题。特别是 AI coding 工具把内部状态直接暴露给产品用户时，程序正确与表达准确不是同一个验收对象。**[研究：独立分析]**

## 值得带回 Codex 日常使用的做法

✅ 先明确容易误判的业务语义，再让 Codex 写实现：空值不是零、未匹配不是删除、字符串标识不应随意转数值。验收预期可以独立于实现形成；选择性加入不同实现的解析器或精确数值工具，提高它们发现共同盲点的机会。独立 Agent 只是获取独立视角的一种手段，不是默认必加的环节。**[研究：采用判断]**

✅ 保存能在另一台机器运行的输入、预期和命令，并将验证绑定具体产物。不要只交“有多少项测试通过”的总数。UI、业务计算、部署、商业效果分别凭相应证据判断，避免一次局部通过升级成整个产品成功。**[研究：采用判断]**

这个案例支持上述具体实践可被复核，不支持“Codex 比其他工具更强”“多 Agent 一定提高质量”或“项目已有真实营收”。没有模型版本、耗时和完整开发轨迹，不能把它当作模型对照数据。**[研究：结论边界]**
