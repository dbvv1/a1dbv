# 研究战略：什么问题值得深入，什么材料能改变判断

> 核实与分析日期：2026-10-12（北京时间）。本文重审本仓库已有来源与选题，不声称本轮新增外部调查或模型实验。评级：✅ 采用下述选题与证据区分；具体开发建议仍按任务试用。全文的优先级、假设与推导属于 **[研究：本仓库分析]**，引用案例的事实范围沿用对应记录。

## 1. 上一阶段为什么仍然浅

“关注上下文、反馈、维护、社区”只是分类，无法决定下一小时值得读什么，也无法回答读者今天应该改变什么。前一轮把项目知识和运行反馈提到前面，有具体依据，但仍不足以成为整个仓库的研究战略。

对当前研究入口、队列与社区专题的自查暴露出三个偏向：

- **容易核实的材料牵引选题。** 配置、源码与本地校验器有明确边界，容易形成可交付结果；产品有没有用、维护是否更容易则难观察。继续前一种工作会让仓库越来越擅长证明“检查器执行了”，却未必更会帮助人开发。
- **防错比创造写得具体。** 我们已有很多不该做什么、什么不能证明什么，但缺少 AI 扩大可行项目范围的完整案例。持续加限制会把“严谨”误写成“少做事”。
- **方向被拆成任务以后，缺少再次比较。** D4/D6 合理，不代表它们因为进了表格就自动最重要。若出现更有解释力的新能力或反例，应调整，而不是用完成率维护旧路线。

这里没有统计整个领域的研究分布；是在反省本仓库的内容选择。修正办法不是再加十个领域，而是明确相互竞争的解释、寻找能区分它们的材料，并把结论转成具体使用选择。

## 2. 研究的结果到底是什么

中心问题应改成：**在给定人的时间、模型预算与真实项目约束下，怎样把值得做的想法更快变成可持续修改的软件？AI 又让哪些原来不值得做的想法变得可行？**

这同时包含三类目标，不能用一个成功率合并：

| 目标 | 应观察什么 | 容易产生的误判 |
|---|---|---|
| 完成已知工作 | 需求是否满足、总等待、人实际投入、缺陷与返工 | 首次 patch 快，就宣布开发更快 |
| 发现值得做的工作 | 原型揭示了什么需求，哪些方案被有理由地保留或放弃 | 生成的功能多，就宣布产品价值高 |
| 保持持续改变的能力 | 第二次需求、换维护者、升级和故障时能否解释与修改 | 初次测试全绿，就宣布代码可维护 |

总耗时应含环境准备、澄清、执行、审查、修复与后续维护；人的主动时间和模型等待应分开。它们可重叠，不能直接相加成一个“效率倍数”。个人的五小时额度还意味着机会成本：一次高 effort 长跑可能挤掉更有价值的探索；但便宜失败多次也可能更贵。具体额度政策与价格另按当前官方资料核实，不能从机制推导个人最优参数。

对于未知需求，放弃错误功能可以是成功。对于明确修复，反复改需求可能是失败。先分清任务性质，再比较工作流，否则同一个“中途改方向”会被随意用来支持相反立场。

## 3. 五个值得持续研究的矛盾

### A. 更强模型应减少流程，还是扩大可承担的任务？

这两个效果可以同时发生。强模型在原任务上不再需要细计划，但用户也可能把更大、更模糊的任务交给它，使总等待和失败重新上升。因此“升级后还是慢”不能单独说明模型没进步，“复杂任务需要规划”也不能证明每个小 bug 都要套流程。

应同时看两条线：固定任务上的最低必要约束，以及新增可行任务的范围。对 Superpowers 的关键问题是它在哪类失败上带来增量，不是文本是否很长。已读入口的低触发阈值与串行关口提供了成本机制，但尚不证明 Astra 上净收益为负；若它减少严重返工，增加的前置时间可能合理。反之，若任务本来一次完成，新增步骤就需要另有收益依据。

**采用判断：** Codex/Claude 原生能力足够的清楚任务，以直接执行和相关验证为起点；将领域知识、工具能力与强制流程拆开。复杂而不明确的任务先识别需要探索什么，不把“少流程”误解成“禁止研究”。依据见[已读 Skill 的机制与限制](README.md#主线三找出-skill-真正带来的增量)。

### B. 编码便宜以后，瓶颈移到哪里？

可能移到需求判断、环境反馈、审查，也可能仍在复杂算法、依赖理解或工具调用。不能预先宣布“以后人只负责产品”。同一开发者的原型任务与数据库迁移可能有完全不同的瓶颈。

最有价值的材料是失败发生的那个转折点：人补了一条领域约束、Agent 获得运行日志、换了模型、缩小了问题，随后结果怎样变。至少保留一个竞争解释。例如补文档后修复成功，也可能只是第二次尝试、多读了日志或人同时指出了根因；完整案例可支持采用建议，不足以把全部收益归给文档。

**采用判断：** 先补阻止下一步判断的具体信息或操作能力，再考虑持续维护一套工具。若同一障碍重复出现，才研究可复用环境接口和项目知识；一次性任务未必值得建设平台。见[开发条件分析](2026-10-12-development-conditions.md)。

### C. 让 Agent 更自主，会释放人，还是转移人的负担？

无人打断不等于人省时。一次产生大改动，可能把逐步沟通转成更难的最终审查；但每一步都询问也会破坏人的连续工作。需要研究的是人在哪个时点介入最有信息价值。

可逆实现细节、尚未决定的产品选择、影响既有用户的行为变化，应分别讨论。人的重要作用也不必表现为审批：一次试用、一个反例、一段业务解释，可能比审核长计划更有用。Agent 也能先实现两种低成本方案，帮助人发现原本说不清的偏好。

**采用判断：** 探索原型优先获取可观察的差异；明确实现任务优先让 Agent 连续完成；重大未定取舍需要人提供目标。不能把三者统一成“永远先问清楚”或“永远不要问”。下一案例须记录人的实际工作，而不仅记录提示数量。

### D. 生成更快以后，应该怎样选择架构与知识资产？

有两种值得比较的路线：保留最直接的实现，等需求出现再改；提前建立边界、测试数据和设计解释，降低后续变化成本。第一条避免为假需求设计，第二条避免每次重新理解。哪条更好取决于变化模式，不能从“AI 重写很便宜”推导已有数据、兼容接口和人的理解也可随意丢弃。

研究应追一个具体决策在第二次需求中的后果。例如为单用户原型直接使用全局状态，后来增加多用户隔离时，实际改了哪些层、漏了哪些路径；这是待查案例设计，不是已发现的项目事实。不要用代码长度、类数或整洁风格直接替代修改成本。

**采用判断：** 优先保存不易从代码恢复的业务理由、关键样例和兼容约束；AGENTS 不必成为所有知识的容器。是否抽象，依据已见变化及代价，而不是默认“AI 喜欢小文件”。

### E. AI 能否改善产品探索，而不只是加快既定实现？

这是目前最缺的正向研究。值得找的案例包括：个人为低频需求做了专用工具、开发者快速比较交互方案、用模拟数据发现设计缺口、游戏作者探索参数和操作反馈。这里也允许失败：快速知道某个想法不好，可以避免继续投入。

但“以前没做、现在做出来”只证明可行性变化，不能自动证明有人需要它。研究必须继续追谁实际使用、什么反馈改变了设计、后来留下什么。游戏特别适合区分机制正确、视觉呈现与操作感受；它不是自动证明 Agent 有或没有创造力的试金石。

**采用判断：** 主线保留一条主动发现新能力的调查，不能让已知缺陷审计占满研究。首先找人的真实反馈；只有生成截图的材料可作灵感，不能充当产品效果。

## 4. 来源应按问题选择，而不是按名气排序

“一手”不是万能可信等级。官方是产品机制的一手来源，使用者是其个人经历的一手来源；两者都不天然拥有跨人群效果结论。源码说明可执行路径，轨迹说明某次实际路径，后续使用说明当时检查没覆盖的现实问题。需要让证据与主张对应。

| 要回答的问题 | 优先追的材料与入口 | 主要盲点及补法 |
|---|---|---|
| Codex/Claude 实际会怎样加载、执行、恢复 | 对应客户端官方文档、changelog、可得源码、复现 Issue；从具体选项追到版本和路径 | 文档意图不等于已安装行为；Codex 开源客户端不公开全部模型或服务端机制，Claude 公开材料也不能替代不可见内部实现 |
| Skill 为什么可能有效或变慢 | SKILL 入口、依赖调用、触发条件，随后追用户运行过程 | 文件存在不等于触发；作者设计不等于效果。查未加载基线、实际额外关口和人工等待 |
| 真实人怎样做项目 | 原始需求、会话片段、PR 讨论、源码、部署后的问题、后续变更 | 演示与成功者偏差；优先同项目连续观察，并找不同作者及接收代码的人 |
| 是否普遍提效、影响谁 | 有任务定义的对照研究、方法与原始数据；不只读摘要 | 模型年代、熟练度、任务分配、对照条件可能改变结果；多 checkpoint 可能非独立样本 |
| 前沿出现了什么新做法 | GitHub 讨论、作者博客、HN/Lobsters、中文技术社区、公开视频/演讲 | 重复转载不是独立证据；从一个线索追到原始材料，平台热度不代表采用率 |
| 结果能否长期承受使用 | release 后 bug、revert、维护者复盘、第二次需求、支持负担 | 不报问题不代表没有问题；公开代码若缺使用数据，只评价能看到的部分 |

### 不只搜工具名：沿行为和失败查找

针对“增加流程是否降低总成本”，既搜方法名称，也搜具体结果，例如 `reverted`、`regression`、`review burden`、`stale plan`；这些是建议检索词，本轮未宣称已经跑过新的搜索。随后到相关项目查看成功使用的对照材料，避免负面关键词制造另一种单边样本。

针对中文实践，优先能追到代码、版本、操作过程或失败条件的原帖；“保姆级配置”和“效率翻倍”可以提供线索，但不据标题形成推荐。公开视频若只有剪辑后的顺利操作，只能支持演示中的可见行为；若有完整过程，也要注意隐藏准备和作者对任务的熟悉程度。

检索要同时沿三条链：从建议追到实现，从实现追到一次实际使用，从实际使用追到后续代价。不是每次都能走完三条链；缺哪条，就把结论停在哪条边界，不再用更多同类链接填补。

### 已有来源里，下一步具体追什么

这些是基于已读材料挑出的调查入口，不是本轮新验证结果：

1. **Claude Code／复杂仓库：** [BAML PR #2259](https://github.com/BoundaryML/baml/pull/2259) 与 [HumanLayer 原始论述、后来复盘](../24-community-workflows.md#4-humanlayer从研究与计划到把人的评审重新放回来)。先找公开后续变更与维护者纠正；分清原 PR 和后来的复盘是否同项目、同工作流，不能自动拼成一条因果链。读后若只获得另一篇立场文章，就不重复扩写总结。
2. **Codex／需求纠正：** [h3o PR #10](https://github.com/simonw/research/pull/10) 已有原需求与人的修正，可作为历史行为案例。下一步找实际使用及后续变化；没有记录就保留范围。需要另找当前版本、不同作者案例，不能靠一个名人重复证明所有主张。
3. **强模型与流程：** 已读 [Superpowers #2470](https://github.com/obra/superpowers/issues/2470) 与 [#2450](https://github.com/obra/superpowers/issues/2450) 只是使用者首帖。追维护者回应、关联修复与运行记录，区分框架缺陷、使用配置和模型局限。找得到修复机制但找不到使用结果时，只给机制判断。
4. **代码接收方的成本：** [Ghostty #8289](https://github.com/ghostty-org/ghostty/pull/8289) 提供维护者立场，尚不足以量化审查负担。以后找具体被接受、要求修订或撤回的贡献，观察理由，不凭“AI 生成”标签推断质量。
5. **连续需求评估：** [SlopCodeBench 报告入口](../24-community-workflows.md#前沿评估线索连续需求比单题更接近日常维护) 已发现统计和费用边界。下一步应追一个旧行为退化的具体 checkpoint，判断测到的是回归、遗漏需求还是评分器问题，暂不继续报模型排名。

这份入口有明显的英语、公开 GitHub 和愿意披露 AI 使用者的偏差。闭源业务、未公开失败者和不熟悉代码的人很难从中代表。中文社区与使用者访谈是需要扩展的证据来源；公开只读调查可继续，访谈或外部联系不因本文自动获得授权。多个博客、视频和仓库若来自同一作者/实验，只算一条来源链。

## 5. 深入分析应该带来什么不同

以“加 Skill 后更好”为例，至少有四种不同解释：它补了模型不知道的事实；它提供了原本没有的操作能力；它强制多花时间搜索验证；它改变了人如何描述任务。相应的替代方案是短参考资料、单个工具、提高原生投入、改善需求输入。若只比较“装／不装整个框架”，即使差异真实，也不知道读者该保留哪部分。

优先寻找能区分这些解释的证据，但不要求每篇文章都跑完整消融。已有轨迹若显示缺 API 后补版本文档就正确，可以给窄知识建议；若一次同时换模型、框架与任务规模，只能评价整套方案这一次发生了什么。源码能指出为什么可能增加等待，不能填补未记录的实际时间。

值得发表的分析应当包含一个可能被推翻的判断。例如：**对于已有明确接口和回归测试的小修复，默认追加访谈与完整规格流程不值得。** 理由是它重复已给定的信息并增加串行等待；反例是那些“明确接口”实际遗漏了业务契约的任务。看到反例后应收窄适用条件，而不是用“执行不到位”保护原结论。

也要避免只对社区项目苛刻、对自己的方法宽松。当前“优先知识与反馈”同样是待检验的优先级；若更强模型能低成本解决同类任务，或专用接口维护负担过高，推荐必须调整。

## 6. 当前明确的取舍与推进方式

**近期优先完成一条真实变更的深入追踪，并把结论用到 D4/D6。** BAML 提供存量代码与 Claude 线索，h3o 提供 Codex 的历史需求纠正；调查后选能获得后续证据的一条深入，不要求两条都写成长篇。若缺完整过程，明确缺口并转向别的可见案例，不无限追一个作者。

**同时保留能力探索，审计按变化和影响触发。** 读取新提交不等于每轮重跑全部历史检查。高影响错误应及时修正；没有新变化的脚本不应反复占用主要研究时间。没有可靠社区材料时，可以做明确标注的机制推导，但不能把研究方法文档当作已补齐的实证内容。

**不优先做：** 新增通用 Agent 编排框架、扩大插件名单、为已有检查器继续造评测平台、没有使用情境的模型排名、又一份最佳配置。可重新考虑的条件是它解决了前述调查中出现的具体障碍。

最终正文要给读者一个可采取的改变，例如“把一个真实失败输入和版本提供给 Agent”“保留这个人工反馈点”“删除这个重复关口”，并说明何时不适用。研究日志负责证明为什么；不能要求读者先掌握本仓库的审计体系才会使用 Codex。

本轮贡献是重新确定解释与选题方法，不是声称上述缺口已经填平。下一轮若仍只产出方向文件而没有新案例、直接机制证据或实用正文改进，就没有实现这里提出的转变。


## dot 新证据之后：研究优先级的实际调整

**更新：2026-10-12；[研究：方向判断]。** [D4 复审](../collaboration/reviews/2026-10-12-5408303.md)已结合 alchemy-utils 与 VibeTunnel，两例并非对全部维护成本的回答。本侧进一步运行前者固定代码，确认批大小改变缺失字段结果。这使下一轮问题从“如何要求更多验证”收窄到“Agent 怎样知道实现变化带来了哪些新义务”。

**优先一：让已有证据进入主力 Codex 的真实任务入口。** [Codex 第 6 节](../01-agents/codex.md#先给什么遇到什么再增加能力)已给出最小输入与增加能力的触发条件；15 已补性能参数与数据语义对照。D6 后续应审查这些建议是否确实改变动作：目标明确可直接做；缺版本知识补源码／窄 Skill；缺工具链补运行条件；缺产品契约才提出具体取舍。若文档只是把任务换成五种标题，仍没有回答“下一步做什么”，就不算完成。

**优先二：研究强 Agent 的领域知识增量，而不是默认追加流程。** 分批案例可作为后续方法比较的候选：原生提示、给出缺失字段契约、加入完整流程分别提供了什么？但该问题及答案现已公开，不能再将同一固定 bug 的命中率当成盲测能力；后续需选未暴露答案的同类真实任务，或只评价信息如何影响实现决策。来源优先找领域 Skill 的具体内容、相应修改与回归，避免用 Star 数和作者宣言证明效果。没有模型运行授权／记录时，先做内容是否提供独立约束的审查，不虚构效果。

这也避免另一个偏差：已经强的 Agent 可能自主推导上述约束，人补信息并非必需；本轮是确定性代码复核，没有运行原生 Agent，不能把发现归功于某种人机分工。若新增 Skill 只是要求“认真测试”，其是否改善发现能力仍未知；若提供模型不掌握的 API 语义或可执行检查，它至少有清楚的增量机制，是否值得保留仍要看实际任务。

**优先三：保留产品发现与有价值的放弃。** 两例主要回答实现／维护，没有说明某功能是否值得存在。下一条来源优先包含公开初始需求、第一次试用反馈、被取消或改变的功能、第二次实际使用；可从已选项目的 feature request／关闭 PR／用户反馈追踪，先排除只有作者自夸或无产物的材料。游戏可用“玩家操作—状态变化—体验反馈”追同一链，不先建引擎配置百科。找不到使用结果就不下产品收益结论，但需求为何改变仍可能提供有价值的设计证据。

这三项不要求另一端等候分派，也不同时开启三个大工程。当前最先可做的是 D6 的正文审阅与针对缺口补证；若又出现真实反例，应允许它改变本文优先级。没有新证据，不重复复跑未改的 30 次 SQLite 调用或重写方向文档。
