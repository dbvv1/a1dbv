## 仓库应该因为什么值得使用

帮助读者回答：**面对手上的开发任务，现在怎样用 AI 做得更好；该改变什么，为什么，何时应撤回这个改变？** 前沿性体现在新能力改变了哪些可行做法，实用性体现在读者能把建议用于自己的项目。以下是维护方向，不是已证明的生产力结论。**[经验：编辑判断]**

主要读者是已经使用 Codex、希望提高自主交付质量的开发者；Claude Code 提供有针对性的对照。初学者需要可跟随的任务入口，有经验者需要机制、证据和反例。两者共用研究，但不必读同样长的材料。

仓库应有三层内容，各自承担不同责任：

| 层次 | 读者得到什么 | 应放在哪里 |
|---|---|---|
| 直接使用 | 当前推荐、适用任务、最小改变、如何判断是否有效 | Agent 专题、15 任务打法、17 故障排查 |
| 理解与选择 | 方法为什么有效、与原生能力是否重复、代价和替代方案 | 03–09 专题、14 分析、24 实践 |
| 核查依据 | 固定来源、原始问题、检查范围、反证和未解问题 | research 记录与原始项目链接 |

入口不应要求读者先读完研究日志；研究记录也不应复制整篇推荐。一个结论在主专题维护，其他页面用简短说明链接过去。

## 双方独立研究，按问题协调

当前共同目标是深入探索 Codex/Claude 的实际能力、人与 Agent 的反馈、持续维护和读者可用性。双方都应形成自己的采用判断；另一端的方向指导与评审只是补充，不是权威或研究范围上限。任务表用于认领和去重，允许以新证据修订优先级及结论。

此前一侧偏重方向/来源研究，另一侧推进模板、脚本、离线验收与机制分析。这是历史工作分布，不是永久职责限制。当前整合保留双方有价值的结果，淘汰重复或证据不足的表述；不因提交较新或模型更强自动采用。协作入口见 [说明](../collaboration/README.md) 与 [任务状态](../collaboration/TASKS.md)。

不默认新增框架、模拟器或验收模板；独立调查、必要实现和验证应围绕具体问题，不能把“只做方向”或“只做实施”当成停止探索的理由。评审检查精确版本、直接来源与反例，不替代实际执行证据。初次审阅仍保留为 [历史记录](../collaboration/reviews/2026-10-11-4946f93.md)。

## 优先补足的价值缺口

| 缺口 | 要回答的问题 | 有价值的产出 |
|---|---|---|
| 可靠性内容多，创造能力的案例不足 | 新一代 Agent 让什么以前做不起的开发成为可能？人在哪些地方改变了结果？ | 一条真实需求到可用产物的过程，包含纠正和放弃方案，而非只列防错规则 |
| 有原生/插件之争，缺少同任务比较 | Codex 已会做哪些事，Skill 实际补了哪条知识或哪段反馈？ | 原生默认、增加单项能力、采用完整流程各自的明确触发条件 |
| 单次成品多，维护证据少 | 第二个需求、升级依赖或出现真实用户后，第一次的快是否变成返工？ | 同一项目跨变更的观察；找不到轨迹就保留未知，不把一次成功写成可维护 |
| 资料按工具分散 | 用户面对慢、跑偏、跨模块修改时，应该先改哪个变量？ | 按问题进入的短推荐，链接到机制及证据，减少重复全文 |
| 版本快照容易掩盖不确定性 | 今天的更新真的改变使用建议了吗？ | 精确指出旧建议如何变化；只有发布新闻而无决策影响的内容留在雷达 |

### 什么值得进入核心文档

优先选择能改变具体开发决策、有可追踪证据、且当前文档回答不足的问题。热度帮助发现线索，不决定推荐。旧案例若能解释重要机制仍可保留，但必须写明时代和客户端，不能拿来证明当前 Astra 的效果。

一段值得借鉴的建议应让读者知道：适合什么任务、今天先做哪一个改变、观察什么结果、付出什么代价、失败后怎样调整。正文先给建议，再给最有力的依据与主要限制；详细调查放到来源记录。不要求每条都套五栏模板，更不为凑完整性添加无关检查。

评价进展看读者是否少做了一次错误选择、解决了一类实际问题，或获得了新的开发能力；目前没有实际读者效果数据。暂用可检查的内容指标：推荐可追溯、例子能解释选择、已知反例会改变建议、入口能找到答案、重复内容有主归属。篇数、字数、项目数量和检查通过数都不能代替这些价值。

## 当前方向判断：从防错资料库走向开发决策参考

以下是对端 `798dd839` 提供的补充方向与来源阅读记录，本次整合不等于自动接受其优先级、实施 D6/D7 或独立复测所有新来源。双方按证据继续形成自己的判断。

2026-10-11 对已有 Codex、13、14、15、17、24 专题的审视表明：机制、失败和验证已有较多材料，但正向能力、人的需求探索与后续维护尚未形成同样清楚的使用路径。这是内容审查，不是读者调研或对所有工具的效果排名。**[经验：方向判断]**

**候选中心问题是：一个已经很强的 Agent，需要人和工具补充什么，才能把想法持续变成有用的软件？** 不预设答案是更多流程，也不预设完全放手。新增内容优先服务下面四条主线；纠错和版本维护作为支持工作，不能长期占满研究。

### 主线一：让主力 Codex 的用户知道先改变什么

目前 Codex 页已有加载、权限、Plan、effort 和慢/停工机制，但读者仍需自己把它们拼成使用方式。应给出少数典型任务的起点：明确 bug、存量仓库的新功能、需求尚不确定的原型、跨会话持续任务。每条都说明最少需要提供什么、Agent 可直接承担什么，以及什么观察出现后才值得改变配置。**[经验：内容设计]**

区分四种成本：等首输出、等实际工具/测试、反复纠正同一理解、审查和返工。它们可能同时发生，不能看到“慢”就统一降 effort、清会话或安装工作流。已有 [续接调查](2026-10-10-codex-continuity.md)提供机制与单例，足以组织诊断入口，不足以给统一最优参数。

**交付价值**：读者能先改一个有依据的因素，而非抄一份“最佳配置”。以 Codex 为基线；Claude 只在交接方式、工具能力或已观察瓶颈上给对照，不要求每个任务双模型互审。见任务 D6。

### 主线二：把 vibe coding 中人的探索写清楚

不能只收集“用了多少提示做出网站”的故事。更值得追的是：用户看到第一次运行结果后，发现原需求哪里不对；是改提示、交互、数据模型还是直接放弃功能；Agent 帮助发现了什么新可能。这里完成标准本身会演化，不能把一切需求变动视作跑偏。**[经验：研究问题]**

选择具有可见迭代的项目：原始目标、可运行产物、至少一次有理由的需求修正、对应改动和使用反馈。已有 Catalog Compare 的界面/导出命名反馈和 h3o 的打包范围纠正是起点，尚不是完整的产品探索过程。追不到公开材料就明确留下空白，不将作者的成功总结补写成原始轨迹。

**交付价值**：读者学会向 Agent 提供哪种反馈、何时应该继续探索、何时收敛，并看到 AI 扩大可做项目范围的具体例子。与 D4 的后续变更调查一起做，不新建一份重复案例任务。熟练开发者与不熟悉代码的用户要分开：前者可直接检查接口和 diff，后者需要运行路径和可观察结果；二者都不能仅凭画面判断持久化或权限正确。

### 主线三：找出 Skill 真正带来的增量

比较的基本单位应是“它补充了什么”，而不是项目名字。将候选拆成：项目/领域知识、可执行工具能力、工作顺序、反馈与验收。模型已经具备的规划习惯和模型不知道的版本 API，不应混为同一种 Skill 收益。**[经验：研究拆分]**

用已有官方 Skills、Superpowers、Starlette 例子回答：不加载时 Agent 缺了哪条信息或哪种能力？加载后多出哪些串行步骤？能否只取有用部分？原生已能做的环节有没有被重复执行？gstack 回执已经由另一端研究，作为它的特定机制引用，不重新从项目概览做一遍。

**交付价值**：形成“原生足够 / 增加窄知识或工具 / 有条件采用完整流程”的任务级选择。暂不声称 GPT-6 Astra 配合某框架一定提速或一定负收益。若认领 D6，先核对其采用边界；只有发现无法用现有资料回答的具体差异，再提出有对照的后续研究，不先安排一批付费跑分。

**具体判断：小 Skill 也可能有很重的控制要求。** 本轮补读以下固定入口，只作为研究材料，没有安装或执行：

| 已读来源 | 有价值的内容 | 应单独评估的控制成本 |
|---|---|---|
| [官方 skill-creator](https://github.com/openai/skills/blob/49f948faa9258a0c61caceaf225e179651397431/skills/.system/skill-creator/SKILL.md) | 默认 Codex 已聪明，补非显然知识；按任务脆弱性选择自由度 | 这些是设计建议，不能仅凭官方来源认定某个生成的 Skill 已有效 |
| [Matt Pocock TDD](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/tdd/SKILL.md) | 在公共行为边界测试、独立预期、逐步验证 | 要求先与用户确认测试边界，未确认不得写测试；即使正文短，也可能给已授权修复增加人工关口 |
| [Superpowers systematic-debugging](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/systematic-debugging/SKILL.md) | 跟踪数据流、比较正常路径、用最小实验区分假设 | 四阶段按序、继续加载 TDD/验证 Skill、三次修复失败后与人讨论架构；触发单项也不代表总工作量小 |

表内机制来自入口原文 **[一手]**。我的采用判断是：**把有效知识与控制要求分开选择**。已有明确公共接口和失败测试的任务，不必只为遵守通用 Skill 再询问相同边界；反复猜修复的任务，系统调试的证据要求可能有用。不能据此直接删除所有测试前对齐——接口契约尚未决定时，询问仍可能避免返工。**[经验：条件判断]**

Superpowers 文中还把多次修复失败强烈关联到架构问题，并写出“95% 的无根因情形是调查不完整”。已读文件没有为该比例提供统计依据；三次失败也可能来自环境、观察缺口或错误假设，次数本身不能确诊架构。可保留“停止重复猜测、改变诊断方式”，不把数字和确定性归因写成仓库事实。**[一手：原文措辞；研究：本仓库推理审查]**

因此对 D6 的建议是比较完整触发路径和人工等待，不按文件行数、Skill 数量或“轻量”标签直接排序。这使建议同时避免两个极端：整套框架默认安装，以及遇到任何额外步骤就删掉必要反馈。

### 主线四：让第二次修改和人的理解成为长期质量标准

成品测试通过只能说明其覆盖的行为。第二次需求、升级依赖、修复线上问题时，能否定位、解释和修改原实现，更能揭示哪些开发习惯值得保留。AI 也可以通过调用链走读、变更影响分析和反例帮助人理解代码；不能预先把人定义为只负责批准的瓶颈。**[经验：研究假设]**

D4 优先追同一项目的后续变化，而非寻找更多一次性成功。记录先前哪些决定被保留或撤销、人的判断改变了哪步，以及修改后什么仍未验证。多提交不自动等于可维护；没有实际使用或后续行为记录时，只能评价可审查性，不能宣称维护成本下降。

**交付价值**：帮助读者决定何时保留快速原型、何时局部重构、怎样借 Agent 建立理解。不是默认“原型转正必须重写”，也不是默认“Agent 写过就无需读”。

## 分析文章自身也要接受反驳

以下推理审查来自对端整合前的第 14 章快照；首轮整合已保留本侧对“接近完美”“只能模仿”及“会判断就应一次写好”等推论的修正。这里保存问题类型和反驳依据，不指称这些措辞仍残留于当前正文。若认领 D7，必须先核对现有 14 的实际内容，只处理剩余问题，不能重复修已解决的旧文本。目标是把普遍定律收窄为有适用范围的判断；未重新验证文中所有外部来源。**[研究：本仓库分析；整合后的适用范围]**

- **容易检查，不等于容易生成。** 编译器能确定报告错误，不代表 Agent 在可编译任务上“接近完美”；可验证性影响反馈质量，但不能单独推出模型成功率。反过来，产品探索没有唯一正确答案，也不等于 Agent “只能模仿”。
- **能识别较好的方案，不等于能一次生成最优方案。** 评审与生成拥有不同输入和搜索机会。指出它们可能共享盲点有价值，以“如果会判断，一开始就会写好”否定评审增益则推理不足；是否值得评审仍看具体检出与返工。
- **人的作用不只有限制吞吐量。** 人可以提供隐含需求、试用反馈、领域判断，Agent 也可能降低理解成本。“前置设计”与“先做原型再发现需求”应按任务不确定性选择，不能只有一种成熟路线。
- **流程轻重需要随能力与任务更新。** 快速变化的模型、工具和调用方式，可能让旧的分工过时；但不能由更强模型推导所有记录、验证或权限约束都可删除。有效结论要指出哪一项能力变化，使哪一条建议发生改变。

这类修改保留解释力，同时允许前沿发展改变建议；不要求为每句话新增免责声明，也不把文章改成没有立场的资料汇总。

## 研究目标

持续探索 AI Coding / Vibe coding 的新能力、开源项目、Skills 和真实开发者工作方式，形成有证据、可操作、敢于取舍的知识库。核心产物是有价值的认识与采用判断；不以文档数量、工具数量或流程完整程度衡量进展。

当前主线是 **Codex（用户主力）**，辅线是 **Claude Code（偶尔使用）**。优先研究官方建议、实际配置、社区正反反馈和真实使用心得；Pi 等其他项目主要提取可迁移思想，只有能解决主线问题时才深入实现。此优先级来自用户最新补充，不缩窄 AI Coding 的长期视野。

用户明确要求：

- 不限于 OpenAI、Anthropic 等厂商；读 GitHub 项目、具体 Skill、源码、技术社区和人类实践。
- 不盲信作者、热度、官方说明或既有仓库结论。读到后要分析机制、适用条件、成本与反例。
- 可以改写、删减和推翻已有内容，不只是追加信息。
- 判断必须结合当前模型与使用情境；尤其关注强 Agent 上的流程重复、过度保守、慢和低自主性。
- Superpowers 只是一个案例，不把整个研究缩成对该插件的支持或反对。
- 这是长期深入研究；每轮交付应包含新发现、独立判断、纠错及尚未解决的问题。

## 每次唤醒的入口

先读 [STATE.md](STATE.md) 获取接续点，再核对[协作任务](../collaboration/TASKS.md)、[研究候选](BACKLOG.md)与相关新提交。任务表用于协调，不指定唯一研究方向；双方独立选择有价值的可执行问题，未经确认的候选不记为已认领。没有待审提交时仍可深入调查，不以等待对端为由停止思考。

研究循环是：提出问题 → 查直接材料与真实案例 → 检查反例与成本 → 形成判断 → 更新核心专题 → 产生下一步。不是定期重写同一批文档，也不是持续增加模板。

## 每轮如何推进

围绕一到两个实质问题深入：读取直接材料 → 检查实现或案例 → 寻找反例 → 形成采用判断 → 修改受影响专题。只有无法融入已有内容时才新增章节。

建议的判断写法：

> 目前我建议在 X 情境采用/不采用 Y，因为机制 A 与证据 B；代价是 C。D 尚未验证。如果观察到 E，应调整这个判断。

不要求每次实验才允许给建议，但没有实测时不要写收益数字或“已证明”。相反，也不要用无限补充免责声明来回避明确取舍。

评估社区材料时问：作者解决的是真实重复问题还是演示问题？读者是否能重现？有什么失败成本？是独立使用者还是项目维护者推广？是否把不同模型、任务和工具混为一谈？

## 会话恢复

开始时读取本文件、状态、队列与 Git 状态，识别已有未提交改动，继续最高价值的问题。保留来源固定提交、原帖链接和判断依据；临时下载目录不保证在新环境中存在。

唤醒由用户的本地会话负责，本研究只负责持续推进与保存接续状态。入口指令可以是：“继续本仓库长期 AI Coding 研究，按 AGENTS.md 与 docs/research/STATE.md 接续。”
