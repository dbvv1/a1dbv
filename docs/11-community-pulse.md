## 1. 已关闭的需求，是否已适合采用

**先核发布实现和实际入口，再判断关闭的 issue 能否采用；关闭只说明维护者如何处理请求。** 原来的 2026-10-03 点赞排行没有任务、用户或版本分母，不再据此判断“共同头号痛点”或“两家功能基本趋同”；成本、质量与平台选择回到各自专题。

以 Codex 的敏感文件排除请求 #2847 为例，三件事会改变采用判断：

- **实现确实存在。** Windows deny-read 的固定补丁已包含于已发布的 CLI 0.138.0；维护者 6 月因 Beta 权限 profile 已提供该能力而关闭请求，同时说明 App 接入当时仍在完善。
- **关闭后仍有不同入口的反例。** 7 月使用者报告，同机同配置下 CLI 0.145.0 拒绝读取，而 Windows App 26.721.31836 仍读取；这是历史自报，不能当成当前 App 故障已复现。
- **当前采用条件已变化。** 官方现在列出原生 Windows 等平台支持，但权限 profile 仍为 Beta，且旧沙箱配置可能覆盖它的选择。具体如何选、何时暂缓，见 [10：Codex 文件排除的采用条件](10-security.md#codex-文件排除的采用条件)。

限制：没有当前 App 构建的实际拒绝结果，不把 CLI 发布、旧用户反馈或测试定义外推为所有入口已经修复；完整证据与反证见[来源记录](research/2026-10-12-community-source-records.md#codex-文件排除从关闭请求到采用条件)。

**依据**：[研究：撤回范围] 2026-10-03 点赞排行不再作为采用依据；[一手：源码、版本与维护者说明] Codex issue #2847 https://github.com/openai/codex/issues/2847、固定补丁 https://github.com/openai/codex/commit/46f30d02828bd4c52827e5f0482a6f2a982cce5b；[社区：原帖后续] 7 月使用者报告（见来源记录）；[一手：当前文档] Codex 文件排除的采用条件（见正文）；核实 2026-10-12。

## 2. Claude Code 与 Codex：何时需要第二工具

**已有工作流能交付，就不因口碑增加第二套工具；先记录一次具体能力缺口（漏检、返工或工具障碍），再按次试用第二工具。** 本页撤回“常见做法是两个都用”作为默认采用理由，也不再把速度、UI 或性价比写成两家的固定强项。

4 月原帖与 7 月原帖能保留的是使用条件，而不是胜负：

- **任务不同，偏好也不同。** d-lo 说 Codex 更合自己的 CLI 任务管理方式；beecasthurlbow 的速度感受限定于小型非遗留项目；aykutulis 则认为复杂系统中 Claude 少返工。这些都是历史作者自述。
- **确有交叉使用，尚不证明值得默认双持。** wek 与 bicepjai 描述交叉检查，但相关评论未附可追查的漏检、修复与复测产物，也没有单工具对照。评审是否值得加一层，见 [09 的采用条件](09-review-and-quality.md#30-秒结论)；没有补上实际缺口，就撤回额外层。

局限：两串自选回复不能估计采用率，也不能区分模型、harness、提示与任务差异的贡献；作者、日期与反证见[来源记录](research/2026-10-12-community-source-records.md#历史口碑不能直接推出双工具采用)。

## 3. Cursor：按实际接入路径判断是否迁移

**先核自己的必要路径，再决定是否迁移；最终日期未定，不保证此前一直可用。** OpenAI 已宣布拟终止对 Cursor 的供模合同，提出 2026-11-12 作为过渡截止日期；这是官方计划与过渡条件，不是 8 月已全面停供。

## 4. 生产力证据与采用边界

**准备改变工作流时，先找与你的任务、样本和收益口径相近的一行，再比较完成质量、返工和总投入；新增环节未补上缺口或成本超过收益，就收窄／撤回。**

| 研究 | 结论 |
|---|---|
| METR 2025 随机对照试验（2025 年 2–6 月数据） | 资深开源开发者使用 AI 后，完成任务的时间**多了 19%**（置信区间 +2% 到 +39%），但他们**事后认为快了约 20%** |
| METR 2026-02 更新（2025-08 开始的新实验） | 原有参与者的耗时变化为 **−18%**（置信区间 −38% 到 +9%，即可能变快）；新招募的开发者为 **−4%**（−15% 到 +9%），**都不显著**。METR 认为数据不可靠：很多开发者不愿意“不用 AI 工作”，30–50% 的人刻意不提交不想手工做的任务；时薪从 150 美元降到 50 美元；同时开多个 Agent 时耗时测不准。METR 判断 2026 年初的提速大概率比 2025 年大，但这组数据只是“非常弱的证据”，正在重新设计实验 |
| METR 2026-05 问卷（349 名技术人员，2026 年 2–4 月） | 自报的**价值提升中位数为 1.4–2 倍**，速度提升中位数为 3 倍；回溯 2025-03 约 1.3 倍，预测 2027-03 为 2.5 倍。METR 提醒：问卷通常高估，2025 年的实验里人们平均高估了约 40 个百分点 |
| GitClear 2026（厂商公开摘要与图示） | 重复指标上升、移动占比下降可提示抽检；单位与定义冲突不支持直接计算维护成本或 AI 因果，见 [09](09-review-and-quality.md)。另条 2026-01 效率报告未复核，不据此预测当前团队提速 |
| 不同实践者的自述 | 《2x, not 10x》作者描述初稿后仍需大量结构迭代；另一评论者自报评审耗时为手写的 2–3 倍；研究任务使用者描述过去不会尝试的任务，也抱怨代码冗长。三者不是同一人的完整成本记录 |

**采用判断**：这些研究与自述的任务、样本和收益口径不同，不能据此预测本团队提速。METR 2025 实验中，自评提速与实测方向相反，说明主观感受不能单独承担采用判断。对原本不做的新任务，先验证产物是否有用，不能用任务数量当净收益；也不按单人评审倍率决定手写或免审。作者与反例见[来源记录](research/2026-10-12-community-source-records.md#实践者倍率分清作者与收益口径)，方法见 [09](09-review-and-quality.md) 与 [18](18-team-adoption.md)。

**依据**：[研究：原文] METR [2025 RCT](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)、[2026-02 实验设计更新](https://metr.org/blog/2026-02-24-uplift-update/)、[2026-05 问卷](https://metr.org/blog/2026-05-11-ai-usage-survey/)；[一手：公开材料；研究：边界] GitClear 2026（厂商公开摘要与图示）；[社区：历史原文与原帖] 《2x, not 10x》https://obryant.dev/p/2x-not-10x/、HN https://news.ycombinator.com/item?id=49118572、https://news.ycombinator.com/item?id=49116268；作者与反例见正文来源记录；[研究：证据边界；经验：采用判断] 采用判断与证据边界；核实 2026-10-12。

## 6. 社区体验能改变哪些选择

**先按你的具体选择查一行，再核证据是否覆盖你的任务；不因热帖分数统一降模型档位，不因乐趣争论要求关键模块必须手写，也不因文件格式开放就认定常驻工具容易迁移。** 下面原帖只支持按具体任务检查，不能代表社区共识。

| 选择 | 原帖中可保留的证据与反证 | 本页判断 |
|---|---|---|
| 是否用更便宜的模型 | 同串讨论里，例行调试使用者报告低档模型够用；SRE 使用者则区分例行健康检查与动态调查，报告后者有工具使用障碍 | 只为边界清楚的任务考虑降档，遇到诊断或工具障碍就撤回；这些自述没有同任务质量与费用对照，不足以推荐具体型号。正式成本与预算规则见 [02](02-models-and-cost.md#3-订阅额度与成本控制)／[18](18-team-adoption.md) |

## 7. 中文社区：额度与交付自述

**不要根据“额度打六折”或“搭配最划算”升级订阅、换模型；先看原帖有没有可复算的任务、前后基线和计量过程。**

额度原帖的第 7 条回复确实自报跨档位、同一模型试用后得到六折判断，但没有公开可复算的任务、前后基线或计量过程；第 8–9 条回复感受相反，第 5 条还报告显示与限额不同步。档位、任务、推理设置和五小时／周窗口不能混为一项额度，百分比变化不能直接换算统一降额或性价比排名。具体预算判断见 [02 的官方 Pro 200 新旧订户条件](02-models-and-cost.md#3-订阅额度与成本控制)；已确认的额度过渡条件与仍未核实的“20 倍降 10 倍”分开看。

**团队交付原帖只支持检查产物能否被解释、修改和接手。** 它描述成员不理解组件输入输出；回复既有强调理解责任的，也有支持继续依靠 AI 定位的。这不能证明 AI 普遍造成技能退化或必须改回手写。
