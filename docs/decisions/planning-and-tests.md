# 测试驱动、规格驱动、计划模式怎么选

**✅ 需求、必须保留的行为和验收方式已清楚，就让原生 Agent 直接实现；缺决定才澄清，缺判错检查才补测试，需要跨次共享契约才留规格。** Plan 帮你先审做法，Spec 保存系统应有的行为，测试负责执行检查；三者可以组合，但不用每次从头走一遍。

| 眼前缺什么 | 当前推荐 | 最小交付与完成信号 |
|---|---|---|
| 没缺关键决定，项目已有实现模式和相关检查 | **直接编码**，边读相关代码边实施 | 按既有要求实现、跑检查、接到实际入口 |
| 不熟悉影响范围，或还有会改变实现的取舍 | **只读调查／短计划**；资料答不了的业务决定才问人 | 能说清改哪里、为什么、保留什么、怎么验 |
| 正确行为已知，但没有能抓住这个错误的检查 | **最小测试先行**：复现 → 修复 → 同输入重跑 | 失败来自目标行为，修复后通过，邻近旧行为保住 |
| 需求要跨会话、角色或并行任务继续使用 | **短规格**；已有 OpenSpec 等工具就沿用当前规格＋差量 | 接手者能找到当前契约、变化理由和验收，不用重拼聊天 |

**“不知道怎么实现”和“不知道要什么”分开处理。** API、目录、调用链和现有默认值先让 Agent 查；默认是否开启、是否修改原数据、兼容到哪一版等缺少依据的产品取舍，才需要澄清。跨多个文件会增加规划收益，但文件数不是流程开关。

**依据**：[官方] [Claude Code 最佳实践](https://code.claude.com/docs/en/best-practices#explore-first-then-plan-then-code)，核实 2026-10-26；[既有选择与实证](../07-workflows.md#2-标准节奏探索--计划--实现--提交-)，原核实 2026-10-25。表格是条件推荐；原生、窄辅助与完整框架在同一真实维护任务上的整体最优仍未知。

## 第一步：在现有任务里补这几句话

**已经授权实现的任务，直接把下面这段交给正在用的 Agent，不必先安装框架。** 方括号替换成任务事实；已有工单或测试能表达的，给链接／路径即可。

```text
目标：[用户可见的结果]。
已确认：[行为要求或权威需求路径]；必须保留：[旧行为／消费者及原因]。
先读相关实现、项目约定和测试，沿用现有模式完成，不做无关重构。
已有检查：[命令或测试路径；不知道时先从项目配置查]。
若正确行为已知而缺少检查，先补最小复现，确认因目标问题失败再修。
仅把现有资料答不了、且会改变实现的决定交给我；其余在授权范围内继续。
交回实际结果、相关检查和仍未验证的用户路径。
```

例如“隐藏已完成任务”，**默认关闭、本机阅读偏好、不改原文、保留未完成子项的父级上下文**一旦明确，Agent 就能沿现有偏好与渲染链实现。Memos 的本仓采用正是这条路线；真实组件反馈又发现结构化列表和 raw Markdown 两种展示路径，促使修补遗漏。工程检查与浏览器体验分别接收，不能由“功能做过了”推断所有交互都通过。

**依据**：[本仓实际采用] [Memos 阅读偏好与保留契约](../../experiments/memos-reading-adoption.md)，原核实 2026-10-25／26；[任务起点](../15-task-playbooks.md#3-新功能)，原核实 2026-10-25。上面的短提示是对已有路线的整理，未另做模型收益对照。

## 先 Plan：让下一步少猜，而不是先写一遍代码

**需要先审方案、摸清陌生模块或澄清关键取舍时，先用 Plan；已经明确的局部修改直接做。** 在 Claude Code 中可用以下入口，再给它一个有终点的调查请求：

```sh
claude --permission-mode plan
```

```text
先调查 [目标路径]，本轮不实现。
交回：现有行为依据、受影响入口、必须保留的契约、建议改法和验收命令。
把“代码里能查到的事实”和“仍需我决定的取舍”分开；只问后者。
```

Plan 是先讨论再执行的工作方式。**需要严格只读时，只给读工具，或使用只读挂载且无外部写凭据的调查环境。** 当前 Claude Code Plan 可运行获准的 shell；可用 bypass permissions 的交互会话另有例外。涉及真实数据或外部写操作时，应核有效权限与隔离，不能靠模式名承担保护。

**计划只记录实施者不能自行决定的内容。** Superpowers 当前 `writing-plans` 的原句是：

> A plan is the set of decisions the implementer cannot make alone.

值得借的是具体文件、接口、需求值、测试断言和验证命令；函数体留给实现者，确有歧义的算法再展开。若修改了接口，同次更新尚未执行的计划与调用方。当前 Skill 已提供 Native 与逐任务子 Agent 两种执行选择；无需把整包的审批、拆分和评审节奏复制到每个小改。

**依据**：[官方] [Plan 行为与权限例外](https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode)；[真实配置] [Superpowers writing-plans 固定版本](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/writing-plans/SKILL.md)；[社区反例] [接口已改、后续计划仍用旧调用的报告](https://github.com/obra/superpowers/issues/2450)，单例未独立复现；核实 2026-10-26。配置已读，未运行该 Skill；[既有计划产物比较](../07-workflows.md#2-标准节奏探索--计划--实现--提交-)保留原实测范围。

## 先测试：正确行为已知，才把它锁成断言

**修明确 bug，先复用已有失败用例；缺覆盖时只补能区分对错的最小用例。** 需求尚未决定时先澄清；重构要保护既有行为时，先补特征测试，起点可以是绿的，不必为了“红灯”制造新缺陷。

1. **从需求、规范或已确认复现取预期**，不要照着待修实现重算答案。
2. **在修复前跑同一检查**，读具体失败：错误输出或目标异常才是复现；缺依赖、路径写错、测试没加载应先修环境。
3. **修实现，保持断言含义**，重跑同一用例及受影响检查；测试预期确有独立错误时，说明依据后修正。
4. **沿真实入口看结果**，保留邻近正常行为、兼容要求和失败保护。完整验收设计见 [15 调试](../15-task-playbooks.md#2-调试)与[强验证](../22-agent-evaluation.md#修-bug-的强验证)。

GitHub Spec Kit 自己的 `AGENTS.md` 对可执行行为写得很直接：

> Behavioral changes need positive and negative coverage; bug fixes need before-and-after regression evidence.

**本仓可重放的例子：Oil UI 合法 CSS 字符串续行打包失败。** 三个行为回归在旧实现上暴露问题；局部修复后，58 个非浏览器测试通过，真实 CLI 生成内嵌资源的 HTML，缺资源时仍保留旧产物。新增参数的 `TypeError` 单独只能说明 API 尚未实现，证明原 bug 要看行为回归与 CLI。这比只写“tests failed → passed”多一个关键判断。

已有 Python 3.10+、Git、Node 和固定上游 checkout 时，可从本仓根目录运行：

```sh
python3 experiments/replay_oil_ui_css.py /path/to/oil-ui-checkout
```

固定版本与准备方法见[完整示范](../research/2026-10-23-real-coding-demo.md#可复制入口与实际产物)。入口会创建隔离副本；本页重新跑过上述结果，3 个浏览器测试与 1 个 Windows 测试未运行。它验证修复与检查方法，不评比模型或 TDD 插件的效率。

**依据**：[真实项目配置] [Spec Kit AGENTS.md 固定版本](https://github.com/github/spec-kit/blob/9783b49ed66c26935cf7ef5ccc6ae5a296316eb7/AGENTS.md)，核实 2026-10-26；[本仓实测] Oil UI 原采用 2026-10-23、重放 2026-10-26；测试先行的采用边界沿用 [07](../07-workflows.md#4-测试驱动tdd)，不据此升级为所有任务必须 TDD。

## 留 Spec：下一次修改还需要这份契约

**把规格留给会被继续使用的行为与取舍，计划留给这次怎么做。** 已有工单、ADR、API 契约或测试足够，就更新原位置；需要跨角色共享、长期审计或维护规格资产时，再试完整 SDD。🧪 已有 OpenSpec 的存量项目适合先做一个增量变更；Spec Kit 的 existing-project 入口也不要求先逆向重写全系统。

短规格先保留这些内容，删掉不适用项：

```markdown
# [变更目标]
- 已确认：[需求、来源及选择原因]；待决定：[会改变实现的问题]。
- 本次改变：[输入／场景 → 新行为]。
- 必须保留：[旧行为、数据或消费者]；不做：[明确排除项]。
- AC-01：[输入／操作 → 可观察结果]；验证：[命令或实际用户路径]。
- AC-02：[相关失败或边界 → 应有结果]；验证：[检查入口]。
- 后续变更：更新当前契约，说明改变了哪条决定以及为什么。
```

验收 ID 用于后续引用；数量由真实需求决定。**不要让已勾选的任务替代验收，也别为让实现通过而悄悄删除旧条件。** 本仓 OpenSpec／MDX 采用中，第二次只把运费阈值从 50 改到 75，三工作日送达要求和组件依赖继续保留；两轮归档后都交给真实 MDX 编译器与 React 消费者检查。验证范围是 CLI、模块执行与静态渲染，浏览器交互另验。

社区的 LINUX DO 使用者也把规格的价值放在 Git 共享当前要求、归档合并后的约定与决策。能接着用才值得维护；若只是把同一份实现重复描述，缩回原任务和测试即可。

**依据**：[官方] [Spec Kit existing-project 指南](https://github.github.com/spec-kit/guides/existing-projects.html)、[OpenSpec 工作流](https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md)，核实 2026-10-26；[本仓实际采用](../../experiments/openspec-mdx-adoption.md)，沿用 [07 的 2026-10-25 核查](../07-workflows.md#从规格到实际消费者原生-agent-完成一次扩展及二改)；[社区原帖](https://linux.do/t/topic/2099475)，2026-05 使用经验、2026-10-26 重读。更多可借机制见 [21](../21-agent-patterns.md#1-选择依据)。

## 何时不适用：看补上的能力，不看流程是否齐全

- **已有可靠测试、范围和行为都明确**：直接实施；计划和规格若不增加决定，就省去。
- **效果必须看样品才能判断**：先做可撤回的垂直样品，让人比较；确认后的约束再进规格与测试。
- **原生 Agent 总漏回归**：先加上面的窄要求，再考虑 TDD Skill；验收看留下的测试能否抓错，而非是否严格执行仪式。
- **完整 Skill 包让小任务等待、文档或评审膨胀**：保留有效的缺口补充，撤掉重复层；已有团队流程仍按其约定执行。

近期同题证据支持这种取舍：Krupa 用 Sonnet 5.5／Superpowers v6.4.2 对照 12 个小任务，bug 修复附带回归测试为 8/8 对 4/8；新函数两组都正确，差别主要是测试顺序。12 个任务各自费用比的均值为 1.33 倍，长程工作未测。V2EX 的同一讨论也同时出现“一次做对”的正面自述与慢、耗 token 的抱怨。这些证据支持**按缺口采用**，不能给整包流程判一个通用胜负。

**依据**：[社区作者实测] [Superpowers 与无插件对照](https://bartlomiejkrupa.dev/articles/does-superpowers-beat-no-plugin/)，2026-09-29 发布，单模型、小样本、包含过程评分；[中文社区正反反馈](https://www.v2ex.com/t/1210981)，2026-05 原帖，非当前版本复测；均于 2026-10-26 重读。
