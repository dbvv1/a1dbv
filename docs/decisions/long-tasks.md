# 子代理怎么组织，长任务怎样无人值守

**🟡 一位主 Agent 持有完整目标，独立工作按需委派；结果回来就核产物、整合并继续剩余工作。** 先用已有会话、Git 和项目检查。此前版本已有新读者实施、本机交回和云端续修；新增基线步骤已实跑一次，整页新读者复测和离开后稳定接续仍待验证。无人值守要有实际可用的接回入口，写下“下一步”不会自动唤醒 Agent。

<a id="从当前任务开始不重新搭工作流"></a>

## 1. 用当前需求起步

**先准备目标、项目入口和最终验收，再交给主 Agent。** 需有已配置可用的执行环境、项目依赖和权限；没有原生委派工具时按同样验收串行做。要离开或关闭本机，开跑前选已配置的远端／云端；本机任务需要电脑与客户端保持运行。

```text
继续完成 <需求或 issue>，让 <用户> 能 <可观察结果>。
保留 <必须留下的行为>；不做 <非目标与取消项>。
项目入口是 <指令文件、源码、已有任务记录>；最终验收是 <命令和真实使用路径>。

先核最新需求、项目规则、实际版本、工作区改动、已有结果和当前写者。
你保留完整目标、共享决定和最终验收。已有结果先接收，不重派。
按需委派独立调查、实现或验证；先定共同接口与单一写入归属。
每项交接给目标、必要输入、写域、验收、结果位置和停点。
若任务指定基线或依赖提交，给已核对的 SHA；子任务首次判断或写入前核实际版本。
先核一致性检查所需的同步副本；写域没覆盖时由主线补齐分工。

结果回来后看实际 diff、运行输出和受检版本，决定接收、返工或阻塞。
按依赖整合；复用未受影响的有效检查，重验受影响或影响不明的路径。
在最终版本跑项目要求的检查，并从真实消费者入口验证成功和失败路径。
每个阶段结束回到原目标，有可执行的实施、接收或验收就继续。
未知外部写入先查实际结果；明确拒绝只停该动作，不换路重试。
最终验收完成或确实阻塞再收口；阻塞留可恢复产物、缺项及下一步。
已获准发布时串行提交并回读目标仓库、分支、提交与内容，另核该版本 CI。
```

**派发前的任务与写者核对由主 Agent 负责，实施者按交接中的写域工作。** 从项目已有记录、原调用和实际工作区核对；本仓用 [TASKS](../collaboration/TASKS.md) 与 [local-jobs](../collaboration/local-jobs/README.md)，其他项目用自己的入口。表上没登记不能证明没有写者；归属不清先交回负责人确认。短任务保留交接消息即可，跨会话沿用[现有交接模板](../../templates/generic/.claude/skills/handoff/SKILL.md)，无需另造台账。

<a id="按依赖决定怎么拆"></a>

## 2. 拆工作，不拆掉主线责任

| 当前需要 | 先选 | 交回后谁继续 |
|---|---|---|
| 小改动、步骤共享大量状态 | 一位 Agent 连续实现 | 原主线完成检查与交付 |
| 独立查代码、日志或风险 | 原生子代理，交结论与证据入口 | 主线核事实，再作共享决定 |
| 几项可独立写入的实现 | 每个写入面一个写者，需要隔离时用 worktree | 主线按依赖整合并验最终版本 |
| 持续互相协调、自主认领共享任务 | 原生能力不够时再试 Teams 等编排 | 仍指定完整目标的负责人 |
| 跨进程保存在途工具调用 | 确有缺口才评估耐久宿主 | 先核调用是否完成，再决定续跑 |

**先对齐接口、数据含义和失败行为，再并行写。** 文件不同不代表决定独立；worktree 也不隔离端口、数据库、依赖或服务。所需未跟踪资料和环境要各自准备。Python editable 开发尤其要用测试的同一解释器核实际模块来源，避免在新树测到主检出；[命令、wheel 与 namespace 边界](../08-multi-agent.md#11-python-worktree确认测试实际导入哪份代码)按需读。

**后续任务真被依赖卡住时，先交能开工的最小产物，不等整个子任务完成。** 例如先交固定接口、样例数据和一个已过的最小测试，带上版本、已有检查和仍会变的部分；消费方核完就开工，替换时通知对方，主线仍按同一最终验收规则收口。只在已有职责和写域内试，按首个可用产物、消费方开工、最终通过三个时点看等待是否减少，费用记整个任务。

依据：[DeLM v3 作者对照](https://arxiv.org/html/2606.10662v3#S3.SS5)在 10 项选定长任务固定两代理实现，撤掉提前交付后，相对单代理的提速从 Astra 的 1.54 倍和 Opus 的 2.02 倍降为 0.98 倍和 0.93 倍；[Astra 整题费用](https://arxiv.org/html/2606.10662v3#S3.SS1)则从单代理 $9.01 升至两代理 $13.65。论文按模型运行时间统计且每个代理各交完整解；仅借先交可用依赖的做法，不能预计项目的实际验收时间或成本，2026-11-22 核原文，未在本仓采用。

**启用 worktree 后，先核它从哪一个提交开始。** 有指定基线时，首次回执用 `git rev-parse HEAD` 核起点；任务只要求包含某个上游提交时，用 `git merge-base --is-ancestor <必需SHA> HEAD`。若祖先检查返回 1，先用 `git rev-parse --is-shallow-repository` 确认是否浅克隆：即使两个 SHA 都能读到，必要父链未取全也只能记未证实，先在已有足够历史的审查检出核同一对 SHA。确认实际基线不符后，再保留现有改动、停相关写入并另建隔离树；不一律改用最新 main。不要根据错误树里没找到文件就改实现。

依据：[Hermes 使用者遇到旧锚点](https://github.com/NousResearch/hermes-agent/issues/146056)与[固定版的创建代码](https://github.com/NousResearch/hermes-agent/blob/aeb5a071069dbd85d85f2c8d44337f16df29d475/hermes_cli/kanban_db_workspace.py#L689-L704)。2026-11-21 在真实源码中调用创建函数：旧锚点创建成功但落后两提交，不包含指定的 [回归提交](https://github.com/NousResearch/hermes-agent/commit/26264afd174206eb3b2c5be3f4ea976a554c7a18)；按已获取的基线 SHA 另建时，祖先检查通过且找到该测试。验证的是起点与测试文件，不是测试运行或守护进程的接续。 另用本仓相隔两提交实跑 [Git 浅历史](https://git-scm.com/docs/shallow)边界：只取两端时关系检查退出 1，补齐中间历史后同一对 SHA 退出 0，实际 HEAD 未变。

已有 Git 和准备脚本够用就沿用。具体缺口才试 [Worktrunk 的依赖准备](../../experiments/worktrunk-ready.md)、[Portless 的端口与状态隔离](../../experiments/portless-state-isolation/README.md)或 [gh-stack 的依赖分支](../../experiments/gh-stack-submodule/README.md)。Teams 仍属实验功能，`/resume`／`/rewind` 不恢复 in-process 队员；普通具名子代理也可能互发消息，不能仅凭这一点选 Teams。

**依据**：[官方能力] [子代理与主循环](https://code.claude.com/docs/en/sub-agents#choose-between-subagents-and-main-conversation)、[Teams 比较与限制](https://code.claude.com/docs/en/agent-teams#compare-with-subagents)、[Pi Durable](https://earendil.com/posts/pi-durable/)，复核 2026-11-01；[使用反馈] [worktree 资料缺失](https://v2ex.com/t/1243449)，原核实 2026-10-26。工具试用范围与日期保留在对应入口，未比较整套编排的同任务收益。

## 3. 离开前，先看一次真实结果能否接回

**拿当前任务的第一个独立单元检查交接，不为测试制造中断或新建调度。** 用宿主已有且获准的运行入口，核以下三件事：

1. **工作确实执行。** 有本次工具返回、实际进程或新产物；只有 ready／running 标签不算。
2. **主线确实接收。** 结果回来后，主线实际读取产物和检查结果，作接收或返工决定；不是只看到通知、输入已送达或一句完成摘要。
3. **下一步确实开始。** 原目标还有剩余时，主线实际启动下一项实施或验收。保留原任务入口、版本和这一动作的证据，别把写下计划当已经续接。

只有前两项时，可把它当“一次后台任务已接回”；第三项尚无证据，就保留“持续自动续接未验”。本机需跨回合运行时，另核现有接收器／调度器是否保持工作、结果由谁接收；没有配置可用的触发入口就先按有人接回使用。不要靠不断发“继续”、重复派任务或增加权限补出一次伪无人值守测试。

**会话意外退出后，先核关键结果有没有落盘，不凭通知或恢复成功重派。** 将不可丢的子任务结果写到项目已有且获准的交付位置，通知只带位置与版本；恢复后先找产物，再核旧写者。用 Linux 上官方 Claude Code 2.1.329 和本地模拟提供方复跑[公开四组对照](https://github.com/anthropics/claude-code/issues/111391)：普通后台子代理的 `SendMessage` 与自动完成通知各跑两组。接收进程在消息仅入队时被强制终止，同一会话恢复成功但两条消息均未重放；终止前已进入主会话输入并写入历史的两条均保留。2026-11-21 复跑；未验正常退出、远程会话或 Teams。

**Claude Code 子代理列表只有计时，不等于停了。** 先打开原子代理的详情，再判断是否该派替换任务。[使用者对照](https://github.com/anthropics/claude-code/issues/96231#issuecomment-7054371849)中，macOS 的 2.1.330 在已启用 retry watchdog、模拟服务只对子代理返回额度 429 时，详情显示等待重试的倒计时，父列表仍只有计时；2.1.301 的详情也只显示转圈。这个对照只验证了状态显示，不保证实际恢复。

**把 `claude -p` 的输出重定向到文件时，接收本轮新文件，不只看退出码。** 保留 stderr，按任务契约核输出可读、完整，内容确实对应本轮；空文件、旧文件或截断输出不算交付。2026-11-22 用官方 Linux 二进制和同一回环合成响应复跑：2.1.329 与 2.1.330 写普通文件都退出 0 并留下完整文本；stdout 改到 `/dev/full`（模拟写入返回 ENOSPC，不填真实磁盘）后，两版仍各收到一次有效响应，但 2.1.329 静默退出 0，2.1.330 报错退出 1。依据：[2.1.330 发布说明](https://github.com/anthropics/claude-code/releases/tag/v2.1.330#whats-changed)，满 NFS 是上游注明的例外，本次未测 NFS。

**命令转后台后，按原 ID 收子进程退出码，不重跑。** OpenCode 2.3.1 的前台等待超时后，工具可以已是 `completed`，原命令却仍是 `running`。保留 shell ID，等同一 ID 的终态并核命令自己的退出码；外层 CLI 退出 0 不算命令成功。用官方 2.3.1 CLI 和本地模拟提供方，实跑两次良性命令：各自只启动一次、原 PID 不变，按原 ID 各收到一条终态，shell 分别退出 0 和 7，外层 CLI 两次均退出 0。依据：[2.3.1 发布](https://opencode.ai/changelog/v2.3.1)、[上游同进程与最终结果用例](https://github.com/anomalyco/opencode/blob/v2.3.1/packages/core/test/tool-shell.test.ts#L1442-L1545)；2026-11-21 Linux，未验断线或重启。

**Codex CLI 的 `/side` 用来短暂岔开，不当作恢复入口。** 回主线前，把需要保留的决定和产物位置写进原任务记录。0.167.0 的侧聊是临时的；0.171.0 默认开启 TUI workspace，但只有兼容的本机全屏与已保存历史才能持久化，条件不符仍可能是临时侧聊。若靠侧聊接续，先确认重启后同一侧聊能打开并接受新输入，不只看到回放。见[旧版回放案例](https://github.com/openai/codex/issues/62649)、[0.171.0 发布](https://github.com/openai/codex/releases/tag/rust-v0.171.0)与[存储选择](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/tui/src/app_server_session.rs#L1372-L1394)；核读源码，未实跑侧聊重启。

从另一台设备继续指导时，先区分[留在原主机与转移执行主机](../01-agents/codex.md#codex-remote-keep-or-transfer-host)。已有获准的 Codex app-server 和空闲原任务时，可用[原 UUID 非交互续接](../20-codex-long-horizon.md#codex-remote-resume-idle-thread)核一个剩余验收；不把这个入口当成关机恢复或自动唤醒。

<a id="旧写者状态未知时接收固定成果与接管旧树分开"></a>

需要换执行者时确认旧写者停止，再交同一写域。已正式交回的固定成果若允许独立接收，可以在新树审查整合；这不等于旧进程已退出，也不能跳过原任务明确规定的退出条件。跨宿主恢复用 [checkpoint-resume](../../templates/codex/.agents/skills/checkpoint-resume/SKILL.md)，恢复仍须实际读取当前记录和工作区。

**依据**：[宿主能力与边界](../08-multi-agent.md#21-启动与撤回后台不等于无人值守)，原核实 2026-10-15；[本仓状态实试](../../experiments/deepseek-superagent-receipt/README.md)，核实 2026-11-02：输入 delivered／read、assignment 与原任务完成分别处理，未运行 DSH／模型。这三步是据上述边界提出的本仓操作检查；本次单轮接续见 §5 的采用记录，不由此推定长期可靠性。

<a id="交出去什么收到后核什么"></a>

## 4. 接回产物，跑到真正的消费者

**先确认接的是当前任务和正确版本，再决定哪些检查要重跑。**

1. 对原目标、保留行为和撤回项，核实际 diff、基线、结果提交及其他在途写域。检查要求改动写域外的副本时，实施者交回失败输出和所需差量，由负责人确认归属，再同步或调整写域后返工，不删检查。
2. 看实际命令、退出码、原始输出、受检版本和环境；失败、跳过、零测试和未运行分开记。再按[产品承诺选最终入口与证据](verification.md#按产品承诺选证据)。要判断旧检查能否复用，或验交互下一轮、重启后读回，跟[实际消费者与差量检查](../20-codex-long-horizon.md#13-接收真实产物复用检查与消费者边界)，不只比检查器有没有改。
3. 当前宿主不能执行必需检查时，保留已验结果和未跑部分，把同一固定产物交给已有权限的合适环境补验；没有可用执行者就不算通过。只有实际观察到资源争用才错峰，不默认减并行或放宽超时。

<a id="接回之后走到当前目标的终点"></a>

## 5. 按原验收收口，不按回合收口

- **已回但未验收：** 当轮接收；有缺陷就向同任务给具体返工要求，不另派一份。
- **一个动作阻塞：** 留目标、原因和恢复条件，继续不依赖它的工作。
- **外部操作结果未知：** 按原请求查实际文件、提交或服务回执；已生效就只收结果，未知不重放。
- **还有已授权的实施或验收：** 继续原目标；子任务结束不等于任务完成。
- **已满足全部验收：** 按授权交付。发布另回读实际目标与内容，CI 按该提交的真实运行报告；未查到运行记未确认，不用发布成功替代消费者验收。
