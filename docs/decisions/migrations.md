# 遗留代码与大迁移：怎样选改法、保住原行为

**🟡 先按改动形状选迁移器，用一个真实消费者验清，再扩到其余范围。** 重复语法交现成规则，跨文件引用与类型交类型工具，Agent 处理例外；依赖升级沿项目包管理器，数据迁移沿既有受支持迁移器。协议迁移路线已有独立云端实做；其他分支按下方各例的验证范围采用。

## 第一步：给 Agent 一个真实迁移目标

准备目标仓库、要升级的版本或要替换的旧写法、已有 issue／PR。先读项目规则、核工作树与写者，再把下面这段和任务交给 Agent：

```text
在 [仓库] 完成 [旧状态 → 新状态]，保留 [必须兼容的输入、行为和数据]。
先核当前主干、在途实现和项目已有的迁移器、包管理器、检查入口。
按改动形状选路，找一个实际受影响的消费者试做，核旧行为、新行为和失败路径。
已有 PR 时只接必要差量，保住主干后来增加的功能与测试，不整份覆盖旧文件。
试做后列出已改、未改和例外；覆盖明确且消费者通过，再完成剩余范围并验整合结果。
交回 diff、真实入口结果和未验项。数据操作先在合成数据或获准副本验证恢复，
不把 reset／seed 当迁移，不自动扩大到真实数据、生产部署或外部投稿。
```

**第一轮应得到可运行的局部结果和明确的扩量依据。** 缺依赖先在当前授权范围内按项目支持方式准备；无法准备时记精确缺口。不要把安装失败归为迁移失败，也不要用依赖桩、编译成功或 Agent 的完成自报代替消费者验收。

## 按改动形状选路

| 你的任务 | 起步选择 | 必须看到的结果 |
|---|---|---|
| 大量相同语法／API 写法 | 官方 codemod 或已有语法规则先试代表性文件，Agent 处理规则外语义 | 核已改、未改、警告和例外；再验相关行为。零命中先查是否根本无需改写 |
| JS→TS、重命名、跨文件引用 | 用类型／框架工具定位改动；有预览先核编辑清单，再跑严格检查 | 开发与发布入口都找到正确文件，类型符合真实返回值，构建产物能运行 |
| 发布库的公开 API 变化 | 先用语言生态的兼容检查定位，再用同一旧调用方对照两个版本 | 编译破坏与行为变化分开核；warning、库自身构建成功或改检查基线都不能代替消费者兼容 |
| 依赖大版本升级 | 先核已有迁移与跨过的版本指南；用项目声明的包管理器更新依赖和锁文件 | 真实 client 能构造、请求与消费者契约保留，锁文件可复用；已有失败与新增失败分开 |
| 同一依赖分阶段切换，部分环境仍跑旧版 | [先核每个环境实际解析的 runtime 与 adapter](#导入已换新运行时可能还没换)，保留并行期必要检查 | 各环境产物与消费者对应预期版本；全部支持范围切完，才撤旧版与临时检查 |
| 协议升级，要兼容两代客户端 | 分别固定旧／新协议，运行项目真实入口，有构建步骤先构建；已有实现只接目标 server 的差量 | 两代真实调用各自通过，旧版失败路径与状态隔离保留；自动回退后的成功不能证明新协议可用 |
| 带持久数据的结构变化 | 保留受支持迁移器，先确认写入者、事务边界与恢复点 | 关闭后重新打开，业务行和 schema 都符合预期；失败回滚与后续读写分别验证 |

**已有迁移先接收，不从零重写。** 固定当前主干与原实现的提交，把必要差量适配到主干；捆绑的依赖、打包和 CI 改动另判是否需要。测试风格迁移也属于第一行，但要逐项保留子场景、异常、对象身份、日志与 fixture 重置语义，不能用测试总数相同证明等价。

**依据**：语法、类型、依赖与数据的选择来自已接收的[迁移指南材料](../collaboration/local-jobs/artifacts/A-LEGACY-MIGRATION-GUIDE-20261030/candidate.md)和[15 §5 的同题比较](../15-task-playbooks.md#5-大规模迁移与升级)。材料原核实 2026-10-30，2026-11-01 加入 Hermes 实作与 Extruct 读者卡点；协议分支的新增复现见下。没有新增工具排名或净提效结论。

## 真实任务告诉你该验哪里

### 自动协商成功：还要固定新版客户端

MCP sequentialthinking 的同一 SDK 2.3.1 下，旧入口能服务旧协议，新版需接入 `serveStdio`。固定 #5131 的单 server 差量后，构建产物在旧／新协议下都能保留两轮 thought、拒绝缺参数并从新连接重新计数；迁移前固定新版会明确拒绝，原生 101 项测试通过并不代表支持新协议。

**照这个顺序做：固定两代协议 → 验基线消费者 → 接必要入口差量 → 有构建先构建，重启真实入口 → 重跑相同消费者。** TypeScript SDK 2.3.1 固定新版使用 `mode: { pin: "2026-07-28" }`；Python mcp 2.3.0 则用 `mode="2026-07-28"`，旧代用 `mode="legacy"`。`auto` 能回退，只验请求成功会漏掉新版仍不支持；Python 显式新版模式还可能合成 discovery 信息，所以要同时核实际 `tools/list` 和工具调用，不能只看客户端版本字段。

**按实际交付形式验收。** Python time 开发态的 editable 安装可在修改后直接重启 `python -m mcp_server_time`；按 wheel 交付时，必须重建并在独立环境安装该 wheel。验收时离开源码目录、清除 `PYTHONPATH` 并核实际导入位置，再分别测试模块与控制台入口，避免用源码通过替代发行包通过。

**依据与复跑入口**：[固定版本、命令和真实 stdio 消费者](../../experiments/mcp-protocol-migration/README.md)，2026-11-07：作者完成 sequentialthinking；time 首轮读者的语言／启动入口卡点修正后，另一独立云读者只照修订页，在 Python 3.10.22、mcp 2.3.0 下实做基线与四文件迁移。两代工具调用、错误分层与新进程连接通过，基线 122／候选 133 项原生测试及静态、构建、覆盖门槛通过，零 skip。[本机 V2](../collaboration/local-jobs/A-MCP-TIME-MIGRATION-READER-V2-20261107.md)缺依赖及已安装控制台入口，且禁止安装；两代真实 stdio、原生测试及 Ruff／Pyright 均未运行（`taskDone=false`），云端结果不替代它。2026-11-08 又在独立环境安装 time 两版 wheel，候选的模块与控制台入口均通过两代消费者，基线仍明确拒绝新版；两包版本号相同，须核实际安装产物。这里只证明两个 server 的局部复现，不是新的上游采用；HTTP、LLM 客户端及全发布门槛未验。

### 导入已换新：运行时可能还没换

**👀 分阶段升级时，先让 Agent 查清每个环境真正运行哪一版，再决定能否用新 API。** Sentry 曾先改为 React Router V8 的导入路径，却通过兼容层继续运行 V6；下一阶段的构建默认仅本机开发用 V8，生产与 preview 仍用 V6，应用测试和类型检查另按两版跑。只看 import 或一份 `package.json`，都会选错行为和检查。

1. **沿真实入口查解析。** 列出项目实际使用的开发、构建、preview、CI 与测试入口，追构建 alias、测试 resolver、类型映射和配套 adapter；写清每个入口对应的 runtime、允许的 API 与检查命令。测试 runner 的版本覆盖单独核。共用代码须兼容所有仍支持的 runtime；新版独有 API 只用于已验证的新版专用路径，或等相关入口全部切换后再用。
2. **每版检查产物与消费者。** 对照预期主版本，核产物有没有混入另一版、adapter 是否匹配；依赖共享 context 时再核实例身份。Sentry 的构建测试还加载产物，检查路由参数、查询串与返回导航；这比只看类型检查或应用启动更接近原目标。
3. **全部受支持入口切完，再清迁移支架。** 清旧依赖、别名、兼容映射及专为双版本增加的 runner／CI 检查，同时改共享指令；保留业务回归、分片和仍有消费者的兼容行为。最后切换与清理可在同一补丁内完成，不能只因双跑成本高就提前删旧支持。

把下面这段补到本次迁移任务中，不给单版本升级增加双矩阵：

```text
先列本项目各入口的实际 runtime、adapter、允许 API 和原生检查命令，标明解析依据。
导入改名不等于行为升级。按仍支持的版本验证构建产物和一个真实消费者，
包括失败路径；只有全部受支持入口切到新版，才删除双版本支架并更新共享指令。
交回各入口已验／未验项，不把静态映射当运行结果。
```

**依据**：[Sentry 首阶段指令](https://github.com/getsentry/sentry/blob/8891ab865ca741f83cbcd20349bd21c03ad92ffc/static/AGENTS.md#L30-L39)、[阶段二环境选择](https://github.com/getsentry/sentry/blob/9d75e921c32de2d4c122fbc5e4cff39d16175172/build-utils/react-router.ts#L8-L39)与[构建消费者断言](https://github.com/getsentry/sentry/blob/9d75e921c32de2d4c122fbc5e4cff39d16175172/build-utils/react-router.test.ts#L28-L162)、[双版应用测试](https://github.com/getsentry/sentry/blob/9d75e921c32de2d4c122fbc5e4cff39d16175172/scripts/testCi.js#L18-L31)与[类型检查](https://github.com/getsentry/sentry/blob/9d75e921c32de2d4c122fbc5e4cff39d16175172/scripts/typecheck.ts#L56-L81)、[完成切换并撤除支架](https://github.com/getsentry/sentry/commit/de3060f736c6dd55836bfae104336a967ec41d8d)。已有候选原核实 2026-11-03，2026-11-08 复核固定源码；这是已完成迁移的历史机制，不是建议 Sentry 继续 V6。本仓未运行该迁移或完成此分支的新读者实做，未验证净收益。

### 公开 API：库能构建，旧调用方仍可能坏

**让 Agent 改公开 API 时，把原消费者的输入、调用方式与检查命令一起交给它。** 在两个独立消费者副本里保留同一源码与检查命令，只切换目标库版本并更新相应锁文件。Rust 库已安装 cargo-semver-checks 时，从新版库目录运行 `cargo semver-checks -p <crate> --baseline-root <旧版源码目录> --color never`（先替换占位符，含空格的路径加引号），再分别进入消费者目录运行 `cargo check --locked`。固定源码、工具链和所需 features；多 crate 各选自己的基线。工具未覆盖或跳过的检查仍是未验，纯内部改动不用统一增加这一关。

**编译错误按原调用定位，行为警告回真实输入验证。** librouting 的 `lr-bgp` 新增公开枚举分支后，自身构建成功，但原 23 分支穷尽匹配消费者从通过变为 E0004；同次 PartialOrd warning 却未证明旧值排序改变：显式 discriminant 下，278 个旧值的 77,284 对比较结果一致。不能为消警告擅自改排序、加兜底分支或抬高检查基线；要保兼容就调整库侧方案并重验原消费者；已决定接受破坏性升级，再迁移调用方并保留回归。

**依据与复跑入口**：[固定版本、同一消费者与两类结果](../../experiments/rust-semver-consumer/README.md)，2026-11-05 Linux 实测；cargo-semver-checks 0.51.0、Rust 1.99.0，工具报 1 fail／1 warn／31 skip。消费者是针对真实 API 写的最小下游探针，不是已有第三方应用；只验证固定历史两版、一个 crate 和所列 features，未证明完整工作区或运行时兼容，也未完成本分支的独立照做验收。

## 什么时候停扩量或保留旧实现

- **规则漏改、额外改动或例外增多**：先修规则或退回局部 Agent 补丁，覆盖清楚后再扩量。
- **消费者或新主干行为未保住**：先修适配，不删测试、放宽断言或拿旧文件覆盖主干。
- **目标包含 UI、旧缓存或持久数据，但缺对应验收**：保留旧实现或旁置候选，不用工程检查替目标通过。
- **已经写入新状态**：回退前明确恢复点与将丢的新增数据；依赖补丁反向应用不恢复数据库。无法安全回退时保状态继续修复。

批量与并行只在迁移单元可独立接收时增加，见[15 §5 的执行与恢复边界](../15-task-playbooks.md#5-大规模迁移与升级)。本页保持 🟡：协议路线的独立实做支持固定两代客户端与只接必要差量的选择，尚不覆盖其他迁移分支。Extruct 首轮读者的选路与旧 PR 卡点已回流，其任务后来取消，不算完整通过，也不重启原任务。
