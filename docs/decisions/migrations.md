# 遗留代码与大迁移：怎样选改法、保住原行为

**🟡 先按改动形状选迁移器，用一个真实消费者验清，再扩到其余范围。** 重复语法交现成规则，跨文件引用与类型交类型工具，Agent 处理例外；依赖升级沿项目包管理器，数据迁移沿既有受支持迁移器。协议迁移路线已有独立云端实做；其他分支按下方各例的验证范围采用。

## 第一步：给 Agent 一个真实迁移目标

准备目标仓库、要升级的版本或要替换的旧写法、已有 issue／PR。先读项目规则、核工作树与写者，再把下面这段和任务交给 Agent：

```text
在 [仓库] 完成 [旧状态 → 新状态]，保留 [必须兼容的输入、行为和数据]。
先核当前主干、在途实现和项目已有的迁移器、包管理器、检查入口。
按改动形状选路，找一个实际受影响的消费者试做，核旧行为、新行为和失败路径。
已有 PR 时只接必要差量，保住主干后来增加的功能与测试，不整份覆盖旧文件。
试做后列出已改、未改和例外；覆盖明确且消费者通过，再完成剩余范围并验整合结果。
交回 diff、真实入口结果和未验项。数据操作先在合成数据或获准副本验证恢复，
不把 reset／seed 当迁移，不自动扩大到真实数据、生产部署或外部投稿。
```

**第一轮应得到可运行的局部结果和明确的扩量依据。** 缺依赖先在当前授权范围内按项目支持方式准备；无法准备时记精确缺口。不要把安装失败归为迁移失败，也不要用依赖桩、编译成功或 Agent 的完成自报代替消费者验收。

## 按改动形状选路

| 你的任务 | 起步选择 | 必须看到的结果 |
|---|---|---|
| 大量相同语法／API 写法 | 官方 codemod 或已有语法规则先试代表性文件，Agent 处理规则外语义 | 核已改、未改、警告和例外；再验相关行为。零命中先查是否根本无需改写 |
| JS→TS、重命名、跨文件引用 | 用类型／框架工具定位改动；有预览先核编辑清单，再跑严格检查 | 开发与发布入口都找到正确文件，类型符合真实返回值，构建产物能运行 |
| 依赖大版本升级 | 先核已有迁移与跨过的版本指南；用项目声明的包管理器更新依赖和锁文件 | 真实 client 能构造、请求与消费者契约保留，锁文件可复用；已有失败与新增失败分开 |
| 协议升级，要兼容两代客户端 | 分别固定旧／新协议，运行项目真实入口，有构建步骤先构建；已有实现只接目标 server 的差量 | 两代真实调用各自通过，旧版失败路径与状态隔离保留；自动回退后的成功不能证明新协议可用 |
| 带持久数据的结构变化 | 保留受支持迁移器，先确认写入者、事务边界与恢复点 | 关闭后重新打开，业务行和 schema 都符合预期；失败回滚与后续读写分别验证 |

**已有迁移先接收，不从零重写。** 固定当前主干与原实现的提交，把必要差量适配到主干；捆绑的依赖、打包和 CI 改动另判是否需要。测试风格迁移也属于第一行，但要逐项保留子场景、异常、对象身份、日志与 fixture 重置语义，不能用测试总数相同证明等价。

**依据**：语法、类型、依赖与数据的选择来自已接收的[迁移指南材料](../collaboration/local-jobs/artifacts/A-LEGACY-MIGRATION-GUIDE-20261030/candidate.md)和[15 §5 的同题比较](../15-task-playbooks.md#5-大规模迁移与升级)。材料原核实 2026-10-30，2026-11-01 加入 Hermes 实作与 Extruct 读者卡点；协议分支的新增复现见下。没有新增工具排名或净提效结论。

## 真实任务告诉你该验哪里

### 自动协商成功：还要固定新版客户端

MCP sequentialthinking 的同一 SDK 2.3.1 下，旧入口能服务旧协议，新版需接入 `serveStdio`。固定 #5131 的单 server 差量后，构建产物在旧／新协议下都能保留两轮 thought、拒绝缺参数并从新连接重新计数；迁移前固定新版会明确拒绝，原生 101 项测试通过并不代表支持新协议。

**照这个顺序做：固定两代协议 → 验基线消费者 → 接必要入口差量 → 有构建先构建，重启真实入口 → 重跑相同消费者。** TypeScript SDK 2.3.1 固定新版使用 `mode: { pin: "2026-07-28" }`；Python mcp 2.3.0 则用 `mode="2026-07-28"`，旧代用 `mode="legacy"`。`auto` 能回退，只验请求成功会漏掉新版仍不支持；Python 显式新版模式还可能合成 discovery 信息，所以要同时核实际 `tools/list` 和工具调用，不能只看客户端版本字段。Python time 无需 TypeScript 式重建，按项目安装后重启 `python -m mcp_server_time`；原生套件另核控制台入口。

**依据与复跑入口**：[固定版本、命令和真实 stdio 消费者](../../experiments/mcp-protocol-migration/README.md)，2026-11-07：作者完成 sequentialthinking；time 首轮读者的语言／启动入口卡点修正后，另一独立云读者只照修订页，在 Python 3.10.22、mcp 2.3.0 下实做基线与四文件迁移。两代工具调用、错误分层与新进程连接通过，基线 122／候选 133 项原生测试及静态、构建、覆盖门槛通过，零 skip。[本机 V2](../collaboration/local-jobs/A-MCP-TIME-MIGRATION-READER-V2-20261107.md)缺依赖及已安装控制台入口，且禁止安装；两代真实 stdio、原生测试及 Ruff／Pyright 均未运行（`taskDone=false`），云端结果不替代它。这里只证明两个 server 的局部复现，不是新的上游采用；独立安装 wheel、HTTP、LLM 客户端及全发布门槛未验。

### 规则零命中：保留仍兼容的生成代码

Memoh 的 Pinia Colada 0.21.2→1.4.8 升级中，官方规则零命中，原调用不需要该语法转换。149 个生成定义继续通过新版本类型检查，实际只改四个依赖／锁文件；重生成它们没有已证明的收益。

**照这个顺序做：查调用形状 → 更新声明与锁文件 → 验实际消费者 → 核遗漏与已有失败。** 如果目标包括旧缓存兼容，另验同一 profile／origin／会话跨版本的恢复与重新请求。该例类型、构建和相关单测通过，页面与旧缓存未验，全量测试也不是全绿；不能当作完整产品升级已通过。

**依据与复跑入口**：[固定补丁、版本、命令和已知失败](https://github.com/dbvv1/a1dbv/blob/98e7a5987223474ad008140e0dd8ea86a1458dd6/docs/collaboration/local-jobs/A-MIGRATION-ADOPTION-001.md#应用方式与回滚)，2026-10-25 实测。完整产品 QA 后来已取消，不据此重启旧任务。

### 编译通过：还要核真实值与发布产物

Actual 的配置迁移里，LSP 重命名预览报告 success，却没有任何编辑；真正推进的是显式核开发／发布 alias、严格类型检查和运行值断言。被误当作元数据的 `doc` 实际在返回对象里，是字符串字段；正确做法是修类型，保留运行行为。

**照这个顺序做：核实际编辑与 alias → 用真实值定类型 → 修消费者 → 运行构建产物。** 该例 36 项相关回归、typecheck、lint、SSR build、启动与健康检查通过；全量依赖安装、浏览器与完整产品 QA 没有通过结论。

**依据与复跑入口**：[Actual 固定补丁、公开同树与消费者验收](../../experiments/actual-config-type-migration.md)，2026-10-26 实测；原上游投稿已取消。

### 旧 PR 可用：接回新主干仍要验请求

Hermes 的 Anthropic SDK v1 迁移已有实现，但旧 PR 的依赖文件与新主干冲突。接收时只移植必要源码与两处版本 pin，用当前项目包管理器生成锁文件，保住新主干后来增加的 Bedrock timeout 参数和其他依赖。

**照这个顺序做：验固定 PR → 对照当前主干差量 → 适配并生成锁文件 → 验真实 client 与请求。** 该次适配的 178 项相关测试与 14 项原生静态检查通过；请求用真实 SDK 加合成传输核认证头。Mock 返回 200 不能证明请求正确，v1 通过也不证明 v2 可用。没有验证线上 provider、完整 Hermes 或发布矩阵。

**依据与复跑入口**：[固定补丁、隔离环境和完整命令](../../experiments/anthropic-sdk-migration/README.md#hermes-v1-在途迁移接收旧-pr-时保住新主干)，2026-11-01 Linux 实测；这里只引用固定版本结果，不断言 PR 当前状态。

### 事务没报错：重新打开检查业务行

SQLite 父表重建曾级联删掉三条子记录，外键检查仍为空。接收后的实现会拒绝同一危险事务；验证不仅看异常，还重开数据库逐行核数据、schema、STRICT 与后续级联。

**照这个顺序做：确认停写／桥接与事务边界 → 验失败恢复 → 重开核业务行和约束 → 验成功迁移及后续读写。** 只改列名先用原生重命名；整批父子表转换的外键与事务安排按下面实作入口，不在已开始的事务里尝试关闭外键。已有回滚输出和成功阶段的新结构是两种预期，分开接收。

**依据与复跑入口**：[SQLite 关联表实作与合成数据库检查](../research/2026-10-23-sqlite-migration.md)，2026-10-23 实测。未验生产并发、崩溃耐久、真实数据或复杂 schema；不能据此省去生产恢复演练。

## 什么时候停扩量或保留旧实现

- **规则漏改、额外改动或例外增多**：先修规则或退回局部 Agent 补丁，覆盖清楚后再扩量。
- **消费者或新主干行为未保住**：先修适配，不删测试、放宽断言或拿旧文件覆盖主干。
- **目标包含 UI、旧缓存或持久数据，但缺对应验收**：保留旧实现或旁置候选，不用工程检查替目标通过。
- **已经写入新状态**：回退前明确恢复点与将丢的新增数据；依赖补丁反向应用不恢复数据库。无法安全回退时保状态继续修复。

批量与并行只在迁移单元可独立接收时增加，见[15 §5 的执行与恢复边界](../15-task-playbooks.md#5-大规模迁移与升级)。本页保持 🟡：协议路线的独立实做支持固定两代客户端与只接必要差量的选择，尚不覆盖其他迁移分支。Extruct 首轮读者的选路与旧 PR 卡点已回流，其任务后来取消，不算完整通过，也不重启原任务。
