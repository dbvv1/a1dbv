# 强弱模型、推理档位和成本怎么选

**保留已达标配置；新任务用 Sol 6.1＋`medium` 或 Sonnet 5.5＋`medium` 起步，把更高投入留给难题和质量审查，把规格明确的重复工作交给轻量模型。** 🧪 这是可试的任务分工：先用现有验收检查结果，再决定保留。日常起点沿用 [02 的选择](../02-models-and-cost.md#1-原则按任务分档而不是追榜单)，当前模型的通用最佳搭配与本仓净收益仍未知。

## 第一步：只改这一次任务

**在已有项目和已能使用的客户端里，按工具二选一启动；不用先改全局配置。**

```bash
# Codex
codex --model gpt-6.1-sol -c 'model_reasoning_effort="medium"'

# Claude Code
claude --model claude-sonnet-5-5 --effort medium
```

给它一个正在做的功能或修复，带上目标、必须保留的行为和已有检查命令。Codex 的 `-c`、Claude 的 `--effort` 都只覆盖本次启动；型号与档位须在当前账号和客户端可用，Sonnet 5.5 要求 Claude Code v2.1.284+。使用第三方 Claude 提供方时，以其实际模型 ID 为准。

**依据**：[官方配置] [Codex 单次覆盖](https://learn.chatgpt.com/docs/config-file/config-advanced#one-off-overrides-from-the-cli)、[Claude CLI 参数](https://code.claude.com/docs/en/cli-reference)、[Claude 型号与版本要求](https://code.claude.com/docs/en/model-config#model-aliases)；核实 2026-10-26。命令参数已核文档与本地 Codex 帮助，未启动模型任务。

## 按任务分配，而不是全员一起升档

| 眼前的工作 | Codex 起点 | Claude Code 起点 | 保留这项选择的条件 |
|---|---|---|---|
| 范围清楚的功能、测试与日常协调 | Sol 6.1＋`medium` | Sonnet 5.5＋`medium` | 能按现有要求交付，检查与返工可接受 |
| 跨文件审查、追调用链、查边界遗漏 | 同模型试 `high` | 同模型试 `high` | 找到更多可核实的问题或补足关键验证；协调器无需跟着升档 |
| 架构取舍、跨模块疑难 bug、复杂重构 | Astra＋`low`（Light）起步 | Opus 5.5＋`medium`；重验证可试 `high` | 有明确的推理或质量需要，可以直接选，不必先用轻量模型失败一次 |
| 明确的检索、提取、按既有模式批量小改 | Luna＋`high` | Haiku 5.5＋`medium` | 输出容易核对；发现遗漏或返工抵消节省就恢复原配置 |

**先补缺上下文和有效检查，再判断能力缺口。** 子 Agent 也按任务难度选：探索未知根因、解决矛盾证据，不能仅因它是“子任务”就降档。Codex 子 Agent 未显式配置时继承父级模型与 effort；分档时明确指定该角色的两项设置。需要额外角色时用[原生委派](../08-multi-agent.md#6-操作手册从一个大任务到并行执行)，已有单 Agent 能完成的工作保持原样。

Codex 的 Sol effort 默认随客户端而异；这里明确选 `medium` 是本页起点。Luna 的 `high`、Astra 的 `low` 来自官方起步建议；同名 effort 不能跨模型当成同等投入。

**依据**：[官方任务定位与档位] [OpenAI Models](https://learn.chatgpt.com/docs/models#pick-a-reasoning-effort)、[子 Agent 模型选择](https://learn.chatgpt.com/docs/agent-configuration/subagents#choosing-models-and-reasoning)、[Claude effort](https://code.claude.com/docs/en/model-config#choose-an-effort-level)；[既有判断](../02-models-and-cost.md#1-原则按任务分档而不是追榜单)，原核实 2026-10-22；官方入口重核 2026-10-26。

## 先委派哪种小任务，何时收回

**先委派输入固定、做法明确、结果能逐项核对的执行单元；负责人保留取舍与最终接收。** 下列两类已有真实接收结果，可作为尝试轻量模型的任务起点，保持原验收标准：

| 可以先交出去 | 派发时写清 | 负责人怎样接收 |
|---|---|---|
| 按现成命令提取固定提交的 CI 状态 | 完整 SHA、三个来源、只读入口；保留 `query_scope`、计数、原状态与 `description`；原响应留到接收 | 对照原响应和实际投影，核对“成功但跳过审核”、零记录、`action_required`；收数据，不让执行者代定能否合入 |
| 有明确输入契约的小修复与回归 | 独占实现／测试文件，给失败输入、必须保留的合法输入与检查命令 | 从真实 CLI 重放非法与合法输入，再跑定向回归；本仓 JSON 语法修复由负责人重放 25 项 CLI 输入与 9 项回归后接收 |

**看见以下信号就改变接法，先别把问题都归为模型不够强：**

| 可观察信号 | 下一步 |
|---|---|
| 数据提取正确，但指定文件没改、必需字段仍缺 | 只接收已核数据，退回未完成的交付；把下一单改成定点编辑，核实际 diff |
| 已明确要求复用保留结果，执行者仍重新采集、重复做原流程 | 请求停止并核终止回执；确认旧写者已停后，负责人收回修订或换成只编辑产物的任务，复用证据 |
| 读者看过旧答案或历史验收记录 | 可用的运行结果单独接收；盲读验收保持待补，等下一真实任务交给未接触答案的新上下文 |
| 缺运行时、权限或输入；上下文补齐后仍反复误解契约 | 前者先补实际缺口；后者再按上表提高对应角色投入，并保留同一验收 |

CI 读者任务中，Memos 的状态与跳过说明被正确区分；Datasette 的数据由负责人重放确认，但读者读过旧记录，盲读验收未通过。随后一个交付补项连续两轮重新取数、只增读者记录，仍未补 `result.md` 的 `query_scope`；任务卡已标为 `cancelled`，现有记录缺少接收端终止回执，实际停止状态未知。保留取消记录与原证据，确认终止且没有其他写者后，再派发定点修订：

```text
这轮只修结果文件，不再做读者实测。
从已保留的投影补齐 result.md 三来源的 query_scope，保留原观察时间与其他已核结果。
不新增 CI API 调用；保留件不可用时指出缺哪份输入，交负责人决定。
交付实际 diff，并逐源核对新增字段；原读者与复核记录保持不动。
```

**依据**：[本仓真实委派与接收] [CI 结果与盲读卡点](../collaboration/local-jobs/A-CI-PROJECTION-READER-20261027.md)、[停止重复修订的记录](../collaboration/local-jobs/A-CI-EXACT-SHA-READER-20261028.md)、[JSON 修复接收](../collaboration/local-jobs/A-JSON-SYNTAX-READER-001.md)；核读 2026-10-28。记录支持上述任务划分与收回信号；模型档位、总耗时与返工成本尚无同题比较，轻量模型的净收益仍待实际任务验证。

## Cloudflare 实际怎么配：审查升档，协调不跟涨

**借它按角色取舍的方法，不照搬整套配置。** Cloudflare 的生产代码评审链在 10 月复盘中公布了这些实际选择：

| 角色 | 复盘时配置 | 为什么值得借鉴 |
|---|---|---|
| 协调器 | Opus 5.5＋`medium` | 同模型升到 `high` 增加成本，未带来有意义的发现增量 |
| 代码质量审查 | Sonnet 5.5：从 `medium` 转向 `high` | 随机分流后，高档产生更多被作者后续修改的发现 |
| 安全、性能审查 | Sonnet 5.5＋`medium` | 裁判评估的重要性能发现减少，团队计划继续试高档；这两项不宜直接当作低档成功样板 |

这里的“被采用”以作者后续修改被标行衡量，另有模型裁判；最新观察窗口很短。可借的结论是**分别看每个角色的重要发现和总投入**，而不是看到整条链降本就认定所有角色质量都保住了。

**依据**：[一手／采用团队生产自报] [Cloudflare 工程复盘](https://blog.cloudflare.com/obsessive-inference-optimization/)，2026-10-19 发布、2026-10-26 重核；独立于被比较模型厂商。细节与指标限制见 [02](../02-models-and-cost.md#当前最高水平为质量缺口分配投入而不是统一加档)。

## 成本高时，先改哪一项

**看一项工作被接收前的全部投入：主 Agent、子 Agent、重试、检查和返工。** 第一步只处理眼前的主要浪费，不为省费先装路由器或新建评测框架。

- **重复读长材料、重复派同一调查**：先收窄输入与分工；长会话中途只换 effort 时，核对[保缓存入口](../02-models-and-cost.md#同模型换推理档保留缓存前缀)。
- **规格明确的大量小活**：试表中的轻量档，保持原验收标准；新增加的复核与修补要一起算。
- **任务本身难、不断返工**：提高相应角色的 effort 或直接用更强模型，别只压单价。
- **质量已达标，只是等得太久**：再比较提速选项；模型、effort、速度模式分开选择。订阅额度、额外 credits 与 API 计费按实际入口核对。

真实使用反馈也有分歧：V2EX 的 ezioswj 自述用 Sol 开荒、将路径明确的工作交给 Luna；另一位用户报告 Sol 6.1 `low` 仍慢、额度消耗高。它们适合提醒你检查自己的任务形状，不能据此估算能用几天或承诺某档更省。

**依据**：[社区原帖] [V2EX：模型分工（#2）](https://www.v2ex.com/t/1247018)、[V2EX：低档仍慢的反馈](https://www.v2ex.com/t/1248411)；[官方计费入口] [OpenAI Work／Codex](https://learn.chatgpt.com/docs/pricing)、[Claude API 分项计费](https://platform.claude.com/docs/en/about-claude/pricing)；核读 2026-10-26。

## 何时不适用

- **当前配置稳定达标**：保持；新模型名与更高 effort 本身不是迁移理由。
- **任务难以核验、错误代价高**：保留强能力与必要的人工／专业检查，不拿轻量输出代替验收。
- **真正缺的是工具、权限或输入**：先解决缺口；换模型不能补回没给它的文件、执行权限或测试环境。
- **模型在当前入口不可用，或数据不能走该服务**：沿用合规可用的配置，不为照抄表格换账户或购买套餐。
