# 怎样让 Agent 自己验证，尤其是前端与 UI 任务

**✅ 默认让 Agent 复用项目现有检查，实际运行改动后的入口，按结果修复，再交回可复查的证据。前端任务再走用户操作路径：组件状态用交互断言，布局用截图，服务端保存用独立读回。** 先打通这条路径，再考虑新增浏览器工具、验证 Agent 或停止 Hook；已有反馈足够就沿用。

## 第一步：把“做完告诉我”换成下面这段任务

**先让 Agent 从项目指令、包配置和 CI 找到真实命令；已有测试能检出目标错误就直接复用。** 将下面方括号替换后交给当前 Agent，纯代码任务删去 UI 段。

```text
目标：[用户能完成的具体事情]。
保留：[原有行为、兼容要求、失败后应保留的数据]。

先读项目指令、相关实现、测试和 CI，找出本次任务的启动、定向测试、
类型／构建及提交前检查命令。沿用项目配置、夹具和依赖，不猜命令。
运行前从启动日志、进程或构建信息确认测到本次改后的代码；
按提交检出的入口只验该版本；未提交修改用能读取当前工作树的入口验证。
先复现已有问题；缺能区分错误的检查时，在现有套件补回归，再改实现。

UI：从[原 URL／入口及前置状态]实际输入、点击或键盘操作，
核[成功结果]和[本次相关的加载、失败恢复、取消或重复操作]。
涉及外观，查看[目标视口／主题]的关键状态截图；
涉及保存，按保存契约重新打开或从测试后端独立读回。
使用获准的隔离测试环境与合成数据，不接真实账号或个人浏览器。

遇到失败先定位是实现、测试还是环境，再修复并重跑受影响检查。
保留验收含义和必要前置状态；修改断言、夹具或视觉基线时说明需求依据。
新增 skip／fixme、删掉原触发步骤、降低断言，不算修好。

完成时写清：改了什么；最终代码实际运行的命令与结果；
走过的路径及报告／截图位置；失败、未运行和待人工判断的部分。
缺权限或环境时说明具体入口、原因与恢复动作，继续不依赖它的工作。
```

这一段约定的是**验什么、怎样证明**，不规定必须增加几轮评审。共享行为改动还要查直接消费者；项目要求的提交前检查照常执行。短小修复无需另写规格或新建验证框架，工作流取舍见 [07](../07-workflows.md#1-核心验证闭环-)。

**依据**：[既有选择与实试] [07：项目反馈](../07-workflows.md#2-标准节奏探索--计划--实现--提交-)、[15：实际入口与回归](../15-task-playbooks.md#2-调试)，沿用 2026-10-25 的结论；[一手／作者实践] [Willison：让 Agent 实际运行代码和浏览器](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/)，重核 2026-10-26。任务片段是这些机制的整理，未做提示词效果对照。

## 按承诺取证，别让一张截图承担全部验收

| 本次要交付什么 | Agent 应实际做什么 | 可以接收的范围 |
|---|---|---|
| 代码或公共接口行为 | 跑相关测试、类型／构建检查及直接调用方；修 bug 时保留能检出原问题的回归 | 所测代码与接口行为 |
| 组件新增状态 | 用真实组件和现有 story／组件测试，触发正常、进行中及失败恢复状态，等交互断言完成 | 组件交互；假服务的结果标明为模拟 |
| 页面里的用户任务 | 在当前构建从原入口输入、点击、导航，核业务结果及相关 console／请求失败；时序问题查看 trace | 实际走过的浏览器路径 |
| 布局、裁切、遮挡、主题 | 查看目标视口和关键状态截图，按需要核 computed style、焦点与键盘可达性 | 所见尺寸与状态的外观、操作；完整无障碍另按要求验 |
| 数据确实保存 | 本地保存按契约重开；服务端保存从测试后端独立读回本次记录，核缓存与响应来源 | 实际验证的持久化或集成范围 |

**前端先保用户真正失败的时刻。** 比如“加载中输入丢了”，就从页面已经可输入、数据尚未返回时开始；“关闭弹窗后不能再打开”，就走关闭→重开，而不是只拍打开的弹窗。用角色、可访问名称或稳定 test ID 找控件，等待业务状态；内部函数调用可以帮助诊断，用户路径验收仍用实际输入。

**已有 Storybook 就复用目标 story；没有就沿用当前浏览器或组件测试。** Storybook 的 `play` 可以执行输入、点击和结果断言，静态构建只说明故事能打包。跨页面导航、真实后端、桌面宿主等目标继续回应用验证，详细路径见 [23](../23-browser-verification.md#4-一次完整验证的顺序)。

**依据**：[官方] [Playwright：用户可见行为、隔离与定位](https://playwright.dev/docs/best-practices)、[Storybook：交互测试](https://storybook.js.org/docs/writing-tests/interaction-testing)，核实 2026-10-26；[既有证据] [23：状态、截图与后端的分工](../23-browser-verification.md#1-为什么编译通过仍然不够)，原核实 2026-10-21，Maka／Memos 采用见下。

## 向强项目借实际入口，而不是整包加工具

### VS Code：先选被测构建，再分一次验收与持续回归

**先确认测到哪份代码，再跑原问题场景。** VS Code 的 UI 验证 Skill 默认启动已安装的 Insiders，找不到才用 Stable；验证未合入修改时则选 `--dev`，使用含该改动的检出，并准备匹配的 Electron 和开发构建。换到自己的项目，也要从运行输出核对实际应用／服务身份，避免把旧安装或另一份工作树的结果交回来。

Next.js 团队也把“仅改 `test/` 时可直接跑测试”的前提写为工作区已准备好、框架构建最新；源码改动、切分支或拉取使产物过时时，先重建受影响部分再测。

**一次性验收复用现有入口，需要长期防回归再接进测试套件。** VS Code 用 issue 场景收集逐步断言、截图和 trace，持续随构建运行的回归则写入 smoke tests。已有测试能覆盖就沿用；临时验收无需先搭一套场景框架。

**依据**：[一手／项目实际配置] [VS Code UI 验证 Skill](https://github.com/microsoft/vscode/blob/6ba33e0ca0954b1ca03607d016f4b90768b32732/.github/skills/validate-ui-scenario/SKILL.md)、[Next.js 构建前提](https://github.com/vercel/next.js/blob/f922205f9e860de24673269f81dea51e9e33b0cb/AGENTS.md#L73-L107)，核实 2026-10-28；[本仓实际采用佐证] [并行检查候选接收](https://github.com/dbvv1/a1dbv/commit/144409dcd3e507520157d9e3a939c6ccd50f4218)，同日核对被测提交、离线结果与发布内容。实测范围为 Linux 离线检查，VS Code 场景与 Next.js 均未运行。

### GitButler：按任务看组件，检查接回项目自己的命令

**借它的做法：先找已有界面和当前组件源码，只读本次涉及的设计要求，然后打开目标 story 检查。** GitButler 把每个任务都要读两份设计文档、查 Storybook MCP 的清单改为按需 UI Skill；作者报告删去强制清单后工作表现改善。因此本页不把 MCP 接入作为前端任务的起点。

GitButler Lite 的真实 `AGENTS.md` 将检查分成不同入口；以下四条仅适用于**已按其说明准备好的 GitButler 检出**，从仓库根目录运行：

```sh
pnpm -F @gitbutler/lite check
pnpm -F @gitbutler/lite test
pnpm -F @gitbutler/lite test:e2e
pnpm -F @gitbutler/lite demos
```

最后一条启动 Storybook，不是测试通过回执。该项目另给单 story 入口、明暗主题及截图要求。换成自己的仓库，就从自己的配置复制相应命令和目标页面；用这个结构替换空泛的“请充分测试”。

**依据**：[一手／真实配置与作者反馈] [GitButler 按需 UI 修订](https://github.com/gitbutlerapp/gitbutler/commit/d44d5f6382a9c8719c0873ab3d9250c2c2661adf)、[同版 Lite 指令](https://github.com/gitbutlerapp/gitbutler/blob/d44d5f6382a9c8719c0873ab3d9250c2c2661adf/apps/lite/AGENTS.md)，重核 2026-10-26。源码与命令已核，未在本页运行 GitButler；作者体验不是受控收益比较。

### 已有实试：直接测新增消费者，才能接住 UI 续改

**本仓 Maka 续改选择了“真实 Panel／hook＋目标 story play”，没有先加 MCP。** 初次候选只通过通用 picker 测试，却漏掉“模型失效后恢复入口也被禁用”和“发送未等待模型写入”两处问题。补上直接消费者回归后，同组测试在旧候选有 **5 项失败**；修后 **82 项受影响测试、4 个 Chrome story play 通过**，包括恢复选择、失败保留草稿和进行中锁定。

这说明接收新增路径时，应把测试落到**实际组合组件与状态**，而不只复测通用控件。82 项含既有用例；play 使用假服务与真实组件，真实后端／Electron 未验，Storybook MCP 未调用。原命令、补丁与独立复核可从 [23 的组件续改入口](../23-browser-verification.md#先让真实组件接住续改再验完整应用)复用。

另一条 Memos 实试把证据接到应用：匿名页面过滤和键盘操作在真实浏览器验，阅读是否写原文用网络记录与 SQLite 比较，导出内容另查实际 PNG。读者应照着**产品承诺选入口**，而不是把每种检查套到每个小改动。

**依据**：[本仓既有实际采用] [Maka 最终独立差量复核](../collaboration/local-jobs/A-STORYBOOK-ADOPTION-001.md#本地执行端最终独立差量复核)，原核实 2026-10-25；[Memos 真实匿名页面接收](../collaboration/local-jobs/A-MEMOS-BUILT-SMOKE-001.md#已完成范围)，运行 2026-10-25、回流 10-26，owner 写入与完整应用未验。本页复用有效结果，未重跑这些应用。

## 检查失败后，让 Agent 继续修，别把契约修没了

| 失败在哪里 | 下一步 |
|---|---|
| 缺依赖、服务没启动、浏览器访问不到 | 按项目文档恢复入口，核进程属于当前检出及浏览器实际可达性，再跑原命令；权限受限则报告具体动作和恢复条件 |
| 元素改名或 DOM 重构 | 对照需求修定位器，保留原业务结果和必要状态；多种新动作都能过旧断言时，先确认原意 |
| 真的不能保存、恢复或继续操作 | 修实现，重跑原失败路径和相关回归；缺回归就补在现有套件 |
| 数据串用或异步竞争 | 隔离夹具，等待明确业务状态；保留首次失败，按 trace 查顺序，不靠持续加重试掩盖 |
| 需求确实变了、旧断言或视觉基线过时 | 列出变更依据，更新相应预期并检查实际结果；单纯“让 CI 绿”不是依据 |

**特别看 skip／fixme 和被删的前置步骤。** Playwright 官方 healer 的输出允许“通过”或“认为功能坏了而跳过”；进程退出码为 0 时，原任务也可能没执行。交付时核目标用例确实运行、覆盖仍在，跳过项单列；重试才过的测试也保留不稳定状态。已有原问题复现可用来检查修后的测试还能否检出错误。

时序问题先读现有 trace：动作、DOM、截图、console 和网络记录能对上失败窗口。临时诊断用项目已安装的 Playwright 开启 trace，复测后回到项目原配置；trace 可能含页面数据，留在获准的测试环境。更多恢复分流见 [23：自修复边界](../23-browser-verification.md#6-自修复测试的边界)。

**依据**：[官方] [Playwright healer 的输出](https://playwright.dev/docs/test-agents#-healer)、[Trace Viewer](https://playwright.dev/docs/trace-viewer)，核实 2026-10-26；[既有公开运行与回归研究](../research/2026-10-13-browser-healing-outcomes.md#修后仍走原状态而非只保留结果断言)，原核实 2026-10-21。

## 怎样看交付报告，何时需要别的路线

**能从报告找到“最终版本＋运行结果＋目标行为”，才接收对应范围。** 一个够用的报告可以这样写：

```text
改动与版本：[提交／最终工作树差量]。
实际运行对象：[构建版本／被测提交；必要时注明工作树差量]。
已通过：[实际命令、测试数量与结果]；[实际走过的用户路径]。
证据：[测试报告／trace／关键状态截图位置]。
失败或跳过：[检查、失败原因、处置]。
未运行／待人工判断：[具体范围、原因、恢复动作]。
```

检查之后又改了相关实现，就重验受影响路径。构建、组件交互、真实后端和发布分别写结果；部署成功不能盖过同版本尚未解释的测试失败。

- **没有 UI 改动**：实际运行 CLI、库调用或 API 就能补足目标证据，不必打开浏览器。
- **缺的是产品判断**：先给参考或可比较样品，由使用者判断交互是否合意；自动化继续负责可明确断言的要求。
- **需要原生系统或真实设备行为**：回目标环境验；浏览器手机视口不能覆盖原生输入法、系统弹窗或设备表现。
- **现有浏览器入口真有能力缺口**：再比较 CLI、MCP 或诊断工具；保持原验收路径，新增工具先试用，不默认整套替换。

真实用户反馈也呈现这条分工：V2EX 有使用者用 Gemini＋Playwright 跑 Web 端到端测试，也有人报告单测顺利却在真机发现功能消失，另有使用者认为功能测试仍需人工接收。**可借的是把执行交给 Agent、把产品承诺落实到正确环境；这些自述不足以给工具或模型排胜负。**

**依据**：[社区原帖／个人使用反馈] [V2EX：使用 AI 进行测试的疑问](https://www.v2ex.com/t/1248370)，重核 2026-10-26；[既有同版本验收反例](../23-browser-verification.md#8-交付报告写到能复查)，原核实 2026-10-21。当前推荐比较了项目原生反馈、按需 Storybook 和自动修测试路线，跨任务最优组合仍未知。
