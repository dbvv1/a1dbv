# 功能正常，怎样让 Agent 继续改好而不重做

**✅ 先选一个具体使用或维护问题，让 Agent 沿现有入口做可撤回的改动，保住旧行为，再用原任务和下一次真实修改接收。** “更好”可以是信息更容易辨认、等待时仍能继续操作、下一项需求更容易接上；不必等功能出错，也不以重写、删行或增加测试数作为成果。

## 第一步：从一个真实操作开始

**把页面、命令、输入或反馈交给 Agent，说明谁在什么时刻遇到什么麻烦。** 已有明确需求就直接实现；只有“整体优化一下”时，先让它从当前入口找一个有证据的问题，不自动扩成全站改版。

| 要改善什么 | 交给 Agent 的具体任务 | 怎样判断值得保留 |
|---|---|---|
| 信息表达 | 长清单难找未完成项；复用现有阅读偏好，只改展示，保留原文与编辑入口 | 原读者能找到剩余工作，父级上下文、完整内容仍可取回 |
| 操作响应 | 翻页等待时不知道是否生效；沿已有请求状态补提示、保留旧结果并处理重复操作 | 按正常速度走“操作→等待→完成／恢复”，状态与结果一致；这不是请求变快 |
| 实际耗时 | 某次查询或检查确实慢；先取该输入的运行证据，再改瓶颈 | 同输入、环境下结果保持，耗时有可复查改善；不是删检查换速度 |
| 可维护性 | 下一项需求总要在多处同步同一规则；先找真实消费者和现有共用入口，再收拢该规则 | 下一次真实改动能在清楚的位置完成，旧调用方和兼容行为仍成立 |

可撤回通常只需独立补丁与现有版本控制；需要在产品内试用或切回旧体验时，再加开关。先确定问题与必须保留的行为，方案细节交给 Agent 查代码决定。

```text
在现有项目改善：[谁在什么入口、用什么输入、遇到什么具体负担]。
本次希望：[能观察到的改变]。必须保留：[旧行为、数据、入口或调用方]。

先读项目约定、该入口及相近实现，沿现有组件／状态／函数完成。
用一个可撤回的差量解决本题，不顺带重做其他页面或替换技术栈。
实现中发现现有方案已经能满足需求，就改善通往它的入口，而非再造一套。
运行相关现有检查，并从原入口重走目标操作；性能目标用相同输入比较。
若有这次使用暴露的反馈或下一项真实需求，在当前产物上续改，保留旧要求。
交回改动前后结果、保住的行为、实际检查和未验证部分；没有目标收益就说明原因。
只有现有资料答不了、且会改变实现的取舍才问我，其余在授权范围内继续。
```

何时先规划、补测试或留规格，见[计划与测试选择](planning-and-tests.md)；实际入口、截图和数据读回怎样分工，见[让 Agent 自己验证](verification.md)。

## 向强团队借的是增量改法

**界面改进，借 GitButler 的“从最相近现有界面开始”。** 它的真实 `gitbutler-ui` Skill 要求只改任务涉及的部分，以当前组件源码为接口依据，按本次按钮、表单或文案读对应设计章节；旧页面不是任务就保留。作者把全任务强制阅读设计文档、查询 Storybook MCP 的清单改成按需 Skill，并报告工作表现改善。可借的是复用当前实现和相关知识，不是给每次小改安装整套工具。

**维护改进，借 OpenAI Core Experimentation 的“先一项有运行依据的小改，再按反馈扩大”。** 团队让 Codex 查历史、配置和获准的运行证据，保留生产行为与应急开关，为具体清理给出理由；评审反馈进入下一轮。作者也承认部分建议增加的复杂度不值预期收益。因此让 Agent 找眼前可证明的负担，而非把“清理整个仓库”当默认任务。

**依据**：[一手：真实配置与作者反馈] [GitButler 固定修订及 Skill](https://github.com/gitbutlerapp/gitbutler/commit/d44d5f6382a9c8719c0873ab3d9250c2c2661adf)（2026-09-25）；[一手：团队实践自报] [OpenAI 维护实践](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family)（2026-10-14）；重核 2026-10-26。两者支持借用机制，不构成跨项目最优或本仓效率收益证明；同预算整体最优仍未知。

## 已有产物怎样接住下一次修改

**继续用同一份代码、同一个真实入口，才能发现第一次“做完”漏掉了什么。** 本仓已有三种可复用起点，按问题看对应产物，不必另装这些应用：

| 实际任务与起点 | 反馈怎样改变实现 | 已验到哪里 |
|---|---|---|
| **Memos 阅读模式**：[完整补丁与入口](../../experiments/memos-reading-adoption.md)，主入口 `web/src/components/MemoEditor/view/MemoContentView.tsx` | 隐藏完成项先覆盖结构化与 raw Markdown 两条渲染路径；随后继续修“父项仍显示、勾选后焦点却丢失”。按稳定 block id 恢复焦点，保留过滤刷新，不重写编辑器 | 二改的 jsdom 组件模拟键盘激活在旧候选失败、修后通过；7 文件／72 项相关测试通过。匿名浏览器过滤、偏好和完整分享 PNG 已验；owner 写入与写后焦点未验 |
| **Maka 侧聊模型选择**：[补丁、直接测试与故事](../collaboration/local-jobs/A-STORYBOOK-ADOPTION-001.md#本地执行端最终独立差量复核)，沿现有 Panel／hook 与 `apps/desktop/stories/session-workbar.stories.tsx` | 新选择器遇到无效模型无法恢复，发送也没等设置写入；续改分开选择与发送就绪状态，让发送等待写入结算 | 同组检查旧候选 5 项失败、修后 82 项通过；4 个 Chrome story play 通过。82 项含既有用例，play 使用假服务和真实组件；真实后端／Electron 未验 |
| **a1dbv 配置导出**：[现有解析器](../../scripts/export_ai_config.py)与[回归](../../tests/test_config_export.py) | 正常配置能导出，继续维护时发现非法数字常量会穿过合法 JSON 契约；只补 `parse_constant` 拒绝，不把合法大指数一并封掉 | 真实 `stage` 对 6 份直接／嵌套非法输入由接收 6/6 变为 0/6；8/8 合法对照仍能 `stage → promote`，21 项模块测试通过 |

Memos 的关键不是“又多一轮测试”，而是**真实续改要求同时保住父子过滤与键盘焦点**；a1dbv 则说明收紧一条契约也应保留 `{}`、引号内常量和合法大指数等旧输入。只有清楚地减少了当前负担，才把改法保留；这些案例没有测得模型、工具或流程的净效率收益。

**依据**：[本仓实际采用] [Memos 组件二改](../collaboration/local-jobs/A-MEMOS-CONTINUATION-001.md#执行与结果)、[匿名页面接收](../collaboration/local-jobs/A-MEMOS-BUILT-SMOKE-001.md#已完成范围)，原运行 2026-10-25、回流 2026-10-26；[Maka 固定消费者](../23-browser-verification.md#先让真实组件接住续改再验完整应用)，原核实 2026-10-25，未调用 Storybook MCP；[a1dbv 固定修复](https://github.com/dbvv1/a1dbv/commit/023c325247b9f50375cea14e72b807d35b3fa316)，实跑 2026-10-26，合成配置、未读取个人配置。本页复用这些结果，未重跑应用或做正式方法对照。

## 使用反馈怎样决定保留、再改或撤回

**信息改善要问“现在会怎样理解和操作”，不只问“看起来更好了吗”。** CodexBar 一名使用者在 0.72.0 看到菜单栏 `+23%`，却在详情读到 deficit，认为符号像好消息；他提出保留旧默认、提供可选符号惯例。这个反馈能指导 Agent 改显示语义，不能证明颜色设置已开启或最终修订已被用户复测。

中文使用反馈也提醒接收环境要跟目标一致：V2EX 有人实际用 Gemini＋Playwright 做 Web E2E，另有人报告单测顺利、真机上的组件仍因字体包过大消失。把可执行部分交给 Agent；“更好理解”“目标设备可用”等承诺，回原读者和实际路径判断。

**依据**：[社区：使用者原帖] [CodexBar #4386](https://github.com/steipete/CodexBar/issues/4386)、[V2EX 使用 AI 测试讨论](https://www.v2ex.com/t/1248370)，重读 2026-10-26；[既有修订链](../research/2026-10-13-product-feedback-contract.md#codexbar发布后的理解反馈)原核实 2026-10-13。个人回执不作为工具或模型排名。

## 何时换路线

- **尚不知道改善什么**：先给 Agent 原页面、输入或一条使用反馈，做可比较的小样；产品取舍确定后再扩，不把猜测铺到全项目。
- **需求本身改变数据、公共接口或旧操作语义**：按迁移／重构接收，明确兼容与恢复；“不重做”不是永远不能换架构。
- **已有实现根本承接不了目标**：让 Agent 用具体限制说明为什么，比较窄适配与替换；局部补丁累积的复杂度超过收益就重新划范围。
- **没有自然的第二次需求**：当前目标完成即可，不制造续改或为了证明方法故意埋 bug。
- **缺的是工具能力，而不是改进方向**：再看[Skill 与插件选择](skills-and-plugins.md)；单纯指令／流程膨胀看[Codex 过度工程](codex-overengineering.md)。

改进对象是模型、Skill 或工作流时，看[工具采用取舍](tool-adoption.md)；需要扩大比较再看 [22](../22-agent-evaluation.md#7-何时推广何时停止)。**探索回执**：截至 2026-10-26，重读 OpenAI 团队原文、GitButler 固定配置／提交、GitHub 用户原帖与 V2EX 中文反馈，并核本仓三条实际产物链；决定性来源均取得正文。
