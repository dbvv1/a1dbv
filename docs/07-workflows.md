## 30 秒：先解决哪一种不确定性

✅ **〔跨代保留〕目标和约束已清楚，就直接实现并验证；别先选一套流程。** 还缺什么，再补什么：
- **〔跨代保留〕业务规则、兼容或交付约束不能猜**：先查现有依据，只问答案会改变实现的问题，把决定写进任务或短 Spec；已有依据就不再访谈。
- **〔跨代保留〕已知正确行为，但缺少能区分错误的检查**：先复现或补 red/green 用例；已有可靠用例则复用，不为 TDD 另写一套测试。
- **〔跨代保留〕布局、交互或效果必须看过才知道**：先做可撤回的样品，尽早让使用者比较；暂不接无关后端或写完整规格。若看了也不会判断，先补参考与评价依据，而不是继续生成变体。

**〔10 月确认〕样品与完整可验收轮次都可自主实现、自验，人看结果再改目标。** [Battle Drones（10-20）](https://simonwillison.net/2026/Oct/20/battledrones/)的过夜玩法修改与作者试玩支持这一选择；反馈不足或连续改不对时，再收紧范围，而非强制每步审批。[社区：作者实践；研究：条件建议]

新证据是 GIF 优化器的[原任务与固定实现](research/2026-10-12-baml-and-review.md#工作流首选契约与可观察偏好)：作者保留参数选择空间，却在实施中补了源码与静态部署约束；Anthropic 的原型建议也区分“看过能选”和“尚不会评价”。**局限：这些是具体机制和作者经验，不是四种工作流的同预算优劣实验。** **[一手／社区；经验：条件建议]**

## 当前最高水平与比较范围

**当前领先做法是让强 Agent 完成整轮工作，再按缺失的依据补约束、样品或实际路径验证，而不是预先固定流程长度。** 近期参照为 Addy Osmani／Anthropic 的 [Opus 5.5 实践（9-22）](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/)、Cursor 的[探索委派删减（9-23）](https://cursor.com/blog/improved-token-efficiency)与 John Phamous／Vercel 的[产品设计方法（6-25）](https://vercel.com/blog/teaching-agents-product-design-at-vercel)。本仓选择这一层的条件做法；跨任务最佳流程仍未知。[一手：团队原文；研究：比较]

| 同一个选择 | 领先路线与本仓取舍 | 独立来源的支持与反例 |
|---|---|---|
| 直接实现，还是先规划／写规格 | 目标清楚便整轮执行；未决决定会改变产品时先澄清，不按文件数分级 | [Willison 的 Battle Drones（10-20）](https://simonwillison.net/2026/Oct/20/battledrones/)既有过夜整轮玩法修改，也有第8轮先分析再约定新地图；支持随未知切换，不证明规格因果提效 |
| 原生流程，还是整包 Skill／外层循环 | 先保原生自主性；具体漏项才加窄反馈，已有反馈足够便撤去额外层 | [Krupa 的同题比较（9-29）](https://bartlomiejkrupa.dev/articles/does-superpowers-beat-no-plugin/)把补丁正确性、回归测试与整包投入分开；小题结果不能决定所有长任务或窄 TDD Skill 的价值 |
| 有了设计配方／测试结果，能否接收 UI 二改 | 设计依据交代方向；新消费者和新状态另核关键交互，机械检查直接对应目标 | Equinor 的 [10月公开评审与修复](https://github.com/equinor/design-system/pull/5584#discussion_r4193983965)发现短对话框遗漏的长内容滚动关闭问题；旧短实例检查没有覆盖新消费者的关键手势 |
| 把纠正沉淀为全局流程，还是局部依据 | 业务决定放任务／规格，行为回归放测试，真正通用的方法才固化 | 同一 Equinor 评审要求测试对照 ADR 的目标阈值，而非重算实现公式；基础层合入与后续页面可用也分开接收 |

**本仓已比较领先路线并给出条件默认，尚未证明统一最优。** 差距仍在四种路线缺少同一真实维护任务的完整成本对照。来源独立性、固定SHA和验证范围集中见[本轮研究](research/2026-10-12-baml-and-review.md#p69工作流整页比较与ui二改)。[研究：2026-10-22 UTC+8]

## 1. 核心：验证闭环 ✅

> “给 Claude 一个它能运行的检查：测试、构建、截图对比。这是‘你得盯着的会话’和‘你可以走开的会话’的区别。”——Claude Code 官方最佳实践 **[一手]**

✅ **优先复用能检出目标错误的检查；需要人判断的体验仍保留试用反馈。** 续接机制可以减少反复催促，但不能补出缺失的验收依据。**[经验：采用判断]**

| 当前缺口 | 做法 |
|---|---|
| 已有可靠检查，只需执行 | 要求运行检查并展示结果，不另加循环；增量检查须保留原生失效判断，不能被外层旧结果短路，见 [15 §6](15-task-playbooks.md#6-补测试) |
| 有明确验收，但仍提前收尾 | 🧪 Claude Code `/goal <完成条件>`：由另一个模型判断会话中已展示的证据，决定续接；不会独立读文件或跑检查 |
| 程序化检查（有条件） | **命令型 Stop hook** 按运行时协议阻止正常收尾；需测试缺文件、超时和连续阻止上限，不代替最终验收或权限边界，见 [06](06-hooks-and-guardrails.md) |
| 现有检查漏掉关键行为或假设 | 再用能取得独立依据的验证子 Agent；只换上下文不等于新增证据，按 [09](09-review-and-quality.md#按风险选择评审层不默认逐层叠加) 选择 |

还要让 Agent **出示证据**（测试输出、跑过的命令和结果、截图），而不是只说“已完成”。

**检查命令已有、Agent仍不能验证时，先修可运行和可观察的入口，不先加催促。** OpenAI的[自用复盘（2026-02-11）](https://openai.com/index/harness-engineering/)让每个worktree可启动应用，并让Agent直接读取界面、日志与指标；这比只要求“给证据”多了一层实际能力。默认先打通一条目标行为的启动→观察→检查路径，已有入口足够就复用；搭建负担超过当前问题时缩回最小复现，不照搬整套基础设施。人核检查是否对应真实需求，Agent负责执行与解释失败。[一手：团队自报；研究：采用判断]


**`/goal` 的成本与撤回**：会增加评估模型调用及可能的后续工作；已有会话能完成时不必加。目标被清除也可能是模型判为不可能或遇到需处理的错误，应核对停止原因与真实结果。提示中的时间／轮数条款仍由模型判断，不是硬预算；需硬限额时用已有执行环境的相应控制。没有新反馈、只是在重复说明时，清除目标并处理缺口。**局限：这是[官方机制](https://code.claude.com/docs/en/goal)，不是独立验收或净收益证明；细节见[现有核查](research/2026-10-12-long-task-evidence.md#2026-10-15按故障选择压缩清空与停止检查)。[一手；经验：采用边界]**

**来自一线的证据 [一手]**：
- Anthropic 用 16 个 Agent 写 C 编译器，作者总结：“它会自主解决你给它的任何问题，所以**任务的验证器必须近乎完美**。”项目用 GCC 作为“已知正确”的对照，并把测试输出设计成适合模型阅读（简洁，并按 1–10% 确定性采样）。
- 长时任务 harness：作者报告分离生成与评价后发现了交互缺口，支持针对性补反馈；这是其特定任务的观察，不证明当前任务加一个评判者就有净收益，采用与撤回见 §7。

## 2. 标准节奏：探索 → 计划 → 实现 → 提交 ✅

以 Claude Code 中先调查、审方案再实施的任务为例；Plan 是规划工作流，需真正只读时另设工具与执行环境限制，见 [06 权限模式](06-hooks-and-guardrails.md#3-权限模式)：

1. **探索**（Claude Code Plan 模式）：“阅读 src/auth，理解 session 和登录是怎么处理的。”
2. **计划**：“我要加 Google OAuth，需要改哪些文件？写个计划。”可以按 `Ctrl+G` 在编辑器里直接改计划。
3. **实现**：退出 Plan 模式，“按计划实现，给回调写测试，跑测试并修复失败”。
4. **提交**：让它写提交信息并开 PR。

**按未知和决策分流**：上面是需要先审方案的示例，不是所有任务的四个关卡。目标、兼容要求和授权清楚时，Agent 可在执行中规划并连续完成；多文件本身不要求 Plan 或人工批准。存在会改变实现的关键歧义时，再先调查或讨论。**[经验：采用判断，2026-10-13]**

**✅ 计划开始反复构建整套实现、再转抄代码时，先改计划产物，不先加评审或继续细拆。** 让 Agent 留下文件、接口、规格值、测试名与断言代码和验证命令；实现者能自行决定的函数体不逐段复制，尚未确定的算法与确需探明的 API 仍可调查。人检查缩减后是否仍能明确实施与验收，以计划相对规格的膨胀和重复代码为信号，不设统一行数上限。Superpowers 的实际修订支持这一窄选择，见[计划产物核查](research/2026-10-12-community-source-records.md#计划变成实现先改变产物)。**局限：作者重放只支持所测规划行为；不能推出所有任务应少写测试，或新计划已改善当前模型的最终交付。** **[一手：补丁；社区：作者报告；经验：采用判断，2026-10-21 UTC+8]**

**模式名不构成通用安全边界**：CodeBuddy CLI 官方契约中，`plan` 期间普通文件编辑与命令仍委托进入前的权限模式，另受规则与目标保护约束；不能照搬上例认定只读，更不等于沙箱。客户端范围见[入口核查](research/2026-10-12-community-source-records.md#codebuddy入口与计划权限)，环境隔离原则见[10 §3](10-security.md#3-防护原则)。**[一手；研究：范围，未执行验证]**

## 3. 大功能：访谈式 Spec ✅

适用于尚有会改变实现的关键取舍，不由“大功能”三个字自动触发。只补不可从现有资料取得的决定；视觉偏好可先用样品澄清，再写已确认约束。**[经验：采用条件，依据见上文]**

```
我想做 [简述]。用 AskUserQuestion 工具详细采访我。
优先问答案会改变行为、接口或交付方式的问题；已有资料能回答的先自行查。
把确认的约束、未决事项和验收方式写进短 SPEC.md；不要替我猜定尚需看样品的偏好。
```
需求明确后可直接继续实现；探索历史已成为负担或需要交接时，再开新会话并带上必要依据，不强制清空仍有用的上下文。**[经验：采用判断]**
好的 Spec 是自包含的：写明涉及的文件和接口，**写明不做什么**，最后有一个端到端的验证步骤 **[一手]**。

**连续升级先写预期行为与必须保留的约束，不默认写完整解法。** SWE-Chain 的同模型、同升级链对照支持先补这一层信息，更细规格并非始终更好。Agent 负责沿代码找歧义，人用真实需求和现有契约确认约束；只有具体歧义仍阻碍实现时再补 API 细节或验收例，无依据或过时的约束应撤回。[同链证据与取舍](research/2026-10-13-slopcodebench.md#p44连续升级先补行为约束不自动补整套解法2026-10-21)。这是参考差分辅助生成规格的单链证据，不是现实提示收益保证。[一手；研究：2026-10-21]

## 3.4 大功能的前置设计与垂直切片 ✅

来自 HumanLayer《Why Software Factories Fail》**[社区：原文]**，和访谈式 Spec 互补：

| 环节 | 对齐什么 | 形式 |
|---|---|---|
| 产品评审 | 解决什么问题、怎么算成功（最好是用户结果或可观测指标） | 短文档 + **粗糙的 HTML 原型**（“一个原型能结束三段文字吵不完的争论”） |
| 系统架构 | 服务、接口、数据如何交互 | 时序图、接口形状、表结构 |
| **程序设计** | 代码的形状：类型、函数签名、文件布局、调用栈 | **伪代码调用树**（可以用 diff 语法标出新增和删除）、文件树 diff |
| **垂直切片** | 实现顺序 | 每片都是能实际运行的端到端路径，做完马上评审 |

- 作者观察到按数据库、服务、API、前端顺序实施会推迟可运行反馈。若当前计划存在这个问题，可改成能尽早试用的切片，例如先定接口并返回假数据，再接前端、服务与持久化；底层迁移或接口约束可能要求不同顺序，不据单一作者经验称所有模型“天然偏好”某种计划 **[社区：作者观察；经验：采用条件]**。
- 作者建议每次评审 100–200 行；本仓库将其作为保持 diff 可评审的参考，按行为、接口和风险确定检查点，不作为必须等待人工批准的固定行数门槛 **[社区：作者经验；经验：采用判断]**。
- **按未决问题选环节**：作者按任务大小选择流程是其场景经验，不作为本仓通用门槛；已有产品目标或接口依据就复用，只补会改变实现的缺口，不因“大任务”自动走完四环节。**[社区：作者经验；经验：采用边界]**
- 作者总结“30 分钟的计划能省几个小时的评审”，但已读材料没有可复算的时间对照，不能承诺稳定快 2–3 倍；配套 80/20 曲线也是假设示例。是否加前置研究，应看它能否解决会改变实现或验收的未知，而非先规定规划时长。见[BAML 对照与原文审查](research/2026-10-12-baml-and-review.md#baml实现反馈纠正研究计划) **[研究]**。

**🧪 选长期底座或准备扩大内容生产时，让同一切片经历一次真正的第二次需求修改。** 选择会触及原有边界的变化，如给异步任务加取消／重试、改变持久化字段后读取旧数据，或替换资源后保留原消费者；先写清哪些旧行为与身份必须保持，再用新旧数据和引用回归，记录返工、主动工时及重生成成本。游戏线的[资产替换核查](research/2026-10-14-game-wp9-engine-handoff.md#5-采用改造不用与最小验收)与[玩法生命周期分析](research/2026-10-14-game-wp11-gameplay-architecture.md#9-ai-第二次修改交付契约切片不强制再搭一层工具)说明首次导入／运行成功仍不足以覆盖这些边界；沿用现有任务与测试，不给每个小修另造验收流程。**局限：这是基于文档与源码分析的试用建议，尚未通过游戏切片实测证明维护成本下降。** **[研究：本仓库分析；经验：试用建议]**

### 流程也需要删减

强 Agent 已稳定完成规划、实现和验证时，小任务不必再套完整规格、逐任务子 Agent 和多轮评审。出现具体能力缺口或有依据的质量目标时，按 [05](05-skills-and-plugins.md) 补最小必要资料或方法；目标清楚时保持自主推进。删流程要保留目标反馈：已知用户反例须改变下一动作，局部测试通过不能替代全部范围；“知道尚未完成却停工”的反例与源码核对见 [续接研究](research/2026-10-10-codex-continuity.md)。对 Superpowers、组合式 Skills 与轻量结对的实际比较见 [24 社区工作流](24-community-workflows.md)。**[经验：采用判断]**

## 3.5 Fable 级模型时代的提示与收尾 ✅

来源：Anthropic《Getting the most out of Opus 5.5》**[一手]**，Simon Willison《Agentic Engineering Patterns》**[社区]**。

**交代任务**
```
把支付接口从旧 client 迁到新 client。
完成标准：所有接口都用新 client，旧 client 已删除，测试套件全部通过。
只有当某个测试失败、而你解释不了原因时，才停下来问我。
```
- 一条消息给出**完整任务 + 完成标准 + 停止条件**，然后放手让它做。
- 删掉“think carefully / 一步步思考”这类话：模型自己会思考，改用 effort 控制。
- 运行中想起什么，直接追加消息，不必重启任务。
- 设计类任务：**列出要避开的具体样式**（只说“别太普通”只会换成另一种默认风格）。

**开局的短提示**
- `First run the tests`：让 Agent 知道有测试套件、大致了解项目规模、进入“测试心态”。
- `Use red/green TDD`：预期行为已有依据、且需要补可执行检查时，先写测试、确认因目标问题失败，再实现；不把尚未决定的产品偏好锁成断言。

**长任务**
- 在 CLAUDE.md 里写**停止规则**（模板已包含）：不需要你时继续做，只在无法继续或要做破坏性操作时停下。
- 在 `TASKS.md` 或已有记录中维护最新目标、进度与验证；恢复时重读并核对当前状态。文件存在不保证已加载或仍有效，见 [20 恢复边界](20-codex-long-horizon.md#4-恢复包必须包含最新任务而非最长历史) **[经验：采用判断]**。
- 审计和迁移中**可独立调查的部分**可拆给子 Agent；实际迁移先对齐共享接口和依赖顺序。**主 Agent 要逐个检查子 Agent 交回的证据**，再验证整合结果，见 [08](08-multi-agent.md)。

**收尾与验证**
- 总结格式固定为：**Blocked on me / Changed / Found**，先看需要你决定的事项。
- **Agent 式手工测试**：测试通过不等于能用，让 Agent 用 `python -c`、curl、浏览器自动化实际跑一遍。
- 要求它“**标出无法确认的内容，并说明查过哪里**”。
- 评审提示：“只列你会因此拒绝合并的问题，给出文件、行号、原因，以及怎么证明它是错的。”

**理解与交接**
- **线性走读**：让 Agent 为代码写一份逐段讲解，适合接手 vibe 出来的代码。
- **术语对齐**：评审前让 Agent 列出它自创的术语和含义，你改名后它全局替换；长期维护一份 GLOSSARY.md（Lobsters 上的做法）。
- **交接**：确需换会话或交给另一工具时，复用现有任务记录，补当前目标、已验结果和未决事项；只需腾空间则按 [03](03-context-engineering.md#3-会话层面的上下文管理) 选压缩。不要假定 `/handoff` 是内置命令，应核对当前宿主／扩展，普通提示也可整理交接。**[一手：当前命令表；经验：采用判断]**
- **PR 礼仪**：不要把自己都没审过的代码丢给同事；PR 要小，并附上证据（手工测试记录、截图）。

## 4. 测试驱动（TDD）🧪

- 先从原需求、已确认复现或独立计算确定预期；已有测试能检出目标缺陷就复用，只为未覆盖行为补测试，再确认因目标缺陷失败、修复后通过，见 [22 的强验证](22-agent-evaluation.md#修-bug-的强验证)。
- 不为变绿削弱断言或删除用例；生成测试失败时先核对实现与预期，有独立依据证明预期错误时可以修正测试。
- 可选形式：一个会话写测试，另一个会话实现；分开上下文不自动获得独立预期，只有能补现有检查的缺口且值得交接成本时再用，见 [09 的按风险选择](09-review-and-quality.md#按风险选择评审层不默认逐层叠加)。
- 不默认增加强制工具；确有可机械检查的流程缺口时，按 [06 的条件与失败边界](06-hooks-and-guardrails.md#高价值的-hook-场景) 选用，不能把 TDD Skill 或编辑 Hook 当完整执行保障。

## 5. Spec 驱动开发（SDD）

| 工具 | 风格 | 评级 |
|---|---|---|
| [GitHub Spec Kit](https://github.com/github/spec-kit) | 功能流程含 Constitution → Specify → Clarify → Plan → Tasks → Implement → Converge；当前另有 bug/想法评估入口 | 🧪 按未决约束与维护需要试用 |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | 轻量，偏增量变更（`/opsx:propose`），支持 30+ 工具 | 🧪 |
| [Kiro](https://kiro.dev) | 原生需求／设计／任务与显式修订，见[采用边界](research/2026-10-12-community-source-records.md#kiro规格修订能力与采用边界) | 🧪 按审阅与维护需要试用 |
| [BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) | 模拟敏捷团队的多个角色，产出物很多 | 👀 |

**历史批评（[社区]：Birgitta Böckeler、François Zaninotto 与 HN 讨论）**

下面是历史使用体验，不代表当前版本只有完整 SDD 一条路径；Spec Kit 的2026-10-10源码已提供独立 bug 流程，见 [21 的版本与原帖](21-agent-patterns.md)。
- Spec Kit 给一个简单的日期显示功能生成了 **1300 行 Markdown**；审阅大量生成的 Markdown 可能比审代码还累；
- Böckeler 在2025-09用 Kiro 修一个小 bug，却得到四个 user stories、十六条验收标准，认为过重；这支持按任务收窄规格，不证明当前没有修订通路；
- 有人报告写规格占了项目一半的时间；用完整 SDD 修 bug 显然是大材小用。
- 支持者的反驳：瀑布模型的问题在于反馈周期长达数月，而 SDD 的周期是几分钟。

**本仓库的判断 [经验：条件采用]**：规格的价值是固定容易猜错或丢失的约束，不是先写齐文档。中大型功能不自动需要完整 SDD；小修若涉及有歧义的行为，也先用一两个例子说清预期。探索／原型期避免长 Spec，先用能回答当前问题的样品；已确认的边界可以写短说明。已有任务与测试足以表达时直接做，只有跨步骤决策需要保存时再选轻量 Spec 或增量工具。实现发现约束冲突时更新规格，不能为服从旧计划继续做错。Kiro已有显式修订与任务同步入口，但仍需人确认新约束、核对受影响任务与实现；不把同步或任务勾选当验收通过。若额外文档没有补上真实缺口，就收窄或撤回规格流程，见[原文与修订边界](research/2026-10-12-community-source-records.md#kiro规格修订能力与采用边界)。上面的历史成本反例仍成立；新增依据与适用范围见[契约与可观察偏好](research/2026-10-12-baml-and-review.md#工作流首选契约与可观察偏好)。

### OpenSpec：让下一位接手当前约定，而不只是旧计划

**🧪 功能要跨角色接手、连续二改时，试用当前规格＋本次差量；明确小改沿用现有任务与测试。** Ilya的团队由PM起草、开发者接手，再复用变更材料生成发布说明；Talk Think Do却因范围／预算难追踪，把规格工作迁回工作项系统。选择关键是下一位读者能否接着工作，不是Markdown写得多不多。[社区／研究；[正反原文与固定实现](research/2026-10-22-frontier-trials.md#openspec规格接力与协作落点)，2026-10-23，未试用]

- 从已有功能的一次二改开始，明确需求确认者、实现者与接收者。
- 记录本次改变及必须保留的行为，新决定回写同一份变更材料。
- 合入前一起核对实现、测试和当前规格，并确认本次差量已同步。
- 无人复用或协作者主要在工作项系统接手，就收缩流程或沿用原有落点。[经验：试用方案]

### 已有界面能跑，但还不像可交付的产品

**🧪 先补能直接使用的设计参照，再用原生Agent改一轮。** 仓内修改优先给共享组件的导入／用法和已交付实例，不只描述外观让它重造；仓外独立产物确实无法用原组件时，再给短设计方向和可用的基础样式。目标使用者、当前差距与必须保留的行为仍要明确，不默认加完整评审循环。[一手：Vercel／独立Atlassian采用与反例；研究，见[环境分流](research/2026-10-12-baml-and-review.md#p81设计参照按实现是否可用分流)]

**重复纠正落到能稳定执行它的位置。** 组件／CSS承担可复用机制，已有检查承担机械规则，产品判断留在短指导；单个模型一次失误不立即变成全局禁令。改共享指导后复核受影响的旧产物类型，某页变好而别类退步，就缩窄或撤回该规则。Anthropic九月配方仍按需参考，不把反模板偏好变成永久禁用清单。[一手／研究；原[P45记录](research/2026-10-12-baml-and-review.md#p45功能能跑以后先改善哪种质量)]

人先核方向和关键操作；行为证据不足再补独立实际路径检查，方向还不清就先比样品。评分上涨但任务更难完成、后续维护更重，就撤回该轮；中间版可能比末版好。现有四条路线的当前同预算最优未知。[一手：历史作者实验；经验：采用边界]

**✅ 二改新增消费者或状态时，沿新路径补检查，不重套整套设计流程。** 例如旧对话框很短，新页面加入长内容：让 Agent 验证滚动、拖选、关闭及旧实例行为，人核目标操作是否顺畅。Equinor 的共享Dialog在长内容状态把滚动条命中误判成背景点击；修复是把滚动移入内容容器，而非再换一份设计提示。[具体评论](https://github.com/equinor/design-system/pull/5584#discussion_r4193983965)与[固定修补](https://github.com/equinor/design-system/commit/aad58d728969600be0f01f659cb40752668f79e9)支持这一故障层的选择。[一手：公开评审／源码]

**基础层合入不等于完整功能交付。** 同链基础PR已接收，Theme Builder及其他页面仍未合入；Agent应分别报告基础修复、行为检查和剩余交付。若关键手势还没有实际回执，就保留该项待验，而不是靠测试总数放行。此链只有参与者运行自报及本仓源码核对，新增jsdom结构断言不证明真实滚动手势已回归通过。[研究：范围及链接见本轮研究]

## 6. Ralph 循环 🧪

✅ **普通会话能连续实现并验证，就不加外层循环。** 🧪 已有明确目标与授权，仍反复在可继续的工作前收尾时，才试受限续接；若缺的是检查覆盖、需求决定或工具权限，重复原提示不能补上它们。先区分两种常被混称为 Ralph 的实现：**[经验：采用判断]**

- **同一会话续接**：官方 Ralph Loop 插件用 Stop hook 重送提示，不等于清空上下文或启动新进程
- **新进程循环**：社区 shell 方案每轮重新启动 CLI，靠文件承接状态；只有已观察到上下文／恢复问题，且必要信息能可靠交接时才考虑

官方固定实现的 `completion-promise` 比较模型文字，不运行项目验收；上限退出也不是完成。只在保留真实验证结果、预算上限与可用取消路径的条件下试用。连续重复同一失败、缺少新反馈，或已需要人决定时应退出循环并处理原因；外部操作结果不明时按 [20](20-codex-long-horizon.md#9-超时后动作究竟发生了吗) 先对账，不能自动重放。**[一手：固定源码；经验：撤回条件]**

**局限：两位开发者的表格与投票应用案例说明 fresh-process 路线可用，但没有证明它胜过普通会话；官方终止回归测试也只检查控制逻辑。** 版本、具体任务与反例见[循环采用核查](research/2026-10-12-long-task-evidence.md#循环采用核查续接重置与新增反馈)。**[社区／一手；研究：证据边界]**

## 7. 长时 harness：保留解决当前缺口的部分 🧪

✅ **按失效原因补机制，不照搬历史架构。** 跨会话丢状态时补可核对的交接；生成结果漏掉可观察行为时补针对性测试或独立评价；已有检查足够时继续用普通会话。评审放在哪里由风险与中间契约决定，不默认每功能一轮，也不默认全部拖到最后。**[经验：采用判断]**

Anthropic 的两篇历史工程报告应连着读：2025-11 的方案逐功能执行并交接；2026-03 的作者已在 Opus 4.5 上撤去上下文重置、改用自动压缩，又在 4.6 上移除 sprint，转为整轮构建后的评价。不能再由早期 Sonnet 4.5 的问题推出“长任务重置总比压缩好”。保留评价的具体理由是它仍发现 DAW 的拖动、录音等核心交互缺口，而不是运行时间更长或功能更多。**[一手：作者实验报告]**

**撤回方式**：模型或任务变化后，一次移除一个可选环节，看原缺陷是否回来、是否仍产生有用的新反馈，再决定保留；目标质量提高但投入也增加时，明确这一取舍。**局限：这些历史任务并非同预算、同范围的因果对照，不能推导当前模型的固定重置频率、评审轮数或收益率。** [完整范围与不同作者案例](research/2026-10-12-long-task-evidence.md#循环采用核查续接重置与新增反馈)。**[一手；经验：采用与撤回建议]**

### 公网服务交付：验实际开放范围，不只验登录配置

**✅ Agent新增或修改公网服务时，先核实际部署目标，再按批准的公开范围接收；仓库测试与登录配置通过还不够。** 有现成平台检查就复用，不默认自建扫描器。这里只讨论已授权目标上的验收，详细依据见[部署事实与匿名访问](research/2026-10-12-development-conditions.md#公网交付部署事实匿名访问与数据隔离)。[研究]

| 当前证据 | 允许的决定 | 后续修改如何保留 |
|---|---|---|
| 部署清单与实际入口一致，访问控制按预期阻止未授权访问 | 可按原受限范围接收，不外推所有路径和数据安全 | 改入口、代理或鉴权后重验受影响路径，不只重跑仓库单测 |
| 匿名可读，且对象、路径与数据范围均已获准公开 | 按明确公开范围接收；公开不是漏检，也不是免检 | 公开例外变化时重新核实际行为，移除过时例外 |
| 未获准的内容可被匿名取得，或访问范围超出预期 | 暂停该开放路径，收窄到批准范围；独立开发检查可继续 | 先修边界再接收，不靠更换状态标签放行 |
| 超时、错误响应、未知路径或目标覆盖不全 | 标未判定，补缺少的观察；不能按“未发现暴露”放行 | 保留待核对象与原因；403／404不能脱离实际入口语义判安全 |

**第二次修改同时复验保护与正常使用。** 固定一个需登录的数据服务，随后新增公开路径或更换部署入口：Agent对账实际目标、受影响访问方式及判据变化；人确认哪些数据可以公开。修改判定规则时复用有已知结果的案例，并比较旧结果为何改变，不以未判定比例下降当安全率提高。[研究：接收设计]

若公网应用仍能接触不应公开的数据，先按[10的隔离边界](10-security.md#公网产物把数据边界留在查询过滤之外)收窄其能力，而非持续堆叠默认过滤。这里没有部署、探测第三方目标或自动修改云权限的授权，也没有本仓实测收益。[研究]

## 8. 把纠错沉淀下来（复利工程）

| 纠正的是什么 | 写到哪里 |
|---|---|
| 已确认且会影响后续任务的项目事实或约定 | 更新已有资料；确需常驻时才放 CLAUDE.md / AGENTS.md |
| 需要复用的领域配方或可靠操作步骤 | 先用资料入口／已有脚本，仍有缺口再考虑窄 Skill |
| 可机械检查的流程约束 | 命令型 Hook，并测试失败路径；权限约束交给沙箱等运行时边界 |
| 有独立调查价值的某类审查 | 按风险与证据缺口选 Subagent |
| 多仓库确需共同分发多个组件 | 再考虑插件；仅共享文档不需要插件 |

不按犯错或粘贴次数自动增加配置；先确认缺的是资料、反馈还是执行边界。新增内容不再改变结果、已失效或维护成本超过价值时删减，具体采用条件由 [03](03-context-engineering.md)、[05](05-skills-and-plugins.md) 和 [06](06-hooks-and-guardrails.md) 维护。Every 的 [Compound Engineering](https://github.com/EveryInc/compound-engineering-plugin) 是一种实现参考，不是流程越多收益越大的证据。**[经验：采用与撤回建议]**

## 9. 常见失败模式（结合官方建议按原因处理）

| 失败模式 | 修复 |
|---|---|
| 大杂烩会话：一会儿做 A 一会儿做 B | 不相关的任务之间 `/clear` |
| 反复纠正 | 先区分预期不清、缺反馈与错误思路累积；确需舍弃旧思路时保留已验结论再 `/clear`，不按次数清空 |
| CLAUDE.md 规则被忽略 | 先核加载、冲突与相关性，再删重复／失效信息；只有机械检查适合 Hook，不能把所有说明转成脚本 |
| 信任但不验证 | 一定要有测试、脚本或截图；无法验证就不要上线 |
| 无边界的探索 | 限定调查范围，或交给子 Agent |

以上采用条件与 [03 的会话选择](03-context-engineering.md#3-会话层面的上下文管理)一致；官方的纠正次数是实践建议，不是错误根因或清空收益的证明。**[一手：最佳实践；经验：诊断边界]**

## 官方示例也要匹配协作方式

OpenAI Cookbook 同时有“里程碑后自主继续”的 ExecPlan 和“每阶段等待人工批准”的阶段式教程。它们并非对所有用户的统一指令。✅ 先按当前授权和协作需要选择，再借鉴有用的证据与恢复机制；不把两套相反的停止规则都复制进全局配置。迭代修复教程的 staged 轮数也不能转为生产任务的固定返工次数。**[一手；研究：采用判断，见官方原文及代码核对](research/2026-10-11-codex-cookbook.md)**
