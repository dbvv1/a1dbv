## 1. 30 秒：按反馈与恢复需要选机制

代际复核：2026-10-21，Astra／Opus 5.5 与当前原生 harness；标签定义见 [00](00-state-of-ai-coding.md#30-秒结论)。

**✅〔10 月确认〕把完整可验收结果交给 Agent 连续执行，按反馈缺口与中断风险补机制，不按任务体量设自主上限。** 无人值守是一段执行方式，不是无人负责的整个生命周期；验证失真、重复返工不收敛或外部结果不明时，收紧对应范围。[研究：条件默认]

| 工作 | 建议起点 |
|---|---|
| 文案、明确的小修复〔跨代保留〕 | 直接改 + 对应检查；风险或验收不清才补计划 |
| 多文件功能〔跨代保留〕 | 可观察的验收项 + 依赖顺序 + 最终集成检查 |
| 跨会话、容易中断〔跨代保留〕 | 再加恢复记录与版本绑定证据；跨执行者派发前确认失联后仍能找回同一任务；有程序消费记录才用 JSON |
| 执行逻辑或保存格式升级〔10 月补核〕 | 不紧急就到可核验边界再换版；须热续接时，验首次新写后的冷读与下一轮，见 [§4.1](#41-任务未完执行逻辑却要升级) |
| 外部写入、部署、数据变更〔跨代保留〕 | 再加明确授权与结果核对；执行结果未知时先查远端 |

主要依据：官方 Astra 指南建议缩短常驻指令、按需读文档，避免复杂流程束缚模型。**[一手]** 局限：这是特定模型代际的指导，项目命令、安全边界与验收要求仍须保留。

## 当前最高水平（2026-10-22）

前沿比较：已比较（完整目标、恢复策略、升级与当前版本接收）。本页比较的是在不同失败状态下选什么，不宣称某套 harness 通用最优。[研究：比较范围]

**默认让 Agent 连续完成完整目标；中断后先辨别状态是否仍有效，再选继续、回退或重新接收。** 保留恢复、授权与结果对账，撤回固定 reset／sprint。短执行段是升级与恢复边界，不是任务体量或自主能力上限。[研究：条件默认]

- **近期领先参照：** Earendil Engineering 的 [Pi Durable（10-01）](https://earendil.com/posts/pi-durable/)把中断任务与工具重试分开；Anthropic／Lance Martin、CJ Avilla 的 [automation 参考实现（10-08）](https://claude.dev/blog/building-effective-agent-automations/)把运行、游标和外部回执分开。它们提供当前机制，不单独证明净收益。
- **独立佐证：** UCAS／清华等团队的 [AgentRewind（8-14）](https://arxiv.org/html/2608.14380v1)比较继续、重启和联合恢复；Shopify／Erin Son、Kaiyi Li 的 [River（9-02）](https://shopify.engineering/river-vulnerability-remediation)报告从接续改动到当前主干接收的生产实践。前者主要使用 GPT-5.4，后者是采用方自报，不是两套当前机制的独立复现。
- **主流与可行基线：** 原生继续配合现有 Git、任务源和测试；采用比例未知。宿主已有能力够用时，不另装记忆或耐久平台。
- **本仓推荐层级：** 比较后的条件默认。总体最佳与通用可靠时长仍未知；读者可以按下表选择，不必等待一个跨任务总排名。[研究]

| 同一完整任务到了哪种状态 | 选什么、借什么 | 验收与撤回 |
|---|---|---|
| 进程断开，但已产出的状态仍有效 | 原生继续；耐久宿主复用原任务与检查点 | 核待完成调用与外部回执。状态污染或无法确定副作用时，不盲目续跑 |
| 已走入错误路径，前向修复不收敛 | 已有可核恢复点时优先试受控联合回退，带上失败经验；没有则在保留旧产物后重启 | 恢复范围须明确，原工作另存；外部状态和 Git 身份不在恢复范围内就单独对账 |
| 任务未完，执行逻辑或保存格式换版 | 按 §4.1 选择旧版排空、兼容热续接或边界交接 | 验旧读、首次新写、冷读及下一轮；坏版本停止接新任务 |
| 代码、需求或接手者已经变化 | 在当前 head 接收仍有效的目标，而非重放旧补丁 | 核合入后的真实结果；人已接管或原需求推翻旧修复时，停止覆盖并交接决定 |

配置加载、委派回收、隔离、预算、工具与 Hook 仍按下文各自契约验收；论文或采用案例不能替这些机制盖章。完整卡与原升级链见[研究](research/2026-10-12-long-task-evidence.md#p60续接从恢复执行到完成当前目标)。[研究：整页范围]

## 2. Codex 原生配置：先验证实际加载，再谈效果

✅ 先用最小配置跑通一条任务：配置可解析 → 运行时接受 → 目录/角色可见 → 正例触发、近邻反例不触发 → 输出满足契约。可从[可选示例](../templates/codex/README.md)开始。**[经验：设计]**

主要依据：官方文档使用 `AGENTS.md`，同层 `AGENTS.override.md` 优先，项目指导默认总上限 32 KiB；技能放 `.agents/skills/<name>/SKILL.md`，先加载元信息、再按需加载正文。子 Agent 角色与权限按所用客户端核对。**[一手]** 局限：配置解析成功或会话中改了文件，都不足以确认本次任务已加载并有效使用。

## 3. 完成条件来自验收原文，不能由总结重新定义

✅ 给重要行为稳定 ID，分别覆盖成功、非法输入、取消后的副作用；保留一条故事中的每个验收场景。[独立 spec 与运行报告](../templates/long-task/README.md)可检查漏项、重复/错配 ID、证据版本和未完成 worker。验收输入由独立评审或权限边界保护，真实测试输出单独留存。**[经验：设计]**

主要依据：Spec Kit #3752 报告把 16 个场景压成 4 条故事后误判完成；本仓库校验器要求必需检查 passed、证据绑定工作版本、登记的 checkpoint/worker 完成，预算耗尽也不能记成成功。**[社区：单例；经验：本仓库实现]** 局限：校验器只核对记录一致性，证据真伪、实际代码正确性和 spec 被共同篡改仍需外部验证。

**恢复成功以后，还要按当前目标接收。** River 会把待升级依赖接到当前锁文件，而非覆盖邻接升级；人已接管的分支不再改。合入后继续核主干实际依赖与任务源，再关闭事项。借用的是“当前版本与真实结果一致才完成”，不是要求所有项目接入安全平台；原需求证明补丁方向错了，就撤回建议。见[续接研究](research/2026-10-12-long-task-evidence.md#p60续接从恢复执行到完成当前目标)。[一手：独立采用自报；研究]

## 4. 恢复包必须包含最新任务，而非最长历史

✅ 在现有任务记录保留六项信息，简单任务不必另建文档。**[经验：设计]**

1. task/run ID、最新目标与约束，以及取消或被取代的要求
2. 仓库、分支、base commit 与工作树差异或内容指纹
3. 已完成动作及观察到的结果，关键决定的理由
4. 验收 spec 版本，以及通过、失败、未运行证据适用的版本；[后续一轮全通过不替代未决旧项](22-agent-evaluation.md#连续需求先分清旧债新回归与测量问题)
5. 待收集子任务、外部 job ID、未知结果与待授权动作
6. 下一步最小安全动作与停止条件

可复制的 [checkpoint-resume Skill](../templates/codex/.agents/skills/checkpoint-resume/SKILL.md)沿现有记录保存与恢复，先核新要求、取消及接管，再续旧步骤；本轮是正文与模板的一致性修订，未验证自动加载或模型收益。[经验：2026-10-24]

**恢复后先判断哪些检查仍适用，再决定重跑什么。** 沿既有交接记录核受检代码、输入、依赖与环境；只换提交SHA或合入无关文档时，可保留未受影响的结果。代码影响不明或执行环境已变，就复验相应路径；发布状态和精确提交CI仍须另核。两份[通用交接](../templates/generic/.claude/skills/handoff/SKILL.md)／[Codex恢复](../templates/codex/.agents/skills/checkpoint-resume/SKILL.md)模板同步此选择，不新增记录格式；这是指令修订，未测客户端自动加载或节省工时。[经验：2026-10-24]

**有效状态被中断，优先继续；错误路径污染了工作树，才比较回退。** Pi Durable 的任务恢复与 AgentRewind 的失败路径恢复回答不同问题：前者保住可继续的运行，后者把上下文与受控文件一起退回，并保留失败经验。不要因一次进程退出清空任务，也不要只清聊天、留着坏文件继续试。见[续接研究](research/2026-10-12-long-task-evidence.md#p60续接从恢复执行到完成当前目标)。[一手／研究]

**回退之前先核它能恢复什么。** AgentRewind 不撤销网络、外部服务或外部进程；工作区根目录的 .git 也不恢复。因此文件回去了，提交历史和外部事实仍可能向前。Agent 先对照当前分支、HEAD、文件差异及外部结果，人确认有权撤回的范围；范围不清就保留原状态并停止相关写入，不重放已完成操作。[一手／研究]


同一交付物先确认原任务能否读取并继续，只补当前变化与必要依据；确实无法接续才交接上述信息。任务复用不替代独立评审，具体边界见 [dot 使用建议](01-agents/codex.md#长时运行与-dots按能力缺口增加任务)。**[一手；社区；经验：采用判断]**

**需求改变记录用途时，重查旧过滤条件，而非只保存旧理由。** Pydantic AI 的 interrupted 消息从“保存已有部分结果”扩展为“下一轮恢复信号”后，旧的“没有 tool result 就不记”条件使首个工具取消无法恢复；后续沿已有 repair 层补发空标记，见[累计演化与下游恢复验收](research/2026-10-12-development-conditions.md#累计到下一次需求保存重放整轮取消不是同一个契约)。恢复记录应指出失效的前提，验收则检查保存、反序列化、新实例继续使用的路径。**[一手：需求与固定补丁；研究：采用建议]**

**续改失败时，也查新功能依赖的继承行为，不只看最新 diff。** 核对输入拒绝条件、缺值默认与错误传播，再补最小回归；已确认的新需求可以改变旧契约。[CodeThread 的两阶段比较](research/2026-10-12-development-conditions.md#codethread下一次修改失败先查继承了什么行为)提示静态复杂度不能代替这项诊断，故不默认增加复杂度门禁或全盘重写。局限是重建函数后的 Agent 续改实验，尚未证明这种诊断能降低真实接管工时。**[研究：论文与固定源码；经验：采用判断]**

**历史显示缺失时，先区分原始记录丢失与读取／投影停滞，再选恢复动作。** 对已确认的版本缺陷，先保留原数据、核对实际运行的后端是否包含修复，再用受支持的 resume 检查原来缺失的轮次；原生恢复足够时，不再增加修复脚本或直接改数据库。[Codex 的重复序号恢复报告](research/2026-10-10-codex-continuity.md#6-2026-10-14原生恢复已够时撤回手工修复)在不改 SQLite／JSONL 的条件下恢复了三轮历史。局限是特定 CLI 版本与故障形态的公开自报，不代表删除的原始数据、全部 Desktop 故障或任务语义都已恢复。**[社区：复测；一手：固定实现；经验：采用判断]**

**压缩失败后，不把已出现的部分摘要当作恢复依据。** 先核对运行版本，通过正常续接／恢复检查原消息与工具结果；已有结果可核实时，不因压缩失败重跑副作用操作。官方修复将摘要记录延后到响应成功完成，见[失败压缩的提交边界](research/2026-10-12-long-task-evidence.md#失败压缩的提交边界)。局限是响应完成、历史替换与落盘成功仍是不同边界，且本轮核对的最新稳定／预发布 tag 尚未包含该修复。**[一手：固定补丁与回归定义；研究：采用判断]**

恢复时先核对文件、worker、外部操作和授权；重建并检查进程、端口、浏览器与认证。确认最新任务、路径规则及 Skill 正文仍可见或可重载，不能只看“已激活”标记。检查点不新增授权，也不保存密钥或模型内部思考过程。

主要依据：OpenAI 长时任务实验使用持久化需求、计划和状态；Codex 有压缩后回到旧任务、压缩失败的实际报告。连续任务评测也提示应分别检查旧约束和运行反馈是否可取得，因此保留无法从代码恢复的接口约定、决定理由与相关回归输出，需求取代旧决定时同步理由。**[一手；社区；研究：采用判断]** 局限：代码或聊天快照不能恢复全部活跃资源，这些证据也不足以要求已有记录可用的项目额外安装记忆平台。

### 4.1 任务未完，执行逻辑却要升级

**✅ 不紧急时，先到可核验边界再换版；不能等时，才走已验证的兼容续接。** 短工作段划分的是执行版本边界，完整目标、交付责任和后续检查仍连续，不按固定轮数重置或拆碎用户目标。[研究：条件默认]

同题：代码 K 已提交、旧测试 A 通过、外部 CI 任务 J 未完；新版拆开测试节点并新增评审。三路都须接收 K、J 和剩余验收，下表是机制比较，非效果实测。[研究]

| 路线 | 同一任务怎样继续 | 采用与撤回 |
|---|---|---|
| 旧版排空 | 宿主固定旧执行代码，等当前运行结束，新版接余项 | 短期可结束时优先；保留旧 worker／依赖至排空。遇紧急安全问题、权限撤销或无法排空，停止依赖旧版继续的安排 |
| 兼容热续接 | 新逻辑仍识别旧节点、字段与在途位置，补新版要求 | 适合不能等待且兼容已验证的任务；代价是维护旧行为分支。新写丢失或状态不明就暂停相关写入 |
| 短工作段交接 | 当前运行在可核边界结束，新运行用新版接收 K、J | 适合频繁升级；在途任务须可查询且有接收者。无法交接就不强切，先补接收条件 |

**只用宿主确实提供的版本固定／兼容入口。** Temporal 与 LangGraph 的契约不同，不能据其例子推定托管 Codex 可固定旧后端；普通使用者沿产品支持的继续／交接入口，不为升级自建平台。[一手；研究：适用边界，详见上述研究]

**迁移要验“旧状态 → 首次新写 → 冷读 → 下一轮”。** LangGraph 曾在旧记录可读、当轮返回正确时，丢掉内存后端迁移后的首次非 snapshot 写入；仅验旧记录不够。上游修复发行后，还要核实际加载的独立依赖与旧兼容补丁，确认测试验到原生实现，再退役对应补丁。[一手：公开修复链；研究：采用判断]

Agent 列受影响节点、字段和依赖，沿已有回归核新旧消息顺序／身份及下一轮恢复；人决定新要求是否追溯旧任务。K、命令和环境未变时，A 仍证明原范围；被验输入、验收语义或恢复数据改变才补验受影响部分，A 不自动满足新增评审。[研究：职责与证据复用]

**失败先停新任务进入坏版本，再对账。** 回旧部署不会撤销已写状态或外部动作，结果未知仍按 §9 处理。本节是运行／保存格式升级；请求回退和未决工具绑定分别见 [§9](#模型回退先区分请求续接与工具重放)，不新增控制层。[研究：撤回边界]

## 5. 子任务应缩短关键路径，不应制造评审树

✅ 原生按需委派；确能减少上下文负担或缩短关键路径时，再把边界清楚的调查拆出去。每次带明确问题、输入版本、读写范围、结果和验收方式；同一修改表面由一人整合。区分 worker 自称完成、结果送达、主任务收集、主任务验证四个时刻。**[经验：设计]**

**下一步依赖嵌套子任务结果时，先用宿主支持的原生前台返回。** 不把交互会话的后台唤醒行为照搬到非交互／SDK；Claude Code 2.1.302 的默认前台变更已有[父任务消费结果的公开复测](research/2026-10-12-long-task-evidence.md#嵌套结果回收先复用原生前台返回)，无需因此另加轮询或回调层。确需后台并行时，先明确哪个任务接收结果、由谁继续整合。局限：复测仅覆盖三种非交互入口的标记任务；显式后台调用仍有未唤醒报告，升级不等于旧任务自动恢复。**[一手／社区；研究：采用判断]**

**观察工作要持续到子任务结束以后，就交给负责后续交付的主任务。** ✅ 在原授权范围内，让实施子任务返回任务 ID／PR 与 SHA，由主任务用现有入口继续查询 CI 或远程任务；短命子任务不默认启动一个留给父任务等待的后台 watcher。已启动的进程须核宿主是否真正移交所有权、结果投递与恢复记录，不能只凭“已移交”回执继续等。Hermes 的[故障报告、发布实现与反例](research/2026-10-12-community-source-records.md#观察者要比实施子任务活得久)支持这一选择，不是 Codex 的内置生命周期契约。局限：已有公开修复只覆盖部分路径；主任务负责接续不等于宿主保证常驻或跨重启送达，不因此扩大后台任务权限或新建服务。**[一手／社区；经验：采用判断]**

**跨执行者派发前，先确认回执丢失后仍能找到同一任务。** 优先复用双方可读取的既有 issue／PR 或任务记录，将身份与基线、交付版本和接收结果关联；需要长时间异步执行时，先核可用的查询入口及记录保留范围。CAO 的[固定修复与未闭合缺口](research/2026-10-12-long-task-evidence.md#跨执行者派发先保证任务身份可重新发现)表明，结果已保存也可能因查询 ID 未送达而无法取回；仅有去重键也不证明任务已投递。已有载体足够时不另建编排层，结果未知仍按 §9 先对账。局限：公开源码与设计契约不能证明真实恢复成功率，Git／PR 本身也不保证唤醒接手者。**[一手／社区；研究：采用判断]**

**收到空的“成功结果”时，先查宿主是否丢了子任务错误。** 在更换 worker 或重新派发之前，核对子任务的错误／结束原因与父任务收到的状态；空评审不能计为“没有发现”，也不能据此断定没有已有产物。确认是状态转换缺陷时，优先核对原生修复及适用版本，保留原来的子任务 ID、核对产物后再续接，不靠放宽下游验收继续。OpenCode 的[失败变空成功修复链](research/2026-10-12-development-conditions.md#委派失败被转换为空成功父任务已经收集也可能误判)支持这一处置；合法无文本结束仍须与异常区分。局限：修复只覆盖特定错误路径，不能证明弱模型委派或长程完成率已改善。**[一手／社区；经验：采用判断]**

**续接指令已接受，也可能还没被处理。** 子任务长时间没有新结果时，先查原任务的最后执行记录、待审批／待工具状态和续接指令是否已处理，避免反复发送同一催促；恢复后先核对最新目标与已被取代的要求，再继续剩余工作。dot 的[公开阻塞报告](https://github.com/openai/codex/issues/51610)出现 `steered` 回执后延迟集中收到 follow-up；Codex 固定源码也区分接受与后续处理，见[输入边界核对](research/2026-10-12-development-conditions.md#dot-长任务续接接受处理与停止范围)。**[社区；一手；经验：处置建议]** 局限：两者不能据此认定同一根因，回执与运行状态都不能单独证明指令已执行。

**子任务失败，按原验收决定接管、降级或暂停。** ✅ 必需检查可换执行者，但保留原验收门槛，包括独立审阅；完成不了就暂停该项交付。已约定可选的补充可标为不可用，继续不依赖它的交付。切换前先停共享状态的写入者、核对产物；停不掉就暂停相关交付。[gstack失败策略与修复](research/2026-10-12-long-task-evidence.md#可选子任务可降级必要验收换执行者)支持这种分流，尚未证明超时恢复效果。**[一手；研究：采用判断]**

给整棵任务树设生命周期预算；并发上限之外还要限制总调用。检查结果按版本、diff、命令、依赖和环境复用。评审聚焦可复现的正确性问题，不收敛时换方法或报告阻塞；小型 grep、机械修改直接做。

主要依据：官方子 Agent 指南要求主任务整合结果；#40932 报告结果投递停滞，#38989 报告递归评审和重复测试。**[一手；社区]** 局限：提示“不要提前结束”无法独自修复投递与唤醒故障，必要结果仍须实际收集、验证。

### 接手 CI：沿同一运行取回当前证据

**✅ 旧观察者没返回时，先用仓库、提交SHA和run ID找回远端结果，不先重跑CI或重新实施补丁。** Agent先核当前attempt与目标SHA，再取该attempt的jobs／相关steps；人核这些检查是否覆盖原验收，而不是只看一个绿色总状态。[经验；2026-10-24公开案例只读复核]

例如接手[cli/cli PR14804](https://github.com/cli/cli/pull/14804)在固定`fa812ef2b1ab1240ca023b7a4b720cbeef7fbdcd`上的[运行40001614534](https://github.com/cli/cli/actions/runs/40001614534)：旧attempt1已结束但结论为`action_required`，jobs=0；本次读取的当前attempt2为success，六个job均完成。第一轮不是测试失败，也不是空jobs就算通过；现在可以依据第二轮接收这条workflow，不继续沿用旧阻塞。[一手：GitHub实际响应]

已有获准的GitHub CLI入口时，可按这个案例查询；没有run ID先按精确SHA与workflow定位，不取全仓“最新一条”。下列CLI参数按[原生文档](https://cli.github.com/manual/gh_run_view)和[固定实现](https://github.com/cli/cli/blob/4f2cfe92e3499f8581bf39db77e0a1431fa7b55c/pkg/cmd/run/shared/shared.go)核对；本仓实际使用等价GitHub GET读取，未运行gh客户端。[一手／源码；本仓只读核对]

```bash
gh run list --repo cli/cli --commit fa812ef2b1ab1240ca023b7a4b720cbeef7fbdcd --workflow go.yml
gh run view 40001614534 --repo cli/cli --attempt 1 --json headSha,status,conclusion,jobs
gh run view 40001614534 --repo cli/cli --attempt 2 --json headSha,status,conclusion,jobs
```

直接API入口：[attempt1](https://api.github.com/repos/cli/cli/actions/runs/40001614534/attempts/1)及[jobs](https://api.github.com/repos/cli/cli/actions/runs/40001614534/attempts/1/jobs?per_page=100)、[attempt2 jobs](https://api.github.com/repos/cli/cli/actions/runs/40001614534/attempts/2/jobs?per_page=100)。其他运行先查当前`run_attempt`；取全分页并核job的SHA，不把截断列表当完整检查。job的steps也须回[该SHA的workflow](https://github.com/cli/cli/blob/fa812ef2b1ab1240ca023b7a4b720cbeef7fbdcd/.github/workflows/go.yml)理解：本例Windows／macOS的debug-overrides步骤按条件跳过，不能一见skipped就认定失败。[一手：真实响应／固定workflow]

交回run URL、SHA、attempt、相关job ID和剩余验收；仍在运行就由负责交付的主任务沿同一ID接续。另一个[真实使用者的多attempt产物问题](https://github.com/cli/cli/issues/12437)说明同run或同名artifact不能证明是本次产物。本例没有读取日志或下载artifact，也不证明PR全部必需检查、合并提交或最终产品通过；只把旧交接更新成当前这一条workflow的证据。[社区／本仓核对／经验]

## 6. 工作树隔离不是权限隔离

**先让每个任务有能启动、能观察的验证路径，再延长运行时间。** [Cursor环境复盘（2026-07-30）](https://cursor.com/blog/cloud-agent-environment)报告：只补启动Skill帮助有限，真正简化的是统一启动入口与长进程管理。与[OpenAI自用harness](https://openai.com/index/harness-engineering/)逐worktree运行应用的做法相比，共同可借的是把启动和检查变成稳定工具能力，而非给模型更多守候职责。默认复用现有启动脚本，按失败点补最小缺口；人核跨任务状态污染、真实行为覆盖及维护负担，不默认搭一套常驻平台。[一手：团队自报；研究：同题比较，未测净收益]

✅ 写入前核对真实 cwd、仓库根、分支与目标路径；收到 commit 后核对祖先和差异范围。需要硬隔离时使用 OS、容器或沙箱实施权限，不能只在模板写“只读”。**[经验：设计]**

主要依据：Superpowers #1040、#2050 曾报告研究返回主 checkout 路径后写错位置、子任务提交到 main。**[社区：历史单例]** 局限：worktree 共享部分 Git 状态和机器资源，无法单独提供权限隔离。

**并行编辑时，验收对象应固定到本次要发布的树。** ✅ 先界定文件归属，再由整合者仅暂存本单元文件；检查 `git diff --cached --check` 和暂存差异，从 `git write-tree` 得到树 SHA 并归档到独立目录运行检查，提交后核对 commit 的 tree 与受检树一致。共享工作区的检查结果可能混入其他单元，不能直接套在某次提交上。**[经验：本仓库单例的采用建议]** 新文件含尾空格但尚未跟踪时，普通 `git diff --check` 返回 0；暂存后 `git diff --cached --check` 返回 2 并指出该行，已在临时仓库确定性复现。**[经验：Git 行为复现，2026-10-16]** 局限：这不是原返工现场日志的重放，也未证明减少多少返工；归档只包含 Git 树内文件，所需依赖仍须明确，固定受检输入不等于权限隔离或真实产品运行验证。

## 7. 预算与停止：把状态说清楚

✅ 明确区分已验证完成、缺权限/输入而阻塞、预算用尽、用户暂停和失败；预算用尽就保存剩余工作，不改验收标准。遇到状态版本冲突先重新读取，再决定更新。**[经验：设计]**

dot 的 Pause 只停止当前主任务；需要停止委派任务或未来排程时，分别核查 Activity 与 Scheduled，不能把暂停主任务当作全部工作已停。**[一手：[官方停止范围](https://learn.chatgpt.com/docs/dots/controls#stop-work)]**

比较方案时分开记录缓存/非缓存输入、输出、调用数、重试、子任务、墙钟、人类审查时间和实际计费；推理若属输出子集，不重复相加。

自建 API 调用的请求超时、重试次数与整项任务截止时间需分别核实，按 [16 §4.5](16-building-agents.md#45-安全与成本)选择已有控制；不能由一个 `timeout` 字段推定整项任务已受限。**[研究：采用判断]**

主要依据：官方 Goals 指南包含可度量目标、验证、预算及停止原因；app-server 源码区分关闭拒绝新工作、历史读取失败和历史耗尽，并用 `expectedRevision` 检测实验性状态更新冲突。**[一手]** 局限：客户端支持范围和实际计费需分别核对，不能从源码能力或 API 估值推定当前产品行为与订阅扣额。

### 7.1 已有完成标准，也可能提前停止

✅ 阶段成果形成后，继续可独立推进的授权工作；平台边界导致停止时记录暂停和接续点。🧪 可对确定性缺口试受限 Stop 检查，避免无条件催促循环。**[研究：采用判断]**

主要依据：#52345 报告知道未完成仍结束，#50771 记录承认修正后没有行动；源码存在 `needs_follow_up` 与 Stop hook 续接路径。**[社区；一手]** 局限：补写标准或另一个 LLM 判“通过”都不能替代执行与验证；部署根因仍需复现，见[证据核对](research/2026-10-10-codex-continuity.md)。

## 8. 效果校准：哪些问题仍值得实测

本页已作机制与采用选择；后续实测用于校准当前模型下的恢复效果、人工介入与总投入，不把尚无通用排名等同于所有条件建议都未比较。[研究]

🧪 从最可能误报完成的失败路径选一项实测：测试通过后又改代码、恢复时进程失效、worker 只报进度、外部写入回执丢失。固定任务和预算，比较结果质量、成本与人工审查时间。技能分开测发现、触发、执行与结果。**[经验：实验设计]**

主要依据：本仓库已有确定性检查与模拟引擎回归，负面样例和后续实验矩阵见[研究记录](research/2026-10-12-long-task-evidence.md#待运行实验矩阵)与[实测记录](19-experiments.md)。读取完整报告并保留原退出码，零测试、skipped 或截断输出都要核查。**[经验：仓库实测]** 局限：当前这些检查尚不能回答真实模型跨会话的成功率是否提高。

## 9. 超时后，动作究竟发生了吗

✅ 先按副作用决定重试策略，结果未知时标记 `unknown` 并对账。**[经验：工程建议]**

- 只读：有限退避重试，核对结果时效
- 可重复计算：固定输入与输出位置，防止覆盖其他运行
- 本地编辑：先看当前版本与 diff，再决定是否重放补丁；恢复暂存／提交前，对照操作开始前保存的分支和 HEAD，不符或缺失先对账，不能重取当前值冒充原预期
- 外部写入：先查操作状态；服务支持时持久化幂等键，同一操作重试复用原键，新操作才换键

本地前置检查与远端基线校验保护不同边界：同一 HEAD 也可能已切到错误分支；已发布成果也可能对应不同 commit SHA。结合发布回执、tree 和内容判断是否还有实质增量，不为已完成成果重写同义状态。检查不是原子锁，仍须串行整合，发布前核对生成提交的父提交与预期基线、tree 与受检树一致。见[本仓单例与最小 Git 检查](research/2026-10-12-long-task-evidence.md#续接提交前检查分支与本地基线)。**[经验：单仓观察与确定性检查]** 局限：不能拦截所有同版本语义重复，也未证明真实恢复成功率提高。

Code Mode 提示运行时被替换时，先核对先前工具操作与外部任务的实际结果，再用新 `exec` 重建必要状态；cell 与 `store` 值丢失，不代表外部命令已取消或副作用已撤销，不能盲目重放。见[恢复证据与版本边界](research/2026-10-10-codex-continuity.md#5-2026-10-13解释器重置先对账再恢复)。**[一手：源码；研究：采用判断]**

主要依据：请求超时可能发生在执行前、执行中或完成后丢回执；MCP 传输恢复要求与业务去重是不同层次。**[一手：规范；经验：工程推论]** 局限：自加 HTTP 头、JSON-RPC request ID 或重新发起请求，都无法代替接收服务真正支持的幂等处理。

### 模型回退：先区分请求续接与工具重放

✅ **给编码 Agent 加供应商回退时，保留原生恢复入口；先验备用模型能接收本轮工具／历史，再验失败发生在什么边界。** 已交付工具调用片段后，不把“尚无文字”当作尚未输出；工具已完成但回执未知时，仍按本节核结果，换模型或换 tool-call ID 都不授权重做。LiteLLM 1.106.1 与 PydanticAI 2.58.0 的固定实现分别以已生成内容、首个模型事件约束流式回退；原生模型事件与HTTP分块不是同一粒度。不能把滚动文档里的新开关当发行版本已有能力。[一手；研究：采用默认，见[P47比较](research/2026-10-12-long-task-evidence.md#p47模型回退历史兼容不等于工具可重放)]

**第二次改配置也要验。** 保存／重载重试配置后，核运行时策略是否需要重新绑定。OpenAI Agents 0.24.0 明确不序列化 retry policy；这不是漏洞或安全绕过。保留原流程的条件是兼容性、失败边界和重载后的策略都可解释；否则关闭这条自动回退并保留可恢复的失败，不删工具历史求通过。局限：本仓只复核固定源码摘录与配置对象，未运行三套SDK或证明外部动作恰好一次。[一手；经验：限定离线复核]

**改模型与改工具执行绑定分开验。** 只换模型，不等于要迁移耐久宿主；改工作目录、工具定义或extension前，先让已发出的旧调用落定，或明确保留其执行绑定。Pi Durable固定文档中，请求准备时锁定模型与提供的工具清单，工具阶段却解析当前agent／cwd，配置改变可影响旧调用。Agent列出受影响调用与实际目标，人核迁移后的副作用；旧绑定不能保留已撤销权限。解释不清就暂停这些调用，保留原记录。[固定契约与二改判据](research/2026-10-12-long-task-evidence.md#p47续查配置改变后旧工具在哪执行)。[一手／研究：文档契约，未运行宿主]

### 恢复其他子任务时，已完成动作有没有重做

✅ **把外部写入流程改为嵌套委派，或更换 checkpoint 续接入口时，同时核最终状态和已完成动作的执行记录。** LangGraph 的[修复](https://github.com/langchain-ai/langgraph/pull/9315)处理了最终状态正确、已完成兄弟任务却被重跑的问题；保存过审批或 issue 关闭不能代替这项验收。优先核原生修复及实际版本，不靠增加摘要或审批次数补救。[一手／社区／研究]

正常恢复可以重新进入尚未完成的中断节点，主动回放旧 checkpoint 也可以有意重跑；不要把两者一律禁止。只读调查不必增加副作用检查。**局限：公开复测主要采用合成副作用，不能推出所有 Agent 的故障率或外部服务保证；所核发行源码尚未包含修复。** 版本、反例和复测范围见[研究记录](research/2026-10-12-long-task-evidence.md#完成状态正确已完成动作仍可能被重新执行)。[研究]

### Git 发布：只传差异，失败从已核实的断点继续

✅ 已获发布授权且目标环境具备 Git 认证时，优先本地 `git commit` 后 `git push`，一次推送整批提交。连接器已获 GitHub 授权，不代表 shell 已有 Git 凭据；无人值守前先确认实际可用的发布路线，不能靠重复 push 补齐认证。**[经验：采用建议与环境观察]**

若只能用已授权连接器发布：

1. 读取最新 `main` 的 commit 与 tree；本地 `origin/main` 可能过期，使用 `git fetch origin main` 后核对 `FETCH_HEAD`，或直接读取远端 ref。基线前进时，先整合并重新检查，不把旧快照整页覆盖回去
2. 发布输入固定到已检查的提交，按该提交读取相对最新基线的变更内容，不从仍在并行修改的工作目录取文件；删除也显式表示，复用 `base_tree` 保留其余内容
3. 工具允许时尽量一次写入全部变化；只有工具上限或调用失败需要时才拆分，不设固定文件数。`create_tree` 成功后仍要创建 commit、更新目标 ref，不能把一次写入称为整个发布完成
4. 失败或回执丢失先查远端 ref、已返回的 tree／commit SHA 与内容；分步上传时，回执没记录的 blob 也可能已经存在：从受检提交以 `git rev-parse <commit>:<path>` 取预期对象 ID，核对远端对象后复用，只补确认缺失的内容；对象存在不代表 ref 已发布。保存已核实结果，只继续未完成步骤。若 `main` 已前进，重查差异并处理冲突，不强推覆盖
5. 以非强制方式更新 ref；发布后回读目标 ref、commit／tree SHA 和实际文件差异，确认指向预期成果；远端 CI 的结果另核，不能用本地检查代替

主要依据：[blob 查询](https://docs.github.com/en/rest/git/blobs#get-a-blob)可按对象 ID 核内容；[GitHub tree API](https://docs.github.com/en/rest/git/trees#create-a-tree)支持基树与多条变更，省略基树会丢掉未列文件；[ref API](https://docs.github.com/en/rest/git/refs#update-a-reference)支持非强制更新。**[一手；经验：恢复策略]** 关键局限：实际连接器可能有不同的载荷、权限或分支保护限制，批量能力与成功回执必须按当前工具核实，不能为减调用绕过审批。核验范围见[研究记录](research/2026-10-12-development-conditions.md#dot-效率选择少一层包装不等于少一项验收)。

**本仓库单例（2026-10-16）**：E4 发布前主干已前进到 `244bc9f`，重新整合后的 [`c9e71c7`](https://github.com/dbvv1/a1dbv/commit/c9e71c790050dd8b410de10d0b05c3fcfc0fe2c2)以它为父提交；后续 [`7a475db`](https://github.com/dbvv1/a1dbv/commit/7a475db46245fb88ed6869b70d9b2a315a34be48) 的发布回执分别记录 tree、commit 和 ref 更新，回读核对五个变更文件与本地受检提交内容相等。这支持把“整合、受检版本、发布、回读”分开核实；不是跨仓库成功率、长任务不中断或 hosted CI 通过的证明。**[经验：Git 历史与发布回读]**

## 10. 工具契约要写到失败方式

✅ 为无人值守工具写清输入约束、所需权限、成功究竟是接受/完成/验证、错误分类、副作用与可撤销性、重复调用语义，以及完整日志位置和截断处理。客户端遇到 MRTR `input_required` 应保留调用状态、收集输入后继续，按规范兼容旧结果。**[经验：工程建议]**

主要依据：MCP 工具规范提供 `inputSchema`、annotations 与 `resultType` 等契约信息。**[一手]** 局限：schema 和 annotations 不能替代客户端/服务端验证与权限执行，“还需输入”也不能记成业务完成。

## 11. Hook 的价值取决于故障路径

✅ 保护敏感写入前，测试放行、拒绝、超时、无效输出与解释器缺失，检查 matcher 覆盖全部写入口；普通格式化可选不同故障策略。先核对[失败策略与版本边界](06-hooks-and-guardrails.md#返回值)，再采用字段。**[经验：工程建议]**

主要依据：Claude Code 文档与 changelog 引入 `onFailure: "block"` 并修复部分 managed hooks 行为，但事件和异步路径有排除条件。**[一手]** 局限：Hook 的模型判断或失败策略不能统一保证 fail-closed，最终访问边界仍依赖 OS 与服务端。

## 12. 记忆作为候选变更，而非事实来源

✅ 记忆附项目、来源和失效条件，历史经验先成为待审候选；当前配置、源码和命令输出优先，冲突时更新或删除旧记忆。临时故障不直接升级为永久规则。凭证、个人信息和外部页面指令不进入可传播记忆。**[经验：工程建议]**

交接传目标、约束、已验证事实、产物位置和未解决问题；接收者再次核实会影响写操作的假设。

主要依据：Gemini CLI Auto Memory 的文档设计是从历史提出 patch/Skill 草稿，存入 inbox 后由用户审阅应用。**[一手]** 局限：这是实验性、默认关闭的功能设计，是否可用仍须按安装版本验证。
