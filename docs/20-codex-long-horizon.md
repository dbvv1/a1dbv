# 20 · Codex 长程任务：可恢复、可验收、可控成本

> 核实时间：2026-10-11（UTC+8；检索截至 2026-10-10 UTC）。
> 范围：Codex 官方当前文档、近期 GitHub 原帖，以及本仓库的执行模板。本文的设计建议不等于已经测得生产力提升；模型驱动的恢复实验尚未运行。

## 1. 先选任务规模，再选机制

本篇是 [07 工作流](07-workflows.md)、[08 多 Agent](08-multi-agent.md)、[09 评审](09-review-and-quality.md) 的执行补充，不要求每个任务都采用全套流程。

| 工作 | 建议起点 | 何时增加机制 |
|---|---|---|
| 文案、一个明确的小修复 | 直接改 + 对应检查 | 风险或验收不清才补计划 |
| 多文件功能 | 可观察的验收项 + 依赖顺序 + 最终集成检查 | 可独立的大块调查再拆子任务 |
| 跨会话、容易中断的任务 | 以上 + 恢复记录 + 版本绑定的证据 | 有程序消费记录时才引入 JSON |
| 外部写入、部署、数据变更 | 以上 + 明确授权 + 结果核对 | 不确定是否执行成功时先查远端，不能盲重试 |

**[一手]** OpenAI 2026-09-11 的 [Astra 提示与 Skills 指南](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) 建议缩短常驻指令、按需读文档、避免复杂技能流程束缚模型。它针对特定模型代际，不证明所有脚手架都应删除。保留项目特有命令、安全边界和验收要求。

**[经验：设计]** 优化目标应是“单位成本内完成并验证的工作”，不是运行小时数、agent 数量或文档体积。

## 2. Codex 原生配置：先验证实际加载，再谈效果

- 项目指令入口是 `AGENTS.md`；同层 `AGENTS.override.md` 优先，项目指导默认总上限 32 KiB。更长不是更强；会话中修改文件也不证明已自动重载。**[一手：[AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)]**
- 项目技能放入 `.agents/skills/<name>/SKILL.md`；初始目录加载元信息，再按需加载正文。目录可发现、触发成功、步骤执行、结果正确是四个不同检查。**[一手：[Build skills](https://learn.chatgpt.com/docs/build-skills)]**
- 子 Agent 配置、角色和权限以当前客户端文档为准；本地 Codex 与托管 Work 不应混为一种权限模型。**[一手：[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)]**
- 可参考 [Codex 示例](../templates/codex/README.md)。它是可选配置，不是已安装配置；Sol 6.1 / high 仅是该示例的成本与能力选择，需按任务做对照。

**采用门槛**：配置能解析 → 当前运行时接受 → 实际目录/角色可见 → 正例触发、近邻反例不触发 → 输出满足契约。只完成前两步不能宣称 Skill 有效。

## 3. 完成条件来自验收原文，不能由总结重新定义

给重要行为稳定 ID，例如 AC-01“有效输入成功”、AC-02“非法输入有明确失败”、AC-03“取消后不继续产生副作用”。一条用户故事可以含多个验收场景，不能把场景数量压成一个勾。

**[社区：单例]** [Spec Kit #3752](https://github.com/github/spec-kit/issues/3752) 报告把 16 个场景压成 4 条故事导致误判完成；此处借鉴的是故障模式，不是已测出的普遍发生率。

本仓库提供 [独立 spec 与运行报告](../templates/long-task/README.md) 和 `scripts/validate_task.py`：

- 检查验收/check ID 是否遗漏、重复、错配
- 必须通过的检查不能是 failed、blocked 或 not_run
- 证据引用必须绑定报告中的工作版本
- 必要 checkpoint 和 worker 不能仍在运行或缺失
- 因预算耗尽停止不等于完成；恰好在预算内完成可正常通过

**边界**：脚本只核对记录一致性，不执行检查、不打开证据、不证明证据真实，也不防止同时篡改 spec 与报告。将验收输入放在独立评审/权限边界，并让真实测试系统保留可核查输出。不要把这个小校验器称为完整 agent harness。

## 4. 恢复包必须包含最新任务，而非最长历史

**[一手]** [OpenAI 长时任务实验](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex) 使用持久化需求、计划和状态；报告的约 25 小时运行是实验，不是对任意任务的承诺。[ExecPlans 旧文](https://developers.openai.com/cookbook/articles/codex_exec_plans) 已标为 archived；它的文件名是约定，不是系统保证。

**[经验：设计]** 一个可恢复的快照应记录：

1. 当前 task/run ID，最新目标、约束、已取消或被取代的要求
2. 仓库、分支、base commit、工作树差异或内容指纹
3. 已完成动作与已观察到的结果，不能只记计划做什么
4. 验收 spec 版本、通过/失败/未运行的证据及其适用版本
5. 待收集的子任务、外部 job ID、未知结果、待授权动作
6. 下一步最小安全动作和停止条件

恢复时先核对现实状态：文件有没有变、worker 是否真的返回、外部动作是否已执行、授权是否仍覆盖当前目标。检查点是恢复材料，不是新增授权；不得保存密钥或模型内部思考过程。

**[社区：多个观察、非统计]** [Codex #42695](https://github.com/openai/codex/issues/42695) 有压缩后回到旧任务的报告；[PR #44659](https://github.com/openai/codex/pull/44659) 已合并触发元信息传播修复，但本轮未确认首次发布版本，也不能认为它修复了所有旧任务症状。[#38969](https://github.com/openai/codex/issues/38969) 的 10 月报告仍涉及压缩失败，不同环境的根因未必相同。不要把一个关闭的旧 issue 当作整个故障类别已消失。

**[经验：设计]** 恢复演练还应检查“记录存在但当前未加载”的状态：最新任务与取消指令、适用的路径规则/Skill 是否仍可见或可重载。不要把已激活标记当作指令正文仍在的证据。相关实现反例见 [03](03-context-engineering.md#43-实际运行中的反例)。

## 5. 子任务应缩短关键路径，不应制造评审树

**[一手]** 官方建议把边界清楚、读多写少的工作拆出去，并由主任务整合结果。**[经验：设计]** 每次委派最少带：明确问题、输入版本、读写范围、预期结果和验收方式。

需要区分四个时刻：worker 自称完成、结果送达、主任务收集、主任务验证。前一个不能替代后一个。

**[社区]** [#40932](https://github.com/openai/codex/issues/40932) 不仅有父任务过早结束，还包含等待中的结果投递停滞报告；“不要提前结束”这一句不能修复所有唤醒路径。[#38989](https://github.com/openai/codex/issues/38989) 报告大量递归评审、重复测试和巨量记录 token，但记录 token 不是实际账单。

建议：
- 给整棵任务树设置可解释的生命周期预算；并发上限不等于总调用上限
- 独立文件可并行写，同一表面有唯一整合负责人
- 检查结果按版本、diff、命令、依赖和相关环境复用；代码变了就重新判断有效性
- 评审集中在可复现的正确性问题；反复修改没有收敛时换方法或报告阻塞
- 小型 grep、机械修改不默认套“实现者 + 两轮独立 reviewer”

## 6. 工作树隔离不是权限隔离

**[社区：单例，历史缺陷]** [Superpowers #1040](https://github.com/obra/superpowers/issues/1040) 报告研究返回主 checkout 绝对路径后写错位置；[#2050](https://github.com/obra/superpowers/issues/2050) 报告子任务提交到 main，后者已关闭，不能作为当前所有版本仍受影响的证据。

**[经验：设计]** 写入前核对真实 cwd、仓库根、分支和目标路径；返回的 commit 要核对祖先与差异范围。worktree 仍共享部分 Git 状态和机器资源；硬隔离由操作系统、容器或沙箱提供。模板中写“只读”不等于实际没有 Bash 写权限。

## 7. 预算与停止：把状态说清楚

官方 [Goals 指南](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex) 描述可度量目标、验证、预算和停止原因，标注 Codex 0.128.0 起支持。**[一手]** 这不表示 dot 或任何 API runner 都暴露同一 `/goal` 命令。

合理停止状态包括：已验证完成、缺权限/输入而阻塞、预算用尽、用户暂停、失败。预算用尽时保存剩余工作，不能修改验收标准把它变成成功。

比较方案时分别记：缓存输入、非缓存输入、输出（推理是否为子集）、调用数、重试、子任务、墙钟时间、人类审查时间和实际计费信息。API 估值不能替代订阅额度扣除；模型更便宜也不意味着完成同一任务更省。

## 8. 下一轮实测：不把建议写成实验结论

| 实验 | 负面样例 | 判定 |
|---|---|---|
| 恢复 | 写完未测、测试失败、测试通过后又改代码 | 不用旧绿灯宣称新版本完成 |
| 验收 | 缺 ID、只测快乐路径、零测试、skipped | 明确 incomplete/blocked |
| 子任务 | 仅进度、迟到、失败、结果未收集 | 必要结果未验证前不收尾 |
| 权限 | 目标变了、授权过期、外部写结果未知 | 先核对，不重放危险动作 |
| 成本 | 单 agent、分组读、逐项 reviewer | 同任务、同预算、记录质量与成本 |
| 技能 | 正例两种说法、近邻反例、旧版本配置 | 分开测发现、触发、执行、结果 |

目前已运行的仅是本轮仓库的确定性检查和模拟引擎回归，见 [19 实测记录](19-experiments.md)。上表的真实模型/跨会话实验仍待执行，不因为脚本单测通过就宣布长程成功率提高。
