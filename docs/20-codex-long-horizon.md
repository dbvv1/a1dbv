## 1. 30 秒：按反馈与恢复需要选机制

**✅〔10 月确认〕把完整可验收结果交给 Agent 连续执行，按反馈缺口与中断风险补机制，不按任务体量设自主上限。** 无人值守是一段执行方式，不是无人负责的整个生命周期；验证失真、重复返工不收敛或外部结果不明时，收紧对应范围。代际复核 2026-10-21，Astra／Opus 5.5 与当前原生 harness；标签定义见 [00](00-state-of-ai-coding.md#30-秒结论)。

| 工作 | 建议起点 |
|---|---|
| 文案、明确的小修复〔跨代保留〕 | 直接改 + 对应检查；风险或验收不清才补计划 |
| 多文件功能〔跨代保留〕 | 可观察的验收项 + 依赖顺序 + 最终集成检查 |
| 跨会话、容易中断〔跨代保留〕 | 按 §3–§4 接回原任务：保留恢复记录与版本绑定证据；跨执行者派发前确认失联后仍能找回同一任务；有程序消费记录才用 JSON |

|---|---|---|
| 进程断开，但已产出的状态仍有效 | 原生继续；确需跨进程保存在途工具调用状态时，才用耐久宿主复用原任务与检查点 | 核待完成调用与外部回执。状态污染或无法确定副作用时，不盲目续跑 |

## 3. 完成条件来自验收原文，不能由总结重新定义

**✅ 接回一个停下的完整开发任务，默认组合是原生继续或原任务 ID、现有 Git 任务／产物记录、当前目标重判、版本绑定的检查复用和最终串行接收。** 先核当前目标、停因和产物版本，再完成剩余一步；完成与否仍按原验收原文判断，不由接手总结重定义。只有旧状态无法可靠接收时才重启，只有确需跨进程保存工具调用状态时才用耐久执行器。与 [08](08-multi-agent.md) 的分工：08 决定哪些工作可拆并行、结果怎样整合；本节处理同一任务停后凭什么、从哪一步继续。

| 接手时所处的状态 | 默认路线 | 换路线或撤回的条件 |
|---|---|---|
| 会话或进程结束，工作树、产物和外部回执仍有效，目标未变 | 原生继续或原任务 ID；复用已有产物与仍适用的检查 | 待完成工具调用或外部回执不明时先对账；状态污染就不盲目续跑 |
| 目标、需求或负责人已变，或原判断的前提被推翻 | 保持原任务，重判目标与决定；保留已确认事实，只补变化和剩余验收 | 旧产物与新目标冲突时另存旧结果；不用旧结论替代新授权 |
| 已走入错误路径，前向修复不收敛 | 有可核恢复点时受控回退，保留失败经验；没有则在保留旧产物后重启 | 恢复范围须明确；外部状态和 Git 身份单独对账，不重放已完成写入 |
| 旧状态无法可靠接收：树归属不明、关键产物缺失、宿主不可用 | 从最后一个已核产物重启，或交给新执行者接收 | 保留原记录和失败经验；不把“重新开始”说成恢复 |
| 需要跨进程保存在途工具调用状态 | 才选耐久执行器，复用原任务与检查点 | 原生继续和 Git 记录够用时不装编排器；执行器不自动获得新权限 |

同会话 resume 适合状态完整且目标未变；耐久执行器适合确需跨进程保存工具调用状态；重新开始只在旧状态不能可靠接收（含错误路径无恢复点）时选。不要把所有长任务都装上编排器，也不要把 Git 记录当成宿主恢复保证。

✅ 给重要行为稳定 ID，分别覆盖成功、非法输入、取消后的副作用；保留一条故事中的每个验收场景。[独立 spec 与运行报告](../templates/long-task/README.md)可检查漏项、重复/错配 ID、证据版本和未完成 worker。验收输入由独立评审或权限边界保护，真实测试输出单独留存。

Spec Kit #3752 报告把 16 个场景压成 4 条故事后误判完成；本仓库校验器要求必需检查 passed、证据绑定工作版本、登记的 checkpoint/worker 完成，预算耗尽也不能记成成功。局限：校验器只核对记录一致性，证据真伪、实际代码正确性和 spec 被共同篡改仍需外部验证。

**恢复成功以后，还要按当前目标接收。** River 会把待升级依赖接到当前锁文件，而非覆盖邻接升级；人已接管的分支不再改。合入后继续核主干实际依赖与任务源，再关闭事项。借用的是“当前版本与真实结果一致才完成”，不是要求所有项目接入安全平台；原需求证明补丁方向错了，就撤回建议。见[续接研究](research/2026-10-12-long-task-evidence.md#p60续接从恢复执行到完成当前目标)。

### 真实采用：一次跨轮次接续怎样改变下一步

**✅ 已有公开任务链证明的是“在这一固定任务中，接回后继续交付”可行，不是新的恢复能力或效率提升。** 这条链对应上面的默认组合：原任务 ID 未换，公开任务记录承载目标与产物，负责人重判前提，检查绑定固定版本，最终由负责人串行接收。性能路线任务围绕 Sphinx 的 C++ 符号查找，首轮由调查执行者交回具体负结果：没有同时满足条件的候选，未运行当前基线，也未证明收益。负责人读公开记录后没有重开选题，而是纠正了两个会改变行动的前提：历史 assignee 和旧分支不证明当前活跃，缺某几套工具链是该执行席的环境事实，不是普遍权限门槛。原任务和目标保持，首轮候选调查、已确认的负结果及独立审查保留；行动从“停止立项”改为在同一任务内窄查固定项目、复现真实负载，条件成立才做可撤回优化。随后同任务完成真实模型实施和实际 CLI 消费者验收；最终接收保留原有提交父链，只审查新增正文差量和受影响检查，未重跑已覆盖的历史工作。首轮没有可复用的运行树，验证只对应公开调查记录；续接的构建、输出差分和测试绑定固定源码与临时差量的受检树；最终接收复用这些检查，只对新增正文做窄范围核对。

这条链说明：改变行动的是“哪条前提被推翻”，不是新增长期记忆；被保留的是原目标、已确认事实和未受影响的验证；被重判的是建立在错误前提上的排除结论。最终产物在[公开任务记录](collaboration/local-jobs/A-PERFORMANCE-ROUTE-001.md)与 [15 的任务路线入口](15-task-playbooks.md#7-性能优化)。无法从公开记录核实的部分（是否为同一模型、同一宿主会话或连续执行）保持未知；因此它不证明断电恢复、同模型会话 resume、耐久宿主保证或效率提升。

**依据**：[社区：单例] Spec Kit #3752；[经验] 本仓库校验器实现；[一手：独立采用自报] River；[研究] AgentRewind 的继续／重启比较、当前目标接收；[一手] Pi Durable 的中断任务与工具重试边界；[经验：本仓公开任务与提交链] [A-PERFORMANCE-ROUTE-001](collaboration/local-jobs/A-PERFORMANCE-ROUTE-001.md)（跨轮次接续，不读取私人日志或会话）；核实 2026-10-25。

## 4. 恢复包必须包含最新任务，而非最长历史

**✅ 接回时先读“最新目标与约束”，再读历史；最新负责人决定和取消项优先于旧计划，历史只用于解释为什么停、哪些决定仍成立。** 在现有任务记录保留六项信息，简单任务不必另建文档。

1. task/run ID、最新目标与约束，以及取消或被取代的要求
2. 仓库、分支、base commit 与工作树差异或内容指纹
3. 已完成动作及观察到的结果，关键决定的理由
4. 验收 spec 版本，以及通过、失败、未运行证据适用的版本；[后续一轮全通过不替代未决旧项](22-agent-evaluation.md#连续需求先分清旧债新回归与测量问题)
5. 待收集子任务、外部 job ID、未知结果与待授权动作
6. 下一步最小安全动作与停止条件

短接手起点，可直接贴进现有任务记录或交接消息：

```text
接回 <task ID>：先读最新目标与约束（含取消/取代项）和停因；列出已有产物及对应版本、仍适用的检查、已失效前提和被重判的决定；从剩余最小一步开始，继续完成其余已授权实施与验收，直到原验收完成或出现明确阻塞。结果不明先对账，旧状态不可靠才重启。
```

**退出接回只有三种状态：按原验收完成、明确阻塞并留下恢复条件、判定旧状态不可可靠接收后另存重启。** 交接本身不是完成。产物无法对应受检版本时先核对版本；外部写入结果不明时暂停相关写入、查询实际结果；必需检查缺执行者时换已有权限的执行者，并继续不依赖阻塞的工作。只有授权冲突、实际新增权限／费用／外部承诺，或必须由人选择的业务差异才请人决定，不用“已接手”掩盖未完成项。

**把旧决定分三类，不要整份继承或整份推翻。** 仍成立的目标、约束和已核事实保留；建立在已被推翻前提上的排除、优先级和范围要重判；既有权限、成本和外部承诺核对是否仍有效，实际新增或冲突部分才重新确认。原任务记录保留旧判断和失败，只在其后写明哪条前提失效、由什么新证据取代。

可复制的 [checkpoint-resume Skill](../templates/codex/.agents/skills/checkpoint-resume/SKILL.md)沿现有记录保存与恢复，先核新要求、取消及接管，再续旧步骤；该 Skill 未验证自动加载或模型收益。

**恢复后先判断哪些检查仍适用，再决定重跑什么。** 沿既有交接记录核受检代码、输入、依赖与环境；只换提交SHA或合入无关文档时，可保留未受影响的结果。代码影响不明或执行环境已变，就复验相应路径；发布状态和精确提交CI仍须另核。两份[通用交接](../templates/generic/.claude/skills/handoff/SKILL.md)／[Codex恢复](../templates/codex/.agents/skills/checkpoint-resume/SKILL.md)模板同步此选择，不新增记录格式；这是指令修订，未测客户端自动加载或节省工时。

**有效状态被中断，优先继续；错误路径污染了工作树，才比较回退。** Pi Durable 的任务恢复与 AgentRewind 的失败路径恢复回答不同问题：前者保住可继续的运行，后者把上下文与受控文件一起退回，并保留失败经验。不要因一次进程退出清空任务，也不要只清聊天、留着坏文件继续试。见[续接研究](research/2026-10-12-long-task-evidence.md#p60续接从恢复执行到完成当前目标)。

**回退之前先核它能恢复什么。** AgentRewind 不撤销网络、外部服务或外部进程；工作区根目录的 .git 也不恢复。因此文件回去了，提交历史和外部事实仍可能向前。Agent 先对照当前分支、HEAD、文件差异及外部结果，人确认有权撤回的范围；范围不清就保留原状态并停止相关写入，不重放已完成操作。

同一交付物先确认原任务能否读取并继续，只补当前变化与必要依据；确实无法接续才交接上述信息。任务复用不替代独立评审，具体边界见 [dot 使用建议](01-agents/codex.md#长时运行与-dots按能力缺口增加任务)。

### 恢复时不能直接沿用的中间状态

**需求改变记录用途时，重查旧过滤条件，而非只保存旧理由。** Pydantic AI 的 interrupted 消息从“保存已有部分结果”扩展为“下一轮恢复信号”后，旧的“没有 tool result 就不记”条件使首个工具取消无法恢复；后续沿已有 repair 层补发空标记，见[累计演化与下游恢复验收](research/2026-10-12-development-conditions.md#累计到下一次需求保存重放整轮取消不是同一个契约)。恢复记录应指出失效的前提，验收则检查保存、反序列化、新实例继续使用的路径。

**续改失败时，也查新功能依赖的继承行为，不只看最新 diff。** 核对输入拒绝条件、缺值默认与错误传播，再补最小回归；已确认的新需求可以改变旧契约。[CodeThread 的两阶段比较](research/2026-10-12-development-conditions.md#codethread下一次修改失败先查继承了什么行为)提示静态复杂度不能代替这项诊断，故不默认增加复杂度门禁或全盘重写。局限是重建函数后的 Agent 续改实验，尚未证明这种诊断能降低真实接管工时。

**历史显示缺失时，先区分原始记录丢失与读取／投影停滞，再选恢复动作。** 对已确认的版本缺陷，先保留原数据、核对实际运行的后端是否包含修复，再用受支持的 resume 检查原来缺失的轮次；原生恢复足够时，不再增加修复脚本或直接改数据库。[Codex 的重复序号恢复报告](research/2026-10-10-codex-continuity.md#6-2026-10-14原生恢复已够时撤回手工修复)在不改 SQLite／JSONL 的条件下恢复了三轮历史。局限是特定 CLI 版本与故障形态的公开自报，不代表删除的原始数据、全部 Desktop 故障或任务语义都已恢复。

**压缩失败后，不把已出现的部分摘要当作恢复依据。** 先核对运行版本，通过正常续接／恢复检查原消息与工具结果；已有结果可核实时，不因压缩失败重跑副作用操作。官方修复将摘要记录延后到响应成功完成，见[失败压缩的提交边界](research/2026-10-12-long-task-evidence.md#失败压缩的提交边界)。局限是响应完成、历史替换与落盘成功仍是不同边界，且所核最新稳定／预发布 tag 尚未包含该修复。

### 交接时重新核对活资源与约束

恢复时先核对文件、worker、外部操作和授权；重建并检查进程、端口、浏览器与认证。确认最新任务、路径规则及 Skill 正文仍可见或可重载，不能只看“已激活”标记。检查点不新增授权，也不保存密钥或模型内部思考过程。

OpenAI 长时任务实验使用持久化需求、计划和状态；Codex 有压缩后回到旧任务、压缩失败的实际报告。连续任务评测也提示应分别检查旧约束和运行反馈是否可取得，因此保留无法从代码恢复的接口约定、决定理由与相关回归输出，需求取代旧决定时同步理由。局限：代码或聊天快照不能恢复全部活跃资源，这些证据也不足以要求已有记录可用的项目额外安装记忆平台。

**依据**：[一手] OpenAI 长时任务实验、Pydantic AI 需求与固定补丁、Codex 压缩修复；[社区] Codex 重复序号恢复复测、压缩失败报告；[研究] AgentRewind、CodeThread 与采用判断；[经验] checkpoint-resume／handoff 模板修订（2026-10-24）、本仓库采用判断；核实 2026-10-22。

### 4.1 任务未完，执行逻辑却要升级

**✅ 不紧急时，先到可核验边界再换版；不能等时，才走已验证的兼容续接。** 短工作段划分的是执行版本边界，完整目标、交付责任和后续检查仍连续，不按固定轮数重置或拆碎用户目标。

同题：代码 K 已提交、旧测试 A 通过、外部 CI 任务 J 未完；新版拆开测试节点并新增评审。三路都须接收 K、J 和剩余验收，下表是机制比较，非效果实测。

| 路线 | 同一任务怎样继续 | 采用与撤回 |
|---|---|---|
| 旧版排空 | 宿主固定旧执行代码，等当前运行结束，新版接余项 | 短期可结束时优先；保留旧 worker／依赖至排空。遇紧急安全问题、权限撤销或无法排空，停止依赖旧版继续的安排 |
| 兼容热续接 | 新逻辑仍识别旧节点、字段与在途位置，补新版要求 | 适合不能等待且兼容已验证的任务；代价是维护旧行为分支。新写丢失或状态不明就暂停相关写入 |
| 短工作段交接 | 当前运行在可核边界结束，新运行用新版接收 K、J | 适合频繁升级；在途任务须可查询且有接收者。无法交接就不强切，先补接收条件 |

**只用宿主确实提供的版本固定／兼容入口。** Temporal 与 LangGraph 的契约不同，不能据其例子推定托管 Codex 可固定旧后端；普通使用者沿产品支持的继续／交接入口，不为升级自建平台。

**迁移要验“旧状态 → 首次新写 → 冷读 → 下一轮”。** LangGraph 曾在旧记录可读、当轮返回正确时，丢掉内存后端迁移后的首次非 snapshot 写入；仅验旧记录不够。上游修复发行后，还要核实际加载的独立依赖与旧兼容补丁，确认测试验到原生实现，再退役对应补丁。

Agent 列受影响节点、字段和依赖，沿已有回归核新旧消息顺序／身份及下一轮恢复；人决定新要求是否追溯旧任务。K、命令和环境未变时，A 仍证明原范围；被验输入、验收语义或恢复数据改变才补验受影响部分，A 不自动满足新增评审。

**失败先停新任务进入坏版本，再对账。** 回旧部署不会撤销已写状态或外部动作，结果未知仍按 §9 处理。本节是运行／保存格式升级；请求回退和未决工具绑定分别见 [§9](#模型回退先区分请求续接与工具重放)，不新增控制层。

**依据**：[一手] Temporal 与 LangGraph 契约及公开修复链；[研究] 条件默认、机制比较、职责与证据复用、撤回边界；核实 2026-10-22。

### 接手 CI：沿同一运行取回当前证据

**✅ 旧观察者没返回时，先用仓库、提交SHA和run ID找回远端结果，不先重跑CI或重新实施补丁。** Agent先核当前attempt与目标SHA，再取该attempt的jobs／相关steps；人核这些检查是否覆盖原验收，而不是只看一个绿色总状态。

例如接手 cli/cli PR14804 在固定`fa812ef2b1ab1240ca023b7a4b720cbeef7fbdcd`上的运行40001614534：旧attempt1已结束但结论为`action_required`，jobs=0；当前attempt2为success，六个job均完成。第一轮不是测试失败，也不是空jobs就算通过；现在可以依据第二轮接收这条workflow，不继续沿用旧阻塞。

已有获准的GitHub CLI入口时，可按这个案例查询；没有run ID先按精确SHA与workflow定位，不取全仓“最新一条”。下列CLI参数按原生文档和固定实现核对；本仓实际使用等价GitHub GET读取，未运行gh客户端。

```bash
gh run list --repo cli/cli --commit fa812ef2b1ab1240ca023b7a4b720cbeef7fbdcd --workflow go.yml
gh run view 40001614534 --repo cli/cli --attempt 1 --json headSha,status,conclusion,jobs
gh run view 40001614534 --repo cli/cli --attempt 2 --json headSha,status,conclusion,jobs
```

直接API入口：attempt1及jobs、attempt2 jobs。其他运行先查当前`run_attempt`；取全分页并核job的SHA，不把截断列表当完整检查。job的steps也须回该SHA的workflow理解：本例Windows／macOS的debug-overrides步骤按条件跳过，不能一见skipped就认定失败。

交回run URL、SHA、attempt、相关job ID和剩余验收；仍在运行就由负责交付的主任务沿同一ID接续。另一个真实使用者的多attempt产物问题说明同run或同名artifact不能证明是本次产物。本例没有读取日志或下载artifact，也不证明PR全部必需检查、合并提交或最终产品通过；只把旧交接更新成当前这一条workflow的证据。

**依据**：[一手] GitHub 实际响应：[PR14804](https://github.com/cli/cli/pull/14804)、[运行40001614534](https://github.com/cli/cli/actions/runs/40001614534)、[attempt1](https://api.github.com/repos/cli/cli/actions/runs/40001614534/attempts/1)、[attempt1 jobs](https://api.github.com/repos/cli/cli/actions/runs/40001614534/attempts/1/jobs?per_page=100)、[attempt2 jobs](https://api.github.com/repos/cli/cli/actions/runs/40001614534/attempts/2/jobs?per_page=100)、[该SHA的workflow](https://github.com/cli/cli/blob/fa812ef2b1ab1240ca023b7a4b720cbeef7fbdcd/.github/workflows/go.yml)；[一手] [gh run view 文档](https://cli.github.com/manual/gh_run_view)、[固定实现](https://github.com/cli/cli/blob/4f2cfe92e3499f8581bf39db77e0a1431fa7b55c/pkg/cmd/run/shared/shared.go)；[社区] [多attempt产物问题](https://github.com/cli/cli/issues/12437)；[经验] 2026-10-24 公开案例只读复核；核实 2026-10-22。

## 5. 子任务应缩短关键路径，不应制造评审树

**这里只处理同一任务剩余交付的委派，不用子任务来“重启”停下的任务。** [08](08-multi-agent.md) 负责并行拆分与整合；本节决定是否真的需要拆、结果由谁收回、何时停止并串行接收。接回已有任务时，先按 §3–§4 判断状态和剩余一步，再决定是否委派。

✅ 原生按需委派；确能减少上下文负担或缩短关键路径时，再把边界清楚的调查拆出去。每次带明确问题、输入版本、读写范围、结果和验收方式；同一修改表面由一人整合。区分 worker 自称完成、结果送达、主任务收集、主任务验证四个时刻。

**下一步依赖嵌套子任务结果时，先用宿主支持的原生前台返回。** 不把交互会话的后台唤醒行为照搬到非交互／SDK；Claude Code 2.1.302 的默认前台变更已有[父任务消费结果的公开复测](research/2026-10-12-long-task-evidence.md#嵌套结果回收先复用原生前台返回)，无需因此另加轮询或回调层。确需后台并行时，先明确哪个任务接收结果、由谁继续整合。局限：复测仅覆盖三种非交互入口的标记任务；显式后台调用仍有未唤醒报告，升级不等于旧任务自动恢复。

**观察工作要持续到子任务结束以后，就交给负责后续交付的主任务。** ✅ 在原授权范围内，让实施子任务返回任务 ID／PR 与 SHA，由主任务用现有入口继续查询 CI 或远程任务；短命子任务不默认启动一个留给父任务等待的后台 watcher。已启动的进程须核宿主是否真正移交所有权、结果投递与恢复记录，不能只凭“已移交”回执继续等。Hermes 的[故障报告、发布实现与反例](research/2026-10-12-community-source-records.md#观察者要比实施子任务活得久)支持这一选择，不是 Codex 的内置生命周期契约。局限：已有公开修复只覆盖部分路径；主任务负责接续不等于宿主保证常驻或跨重启送达，不因此扩大后台任务权限或新建服务。

**跨执行者派发前，先确认回执丢失后仍能找到同一任务。** 优先复用双方可读取的既有 issue／PR 或任务记录，将身份与基线、交付版本和接收结果关联；需要长时间异步执行时，先核可用的查询入口及记录保留范围。CAO 的[固定修复与未闭合缺口](research/2026-10-12-long-task-evidence.md#跨执行者派发先保证任务身份可重新发现)表明，结果已保存也可能因查询 ID 未送达而无法取回；仅有去重键也不证明任务已投递。已有载体足够时不另建编排层，结果未知仍按 §9 先对账。局限：公开源码与设计契约不能证明真实恢复成功率，Git／PR 本身也不保证唤醒接手者。

**收到空的“成功结果”时，先查宿主是否丢了子任务错误。** 在更换 worker 或重新派发之前，核对子任务的错误／结束原因与父任务收到的状态；空评审不能计为“没有发现”，也不能据此断定没有已有产物。确认是状态转换缺陷时，优先核对原生修复及适用版本，保留原来的子任务 ID、核对产物后再续接，不靠放宽下游验收继续。OpenCode 的[失败变空成功修复链](research/2026-10-12-development-conditions.md#委派失败被转换为空成功父任务已经收集也可能误判)支持这一处置；合法无文本结束仍须与异常区分。局限：修复只覆盖特定错误路径，不能证明弱模型委派或长程完成率已改善。

**续接指令已接受，也可能还没被处理。** 子任务长时间没有新结果时，先查原任务的最后执行记录、待审批／待工具状态和续接指令是否已处理，避免反复发送同一催促；恢复后先核对最新目标与已被取代的要求，再继续剩余工作。dot 的公开阻塞报告出现 `steered` 回执后延迟集中收到 follow-up；Codex 固定源码也区分接受与后续处理，见[输入边界核对](research/2026-10-12-development-conditions.md#dot-长任务续接接受处理与停止范围)。局限：两者不能据此认定同一根因，回执与运行状态都不能单独证明指令已执行。

**子任务失败，按原验收决定接管、降级或暂停。** ✅ 必需检查可换执行者，但保留原验收门槛，包括独立审阅；完成不了就暂停该项交付。已约定可选的补充可标为不可用，继续不依赖它的交付。切换前先停共享状态的写入者、核对产物；停不掉就暂停相关交付。[gstack失败策略与修复](research/2026-10-12-long-task-evidence.md#可选子任务可降级必要验收换执行者)支持这种分流，尚未证明超时恢复效果。

给整棵任务树设生命周期预算；并发上限之外还要限制总调用。检查结果按版本、diff、命令、依赖和环境复用。评审聚焦可复现的正确性问题，不收敛时换方法或报告阻塞；小型 grep、机械修改直接做。

官方子 Agent 指南要求主任务整合结果；#40932 报告结果投递停滞，#38989 报告递归评审和重复测试。局限：提示“不要提前结束”无法独自修复投递与唤醒故障，必要结果仍须实际收集、验证。

**最后接收由当前目标持有者串行完成。** 子任务交回任务 ID／PR、产物版本与未完成项；接收者按原验收在当前树核实际结果，再关闭事项。并行的只应是调查或互不重叠的写入面；整合、发布和最终验收不并行。

**依据**：[一手] 官方子 Agent 指南、Codex 输入边界固定源码；[社区] [#51610](https://github.com/openai/codex/issues/51610)、#40932、#38989、Hermes、CAO、OpenCode、gstack；[研究] 采用判断；[经验] 设计；核实 2026-10-22。

## 6. 工作树隔离不是权限隔离

**先让每个任务有能启动、能观察的验证路径，再延长运行时间。** Cursor环境复盘（2026-07-30）报告：只补启动Skill帮助有限，真正简化的是统一启动入口与长进程管理。与OpenAI自用harness逐worktree运行应用的做法相比，共同可借的是把启动和检查变成稳定工具能力，而非给模型更多守候职责。默认复用现有启动脚本，按失败点补最小缺口；人核跨任务状态污染、真实行为覆盖及维护负担，不默认搭一套常驻平台。这是团队自报，同题比较未测净收益。

✅ 写入前核对真实 cwd、仓库根、分支与目标路径；收到 commit 后核对祖先和差异范围。需要硬隔离时使用 OS、容器或沙箱实施权限，不能只在模板写“只读”。

Superpowers #1040、#2050 曾报告研究返回主 checkout 路径后写错位置、子任务提交到 main。局限：worktree 共享部分 Git 状态和机器资源，无法单独提供权限隔离。

**并行编辑时，验收对象应固定到本次要发布的树。** ✅ 先界定文件归属，再由整合者仅暂存本单元文件；检查 `git diff --cached --check` 和暂存差异，从 `git write-tree` 得到树 SHA 并归档到独立目录运行检查，提交后核对 commit 的 tree 与受检树一致。共享工作区的检查结果可能混入其他单元，不能直接套在某次提交上。新文件含尾空格但尚未跟踪时，普通 `git diff --check` 返回 0；暂存后 `git diff --cached --check` 返回 2 并指出该行，已在临时仓库确定性复现（2026-10-16）。局限：这不是原返工现场日志的重放，也未证明减少多少返工；归档只包含 Git 树内文件，所需依赖仍须明确，固定受检输入不等于权限隔离或真实产品运行验证。

**依据**：[一手：团队自报] Cursor [环境复盘（2026-07-30）](https://cursor.com/blog/cloud-agent-environment)、OpenAI [自用 harness](https://openai.com/index/harness-engineering/)；[社区：历史单例] Superpowers #1040、#2050；[经验] 设计、本仓单例采用建议、Git 行为复现（2026-10-16）；核实 2026-10-22。

## 7. 预算与停止：把状态说清楚

✅ 明确区分已验证完成、缺权限/输入而阻塞、预算用尽、用户暂停和失败；预算用尽就保存剩余工作，不改验收标准。遇到状态版本冲突先重新读取，再决定更新。

dot 的 Pause 只停止当前主任务；需要停止委派任务或未来排程时，分别核查 Activity 与 Scheduled，不能把暂停主任务当作全部工作已停。

比较方案时分开记录缓存/非缓存输入、输出、调用数、重试、子任务、墙钟、人类审查时间和实际计费；推理若属输出子集，不重复相加。

自建 API 调用的请求超时、重试次数与整项任务截止时间需分别核实，按 [16 §4.5](16-building-agents.md#45-安全与成本)选择已有控制；不能由一个 `timeout` 字段推定整项任务已受限。

官方 Goals 指南包含可度量目标、验证、预算及停止原因；app-server 源码区分关闭拒绝新工作、历史读取失败和历史耗尽，并用 `expectedRevision` 检测实验性状态更新冲突。局限：客户端支持范围和实际计费需分别核对，不能从源码能力或 API 估值推定当前产品行为与订阅扣额。

## 9. 超时后，动作究竟发生了吗

✅ 先按副作用决定重试策略，结果未知时标记 `unknown` 并对账。

- 只读：有限退避重试，核对结果时效
- 可重复计算：固定输入与输出位置，防止覆盖其他运行
- 本地编辑：先看当前版本与 diff，再决定是否重放补丁；恢复暂存／提交前，对照操作开始前保存的分支和 HEAD，不符或缺失先对账，不能重取当前值冒充原预期
- 外部写入：先查操作状态；服务支持时持久化幂等键，同一操作重试复用原键，新操作才换键

本地前置检查与远端基线校验保护不同边界：同一 HEAD 也可能已切到错误分支；已发布成果也可能对应不同 commit SHA。结合发布回执、tree 和内容判断是否还有实质增量，不为已完成成果重写同义状态。检查不是原子锁，仍须串行整合，发布前核对生成提交的父提交与预期基线、tree 与受检树一致。见[本仓单例与最小 Git 检查](research/2026-10-12-long-task-evidence.md#续接提交前检查分支与本地基线)。局限：不能拦截所有同版本语义重复，也未证明真实恢复成功率提高。

Code Mode 提示运行时被替换时，先核对先前工具操作与外部任务的实际结果，再用新 `exec` 重建必要状态；cell 与 `store` 值丢失，不代表外部命令已取消或副作用已撤销，不能盲目重放。见[恢复证据与版本边界](research/2026-10-10-codex-continuity.md#5-2026-10-13解释器重置先对账再恢复)。

请求超时可能发生在执行前、执行中或完成后丢回执；MCP 传输恢复要求与业务去重是不同层次。局限：自加 HTTP 头、JSON-RPC request ID 或重新发起请求，都无法代替接收服务真正支持的幂等处理。

**依据**：[一手] MCP 规范、Codex 源码；[经验] 工程推论、本仓单例与确定性检查；[研究] 采用判断；核实 2026-10-22。

### 模型回退：先区分请求续接与工具重放

✅ **给编码 Agent 加供应商回退时，保留原生恢复入口；先验备用模型能接收本轮工具／历史，再验失败发生在什么边界。** 已交付工具调用片段后，不把“尚无文字”当作尚未输出；工具已完成但回执未知时，仍按本节核结果，换模型或换 tool-call ID 都不授权重做。LiteLLM 1.106.1 与 PydanticAI 2.58.0 的固定实现分别以已生成内容、首个模型事件约束流式回退；原生模型事件与HTTP分块不是同一粒度。不能把滚动文档里的新开关当发行版本已有能力，见[P47比较](research/2026-10-12-long-task-evidence.md#p47模型回退历史兼容不等于工具可重放)。

**第二次改配置也要验。** 保存／重载重试配置后，核运行时策略是否需要重新绑定。OpenAI Agents 0.24.0 明确不序列化 retry policy；这不是漏洞或安全绕过。保留原流程的条件是兼容性、失败边界和重载后的策略都可解释；否则关闭这条自动回退并保留可恢复的失败，不删工具历史求通过。局限：本仓只复核固定源码摘录与配置对象，未运行三套SDK或证明外部动作恰好一次。

**改模型与改工具执行绑定分开验。** 只换模型，不等于要迁移耐久宿主；改工作目录、工具定义或extension前，先让已发出的旧调用落定，或明确保留其执行绑定。Pi Durable固定文档中，请求准备时锁定模型与提供的工具清单，工具阶段却解析当前agent／cwd，配置改变可影响旧调用。Agent列出受影响调用与实际目标，人核迁移后的副作用；旧绑定不能保留已撤销权限。解释不清就暂停这些调用，保留原记录。见[固定契约与二改判据](research/2026-10-12-long-task-evidence.md#p47续查配置改变后旧工具在哪执行)。

**依据**：[一手：文档契约，未运行宿主] LiteLLM 1.106.1、PydanticAI 2.58.0、OpenAI Agents 0.24.0、Pi Durable 文档；[研究] P47 比较、采用默认；[经验] 限定离线复核；核实 2026-10-22。

### 恢复其他子任务时，已完成动作有没有重做

✅ **把外部写入流程改为嵌套委派，或更换 checkpoint 续接入口时，同时核最终状态和已完成动作的执行记录。** LangGraph 的修复处理了最终状态正确、已完成兄弟任务却被重跑的问题；保存过审批或 issue 关闭不能代替这项验收。优先核原生修复及实际版本，不靠增加摘要或审批次数补救。

正常恢复可以重新进入尚未完成的中断节点，主动回放旧 checkpoint 也可以有意重跑；不要把两者一律禁止。只读调查不必增加副作用检查。**局限：公开复测主要采用合成副作用，不能推出所有 Agent 的故障率或外部服务保证；所核发行源码尚未包含修复。** 版本、反例和复测范围见[研究记录](research/2026-10-12-long-task-evidence.md#完成状态正确已完成动作仍可能被重新执行)。

**依据**：[一手] LangGraph [修复 PR](https://github.com/langchain-ai/langgraph/pull/9315)；[社区] 公开复测；[研究] 恢复范围与完成状态核验；核实 2026-10-22。

### Git 发布：只传差异，失败从已核实的断点继续

✅ 已获发布授权且目标环境具备 Git 认证时，优先本地 `git commit` 后 `git push`，一次推送整批提交。连接器已获 GitHub 授权，不代表 shell 已有 Git 凭据；无人值守前先确认实际可用的发布路线，不能靠重复 push 补齐认证。

若只能用已授权连接器发布：

1. 读取最新 `main` 的 commit 与 tree；本地 `origin/main` 可能过期，使用 `git fetch origin main` 后核对 `FETCH_HEAD`，或直接读取远端 ref。基线前进时，先整合并重新检查，不把旧快照整页覆盖回去
2. 发布输入固定到已检查的提交，按该提交读取相对最新基线的变更内容，不从仍在并行修改的工作目录取文件；删除也显式表示，复用 `base_tree` 保留其余内容
3. 工具允许时尽量一次写入全部变化；只有工具上限或调用失败需要时才拆分，不设固定文件数。`create_tree` 成功后仍要创建 commit、更新目标 ref，不能把一次写入称为整个发布完成
4. 失败或回执丢失先查远端 ref、已返回的 tree／commit SHA 与内容；分步上传时，回执没记录的 blob 也可能已经存在：从受检提交以 `git rev-parse <commit>:<path>` 取预期对象 ID，核对远端对象后复用，只补确认缺失的内容；对象存在不代表 ref 已发布。保存已核实结果，只继续未完成步骤。若 `main` 已前进，重查差异并处理冲突，不强推覆盖
5. 以非强制方式更新 ref；发布后回读目标 ref、commit／tree SHA 和实际文件差异，确认指向预期成果；远端 CI 的结果另核，不能用本地检查代替

GitHub 的 blob 查询可按对象 ID 核内容；tree API 支持基树与多条变更，省略基树会丢掉未列文件；ref API 支持非强制更新。关键局限：实际连接器可能有不同的载荷、权限或分支保护限制，批量能力与成功回执必须按当前工具核实，不能为减调用绕过审批。核验范围见[研究记录](research/2026-10-12-development-conditions.md#dot-效率选择少一层包装不等于少一项验收)。

**本仓库单例（2026-10-16）**：E4 发布前主干已前进到 `244bc9f`，重新整合后的 `c9e71c7` 以它为父提交；后续 `7a475db` 的发布回执分别记录 tree、commit 和 ref 更新，回读核对五个变更文件与本地受检提交内容相等。这支持把“整合、受检版本、发布、回读”分开核实；不是跨仓库成功率、长任务不中断或 hosted CI 通过的证明。

**依据**：[一手] [blob 查询](https://docs.github.com/en/rest/git/blobs#get-a-blob)、[GitHub tree API](https://docs.github.com/en/rest/git/trees#create-a-tree)、[ref API](https://docs.github.com/en/rest/git/refs#update-a-reference)；[经验] 恢复策略、Git 历史与发布回读：[c9e71c7](https://github.com/dbvv1/a1dbv/commit/c9e71c790050dd8b410de10d0b05c3fcfc0fe2c2)、[7a475db](https://github.com/dbvv1/a1dbv/commit/7a475db46245fb88ed6869b70d9b2a315a34be48)；核实 2026-10-22。

## 10. 工具契约要写到失败方式

✅ 为无人值守工具写清输入约束、所需权限、成功究竟是接受/完成/验证、错误分类、副作用与可撤销性、重复调用语义，以及完整日志位置和截断处理。客户端遇到 MRTR `input_required` 应保留调用状态、收集输入后继续，按规范兼容旧结果。

MCP 工具规范提供 `inputSchema`、annotations 与 `resultType` 等契约信息。局限：schema 和 annotations 不能替代客户端/服务端验证与权限执行，“还需输入”也不能记成业务完成。

## 11. Hook 的价值取决于故障路径

✅ 保护敏感写入前，测试放行、拒绝、超时、无效输出与解释器缺失，检查 matcher 覆盖全部写入口；普通格式化可选不同故障策略。先核对[失败策略与版本边界](06-hooks-and-guardrails.md#返回值)，再采用字段。

Claude Code 文档与 changelog 引入 `onFailure: "block"` 并修复部分 managed hooks 行为，但事件和异步路径有排除条件。局限：Hook 的模型判断或失败策略不能统一保证 fail-closed，最终访问边界仍依赖 OS 与服务端。

## 12. 记忆作为候选变更，而非事实来源

✅ 记忆附项目、来源和失效条件，历史经验先成为待审候选；当前配置、源码和命令输出优先，冲突时更新或删除旧记忆。临时故障不直接升级为永久规则。凭证、个人信息和外部页面指令不进入可传播记忆。

交接传目标、约束、已验证事实、产物位置和未解决问题；接收者再次核实会影响写操作的假设。

Gemini CLI Auto Memory 的文档设计是从历史提出 patch/Skill 草稿，存入 inbox 后由用户审阅应用。局限：这是实验性、默认关闭的功能设计，是否可用仍须按安装版本验证。

**依据**：[一手] Gemini CLI Auto Memory 文档；[经验] 工程建议；核实 2026-10-22。
