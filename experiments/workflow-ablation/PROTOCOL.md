## 配对与顺序

**试运行方案**：本玩具任务用 A/B/C 各 3 次，仅用于检查接入，不做效益或显著性结论。此处没有执行这 9 次。

正式研究先选足够多、来自目标项目真实失败的任务，分层覆盖难度/规模，再固定每任务重复数。任务是推广的统计单位；一个 bug 重跑 30 次仍只有一个任务。

每个 `(task_id, repeat)` 配对区组都包含 A/B/C，输入、模型、预算相同。在每个三重复周期使用以下平衡顺序：先按固定随机种子打乱 A/B/C 为 `(x,y,z)`，再使用 `(x,y,z)`、`(y,z,x)`、`(z,x,y)`；打乱任务区组顺序并提前保存全部排程。交错执行，不能先跑完所有 A 再跑 B/C。若重复数不是 3 的倍数，提前记录不平衡及处理。模型支持固定 seed 时配对使用同一 seed，但不宣称完全确定。

为减小时段、服务负载与缓存干扰，保持每组硬件/并发相同，记录运行时间与缓存命中。不要让上轮解法、历史聊天、共享记忆或评估反馈泄漏到下轮。人工评审隐藏条件标签；审查用相同标准。

## 指标与判定（先填，不追结果换口径）

主要指标：所有计划尝试中的独立固定验收通过比例；分母包含 timeout、failed、budget_exhausted、blocked。基础设施故障另分类并保留原始轮；重试增加 attempt_id，不覆盖旧记录。还应分开报告“未开始/未完成”和“已完成但错误”。

次要指标：

- false-green：固定 public 通过且 held-out 未通过；与 agent 自称通过分别记录
- 新回归测试是否在基线上以正确原因失败、在最终源码上通过；既有测试是否削弱、修改是否越界
- 墙钟、队列时间、模型/工具活动时间（若可观测）、人类审查/返工时间；不能把并行 agent 秒数相加当墙钟
- 每次尝试的 uncached input、cache read、cache write、output、reasoning token，后者是否为 output 的子集。保留供应商原始字段与定义，**不能重复计数**
- 请求、重试、工具与全部子任务调用数；计费已含子任务时不能再加一次
- 实际 API 账单金额/币种、公开费率估算及价格日期分开。订阅限额扣除单列；没有可观测值记 unknown/null，不能由 token 估成真实订阅消耗。工具费、计算费、人工费另列；不同币种不直接相加

报告每任务配对差、所有原始值与分布，再给跨任务汇总。小 n 不给显著性/因果泛化/生产力倍数；不把单次最快、pass@k 和单次成功率混淆。若报告不确定区间，预先选任务级聚类方法及适用样本量。测试反复采样与同任务重复不是独立样本。
