# 等待齐帧还是预测回滚：让同一个官方模拟付出真实成本

**🧪 用这个实验判断你的模拟是否值得接预测回滚，不为跑它迁移现有引擎。** 两个真实 GGRS `P2PSession` 消费同一份官方飞船 `State::advance`；把传输替换成用户态延迟队列，比较等待与预测，随后增加带冷却的推进脉冲，验证新状态也能完整恢复。[07 的项目选择](../../domains/game-dev/07-networking-and-server.md#rollback-adoption)保留 Unity／UE 的现成路线。

## 开始

需要 Python 3.11+、Rust 1.87+ 与普通本地编译工具。首次准备只从官方 GitHub／crates.io 下载代码和依赖；不建账号、不改 OS 网络设置、不运行窗口。

```bash
cd experiments/ggrs-rollback-adoption
python3 prepare.py
cargo test --locked --lib -- --nocapture
python3 -m unittest -v test_prepare.py
```

已有固定上游源码时，可用 `python3 prepare.py --source /path/to/ggrs/examples/ex_game/ex_game.rs` 离线准备；脚本核 SHA-256 后才写入 `.work/ex_game.rs`。依赖已缓存后，测试可追加 `--offline`。主目录不可写时，将 `CARGO_HOME`、`RUSTUP_HOME`、`TMPDIR` 指向自有磁盘目录；保留对应已安装工具链，不把大 SDK 解压到内存临时盘。

**依赖固定在官方修复源码，而不是把发布版与开发版混称 0.13.0。** GGRS 的 [MIT／Apache-2.0 双许可源码 `25bd9983`](https://github.com/gschup/ggrs/tree/25bd9983dee3ecb0677be03b9e2e23d2bd6d29cb)仍使用 `0.13.0` 包版本字符串，但包含未发布的 input packet `base_frame` 修复，改变 wire format；所有通信端必须采用同一兼容版本。`Cargo.toml` 的 git revision 和 `Cargo.lock` 才是本例身份。官方 `ex_game.rs` 与发布 tag `v0.13.0` 内容相同，下载后不修改；只调用它的模拟，不调用 Macroquad 的窗口／输入／渲染函数。

选择这个固定源码的原因来自实际失败：crates.io 0.13.0 在相同三轮延迟的等待式输入下没有在 2,000 个调度轮内完成 80 帧；加真实 1 ms 轮间等待后仍仅到第 11 帧。固定修复源码同题完成。源码差量为压缩包显式传编码基准，并保留解码所需输入；不把首次失败抹掉，也不推荐项目无条件追开发分支。需要稳定发行依赖的项目先核其已发布修复，或保原网络栈。

## 真实接线和可观察结果

```text
固定脚本输入 → 两个 P2PSession → GGRS Message 编解码／用户态延迟队列
                         ↓
             Save / Load / Advance 请求（按原顺序处理）
                         ↓
       官方 State::advance ＋本例冷却／使用次数增量
                         ↓
        完整序列化字节，与同输入确认版模拟逐字节对比
```

`src/lib.rs` 只拥有测试传输、请求适配和一项技能增量；预测、历史输入、回滚调度与请求生成都交给 GGRS。官方模拟原有位置、速度、旋转与帧号参与快照；第二版的每人冷却和使用次数也放进同一份可克隆状态。

2026-10-26 在 Linux x64／Rust 1.99.1 实际运行，三轮延迟、40 帧脚本输入后接 40 帧中性输入收敛，共 80 个最终逻辑帧下，每端结果：

| 同一消费者 | 无推进尝试 | Save | Load | 实际 Advance | 单次调用最多 Advance |
|---|---:|---:|---:|---:|---:|
| 等待齐帧，预测窗口 0 | 240 | 0 | 0 | 80 | 1 |
| 预测窗口 8，原飞船输入 | 0 | 99 | 9 | 107 | 4 |
| 预测窗口 8，增加脉冲／冷却与新输入 | 0 | 117 | 18 | 134 | 4 |

两端结果均与同输入的确认版完整状态相同。二改多出的重演来自新的输入变化，不证明“多两个字段就使回滚次数翻倍”。本例序列化状态为 86 字节，包括两版都保留的冷却／次数字段；这不是堆内存、环形快照总占用或真实游戏预算。

- 故意只恢复官方飞船而漏恢复冷却／次数时，使用次数从确认版每人 3 次变成 6 次，完整状态比较确实失败；负例以“检出不一致”为通过，不能当成坏恢复可用。GGRS 不知道游戏漏了哪些字段，本例的确认版对照发现该错误。
- 远端输入一直缺失时，第 8 帧后不再推进；本固定源码可以返回 `Ok` 但没有 `AdvanceFrame`，不要只等 `PredictionThreshold` 异常或把一次调用算一帧。
- 七组 Rust 检查覆盖即时队列、迟到输入、等待式、技能二改、漏恢复、缺本地输入和缺远端输入；三组 Python 检查覆盖原文件、损坏文件保旧值、缺文件。缺源码／依赖会真正失败，无 skip。

这里的“轮”是用户态调度轮，不是毫秒、60 Hz 的显示帧或真实 RTT。即使队列延迟设 0，两端顺序调用也可能让第一端先预测；不要据此声称零延迟基线。两会话同进程、同编译器，未测跨设备确定性、UDP／WebRTC、公网抖动、反作弊、视听或原生 Unity／UE 性能。保留官方浮点模拟只支持这个固定运行条件，不把它包装成跨平台确定性实现。

## 改自己的游戏时

先沿现有引擎预测实现接入一项操作，再列完整模拟状态：运动、技能阶段、冷却、生成／销毁、稳定 ID 分配器、随机源与待执行命令。AI 可写字段差量和回归；不能用只保存 Transform、重新播一次动画来冒充恢复。

把输入延迟、预测窗口、重演上界、快照大小和表现纠正一起选；声音／粒子是模拟外副作用，沿 [07 的事件与表现说明](../../domains/game-dev/07-networking-and-server.md#rollback-adoption)处理。新增技能后同时验正确恢复和故意漏字段的反例，再在目标设备看 CPU 峰值与玩家能否看见纠正。若本地操作已够及时，保等待／已有状态同步往往比为全世界补快照更合算。
