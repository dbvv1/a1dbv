# Continue：参数能被接受，还要核值有没有被改掉

**🧪 MCP 工具调用优先按 `tools/list.inputSchema` 传原生数组、对象和布尔值；不要把所有“像 JSON 的字符串”一律解析。** Continue 的两个既有修复都让本次“重复读文件 → 预览修复 → 实际修改 → 错误恢复 → 再修改”完成，但转换语义不同：较小方案改变本来合法的字符串并舍入大整数；较保守方案仍会舍入数组内的大整数。**本次不把任一方案采为通用转换器，也不改变现有工具默认或读者评级。**

## 接收的真实问题和两个候选

Continue 用户报告第一次 `read_multiple_files` 传数组成功，第二次把 `paths` 传成 JSON 字符串便失败；`edit_file` 的 `edits` 和 `dryRun` 也受影响。本次用合成仓重现这组输入形状，未判断原报告究竟由模型还是客户端产生字符串。

| 固定版本 | 变更与本次选择 |
|---|---|
| main／共同基线 `5522c6f44ca0ac3528b37244818fbfa39b5af470` | 不做这项补偿，留作失败对照 |
| 既有 PR #13416 `9da7044f0e6019439e9da62473517671540542e6` | 3 文件新增 743 行；按 schema 解码，接受 string 的联合类型保持字符串，拒绝顶层不安全整数转换 |
| 既有 PR #13386 `75367f352dafdd5f8913c7de3c0f63857640abf4` | 3 文件 181 加／7 删；较短转换路径，还修改 built-in 分支；本次消费者只验 MCP |

观察时两项 PR 都开放，项目 Apache-2.0、约 3.64 万 Star。选择来自已有用户问题与竞争实现，不是为了另写重复补丁；没有向上游发评论或 PR。

## 真正走过什么

非实现者通过 `vite-node` 加载三版原始 `callTool`、`MCPManagerSingleton` 和 `MCPConnection`，连接真实 SDK stdio，调用固定的官方 `@modelcontextprotocol/server-filesystem@2.1.0`。工具 schema 来自该服务的实际发现，不改 schema；传输、管理器、文件系统与原生依赖均未替身。最小宿主衔接仅提供 MCP 分支所需的 `tool`，不是打包后的 IDE 扩展、CLI 或模型生成验收。

合成 `amount.cjs` 初始把 `gross - discount` 写成了加法，税率为 `0.10`。每臂各用独立的“字符串化参数”与“原生类型”目录：

| 消费步骤 | 基线 | #13416 | #13386 |
|---|---|---|---|
| 首次原生数组读；再次字符串数组读 | 第二次被官方服务拒绝，原文件未改，停止该任务 | 两次读成功 | 两次读成功 |
| 字符串 `edits`、`dryRun="true"` 预览 | 未运行 | 预览成功，文件哈希不变 | 同左 |
| `dryRun="false"` 真正修复 | 未运行 | 独立 Node 进程断言净值 90，输出总值 99 | 同左 |
| 修改不存在的旧文本 | 未运行 | 实际错误，文件不变 | 同左 |
| 错误后把税率改为 `0.20`，再次读回 | 未运行 | 独立 Node 断言总值 108，MCP 回读正确 | 同左 |
| 独立原生类型正控 | 完成上述流程 | 完成 | 完成 |

基线没有被正确类型正控“救回”；它的字符串化任务仍失败。这里的数值只验合成模块，不是支付应用。成功标准是修改后的代码实际运行及错误后的续接，不是调用次数或进程 exit 0。

## 为什么任务成功还不足以采纳转换器

另一台自有 SDK stdio 服务公布普通 schema，由自己的 handler 验类型并回显值；这不是 SDK 自动 JSON Schema 校验，也没有改造官方文件服务。

| 参数与契约 | 基线 | #13416 | #13386 |
|---|---|---|---|
| `string | array` 接收字符串 `'["invoice"]'` | 保持字符串 | 保持字符串 | 改成数组；仍合 schema，却改变了已有合法值的类型 |
| `integer` 接收字符串 `'9007199254740993'` | 保留字符串，被服务拒绝 | 保留字符串，被服务拒绝 | 变成数值 `9007199254740992`，服务接受但回报非安全整数 |
| `array<integer>` 接收字符串 `'[9007199254740993]'` | 未补验 | **变成 `[9007199254740992]`，服务接受但回报非安全整数** | 未补验 |

最后一行是审源码后新增的**一次真实候选调用**，没有重跑原三臂。候选的安全整数判断只挡住顶层数字，不能证明嵌套转换无损。顶层拒绝是保守结果；数组调用的“成功”反而暴露数值变化。

**本次可借用的接收方法，是把“任务恢复”与“转换不改含义”分别验。** 这也和 [Inspector prompt 参数实测](../inspector-prompt-strings/README.md)互补：prompt 参数是文本，tool 参数按各自 schema；同一个通用 `JSON.parse` 不能同时替两者决定含义。已有原生类型入口可用就保留，不因某个补丁能消除报错而统一启用强制转换。
