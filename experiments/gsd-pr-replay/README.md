# GSD：同一工作分支连续交付，要核上一批确已接收

**🧪 需要把本地规划历史留在工作分支、只交付代码时，先在隔离仓跑通连续多轮，再采用 GSD 的 PR 分支流程。** 当前固定 `next` 仍会重选已交付的原提交；既有候选修正了本次三轮接收，并提前挡住未合并的旧分支。
**可借用的是“已构建”和“已接收”分开记：构建后保留源 tip 与产物 tip，确认目标接收后才推进重放起点。** 不要把生成 `-pr` 分支或一次 exit 0 当作交付完成。
**本次仅试原工作流 Bash＋真实 `gsd-tools`＋自有 local bare；保留长程路线 🟡 和现有工具默认。** 没有安装 Skill／Hook、调用模型或创建 GitHub PR。

## 对读者有什么用

长程 Agent 会反复从同一工作分支交付。GSD 的过滤流程会复制代码提交并剔除规划文件，复制后的 SHA 与源提交不同；若下一批仍用 `target..work`，原提交会反复入选。**选这类流程时，看第二、第三轮实际差量和未合并分支的拒绝行为，不只看第一批成功。**

这里接收的是上游已有 [#5486](https://github.com/open-gsd/gsd-core/pull/5486)，没有另写或投稿重复修复。它给源分支、模式和目标分别记录 published／pending／built-head refs；确认上一批已合入后才移动 published，并允许替换已合并的旧 `-pr`。遇到未合并的旧分支，候选在构建之前停止。

原高 Star 仓库 `gsd-build/get-shit-done` 已归档，README 指向 `open-gsd/gsd-core`；选型要沿当前维护入口，不照旧安装说明直接装。观察时两仓约 6.4 万／1.1 万 Star，均为 MIT；热度只用于找候选，不作为效果证据。

## 两版实际接收

输入是每轮一项代码＋规划混合提交、一项纯规划提交，显式 `planning.pr_strict=true`，目标最初没有 `.planning/`。每轮保留旧 `-pr`，执行原文块、核过滤结果，再向自有 local bare 快进；独立目标检出由 Node 读取合成模块的 `round` 值。

| 消费路径 | 基线 | 既有候选 |
|---|---|---|
| 第一轮 | 过滤后 1 个代码提交，目标读回 `1` | 同样通过；源提交与过滤提交 SHA 确实不同 |
| 第二轮，保留已合并 `-pr` | `checkout -b` 失败仍继续重放旧提交，代码冲突后 exit 1，并删除旧 `-pr` 引用；停止该臂 | 仅新 1 个代码提交，目标读回 `2` |
| 第三轮 | 未运行 | 仅新 1 个代码提交，目标读回 `3` |
| 旧 `-pr` 尚未合并，又有新提交 | exit 1，但旧 `-pr` 引用被删 | 预检 exit 1；refs、tree、HEAD、当前分支及状态均未变 |
| 原工作分支历史 | 保留 | 保留 |

所有成功接收轮次的目标规划路径为 0，验证块的禁止路径与规划删除计数均为 0；混合提交中的规划冲突由原过滤逻辑处理，不能把 stderr 中出现 `could not apply` 单独判为失败。基线第二轮另有代码冲突和引用删除，不能写成“安全拒绝”，也没有证据称原代码历史丢失。

候选第三轮合并后，published 仍指第二轮源 tip，pending 指第三轮源 tip；下一次检测确认后才晋升。此次没有额外运行第四轮或手工推进 marker。

## 这项比较怎么做、哪里没覆盖

- 两臂固定源码的原 Bash 块逐字提取，在同一 shell 顺序执行；使用对应构建后的真实 `gsd-tools` 读取配置。文稿中的 INCLUDE／EXCLUDE 判断由消费者按 strict 条件执行，这是明确的人工逻辑衔接，未验证模型能否正确执行整篇 slash command。
- 消费者使用隔离 HOME／配置／临时目录、禁用 Git hooks 和全局配置、最小 PATH 无真实 `gh`；远端只有合成 local bare。真实账号、GitHub 合并证明、fork、squash／rebase 和其他操作系统未做消费者验收。
- strict 过滤不负责删掉目标已跟踪的规划文件。本次目标起初没有规划，不能由“0 路径”推导一般隐私隔离保证；未试仓库内其他敏感内容。
- Node 只消费合成模块的轮次值，不是支付应用或完整项目功能验收。全套 GSD、本机安装与全局配置未试。

## 检查和原始失败

两版环境检查、锁定依赖安装（禁生命周期脚本）、`build:lib` 和规划模式漂移 lint 均通过。定向范围为规划过滤、模式、漂移、base-branch 与候选新增 published-marker 用例：基线 197／197；候选首批 241／242，唯一失败来自本试验最小 PATH 漏掉 Git editor 所需的外部 `true`。补入普通工具后**仅该 1 例通过**，未把原批次改写成一次 242 全绿，也未运行本地全套。

消费者准备期出现一次 Python 引号语法错误，尚未执行产品；首次基线适配又遗漏原文的提交列表枚举，产生 3 条无效记录。两者原样保留，只修正并重跑无效基线；候选有效三轮未重跑。这些是试验实现错误，不计作产品故障。

固定候选的托管 Tests 工作流成功；读取到的 51 个检查含 45 成功、3 失败、3 跳过，其中包括旧 Self-test 失败及后续成功，`Reviewed or maintainer` 门禁仍失败。PR 仍开放，不称整套 CI 或合入通过。版本、时间、数值与原证据哈希见 [results.json](results.json)；完整原输入、输出、Git bundles 和源码快照在云端保全，未公开上传。
