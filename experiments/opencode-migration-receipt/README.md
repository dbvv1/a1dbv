# OpenCode 迁移：失败后重启，要验到真正读回历史

**接收分批迁移补丁时，先在合成副本制造中途失败，再用新进程恢复并读回会话；一次迁移返回成功还不够。** OpenCode 现有 #56929 在本次消费者中保住了已完成的清理批次，最终消息与工具结果仍可读。🧪 限定接收这项恢复能力，不据此升级整套 OpenCode 或迁移真实历史。

## 真实输入与选择

使用者 [#41739](https://github.com/anomalyco/opencode/issues/41739) 报告旧库升级时服务启动失败。后续[实践者复现](https://github.com/anomalyco/opencode/issues/41739#issuecomment-6258602627)把其中一项缺陷缩小到旧事件清理：代码每次删 1,000 行，但所有批次仍在一个事务；后面一批报错，前面已删的也回滚，重试重新清理。

原 issue 后来因 2.2.0 未复现启动超时而关闭；它不是“分批提交已修好”的证据。[已有 PR #56929](https://github.com/anomalyco/opencode/pull/56929) 仍 open／未合并。本次接回原补丁，没有另写实现或重复投稿；固定 dev `ff90ed916` 与原 PR `fb1cd27d`，二者仅迁移实现和对应测试有差量。

适用于维护持久化迁移、接回 Agent 改动或审核现成修复的人。正常使用者仍按[官方 V1→V2 迁移说明](https://opencode.ai/v2/docs/migrate-v1/)保留原设置副本；官方另有插件、服务 API 和客户端配置变化，这次数据库结果不覆盖它们。

## 独立消费者实际走了什么

两版接收相同合成输入：两个项目、三个会话（含父子关系）、六条 user／assistant 消息、三个工具结果，以及 2,501 条旧事件。用官方 `Database`／`V1Migration.run()` 和真实 SQLite，不替换迁移逻辑；每阶段是新的 Bun 进程。

```mermaid
flowchart LR
  A[创建合成旧库] --> B[真实 SQLite 触发器令清理失败]
  B --> C[退出后新进程核持久行与检查点]
  C --> D[解除夹具故障并恢复迁移]
  D --> E[再新进程用 SessionStore 读回历史]
  E --> F[重复迁移与后续新事件检查]
```

| 相同输入下的观察 | 当前基线 | 原 PR 候选 |
|---|---:|---:|
| 删除第 1,001 条时失败，重启剩余旧事件 | 2,501 | 1,501 |
| 最后写清理检查点时失败，重启剩余旧事件 | 2,501 | 501 |
| 上述失败后检查点／提前生成的 V2 消息 | 都没有 | 都没有 |
| 失败与最终恢复后的 V1 原始会话、消息及 parts | 保留 | 保留 |
| 解除故障后恢复、再进程读回全部预期内容 | 通过 | 通过 |

**候选的改进是少重做已提交批次，不是基线永远不能恢复。** 两版解除夹具故障后均能完成；候选最后 501 行与检查点同事务失败，前两批 2,000 行已经提交。另一个恰好 2,000 行的输入验证整批边界：最后零行批次仍能写检查点并完成。

最终用生产 `SessionStore.get()`、`messages()`、`list()` 核对消息 ID／顺序、中文和引号文本、工具输入／结果、父子关系和两项目隔离；重复 `run()` 后内容逐项一致、没有新增重复行。完成后插入一条合成新事件，再运行迁移仍保留它。六个最终数据库的完整性与外键检查通过。

## 可借用的接收方法

本轮把已有长程路线中的“真实消费者和失败路径”用于迁移：**分清已提交进度、阶段检查点、最终可读内容**。清理中途和最后检查点各有一次真实失败；重启后既查剩余行，也走项目自己的读取／解码接口，最后再核重跑是否误碰新数据。

本次失败是 SQLite trigger `ABORT`，随后正常结束进程；没有模拟断电、强杀、磁盘损坏或并发迁移。没有测峰值 WAL、28 GiB 原库、服务启动时间、HTTP／TUI、模型调用或 Windows，因此不能用本表承诺大库性能或整个升级过程已可靠。[长程路线](../../docs/decisions/long-tasks.md)默认及读者 🟡 状态不变。

## 执行与检查范围

Linux／官方 Bun 1.4.4，固定 lock；依赖只装在独立云工作树，关闭安装生命周期脚本。消费者 import 前白名单隔离 HOME、全部 XDG／临时目录，完整替换 `Global` 路径与文件 DB，显式指定不存在的 next DB；使用非 global 合成项目，避免向上发现实际仓库。没有读取真实会话、运行产品安装器、注册 Hook 或启动模型／后台服务。

最终五份相关测试（V1 migration、database、database-drizzle、database-migration、session-store）基线 **72 通过**、候选 **73 通过**；两版 core `typecheck:tsc` 通过。完整 monorepo `check`、所有 core 测试、产品构建未运行。原测试包含临时 Git 和固定路径探测，其范围比独立消费者的合成 DB 更宽。

准备失败均保留：首次消费者把 seed 快照和阶段报告写成同名，修正后换新目录完成；后续一版与依赖补装重叠，最终在依赖稳定后重验。相关测试最初缺 Bun 子进程 PATH，补齐后又暴露 filtered install 未链接 root 的 prettier／tsc；补装相同锁定依赖后，最终五文件与类型检查均通过。这些不是产品缺陷，也没有隐藏为跳过。

上游精确 PR head 的托管快照为 **2 项规范检查成功，4 个工作流 `action_required`**（含测试和主检查），不是全部 CI 通过。原始过程、失败、每阶段 DB 快照、源码与原补丁保留，公开数据投影见 [results.json](results.json)。
