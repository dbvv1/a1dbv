## 30 秒结论：先定来源，再选模型

| 你的资源缺口 | 优先采用 | 何时撤回 |
|---|---|---|
| 图标、UI、重复道具 | 现成合法资源、引擎 UI、共享源和参数变体 | 实际显示下无法区分，或二改破坏整套 |
| 刚体 3D、材质、特效 | 成套资产与程序化处理，保源和身份 | 脚本达标却损失语义部件或玩法时序 |
| 角色动作、配音和音乐 | 完整动作体系、分段声音与明确的输出权利 | 必须手修、授权不清或后续无法补录 |
| 固定宣传镜头 | 静态／引擎镜头先行，独特片段再试生成 | 把生成展示误当真实玩法或状态可控 |
| 准备发行 | 逐项清权、渠道披露、真实设备与二改验收 | 理论材料不能替代成品证据 |

分档与动态事实见下文各专题；没有一个品牌能一次解决全部资源的许可、质量和迭代问题。[研究]

## 1. 资产管线：Agent 负责搬运和规范

**采用起点**：先让 Coding Agent 编排规则明确的下载、导入、参数和来源记录；是否更快、更稳要按实际产物验证，有损几何处理不能当作普通规格设置。**[经验：采用建议]**

### 1.1 推荐流程（跨引擎）

```
按玩法/设备定规格 → 核授权并选现成/程序化/生成来源 → 隔离原始资产 → 编辑器脚本批量导入并设置参数 → 记录来源 → 引擎内质量验收 → 重新生成／程序化调整或采用
```

1. **隔离**：AI 生成物统一放在单独目录（Unity：`Assets/_Generated/<来源>/`），和正式资源分开，方便替换和许可审计。
2. **记录来源**：同目录放 `SOURCES.md`，写明工具、版本、日期、提示词、许可。发售时的商店披露就从这里汇总。
3. **规格批量设置，有损处理单独验收**：命名、明确的单位换算与导入设置可交给脚本；简化、移除小部件、修复非流形边和补洞要保留原始网格，比较处理前后外观与最终面数，再决定采用。现有清理代码曾把细薄表面误删为碎屑，程序化修复可作为试验路线，不能视为自动提升质量；[固定源码与回归](../../docs/research/2026-10-13-game-asset-editing-boundary.md#生成网格有损后处理不等于规格设置)尚未证明真实游戏发布质量。**[一手：源码与测试阅读；经验：采用边界]**
   - **先定位缺陷，再选修补或重生成**：锁骨扭曲可能来自重定向代码，局部颜色可用区域 UV 脚本修补；有限修补仍无改善时再考虑重生成，避免为程序错误重复生成资产。一个已合并游戏案例提供了三类处理记录及可核验的最终动画，但原始／拒绝资产不完整，不能据此保证零手修发售质量或更低成本。见[产物与反证](../../docs/research/2026-10-13-game-asset-editing-boundary.md#生成资产返工先判断缺陷来自哪一层)。**[一手：项目记录与源码；研究：GLB 局部复算；经验：🧪 采用诊断顺序]**
4. **在脚本里设置数量和费用上限**：生成 API 按次计费。
5. **占位资源要有替换计划**：开发早期的 AI 占位贴图也可能在发售后引发争议（见第 3 节）。

### 1.3 授权与商用门槛总表（WP1）

**✅ 授权先于质量排名。** 分开判断：代码能否商业运行/分发，具体权重能否生产/修改/分发，输出能否装入游戏，以及平台是否接收。表中的“👀 候选”只表示可进入后续质量调查；“👀 有条件”须先满足条件；“⛔ 不默认”不进入默认商用方案。未见特别门槛不等于免除法律、输入素材、人物/声音或第三方依赖的权利要求。**[研究：采用门槛；一手原文、固定 SHA 与反证见 [WP1 记录](../../docs/research/2026-10-14-game-wp1-licensing.md)]**

“封闭服务／不授权重”不妨碍按服务合同使用输出，但不允许自行取得或分发后台模型。开放代码/权重的许可证也不自动变成输出的许可证；Apache-2.0/MIT 的许可、NOTICE/署名、修改及再分发义务按实际分发对象履行。本表以离线生产后交付资产为主，嵌入权重或向玩家提供运行时生成必须重新查整条链。**[研究：适用范围]**

### 1.4 2D采用结论：先可修改，再生成

**✅ UI文字与布局留在引擎，图标/瓦片先找匹配现成资产。🧪 透明静态精改优先评估Image2.5 Sunburst，无alpha插图变体对照Nano Banana2.1，本地小批静态保留klein4B；这是按接口、授权与成本条件选的首试顺序，未证明实测冠军。** 先用批准母版与原生多参考、独立图层合成；反复漂移且训练源与摊销条件成立时再加LoRA。最新Qwen2.1研究许可不允许默认免费商业升级。完整三档、静态/动画/瓦片的撤回条件见[2D专题](assets/2d.md)。**[一手／研究：依据与反证见[WP2](../../docs/research/2026-10-14-game-wp2-2d-assets.md)]**

最关键限制：现有公开证据不足以保证几百件成套资产及第二次修改均零手修；自动QA、透明通道和sprite sheet出口都不能代替动作/连接语义验收。

### 1.5 3D采用结论：原生低模与可修改结构

**✅ 现成同风格模块/角色优先，独特刚体道具再🧪原生低模T2；高细节近景保留7.1/Rodin2.5对照。** 当前原生低模已是商业接口，不能继续默认先密网格再强减面；但目标面数不是硬上限，quad和自动绑定都不证明变形可用。场景保留门、挂点和碰撞边界，角色优先已知骨架体系。分档、工具处理、成本与第二次修改见[3D专题](assets/3d.md)，新候选授权见[WP1增补](../../docs/research/2026-10-14-game-wp1-licensing.md#wp3追加现成3d资产与处理工具)。**[一手／研究]**

关键局限：已有来源和作者产物记录不构成零手修发售通过率；缺拓扑/权重的角色不能靠减面、改格式自动补齐。

### 1.6 音频采用结论：离线资产，运行时调度

**✅ 短反馈先用成套CC0资源/jsfxr；独特声源、主题或角色才增加生成。** SFX按事件、音乐按可切换段落、配音按台词ID交付，默认离线；音乐循环/状态切换和声音可持续补录，比一次出声更重要。三档候选和当前型号见[音频专题](assets/audio.md)。**[一手／研究：来源与代码反证见[WP6](../../docs/research/2026-10-14-game-wp6-audio.md)]**

关键局限：参数化噪声也未必同参数位级复现；局部repaint、下载商用权和未来同voice_id供应是不同承诺，程序处理修不了错误表演或未授权声音。

### 1.7 跨资源风格：优先共享源资产，生成只补缺口

**✅ 几百件资产先统一可修改的源，不靠同一句prompt或同一个seed。** 同风格资产包、参数化材质、同一角色骨架与服装体系优先；已有3D道具时，背包图标优先从同一模型渲染，再检查最终尺寸辨识度。换色、文字、状态角标改参数或图层，轮廓和内容确需改变才重新生成。调色板能统一色域，不能统一透视、头身比例、装备零件或动作。[经验；[证据与反例](../../docs/research/2026-10-14-game-wp8-style-consistency.md)]

| 优先级 | 采用路线 | 何时撤回 |
|---|---|---|
| **质量优先** | ✅ 满足玩法的成熟同风格源资产；🧪 2D缺口沿[WP2](assets/2d.md)用Sunburst固定版本、多参考和保留图层，3D沿[WP3](assets/3d.md)按刚体／变形角色选择 | 局部修改持续串改身份、轮廓或挂点时，换分件、现成资产或收窄需求，不以人工美术修补兜底 |
| **性价比优先** | ✅ 同源的颜色、材质、尺寸和布局变体；🧪 无alpha图像缺口沿WP2对照Nano Banana2.1付费API | 原生参考编辑已满足时不加训练；全部重试、筛选和二次修改成本超过复用源时撤回 |
| **本地／免费** | ✅ 许可清楚的成套资源与已有程序化表示；🧪 ComfyUI加WP2已核klein4B／Qwen指定版本的原生参考 | 硬件、维护或通过率不合适则改现成资源/API；不自动换免费9B/dev或未清权风格模型 |

以上是零手修条件下的首试顺序，不是同题质量冠军；商业门槛沿授权总表，具体模型版本与成本见资源专题。[研究]

**🧪 LoRA只在实际类别反复出现风格漂移、训练源权利清楚且能摊销时再评。** 300件换色道具可能只需少量源资产；少数多向、多动作角色的需求反而更大。风格参考、身份参考和结构约束各有职责，不能只用宝石训练/试验后就推断人物、门和UI也一致。保留未入训练的类别与旧资产作为比较，避免训练集重现好看却无法新增内容。[经验]

**✅ ComfyUI保存配方与输出，seed只作采样参数。** 沿用已有工作流，保存实际执行JSON、参考/权重哈希、节点/依赖版本、采样参数（含seed、批索引）及裁切参数以及批准输出；PNG内嵌workflow不包含所有模型、输入和节点。换底模或LoRA先在旁路与旧件比较，不原地更新整套；缓存与QA结果必须随输入内容和配置变化而失效，文件存在不代表第二次修改已经完成。[一手／研究：固定源码与批量脚本反例见[WP8](../../docs/research/2026-10-14-game-wp8-style-consistency.md)]

验收同时看“属于同一个世界”和“仍是正确的东西”：在最终尺寸／渲染条件下混排旧件、新件、背景、UI和VFX，保留敌我、危险与稀有度的辨识差异。CLIP/DINO高分可能奖励错误复制参考物体；VLM作为异常筛查，不能单独放行，解析失败或漏检应保留为未知。改阵营颜色可批量更新对应图层/材质；改武器长度还须重看持握、碰撞和图标，不是换色验收。[研究／经验]

静态像素道具与简单刚体较容易收窄问题；像素逐帧动画不能靠减色补动作，低模/toon角色也不会自动修好蒙皮。固定视角、有限换装和成熟骨架更可控，代价是限制自由镜头、复杂表演与动态装备；先确认玩法能接受，再选风格。[经验]

**关键限制：现有公开证据不足以证明几百件跨2D/3D资产及第二次修改能全部零手修完成；本轮未运行生成模型或引擎。**[研究]

### 1.8 动画采用结论：骨架、位移、循环与接触分验

**✅ 已绑定角色和完整动作组优先；文本表演、视频动捕、数值控制移动分别补缺。** 先固定骨架与位移权威，改变外观尽量复用已验收动作；清零root不等于loop，首尾姿态相同不等于脚接触正确。当前商业/本地及2D三档见[动画专题](assets/animation.md)，固定源码反证见[WP4](../../docs/research/2026-10-14-game-wp4-animation.md)。**[一手／研究]**

关键局限：自动rig、IK或FBX出口不能制造缺失动作、正确蒙皮与隐藏肢体；仍需手画、刷权重或逐帧摆姿时，零手修路线应收窄或更换来源。

### 1.9 材质与特效采用结论：共同参数源与可控时间

**✅ 同风格现成材质／参数图优先，玩法相关特效先用原生粒子；生成贴图和视频只补明确缺口。** 材质的base color、normal／height、roughness与metallic由共同结构驱动，不能把四张独立生成图当同一表面；蓄力、取消和命中事件留在运行时，flipbook可以承担烟火内部动画，six-way需要正确的多方向源数据。商业、性价比、本地三档及撤回条件见[材质与特效专题](assets/materials.md)，固定源码、许可和真实采用反证见[WP5](../../docs/research/2026-10-14-game-wp5-material-effects.md)。**[一手／研究]**

关键局限：本轮没有同题资产、真实引擎性能及二次修改实测；Material Maker CLI故障不能外推整个工具不可用，现成工具发售案例也不证明全程零美术修补。

### 1.10 视频采用结论：可编辑镜头先行，生成只补固定片段

**✅ 引擎镜头或静态图＋程序运动优先，无叙事收益就删过场；🧪 生成视频只承担外观固定、少分支的短镜头。** 质量条件档比较Runway Gen-4.5/Aleph2.0及Veo3.1；性价比先复用资产，确需生成再评估Omni1.1；本地Wan5B作无对白基线，LTX作有条件的局部控制路线。Omni详细页也支持首尾帧/延展，不因总入口旧分工直接改选Veo；Aleph按秒更贵，但Edit Studio仅改短范围可能更便宜。具体成本、许可和撤回条件见[视频专题](assets/video.md)与[固定证据](../../docs/research/2026-10-14-game-wp7-video.md)。**[一手／研究]**

字幕、音轨与玩法进度独立于影片；正常结束/跳过/恢复走幂等状态出口。关键局限：局部编辑不保证非目标画面不变，本轮尚无零手修成套过场与真实设备播放验收。

### 1.11 入库与推荐的最低记录

资产登记保留：具体模型/snapshot 与下载来源、代码和权重许可证版本、生成日期、当时套餐/商业许可凭据、输入/声音权利、官方许可下载状态、必要署名与披露、程序处理和筛查记录。换版本/提供商、进入新发行地区、跨营收门槛或转为运行时生成时先重查 WP1，未查清只作候选。**[经验：根据 WP1 条款差异制定]**

授权通过只让方案进入 WP2–8 的质量、可控性、成本与引擎可用性比较，不能证明输出可获版权、无侵权风险或平台必然接收。

## 2. 游戏运行时的 AI

| 方向 | 现状 | 评级 |
|---|---|---|
| **生成式对话 NPC** | 只有开放回答本身服务核心玩法时才试；固定任务状态和不可逆奖励仍由确定性规则提交 | 👀 明确玩法收益后做对照，不替换所有对话树 |
| **受限动作选择** | 先以现有状态机／行为树为基线；模型只能选择允许动作也不保证延迟、有效性或玩法更好 | 👀 以同题收益与成本决定，不根据参数规模推定适用 |
| **生成世界／场景** | [Marble 等背景候选](assets/3d.md)仍需核网格、碰撞、导出和许可；可浏览世界不等于可维护的玩法状态 | 👀 背景或概念对照；不替代游戏引擎 |

表内是研究判断，不列未复核的收购新闻、通用延迟或“成功案例都如此”的归纳。运行时模型调用尚未实测，不能以离线资产调查外推其经济性或体验。

**运行时 AI 的工程要点**（和 Coding Agent 的验证闭环直接相关）：
1. **LLM 调用放在可替换的接口后面**：测试和回放时用固定回复的假实现，正式运行再接真模型。否则确定性测试和 bug 复现都会失效。
2. **先用无头模拟评估**：比如“行为树”对比“行为树 + 决策模型”，看玩家可感知的差异是否值得增加的复杂度（见 [02 验证阶梯 L2](02-verification-and-playtesting.md#2-验证阶梯从便宜确定到昂贵主观)）。
3. **成本和延迟**：云端成本随玩家调用增长；买断价需要覆盖预期用量，端侧路线则受最低设备、内存和更新预算约束。先估同一玩法的全程成本，不因“本地”就视为免费。
4. **内容安全**：玩家一定会尝试越狱，要有输出过滤和分级合规方案。

## 3. 外部约束：披露与玩家态度

**✅ 生成许可与发布渠道分别检查。** Steam 当前 Content Survey 重点是随游戏交付、由玩家消费的 AI 内容，区分预生成与运行时生成；后者还须说明防止非法内容的措施。普通开发效率工具并非该问题的重点，披露也不豁免侵权或内容规则。Unity Asset Store 的 AI 内容说明针对资产销售提交，不是所有 Unity 游戏的统一发行条款；Fab 摘要允许把 Standard License 资产整合进商业项目，禁止单独再分发，购买仍须核完整 EULA 与具体商品许可。Godot 引擎贡献和 Asset Store 继续按不同渠道判断。**[一手：2026-10-14 官方规则；来源、例外及未访问后台的边界见 [WP1 发布渠道](../../docs/research/2026-10-14-game-wp1-licensing.md#发布渠道不能被生成许可替代)]**

以下行业统计和历史争议保留原核实日期，不能单凭相关性决定某类资产一律采用或不用：

| 事实 | 来源 |
|---|---|
| GDC 2026：36% 的从业者在工作中用生成式 AI（程序相关用途中“代码辅助”占 47%）；但 **52% 认为它对行业有害**（2025 年 30%，2024 年 18%），美术（64%）、策划（63%）、程序（59%）最负面 | GDC 官方摘要 **[一手]** |
