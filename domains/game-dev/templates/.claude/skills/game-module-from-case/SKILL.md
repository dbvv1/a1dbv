# 从案例需求做核心模块

需求：$ARGUMENTS

**模块做完的标志是：它在某个案例的默认分支和公开网站里被真实游玩路径用到，并且写成了别人能照着做的知识页。** 独立实验、只在测试里跑通、只写了页面，都还没做完。网页案例承载不了的引擎专属部分（编辑器工具、导入设置、引擎物理等），以引擎小工程实跑通过加知识页为完成。

## 1. 从案例需求起题

- 一句话写清玩家或开发者得到什么：“MOBA 玩家看不到视野外的敌人，草丛能藏人”，不是“研究战争迷雾”。
- 需求来自案例的差距清单、brief 的里程碑或开发中真实卡住的地方。同一模块服务多个案例时，先接最需要的那个。
- 地图上已有的模块实验（如帧同步、存档、菜单焦点）优先接进案例，再开新模块。

## 2. 先读两三个最强实现

**动手前读到具体代码路径或设计原文，写一页对照，再决定写什么。**

- 去哪里找，按这个顺序：
  1. 引擎官方示例和文档：Unity 官方示例仓库（如 Boss Room、各 package 的 Samples）、Unreal 的 Lyra、Godot 的 godot-demo-projects；
  2. 同品类开源游戏：RTS／MOBA 看 OpenRA、0 A.D.，竞速看 SuperTuxKart，FPS 看 ioquake3、Xonotic；
  3. 做过的团队的原文：GDC 讲座与开发博客，如 Riot《Determinism in League of Legends》、Overwatch 的 Gameplay Architecture and Netcode（GDC 2017）、Rocket League 物理（GDC 2018）、Valve 开发者 wiki 的 Source Multiplayer Networking 与延迟补偿、Gaffer on Games 的固定步长；
  4. 服务端起点：托管服务和开源服务端（如 Nakama、Colyseus）的官方示例。
- 源码用 `git clone --depth 1` 并固定 SHA，读那个机制的实际代码路径。对照页写：数据结构、更新顺序、与其他系统的接口、边界情况、它们刻意不做什么、各自的代价。三者一致的部分作默认，有分歧的部分按我们案例的条件选。
- 许可与案例仓库不兼容的源码只提炼机制，不复制代码：上面的开源游戏多为 GPL，Lyra 受 Epic EULA 约束；MIT、BSD、Apache、CC0 的代码注明出处后可复用。

## 3. 做进案例的可玩版本

- 按案例的架构接入：玩法在固定步长、按种子可复现的模拟层，渲染和界面只读状态、只发命令。先定接口（输入、输出、谁拥有状态、生命周期），再实现。
- 合入门槛：模拟层单元测试、无画面批量模拟断言、真实浏览器里走一遍玩家路径。模块的可见部分（如迷雾边缘、存档提示）按 [game-quality-pass](../game-quality-pass/SKILL.md) 的机位截图对照。
- 做一次第二次需求修改：在接入后改一次真实需求（如迷雾加“侦察守卫”，存档加新字段并读旧档），记下改了几处、有没有破坏旧行为。这一步暴露接口是否站得住。
- 推送案例默认分支并更新网站；模块目录自包含，另一个案例能直接复用。

## 4. 写成知识页

- 写进 `domains/game-dev/` 的对应模块页，模块已有页面就合并补全，不另开新页。每节结构：**默认做法 → 实现起点（案例提交链接、关键文件）→ 引擎对照 → 何时不适用**。
- 引擎对照：Unity 写对应的官方包或 API 与接入点，Unreal、Godot 各一行对照。网页证明不了的引擎专属部分以官方文档为据；需要引擎实跑时交给装了引擎的本机做小工程验证（a1dbv 里走 local-jobs）。
- AI 怎样实施：哪些部分交给 Agent 一次写对、哪些容易错（典型失败和修法）、用什么验证。
- 更新模块地图的成熟度：进了案例并验证的改为“案例证实”。

**依据**：上述官方示例、开源项目与 GDC／开发博客为常用一手来源；“接入案例才算完成”来自 2026-10-27 的现状：菜单焦点已随 FPS 网站发布，帧同步仍停在实验。核实 2026-10-27。
