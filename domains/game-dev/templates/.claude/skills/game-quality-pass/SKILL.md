# 画面与手感的质量单元

目标：$ARGUMENTS

什么算达标见 [references/quality-bar.md](references/quality-bar.md)（画面、手感、内容三条达标线与记分卡），手感的管线、运动模型与标杆数值见 [references/feel.md](references/feel.md)。

**同一执行者整场景推进，不拆成逐层小卡**：按下方流程从最大差距入手，无环境光照和后处理的先做灯光层，再在同一上下文里连带调材质、天气、后处理、特效与声音；单元时限按所在项目，超时保全后续接。

## 1. 先有可靠的看图手段

**截图和录像必须是同机位、同状态、可重复的；做不到就先修看图手段，不改画面。**

按 [capture.md](references/capture.md#拍摄规范) 建固定种子／虚拟时钟、命名机位、录像、独占目录与画质 manifest；软件渲染图的使用范围、渲染器分类和看图回路时限都在该页。手感测法见 [feel.md §5](references/feel.md#5-测量与对照)。

## 2. 改之前先查别人怎么解决

先查同品类强作品与专业流程，读到手段再改。 同品类网页参照与本作默认先在同一机器、1280×720取样并排看；记录各自版本、视角、画质和实际renderer，参照不是同一游戏时不伪称同机位性能对照。整场景改动仍以本作前后同机位盲选验收，参照图只定方向，不增加升档或目标图完成前置。

- 先读品类要点：[references/genre-targets.md](references/genre-targets.md)（MOBA／公路竞速／战术 FPS 的画面语法、机位量法）。其他品类照同样结构先写一节。
- 再按差距查：开发者原文（GDC、官方开发博客、美术师的作品拆解）、同品类开源或网页高质量作品、引擎官方示例场景。专业环境美术的顺序是：美术方向（一页风格说明）→ 体块与比例 → **先打光** → 模块化套件与材质族 → 布景密度 → 后处理与调色 → 优化。画面差距多出在前三步，细节和后处理补不上。
- 目标效果图（paint-over）：把当前机位截图交给能保持构图的图像编辑模型，要求“保持构图、地形和玩法布局不变，按 <品类> 的美术方向重绘”，出 2–3 张，选一张做目标。从目标图提炼一页“目标说明”：5–7 个主色及明度、明暗结构（眯眼看能分几块）、材质族、光的方向和冷暖、各区域道具密度、角色轮廓规则。目标图只当方向，不进游戏。

## 3. 改完整场景，让视听服务同一体验

整场景由同一执行者联动推进，不拆成逐层小卡。网页的具体机制与失败反例见[整场景视听配方](../../../../assets/materials.md#web-scene-recipe)：共享地表 mask／PBR 通道、成组画质、后处理顺序、事件效果池与混音。先保存同机位默认图，再独立实现；参照源码公开不等于有复制许可。

1. **灯光、雾与色调**：先核实际材质的直接／间接受光路径，再选光源和遮蔽；不把 HDRI＋AO 当通用起点。一盏主光（大场景用级联阴影）建立明暗结构，雾色与天空同色系做空气透视，色调映射选定后固定，再用 LUT 调色。
  - Three.js 的 Standard／Physical 与 Toon、AO 和后处理链，以及 Unity／Unreal／Godot 对应入口见[材质与渲染路径](references/lighting.md)。

2. **空间层次**：近、中、远三层各有连续剪影；视线落点放地标；围合空间的墙、崖、建筑用同一网格的模块化套件拼，交接处有收边，不出现巨型素面方块。
3. **地表与材质族**：地表混 3–4 种可平铺材质（splat 或顶点色、地形图层），加磨损贴花，打破平涂；墙面和道具用 trim 材质，同一材质族共享粗糙度与色相范围。
4. **角色与可读性**：角色比环境饱和、对比更高；轮廓靠形状区分（武器、体型、剪影），不只靠颜色；必要时用边缘光或描边。
5. **布景密度**：按目标说明撒道具和植被（网页 `InstancedMesh`，引擎用地形散布或 GPU 实例化）。
6. **反馈与声音**：每个关键动作（开始、命中、结果）都有画面、声音、镜头三路反馈且同帧到达；先补缺失的环，再调幅度。混音分层（玩家动作 > 威胁 > 环境），重要声音出现时压低环境（侧链），有方向和距离衰减。
7. **界面**：信息层级与游玩净空优先，主要数字字号和对比足够，次要信息收进次级层；不缩字挤控件。

场景里缺的角色、场景件、动作和声音按 [game-content-production](../game-content-production/SKILL.md) 成套取得，不在质量单元里逐件补。

## 4. 同机位对比，非作者判定

- **四道反负优化阻断门**（详见 [02 视觉反负优化四道门](../../../../02-verification-and-playtesting.md#visual-anti-regression-gates)）：
  1. **强锁机位与多角度覆盖**：改前与改后必须同坐标、同朝向、同 FOV；角色与武器须加拍 **360° 五角度围绕＋多动作状态（站/瞄/蹲/跑/换弹/行进 4 帧）**，禁止只凭单张背影宣称动作达标。
  2. **像素分布与俯仰扫线预筛**：进评审前先跑 `python scripts/visual_pregate.py --baseline <前图> --candidate <后图>`（或 `--side-by-side`，可选 `--flip`）；启用 SSR/SSGI 的室内反射场景另跑 5 档仰角 `python scripts/visual_pregate.py --pitch-sweep <img...>` 检查是否存在随相机仰角移动的水平截断黑线；任一项失败即**自动 `FAIL` 退回，不交盲评**。
  3. **上下文隔离双序盲选**：在同一命名机位拼三联图或全角度拼接图，缩到 320 像素宽仍看得清进步才算有效。交给新上下文且**完全不看源码、FPS、IK 数值和提交说明**的非作者评审，A/B 对比须分别以 `[前 | 后]` 与 `[后 | 前]` 双序盲判，结论冲突视为未通过。
  4. **独立真 DPR 性能＋非补偿否决**：在目标分辨率（如 `1920×1080`、实际 DPR）关闭截图单独跑通交火与阶段切换核查稳态 `P95` 与 `0` 战斗卡顿长帧；同时阴影发灰、四手穿模、手离握把、静蹲沉地、道路堵截或俯仰截断线触发任一即一票否决。
- **合入和换默认按项目现行规则**。a1dbv 三案见[游戏方向细则 §6 第 3 条](../../../../../../docs/collaboration/game-taskbook.md#6-作品案例)：换默认用拟发布入口的本机真 GPU 整局 smoke、帧耗记录，以及一位非作者比较以当前默认为前图的同机位前后图。非作者判新版不更差且帧耗无明显劣化，才可换默认；软件档可供迭代，不代替真 GPU 验收。旧版留开关可回退；换默认不等于网站已部署。没有前图的新内容单列非作者标准件验收；手感补[操控对照](references/feel.md#5-测量与对照)，声音先验响度与削波。换默认后在 `docs/quality.md` 回写图和差距；变差就退回第 2 步换手段。
- 下一个单元从审查者给出的第一处差距开始；大差距没补上之前不做细节打磨。

**整场景反例与工具：** 积水、磨损、雨、雾和混音分别生成，最后叠加，容易出现室内下雨、湿地干脚步、低血暗角盖住敌人。用同一布局和接触事件驱动它们，表面、接触高度与介质一起传递，避免桥上干金属被桥下积水覆盖；既有接触测试核正常、高低重叠和查询失败。沿现有画质开关与浏览器帧耗入口，检查正常、受伤、开镜、暂停／返回状态，不另建一套验收框架。源码定位命令、失败反例与实现入口见[整场景视听配方](../../../../assets/materials.md#web-scene-recipe)和[Web混音](../../../../assets/audio.md#web-scene-mix)。
