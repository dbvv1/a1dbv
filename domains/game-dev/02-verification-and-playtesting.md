# 游戏验证：按缺少的证据选择试玩方式

> 最近核实：2026-10-22（UTC+8；本轮补自动反馈与真人换用比较，既有引擎契约沿原日期）。本文是公开文档、作者案例和既有源码研究的采用判断，未运行真实引擎或玩家实验。

## 1. 30 秒结论：这次改动，什么结果还没有证据？

**✅ 先用项目已有入口回答具体问题，再补缺少的观察；不按“单测→接口→像素→人工”的阶梯建设。** 编译通过只说明代码入口成立；状态正确、输入可用、画面清楚和玩家愿意继续玩，是四种不同的待证事实。真人反馈从核心玩法原型就开始，不排在自动化全部完成之后。

**第一步：把这次改动要证明的结果写成一句可观察的话**（例如“暂停后松键不会释放攻击”），在下表找到对应的行，用现有入口验证；现有入口答不了，才补最小观察手段。

| 现在要决定什么 | 优先采用的观察 | 什么情况下换／补手段 |
|---|---|---|
| 规则、费用、奖励次数、状态转移是否正确 | 现有纯逻辑测试；保留触发错误的动作序列与预期结果 | 错误依赖场景对象、物理、异步或引擎生命周期时，补真实运行路径，别继续扩大 mock |
| 角色、场景和物理是否真的在运行 | 现有 PlayMode／Functional Test 或可调用的运行时入口；观察相关对象、时钟和动作结果 | 编辑器通过但目标构建不同，就查目标构建；工具连接成功、进入 Play 都不足以证明玩法推进 |
| 长链交互能否走通，哪些状态不可达 | 已有状态快照＋玩家动作入口；需要时保存最小复现场景 | 文本／回合制通常适合；实时画面、设备绑定或呈现时序是问题时，补对应输入与画面，不另写一份游戏逻辑 |
| 改键、焦点、暂停菜单是否可用 | 经过实际输入系统与 UI 路由的测试；目标设备实际操作 | 调用按钮业务函数绕过绑定／焦点；引擎合成输入也不能证明 OS 与外设路径，设备问题须在目标设备复核 |
| 画面、动画、音频是否退化 | 固定场景的截图差异、动作录像／听验和目标设备帧时间；与已认可版本比较 | 静态差异适合找变化；拖影、遮挡、节奏、声音竞争要看连续过程，不能靠一张“漂亮截图”验收 |
| GUI 试玩没进展，是否继续自动改 | 核关键动作是否送达、玩家是否到达待验情境，再看反馈是否提供新信息 | 操作器漏控件先修测试器；后期细微交互或反馈重复时，保留旧版并追加独立试玩简报，不盲加轮数 |
| 自动分数与试玩感受冲突 | 分开可执行、规格符合、下一动作可理解与乐趣，先对齐评价问项 | 规格失败先修；可读性分数不测乐趣。问项已一致仍冲突时，再查裁判与目标玩家差异 |
| 动作是否有力、挑战是否公平、玩家是否想继续 | 让目标玩家完成具体情境，观察误解与操作，再比较候选 | 指标定位问题，人决定目标和取舍；自动通过、Agent 自评或短时玩通都不能证明长期乐趣 |

若改动只影响一个公式，无须为此建设整套试玩接口；若问题是第一分钟不好理解，也不应先把模拟对局跑到上千场。批量模拟适合已有可执行规则与明确统计目标；代理策略的胜率不直接代表真实玩家平衡。

**专用管线的“可交付”状态也要看降级项：** GCA 固定版本默认允许视觉供应商失败转警告；同 build／URL／运行回执能防陈旧证据，却不能证明未执行的视觉、压力或真人检查已通过。采用时核真实报告和覆盖，不撤掉上表仍适用的通用检查。

**本节来源与范围**：观察选择归纳自公开文档、作者案例与既有源码研究（研究）；GCA 降级与证据绑定见 [源码边界](../../docs/research/2026-10-14-game-wp13-agent-config.md#53-gca采用证据绑定机制不把配置通过当全面放行)（源码／研究），2026-10-20 复核；其余判断核实 2026-10-22（UTC+8）。

## 2. 工具到底观察了哪一段

**同帧多次rAF回调不是多帧，也不是时间倒退。** 全局包装`requestAnimationFrame`会同时观察游戏与测试器的回调；同一渲染时刻可以共享时间戳。保留所有原始回调，把相同时间戳的CPU耗时合计成帧CPU，另报每回调分布、回调数、独立帧数及独立帧间隔；不得删除零间隔样本来伪造流畅，倒序、缺值、负值仍拒绝。测试器的就绪等待用定时轮询，减少自我污染，但未记录回调身份时不能认定额外回调来自谁。CPU耗时与rAF间隔均不是GPU计时。

在 [MOBA-Like 固定检出 `c903a4e`](https://github.com/dbvv1/MOBA-Like/tree/c903a4e738b9224a3e5f677894cd1d3fece7eb63) 的根目录先运行 `npm ci`，再运行 `npm test -- tests/client/browser-smoke/full-match.test.ts`。这是 Vitest 单测，不启动浏览器；覆盖同帧双回调、全部同时间戳、倒序和非法值等情形（Node 24.22.3 实跑 9/9）。[原观察器修复](https://github.com/dbvv1/MOBA-Like/commit/b8a377078e15c0dd2fb7c367b0bf24adbee09468)核实于 2026-11-12。旧证据离线重算只能验证统计口径，不能补齐未执行的整局、交互或对照性能。

**✅ 复用现有测试／调试入口；发现观测缺口才加一个窄接口。** 项目没有 MCP 不意味着不能测试，也不因此要求安装。下表只列会改变选择的差别；具体接入见 [Unity](unity/01-toolchain.md)／[Unreal](unreal/01-toolchain.md)。

| 已有入口 | 能得到的证据；选择边界 |
|---|---|
| Unity CLI／Pipeline | 当前 Pipeline 提供时，`status --format json` 的 `frameCount`、`playerLoopTicking` 可帮助确认 PlayerLoop 推进；字段缺失改用既有进度观测，否则标明未验证，不能判为停帧；还要读本次涉及的玩法状态，不能把帧数增长当作伤害／物理已执行。 |
| Unity Input System 1.19 | `InputTestFixture` 用隔离的输入系统与合成设备测试绑定、交互和输入处理；不依赖真实平台后端／硬件。适合可重复的输入回归，外设与 OS 问题仍需实机。 |
| Unreal 5.8 | 原生 Functional Testing 可测关卡，Automation Driver 模拟应用收到的键鼠输入，现成定位器面向 Slate；当前文档未提供手柄／触摸支持。别把它写成通用真实设备试玩，也不因有 MCP 就假定所需测试工具已暴露。 |
| Roblox Studio MCP | 官方提供 `playtest` 子 Agent、状态／日志／截图与键鼠模拟；`character_navigation` 是另一个移动入口。导航到位置并不能证明玩家按键、UI 焦点与操作提示正确；回读应选对 Studio 实例及 Client／Server 状态。 |

**局限：工具的官方能力契约不等于本项目已验证。** 缺少结果就报告具体缺口，例如“逻辑序列通过，手柄返回菜单未验证”，而不是把一种入口的成功升级成全部验收通过。

**开跑前先检查自动化能否完成配置。** 定位到控件不代表能操作它，隐藏面板中的下拉框仍会等待可见。验菜单时走正常展开路径；固定画质的测试预设可以明确跳过这项可见性检查，但仍须触发原设置事件并核保存值，不能把预设当菜单可用的证据。

### 手感回归：数值规格、真实按键探针、类人合成玩家

**先沿玩家实际按键入口验方向、短拨和松开，再用合成玩家批量找回归。** 固定初速、初态与帧步，记录键的按下／松开、首次响应、带符号角度或位移、峰值和松键恢复。脚本要通过正常绑定和输入处理，不直接写油门／转向轴或调用模拟指令；只测应用内处理时，不能据此验 OS、外设或真实人的操作。反例：只给赛车物理输入轴，方向和幅度都能过，浏览器绑定却仍能把右转接成左转，或把轻点变成满舵。

**同动作绑两颗键时，先叠按、再只松一颗。** 关闭脚本回放，分别跑 `A↓、←↓、A↑、←↑` 和交换两键后的顺序。每步都让游戏消费一次输入，预期左转为 `1/1/1/0`，另跑单键 `1/0` 作对照。固定 [Uno com escada 的 Fable 版键盘回调](https://github.com/viktorkav/uno-com-escada/blob/48043ff29f7ba038083f327dc41d2c94cf64b0ef/fable/source/js/45_game.js#L15-L17)在隔离夹具中两种顺序都得到 `1/1/0/0`。同一夹具喂入预录指令时，[模拟读入路径](https://github.com/viktorkav/uno-com-escada/blob/48043ff29f7ba038083f327dc41d2c94cf64b0ef/fable/source/js/45_game.js#L130-L146)改走录带，收到 `1/1/1/0`；录带通过不等于键盘通过。[Star 的输入回调](https://github.com/dbvv1/Star-Rush-Reborn/blob/fd9efc1069a89ce76a6ba4b817aae2ce4c2263ef/race.js#L193-L196)按实体键分别保留状态，同样两种顺序均为 `1/1/1/0`。只测按键处理到车辆输入的交接，未运行浏览器或车辆模拟（本端实测，2026-11-23）。

**短拨先核输入被模拟采到，再用横摆判手感。** 记录事件顺序、输入消费 tick 数和带符号响应。若按下、松开都在两次取样之间，轮询当前按键状态的实现可能两次都读零；此例单列为采样诊断，不能拿它检验左右是否反向或转向是否过敏。固定 [Star 公路输入处理](https://github.com/dbvv1/Star-Rush-Reborn/blob/e25ea50e851cf1a7d2c12008c1f5d17f6949f337/race.js#L194-L196) 和[转向采样表达式](https://github.com/dbvv1/Star-Rush-Reborn/blob/e25ea50e851cf1a7d2c12008c1f5d17f6949f337/handling.js#L41-L49)在隔离 CPU 探针中实跑：右键两边沿之间不取样，前后读值为 0／0；保持八次取样，读到八次 +1，左键在一次取样读到 −1。未运行物理整局或真实浏览器按键，不据此认定玩家缺陷。另一个合同是 [ioquake3 的按帧时长比例](https://github.com/ioquake/ioq3/blob/52088b9eae247d8e321c8dc1fb49a879652854f9/code/client/cl_input.c#L138-L192)，不能拿同一套零／一预期去验（本端 CPU 探针与固定源码，2026-11-18）。

**瞄准回归要在模拟没推进时验画面接到的输入。** 用实际锁定后的鼠标处理器，安排一次发生在两个模拟步之间的渲染，分别记相机收到的角度和角色权威角度。只验“视角有变化”或只在下一 tick 检查角色角度，都可能漏掉渲染错误地使用旧瞄准。固定 [FPS-Like 的组装客户端测试](https://github.com/dbvv1/FPS-Like/blob/720450c790d4e2ae84bab6b4c8feabbe39c809c5/tests/offline-training-v1/client-squads.test.ts)中，模拟步增加 0，角色仍为 (0, 0)，画面入口收到 (0.10, 0.05) rad。将渲染输入在测试副本中换成角色角度后，原测试仍退出 0，新断言退出 1，未改运行代码时退出 0。在该固定版本安装锁定依赖后，用 Node 22.13.0 运行 `node --import tsx --test tests/offline-training-v1/client-squads.test.ts`。不要照该版本 `engines` 的最低值选 22.12.0：实测会在加载测试时因缺少 [`stripTypeScriptTypes`](https://nodejs.org/download/release/v22.13.0/docs/api/module.html#modulestriptypescripttypescode-options) 而退出，尚未执行瞄准断言。这是应用处理器到渲染入口的 CPU 实测，不测真实浏览器事件、实际画面或端到端延迟（本端实测，2026-11-19）。

**用有限反应的代理覆盖整圈，不以它的高分当真人通过。** 代理只输出按下／松开，经同一键盘入口，限制最短按键和频率，给感知加噪声、给反应加延迟。赛车实例用约 0.2 s（不是通用规格），普通／熟练各三种子，每趟跑三圈。状态预瞄如果比玩家能看到的更多，保留这个偏差；同一策略参数用于前后对照及未调参种子。

**先验坏夹具真的改变了响应，再跑整圈。** 固定初速、初态与按键时序，逐步对比限幅后的转向请求和实际轮角。Star 的二值方向键在灵敏度 100 与 120 时都被钳到同一满幅请求，隔离公路模型中两档的轮角曲线相同；这组对照没有施加故障，不能用来评价指标。要构造“短拨过强”，可只在测试副本中提高入舵速率，先核同一组按键下实际轮角确有差异；保留原按键入口，松开回正也照测。依据：[Star 公路模型的限幅和入舵速率](https://github.com/dbvv1/Star-Rush-Reborn/blob/f4b90161aad5558d3c6d0f50990110fe07c214c0/road-vehicle-core.js#L35-L52)（120 Hz 离线模型实测，非实机手感）。

**先用坏版本证明指标能分出已知问题。** 除完赛率，还记录碰墙／出路／打转、松键恢复和首次异常；用全帧率录像和同时间轴的按键、车速、横摆回看异常及关键弯段。独立赛车样本的反向和过敏夹具均 0/6 完赛；迟钝夹具也 6/6，但碰墙由 8 次升到 40 次。夹具按旧版实测量级构造，并非重跑旧构建；控制器只在当前版调过参。擦墙后路牌遮住视野是回看录像才发现的，碰墙次数解释不了遮挡。

**校准代理时，把成绩和驾驶行为分开看。** 各档分别用相同的一组种子对照；未完赛也记跑到哪。若已有连续接触状态，分别记接触次数和累计秒数：一次贴墙很久，不等于多次擦墙。先回看两版差异最大的同一弯段，用同步录像对上按键和车辆状态。反例：[Solid Rally 的新手对照](https://arxiv.org/html/2209.00459v1#S5.SS1)中，代理与真人组平均得分接近（14.33 对 14.00），但发生碰撞的时间窗占比为 17.34% 对 4.79%，出路时间窗占比为 5.92% 对 24.88%。论文碰撞含对手和护栏，统计的是时间窗占比，不是上例的碰墙次数（一手研究，2026-11-18 核实）。

**自动化只代替改操控、改镜头后的重复检查。** 学习成本、能否读懂抓地边界、驾驶信心、镜头舒适、声音和乐趣仍交目标玩家判断。公开研究支持用代理减少已选机制的低层调参成本，并不支持拿代理分数代替玩家偏好；若录像用于重现问题，同时保留可重放的输入带与初态，别指望只从像素反推动作。依据：[赛车样本与对照限制](../../docs/collaboration/demo-trial-20261117.md#赛车类人合成玩家能否替代部分人工试玩)、[自动调参研究](https://faculty.cc.gatech.edu/~riedl/pubs/zook-fdg14.pdf)、[从录像复现玩法的研究](https://sscalabrino.github.io/files/2024/FaSE4Games2024TowardsTheAutomatic.pdf)（本端样本／一手研究，2026-11-18；不是三个正式案例的实机验收）。

**完整一局按项目的自然结束条件验收，不按脚本运行了多久或出现结算页判断。** 使用正常配置，经实际输入或明确的玩家级入口，从开局推进到规定终局并记结束原因。多回合赛核回合记录和换边；有完赛收尾窗口的比赛，逐个参赛者核进度与最终状态。测试超时只能记未完成，不能充当玩法截止；缩短回合、改生命或直接装入终局情境仍是有用的状态转换回归，但不证明正常过程能走通。重开检查另核下一局实际动作，沿用[核心循环](05-gameplay-architecture.md#一条完整制作链先让第一局和第二局都能玩)的生命周期。

**帧耗和完整流程绑定同一次运行。** 从开局到终局连续采样，注明采样起止、实际 renderer、分辨率及暂停／页面隐藏区间；保留长帧，不把慢帧夹到模拟步长，也不用平均 FPS 隐去尾部停顿。比较新版与当前默认时保持同档、同入口规则和同输入方案。加速模拟、固定截图和短时采样各自报告，不冒充整局渲染成本。脚本实现这些检查只代表具备取证入口，真实运行结果回来前仍记未验。[^complete-match-evidence]

**整局帧耗和画面录像分两次采，不把两条曲线混在一起。** 同一构建、设备、分辨率和输入先关截图／录屏跑一遍完整流程，再开录制复跑用于看遮挡、闪烁和镜头时序。保留两次的最长帧和发生点；若仅录制时出长帧，先按同一段重复开关对照，不直接定为游戏回归或归因给录制器。反例：[同一 FPS demo 的整关复跑](../../docs/collaboration/demo-trial-20261117.md#同型号在旧作续接与空工程首交中的表现)未录制的三次最长为 33.4 ms，截图和录屏同时开启的一次出现 283.4 ms 长帧；单个样本不证明具体开销来自哪一步。（本端样本，2026-11-19。）

**对照帧间隔前，先核面板有没有剪掉最慢的帧。** 取连续前台原始帧时间戳，报告 p95、最长间隔和长停顿次数；切到后台与恢复另外记。若模拟每帧限制追赶量，等长的墙钟片段可能已经跑到不同场景：对齐赛道位置和运行 tick 窗，分别报墙钟秒数及运行 tick 差除以模拟频率。升降档响应仍按墙钟计。反例：Star 的 F2 排除 1 s 及以上间隔；用「九帧 16.7 ms、一帧 1,200 ms」的合成序列复算，面板口径约 60 FPS／p95 16.7 ms，原始序列却是 7.4 FPS／p95 1,200 ms。取[整局观察器](https://github.com/dbvv1/Star-Rush-Reborn/blob/f4b90161aad5558d3c6d0f50990110fe07c214c0/tests/smoke-full-race.mjs#L37-L51)的时间戳而非游戏面板；它当前固定 High，不能代验 Auto。依据：[面板采样](https://github.com/dbvv1/Star-Rush-Reborn/blob/f4b90161aad5558d3c6d0f50990110fe07c214c0/race-features.js#L106-L110)、[模拟循环](https://github.com/dbvv1/Star-Rush-Reborn/blob/f4b90161aad5558d3c6d0f50990110fe07c214c0/race.js#L215-L218)（源码与合成复算，2026-11-20；不是实机帧耗）。

**同一组原始数据用同一个 p95 算法。** 发布前后都从原始数据用最近秩（升序第 `ceil(0.95 × n)` 项）重算，同时报最长间隔与超过 50 ms 的次数。反例：180 个间隔里 171 个为 16.7 ms、9 个为 60 ms，[Star-Rush 面板](https://github.com/dbvv1/Star-Rush-Reborn/blob/a91b422375793c9ac62cd4fe842b56b2eba92fea/race-features.js#L105-L110)用零起点的 `floor(0.95 × n)` 索引，得 60 ms；[整局脚本](https://github.com/dbvv1/Star-Rush-Reborn/blob/a91b422375793c9ac62cd4fe842b56b2eba92fea/tests/smoke-full-race.mjs#L125-L131)用最近秩，得 16.7 ms。两者最长均为 60 ms，超过 50 ms 的都是 9 次；只看 p95 会把计算差异误读为性能改善（源码与合成复算，2026-11-22）。

**定位短卡顿，看它是否随单项改动出现在同一路标。** 整局仍报实际 p95；定位时关录制，用同一构建和路线按「旧件→只开新件→旧件」复跑。记录每个帧间隔两端的路标和阶段，过场与跨段间隔另记；在匹配的游玩段里，用同一个阈值（例如旧版稳定间隔的 1.5 倍，稳定 60 Hz 约为 25 ms），报慢间隔数／总间隔数、最长连续慢段的时长和起点。整局 p95 会受各段停留比例影响，不能单凭它给某个地形归因；浏览器帧间隔也不是 GPU 耗时。

反例：同为 92 个 16.7 ms 和 8 个 33.3 ms 间隔，慢间隔分散或连续时，p95 都是 33.3 ms、超过 50 ms 的都为零；最长连续慢段却是 33.3 ms 对 266.4 ms。[《雪线回波》整关记录](../../docs/collaboration/demo-trial-20261117.md#第六批11-24换生产手段用-blender-重做枪手和雪山)有 p95 回退但原因未查；上面的连续段数字来自合成复算，不是它的实机结果。

**测自动画质，首局对首局，重开对重开。** 比较两个策略时，两边都新开页面、不沿用历史恢复，保持开跑前停留和倒计时一致。专测重开时，保留上一局的档位和结算停留时长，再对齐起跑档、同一赛段以及画质控制器实际采到的间隔；玩家看到的帧间隔另算。别以为只截取开跑后的数据，就清掉了菜单对控制器的影响。实际档位和缓冲尺寸分别记录：两个档同尺寸时，不能凭尺寸认档。

反例：Star-Rush 的[候选控制器](https://github.com/dbvv1/Star-Rush-Reborn/blob/1bfd8fd803de232ca66043b8009d8bef7ee34fec/auto-quality.mjs#L16-L65)由[渲染器持有](https://github.com/dbvv1/Star-Rush-Reborn/blob/1bfd8fd803de232ca66043b8009d8bef7ee34fec/render-three.js#L19-L35)，[重开重置比赛](https://github.com/dbvv1/Star-Rush-Reborn/blob/1bfd8fd803de232ca66043b8009d8bef7ee34fec/race.js#L137-L140)，但[结算和倒计时仍绘制](https://github.com/dbvv1/Star-Rush-Reborn/blob/1bfd8fd803de232ca66043b8009d8bef7ee34fec/race.js#L215-L217)。用同一个低档初态，在合成序列中分别停留约 0、6、15 秒，再喂同样的倒计时帧，起跑档变成低、中、高；随后施加同样的 50 ms 帧间隔，到低档分别需 0、4.8、9.35 秒。仅改变赛前历史就能制造降档延迟差异；这些是控制器复算，不是实机帧耗（2026-11-22）。

**短命效果在交付时留快照，不在整局末尾查存活。** 接受指令不等于效果已交付。用只读快照在效果存续窗口内同时记录实际生成的对象、位置、到期 tick 和匹配的表现对象；后续检查界面与重开时复用这份快照，别要求效果一直存活。没生成、没接入表现层、错位置或观察时已经过期都不算通过。

MOBA-Like 的原检查在 R 技能及多轮 HUD 改尺寸后才问 E 区域是否还在。在原版的固定步长 CPU 复现中，Morrow E 于 tick 11 生成区域并挂接两个网格，147 按期移除；到 191，旧断言会报失败。用项目的固定步长入口核交付与到期两个点，可以检验断言时序；网格记录不是屏幕像素，也不能据此确定历史浏览器失败原因。[原浏览器断言](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/tests/client/browser-smoke/run.mjs#L208-L217) · [技能时长配置](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/src/content/catalog.ts#L483-L501)（本端 CPU 实测，2026-11-17）。

**只闪一瞬的画面异常，按实际动作对齐完整画面。** 例如从普通入口固定初始站位、视角、武器和画质，用真实输入腰射一发；保留含 HUD 的连续原分辨率画面，标记实际出枪后首个完成合成的画面，并检查前后是否缺帧。另从相同初态不扣扳机，截同一时间窗。验修复先用同一采法抓到旧版，再看新版；旧版没复现或关键窗漏帧，只记本次未复现。反例：合成的 60 帧／秒序列只在第 11 帧置异常，隔帧采样从偶数帧开始会漏掉，从奇数帧开始却能看到；录像标称帧率不证明采齐。该算例只验证漏检机制；[《雪线回波》玩家报告](https://github.com/dbvv1/a1dbv/blob/0696361e90c4c0893dbd08cdc46f6754f9d93210/docs/collaboration/demo-trial-20261117.md#L194-L204)没有确认黑线持续帧数、根因或修复。


**第一次看危险预警，要有交战上下文，但不给命中结果。** 从预警前一小段开始，以正常速度播放整个玩家视野；保留单位、地面特效及其它提示，不先圈出目标。到命中前即停，请没见过技能的人先答「哪里危险、往哪退」，再播放命中并看定位图。不用已知答案的反复看图替代第一次判断。这个试验看提示能否被发现与理解；要测实际逃脱，还要让玩家操作并核碰撞外沿已离开伤害区，不能只看角色中心。

**直接试用：取 MOBA-Like v24 的同一段交战。** 以 [固定版 `fa3076f` 的拍摄入口](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/docs/capture.md#请求与逐帧合同)为例，打开：

```text
capture.html?shot=gameplay&seed=1&input=march&t=18.8&frames=109&lighting=forest-light-v1&materials=quiet-family-v1&scene=forest-lane-v1
```

1. 以 60 帧／秒播放第 0–103 帧，不给读者看后面的判定或图注。此样例从第 64 帧开始出现 Veyra R 预警，第 104 帧才命中；前导时间不算进反应窗口。
2. 记录第一次回答后，播放第 104–108 帧并核实际伤害。加长窗口比只从 19.8 秒开始多 1 秒交战上下文；在原 `CaptureSession` 和 `createEffects` 的 CPU 复跑中，新增 60 帧没有目标预警，后 49 帧状态与特效逐帧相同，仍在 tick 596–615 预警，616 结算（0.67 秒）。[伤害范围按目标半径扩展](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/src/sim/simulation.ts#L1140-L1170)。
3. **只在首次回答之后区分「看见施法」和「找到危险」。** 若读者只说看见角色抬手，回看第 50–63 帧；若指出了圈却以为它是持续区域，就单独记为误读生效时机。固定版的 `CaptureSession` CPU 复跑在第 50 帧（tick 589）收到施法开始事件，第 64 帧才出现地面预警；[共享施法动作](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/asset-pipeline/presentation/motion-state.js#L8-L51)不标出地面落点，[虚线轮廓](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/src/render/effects.ts#L131-L158)没有倒计时。别把早到的动作算成额外的地面预警时间。
4. 保留三个画面参数：[普通首页](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/index.html#L1-L2)默认是森林场景、森林照明和 quiet 材质，[独立拍摄页](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/src/capture/client.ts#L60-L76)不继承，不带参数三项都回到 baseline。它不含玩家 HUD，只用于场内提示。上述定位是 CPU 实测，GPU 画面、新玩家的读图与反应仍待验（CPU 定位核实：2026-11-18、2026-11-22）。

**预警持续时间不是可反应时间。** 要核能否走出伤害区，复制预警前的输入，沿测定路线把同一移动指令延后几个 tick，读结算时的角色碰撞外沿和实际受伤事件，不用圈宽与最高移速代算。上例保持原导航、单位和 AI，沿离开圆心的方向下达移动：预警出现后最早下一 tick 生效；额外等待 2 tick 时成功，碰撞外沿仅多出约 2 cm；等待 3 tick 时仍在范围内并受伤。0.67 秒预警在这条路线只留出约 67 ms 的额外输入余量，不代表玩家反应时间，也不代表别的路线。盲看片仍只判读图，不把看到圈就当成能躲。依据：[命令、伤害与移动的执行顺序](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/src/sim/simulation.ts#L264-L291)（本端 CPU 实测，2026-11-19）。

## 3. 一个真实案例：答对了，为什么还走不出去？

Jeff Schomay 的 Crossword Dungeon 开发记录展示了适合状态接口的情境：网页、文字为主、回合制。他为现有游戏加 Node.js 外层，以文本呈现状态并发送合成事件，再让 Agent 建立指定情境的 fixture。正文保留的是作者公布的运行记录，不是本仓库复现。

“笼子陷阱”的关键路径是：答错被困→移动被拒绝→答对显示解脱→关闭提示→再次尝试移动。Agent 观察到房间完成而移动仍被拒绝，定位到 `state.caged` 未清除；修正后记录了坐标变化。作者随后仍人工发现其他 bug 和手感问题。

**✅ 借用的是“验证退出后的下一步”，不是“单元测试发现不了状态 bug”。** 若规则能独立调用，这条状态序列也能写成确定性测试；依赖实际事件分发时则保留运行时回归。只断言“房间完成”会漏掉“恢复移动”，换成更多截图也未必弥补错误的验收条件。这个案例支持给已有游戏补合适的观察入口，不支持所有新项目第一天先建 HTTP、文本渲染器和时间控制层。

**本节来源与范围**：案例来自 Jeff Schomay 的 [Crossword Dungeon 开发记录](https://blog.jeffschomay.com/letting-ai-play-my-game)（一手：作者报告与公开运行记录）；案例复核与采用判断为本仓研究，沿用 2026-10-15（UTC+8）。

## 4. 如何验证第二次修改：给已有动作加入暂停菜单

**✅ 先决定暂停时蓄力、输入缓冲和恢复后的释放规则，再选择能观察这些规则的现有入口。** 假设原先“按住蓄力、松开释放”已可用，现在加入暂停与设置菜单；下面是按风险组合的例子，不是每项功能固定跑几个异常场景。

- **规则回归**：用原有测试走蓄力→暂停→松键→恢复，按设计检查是否取消／保留、费用与释放次数。不是让测试自行决定“恢复后应该攻击”。
- **真实运行**：确认暂停前后相关对象与计时的变化。Unity `timeScale=0` 停止 `FixedUpdate` 和 `WaitForSeconds` 的继续执行，但 `unscaledDeltaTime` 不受它缩放；UE 的 Tick 可设置 `bTickEvenWhenPaused`。因此菜单能动、帧数增长、世界冻结可以同时成立，要检查玩法自己的时钟。
- **输入与 UI**：通过项目实际输入路径走暂停→设置→弹窗→返回，检查焦点、按键提示以及恢复后角色是否误释放；涉及改键／设备切换就加入该路径。Unity UI Toolkit `Button` 的 `ClickEvent` 与手柄 `NavigationSubmitEvent` 不同，`Button.clicked` 覆盖两者，仅调用业务回调会漏过这个差别。
- **玩家体验**：让人实际操作这段切换，确认按键释放是否符合预期、菜单是否可理解、恢复是否突兀；日志用来定位被拒绝／延迟的动作，不能替人决定操作是否自然。

**何时补接口？** 只有当前无法回答关键问题时，例如看得见“没有攻击”，却分不清输入未到、状态拒绝还是动画延迟，才在已有入口增加对应状态或时间戳。复现场景保留版本、输入序列与预期结果；不要为了自动试玩复制规则实现或改造全部架构。

### 重复 Play 与新进程：先核实这次从什么状态开始

**✅ 第二次改动触及启动、静态订阅／缓存或编辑器热更新时，保留“刚编译后的首次进入”和“不改源码的退出→再进入”两个观察；需要判断首次启动时，再用新进程走同一动作。** 复用项目已有 PlayMode／Functional Test、日志与操作入口，不新建一层试玩服务。只改无共享状态的公式、已有测试已覆盖输入输出时，无须强制双 Play。

- **Unity 使用关闭 Domain Reload 的迭代设置时**：记录 Domain／Scene Reload 开关；第一次完成动作后退出，不修改脚本、不主动刷新，再进入并核对动作结果、回调次数与本局初始状态。脚本变化触发的刷新仍会重载域，所以“每改一次代码就 Play 一次”可能一直看不到残留订阅；另一方面，关闭 Scene Reload 的历史缺陷也曾表现为首次失败、第二次成功，不能只保留较好的那次；维护反例见本节末来源。
- **UE 只改 `.cpp` 也要看改了什么**：Live Coding 后已有对象不自动获得 `.cpp` 构造函数里的新默认值。若改动涉及初始化，回读旧实例及重新完整构建、启动后的实例，并区分蓝图／关卡保存的覆盖值；不要因为热会话仍显示旧值就反复补业务逻辑。涉及 Object Reinstancing 时，另查缓存引用是否失效重建、退出是否正常。

**关键局限：这些检查区分状态来源，不保证发布正确，也不表示每个改动都要打包。** Realm 的第二次启动挂起与 NGO 的首次进入漏回调都是已处理的历史维护案例；本节末来源给出具体版本、修订与未实测范围。

**本节来源与范围**：暂停时钟见 Unity [timeScale](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Time-timeScale.html)、[unscaledDeltaTime](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Time-unscaledDeltaTime.html) 与 UE [FTickFunction](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FTickFunction)，输入路由见 Unity [UI support](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.19/manual/UISupport.html)，均为官方文档（一手）；按风险选择动作链与“何时补接口”为本仓研究。重复进入部分含 Unity 6.3 [Domain Reloading](https://docs.unity3d.com/6000.3/Documentation/Manual/domain-reloading.html)／UE 5.8 [Live Coding](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-live-coding-to-recompile-unreal-engine-applications-at-runtime) 官方契约（一手）及 Realm／NGO 维护记录（一手／社区），具体版本、修订与未实测范围见 [WP10 重复进入补研](../../docs/research/2026-10-14-game-wp10-client-modules.md#重复进入补研不要让编译刷新替你重置验收状态)。引擎契约原核实 2026-10-15（UTC+8）。

## 5. 质量上限：可测的部分交给工具，体验取舍交给人

**✅ 把“手感不好”拆成能修改的假设，而不是写成“没有可计算标准”。** [04 客户端质量](04-client-modules.md)已结合 Celeste、Celeste 64 和 Deepnight 的公开实现，区分输入容错、运动、反馈与呈现。借用其机制时，应保持纯呈现对照与规则变化分开：视觉后坐力与实际位移不是同一改动，顿帧／缓冲也会改变操作时序。

| 具体问题 | Agent 可以推进什么 | 人保留什么决定 |
|---|---|---|
| 按了没反应／恢复后误操作 | 对照输入、动作接受、首次反馈的程序时刻；检查缓冲消费和状态退出 | 容错窗口、动作承诺是否适合玩法；程序日志不等于外设到显示器的完整延迟 |
| 攻击看不清／画面不顺 | 对比同场景运动录像、帧时间和命中反馈，找长帧、遮挡与信号冲突 | 哪个威胁应优先被看见，效果是有力还是干扰；用目标设备连续试玩判断 |
| 换素材后风格或清晰度退化 | 自动检查规格、引用、布局与基准截图，生成候选对照 | 选择认可的基准、判断风格与信息层次；不是把全部美术检查留给人 |
| 玩通却无聊／策略单一 | 汇总行为与失败位置，比较候选规则，按已定目标模拟 | 目标玩家、挑战、节奏与公平性的取舍；Agent 能帮助迭代，不能自证好玩 |

**✅ 反馈重复时，换一个明确的问题，不先换整套工具。** GUI 没玩过去先核输入与观察；已经玩通但改了几轮仍说不清改善在哪里，就保留当前可用版，请独立试玩者描述目标、卡住的位置和必须保住的体验。程序员把简报转成候选修改，再沿原路径对照。

**真人参与不等于自动获得正确答案。** 先统一情境和评价问项，再比较分歧；用目标玩家回答可理解性、挑战与继续玩的意愿。若新增简报没有可执行信息，或维护／试玩投入超过所解决问题的价值，就停止扩展反馈回路，保留有效回归与原型真人试玩。

**截图差异不是审美评分。** UE 截图比较支持容差，也可关闭 TAA、运动模糊等噪声来源；这有助于稳定回归，但若正在检查拖影／动态清晰度，就必须另外观察保留实际渲染特性的运动过程，不能用“关掉后通过”代替问题解决。

**同一机位和 tick 不够：镜头有记忆时，A、B 各自重放。** 从遮挡前同一初态与输入开始，分别跑完两版，再对齐相同 tick；只想比较定格开关时，则每次先恢复同一份完整的镜头状态。记录理想机位、实际机位与碰撞缩距，交换 A、B 执行顺序再跑一次：同一版的机位如果变了，先查上一轮留下的状态，别把差值判成画面改进。

反例：Redrock 的[固定机位脚本](https://github.com/StarKnightt/redrock/blob/028846ab4adf44358ce389f7f3a48738fc574f0b/tools/campair.mjs#L29-L65)适合在同一暂停帧看「有无整套防穿墙修正」。但[关碰撞会清除缩距、抬升和侧移](https://github.com/StarKnightt/redrock/blob/028846ab4adf44358ce389f7f3a48738fc574f0b/src/car/camera.js#L280-L354)，即使 `dt=0`。用固定版 `ChaseCamera`、同一车位和合成射线结果，有历史的开／关／再开镜头 x 坐标为 6／10／9 米；另建镜头实例并从同一初态开启，回到 6 米。（本端函数对照，2026-11-23；未用真实场景渲染或评估舒适度。）

**验某个视觉线索，先让评审指出线索，再回答它的意思。** 例如验赛车路牌能否更早指明方向：先给非作者匿名、同机位且同 tick 的原始场景图，问「三连箭头路牌在哪、指向哪」，两题都答对才记该版首次可辨的 tick 和车位。只答对方向，可能是从弯道形状猜的；先给整页截图，还可能直接从 HUD 的左右提示读到答案。同一时刻只有一对图，只能判断那一帧，不能判断谁更早。先单验路牌，再用完整 HUD 看正常游玩时会不会被其他提示抢读。Star 固定版本的普通 PNG 与 `-scene.png` 实际写入同一份画布字节，不能分别作为「有 HUD／无 HUD」两份证据。依据：[HUD 指向](https://github.com/dbvv1/Star-Rush-Reborn/blob/1796e9fc65c1af64415ecbf151432f0e273c1c3c/race.js#L192) · [截图写入](https://github.com/dbvv1/Star-Rush-Reborn/blob/1796e9fc65c1af64415ecbf151432f0e273c1c3c/tests/capture.mjs#L70-L82)，源码核实 2026-11-18。后续[本机同机位图与非作者盲评](../../docs/collaboration/local-jobs/B-STAR-COAST-READ-TURN-20261117.md#当前结果)中，粉色与深蓝原图都在 21.50 秒首次判对，320 像素宽缩图都在 23.00 秒首次判对。深蓝对比更清楚，但这组采样没证实读向提前，保留默认；静帧也没验证玩家是否来得及打方向。

**先分清源码、构建与实际加载的脚本。** 固定源码 SHA，在隔离目录重建并保存构建退出；从最终入口的实际脚本响应取字节，按路由与该次新构建的对应文件比 SHA256。客户端文件和服务端内嵌脚本即使互相匹配，也可能一起是旧生成物；不能只核 checkout 或 URL。默认与候选用同一口径，构建字节一致仍不证明候选已画出或没有回退。[^fresh-served-build]

**拍候选前，先确认当前帧确实在运行候选。** URL 带了开关、PNG 存在或渲染器可用，仍可能是在拍初始化失败后的默认回退。沿现有捕获入口同次读取画面元数据与实际运行状态，按本次入口校验开关、警告、后端和模拟时钟；默认入口应有自己的预期，不一律要求开启候选。先保存该帧的错误与 renderer，再让校验失败，避免报告沿用上一帧信息。Star 原硬件档入口曾缺这道检查，现沿原捕获脚本修正；正常、缺状态、回退与错配的 CPU 契约已过，真实硬件与新图仍未验。依据：[捕获接受契约](https://github.com/dbvv1/Star-Rush-Reborn/commit/ce68aa13fc958a9331b81edfdca7a62a5efa4cad)，2026-11-11；工具检查不替代同机位盲评，也不证明原拍摄调用已退出。

**场景先就绪，也不能漏掉稍后加载的角色与武器。** 固定拍摄应等待这张图实际使用的生产消费者就绪，失败或缺少状态就停止，别用固定延迟碰运气。FPS 训练候选原先只等环境标准件与材质，角色、RX24和命中源还在加载或已经回退时也会报告可拍；[原捕获入口修复](https://github.com/dbvv1/FPS-Like/commit/f3ddecdd26cd4a702e2d81515f6fb85d06f734f0)直接等现有三项状态，没有另造加载层。这是生产控制流的 CPU 复现与回归，未验真实网络、素材画面或浏览器；不依赖这组训练资源的材质对照继续用原入口。核实：2026-11-11。

**首帧卡顿先分清编译、上传和实际绘制，再决定要不要预热。** Three.js WebGL 的 `compileAsync` 只准备当时挂在对象树里的组合；有并行编译扩展也只等完成状态，不检查链接成功，无扩展时更不能把 Promise 返回当作完成信号。它不上传纹理，也不运行实际阴影／后处理链。先从冷开记录真正首次可见绘制和首次普攻／施法；若确有编译卡顿，再用首个状态同步后已挂载的对象和真实场景配置准备组合，对照开局时长和首个动作帧耗，避免把同一停顿挪进加载。只在事件中创建的特效、改变灯组的组合和独立后处理仍要走真实绘制。MOBA 森林默认先同步、直接 draw，再经含选择性 Bloom 的后处理；现有提交标记仅证明调用推进，不替代编译日志与画面。依据：[Three 编译入口](https://github.com/mrdoob/three.js/blob/acf77e4c7ea413a0a9638baacef3d78e254b2cac/src/renderers/WebGLRenderer.js#L1519-L1577)、[MOBA 首绘](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/src/client.ts#L121-L129)、[真实渲染链](https://github.com/dbvv1/MOBA-Like/blob/fa3076ffc8d1304bd64e74f8dc1a6f2a5167d939/src/render/world.ts#L70-L87)，2026-11-18；只核源码，未测得本案首帧卡顿或预热收益。

**重开或读档后，再核一次实际入口。** 它们会重新装配资源，中途退回默认可能被下一次成功重开掩盖。MOBA 的[既有交互 smoke](https://github.com/dbvv1/MOBA-Like/commit/18b2634b88d6b51fcc5adb508db9a404c90dd82c)已把当前默认／quiet 选项贯穿原操作链，并在每次重建后核 URL、版本、后端和回退提示；已退役的灯光改验可见恢复。CPU 回归通过，普通诊断没有材质激活字段，不能据此宣称材质已上屏；这条交互链也没有覆盖自然整局或帧耗。核实：2026-11-11。

下一轮只改变明确的问题：先确认动作／画面是否改善，再看第二次需求修改会不会破坏它。人的判断与自动回归相互补充，不需要宣称 AI 不可能做出好游戏，也不把测试通过当作品质保证。

### 短提示也要验被打断之后：可读时间与有效期分开

**🧪 在已有反馈入口试一条完整动作链，不先加统计面板或通用消息队列。** Firefly Lasso v86 的三次首夜实玩中，结算的大圈建议确实改变了下一局画圈动作；最大圈从 3 变为 8，但仍超时，不能把分数增加当成受控改善。作者连续两版先让动作结果与教学提示错开，再保住隐藏提示的剩余阅读时间，给出了可执行的二改目标。

- 教学提示刚出现→触发实际成功／失败反馈→反馈退场：仍有用的提示能继续读，而不在不可见时耗尽。
- 如果提示的成立条件已结束，就清除而不是补播。例如 MOBA 已解除眩晕，不应恢复旧的拒绝原因；赛车越过弯道，不应再提示该弯的动作。
- 完成本局→正常重开：用已有真实结果给一条下一局动作，再观察是否采用。FPS 已有攻守与结束原因，进攻超时落败和防守守时获胜应给不同结论，不需要先新增投掷训练。

来源与范围：本端实玩、作者 v85／v86 连续修订及三个项目固定入口，见 [Firefly Lasso 完整记录与迁移边界](../../docs/research/2026-10-23-game-worth-trying.md#firefly-lasso先让反馈读得到再看重开后是否改变动作)，2026-11-03 UTC。隐藏提示的精确计时未独立测量。2026-11-07，FPS 已将有依据的一条结算建议接入现有训练候选，并核双方换边、终局及重开首帧；同日 MOBA 候选补了取消瞄准时撤旧指令，并保留后来到达的真实拒绝原因；隐藏提示阅读时间与 Star 迁移仍待试。无画面回归不替代目标设备、玩家采用与长期体验验证。

## 当前最高水平：保住旧体验，不能只看改进总分

**✅ 默认沿用已有工程，补“真实动作路径＋必须保留条件”，不为评分换整套管线。** 试玩者／director 提供修改线索，独立评分裁判核对结果；反馈生成者不能凭自己的简报宣布放行。可以装入合法起始情境，但不能直接设成待验结果；动作须经过实际输入或明确的玩家级入口，并核可见游戏的同一状态。Thomas Ricouard 的 2026-09 实践把命名场景与着陆→步行→存档重载→起飞的真实行程分验；场景出现不等于行程走通。新增／替换动作和音效后，仍须在新版本重验旧关卡、引用与玩家反馈，不能让画面总分补偿旧关无法重开。

| 主要选择 | 领先替代与对照 | 本仓决定 |
|---|---|---|
| 继续 GUI 反馈还是追加真人 | Play2Code H 中，真人反馈在筛选出的中等增益任务后期获得更高 rubric 成绩；C.3 又有测试器漏控件反例 | 基础交互继续自动复现；细微交互／低增益先核观察，再补真人，而非把失败一律归因于游戏 |
| 原循环停滞如何推进 | RSIGame F.2 把独立 director 简报与同检查点继续开发比较；也有对照自行追平的游戏 | 冻结可用版本，给独立观察者明确情境；仅采纳能解释问题的简报，不强制每轮换人 |
| 自动评价能否代人 | Spec2Game 区分可执行、规格与呈现；对齐问项后人机一致性提高 | 先修评价覆盖；可读性与乐趣分别验收，避免为错问的问题换整套判定器 |
| 旧需求与修复是否保住 | GameXpert 累积需求、RSIGame 候选／保留版与下文 RAID 修复反例 | 保原工程、旧动作与硬性保留条件；探索和修复验收分账 |
| 输入、状态、存档、视听、性能与真机 | 上述生成／评分研究未覆盖完整设备和生命周期链；现有原生契约与连续观察回答不同问题 | 保留 §2–5 的通用检查；用 GUI 补观察，不替代确定性规则或目标设备验收 |

**完整游戏品质闭环的最高水平未知；近期领先候选支持按反馈缺口换手段，而不是无限自评。** Play2Code（Huang 等，2026-10 修订）、RSIGame（Wu 等，2026-09）与 Spec2Game（Cai 等，2026-10）分别提供真人反馈、外部观察与评价问项的对照。这是有证据支持的可行推荐，不是已证主流或最优：GUI Agent 适合找遗漏、留复现轨迹；没玩过去要区分游戏缺陷、操作能力与观察缺失。人继续判断可读性、节奏和手感；原有规则、输入、取消、存档、设备与性能检查仍适用。完整例子见本节末来源的 P32 两次需求继承设计；本仓尚未运行该游戏链，长期乐趣与目标设备效果仍须项目自身验证。

### 当前生产实践：探索没再找到，不等于修好了

**✅ 保留现有回归，把 Agent 的探索发现转成可复验的旧策略／动作。** 先核输入是否送达、状态是否匹配，由人确认是游戏缺陷、测试器失败还是设计允许；修后专门重现原条件，再继续探索。不能用下一轮“零发现”替代修复验收。

**工业领先候选也保留这道人工判断。** EA 的 RAID（Fuchs 等，2026-07）在 NHL26 旧开发版用强化学习找不同进球策略；作者明确说重新搜索未发现旧漏洞、旧策略模型因动态变化失灵，都不足以证明修复。它不是 LLM coding Agent。较早的 TITAN（NetEase Fuxi 等，2025-09，GPT-4o）提供商业 MMORPG 的 LLM 测试参照，但报告仍须人工分诊；独立制作 Deckhand（2026-08，Godot＋Claude Code）则把误点造成的假阻塞修成测试器校验。条件与原文见本节末来源。

**完整生产闭环的最高水平仍未知，当前推荐属于可行层。** 主流参照仍是既有引擎测试、脚本回归与真人试玩，不据个案估采用率。Agent 可整理轨迹、写回归与寻找遗漏，人保留根因核验和体验取舍；重训、误报与接口维护的总成本超过收益时，撤回自动探索而保留有效回归。上文的视听、输入、存档与目标设备检查不变。
