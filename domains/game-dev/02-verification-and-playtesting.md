# 游戏的验证闭环：让 Agent 自己试玩

> 核实时间：2026-10-08。
> 主干的核心结论是“**验证闭环比模型选择更重要**”（见 [07 工作流](../../docs/07-workflows.md)）。游戏恰恰是**最难验证**的软件之一，所以这一页是整个游戏分支最关键的内容：**AI 和游戏开发结合得好不好，主要看这一环。**

## 1. 为什么游戏特别难验证

| 特点 | 对 Agent 的影响 |
|---|---|
| **实时** | 截图之间状态已经变了。社区例子：一个弹弓绕行星的物理游戏，Agent 截一张图、再截一张，中间玩家已经飞出地图 **[社区：HN 评论]** |
| **状态多、交互链长** | 一个 bug 可能要走十几步才能复现；只靠截图导航，“光是简单移动需要的截图数量就很惊人” **[社区：原文]** |
| **涌现行为** | 单元测试覆盖不到系统之间的组合 |
| **“好不好玩”没有判定标准** | 测试能判断“对不对”，判断不了“好不好玩”；Simon Willison 观察到 vibe 出来的游戏“大约只好玩 75 秒” **[社区：原文]** |
| **编辑器状态不可靠** | 失去焦点的 Unity 编辑器可能停在第 1 帧，状态却显示 playing **[一手：Unity 官方 Skill]** |

## 2. 验证阶梯：从便宜、确定到昂贵、主观

按从下往上的顺序搭，**越往下越便宜、越能让 Agent 自己跑**：

| 层级 | 手段 | 能回答的问题 | 谁来跑 | 例子 |
|---|---|---|---|---|
| L0 | 编译和静态检查 | 能不能编译、有没有明显错误 | Agent | LSP 诊断、`unity recompile`、Unreal Live Coding |
| L1 | 纯逻辑单元测试 | 规则和公式对不对 | Agent | Unity EditMode 测试（逻辑写在纯 C# 类里） |
| L2 | **无头模拟 / 批量对局** | 数值平衡、边界情况、崩溃 | Agent | 把一场战斗模拟上千次，看胜率分布 **[社区]** |
| L3 | **状态接口驱动的试玩** | 功能在真实游戏循环里是否成立 | Agent | 文本渲染器 + HTTP 输入接口（见第 3 节） |
| L4 | 引擎驱动的试玩 | 场景、物理、UI 是否正常 | Agent | Roblox `playtest` 子 Agent + 输入模拟；Unity Play 模式 + `frameCount` 检查 + `eval`；Unreal 自动化测试，以及**打包版托管 MCP**（见 [unreal/01](unreal/01-toolchain.md#14-一个容易被忽略的能力打包后的游戏也能跑-mcp)） |
| L5 | 像素 + 系统输入的 Agent | 无法暴露内部状态的游戏 | Agent / 第三方服务 | 一个做了两年类似工具的团队也是从纯文本表示起步，后来发现只有少数游戏适用，转向纯像素和系统输入的方案（nunu ai）**[社区：HN 评论，厂商自述]** |
| L6 | **人工试玩** | 手感、乐趣、美术一致性 | **人** | 没有替代品 |

**关键认识**：
- L3 的性价比最高，却最常被跳过。多数人直接从 L1 跳到 L4（让 Agent 截图看画面），结果又慢又不可靠。
- L6 不是“验证不充分时的补救”，而是**结构性的必需**：“好不好玩”没有快速、可靠的判定标准，Agent 无法自己优化它。这和主干里“可维护性没有快速判定标准”是同一个道理（见 [docs/14 综合分析](../../docs/14-synthesis.md)）。

## 3. 案例：把游戏变成 Agent 能玩的形态

来源：Jeff Schomay《[Letting AI play my game](https://blog.jeffschomay.com/letting-ai-play-my-game)》（2026-04，HN 136 分）**[社区：原文]**。游戏是网页上的回合制“填字 + 地牢”游戏《Crossword Dungeon》。

**做法**：
1. 考虑过浏览器自动化 MCP，但放弃了：截图太多、太慢。
2. 让 AI 写了一个 Node.js 包装层，**不改任何游戏文件**：
   - 根据游戏状态渲染一个**文本版画面**（ASCII 地牢 + 角色和遭遇面板）；
   - 另外加一张**专门给 AI 导航用的紧凑地图**（同样的房间和走廊，换了一种 AI 更容易理解的格式）；
   - 用 HTTP 接口发送**合成输入事件**（`/key?k=ArrowLeft`、`/dismiss`）。
3. AI 的自述：“游戏完全可以通过无状态的 HTTP 调用在终端里玩……运行逻辑、事件流、状态机和浏览器里完全一样。”
4. 再给它**生成测试场景（fixture）**的能力：描述一个 bug，它就搭一个最小场景复现、亲自体验、修代码、再验证。

**效果**：
- 用 Claude Code（auto 权限模式）跑一个里程碑，指令是“**一项一项做，每项都试玩正常路径和不同场景，确认完全可用再做下一项**”。
- Agent 在试玩“笼子陷阱”时发现：答对之后仍然不能移动，原因是 `state.caged` 在房间解开后没有清掉。它自己改代码、再试玩、确认修好。**这种 bug 单元测试通常发现不了。**
- 作者原以为每轮要人工试玩好几个小时，现在大部分功能验证交给了 Agent。
- 意外收获：AI 卡住的地方和得出的策略，**和人类玩家很像**，可以当作早期的可玩性信号（但不能替代人）。

**HN 评论里的补充** **[社区]**：
- 回合制、文本为主的游戏可以更进一步：完全分离逻辑和渲染，用蒙特卡洛方式**无头模拟上千局**，不需要 LLM；
- 实时物理游戏：给 Agent 一个**代码级接口**（能暂停、单步推进、直接读状态），而不是让它看画面；
- 有人把 MCP 接到 MUD（文字网游）上，几个 Claude Code Agent 在不同窗口里互相聊天、合作建造新区域。

## 4. 设计原则：为“Agent 可试玩”而设计

这是“为可测试性设计”在 Agent 时代的升级版。新项目从第一天就做，老项目可以像上面的案例一样**在外面包一层**，不动原有代码。

| 原则 | 做法 | 在 Unity 中的落点 |
|---|---|---|
| **逻辑和表现分离** | 规则、数值、状态机写成纯代码，不依赖渲染 | 纯 C# 类 + 薄的 MonoBehaviour 胶水层 |
| **状态可导出** | 一个命令就能拿到当前状态的结构化快照（JSON 或文本） | 自定义 `[CliCommand]`，或 `unity command eval` 读状态 **[一手]** |
| **输入可注入** | 用命令或接口发送玩家动作，而不是模拟点击屏幕坐标 | 输入系统抽象出“动作”层；调试命令触发动作 |
| **时间可控** | 能暂停、单步、加速；随机数可固定种子 | `Time.timeScale`、固定随机种子 |
| **场景可加载** | 一个命令就能把游戏置于指定场景（测试 fixture） | 调试场景加载命令；ScriptableObject 存测试场景 |
| **运行可确认** | 确认游戏真的在推进，而不只是“进入了 Play 模式” | `unity status --format json` 的 `frameCount` 和 `playerLoopTicking` **[一手]** |

把这些写进项目的 AGENTS.md，并告诉 Agent：“**每完成一项功能，就用试玩接口验证正常路径和至少两个异常场景，再做下一项**。”

## 5. 什么必须留给人

| 必须人工判断 | 原因 | 建议 |
|---|---|---|
| 手感（操作响应、打击感、镜头） | 没有可计算的判定标准 | 每个里程碑安排人工试玩，记录具体问题后交给 Agent 改 |
| 乐趣和节奏 | 同上；Agent 能做出“像游戏的东西”，做不出“好玩的东西” **[社区]** | 核心玩法循环由人设计、人验收 |
| 美术风格一致性 | 社区实测：Agent 摆放物体时材质不统一、比例错误、没有灯光 **[二手]** | 美术验收不交给 Agent；Agent 负责批量导入设置等机械工作 |
| 数值平衡的**目标** | “什么样的平衡是好的”是设计决策 | 人定目标，Agent 用 L2 无头模拟去逼近 |
