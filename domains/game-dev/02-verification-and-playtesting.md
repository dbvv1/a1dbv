# 游戏验证：按缺少的证据选择试玩方式

> 最近核实：2026-10-22（UTC+8；本轮补自动反馈与真人换用比较，既有引擎契约沿原日期）。本文是公开文档、作者案例和既有源码研究的采用判断，未运行真实引擎或玩家实验。

## 1. 30 秒结论：这次改动，什么结果还没有证据？

**✅ 先用项目已有入口回答具体问题，再补缺少的观察；不按“单测→接口→像素→人工”的阶梯建设。** 编译通过只说明代码入口成立；状态正确、输入可用、画面清楚和玩家愿意继续玩，是四种不同的待证事实。真人反馈从核心玩法原型就开始，不排在自动化全部完成之后。

**第一步：把这次改动要证明的结果写成一句可观察的话**（例如“暂停后松键不会释放攻击”），在下表找到对应的行，用现有入口验证；现有入口答不了，才补最小观察手段。

| 现在要决定什么 | 优先采用的观察 | 什么情况下换／补手段 |
|---|---|---|
| 规则、费用、奖励次数、状态转移是否正确 | 现有纯逻辑测试；保留触发错误的动作序列与预期结果 | 错误依赖场景对象、物理、异步或引擎生命周期时，补真实运行路径，别继续扩大 mock |
| 角色、场景和物理是否真的在运行 | 现有 PlayMode／Functional Test 或可调用的运行时入口；观察相关对象、时钟和动作结果 | 编辑器通过但目标构建不同，就查目标构建；工具连接成功、进入 Play 都不足以证明玩法推进 |
| 长链交互能否走通，哪些状态不可达 | 已有状态快照＋玩家动作入口；需要时保存最小复现场景 | 文本／回合制通常适合；实时画面、设备绑定或呈现时序是问题时，补对应输入与画面，不另写一份游戏逻辑 |
| 改键、焦点、暂停菜单是否可用 | 经过实际输入系统与 UI 路由的测试；目标设备实际操作 | 调用按钮业务函数绕过绑定／焦点；引擎合成输入也不能证明 OS 与外设路径，设备问题须在目标设备复核 |
| 画面、动画、音频是否退化 | 固定场景的截图差异、动作录像／听验和目标设备帧时间；与已认可版本比较 | 静态差异适合找变化；拖影、遮挡、节奏、声音竞争要看连续过程，不能靠一张“漂亮截图”验收 |
| GUI 试玩没进展，是否继续自动改 | 核关键动作是否送达、玩家是否到达待验情境，再看反馈是否提供新信息 | 操作器漏控件先修测试器；后期细微交互或反馈重复时，保留旧版并追加独立试玩简报，不盲加轮数 |
| 自动分数与试玩感受冲突 | 分开可执行、规格符合、下一动作可理解与乐趣，先对齐评价问项 | 规格失败先修；可读性分数不测乐趣。问项已一致仍冲突时，再查裁判与目标玩家差异 |
| 动作是否有力、挑战是否公平、玩家是否想继续 | 让目标玩家完成具体情境，观察误解与操作，再比较候选 | 指标定位问题，人决定目标和取舍；自动通过、Agent 自评或短时玩通都不能证明长期乐趣 |

若改动只影响一个公式，无须为此建设整套试玩接口；若问题是第一分钟不好理解，也不应先把模拟对局跑到上千场。批量模拟适合已有可执行规则与明确统计目标；代理策略的胜率不直接代表真实玩家平衡。

**专用管线的“可交付”状态也要看降级项：** GCA 固定版本默认允许视觉供应商失败转警告；同 build／URL／运行回执能防陈旧证据，却不能证明未执行的视觉、压力或真人检查已通过。采用时核真实报告和覆盖，不撤掉上表仍适用的通用检查。

## 2. 工具到底观察了哪一段

**✅ 复用现有测试／调试入口；发现观测缺口才加一个窄接口。** 项目没有 MCP 不意味着不能测试，也不因此要求安装。下表只列会改变选择的差别；具体接入见 [Unity](unity/01-toolchain.md)／[Unreal](unreal/01-toolchain.md)。

| 已有入口 | 能得到的证据；选择边界 |
|---|---|
| Unity CLI／Pipeline | 当前 Pipeline 提供时，`status --format json` 的 `frameCount`、`playerLoopTicking` 可帮助确认 PlayerLoop 推进；字段缺失改用既有进度观测，否则标明未验证，不能判为停帧；还要读本次涉及的玩法状态，不能把帧数增长当作伤害／物理已执行。 |
| Unity Input System 1.19 | `InputTestFixture` 用隔离的输入系统与合成设备测试绑定、交互和输入处理；不依赖真实平台后端／硬件。适合可重复的输入回归，外设与 OS 问题仍需实机。 |
| Unreal 5.8 | 原生 Functional Testing 可测关卡，Automation Driver 模拟应用收到的键鼠输入，现成定位器面向 Slate；当前文档未提供手柄／触摸支持。别把它写成通用真实设备试玩，也不因有 MCP 就假定所需测试工具已暴露。 |
| Roblox Studio MCP | 官方提供 `playtest` 子 Agent、状态／日志／截图与键鼠模拟；`character_navigation` 是另一个移动入口。导航到位置并不能证明玩家按键、UI 焦点与操作提示正确；回读应选对 Studio 实例及 Client／Server 状态。 |

**局限：工具的官方能力契约不等于本项目已验证。** 缺少结果就报告具体缺口，例如“逻辑序列通过，手柄返回菜单未验证”，而不是把一种入口的成功升级成全部验收通过。

## 3. 一个真实案例：答对了，为什么还走不出去？

Jeff Schomay 的 Crossword Dungeon 开发记录展示了适合状态接口的情境：网页、文字为主、回合制。他为现有游戏加 Node.js 外层，以文本呈现状态并发送合成事件，再让 Agent 建立指定情境的 fixture。正文保留的是作者公布的运行记录，不是本仓库复现。

“笼子陷阱”的关键路径是：答错被困→移动被拒绝→答对显示解脱→关闭提示→再次尝试移动。Agent 观察到房间完成而移动仍被拒绝，定位到 `state.caged` 未清除；修正后记录了坐标变化。作者随后仍人工发现其他 bug 和手感问题。

**✅ 借用的是“验证退出后的下一步”，不是“单元测试发现不了状态 bug”。** 若规则能独立调用，这条状态序列也能写成确定性测试；依赖实际事件分发时则保留运行时回归。只断言“房间完成”会漏掉“恢复移动”，换成更多截图也未必弥补错误的验收条件。这个案例支持给已有游戏补合适的观察入口，不支持所有新项目第一天先建 HTTP、文本渲染器和时间控制层。

**本节来源与范围**：案例来自 Jeff Schomay 的 [Crossword Dungeon 开发记录](https://blog.jeffschomay.com/letting-ai-play-my-game)（一手：作者报告与公开运行记录）；案例复核与采用判断为本仓研究，沿用 2026-10-15（UTC+8）。

## 4. 如何验证第二次修改：给已有动作加入暂停菜单

**✅ 先决定暂停时蓄力、输入缓冲和恢复后的释放规则，再选择能观察这些规则的现有入口。** 假设原先“按住蓄力、松开释放”已可用，现在加入暂停与设置菜单；下面是按风险组合的例子，不是每项功能固定跑几个异常场景。

- **规则回归**：用原有测试走蓄力→暂停→松键→恢复，按设计检查是否取消／保留、费用与释放次数。不是让测试自行决定“恢复后应该攻击”。
- **真实运行**：确认暂停前后相关对象与计时的变化。Unity `timeScale=0` 停止 `FixedUpdate` 和 `WaitForSeconds` 的继续执行，但 `unscaledDeltaTime` 不受它缩放；UE 的 Tick 可设置 `bTickEvenWhenPaused`。因此菜单能动、帧数增长、世界冻结可以同时成立，要检查玩法自己的时钟。
- **输入与 UI**：通过项目实际输入路径走暂停→设置→弹窗→返回，检查焦点、按键提示以及恢复后角色是否误释放；涉及改键／设备切换就加入该路径。Unity UI Toolkit `Button` 的 `ClickEvent` 与手柄 `NavigationSubmitEvent` 不同，`Button.clicked` 覆盖两者，仅调用业务回调会漏过这个差别。
- **玩家体验**：让人实际操作这段切换，确认按键释放是否符合预期、菜单是否可理解、恢复是否突兀；日志用来定位被拒绝／延迟的动作，不能替人决定操作是否自然。

**何时补接口？** 只有当前无法回答关键问题时，例如看得见“没有攻击”，却分不清输入未到、状态拒绝还是动画延迟，才在已有入口增加对应状态或时间戳。复现场景保留版本、输入序列与预期结果；不要为了自动试玩复制规则实现或改造全部架构。

### 重复 Play 与新进程：先核实这次从什么状态开始

**✅ 第二次改动触及启动、静态订阅／缓存或编辑器热更新时，保留“刚编译后的首次进入”和“不改源码的退出→再进入”两个观察；需要判断首次启动时，再用新进程走同一动作。** 复用项目已有 PlayMode／Functional Test、日志与操作入口，不新建一层试玩服务。只改无共享状态的公式、已有测试已覆盖输入输出时，无须强制双 Play。

- **Unity 使用关闭 Domain Reload 的迭代设置时**：记录 Domain／Scene Reload 开关；第一次完成动作后退出，不修改脚本、不主动刷新，再进入并核对动作结果、回调次数与本局初始状态。脚本变化触发的刷新仍会重载域，所以“每改一次代码就 Play 一次”可能一直看不到残留订阅；另一方面，关闭 Scene Reload 的历史缺陷也曾表现为首次失败、第二次成功，不能只保留较好的那次；维护反例见本节末来源。
- **UE 只改 `.cpp` 也要看改了什么**：Live Coding 后已有对象不自动获得 `.cpp` 构造函数里的新默认值。若改动涉及初始化，回读旧实例及重新完整构建、启动后的实例，并区分蓝图／关卡保存的覆盖值；不要因为热会话仍显示旧值就反复补业务逻辑。涉及 Object Reinstancing 时，另查缓存引用是否失效重建、退出是否正常。

**关键局限：这些检查区分状态来源，不保证发布正确，也不表示每个改动都要打包。** Realm 的第二次启动挂起与 NGO 的首次进入漏回调都是已处理的历史维护案例；本节末来源给出具体版本、修订与未实测范围。

**本节来源与范围**：暂停时钟见 Unity [timeScale](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Time-timeScale.html)、[unscaledDeltaTime](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Time-unscaledDeltaTime.html) 与 UE [FTickFunction](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FTickFunction)，输入路由见 Unity [UI support](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.19/manual/UISupport.html)，均为官方文档（一手）；按风险选择动作链与“何时补接口”为本仓研究。重复进入部分含 Unity 6.3 [Domain Reloading](https://docs.unity3d.com/6000.3/Documentation/Manual/domain-reloading.html)／UE 5.8 [Live Coding](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-live-coding-to-recompile-unreal-engine-applications-at-runtime) 官方契约（一手）及 Realm／NGO 维护记录（一手／社区），具体版本、修订与未实测范围见 [WP10 重复进入补研](../../docs/research/2026-10-14-game-wp10-client-modules.md#重复进入补研不要让编译刷新替你重置验收状态)。引擎契约原核实 2026-10-15（UTC+8）。

## 5. 质量上限：可测的部分交给工具，体验取舍交给人

**✅ 把“手感不好”拆成能修改的假设，而不是写成“没有可计算标准”。** [04 客户端质量](04-client-modules.md)已结合 Celeste、Celeste 64 和 Deepnight 的公开实现，区分输入容错、运动、反馈与呈现。借用其机制时，应保持纯呈现对照与规则变化分开：视觉后坐力与实际位移不是同一改动，顿帧／缓冲也会改变操作时序。

| 具体问题 | Agent 可以推进什么 | 人保留什么决定 |
|---|---|---|
| 按了没反应／恢复后误操作 | 对照输入、动作接受、首次反馈的程序时刻；检查缓冲消费和状态退出 | 容错窗口、动作承诺是否适合玩法；程序日志不等于外设到显示器的完整延迟 |
| 攻击看不清／画面不顺 | 对比同场景运动录像、帧时间和命中反馈，找长帧、遮挡与信号冲突 | 哪个威胁应优先被看见，效果是有力还是干扰；用目标设备连续试玩判断 |
| 换素材后风格或清晰度退化 | 自动检查规格、引用、布局与基准截图，生成候选对照 | 选择认可的基准、判断风格与信息层次；不是把全部美术检查留给人 |
| 玩通却无聊／策略单一 | 汇总行为与失败位置，比较候选规则，按已定目标模拟 | 目标玩家、挑战、节奏与公平性的取舍；Agent 能帮助迭代，不能自证好玩 |

**✅ 反馈重复时，换一个明确的问题，不先换整套工具。** GUI 没玩过去先核输入与观察；已经玩通但改了几轮仍说不清改善在哪里，就保留当前可用版，请独立试玩者描述目标、卡住的位置和必须保住的体验。程序员把简报转成候选修改，再沿原路径对照。

**真人参与不等于自动获得正确答案。** 先统一情境和评价问项，再比较分歧；用目标玩家回答可理解性、挑战与继续玩的意愿。若新增简报没有可执行信息，或维护／试玩投入超过所解决问题的价值，就停止扩展反馈回路，保留有效回归与原型真人试玩。

**截图差异不是审美评分。** UE 截图比较支持容差，也可关闭 TAA、运动模糊等噪声来源；这有助于稳定回归，但若正在检查拖影／动态清晰度，就必须另外观察保留实际渲染特性的运动过程，不能用“关掉后通过”代替问题解决。

下一轮只改变明确的问题：先确认动作／画面是否改善，再看第二次需求修改会不会破坏它。人的判断与自动回归相互补充，不需要宣称 AI 不可能做出好游戏，也不把测试通过当作品质保证。

**本节来源与范围**：手感拆解与 04 的公开实现证据见 [WP10 体验质量补研](../../docs/research/wp10-motion.md#体验质量深化响应与顺滑让同一个动作值得反复玩)，机制判断为本仓研究，原核实 2026-10-14（UTC）；UE 截图比较来自 [Screenshot Comparison](https://dev.epicgames.com/documentation/en-us/unreal-engine/screenshot-comparison-tool-in-unreal-engine)（官方文档，一手），记录见 [WP10 验证选择深化](../../docs/research/2026-10-14-game-wp10-client-modules.md#验证选择深化状态输入与体验各自需要什么证据)，原核实 2026-10-15（UTC+8）。

## 当前最高水平：保住旧体验，不能只看改进总分

**✅ 默认沿用已有工程，补“真实动作路径＋必须保留条件”，不为评分换整套管线。** 试玩者／director 提供修改线索，独立评分裁判核对结果；反馈生成者不能凭自己的简报宣布放行。可以装入合法起始情境，但不能直接设成待验结果；动作须经过实际输入或明确的玩家级入口，并核可见游戏的同一状态。Thomas Ricouard 的 2026-09 实践把命名场景与着陆→步行→存档重载→起飞的真实行程分验；场景出现不等于行程走通。新增／替换动作和音效后，仍须在新版本重验旧关卡、引用与玩家反馈，不能让画面总分补偿旧关无法重开。

| 主要选择 | 领先替代与对照 | 本仓决定 |
|---|---|---|
| 继续 GUI 反馈还是追加真人 | Play2Code H 中，真人反馈在筛选出的中等增益任务后期获得更高 rubric 成绩；C.3 又有测试器漏控件反例 | 基础交互继续自动复现；细微交互／低增益先核观察，再补真人，而非把失败一律归因于游戏 |
| 原循环停滞如何推进 | RSIGame F.2 把独立 director 简报与同检查点继续开发比较；也有对照自行追平的游戏 | 冻结可用版本，给独立观察者明确情境；仅采纳能解释问题的简报，不强制每轮换人 |
| 自动评价能否代人 | Spec2Game 区分可执行、规格与呈现；对齐问项后人机一致性提高 | 先修评价覆盖；可读性与乐趣分别验收，避免为错问的问题换整套判定器 |
| 旧需求与修复是否保住 | GameXpert 累积需求、RSIGame 候选／保留版与下文 RAID 修复反例 | 保原工程、旧动作与硬性保留条件；探索和修复验收分账 |
| 输入、状态、存档、视听、性能与真机 | 上述生成／评分研究未覆盖完整设备和生命周期链；现有原生契约与连续观察回答不同问题 | 保留 §2–5 的通用检查；用 GUI 补观察，不替代确定性规则或目标设备验收 |

**完整游戏品质闭环的最高水平未知；近期领先候选支持按反馈缺口换手段，而不是无限自评。** Play2Code（Huang 等，2026-10 修订）、RSIGame（Wu 等，2026-09）与 Spec2Game（Cai 等，2026-10）分别提供真人反馈、外部观察与评价问项的对照。这是有证据支持的可行推荐，不是已证主流或最优：GUI Agent 适合找遗漏、留复现轨迹；没玩过去要区分游戏缺陷、操作能力与观察缺失。人继续判断可读性、节奏和手感；原有规则、输入、取消、存档、设备与性能检查仍适用。完整例子见本节末来源的 P32 两次需求继承设计；本仓尚未运行该游戏链，长期乐趣与目标设备效果仍须项目自身验证。

### 当前生产实践：探索没再找到，不等于修好了

**✅ 保留现有回归，把 Agent 的探索发现转成可复验的旧策略／动作。** 先核输入是否送达、状态是否匹配，由人确认是游戏缺陷、测试器失败还是设计允许；修后专门重现原条件，再继续探索。不能用下一轮“零发现”替代修复验收。

**工业领先候选也保留这道人工判断。** EA 的 RAID（Fuchs 等，2026-07）在 NHL26 旧开发版用强化学习找不同进球策略；作者明确说重新搜索未发现旧漏洞、旧策略模型因动态变化失灵，都不足以证明修复。它不是 LLM coding Agent。较早的 TITAN（NetEase Fuxi 等，2025-09，GPT-4o）提供商业 MMORPG 的 LLM 测试参照，但报告仍须人工分诊；独立制作 Deckhand（2026-08，Godot＋Claude Code）则把误点造成的假阻塞修成测试器校验。条件与原文见本节末来源。

**完整生产闭环的最高水平仍未知，当前推荐属于可行层。** 主流参照仍是既有引擎测试、脚本回归与真人试玩，不据个案估采用率。Agent 可整理轨迹、写回归与寻找遗漏，人保留根因核验和体验取舍；重训、误报与接口维护的总成本超过收益时，撤回自动探索而保留有效回归。上文的视听、输入、存档与目标设备检查不变。
