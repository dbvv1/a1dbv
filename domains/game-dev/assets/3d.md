# 3D：从场景意图到可修改的完整片段

> 整页比较：2026-10-22；最近核实：2026-10-26（UTC，室内作者源与 MOBA 成套资源采用）。适用单人程序员、不做人工美术修补；引擎结论 Unity 优先、Unreal 对照。文中分档是具体任务的条件化首试顺序，不是同题实测冠军；各节在节末标来源性质与验证范围，有补核的另注日期、时区；固定来源、反证、许可和验证边界见 [WP3 研究记录](../../../docs/research/2026-10-14-game-wp3-3d-assets.md)。

## 30 秒结论

| 眼前需求 | 首选 | 何时换路线 |
|---|---|---|
| 只有一个场景想法，不知从哪开始 | ✅ 先定玩法、相机和通行，再用一套同风格包做一个 60–80 米片段：入口→地标、一次交互、一次视线转折（[完整流程](#完整片段先做一个能走能看能改的场景)） | 缺关键轮廓才补生成件；整景生成先验对象级编辑与消费者 |
| 同风格静态道具／模块场景 | ✅ 同包资产与已有参数配方；先按真实镜头比较用途与轮廓，再接消费者（[MOBA 已采用起点](#moba-battle-supply)） | 缺件才生成可替换件；尺寸／拓扑也变时回布局配方，不整栋盲重生 |
| 有资产，却组不成有品质的完整场景 | ✅ 从一个可玩片段开始：真实视角定参照，地形／建筑定大形，按焦点与留白编排近中远层，再统一材质／光照 | 编排后仍缺关键轮廓才补件；整景生成先验对象级编辑与消费者，不能用概念图代替运行画面 |
| 已有精灵的 3D 源，想改实时表现 | 先按新视点／光照／运动重验源；比较保留重烘与补合格实时源 | 转换仍需手修几何／材质或补运动部件，换源或收窄表现，不以已有工程当就绪 |
| 同作品树／灌木／草，二改要近景或定向风 | ✅ 先选同风格且风动数据匹配目标引擎的资源族 | 缺枝条结构先核源端提取／生长路径；恢复不合格、通道未知或须手刷权重，换源或收窄表现 |
| 缺可用几何的自定义低模刚体 | 🧪 新需求先试 Meshy T2.5 灰模；已合格 T2 配方不迁移 | 关键孔洞、细件或挂点反复丢失，退回现成／参数化 |
| 已认可几何，只差预算／导出或面组织 | ✅ 超预算保源简化，仅导出用成熟工具；面组织妨碍编辑才 🧪 形状条件重拓扑 | 重要孔洞、轮廓或接口超出误差线就撤回；重拓扑另验 UV 与引用，不退回图片重生 |
| 认可形体，要换参考外观 | ✅ 改色／磨损保源调材质；新纹样才 🧪 同网格重贴图，先查图与表面对应 | 结构／相机不匹配先重选源／视点；精确文字或背面连续性反复失败，换合格纹理源，不整物盲重生 |
| 变形角色／换装 | ✅ 固定版本、身体覆盖与动作配套的受限衣橱 | 必须刷权重或修面才合格，换角色或收窄玩法 |

**直接开工：** 要搭第一个可玩片段，从[完整片段](#完整片段先做一个能走能看能改的场景)的相机、尺度与通行开始；只改已有场景，直接看[第二改](#第二改傍晚打开视线保留使用空间)；先选资源或处理工具，再看后面对应分节。

以上为条件化选型，不是本轮模型／引擎实测排名。TaoFlowForge 权重仓已声明 Apache-2.0，但必需 DINOv3 的实际来源／版本及适用许可链仍待核，暂不列无条件商用默认；不等于判定它只能非商业研究。

## 完整片段：先做一个能走、能看、能改的场景

**✅ 默认路线：一套同风格、许可清楚的模块／自然包，加项目自己的布局数据和装配脚本；AI 先产出可审的布局与清单，不先产出一张概念图。**

目标不是一次做完整关卡，而是做出一个 60–80 米、单程约 15–30 秒、加上观察和交互约 40–60 秒的片段：它能导入引擎、能在真实相机下观看、能在第二次需求里局部修改。下面的尺寸与数值是工程起点，按玩法、角色速度、目标设备和镜头重新标定；它们不是引擎规格、通用关卡尺寸或审美标准。

本页用下面这个原创小型探索片段贯穿。它不依赖新仓库或完整游戏，也不限定赛车题材。

```mermaid
flowchart LR
  I[玩法 相机 通行] --> M[主辅形体 近中远层]
  M --> S[同包模块 程序布局]
  S --> G[缺件才生成]
  G --> R[运行接入 碰撞 交互 镜头]
  R --> V[三视点 连续移动 验收]
  V --> C[第二改 局部移动 不重生]
```

| 片段要素 | 本例默认 | 为什么先定 |
|---|---|---|
| 入口 | 门、坡道或框景，出生点能读懂路径方向，但先不完整看到地标 | 入口决定第一眼构图与玩家预期 |
| 主要地标 | 1 个，轮廓独特，50–80 米外可识别，体量高于其他建筑／树冠 | 地标是导航锚点，也是第二次“打开视线”的对象 |
| 可交互物件 | 1 个门／钟／开关；使用半径 1.2–1.5 米、接近路径 1.5–2 米 | 交互需要独立对象、运动结构、碰撞和事件绑定 |
| 视线转折 | 1 处路径弯、岩石、树丛或低墙；遮挡地标后在行走中重新露出 | 转折决定“先藏后见”的节奏，第二次改常移动它而不是删掉 |
| 层次 | 近 0–8 米、中 8–30 米、远 30–100 米以上 | 近景框边、中景活动、远景定位三类职责不同 |
| 预算 | 以目标设备基线为准，记录 draw calls、三角面、贴图内存与帧耗时 | 没有设备与基线时，不先编一个绝对值当通过线 |

### 1. 先定相机、尺度与通行

**相机和角色控制器决定资产尺寸，不能先做一批 1:1 建筑再发现门进不去。** 先量角色胶囊、相机臂、视野和通行净宽，再把入口、路径、门洞、台阶和地标体量按这些约束摆放。下表是第三人称步行探索的起点，不是跨类型规格；驾驶、飞行、VR 或固定镜头要重新标定。

| 参数 | 起点 | 条件与调整 |
|---|---|---|
| 角色眼高 | 1.6–1.8 米 | 角色比例改变时重核镜头与门洞 |
| 行走速度 | 3.0–4.5 米／秒 | 冲刺、载具或重手感另测 |
| 第三人称相机臂 | 2.5–3.5 米，离地 1.5–2.0 米 | 室内、狭窄处缩短；先验相机碰撞 |
| 视野 FOV | 本例起步用垂直 FOV 55–65°，并非通用最佳值；按目标画面调整 | 固定机位增大 FOV，近远物体的屏占比都会减小；若为构图移动相机，重新检查近远比例 |
| 入口到地标 | 50–80 米 | 超过 100 米时另设中景引导，否则地标太小 |
| 地标在入口的仰角 | 5–15° | 太高会被近景遮挡，太低会与地平线混在一起 |
| 地标占屏宽 | 约 8–15% | 以实际相机与分辨率截图核对，不只看模型尺寸 |
| 主路径净宽 | 2.5–4 米 | 单人步行；战斗、载具、NPC 同行另加 |
| 交互使用空间 | 半径 1.2–1.5 米、高 2.0 米；接近路径 1.5–2 米 | 角色体型、交互动作和镜头一起定 |
| 视线转折 | 前进方向改变约 30–60°，转折后 5–15 米露出地标 | 转折太早没有“先藏后见”，太晚玩家已迷路 |
| 可行走坡度／台阶 | 坡度约 ≤15°，台阶约 ≤0.3 米 | 以角色控制器实测为准，不照搬本文 |
| 相机碰撞缓冲 | 0.3–0.5 米 | 贴墙、树丛和门框处单独验 |

先用灰盒或基本体走一遍：出生点看得懂方向、路径能通过、转折后地标出现、交互物有地方站。灰盒通过后再替换资产，能避免“模型很精细但门宽不够”的返工。

**同风格包先核比例、枢轴和材质消费者。** Kenney 的模块建筑、城郊和自然包各页列 CC0，适合作为免费起点；它们不承诺任意组合即同风格，也不保证目标设备预算。先导入一个门、一段墙、一棵树，核单位、朝向、底座枢轴、碰撞与材质，再批量摆放。

**本节来源与范围：** [工程建议／经验] 60–80 米片段、相机／尺度与灰盒顺序均为第三人称步行探索的工程起点，未实测；[一手／工程建议] Kenney 模块建筑、城郊和自然包各页列 CC0，样本核对要求与场景供给比较见 [WP3 §4.2](../../../docs/research/2026-10-14-game-wp3-3d-assets.md#42-完整场景从制作参照到可编辑路段)。

### 2. 主辅形体与近中远层

**先保证一个主形体和一条可读路径，再谈装饰密度。** 主形体是地标；辅形体是入口、建筑组、树组和视线阻挡；填充物只补质感，不抢轮廓。每一件都要说明它承担“框边、引导、遮挡还是衬托”，说不出职责的先不放。

| 角色 | 数量与位置 | 形体规则 | 常见错误 |
|---|---|---|---|
| 地形与路径 | 1 条主路径＋可行走坡面 | 高差服务视线与转折；坡度、台阶、净宽先定；边界用山体、挡墙或植被收口 | 先堆资产再改地形，门洞、台阶、转角全部返工 |
| 主形体／地标 | 1 个，远层 | 独特轮廓、明确竖向、与天空／远景有明度差 | 被中景树冠或建筑切掉顶部；与辅形体同样高度 |
| 辅形体 | 2–3 组，中景为主 | 低于地标；重复模块形成节奏；一组框入口、一组压路径一侧 | 等距排开，像样板街；每组都用独特件，维护成本失控 |
| 视线阻挡 | 1 处，中层 | 可移动、可降低、可换成低矮件；不承担关键碰撞或存档 | 做成不可改的主墙体，第二次开视线只能重生整景 |
| 近景框边 | 0–8 米，画面边缘 | 岩石、草丛、枝条或门框；不挡交互物与路径 | 为了“丰富”把近景塞满，挡住脚下与交互提示 |
| 中景活动 | 8–30 米 | 路径、交互物、建筑组、转折 | 交互物放在主地标正前方，开视线时被一起删掉 |
| 远景定位 | 30–100 米以上 | 地标、山脊、树线、天空；用雾和明度分层 | 远景与中景同样清晰，空间压缩成一张贴图 |

编排时先定一条从入口到地标的行走线，再在线的两侧放辅形体和框边。入口用近景框住一部分画面，但保留地标的一个竖向线索；转折用中景遮挡，转折后让地标占住画面一侧而不是正中。留白是构图的一部分，不要求每个空位都填满。

近期作品值得借的是组织方法，不是复刻制作规模。Wanderstop 把植被的色彩感与建筑的轮廓语言分开设计；Ghost of Yōtei 用远景地标和近处压力共同塑造体验；Snow Riders 发现前作的急转／落差不能直接沿用到新的运动方式。它们分别支持“风格职责分开”“参照转成空间关系”“地形服从移动方式”；这些作品由专业团队制作，不能把其产能当成单人默认。

### 3. 选择供给路线：同包＋程序布局、补缺件、显式整景

**默认从同包＋程序布局开始；只有这条路线确实缺一件关键轮廓，才补生成件；显式整景当前只用于有限视点背景。** 三条路线回答不同问题，不是同一张排行榜。

| 路线 | 能给什么 | 采用条件 | 不采用／撤回 |
|---|---|---|---|
| **✅ 同包模块＋程序布局** | 可本地编辑的墙、门、屋顶、地面、树、石；脚本按路径和规则摆放，保留对象 ID 与变换 | 许可清楚、已有包覆盖风格与尺寸；先导入样本核比例／枢轴／材质／风动消费者 | 包内缺关键轮廓或组合接缝反复失败；不要用更多包硬凑同一风格 |
| **🧪 同包＋生成补缺件** | 为地标、交互物或独特近景补一件／一组；先灰模再贴图 | 只补真正缺的件；先导入一个样本，核尺寸、枢轴、材质、碰撞和 LOD；保存请求、任务 ID、版本与许可 | 整批生成后再统一修；单张参考图不交付地形、碰撞、隐藏面或可改布局 |
| **👀 显式整景生成** | 室外分层生成、室内分阶段放置、有限视点背景 | 只作远景、固定背景或概念参照；先核实际可运行交付物、对象编辑与许可 | 入口→地标主路径、门要开、物体要拾取、第二次要改布局时，仍用模块 mesh |

**缺件只补本片段必需的轮廓，不先补满资产表。** 探索片段先有地面、地标、辅助建筑、一个可交互件和能框景的自然物；战斗片段则先有塔、兵、英雄和通路。若组合后仍须反复手修才能成立，换合格包或缩需求。显式整景仍沿 WP3 2026-10-23 的固定判断：WorldClaw 当时只有说明与展示，SceneSmith 偏室内仿真且需模型／服务投入，Marble 的导出档与商用口径有张力，尚不能替代可开门、可拾取、可局部改布局的模块主场景。

**✅ 小道具借作地形／远景，先在行进镜头核比例、距离与落脚。** 放大可能把底部倒角变成显眼黑檐；只按中心等半径摆放，也可能使岩体贴近长条赛道的一侧。Star-Rush 从 Kenney Nature Kit 的两件 CC0 岩体起步：`assets/landscape/convert.py` 固定源件并统一尺寸，`scenery.js::coastalBackdrop` 按该赛道长短轴分布近岬角与远岛、合入原景观网格；逐面检查朝下面是否露在水面之上、底部是否越出现有有限海面，再沿正式自动试驾复看。高处内凹不合题材就换形状，不靠灯光偏移遮掩；真正的洞穴、悬挑或可交互地形应保留实际空间与玩法合同。

#### 已采用起点：把同风格资源接成一次 MOBA 战斗

**✅ 低多边形塔战先比较实际成套模型，再用已有兼容骨架补人物；不要为了“全 AI 生成”混拼风格。** MOBA 同灯查看了 KayKit Medieval Hexagon 免费版和 Kenney Fantasy Town 2.0 的实际模型：前者已有炮塔、堡垒兵营、城堡及共同石木比例，能直接承担战斗语义；后者的模块墙屋更适合自由拼村镇，但本片段还需另造军事形体，因此采用 KayKit 建筑，不混入第二套墙屋。这个选择针对本次俯视塔战，不是两包的普遍品质排名。

**先保运行合同，再改远景大轮廓。** 人物保留本仓原创十五骨骼与 `idle/walk/attack/hurt/death` 五个动作名，重新制作骑士可见网格；复评后把近战兵改成大圆盾／枪，远程兵改成尖风帽／窄肩／横弩，并分别做刺击、短后坐。阵营再加单／双冠脊、矩形／三角旗，颜色不是唯一线索。骨架兼容不等于换装免验：源→GLB 核动作变形与脚底，实际交战镜头再看遮挡和出手；需要共享多单位时接[动画消费者](animation.md#multiunit-animation-consumer)，不把这次同源复用当成任意角色重定向。

**给源和消费者划清可改范围，二改才不会退回整包重做。**

| 所有者 | 实际起点 | 固定接口／负责的修改 |
|---|---|---|
| 资源制作 | 产品 `asset-pipeline/battle/` 的 `tools/build.py`、可编辑 `.blend`、`manifest.json` | 模型／材质／动作与导出；固定 ID、自包含 GLB、米制 Y-up／+Z 朝前、地面锚点及名义高度；保留源 SHA 与许可 |

| 玩法与导航 | 既有模拟与烘焙数据 | 视觉改路边、旗帜或武器时不随模型重烘碰撞、不改攻击资格；需要改玩法再单独验证 |

**发现地表接缝，先在真实 renderer 查重复表面与颜色空间，不先加装饰遮丑。** Blender 预览通过后，Three.js 真帧仍出现浅绿矩形、每 12 米暗缝和闪烁：源草面与消费者外场都在 `y=-0.035`，且源的线性草色不等于外场 `#284c43` 的颜色解释。修法是让消费者独占连续草地，源只留下石路；去掉重复草台和侧面，每段两端各外延 3 cm（相邻段交叠 6 cm）、边缘小幅打破直线。相同运行镜头复拍确认矩形与暗缝消失，另外 **14 个 GLB 字节不变**。这比重新生成整景更能保住已接受的角色、建筑和接口；重叠值只用于本例同材质平面路段，透明面或不同材质交叠须另验。

**复用时从固定产品源和真实消费者一起开始。** 先查看 [b4dff100 的资源入口与生成／检查命令](https://github.com/dbvv1/MOBA-Like/blob/b4dff1007527a2f8bfae81ca4749e90321f7bd7f/asset-pipeline/battle/README.md)，再对照[同提交运行消费者](https://github.com/dbvv1/MOBA-Like/blob/b4dff1007527a2f8bfae81ca4749e90321f7bd7f/src/render/battlefield.ts)与[公开可玩站](https://dbvv1-moba-like.pretty-llama-9945.chatgpt.site)。15 个运行 GLB 约 2.46 MB；原始包与原创资源均按各自 CC0 许可，固定来源、哈希和动作抽样验证集中保存在产品 `source/provenance.json`、许可文件与 `tests/validation.json`，不另抄一份素材台账。

**何时不照搬：** 军事轮廓不合题材、现有骨架不兼容或预算不符时，回到样本比较，不强套这套包。此发布树已有严格软件 WebGL 检查与约 80.6 秒正常输入交战实跑，但此前候选曾页面崩溃，旧版对照出现 GPU 进程 exit 9，不能推出全设备稳定；硬件性能另验。整体基本战斗仍在向 LoL 的响应与可读性优化，Thronefall 只辅助低多边形视觉层级，资源采用不等于品质完成。

### 4. 材质族、灯光与气氛

**先统一少量材质族，再让关键动作和地标突出。** 一个片段先控制在 3–4 个材质族：地面／地形、结构（石／木／灰泥）、植被、强调（金属、发光或交互提示）。每族共享一套颜色与粗糙度范围，用实例色或顶点色做变化；不要给每个道具单独做材质和 shader 变体。纹理密度按目标相机与设备定，近景主角件高于中景，不用一套 4K 贴图铺满全场。

| 层 | 默认 | 检查 |
|---|---|---|
| 颜色 | 5–7 个主色，1 个强调色；地标与交互物用强调色或明度差 | 黑白截图下仍能分出主次 |
| 材质族 | 3–4 族；共享 roughness／metallic 范围 | 新旧件混排时不出现明显色温或光泽断层 |
| 纹理 | 中景够用即可；近景主角件单独提高 | 不用贴图补几何缺失；烘焙阴影不当作可重新打光 |
| 灯光 | 1 个主方向光＋天空／环境光＋1 个补光；固定曝光 | 暗部、逆光、雾和低画质下路径仍可读 |
| 阴影／雾 | 阴影距离覆盖片段主区域；远景用雾和明度分层 | 阴影预算与雾距不吞掉地标轮廓 |
| 预设 | 第一版用白天预设；傍晚作为第二次改的参数预设 | 预设切换不改变对象 ID、碰撞和交互事件 |

白天的起点可用 30–50° 太阳高度、中性偏暖主光、较冷环境光；傍晚的起点用 5–15° 低角度暖光、降低主光强度、略冷的天空补光和更明显的远景雾。具体色温、强度和雾密度以目标相机与设备实测为准；这些数值是调参起点，不是画面品质证明。

**本节来源与范围：** [研究／经验] 材质族划分与画面语言，见 [materials.md 先统一画面语言](materials.md#先统一画面语言再让关键动作突出)；[工程建议／经验] 白天／傍晚数值是调参起点，不是画面品质证明。

### 5. 给 AI 的输入与产出：布局、清单、装配、检查

**AI 先产出可审的布局与清单，再产出资产。** 输入不能只有“日系小镇”一句话，而应包含玩法、相机、路径、尺寸、已有资产、风格参照、预算和禁区。AI 的第一版输出是布局骨架、视点、遮挡／净空检查和缺口清单；人确认构图与交互后，才补资产或生成缺件。

一个够用的作者目录可以很小。下面是项目约定示例，不是引擎内置格式；字段可以删减，也不要把示例当成 API。原包与生成件分别保存，项目文件只记录引用、覆盖和检查，不把第三方源混入项目自有目录。

```text
scene/
  intent.md          # 人写：玩法、相机、路径、风格参照、已有资产、预算、禁区
  layout.json        # AI 产出／人审：对象 ID、来源、变换、层次、材质族、交互 ID
  manifest.json      # 资产来源：包／版本／许可／导入设置／目标引用
  checks.md          # 验收：视点、视线、通行、使用空间、预算、未改项
assets/
  packs/<pack>@<version>/   # 原样保留的授权源，不就地改
  generated/<job-id>/       # 生成请求、任务 ID、版本、产物与许可记录
engine/
  scene/                    # 引擎自己的场景／预制体装配，不替代作者源
```

`intent.md` 至少写清：玩家从哪进入、第一眼应看到什么、路径在哪里转折、交互物是什么、允许玩家做什么、参考图借的是轮廓／配色／密度中的哪一项、已有包及版本、目标设备与帧率、不能改的碰撞／事件／存档键。

**AI 的产出顺序：**

1. 盘点已有包与许可、版本、导入设置；不先调用生成服务。
2. 按 `intent.md` 生成布局骨架、三个视点、视线／净空检查和未决问题；输出差异而不是整份重写。
3. 列缺口清单：哪一件是为了轮廓、哪一件是为了交互、哪一件只是装饰；只为前两类补件。
4. 生成缺件时先灰模，导入一个样本，核尺寸、枢轴、材质、碰撞与 LOD；通过后才批量。
5. 生成装配／导入脚本与稳定 ID 映射，跑检查并留下前后对照。
6. 人确认构图、地标身份、交互语义和画面感后，才进入运行时验收。

**人负责的仍是画面与业务判断：** 地标是否有辨识度、入口是否引导、转折是否成立、交互物是否该在那里、傍晚是否可读、是否接受当前品质。AI 负责把意图变成约束、算遮挡与净空、写装配与检查脚本、应用局部变换和整理差异。

### 6. 运行接入：把对象 ID 串到碰撞、交互与镜头

**作者源、引擎对象和玩法绑定分开保存。** 作者源保留原包、生成记录和布局；引擎场景只引用稳定对象 ID，不依赖 mesh 名称或节点顺序。这样第二次改布局或换外观时，碰撞、交互事件和存档键不会被一起重建。

| 作者层 | 运行时对象 | 必须保持 | 检查 |
|---|---|---|---|
| `objects[].id` | 场景对象／预制体实例 | 稳定 ID；改名不改变引用 | 重载、重启、存档后仍能找回 |
| `source` | 导入网格／材质 | 单位、轴向、底座枢轴、材质槽 | 新旧件混排不漂移、不穿地 |
| `collision` | 独立碰撞代理 | 与可见网格分离；门洞、台阶、路径可通行 | 角色、相机、投射物分别验 |
| `interaction` | 事件／状态机／存档键 | 事件名、使用空间、动画与碰撞契约 | 触发、取消、重载、失败路径 |
| `viewpoints` | 相机变换与 FOV | 视点 ID、镜头参数 | 同视点可重拍前后对照 |
| `materialFamily` | 共享材质／实例参数 | 材质族、实例色、透明与剔除 | 不因单个物件新增 shader 变体 |
| `lighting.preset` | 场景灯光／天空／雾 | 预设名与参数；切换不改对象 | 白天／傍晚切换后路径仍可读 |

Unity 可用嵌套预制体保留子件源链接与局部 override；碰撞先用 box、sphere、capsule 或少量 compound，凹结构再评估凸分解。UE 可用 Level Instancing 组织可重复集合，静态密集外观用 Packed Level Blueprint，动态门和交互物件保留独立 Actor。

具体组件名、事件系统和存档接口由项目自己定；本文不把示例字段写成引擎 API（[嵌套预制体](https://docs.unity3d.com/6000.3/Documentation/Manual/NestedPrefabs.html)、[Level Instancing](https://dev.epicgames.com/documentation/en-us/unreal-engine/level-instancing-in-unreal-engine)）。

**本节来源与范围：** [研究／工程建议] 作者源、引擎对象与玩法绑定分离，见 [WP3 §16](../../../docs/research/2026-10-14-game-wp3-3d-assets.md#16-p37前置二改判据名称与共享数据)；[一手／研究] Unity 嵌套预制体与 UE Level Instancing 的引擎能力，链接见正文。

### 7. 第一片段验收：三个视点、连续移动、一次交互

**验收按真实相机和真实移动做，不按模型预览或参数表放行。** 至少保留入口、转折、地标三个可重拍视点；每个视点记录位置、朝向、FOV、画质和 UI 状态。再连续走一遍，确认路径、镜头、交互和地标露出都不是只在单帧成立。

| 检查 | 通过条件 | 失败时先改什么 |
|---|---|---|
| 入口构图 | 路径方向可读；地标露出一个竖向线索或部分轮廓；近景框边不挡路 | 先移近景框边与相机，不先换地标 |
| 行走 | 主路径净宽、坡度、台阶可通过；相机不穿墙、不卡树 | 先调控制器与摆位；资产尺寸错误才换件 |
| 视线转折 | 转折前地标被遮挡，转折后 5–15 米内重新可见 | 移动或降低遮挡件，不删整段植被 |
| 交互 | 使用空间与接近路径空闲；触发、取消、重载都成立；镜头不穿模 | 先移交互物或障碍，不改事件契约掩盖碰撞问题 |
| 未改区域 | 只改了目标对象与环境预设；其他 ID、变换、碰撞、事件不变 | 回退到上一版布局，不用整景重生兜底 |
| 预算 | 记录 draw calls、三角面、贴图内存、帧耗时；与基线比较 | 先稀疏化、复用实例、缩阴影范围；不先加新渲染框架 |
| 重启／加载 | 场景、材质、碰撞、交互和存档键在重载后仍对应 | 先修引用与 ID；不用重新生成资产掩盖绑定错误 |

**数值通过不等于画面成立。** 轮廓、主次、材质断层、暗部可读性和交互可发现性仍要人看真实画面；没有真实运行画面时，本页只保留流程与待验项，不声称视觉或性能通过。

**本节来源与范围：** [研究／待执行方案] 入口／转折／地标三视点与连续移动验收，Star-Rush 最小路段仍待验，见 [WP3 Star-Rush 最小路段](../../../docs/research/2026-10-14-game-wp3-3d-assets.md#star-rush最小路段方案与待验条件)；[研究／经验] 数值通过不等于画面成立。完整场景补核 2026-10-23。

**交付时留下能支撑第二次修改的源、身份和对照。** 至少保存以下四类内容：

- 原包与固定版本、下载哈希、许可与实际取得档；生成件另存请求、任务 ID、模型／纹理版本和采用文件。

## 第二改：傍晚、打开视线、保留使用空间

**先冻结不变量，再改气氛，再移动遮挡实例，最后验交互与未改区域；不要从重生整景开始。** 第二次需求是“改成傍晚，打开入口到地标的视线，并保留可交互物件的使用空间”，它同时改气氛、遮挡和交互可用性，不是单独恢复或取消一条边界。

```mermaid
flowchart LR
  R[傍晚 打开视线 保留使用空间] --> F[冻结地标ID 交互事件 使用空间 通行与预算]
  F --> L[改灯光 雾 曝光 局部强调]
  L --> V[从入口视点找遮挡实例]
  V --> M[移动或降低遮挡实例 不重生整景]
  M --> C[检查地标轮廓 路径通行 未改区域]
  C --> U[检查交互使用空间与接近路径]
  U --> P[同视点前后对照 性能与重启]
  P -->|不达标| V
```

### 1. 先冻结不变量

动手前把这五项写成检查：地标对象 ID 与来源、交互事件与存档键、交互使用空间、主路径与碰撞、目标设备预算。它们不随气氛或遮挡修改而变化；任何一项要变，就升级为一次明确的场景重做，而不是藏在“打开视线”里。

### 2. 先改气氛，不改结构

- 太阳降到约 5–15° 的低角度暖光，降低主光强度；天空补光略冷，保留暗部可读性。
- 远景雾略增，拉开层次；不要把地标一起吞掉，轮廓仍需可辨。
- 固定曝光后检查路径、交互物和地标；暗到看不清路时先补 1–2 个局部强调光或发光材质，不加满场景点光。
- 保留白天预设作为对照；傍晚是参数预设，不是换一套材质或重生场景。

气氛改动可逆、成本低，先做能把“傍晚是否成立”单独暴露出来；如果这一步就不成立，后面的遮挡修改没有意义。

### 3. 再开视线：移动实例，不重生场景

从入口视点的眼高向地标包围盒的中心、左缘、右缘各打一条射线或细圆柱，列出挡住的实例。按职责处理：

- **装饰性遮挡**（树、灌木、岩石、矮墙）：优先移动、降低、缩小或减少实例；保留转折处的一部分，让“先藏后见”仍成立。
- **辅形体**（建筑组、门楼）：先移出视线轴或降低体量；不要为了开视线拆掉承载碰撞和入口功能的主结构。
- **地标自身或玩法必需物**：不改；回到构图，调整入口位置、路径弯或地标高度。
- **整片植被**：按簇减少，不按均匀比例剃平；保留近景框边和中景深度线索。

开视线不是把入口到地标之间全部清空。保留一个低矮前景或侧向框边，能维持尺度感；如果地标在入口完全无遮挡，转折就不再是转折。目标可以是“入口看到地标顶部或部分轮廓，转折后看到完整主形”，不必第一眼全见。

### 4. 保留交互使用空间

交互物件的使用空间按冻结值检查：半径 1.2–1.5 米、高 2.0 米，接近路径 1.5–2 米。开视线时如果遮挡件正好在这块空间里，移遮挡件或交互物，不要缩小使用空间来迁就构图；缩小会让角色贴墙、镜头穿模或触发失败。傍晚可读性不足时，用交互物自身的小范围发光、局部补光或材质强调，不默认加一个漂浮 UI 标记。

### 5. 同视点复核与停止线

| 检查 | 方法 | 通过／停止 |
|---|---|---|
| 入口视线 | 入口眼高到地标中心／左右缘；允许前景框边，不允许整块遮挡 | 地标轮廓不可辨或只剩一条缝，继续移遮挡件；仍不行则改入口／路径 |
| 转折仍成立 | 转折前部分遮挡，转折后完整主形出现 | 转折被完全清空，补回低矮框边或侧向体块 |
| 地标身份 | 同一 ID、来源、比例、主材质；轮廓不变 | 需要换地标或改比例时，停止本次局部二改，另立场景重做 |
| 交互使用 | 使用空间、接近路径、触发、取消、重载 | 任一失败，先移物件／障碍；仍失败则回退布局 |
| 未改区域 | 对象 ID、变换、碰撞、事件差异清单 | 出现非目标变换，回退到已接受版本 |
| 预算 | 前后 draw calls、三角面、灯光数、帧耗时 | 灯光或植被改动超出预算，先缩范围／减实例 |
| 真实画面 | 白天／傍晚同视点对照＋连续移动 | 没有真实运行画面时，只记待验，不声称通过 |

### 6. 这次二改的取舍

| 改动 | 收益 | 代价／风险 | 处理 |
|---|---|---|---|
| 打开视线 | 入口更清楚地标，导航更强 | 失去围合感，场景显得更小、更空 | 保留低矮前景、侧向辅形体和转折后的完整露出 |
| 改成傍晚 | 气氛与地标轮廓更强 | 对比下降，路径、交互物和暗部更难读 | 低角度暖光＋冷天空补光＋少量局部强调；固定曝光后实测 |
| 减少植被／体块 | 视线更干净 | 深度线索和风动细节减少 | 按簇稀疏，保留近景框边与中景层次 |
| 加局部灯／发光 | 交互物和地标更可发现 | 灯光与 draw call 上升 | 限制 1–2 个，优先发光材质，不铺点光 |
| 保留使用空间 | 交互仍可用、镜头不穿模 | 约束遮挡件摆位 | 移遮挡件或交互物，不缩使用空间 |
| 不重生整景 | 保住 ID、碰撞、事件和存档 | 局部最优可能达不到理想构图 | 接受局部妥协；要到理想构图时另立一次明确重做 |

**人判断的是傍晚是否好看、地标是否仍有身份、转折是否仍然是转折、交互是否仍可发现；AI 负责算射线与净空、列遮挡实例、应用确定性的移动／缩放和输出差异。** 任何“更通透”“更有氛围”的说法都要落在同视点真实画面上，不能由参数正确推出。

## 先采用什么

**✅ 同风格现成资产满足需求时不重新生成；重复尺寸、模块接缝和可动零件优先复用已覆盖需求的参数化配方。** 先按玩法分成静态刚体、模块场景和变形角色，再确定尺寸、占屏大小、材质与设备预算。箱盖能打开、门宽能修改、角色能换衣，比第一张旋转预览精细更能决定后续生产成本。

**先分“改参数”与“补配方”。** 已支持的尺寸、布局与风格可反复复用；新增屋顶轮廓、墙体风格或连接类型，先查是否已有合格源模块及对应规则。Tiny Glade 增加木墙时还需处理开窗、窗框与石基组合，并补木楼梯；开源模块组装器也可能只生成旋转与邻接表，不生成缺失网格。需要手工建模才能补齐时，换完整授权资源体系或收窄需求，别把它记成零手修调参。

**旧生产母版不自动具备新用途资格。** 从固定视角精灵改为实时 3D，先核源在实际新视点、动态光照、运动部件及不同展示窗口是否仍合格，再估批量转换收益。Naev 的实际迁移获得星光、倾斜和多窗口复用，也修材质／坏几何，部分船近乎重做；现成脚本不包办这些工作。只需旧视角下换规格时保留重烘对照；新表现确有价值但源必须手修时，换已合格实时源或缩小范围，不无限补转换器。

图生 3D 适合将已接受的参考变成候选形状；文生 3D 适合探索，部分商业文本路径内部也先生成图像。正式资产尽量先锁参考图或一致多视图，明确不可见面的要求；单图、固定 seed 都不能保证背面、零件结构和成套风格。

## 角色换装：先开放已配套组合

**✅ 先选完整着装身体与配套头部，再开放已经验过的槽位。** Quaternius 服装 v2.0 补入人体部件，官方只承诺配基型头；它不是把任意衣服套到六种裸身体上的拟合器。第二次换装先核实际取得的免费／付费部件、身体覆盖、动作版本与绑定关系，不能只查骨名。

**✅ 射击目标先对齐主要头胸与真实朝向，再替换占位轮廓。** 选完整授权着装人物，按头中心、脚底等比换算到游戏单位；衣甲边缘不必逐顶点塞进胶囊，重点是玩家瞄准主要头胸不会明显打空。先读源相机或枪口的实际前向，再经原控制器和握持 socket 校正；只把控制器 Euler 设成“正视”可能仍带着局部旋转，让枪向上偏。一个可编辑姿态导出共用几何与面颜色，由 Three／CPU 各自投影并保留原掩体遮挡；实际接敌、命中、倒下都比过才接收。FPS 的肩肘、腰腿和胸前持枪因此更完整，但碎色护甲不如旧橙胸大色块醒目，远头仍小。后续按这套源的实际面色与部位聚合头盔／胸板的材料色族，两个后端共用且保留深布、枪和遮挡；正常图只证实浅头盔与背景的分离小幅改善，胸口碎色仍在，不能从调色数值推出发现率。这里只采用单姿态，移动滑移与整身倾倒仍要补动作，不能把带 rig 的源包当成运行端已接动画。

**跨体型先看手里有什么，不默认只能重做角色。** 已有 MHCLO 衣物先比较 MPFB 源端 refit；有源着装身体、对应骨骼与相近姿势，可 👀 比较 LoBoFit；只有 A/T 休息态衣服与目标人形，可 👀 比较 LUIVITON 的代理注册／模拟拟合。后两者是研究候选，不是现成通用衣橱：前者仍有穿插／逐帧闪烁及专利许可待核，后者不擅长硬甲／断开饰件，且初始合身未交付完整动作兼容。

**只有参考图的新角色，另比较联合生成，不先把静态生成＋自动绑定当唯一先进路线。** Rigel3D 联合生成形状、骨架与权重，再预测关节标签，但缺关节、极端姿势和标签歧义仍可能失败；不凭骨架指标升级为零手修默认。AI 可筛输入、整理候选及装配脚本，人验运动穿插、露肤、轮廓和目标动作；需要手工雕衣、补面或刷权重时，换完整体系或减少体型／槽位。

## 静态道具：原生低模与高密度源资产分开

### 实测：三种来源同提示、同机位（2026-10-28）

**规整的风格化件让 agent 写 Blender 脚本；需要质感和复杂形体的单件用 Hunyuan3D 3.1 Pro 再减面；Tripo P1 用在要快、直接进网页预算的道具上。** 四个资产（MOBA 防御塔、FPS 混凝土护栏、苔藓巨石组、四足小狼野怪）用同一句英文提示，分别交 Tripo P1、Hunyuan3D 3.1 Pro 文生 3D，以及 Kimi K3.1 Pro 只写 Blender `bpy` 脚本建模（每件最多三轮“写脚本—渲染—看图—修改”）。全部在同一 Blender 场景、同一相机与灯光下用 Cycles 渲染，再由没参与的审查者看打乱顺序的图逐行排序。

**局限**：每种做法每件只生成一次，提示为文生 3D、没有用概念图；评审是一位没参与的审查者，排序反映“正常游戏视角下好不好看、是否符合需求”。下一步用同一张概念图做图生 3D、贴图压缩后的体积与画面，再在一个案例里少量采用验证。


**✅ 已有认可几何且只差预算，先保源做误差受限简化，不默认从图片重生。** 保护轮廓、孔洞、细件、挂点与材质接缝；可见误差由玩法和目标相机决定，不为达面数强行越线。只有面组织确实妨碍后续编辑，才 🧪 比较形状条件重拓扑；它重新推断连接，不是无损转换。此顺序是保已接受内容的工程默认，不是同预算质量或成本冠军。

| 手里已有的内容／目的 | 当前选择 | 撤回条件 |
|---|---|---|
| 几何与外观已认可，只需降低交付预算 | 保母版，先用现有简化／LOD／烘焙；仅格式处理沿下文 Blender／gltfpack | 关键轮廓、孔洞或接口损失，回更保守设置或换合格源，不强减 |
| 形状已认可，但局部编辑需要更合理的面组织 | 比较以原几何为条件的重拓扑，保留旧源作对照 | 新裂缝、非流形连接、重叠面或法线朝向错误影响用途；修复须人工补面时换源 |
| 只有图片，缺可用几何 | 按预算试原生低模；确需近景细节再走高密度源及派生交付 | 隐藏面、薄件或功能孔洞反复错误，不用更多面数掩盖；回现成／参数化 |

2026-08 的 Meshy T2 论文把重拓扑与图片生成分开评估；2026-09 Alibaba TaoFlowForge 提供独立团队的同单图比较。两者不足以确认当前 T2.5 或完整零手修生产赢家，来源、输入差异与成本局限见 WP3 路线卡。现成合格源优先、场景模块与变形角色分流不变。

**重拓扑后重新验 UV、纹理、部件引用和交付，而非只看网格整齐。** Agent 可整理源／候选差异及预算，人验实际相机下的形状与风格；保留部件名不保证材质、skin 或挂点兼容。改 UV 须重新烘焙／贴图，出现连通但不合用途的面流仍撤回；下面的许可、导入器、碰撞和角色检查全部保留。

**🧪 新的单图／文本刚体需求先试 Meshy T2.5 灰模；已合格 T2 配方保持不变。** 同价且目标范围更宽，使它值得首试，不代表同预算质量已胜出。孔洞、细件或挂点仍失败，回已验 T2 或现成／参数化，不靠加面数掩盖。

**显式锁型号和面数预算。** Smart Topology 省略型号已转 T2.5，默认目标由 T2 的 4,000 升至 15,000；目标仍不是输出硬上限。两版的范围、多图限制、无效减面开关与 10 月 30 日旧接口退役，见 WP3 参数与迁移边界。

历史官方 cookbook 作者记录过 1,000 目标得到 1,096 triangles 的灰模，但没有公开对应 GLB；本轮只读取固定源码、记录及预览来源，没有独立复测网格。这个案例支持“验实际面数、先验灰模”，不证明 T2.5 效果、闭合拓扑或引擎发布质量。

**🧪 近景雕塑或复杂表面再走高密度源资产。** Meshy 7.1 与 Rodin 2.5 的细节路径保留作候选，最终仍要通过轮廓、贴图和预算检查；Rodin 默认 Raw/medium 目标 500,000 面，不是游戏交付规格。Tripo Studio 九月已发布 P2.0 与局部 Mesh Edit，但 API 的 `P2-20260801` 仍标 Preview；不要跨入口推断稳定性，quad／局部编辑也不等于变形与身份保留合格，不自动替换 P1。

成本按所有生成、淘汰、贴图、后处理和主动工时除以合格资产数。灰模、纹理／分辨率、remesh 分开计；Rodin 自动化另核 Business 套餐及配置报价冲突。具体 credits 和套餐只在 [WP3 动态表](../../../docs/research/2026-10-14-game-wp3-3d-assets.md#10-动态事实表限定补核)维护，不把不同品牌 credit 当同一货币，也不把 API 单价当整套生产成本。

## 植被成套供给：先选可改的风动源，不只选树形

**✅ 同作品的树、灌木与草，先选同风格、许可清楚且匹配目标风动消费者的资源族。** 同包不等于三类资源都齐全；树可用分枝运动，草可用简单摆动，不必统一成最复杂管线。只剩静态网格或“支持 Nanite”的标签，不保证第二次改近景、风向或密度仍可用。

**运行时调风，不等于补做风动源。** Unity 6.3 的 `.st9` 响应参数建立在 Modeler 已配置的风动上；Terrain 草不受 Wind Zone 控制。UE 的 SimpleGrassWind 是非定向摆动；5.8 Nanite Foliage／Dynamic Wind 仍为实验功能，后者需骨骼／分组数据，只有全局风、没有玩家／物体互动。以上不是通用碰撞能力的否定，不能据此替换已有合格管线。

**第二次需求先分三种代价。** 只改摆放数量或已有风响应，保源调参数；改树冠／枝条结构或超出已有响应的运动，先核源能否重导出并重核绑定；缺必要源时先比较下述源端恢复；恢复不合格、映射不明或要手工补权重，换源或明确收窄要求。保留旧资产 ID、场景引用与独立碰撞，变更风动不能挤掉覆盖／透明排序、LOD、阴影和目标设备预算检查。

**缺结构不等于只能换掉静态树，但恢复是候选，不是保证。** UE5.8 PVE 可从静态网格提取骨架，再由 Mesh Builder／Export 绑定骨架与风动数据；有叶模型须按材质区分树干，且不回收叶片实例，半径可能算错。它仍是实验功能，5.7 资产不能直接在 5.8 打开；保源图／网格和图配方，恢复要手修才合格就换源。

Witcher 4 技术演示与独立实时 GPU 树生成提供规模／参数化参照，不证明本作品零手修或整管线成本胜出。

**AI 只接已知格式的批处理与核对，不猜风动权重。** TreeIt 顶点色随 DBO／FBX 导出，但 RGBA 定义本轮未核；Firewatch 与 Crysis 已有不同通道含义，不能直接接同一 shader。近景表现与通行由人验，草／灌木分验，未运行模型或引擎。

## 减面、UV、LOD与碰撞：借成熟工具做小处理

**✅ 采用 Blender 无头 bpy 作为程序处理层。** 单位、轴向和部件用途已知时，可批量规范变换，调用原生 modifier、UV 展开／烘焙并导出；只需 glTF 简化、压缩时继续用 gltfpack，不强制绕行 Blender，也不为常规操作另造框架。

**✅ 先固定交付字节，再按“规范检查→实际加载器→游戏首绘”接收。** gltfpack 的量化／压缩会引入不同扩展，先核项目实际导入器和解码能力；Unity glTFast 的 meshopt 解码需要相应附加包，UE 导出扩展列表不能证明导入支持。未核清时保原文件和已支持路径，不先加压缩或换导入栈。

**实现起点：让 Agent 沿现有生成器、加载器和 View 补接线，不另造资产框架。**

| 接在哪一层 | 先做什么 | 接收看什么 |
|---|---|---|
| 导出文件 | 保存可重建源、许可、导出设置；对实际 GLB 跑 Khronos Validator | 扩展声明、顶点格式与对齐；修生成器再导出，不能只改 manifest |
| 目标加载器 | 锁源提交、SHA-256 和字节数，核实际收到的 payload 后解析；读取加载后层级 | extras 在实际承载对象上；FPS 的包元数据／`restMount` 在 `gltf.scene.userData`，节点名可能带后缀，已知子节点须唯一匹配，缺失／歧义就退回 |
| 游戏消费者 | 整套所需件校验、解码及节点／动作合同均通过才置 `ready`；消费者整套挂接并完成一次实际 `View.render` 才置 `active`，reset／dispose 清除该标记 | 状态与实际角色／武器画面一致，再走开火、换弹、结算与重开；保原碰撞、导航和玩法权威 |

**角色替换沿原动作与资源所有者接入。** 武器根后坐／下压、弹匣、枪机与支撑手共用原 `weaponPose`，不再叠这些部位的源 clip；叫 `support-hand` 的网格也可能合并了袖子，先核几何合同。FPS 候选只在精确匹配旧袖三角形后排除其绘制，保留[既有袖形与腕端求解](animation.md#第四步换弹手离开枪是动作的一部分)，这是固定源适配，不是通用切件。每个 View 独占一套资源模板、供本 View 的敌人实例共享；加载换代或 View 退出撤接收资格并释放迟到成功，局内重开保留加载状态（已 `ready` 则仍为 `ready`），只拆实例、清首绘标记；替换模板或 View 最终退出时才释放旧模板。沿[取消与所有权](../04-client-modules.md#场景切换取消等待不等于取消工作)实现，任一件失败保留完整旧角色。

**FPS 的实际失败说明三层不能合并。** 初版四件 GLB 能被 Three 读取，Khronos Validator 仍报 48 项错误；源端补齐 `KHR_mesh_quantization` 的 used／required 声明，并把 `NORMAL`／`COLOR_0` 的量化 VEC3 每元素补到 4 字节 stride 后，四件均为 0 error／0 warning。运行候选原样消费其中两件 CC0 GLB，用 Three `0.186.1` 的 `GLTFLoader`，没有新增解码器。

**何时不照搬：** 换源、网格结构或导入器后重核节点／袖形合同；不匹配就换合格分件或保完整旧表示，不按名称猜部件。此候选已在云端原生浏览器 WebGL2 中看到手臂、武器和敌人，并走过开火／换弹、一次败局、下一局与重开；默认 main／网站 v12 未变。完整 headless smoke、硬件 GPU 身份、同机位画面对比、声音、逐帧手感与品质盲判仍未验证。

**验最终文件，不验“成功”日志。** Blender Collapse 的比例按三角面计算，不是顶点硬上限；逐个 mesh 处理后，检查导出文件的三角面、实际顶点、贴图和材质预算。平面硬表面的 Planar 可限制材质／UV 接缝处消边，但这些 delimit 选项不能当成 Collapse 的保证。现成 Shards 脚本只有近似顶点目标，VAT 还含占位输出，适合借调用机制，不原样当完整管线。

**✅ 路缘或屋顶单侧消失，先查三角形绕序，再调光。** 顶点法线供光照使用，正反面剔除取决于顶点绕序；只翻法线，不会把背面变成正面。让 Agent 在原生成函数中取一个实际坏面，固定相机、材质和变换，分别检查索引、法线与负缩放／坐标转换；临时开 `DoubleSide` 可辅助定位，但不能作为错误绕序的交付修法，也不靠加环境光掩盖缺面。

实际起点是 Star-Rush 的 `race.js::quad`：原函数把向下的法线翻向上，却保留原索引。修正只在同一 `flip` 分支把 `[0,1,2,0,2,3]` 换为 `[0,2,1,0,3,2]`，竖直面保作者顺序。沿配套测试检查真实左右路缘（含坡度）、屋顶斜面和竖直面：在本例局部坐标下，对非退化三角形计算 `(p1-p0)×(p2-p0)`，应与该硬表面的存储法线同向；再核顶点属性与场景变换未变，并用实际单面材质同相机复看。已发布版本在固定六块场景的 144,508 个三角形中仅反转 500 个，全部顶点属性／材质／变换保留，真实 Three 画面恢复左路缘与屋顶表面；这不是阴影条纹或整体赛车品质已解决。

这条索引替换只适用于本例已约定朝上的平面／硬表面，不能把所有面强制朝上；曲面平滑法线、镜像变换和不同导入器要按各自约定检查。双面薄片确有用途时可保双面材质。本案只跑 Web；迁到 Unity／UE，先按目标版本官方文档核手系、正面绕序和导入转换，再做单面三角形小样，不能直接照搬 Three 的索引规则。

**本项来源与范围（2026-10-26）：** [已采用源码与测试](https://github.com/dbvv1/Star-Rush-Reborn/commit/e8f119e7c7a3db951ff06d82f955702d622e0437)，实际同相机 Web 对照；[Three 材质正反面](https://threejs.org/docs/pages/Material.html#side)、[Unity 网格索引](https://docs.unity3d.com/Manual/mesh-index-data.html)、[UE 坐标系与导入轴向](https://dev.epicgames.com/documentation/en-us/unreal-engine/coordinate-system-and-spaces-in-unreal-engine)为迁移核对入口，未运行 Unity／UE。

**压缩后能加载，还要核动作时间。** 本仓用官方无贴图 RiggedSimple 实跑 gltfpack 1.3 与 Three r186／r182 加载器：EXT／KHR 都能在新消费者解码，但默认重采样使本例 clip 多约 25ms；单加 `-af 0` 恢复原时长并保两轮改色／改时长。本例 r182 识别 EXT、不识别 KHR，真实 fallback 另带体积成本；保已兼容 EXT，不只为 KHR 名称迁移。复跑入口见[可复跑小样](../../../experiments/p123-meshopt-consumer.md)，交付判据见本节末；只验 CPU 加载／采样，不是画质通过。

**✅ 蒙皮角色按“作者源→规范检查→实际消费者”接收，整角色移动时一起带上骨架。** 保留生成配方／脚本、可编辑工程、导出设置和许可，把 GLB 作为可重建的运行产物；不要把优化后的 GLB 反当唯一作者源。[原创角色制作起点](animation.md#第二次修改决定是否留下)已用同一源完成长刃二改。导入后先播放动作，再对同时包含 mesh 与骨架的角色根施加整体变换；只移动 mesh 不是整角色移动，蒙皮还取决于关节和绑定矩阵。

**遇到 `NODE_SKINNED_MESH_NON_ROOT`，先验目标加载器怎样带动顶点和骨骼，不为清警告直接拆层级。** Beacon Guard 三个 GLB 在固定 Validator `2.0.0-dev.3.10` 中均为 0 error，但仍有 25／26／25 个该 warning；这不是模型品质通过。

用 Three `0.186.1` 实际加载后，整 `gltf.scene` 平移／等比缩放的 3 变体×3 动作固定时刻，全部蒙皮顶点和 15 根骨骼都符合独立坐标预期；故意只变换 mesh 的反例失败。因此这组资产可保现有导出，继续目标消费者接入；其他警告仍逐项判断，换加载器、非等比缩放及正式游戏行为另验。

需要多单位时，沿[独立实例与快照消费者](animation.md#multiunit-animation-consumer)共享几何／clip，分开骨架、混合器与需独立改色的材质，再区分逻辑同步、绘制插值和释放。正式采用已收敛到前面的 [MOBA 成套资源起点](#moba-battle-supply)：复用十五骨骼五动作合同、替换人物轮廓并在真实交战中核接入；早期 Node 顶点／骨骼数值检查仍用于定位结构问题，不替代运行画面。

**保住第二次修改所需的身份。** gltfpack 默认会合并 mesh、裁剪节点并删除部分元数据；需外部操控的节点、材质和 extras 分别核 `-kn/-km/-ke`，再查输出。Meshy 条款禁止删改输出中的 AI 标识；未知扩展或自定义属性仍可能被处理器丢弃，不能认为 `-ke` 包办保留。

**✅ 减面解决预算，重拓扑解决面组织，UV 解决表面参数化，三者分别验收。** 优先借 meshoptimizer／gltfpack 等已有处理，误差预算不足时允许达不到面数目标；不要为了数字达标无条件损伤轮廓。保 UV 接缝与硬边会限制简化幅度，放宽边界也会改变外观。

无可用 UV 时可评估 xatlas；重建 UV 后重新烘焙或贴图，旧纹理与像素 mask 不能直接沿用。新原生拓扑模型 LATO.2 仍缺完整 UV／纹理／材质，2026-10 的 MeshQuery 研究也将人工 UV 精修放在范围外；不为“Agent 自动展开”另造完整框架。

LOD 按视距和屏幕误差选，核轮廓、孔洞、材质接缝与挂点；固定 50%／25% 只是候选比例。实际顶点数可能因法线／UV 接缝增加，低面数不代表低内存；角色 LOD 还要单独核 skin 和 morph。

**✅ 碰撞代理独立于可见网格。** 动态物件先用 box、sphere、capsule 或少量 compound；确需凹结构时再评估现成凸分解。洞能否穿过、门能否打开和代理精度由玩法决定。

**先选实际暴露预算控制的接口。** CoACD 主分支 Python／CLI 需启用 `decimate`，每包最大顶点值才生效；已核 Unity 包不含该控制，需限顶点时 👀 评估主分支离线处理，不能照搬参数。限制凸包数量需 `merge`，可能牺牲凹度误差且仍达不到目标包数。

Unity 6.3 文档写的是 255 triangles，不能把 CoACD 默认 256 vertices 当作同一限制；分别核最终每包顶点、三角面、包数与目标引擎 cooking。UE 可 🧪 先比较原生 Auto Convex，但其 API 会移除既有碰撞，须先保留原资产／碰撞。若压预算破坏关键孔洞或接触轮廓，退回简单代理或换资产。

**已有 GPU 且复杂凹网格的分解吞吐成为瓶颈时，才 👀 比较 CuACD。** 其预编译运行不需 CUDA toolkit／PyTorch，但仍需 NVIDIA GPU／驱动；LGPL 许可不能沿用 CoACD 的 MIT。论文计时排除预处理，也没有每包顶点／三角预算保证，须把冷启动、显存、导出和引擎验收计入整轮成本。小批保成熟 CPU／原生流程，简单代理不升级。

**局限：自动处理能降低规格不匹配，不能保证修好错误轮廓、缺失结构或关节变形。**

## 材质与风格：有贴图不等于可重新打光

**先分清 base color 中的烘焙阴影、roughness／smoothness、法线方向与通道打包，再判断能否重新打光；PBR 文件齐全不等于同一物理表面。** Meshy 7.1 不输出 emission，部分旧参数虽被接受却被忽略，不能照搬旧模型配方。

输入去背、纹理 alpha、输出透明材质是三件事。TRELLIS.2 默认 GLB 为 OPAQUE，改材质连接可能恢复透明，却不能补玻璃几何和折射；已有合格叶片／头发 cards 重叠出错，先核[覆盖与半透明表达](materials.md#叶片与毛发重叠出错先分覆盖与半透明)；内容持续失败时，仍优先同风格现成资源或不透明几何，并接受外观限制。

**✅ 风格先靠同套源与材质配方；形体已认可，别为换外观整物重生。** 只改色、粗糙度或已有磨损参数，继续改原材质。需要新参考纹样时，🧪 先沿 Meshy 7 保 UV 重贴图入口试同一网格；这是兼顾现有契约的首试，不是质量冠军。图中结构与网格不符时先解决形状／相机对应，不用换贴图模型掩盖。

Meshy 2026-09 同网格自评中，几家当前纹理模型差距较小、优势指标不同；独立团队 SUPRA-Tex 2026-10 论文比较显式表面观测与其他贴图方法，支持把参考外观保真作为独立选择。两者都不证明保原资产身份或商用完整赢家；SUPRA-Tex 发布适配器限非商业研究，导出还会重建网格／UV，只作研究标尺，不替换商用默认。

**先验文字／纹样位置，再验背面接续与换灯表现。** 正面像参考不等于隐藏面连续，也不等于反光材质正确。Agent 可固定同源对照、整理通道与引用差异，人判断目标相机下的可读性及新旧资源混排；关键标记反复失真或必须手绘修补，换授权合格纹理源／收窄外观。把淘汰、补参考、重新烘焙和旧 mask 迁移纳入成本，不以论文单阶段秒数代表交付总投入。

**✅ 已有像素 mask、分件或换装引用时，先保结构再换纹理。** Meshy Retexture 的 `enable_original_uv` 默认 false；需要复用有效旧 UV 时显式设 true，但它不承诺材质槽、节点、skin 全部保留。Hunyuan3D-2.1 的指定 Paint 实现即使关闭 remesh，仍重展 UV，并通过单对象／单材质 OBJ 路径导出；不拿它覆写已有交互或换装资产。输出的 UV、部件与材质对应不满足旧引用时，退回原网格的材质参数修改，或接受重新烘焙／适配的成本。

**局限：保 UV 开关是接口承诺，未证明实际输出或 Unity／Unreal 导入后身份不变。**

## 场景与角色：不沿用静态道具的成功标准

### 完整场景：先做一个可玩片段，不先补满资产表

完整流程、三条供给路线、首片段验收与第二改已上移到[完整片段](#完整片段先做一个能走能看能改的场景)与[第二改](#第二改傍晚打开视线保留使用空间)。本节只保留场景扩展到建筑族、有限背景和角色供给的边界，避免同一流程维护两份。

**已试一条可回流的作者环节：直接取原游戏几何，不在 DCC 另搭相似概念景。** Star-Rush CPU 作者试验保存并重开原路段、核对象与变换，再缩小一棵树：站台露出更多，却不足以采用，保留原场景。读者可借“原源→作者视点→局部差异→原参数”的方法；Blender 离线参考不是游戏截图，真实 WebGL 与移动验收仍沿原路段方案。

### 已有建筑结构与有限背景的供给

**✅ 已有可玩布局，要扩同风格建筑族，先保占地、墙与门窗，再换外观层。** 默认复用合格库内件、部件组合和墙／屋顶材质搭配；只为缺件生成可替换候选。尺寸或拓扑也要变时，回已有参数配方修改布局。这是保已认可内容的工程默认，不是已经测得成本最低。

近期 ProxyBuild 把预分槽壳体映射到有限模块库，独立团队 ShellMaker 比较已知墙／开口骨架上的外观补全。它们支持把结构约束与视觉风格分开，未证明整族零手修赢家；ShellMaker 的结构指标较强，但风格并非全面领先，复杂部件仍可能畸形或交叠。

**👀 不直接用 ShellMaker 发布 GLB 覆盖原玩法壳。** 已核代码会重建墙并将场景居中、最长包围盒边缩至 1，缓存也未完整绑定风格／模型；论文保形不等于原米制、枢轴和引用保留。Agent 可整理部件、材质搭配及装配差异，人验新旧混排、通行与实际相机；原坐标／接口丢失或缺件须手修，退回合格库内件或收窄风格。代码、模型、源资产分别清权，库准备与淘汰返工计入投入。

**🧪 缺室内作者源时，可以先用 Infinigen 2 生成一间，再保源局部修改。** 固定 `2.0.0a3` 已在 CPU 上生成带家具／材质的客厅、保存并重开 `.blend`、渲染；沙发与三个独立抱枕一起后移 0.35 米后，其余对象的变换、网格与材质引用保留。把需要一起移动的部件编成项目自己的组，不靠重新抽 seed 实现“只改沙发”。

这条路线提供可改的场景源；**密度先在保存前控**：本例只降低共享抱枕的作者细分，保存网格去重顶点由约 98 万降到 10 万，其余对象与沙发组二改保留。

仍需另验材质烘焙、目标轮廓、碰撞与运行消费者；保存顶点不是运行总三角，整景导出也尚未跑通，不能替代前面的模块场景默认。实际入口与导出结果集中见 WP3；本轮未验目标引擎和可玩通行。

Marble 的 splat、collider 与高质量 mesh 用途不同；🧪 Pro 可作交互弱、有限视点的背景候选。合同将 Standard 也定义为付费，导出页却把商用列 Pro，故不默认用 Standard 发行；免费旧输出也不因升级追溯取得付费权利。若要开门、拾取、破坏或第二次改布局时隔离影响，默认仍用模块 mesh。WorldAct 等研究专门补对象分解和背景修复，也仍有动态／关节物体与物理属性限制。

**✅ 变形角色优先既有拓扑、骨架与兼容动作。** 自动 rig 成功、T/A-pose 和 quad 都不能代替肘膝、肩、面部与动作接触验收；比例或衣服改变后重验 skin、挂点和动画。TRELLIS.2／LATO.2 推荐安装包含需单独核商业权利的依赖，Hunyuan3D-2.1 输出受地域限制，不能作为全球商用免费默认。

## 装饰改成交互：先选运动结构，再换外观

**✅ 第二次要开门、掀盖或扩大通道时，先保门框／门扇、运动轴与碰撞，再决定换哪块可见网格。** 完整片段里的那件可交互物件按这里选结构。“有多个 mesh”只说明可分对象，不说明绕哪转、开到哪里或角色能否穿过。Kenney Modular Dungeon Kit 2.1 的指定门 GLB 已交付父子节点和作用于门扇的旋转动画数据，可作为结构起点；同包的静态 gate 文件却没有动画，不能把整个包都当可开合成品。

**🧪 自动切件只用于它实际交付的边界。** Meshy Auto Split 面向打印，会封口／加固薄区、丢弃部分碎片且不保原纹理；它的分件输出不承诺游戏铰链、关节限位或碰撞。需要精确接口时，保留已知结构并换外观，或借明确参数化配方；这不否定该服务生成静态装饰的用途。

程序化也要选对导出路径：Infinigen 的单资产关节导出定义连接关系、轴与范围，并有独立碰撞分支（须关闭 `visual_only`）；整场景 USD 导出却明确不带 articulation。可借这种结构分离，不直接采用该固定导出器（其惯量代码另有静态可见类型问题），也不把“能导 USD”当成可交互资产保证；可开合刚体也不等于变形角色，后者仍须保存 skin／morph 与兼容动作。

**局限：上述文件数据与源码只确认输出契约，没有验证目标引擎播放、碰撞通行或改尺寸后的运行表现。**

## 第二次修改决定是否留下这条路线

完整需求示例（傍晚＋打开视线＋保留使用空间）见[第二改](#第二改傍晚打开视线保留使用空间)；下面是局部改件的通用分诊。

**✅ 已分件刚体只改局部时，先让 Agent 定向改件，不默认整物再生成。** EditHero（Yu、Tsai 等，2026-10-01）在同一连续修改子集比较代码改件与生成编辑：前者更能保住未改部分，但复杂新增／替换形状仍弱。它提供目标视图且输入已分件，不是普通文字指令就能做成游戏资产的证明。Agent 负责定位、修改和差异检查，人看新增形状及新旧混排；部件无法可靠定位或形状不合格时，换合法兼容件／生成补缺，不覆盖已接受的整物。下列 UV、挂点、碰撞、预算和许可检查不变。

- **换颜色／磨损：** 先保 mesh 和 UV 改材质；重贴图后核实际 UV、材质槽和资源引用，不假定只改了像素。
- **改尺寸／让箱盖打开：** 先用上节已有运动结构；只换外观时保连接坐标约定，改尺寸时按参数重建／重核连接位置，再验开合空间与碰撞代理。整体重生或自动切件不代替铰链和限位。
- **换衣／比例：** 优先同体系部件；重生网格后不能沿用旧 skin、morph 和挂点验收结果。
- **保留身份：** 保存采用源、模型版本、参数、许可与任务 ID；在原引擎资产身份下替换可见部分，把碰撞、挂点和玩法组件留在稳定封装中。故障先分生成、后处理、导入／运行时，再决定重生。

**适用边界：** EditHero 等生成／改件能力仍据源码、论文与作者记录；本页已实做的 [MOBA 地表二改](#moba-battle-supply)证明了明确所有权、保其余资产与运行复拍的接法，不能推出任意生成刚体或变形角色都能无损局部编辑。
